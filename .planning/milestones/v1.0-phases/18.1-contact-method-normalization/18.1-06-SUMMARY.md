### The bug and its fix

The direct Restore button called `expo-document-picker` (`ACTION_OPEN_DOCUMENT`), which left
this Pixel's DocumentsUI on a blank, non-responsive `PickActivity`. Investigation (see
`.planning/debug/resolved/restore-document-picker-blank.md`) eliminated MIME shape,
orientation, a separate bridge task, and `EXTRA_ALLOW_MULTIPLE`. `ACTION_GET_CONTENT` — the
one untried lever — reproduced the identical blank hang, resolving to the same DocumentsUI
`PickActivity`, which isolated the fault to **this device's DocumentsUI** (RefreshTask
`NullPointerException: name`). `adb shell pm clear com.google.android.documentsui` reset it
and the picker rendered immediately.

The durable app-level change keeps the direct button on the correct code path
(`pickBackupDocument()` launches `ACTION_GET_CONTENT` in Orbit's task so the activity result
is still delivered) and retains the narrow Files -> Share -> Orbit JSON receiver as a
resilient fallback for any device whose DocumentsUI is unhealthy.

## Deviations

- `run-as` DB-query verification (e.g. `canonical_region` survival on Replace-all) was not
  re-run here: the installed artifact is a non-debuggable release build. Those DB invariants
  were covered by the earlier on-device migration pass and the green node suite
  (`restore-apply`, 18.1-04). The merge/restore round-trip was verified UI-observably.
- The checkpoint's literal expectation that a merge would flip Ada's primary to
  `312 555 6789` does not hold under merge's newer-local-wins policy with an older backup;
  that outcome belongs to a Replace-all restore. The safety invariant (unique-safe merge on a
  changed primary) is what this case proves, and it passed.
