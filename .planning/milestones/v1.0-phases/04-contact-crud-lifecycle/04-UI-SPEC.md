# Phase 4 — UI Design Contract

> Visual and interaction contract for Contact CRUD & Lifecycle. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Ground truth for tokens/typography/spacing is the existing codebase (`src/theme/`, `src/components/field-widgets/`, `src/screens/`). This spec pins the *new* surfaces to those established patterns — it does not invent a parallel system.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (React Native / Expo — shadcn is DOM/Tailwind-only and does not apply) |
| Preset | not applicable |
| Component library | none — hand-built RN primitives (`TextInput`, `Pressable`, `Modal`, `FlatList`, `ScrollView`) over the project theme-token system (`src/theme/`) |
| Icon library | none installed — existing surfaces use text affordances ("Back", "Up", "Edit"). This phase introduces two icon-shaped affordances (overflow `⋯`, link remove `✕`) rendered as **text glyphs**, not an icon package. Do NOT add an icon dependency this phase. |
| Font | System default (no custom font loaded; none declared in `app.config.ts`) |

**shadcn gate:** not run. This is a React Native app; shadcn targets the web DOM + Tailwind and cannot render RN `View`/`TextInput`. The design system is the in-repo theme-token module (`FND-05`), enforced by the `npm run check:colors` gate. `Registry Safety` below is therefore not applicable.

**Colour rule (non-negotiable, enforced):** every colour resolves through `useTheme().colors.*`. No hex/rgb literal may appear outside `src/theme/theme-presets.ts`. `npm run check:colors` fails the build on any literal, **including inside Skia draw calls**. This spec names colours only as tokens.

## Spacing Scale

Declared values (multiples of 4), matching the values already in use across `CustomFieldsScreen`, `HomeScreen`, and the field widgets:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Tight inline gaps |
| sm | 8px | Compact element spacing, action-row gaps, screen-root gap |
| md | 12px | Default: row gap, card `gap`, input `paddingHorizontal`, action gaps (the codebase's dominant rhythm unit) |
| lg | 16px | Screen `contentContainer` padding, primary-button horizontal padding, section padding |
| xl | 24px | Section breaks, header-to-list separation, modal horizontal inset |
| 2xl | 32px | Major layout gaps (profile header block → body) |
| 3xl | 48px | Page-level vertical rhythm on tall/empty screens |

Component-internal metrics (already established — reuse exactly, do not re-derive):

| Element | Value |
|---------|-------|
| Input / trigger `borderRadius` | 8px |
| Card / row `borderRadius` | 10px |
| Modal sheet `borderRadius` | 12px |
| Input `paddingHorizontal` / `paddingVertical` | 12 / 10 |
| Primary button `paddingHorizontal` / `paddingVertical` | 16 / 12 |
| Card/row `padding` | 12px |
| Border width | 1px (hairline `StyleSheet.hairlineWidth` for intra-list dividers only) |

**Exceptions:**
- **44px minimum touch target** for icon-only / glyph controls (overflow `⋯` menu trigger, per-link remove `✕`, segmented-control segments). The visual glyph stays small; the `Pressable` hit area (via `hitSlop` or min height/width) must reach 44px. This overrides the existing `iconBtn` padding (12/8), which is below target for a bare glyph.
- **2px** micro-gap allowed inside a stacked label+value pair (`rowMain` uses `gap: 2` today) — sub-grid, not layout spacing.

## Typography

Roles mapped to the sizes/weights already shipping (24/16/15/13; weights 400/600/700). Line-heights are prescribed where the existing code left them implicit.

| Role | Size | Weight | Line Height | Applied to |
|------|------|--------|-------------|-----------|
| Display | 24px | 700 | 1.2 (~29px) | Screen titles ("New contact", "Edit contact", "Archived", profile name in header) |
| Heading | 16px | 600 | 1.3 (~21px) | Field group labels, primary button text, row/list-item primary label, tri-state segment labels |
| Body | 15px | 400 | 1.5 (~22px) | `TextInput` value text, helper/descriptive copy, link URL text, impact-summary body |
| Label | 13px | 600 | 1.4 (~18px) | Meta lines (field type, "quarantined · text"), section headings (uppercase, `letterSpacing: 0.5`), input field labels, "Rarely responds · attempts don't reset the orbit" |

**Weight policy:** the working pair is **regular 400** + **semibold 600**. **Bold 700 is reserved for Display-role screen/section titles only** (matches `CustomFieldsScreen` title `700` and `HomeScreen` hero `700`) — do not introduce 700 on buttons, rows, or body copy. The app hero at 32px in `HomeScreen` is the shell splash and is out of scope for this phase's screens (do not reuse 32px for contact surfaces).

## Color

Palette is the shipped `space-dark` preset (dark-first; `theme-presets.ts`). The 60/30/10 split maps onto the existing tokens:

| Role | Token → value | Usage |
|------|---------------|-------|
| Dominant (60%) | `background` → `#0B0E1A` | Screen background on every Phase-4 surface |
| Secondary (30%) | `surface` → `#141828`, `surfaceElevated` → `#1D2235` | Cards, list rows, inputs/triggers (`surface`); modals, dropdown sheets, the purge-confirm sheet, overflow menu (`surfaceElevated`) |
| Accent (10%) | `accent` → `#6C8CFF` | See reserved-for list |
| Text | `textPrimary` → `#E6E9F5`, `textSecondary` → `#8B93B0` | Primary content vs. meta/placeholder/muted |
| Structure | `border` → `#2A3048`, `borderStrong` → `#3C4568` | Default vs. emphasized borders |
| **Destructive (NEW)** | `danger` = **`#E5484D`** ✅ owner-approved 2026-08-14 | Purge "Delete permanently" button, duplicate-name/validation warning emphasis |

**Accent reserved for (explicit — never "all interactive elements"):**
- The single **primary submit button fill** on the create form and edit form ("Save contact" / "Save changes"), text on it in `background`.
- The **selected segment** of the last-spoke tri-state control — *except* the "Not yet" segment (see below).
- **Selected state** in native/custom pickers and the links editor (selected dropdown option text, active input focus border).
- **Text-link affordances** that are safe/reversible: "Edit", "Restore", "+ Add link", "Add details".

Accent is NOT used for: destructive actions, the "Not yet" segment, plain rows, borders on inactive controls, or the overflow `⋯` trigger (low-emphasis, `textSecondary`).

### ✅ Resolved — add a `danger` token = `#E5484D` (owner-approved 2026-08-14)

**There is no destructive/danger token in the palette today.** `ThemePalette` has 8 tokens; none is red/destructive. Phase 3 deliberately deferred this: its tap-to-fix error emphasis was *composed* from `accent` + `borderStrong` because no dedicated token existed (STATE.md: *"Tap-to-fix error emphasis composed from accent+borderStrong; no dedicated error token yet — owner may add at --to 3 gate"*).

Phase 4 is where a real one is warranted, because it introduces:
1. The **"Delete permanently"** purge button — CONTEXT.md Area 1 explicitly requires *"destructive/red styling via a theme danger token."* Composing red out of `accent` (a blue) is not possible; `accent`-blue cannot read as danger.
2. A **duplicate-name warning** and **validation errors** (future-date, bad interval) that want a consistent non-accent emphasis.

**Recommendation:** add a `danger` token to `ThemePalette` (and `space-dark.dark`). Recommended value `#E5484D` (a desaturated red that sits with the space-dark palette); the owner owns the final value as a taste call. If a foreground-on-danger contrast pairing is needed for a filled button, the button text may use `textPrimary` (`#E6E9F5`) over `danger` — verify contrast at implementation; otherwise use `danger` as text/border on a `surfaceElevated` fill.

**Scope note:** the *native* `Alert.alert` confirm can keep RN's built-in `style: "destructive"` (OS-rendered red, no token needed) — as `CustomFieldsScreen` already does. The `danger` token is required only for **in-app** rendered elements (the "Delete permanently" button on the Archived list and any inline warning text), which `check:colors` governs. This is a palette-contract change → **owner decision**; the executor should not invent a hex inline.

## Screen & Interaction Contracts

### Create-contact form (CRUD-01, CRUD-02)
- **Fixed block first, custom block after** (never interleaved). Fixed order: **Name → Category → Frequency → Last-spoke (tri-state) → Phone**. Then `show_on_new AND NOT quarantined` custom fields.
- **Name** is the only `required` field. Submit disabled/blocked only on empty name; everything else optional.
- **Tri-state last-spoke** default = **"Today"**. "Not yet" is **visually distinct** (muted: `textSecondary` text, `borderStrong` border, **not** accent-filled) so the never-contacted/backlog case reads honestly. "Not yet" → writes contact row with `NULL last_contact`, **no** interaction row. "Today"/"Pick date" → writes an interaction row through the single-writer DAO (`source='manual'`, `direction=null`); future dates rejected at entry.
- **Duplicate-name warning fires on save** (not per keystroke), non-blocking, "save anyway" path.
- Primary CTA: **"Save contact"** (accent fill, `background` text).

### Edit-contact form (CRUD-03, CRUD-04)
- Shows **every non-quarantined field** + dedicated **phone** / **email** inputs + the **links area** + **"Rarely responds"** and **"Turn off reminders"** toggles + birthday (with "Year unknown").
- Initial values assembled by JOIN of `contacts` + custom-values row + `category_id`→label (delegated to §14.10 layer — planner detail; UI just binds).
- Same duplicate-name-on-save warning, symmetric with create.
- Primary CTA: **"Save changes"**.

### Name-only refine path (capture → profile)
- A capture-created name-only contact shows a prominent **"Add details"** affordance on its profile → opens the **full edit form**, surfacing **frequency + last-spoke + phone first** (they drive the decay→SMS loop). No separate slim mini-form.

### Contact links editor (CRUD-04)
- Repeatable rows in insertion order; optional label (unlabelled → show host/URL). Add / edit / remove only (no reorder UI in v1). Each row tappable to open as a web URL; open failures show "Couldn't open this link." `phone`/`email` keep their own `tel:`/`mailto:` dedicated inputs (not part of the links list).

### Lifecycle surfaces (CRUD-05, CRUD-06)
- **Archive**: lives in a **low-emphasis overflow (`⋯`) menu** on the profile header — never one tap from purge. Archiving hides the contact everywhere; reversible.
- **Archived contacts list**: lives **in Settings** as a distinct low-traffic row, **no count badge** (the screen states its count when opened). Hosts **Restore** and **Delete permanently** — purge exists *only* here (two-stage by construction).
- **Purge**: **"Delete permanently"** in `danger` styling → the impact-summary single-confirm (no name typing). Deletes contact + interactions + events + fuel + custom values + `contact_links` + photo file + scheduled notifications in one transaction.
- **Never-contacted and Archived are separate homes** — never merged.

### Settings surface (relocation)
- Phase 4 introduces the real navigation shell and relocates into Settings: **Custom Fields** (from `HomeScreen`'s dependency-free route), the **Reachability** route (from the Phase-3 `HomeScreen` `useState`), and the new **Archived contacts** row.
