## Phase Goal

**As a** person tending my relationships, **I want to** add, edit, archive, and permanently delete the people I track, **so that** my orbit only holds people I still care about and their details stay right.

**This slice (Plan 02):** the data layer for creating a contact. MVP-wise this is the failing-test-first end-to-end path proven headless via `node:sqlite` — the create-form UI (Plans 03–04) then makes it user-reachable. After this plan, `createContactFull` atomically creates a contact + first interaction + custom values, and the shared reads the forms need exist.

<objective>
Build the composed atomic-create core (RESEARCH Pattern 2 — the phase's central architectural task) plus the shared read helpers the create/edit forms need. This is TDD: the tests describe the atomicity + single-writer + not-yet behaviours first, then the cores make them pass.

Purpose: CRUD-01/02 require contact + interaction + `show_on_new` custom values to be written atomically, but the existing `createContactWithInteraction` and `upsertValue` each wrap their own `inWriteTransaction`, and the shared mutex is NON-reentrant — naively composing them is a permanent hang (Pitfall 1 / the HIGH-1 lesson). The fix is the established core/wrapper split.
Output: `contacts-dao.ts` (`createContactFull`), `contact-read.ts` (`isDuplicateName`, `listCategories`, `getContactHeader`), and extracted non-mutexed cores in the two existing DAOs — with their existing wrapped exports left unchanged for standalone callers.
</objective>
