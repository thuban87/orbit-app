# Cross-AI Plan Review — Phase 19.1

## Consensus Summary

Both source-grounded reviewers (Codex, Cursor) independently verified the plans against
the actual repo and agree the phase is architecturally sound, unusually well grounded in
`file:line` evidence, correctly waved (01∥02 → 03 → 04 → 05), and migration-free. Both
conclude the phase achieves IMP-01 for Android ≤16 **if executed as written and plan-05
device UAT passes**, with API-37 system-picker behavior correctly deferred out of scope.
Overall risk from both lanes: **MEDIUM-HIGH** (Codex: "HIGH until Plans 02–04 are
amended"; Cursor: "MEDIUM-HIGH"), driven by one-way native/manifest changes, OEM
permission variance, and device-gated acceptance — not by architectural flaws.

### Agreed Strengths

- Accurate, verified defect targeting: 17+ reader swallows read errors and assigns any
  Event as birthday; nameless bulk rows marked `failed`; `runImportBatch` never finalizes;
  review screen seeds birthday from `mapped.birthday` only; already-linked single-import
  dead-end. Both reviewers confirmed these against disk.
- Fixed, picker-agnostic integration boundary (`PickedContact[]` → `routePickedImport`)
  consistent with ADR-002; downstream pipeline stays unchanged.
- Sound wave/dependency ordering and migration discipline (no new migration; `skipped`
  already terminal; `source_payload`/`TARGET_VERSION 12` reuse verified).
- Strong local-first/security posture: no egress, scoped `maxSdkVersion` permission, PII
  logging prohibitions.
- Plan 05 device-UAT gate correctly separates manifest-packaging evidence (grep) from
  API-37 runtime permission state (`dumpsys`), with a deterministic revoke-after-summary
  D-14 test and a human `autonomous: false` sign-off.

### Agreed Concerns

- **HIGH (both) — Plan 02 photo-staging skip is internally contradictory.** Photos are
  staged in `acceptPickedContacts()` (`import-acquire.ts:69` / `:76-85`) *before* the row
  exists and before `importRowAsNew()` runs, and `importRowAsNew` has no `stageImportPhoto`
  call. The plan's "PREFERRED driver-side skip in `importRowAsNew`" therefore cannot
  prevent staging that already happened, and would ship orphaned PII in staging if executed
  literally. Both require a **mode-gated skip in `acceptPickedContacts`**
  (`options.mode === "bulk" && mapped.nameRequired`) or explicit post-skip cleanup of the
  staged file + `photo_rel_path`; the driver-side-only path must be demoted as insufficient.
- **HIGH/MEDIUM (both) — Plan 04 permission-persistence exemplar is mis-cited.** The plan
  says to "mirror the notifications ask-once persistence pattern," but
  `src/services/notifications/permission.ts` caches **no** state (fresh OS read every call).
  There is no existing permission-persistence pattern in-repo, and the plan names no
  concrete storage, key, or failure behavior for the durable permanent-denial verdict. Both
  recommend an explicit choice (e.g. an AsyncStorage boolean written only after
  `NEVER_ASK_AGAIN`, cleared on a fresh granted check), plus clarifying whether the D-11c
  "priming shown" flag is session-only or persisted.

### Divergent Views

- **Plan 03 selected-name-only import path.** Codex raises this as **HIGH**: the browse
  summary is fixed via the two-query design, but the *selected-key full reader* is described
  as a `Data`-table `LOOKUP_KEY IN (...)` query, and a name-only contact has no
  phone/email/event/photo `Data` row, so it may be omitted from the full result and thus
  never actually imported (UAT only requires it appear/search, not import). Codex recommends
  making the selected full read two-query as well (spine over `Contacts.CONTENT_URI`).
  Cursor did **not** flag this — it viewed Plan 03 as sound and rated it MEDIUM. Worth
  resolving before execution.
- **Plan 01 tracer whole-book photo staging.** Codex flags **MEDIUM** — the intermediate
  tracer build reads and stages photos for the entire address book before any selection,
  a transient privacy/perf cost, and recommends a non-UAT/non-release marker or cleanup of
  unselected tracer photos. Cursor treated the temporary full-book reader as acceptable
  "tracer discipline" (a strength), not a concern.
- **Return-contract typing (Plan 03).** Codex flags **MEDIUM** that `readAllContacts()`
  becoming "found contacts plus an omitted count" leaves the TS type and how
  `routePickedImport()` still receives an array undefined; recommends a dedicated
  `{ contacts, omittedCount }` type. Cursor did not raise this.

## Codex Review

## Summary

The five plans are thoughtfully staged: tracer first, shared-pipeline repairs in parallel, then a scalable picker, permission UX, and hardware gating. They trace several real defects correctly—especially the 17+ reader swallowing failures, nameless bulk rows remaining unresolved, and the already-linked single-import dead end. Two implementation gaps need correction before execution: avoiding photo staging for nameless bulk rows, and ensuring a selected name-only contact can complete the full read/import.

## Plan 01 — tracer / native reader

### Strengths

- The plan correctly targets the existing integration boundary: `routePickedImport()` treats an empty result as cancellation and routes one vs. many by cardinality, so a legacy reader emitting `PickedContact[]` reuses the pipeline unchanged. [src/services/import/import-acquire.ts:152](/home/bwales/projects/orbit-app/src/services/import/import-acquire.ts:152)
- It accurately identifies the two native defects to avoid: every `Event` is currently accepted as a birthday, and reader exceptions resolve as an empty list. [OrbitContactPickerModule.kt:116](/home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:116)
- Replacing the shared unsupported gate is appropriate: both entry points currently depend on it. [AddSpeedDialFab.tsx:30](/home/bwales/projects/orbit-app/src/components/AddSpeedDialFab.tsx:30), [SettingsScreen.tsx:134](/home/bwales/projects/orbit-app/src/screens/SettingsScreen.tsx:134)

### Concerns

- **MEDIUM — the tracer reads and stages photos for the entire address book before the user selects anything.** The current mapper stages each `photoTempUri` before session creation. [import-acquire.ts:69](/home/bwales/projects/orbit-app/src/services/import/import-acquire.ts:69) Plan 03 retires this, but Plan 01 produces an intermediate build that unnecessarily materializes all selected-or-not contact photos in app-private cache.

### Suggestions

- Make the tracer’s full-book reader explicitly non-UAT/non-release, or implement the lightweight summary read first. At minimum, add cleanup of unselected tracer photo files before moving to Plan 03.
- Treat a `ContentResolver.query(...) == null` as a read failure, not an empty successful result. The existing reader returns an empty list if the cursor is null. [OrbitContactPickerModule.kt:137](/home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:137)

### Risk Assessment

**MEDIUM.** The architectural direction is sound, but the temporary whole-book photo staging has privacy/performance cost.

## Plan 03 — scalable custom picker

### Strengths

- The two-query summary design correctly addresses a real data-model limitation: the current native reader groups only `ContactsContract.Data` rows, so a contact with no relevant data row cannot enter the result. [OrbitContactPickerModule.kt:125](/home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:125)
- Keeping search/selection logic free of React Native is a good fit for the existing pure mapper pattern. [picked-contact-map.ts:1](/home/bwales/projects/orbit-app/src/logic/picked-contact-map.ts:1)
- JS-owned chunking is a good boundary, provided the exported wrapper contract is explicit and tested.

### Concerns

- **HIGH — the selected-key full reader is not specified to import a name-only contact.** Plan 03 fixes name-only contacts in the browse summary, but its selected-key reader is described as a `Data`-table `LOOKUP_KEY IN (...)` query. A name-only contact has no phone/email/event/photo `Data` row, so it will be omitted from the full result—exactly as the existing `Data`-only reader would omit it. [OrbitContactPickerModule.kt:137](/home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:137) The plan’s UAT only requires that it appear/search, not that it can be imported.
- **MEDIUM — the `readAllContacts()` return contract becomes ambiguous.** Existing callers require `Promise<PickedContact[]>`. [index.ts:35](/home/bwales/projects/orbit-app/modules/orbit-contact-picker/index.ts:35) Plan 03 says the wrapper returns found contacts “plus an omitted count (or exposes it)” without defining the TypeScript type or how `routePickedImport()` still receives just an array.
- **MEDIUM — chunk failure can leave staged photos from successful earlier chunks.** A later native chunk rejection rejects the overall operation, but earlier chunks may already have copied full photos to cache. The existing cache-copy helpers create files independently. [OrbitContactPickerModule.kt:189](/home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:189)

### Suggestions

- Make selected full reads two-query as well: query `Contacts.CONTENT_URI` for the selected lookup keys as the spine, then merge relevant `Data` rows. This permits a selected name-only contact to emit `{ displayName, methods: [], birthday: null, photoTempUri: null }`.
- Define a dedicated result type, e.g. `{ contacts: PickedContact[]; omittedCount: number }`, and pass `result.contacts` to `routePickedImport()`.
- On a multi-chunk failure, delete cache files produced by already-completed chunks before surfacing the error; test this cleanup at the JS orchestration layer with a mock reader.

### Risk Assessment

**HIGH.** The plan satisfies list visibility but not necessarily successful acquisition/import of the name-only contact it deliberately preserves.

## Plan 04 — permission UX and routing cutover

### Strengths

- The plan correctly avoids using `shouldShowRequestPermissionRationale`; it is not part of the installed React Native API surface described by the project, so relying on it would be brittle.
- It correctly removes the stale unsupported UI rather than merely making it cosmetically reachable. The Settings row is currently disabled and conditionally renders Android-17-only copy. [SettingsScreen.tsx:755](/home/bwales/projects/orbit-app/src/screens/SettingsScreen.tsx:755)
- It closes an existing Settings error-reporting gap: the current Settings handler only logs an import failure. [SettingsScreen.tsx:155](/home/bwales/projects/orbit-app/src/screens/SettingsScreen.tsx:155)

### Concerns

- **HIGH — “mirror notifications ask-once persistence” is not an implementation precedent for durable persistence.** The notification service performs fresh OS reads/requests but stores no state at all. [permission.ts:32](/home/bwales/projects/orbit-app/src/services/notifications/permission.ts:32) Plan 04 requires a durable permanent-denial verdict yet does not select a storage mechanism, key, migration/no-migration decision, or failure behavior.
- **MEDIUM — normal-denied reopen behavior remains underspecified.** `PermissionsAndroid.check()` only tells the app whether permission is granted. Without persisting that a request was previously attempted, reopening after a normal denial cannot distinguish first entry from prior denial; the screen may show the priming explainer again rather than the required calm re-request state.
- **LOW — `Linking.openSettings()` failure is not handled.** The user can be left with an inert button if the deep link rejects.

### Suggestions

- Specify one durable store and test seam—AsyncStorage is consistent with existing local UI-preference stores, e.g. [theme-store.ts](/home/bwales/projects/orbit-app/src/stores/theme-store.ts:1). Persist only a namespaced boolean derived from `NEVER_ASK_AGAIN`; clear it after a fresh granted check.
- Persist a separate `hasRequestedReadContacts` flag for presentation only, explicitly not for permanent-denial classification. That makes first-prime vs. repeat-denied rendering deterministic.
- Guard `openContactsSettings()` and surface a calm “Open Settings manually” fallback if it rejects.

### Risk Assessment

**MEDIUM-HIGH.** The routing work is clear, but the durable-state requirement is presently a design intention rather than an executable implementation contract.

## Plan 05 — build and device UAT gate

### Strengths

- The plan correctly separates generated-manifest packaging evidence from API-37 runtime evidence; that is stronger than checking only a manifest string.
- The deterministic revoke-after-summary test is a good way to exercise the actual selected-key error path rather than relying on a timing race.
- It correctly keeps API-37 system-picker functionality out of the sign-off claim, consistent with the stated phase boundary.

### Concerns

A manual address-book setup can easily invalidate later rows unless fixture creation/reset tooling is specified.
- **LOW — the UAT document must avoid real contact names, methods, and birthdays.** The plan says no PII in artifacts, but its “exact fixture setup” requirement should explicitly require synthetic labels and redacted evidence.

### Suggestions

- Add the exact API-37 command and expected result to the UAT template—for example, attempt a grant after install and record the expected platform refusal/state alongside `dumpsys`.
- Provide a fixture generator/import script or a reproducible adb/content-provider procedure before treating the large-book and >900-selection rows as mandatory.
- Make the UAT template use synthetic fixture identifiers only, with screenshots cropped/redacted before committing.

### Risk Assessment

**MEDIUM.** The gate is comprehensive and appropriately human-blocked; its main risk is repeatability and overly subjective device evidence.
