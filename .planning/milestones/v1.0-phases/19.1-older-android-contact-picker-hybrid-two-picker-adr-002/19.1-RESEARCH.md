## Summary

Phase 19.1 adds the Android ≤ API 36 half of the hybrid picker. The technical shape is already tightly bounded by verified in-repo code: the reader must emit the exact `PickedContact[]` shape (`modules/orbit-contact-picker/index.ts:8-19`), and everything downstream (`routePickedImport` → `acceptPickedContacts` → session pipeline) is picker-agnostic and consumes that shape unchanged (`src/services/import/import-acquire.ts:63-173`).

**The single most important finding:** the existing Kotlin module's `readPickedContacts()` (`OrbitContactPickerModule.kt:125-179`) is ~90% of the ≤16 reader already — same projection strategy, same mimetype grouping (`Phone`/`Email`/`Event`/`Photo`), same `file://` cache-photo staging. The only structural difference is the query URI: the 17+ path queries a **temporary OS-granted session URI**; the ≤16 path queries the **full provider** (`ContactsContract.Data.CONTENT_URI`) under `READ_CONTACTS`. This makes **extending the existing native module** the clear recommendation over a new module or a JS-side read.

The carried-forward fixes are small and, critically, **need no new migration**: the `'skipped'` `row_status` already exists in the schema and is already treated as terminal by both `finalizeSessionIfTerminal` and the leave-guard. D-12 collapses to a one-line status change plus a summary count. D-13 broadens an existing parser and re-routes the review screen to surface the raw value. D-14 is the reader's error contract. D-14b re-routes the single already-linked case to the existing `ImportComplete` "Done" exit.

**Primary recommendation:** Extend `modules/orbit-contact-picker` with a full-provider `ContactsContract` reader (`Event.TYPE == TYPE_BIRTHDAY` filter, error-throwing on read failure), declare `READ_CONTACTS maxSdkVersion="36"` **in the module's own `AndroidManifest.xml`** (merges at build; no config plugin needed), gate on `SDK_INT` via a single shared seam that replaces `useImportUnsupported()`, and build a standalone token-driven FlatList multi-select screen. Apply the four carried-forward fixes in the shared pipeline with **no schema migration**.

## Reader Implementation (D-15 discretion) — RECOMMENDATION

**Recommendation: (a) Extend the existing `orbit-contact-picker` Kotlin module** with a full-provider `ContactsContract` reader, a new `AsyncFunction` (e.g. `readAllContacts()` / `pickLegacyContacts()`), plus the `Event.TYPE` birthday filter and an error-throwing read contract.

### Why (comparison on merit)

| Option | Read efficiency (multi-method + birthday + photo across a large book) | Maintenance | `PickedContact[]` fidelity | Verdict |
|--------|----------------------------------------------------------------------|-------------|----------------------------|---------|
| **(a) Extend native module** | **Best.** One `ContentResolver.query` over `ContactsContract.Data.CONTENT_URI` returns all data rows; group by `LOOKUP_KEY` in a single cursor pass — exactly the existing `linkedMapOf` grouping (`OrbitContactPickerModule.kt:133-168`). No N+1. Photo blob (`DATA15`) staged to `file://` cache in the same pass, with the `openContactPhotoInputStream` fallback already written (`:181-187`). | Lowest — reuses `copyPhotoToCache`/`copyPhotoStreamToCache`/`stringAt`/`blobAt` verbatim (`:189-216`). One native change → one desktop rebuild (owner accepted). | Exact — the module already emits the `mapOf("lookupKey"…"photoTempUri")` shape (`:170-178`). | **CHOSEN** |
| (b) New native module | Same read efficiency but duplicates the projection/grouping/photo helpers into a second module → drift risk between the two readers (the exact class of bug D-03/D-14 are fixing). | Higher — two Kotlin modules to keep in lockstep. | Exact. | Rejected |
| (c) JS `ContactsContract` read (`expo-contacts`) | Weaker. `expo-contacts` returns a JS object graph; multiple phones/emails/birthday come back but you must map its birthday `Date` (no raw `Event.TYPE` control — you rely on its own birthday extraction) and its photo is a `uri` you'd then have to copy to app-private cache from JS. Adds a dependency + config plugin. | Adds a runtime dependency and a second contacts-permission surface; the `Event.TYPE == TYPE_BIRTHDAY` guarantee (D-03) becomes "trust the library." | Achievable but with the birthday-type risk D-03 exists to eliminate. | Rejected |

### Concrete native design for the recommended path

**Projection** (extend the existing one at `OrbitContactPickerModule.kt:126-132` — add `DATA2` for the Event type, absent today):
```kotlin
val projection = arrayOf(
  ContactsContract.Data.LOOKUP_KEY,
  ContactsContract.Contacts.DISPLAY_NAME_PRIMARY,
  ContactsContract.Data.MIMETYPE,
  ContactsContract.Data.DATA1,   // phone/email value, or Event date string
  ContactsContract.Data.DATA2,   // Event.TYPE (NEW — required for D-03; not in the 17+ projection)
  ContactsContract.Data.DATA15,  // photo blob
)
```

**Query the full provider** (vs. the 17+ session URI at `:137`):
```kotlin
// Requires READ_CONTACTS (granted on ≤16). Query the whole Data table and group by lookup key.
context.contentResolver.query(
  ContactsContract.Data.CONTENT_URI,
  projection,
  // Restrict to the 4 mimetypes we map (optional optimisation; grouping below already filters):
  "${ContactsContract.Data.MIMETYPE} IN (?,?,?,?)",
  arrayOf(
    ContactsContract.CommonDataKinds.Phone.CONTENT_ITEM_TYPE,
    ContactsContract.CommonDataKinds.Email.CONTENT_ITEM_TYPE,
    ContactsContract.CommonDataKinds.Event.CONTENT_ITEM_TYPE,
    ContactsContract.CommonDataKinds.Photo.CONTENT_ITEM_TYPE,
  ),
  "${ContactsContract.Contacts.DISPLAY_NAME_PRIMARY} ASC",
)
```
(Full-provider queries accept `selection`/`selectionArgs`, unlike the session URI which rejects them per the comment at `:135-136`.)

**MIME-type grouping** — reuse the `when(mimetype)` block (`:149-166`) verbatim EXCEPT the Event branch, which must gate on `Event.TYPE` (this is the D-03 fix, and the defect NOT to reproduce — the 17+ module maps *any* Event `DATA1` to birthday at `:158-159` with no type check):
```kotlin
ContactsContract.CommonDataKinds.Event.CONTENT_ITEM_TYPE -> {
  val eventType = cursor.intAt(data2Column)   // DATA2
  if (eventType == ContactsContract.CommonDataKinds.Event.TYPE_BIRTHDAY) {
    contact.birthday = contact.birthday ?: cursor.stringAt(data1Column)
  }
  // Anniversary / custom Events are ignored — never stored as birthday.
}
```
`TYPE_BIRTHDAY` is the integer constant `3` in `ContactsContract.CommonDataKinds.Event` `[CITED: developer.android.com/reference/android/provider/ContactsContract.CommonDataKinds.Event#TYPE_BIRTHDAY]`. Prefer the constant to the literal.

**Photo staging** — reuse `copyPhotoToCache(blob)` with the `copyContactPhotoToCache(lookupKey)` fallback exactly as at `:160-164,181-210`. The output `file://` URI feeds `photoTempUri`, which `acceptPickedContacts` moves to durable staging (`import-acquire.ts:77-85`).

**Read-error contract (D-14)** — the ≤16 `AsyncFunction` must **reject the promise** on a read failure, NOT `resolve(emptyList())`. The 17+ path's defect is at `OrbitContactPickerModule.kt:116-121` (catch → `resolve(emptyList())`); combined with `routePickedImport`'s `if (picked.length === 0) return;` (`import-acquire.ts:161`) a failed read is indistinguishable from a cancel. The JS caller (`importContacts` in `AddSpeedDialFab.tsx:62-82`, `onImportContacts` in `SettingsScreen.tsx:155-175`) already has a `try/catch` that shows "Couldn't import contacts" — a rejected promise routes there correctly, while a genuine user cancel (empty selection in our own UI) returns `[]` and is a silent no-op. **Distinguish at the source:** cancel = our picker returns `[]`; read error = promise rejects.

## Permission & Manifest (D-02, D-11)

### Manifest scoping — declare in the module manifest (no config plugin needed)

The existing module already ships an `AndroidManifest.xml` that merges into the app manifest at prebuild (`modules/orbit-contact-picker/android/src/main/AndroidManifest.xml` — currently a `<queries>` block for package visibility) `[VERIFIED: file opened this session]`. Add the scoped permission there:
```xml
<uses-permission
  android:name="android.permission.READ_CONTACTS"
  android:maxSdkVersion="36" />
```
This is simpler and more local than a `withAndroidManifest` Expo config plugin, and it keeps the contact-picker concern inside the contact-picker module. (`app.config.ts` currently declares permissions *implicitly* via plugins and has no `android.permissions` array — verified `app.config.ts:70-84`; a manifest-merge entry avoids touching that file.) `maxSdkVersion="36"` makes the permission **absent from the effective manifest on API-37 devices** → Play Contacts-policy compliant per D-02 `[CITED: ADR-002 Consequences; developer.android.com/guide/topics/manifest/uses-permission-element#maxSdk]`.

> **Verify at prebuild:** confirm `READ_CONTACTS` with `android:maxSdkVersion="36"` lands in the generated `android/app/src/main/AndroidManifest.xml` on droid (mirror the `allowBackup=false` verification note at `app.config.ts:80-83`). The two module manifests already merge, so this is low-risk, but it is a native-surface change → include it in the one rebuild.

### Runtime request flow (D-11a/b/c)

Precedent in-repo is `expo-notifications`' value-moment, ask-once, no-nag pattern (`src/services/notifications/permission.ts` — fresh read every call, guarded, `{granted}` result) `[VERIFIED: file opened this session]`. Mirror its *shape* (a thin guarded wrapper returning a typed result) but use `PermissionsAndroid` for `READ_CONTACTS`:

- **First request (D-11c priming):** show the in-app pre-permission explainer screen/sheet FIRST; on "Continue" call `PermissionsAndroid.request(PermissionsAndroid.PERMISSIONS.READ_CONTACTS)`. Priming before the OS dialog reduces accidental permanent denials. `[ASSUMED — standard Android UX; RN API]`
- **Deny (D-11a):** `request()` returns `PermissionsAndroid.RESULTS.DENIED` → show the calm explainer state with a "Grant access" button that re-calls `request()`. No `ACTION_PICK` fallback (rejected).
- **Permanent denial (D-11b):** `request()` returns `PermissionsAndroid.RESULTS.NEVER_ASK_AGAIN` → switch the button to "Open Settings" → `Linking.openSettings()`. On next focus, re-check with `PermissionsAndroid.check(...)` (fresh read, like the notifications module) so a grant made in Settings is picked up. `[ASSUMED — RN API]`

> **Android-version nuance to confirm on the 3a (MEDIUM confidence):** `NEVER_ASK_AGAIN` is only reliably distinguishable from `DENIED` **after the first denial** — on the very first prompt some OEM/OS versions can report `NEVER_ASK_AGAIN` shapes differently. The robust cross-version pattern is: track "have we requested before" in component state, and on a `DENIED` result call `PermissionsAndroid.check()` — if still denied *and* a re-`request()` returns immediately without a dialog, treat as permanent. Verify empirically on the Pixel 3a (Android 14/15) across a deny → deny-again → don't-ask-again sequence; note behaviour differences vs. API 34/35/36. `[ASSUMED — flagged for device UAT; see Assumptions Log A1]`

**No in-repo precedent for `Linking.openSettings()`** — `BackupScreen`'s `openSettings` is an in-app navigation, not the Android settings deep-link (`BackupScreen.tsx:128,299` opened this session). This is net-new; verify the deep-link lands on Orbit's app-info page on the 3a.

## Routing Seam (D-15 discretion)

**Where the gate lives today:** `isContactPickerAvailable()` returns `SDK_INT >= 37` (native, `OrbitContactPickerModule.kt:63-65`; JS wrapper `index.ts:25-28`). `useImportUnsupported()` = `!isContactPickerAvailable()` (`use-import-unsupported.ts:8-10`). Both entry points consume it: `AddSpeedDialFab.tsx:30,56-59` (blocks with an Alert) and `SettingsScreen.tsx:134,155-156,759,769-779` (disables the row + shows the "requires Android 17+" copy).

**Recommendation — replace `useImportUnsupported()` with a single `useContactImportMode()` seam** returning a discriminated result, so the SDK branch lives in exactly one place and both components dispatch identically:
```ts
// src/screens/use-contact-import-mode.ts (replaces use-import-unsupported.ts)
export type ContactImportMode = "system" | "legacy"; // 17+ vs ≤16
export function contactImportMode(): ContactImportMode {
  return isContactPickerAvailable() ? "system" : "legacy";
}
```
- The native side already exposes `isContactPickerAvailable()` (`SDK_INT>=37`); its inverse is the `"legacy"` (≤16) path. No new native probe strictly required, though exposing `SDK_INT` or an `isLegacyContactReadRequired()` boolean is cleaner than double-negating.
- Both entry points call a single shared handler (e.g. `startContactImport(mode, navigation)`): `"system"` → existing `pickContacts({multiple:true})` → `routePickedImport`; `"legacy"` → navigate to the new custom picker screen, which on confirm calls the native `readAllContacts()` for the *selected* lookup keys → `routePickedImport`. Keep the `getAppSettings`/`effectivePhoneRegion`/`localDateTime()` plumbing identical to today (`AddSpeedDialFab.tsx:63-76`, `SettingsScreen.tsx:158-171`).
- **Retire the unsupported state (D-05):** delete `IMPORT_UNSUPPORTED_TITLE`/`IMPORT_UNSUPPORTED_COPY` usage and the `importUnsupported` branch in `SettingsScreen.tsx:769-784` and the Alert in `AddSpeedDialFab.tsx:56-59`. There is no longer any device on which import is unavailable, so the disabled/greyed row goes away entirely.

**Selection→read handoff (legacy path):** the custom picker shows all contacts (read via a lightweight native list query — lookupKey + displayName + primary method + photo thumbnail), the user multi-selects, and on "Import (N)" the native reader does the *full-field* read for the selected lookup keys → `PickedContact[]`. (One design choice for the planner: read full fields for ALL contacts up front and filter in JS, or read summary-fields for the list then full-fields for the selection. The latter is lighter on a large book; either produces the same `PickedContact[]`.) Both are acceptable; recommend the two-tier read for large address books.

## Custom Picker UI (D-09 / D-10)

### Architecture (decoupled per D-10)
- **Data source (plain logic, no RN import):** a module that takes the native summary-read rows and exposes `{ lookupKey, displayName, primaryMethod, photoThumbUri }`. Mirror `dashboard-search-row-logic.ts` (pure, node-testable, no RN import — verified `dashboard-search-row-logic.ts:1-24`).
- **Selection state (plain logic):** a `Set<lookupKey>` reducer + a search-filter predicate over `displayName + methods` — pure, unit-testable, decoupled from the screen. Mirror the phone-region search filter already in `SettingsScreen.tsx:450-458` (lowercased substring over name + code) as the idiom.
- **Presentation (screen):** a token-driven `FlatList` — the reskin surface. D-10's "single-screen token-level change" is satisfied because colours + layout live only here.

### Concrete UI recipe
- **List:** `FlatList` (virtualized) with `keyExtractor={lookupKey}`. Row = `Avatar` (photo or initials) + display name + primary-method subtitle + a trailing checkbox. Reuse the `Avatar` component (`ImportReviewScreen.tsx:14,366`) which already does photo-or-initials via the themed `avatarSwatches`/`avatarSwatchText` tokens (`theme-types.ts:47-65`).
- **Photo virtualization:** use `expo-image` (`Image` with `source={{uri}}`, `contentFit="cover"`) — already the app's contact-photo renderer (`ImportReviewScreen.tsx:358-364`). `expo-image` caches + lazy-loads within the FlatList window; do not pre-decode all photos. For a large book, prefer loading photo thumbnails lazily per row rather than staging every photo up front (only the *selected* contacts' full photos get staged, at read time).
- **Search-as-you-type:** a `TextInput` header filtering the data source over name + phone/email; mirror `SettingsScreen.tsx:808-824` (search TextInput) + `:450-458` (filter). Debounce not required at address-book sizes but harmless.
- **Multi-select + persistent CTA (D-09):** a fixed-bottom "Import (N)" `Pressable`, `disabled` when N===0, styled with `colors.accent`. **No selection cap** (D-09) — do not port the 17+ path's `SELECTION_LIMIT 100` (that is an OS constraint on the system picker at `OrbitContactPickerModule.kt:90-91`, not our policy).
- **Tokens only (CLAUDE.md):** every colour via `useTheme().colors.*` — `background`, `surface`, `surfaceElevated`, `accent`, `textPrimary`, `textSecondary`, `border`, `borderStrong` (the 11-token palette, `theme-types.ts:29-158`). No hardcoded colours. Row min-height 44 (a11y), matching existing screens.
- **States:** loading (reading the book), empty ("No contacts on this device"), permission-blocked (the D-11a explainer state), and the D-11b "Open Settings" state. Keep these in the screen; the permission logic is the shared hook.
- **Register the screen** additively in `src/navigation/types.ts` alongside `ImportReview`/`BulkImportSetup`/`ImportComplete` (`navigation/types.ts:121` shows the additive pattern), and route to it from the shared `startContactImport` handler on the `"legacy"` branch.

### Anti-patterns to avoid
- **Coupling to dashboard/orrery components (D-10 violation):** the dashboard is redone next milestone; do not import its cards/rows. Same tokens, different layout.
- **Driving photo load from React state per frame:** N/A here (no animation loop), but keep photos in `expo-image`'s cache, not component state.
- **Reintroducing a selection cap:** none (D-09).

## Carried-Forward Pipeline Fixes — on-disk defect + fix + schema impact

### D-12 — Nameless rows auto-terminalize as "skipped" (NO migration needed)

**Current defect (verified):** `importRowAsNew` marks a nameless row `'failed'` with reason `"name-required"` — `import-driver.ts:76-85`:
```ts
if (mapped.nameRequired) {
  await markRowStatus(exec, params.row.id, "failed", "name-required", params.now);
  return { contactId: null, skipped: "name-required" };
}
```
`'failed'` is in the unresolved set, so the session never finalizes: `finalizeSessionIfTerminal` counts `row_status IN ('pending','needs_review','failed')` as unresolved (`import-session-dao.ts:418-420`, verbatim: `WHERE session_id = ? AND row_status IN ('pending', 'needs_review', 'failed')`), and the leave-guard's `UNRESOLVED_ROW_STATUSES` = `["pending","needs_review","failed"]` (`import-leave-guard-logic.ts:7-11`, verbatim). So `getResumableSession` re-offers the session every launch (`import-session-read.ts:97-115`).

**The fix — change `'failed'` → `'skipped'` at `import-driver.ts:79`.** `'skipped'` is already a valid `ImportSessionRowStatus` (`import-session-dao.ts:27-33`, values verbatim: `"pending" | "imported" | "linked" | "skipped" | "failed" | "needs_review"`) and is **already terminal**: it is NOT in the unresolved set of either `finalizeSessionIfTerminal` or the leave-guard. So the session finalizes and the nag stops — **no new migration**. Keep `failure_reason = "name-required"` so the count is distinguishable.

**Completion summary "N skipped — no name" (D-12):** `sessionSummaryCounts` currently buckets `skipped` (with `match_outcome !== 'already_linked'`) into `failedOrSkipped` (`import-session-read.ts:238-243`), rendered as "Failed / skipped (N)" (`ImportCompleteScreen.tsx:170-176`). To report "no name" specifically, add a count keyed on `failure_reason = 'name-required'` (a new grouped query or an extension of `sessionSummaryCounts`) — a read-only query change, still **no migration**.

**Where to apply for the single path too:** the single-import review gates `canImport` on `name.trim().length > 0` (`ImportReviewScreen.tsx:181`), so a nameless single row can't be committed and would dead-end on leave. Cleanest is to auto-terminalize nameless rows at **acceptance** as well: `acceptPickedContacts` already computes `mapped.nameRequired` (`import-acquire.ts:71` via `mapPickedContact`, which sets `nameRequired: name === ""` at `picked-contact-map.ts:73`) but currently discards it. Marking nameless rows `'skipped'` at accept-time (or immediately after) covers both single and bulk uniformly. Planner's call on placement (driver line vs. acceptance seam vs. both); either needs no schema change.

> **Do not** widen the unresolved sets or invert their meaning — they are the terminalization invariant shared by `finalizeSessionIfTerminal`, the leave-guard, and `getResumableSession`. The two lists are explicitly kept in sync (comment at `import-leave-guard-logic.ts:4-6`). The fix moves the row to an already-terminal status; it does not change what "terminal" means.

### D-13 — Broaden birthday parsing; flag (don't drop) still-unparseable

**Current defect (verified):** `mapBirthdayForStorage` (`picked-contact-map.ts:28-38`) handles only `--MM-DD`, `MM-DD`, `YYYY-MM-DD`; anything else → `buildBirthdayForStorage`/`isValidStoredBirthday` returns `null` → **silently dropped**. The single review screen loads the *pre-validated* value (`ImportReviewScreen.tsx:145` sets `birthdayInput` from `mapped.birthday`, which is already null for unparseable input), so a bad format shows as empty and never triggers the screen's error state. The screen DOES have a birthday error state, but it only fires on user-typed input (`ImportReviewScreen.tsx:170-175,516-520`). Findings #6 confirms OEM formats like `MM/DD/YYYY` are dropped (`19-DEVICE-UAT-FINDINGS.md:89`).

**The canonical stored shapes (verified):** `birthday-logic.ts:33-34` — `MM_DD = /^(\d{2})-(\d{2})$/`, `YYYY_MM_DD = /^(\d{4})-(\d{2})-(\d{2})$/`. `daysUntilBirthday` accepts `MM-DD` (year unknown) or `YYYY-MM-DD` (`birthday-logic.ts:14-18,79-105`). Year-less is stored bare `MM-DD` (the Android `--` prefix is stripped: `birthday-logic.ts:130` and `picked-contact-map.ts:32,35`).

**The fix (two parts):**
1. **Broaden a canonicalizer** feeding `mapBirthdayForStorage` (`picked-contact-map.ts:28-38`) to recognise common Android `Event` birthday formats and normalise to the two stored shapes: `YYYY-MM-DD` (already), `--MM-DD` / `MM-DD` year-less (already), plus `YYYY/MM/DD`, `MM/DD/YYYY`, and the `--MM-DD` ISO year-less form. Do the normalisation in the map layer; keep `parseStoredBirthday` (`birthday-logic.ts:79-105`) strict as the calendar-validity gate (it correctly rejects impossible dates like `02-30` — do not loosen that). Applies to **both readers** (shared `picked-contact-map.ts`); the ≤16 reader gets it from the start.
2. **Flag, don't drop, on the review screen:** load the **raw** `snapshot.birthday` into `birthdayInput` (not the pre-nulled `mapped.birthday`) so a genuinely-unparseable value hits the existing `birthdayInvalid` error state (`ImportReviewScreen.tsx:174-175,516-520`) instead of silently vanishing. This matches the custom-fields "flag, don't coerce" philosophy (CLAUDE.md) and 19-13's typed-birthday handling. On the **bulk** path there is no per-row birthday review, so an unparseable birthday is dropped there (birthday is optional) — acceptable; the flag applies where a review UI exists.

**Schema impact:** none — stored formats unchanged; this is parser breadth + a review-load change.

### D-14 — Read-exception ≠ cancel

Covered under §Reader Implementation. **Fix:** the ≤16 `AsyncFunction` **rejects** on read failure (never `resolve([])`); a user cancel returns `[]`. The JS `try/catch` at both entry points already surfaces "Couldn't import contacts" on a rejection (`AddSpeedDialFab.tsx:78-80`, `SettingsScreen.tsx:172-174`). Do NOT reproduce the 17+ swallow at `OrbitContactPickerModule.kt:116-121`. Schema impact: none.

### D-14b — Single-import "Already in Orbit" clean exit

**Current defect (verified):** on an already-linked single import, `ImportReviewScreen.tsx:231-248` calls `resolveAlreadyLinked` + `finalizeSessionIfTerminal`, then shows an `Alert` with a **single "View contact" button** and returns. If the user dismisses the alert (or taps View then backs out), they land back on `ImportReviewScreen`; `resolveAlreadyLinked` set `row_status='skipped'` but leaves `contact_id` NULL (`import-session-dao.ts:301-314`, verbatim `SET row_status = 'skipped', match_outcome = 'already_linked', matched_contact_id = ?`), so on reload `rows.find(candidate => candidate.contactId === null)` (`ImportReviewScreen.tsx:117`) still matches this row → it re-offers reviewing an already-linked contact. No Done, and hardware Back doesn't cleanly dismiss.

**The fix:** route the already-linked single case to the existing terminal screen that already has a correct exit. `ImportCompleteScreen` has a "Done" `Pressable` that does `navigation.reset({ index: 0, routes: [{ name: "Home" }] })` (`ImportCompleteScreen.tsx:234-244`) — the clean, back-safe exit. Replace the bare Alert with `navigation.replace("ImportComplete", { sessionId })` (the same call `skipDuplicate` already uses at `ImportReviewScreen.tsx:316-318`), OR add an explicit "Done" button to the terminal state. Since the session is already finalized and the row terminal, `ImportComplete` will render "Already in Orbit (1)" and offer Done + optional "View contact". Schema impact: none.

## Open Questions

1. **Two-tier vs. single-tier native read.**
   - Known: full-provider queries accept `selection`/`selectionArgs`; grouping by `LOOKUP_KEY` in one cursor pass is efficient.
   - Unclear: whether a large real book (owner mentioned ~63 method-bearing contacts + others) makes the up-front full read cheap enough to skip the two-tier split.

   - Known: `failure_reason='name-required'` distinguishes it; `sessionSummaryCounts` currently merges failed+skipped.
   - Unclear: whether the owner wants a distinct completion line or the existing "Failed / skipped" bucket suffices.
   - Recommendation: add a dedicated read-only count (no migration); render "N skipped — no name" per D-12. Owner-facing copy is taste (owner's bucket) — flag at planning.
