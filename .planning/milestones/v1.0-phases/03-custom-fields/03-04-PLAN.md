<objective>
Build the per-contact custom-value data access (read/UPSERT) and the pure visibility selectors that
decide where each field appears (FLD-07). Tables already exist (FLD-01) — this wires the value
operations.

Purpose: A field's data is one column per field on `contact_custom_values` (one row per contact). This
plan owns reading a contact's values with a dynamic (whitelist-built) SELECT, UPSERTing a single value,
and the three placement rules from §14.7: profile = value-present OR always_show; create form =
show_on_new only; edit form = every non-quarantined field. The host forms/profile are Phase 4's shell —
this plan delivers the selectors those screens call.

Output: `src/db/field-values-dao.ts` (getValuesForContact, upsertValue, visibleDefsForProfile,
defsForCreateForm, defsForEditForm), node:sqlite-proven.

Independence: this plan does NOT depend on Plan 03's DDL — its test fixture adds a value column with a
direct `ALTER TABLE contact_custom_values ADD COLUMN` so it can run in parallel. It DOES depend on
Plan 01's `isSafeColName` (identifier guard) AND `inWriteTransaction` from `src/db/transaction.ts` (the
shared write-serialization boundary through which `upsertValue` must run).
</objective>

    Create `src/db/field-values-dao.ts` (import `inWriteTransaction` from `@/db/transaction`). Export:
    - `getValuesForContact(exec, contactId, defs: CustomFieldDef[]): Promise<Record<string, string |
      null>>` — if `defs.length === 0` RETURN `{}` immediately (review LOW — otherwise the column list is
      empty and the statement becomes a malformed `SELECT  FROM contact_custom_values WHERE contact_id =
      ?`, a syntax error reachable on a fresh install with zero custom fields). Otherwise build the SELECT
      column list from `defs.map(d => '"'+d.col_name+'"')` (each guarded by isSafeColName; throw on an
      unsafe one), `WHERE contact_id = ?`. Return a map of col_name → value (empty map when the
      contact_custom_values row is absent).
    - `upsertValue(exec, contactId, uid, col_name, value: string | null, now)` — MUST run inside
      `inWriteTransaction` (review HIGH-2a): a bare UPSERT on the shared connection races the sweep/DDL,
      and `mutex.ts`'s header documents that foreground code and Phase-11/12 headless taps share one
      connection, so every custom-field write goes through the one serialization boundary — this is a
      stated design contract, not a nicety. Inside the txn: guard col_name with isSafeColName, then
      `INSERT INTO contact_custom_values (contact_id, uid, modified_at, "<col>") VALUES (?,?,?,?) ON
      CONFLICT(contact_id) DO UPDATE SET "<col>"=excluded."<col>", modified_at=excluded.modified_at`.
      ALWAYS bump modified_at (the Phase-16 newest-wins merge depends on it). The col_name is the only
      interpolated identifier (double-quoted); contactId/uid/value/now are `?`-bound.

    UID CONTRACT (review MED — pin it): `uid` is the `contact_custom_values` ROW uid — ONE per CONTACT
    (the row's merge key, `uid TEXT NOT NULL UNIQUE`), NOT one per field. It is written on the INSERT
    branch only; the `ON CONFLICT(contact_id) DO UPDATE` branch NEVER touches uid. Callers MUST mint a
    per-contact uid (e.g. `newUid()` once per contact) — a per-FIELD uid would make the second contact's
    INSERT collide on `UNIQUE(uid)`, and because that constraint is NOT the `ON CONFLICT(contact_id)`
    target, SQLite RAISES instead of taking the DO UPDATE branch and the save fails outright. Phase 4's
    contact-create is the PRIMARY creator of this row; `upsertValue` is safe when the row is absent (it
    INSERTs with the supplied per-contact uid) but must be given the contact's own uid, never a new one
    per write.
  </action>
