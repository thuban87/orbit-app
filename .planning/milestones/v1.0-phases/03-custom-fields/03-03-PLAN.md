<objective>
Build the transactional DDL layer (FLD-02/03/05) and the field-definition metadata DAO. This is the
correctness core of the phase: creating, dropping, renaming, reordering, and quarantining a custom
field, each atomic and each serialized with the recency writers through the shared mutex.

Purpose: `contact_custom_values` is a real column per field. Creating one is `INSERT def + ALTER TABLE
ADD COLUMN` in one transaction; deleting a populated one is irreversible, so it is snapshot-to-history
then `DELETE def + DROP COLUMN` in one transaction, gated behind quarantine. These are the operations
whose atomicity the whole subsystem's data-safety depends on.

Output: `src/db/field-ddl.ts` (createField, the non-mutexed `dropFieldColumns` core, the public
`dropField`, deleteOrQuarantineField, and the sweep-specific `expireFieldIfStale`) and
`src/db/field-defs-dao.ts` (renameField, reorderFields, changeFieldOptions, updateFieldCuration,
quarantineField, restoreField, listDefs, isFieldEmpty — every mutating op serialized through
`inWriteTransaction`), both node:sqlite-proven.

Reuse-not-rebuild: IMPORT `inWriteTransaction` from `src/db/transaction.ts` (Plan 01, Wave 1) — do NOT
re-copy it (four verbatim copies is how the HIGH-1 sweep-deadlock arose). NEVER use expo
`withTransactionAsync` (Phase-2 pitfalls P3/P4). Take `exec: SqlExecutor` as the first argument so
every op stays node-testable.

Concurrency structure (review HIGH-1 / HIGH-2b): the drop logic is split so it can be composed atomically
WITHOUT nesting the non-reentrant mutex. `dropFieldColumns(exec, def, operation, now)` is a PRIVATE,
NON-mutexed core that assumes the caller already holds the transaction (it does the snapshot + DELETE def
+ DROP COLUMN and NOTHING else — no BEGIN, no withMutex). The public `dropField(...)` wraps that core in
ONE `inWriteTransaction`; it is the drop primitive exercised by the drop-mechanics tests. Plan 07's sweep does NOT call `dropField` — it calls `expireFieldIfStale`, which re-verifies staleness under the lock (review cycle-3 TOCTOU). `deleteOrQuarantineField` opens ONE
`inWriteTransaction` and, inside it, does the emptiness check and then calls the core `dropFieldColumns`
directly — so the check and the drop are one atomic transaction and no concurrent write can land between
them, while the public mutex is never nested (which would deadlock, mutex.ts:32-36).

Two review cycle-2 refinements complete the serialization boundary. (1) The sweep does NOT call the public
`dropField`; it calls a sibling sweep-specific entry `expireFieldIfStale` that opens ONE
`inWriteTransaction`, RE-READS `quarantined_at` under the lock, and only then calls the same non-mutexed
core — closing the scan→drop TOCTOU where a field restored between the sweep's candidate scan and its drop
would otherwise still be dropped. (2) Every def-metadata writer in `field-defs-dao.ts` now runs inside its
own `inWriteTransaction` too (not just the reorder batch), so the whole subsystem honours the project's
"every writer through the shared mutex" contract — a bare UPDATE overlapping the async sweep's in-flight
drop transaction on the shared connection can no longer be captured into it (the P4 hazard the mutex exists
to prevent). Neither refinement reverses any decision: TEXT-forever, no index/UNIQUE on value columns,
explicit DELETE+DROP, and the 30-day window all stand.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user field def → DDL/SQL | Label, options, and the generated col_name cross into DDL (`ADD/DROP COLUMN`) and def-table writes. |
| quarantine expiry → irreversible DROP | A populated field's data is destroyed by DROP COLUMN; recovery exists only via the field_history snapshot. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | createField / dropField / isFieldEmpty col_name interpolation | high | mitigate | Only a whitelist-constructed col_name is interpolated (double-quoted), re-checked with isSafeColName before every ALTER; all other values `?`-bound. |
| T-03-02 | Denial (data loss) | dropField ordering / check→drop race / sweep-restore TOCTOU | high | mitigate | Snapshot to field_history BEFORE DROP COLUMN in the same txn; deleteOrQuarantineField runs its emptiness check + drop inside ONE transaction (via the non-mutexed core) so no value can be written between check and drop; immediate delete never offered for a populated field (quarantine first). expireFieldIfStale RE-READS quarantined_at inside its own transaction and skips the drop if the def was restored since the sweep's candidate scan (sweep-TOCTOU guard, review cycle-2); every def-metadata writer runs in inWriteTransaction so a bare edit can no longer be captured by an overlapping drop transaction. The public dropField / expireFieldIfStale are never nested in another mutex (HIGH-1 deadlock guard). |
| T-03-03 | Integrity | orphan def/column | medium | mitigate | createField's INSERT+ADD and dropField's DELETE+DROP are each one atomic transaction (both or neither); rollback test proves it. |
| T-03-05 | Denial (data loss) | index/UNIQUE on value column | medium | mitigate | Value columns declared TEXT with no index/UNIQUE; a populated-field DROP-succeeds test would fail if one existed. |
