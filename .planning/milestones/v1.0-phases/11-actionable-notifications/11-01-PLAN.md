## Phase Goal (MVP user story)

**As a** person maintaining relationships in Orbit, **I want to** get a calm morning notification when I'm overdue with someone (or it's their birthday) that I can act on in one tap — mark contacted, snooze, or open the compose screen — **so that** I actually reach out before the connection decays, without the app nagging me.

**MVP sequencing exception (owner-authorized, grounded in the codebase):** this phase's true end-to-end behaviours (a notification firing, a killed-app headless action write) are OS-runtime and cannot be exercised by the JS test harness — they are Pixel-UAT only (see 11-VALIDATION.md Manual-Only). So, exactly as Phase 9 (expo-sms) and Phase 10 (expo-share-intent) did, the mandatory native/data foundation lands first (Wave 1) and the vertical feature slices (scheduling, headless actions, settings UI, birthday) build on it. Each post-foundation plan still delivers an observable capability.

<objective>
Land the native enablement and the shared contracts every later plan imports: install `expo-notifications` AND `expo-task-manager` (the peer module `registerTaskAsync` requires — absent from package.json), register the expo-notifications config plugin, provide node-safe test doubles so the Wave-0 unit suites can assert call shapes, and create the single `notification-ids` constants module (stable identifiers, channel/category/action ids, generic body copy, the occurrence-scoped `NotificationData` payload type, and the deterministic `actionUid` idempotency helper).

Purpose: unblock every downstream notification plan and guarantee identifiers/copy/channel ids AND the action-idempotency key have ONE source of truth (no drift between the scheduler that mints them and the handler that reads them).
Output: `expo-notifications` + `expo-task-manager` installed + plugin registered; `__mocks__/expo-notifications.ts`; `__mocks__/expo-task-manager.ts`; `src/services/notifications/notification-ids.ts` (+ test).
</objective>

| T-11-IDEMP | Tampering | `actionUid` (idempotency key) | medium | mitigate | actionUid is a PURE deterministic function of (action, kind, contactId, occurrenceKey) — the SAME re-delivered tap always yields the SAME uid, so the existing UNIQUE(uid) constraint (interactions/events) rejects a duplicate write.
