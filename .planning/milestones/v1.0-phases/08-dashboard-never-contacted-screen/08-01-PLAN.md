<objective>
Build the single dashboard read chokepoint — a new `src/db/dashboard-read.ts` that composes the query-time status/progress engine, the ranked-fuel projection, the cross-contact search predicates, the category label, and the favourite marker into ONE parametrized card read, plus the never-contacted inverse read, the birthday-candidate read, and the hidden-population counts. It reuses the EXISTING SQL fragments (extracted from `fuel-read.ts`) rather than re-deriving any of them, and is exhaustively node-tested.

Phase goal (MVP user story): **As a** person keeping up with my people, **I want to** open Orbit to a home screen showing who needs attention — sorted, filterable, searchable, with birthdays and favourites — **so that** I can see at a glance who to reach out to and act without hunting.

This plan is the correctness spine: it delivers the data behind the dashboard list, the never-contacted screen, the search box, the birthday banner, and every count. It is READ-ONLY — no writer, no migration (per D: `favourite_rank`, `snooze_until`, `birthday`, `category_id` all exist in migration 001).

Purpose: keep every dashboard predicate/sort/search in node-testable SQL so the `.tsx` screens stay presentational and nothing drifts from the profile's status or the ranked-fuel line.
Output: `dashboard-read.ts` (+ test) and an exported shared fuel fragment in `fuel-read.ts` (+ parity test).
</objective>
