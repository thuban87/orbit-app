  <action>
    Implement `daysUntilBirthday(stored: string | null, today: Date): number | null` — react-native-free (imports only pure helpers / `formatLocalDate` if useful; NO react-native, NO expo). The parameter MUST accept null: `contacts.birthday` is NULLABLE (migration 001-initial.ts:69) and `edit-contact-logic.ts:98` already types the stored value `string | null`, so a `stored: string` signature would contradict the promised null→null contract and force every caller to pre-guard. FIRST, guard `stored == null || stored.trim() === ''` → return null BEFORE any regex or Date work. Then parse `stored` with a STRICT regex (`^\d{2}-\d{2}$` for MM-DD, `^\d{4}-\d{2}-\d{2}$` for YYYY-MM-DD; anything else → null) BEFORE constructing any Date, then validate the calendar EXPLICITLY — because `new Date(y, m, d)` silently normalizes impossible dates (`02-30` → Mar 2), a length check alone would let malformed stored values through as real dates instead of returning null as promised (addresses review MEDIUM-1). Calendar check: month in 1–12 and day in 1–(days-in-that-month), else → null. For MM-DD the year is unknown, so February is leap-PERMISSIVE (day up to 29 allowed — a genuine Feb-29 birthday must survive); for YYYY-MM-DD validate the day against THAT specific year's calendar (so non-leap `2021-02-29` → null, while leap `2020-02-29` is valid). Only AFTER the calendar passes, extract month (0-based) and day.

    Fix Bug 1 (day-of drop): build BOTH the comparison anchors at LOCAL MIDNIGHT. Derive today's local Y/M/D from `today` (getFullYear/getMonth/getDate) and construct `todayMidnight = new Date(y, m, d)`; construct `birthdayThisYear = new Date(y, birthdayMonth, observedDay)` (also local midnight). Compare date-only, so when today IS the birthday the difference is exactly 0 and the "Today" case is reachable. Compute whole-day difference by differencing the two midnights (divide the ms delta by 86_400_000 and round) rather than comparing a time-carrying `now`.

    Fix Bug 2 (Feb-29 overflow): when birthdayMonth is February and day is 29 AND the target year is NOT a leap year, choose the observed day EXPLICITLY (recommend day 28 — celebrate within the birth month). Do NOT let `new Date(y, 1, 29)` silently roll to March 1. Apply the same explicit choice when rolling to next year. Add a top-of-file tunable/comment recording the Feb-29 observation choice as a FLAGGED minor owner decision (Feb-28 vs Mar-1) — the bug is the SILENT overflow, so the explicit choice is what matters.

    If `birthdayThisYear` (at local midnight) is before todayMidnight, roll to next year (recompute the observed day for the next year's leap status) and return that positive day count. Return null on any parse failure.

    Write `birthday-logic.test.ts` (Vitest node) covering every behavior bullet, constructing `today` Dates at multiple times of day and across leap/non-leap years.
