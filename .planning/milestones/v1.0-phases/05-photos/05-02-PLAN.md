<objective>
Build the single storage chokepoint and the atomic photo write DAOs — the shared data/file foundation every photo slice depends on.

Phase Goal (user story): **As a** user, **I want to** set a contact's (or my own) photo and have it survive reboots and restores **so that** my avatars never silently vanish and never break on a new device.

`photo-storage.ts` is the ONLY place the relative↔`file://` mapping and the `contactId`-derivable filename scheme are observable (so a future `expo-file-system` signature drift is a one-file change). The DAO writers are dedicated atomic single-column updates because `updateContactMetadataCore` deliberately excludes `photo` (05-RESEARCH Pitfall 6) — the photo write is decoupled from the metadata form so the inline old-file delete can pair with the DB update. A net-new `profile-dao.ts` gives the single-row self record its own writers (none existed).

Purpose: PHOTO-03 (one 512px master under the document dir, relative path resolved at read) and the write half of PHOTO-05 (clear + delete). It also closes the cycle-2 HIGH replacement-atomicity finding: the persist never pre-deletes the master, and a launch-time reconciliation sweep (on the existing Phase-2 registry) recovers from an interrupted replace.
Output: `photo-storage.ts` (+ test, incl. the crash-safe persist, the generic relative-path guard, and the reconcile logic), net-new `photo-reconcile-sweep.ts` + its `App.tsx` registration, `contacts-dao.ts` additions, net-new `profile-dao.ts` (+ `photo-dao.test.ts`).
