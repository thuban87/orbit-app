<objective>
Close the file-leak: wire the load-bearing purge cleanup adapter so a purge deletes the contact's photo files.

Phase Goal (user story): **As a** user, **I want to** permanently delete a contact and have their photos gone from my device too **so that** purge really means gone — no orphaned image files left behind.

This implements 05-RESEARCH's single most important finding (Pattern 6 / Pitfall 2): the Phase-4 `onPurgeExtensions(contactId)` adapter fires POST-COMMIT, after the `contacts` and `contact_custom_values` rows are already deleted — so the stored photo filename CANNOT be read from the DB. The adapter must rebuild filenames from `contactId` alone (the derivable scheme in `photo-storage`): the main `avatars/contact-${id}.jpg`, plus one `avatars/cv-${id}-${col_name}.jpg` per `type='photo'` custom field def read via `listDefs(exec, { includeQuarantined: true })` (`custom_field_defs` is a global table that survives purge — and the read MUST include QUARANTINED photo defs, or a contact purged during a photo field's quarantine window would leak its cv- file, violating PHOTO-05). Each delete is idempotent. Phase 4 passes no adapter; this plan supplies it and registers it at the Archived-list purge call.

Purpose: the purge half of PHOTO-05.
Output: `purge-photo-cleanup.ts` (+ test) and the adapter registration in `ArchivedContactsScreen`.
</objective>
