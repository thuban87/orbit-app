## Summary

All eleven constituent findings are **real and still present at HEAD** (`1bb2044`). Audit line numbers drift by at most a few lines; no finding has been fixed in the interim. The four groups decompose into three technical cores:

1. **Restore planning is not authoritative at commit** (RG-009). `applyRestore` reads local state and reconciles *outside* the write mutex (`src/backup/restore-apply.ts:1350-1436`), awaits photo/background staging (`:1454-1471`), then applies the obsolete plan in `inWriteTransaction` (`:1472-1600`). The no-op early return (`:1440-1453`) ignores tombstones, and nothing completes the global contact×definition pair matrix after a graph union. Fix: stage incoming bytes first (outside the lock), then **re-read, reconcile and apply inside one transaction**; treat novel incoming tombstones as a mutation; complete global pairs inside the same transaction with a **deterministic pair identity** (see the D-11 note); repair already-damaged databases with migration **031**.

2. **Photo files have no single ownership authority** (RG-010). Filenames derive from integer IDs (ADR-021), but merge copies path strings verbatim (`src/db/merge-dao.ts:303-360,405-418,483-489`). Restore deletes old paths after writing new files with the same derived names (`restore-apply.ts:1601-1650`). Recovery journal entries never check whether they still own the target (`restore-photo-finalize-sweep.ts:20-73`). Several deletion paths never enumerate the files they orphan (`purge-photo-cleanup.ts:83-98`, `field-ddl.ts:185-188`, `restore-apply.ts:1073`). Fix, with filenames unchanged per D-09: (a) resolve restored custom-photo targets from the def/contact UIDs already on the wire, so **no format bump is required**; (b) route every canonical write through one owned-master helper that holds a per-path lock and retires stale journal intents first; (c) make every delete a durable, idempotent journal intent that is executed only if no live row references the path; (d) re-home merged photos into survivor-derived paths through the same journal.

3. **Failure policy is per-hook folklore** (RG-016). `runLaunchSweep` awaits hooks with no containment and clears `pendingRerun` on rejection (`src/services/launch-sweep.ts:71-90`). Both triggers are `void` with no catch (`:106,111`). Cold start awaits raw background reconciliation inside the bootstrap `Promise.all` (`App.tsx:185-198`), so one failed pending-file delete (`background-storage.ts:150-156`) renders "Couldn't start Orbit". Fix: per-hook isolation with **declared prerequisites** (backup requires background reconciliation, and should also follow restore-photo finalization), handled trigger promises, per-candidate containment inside background reconciliation, and a bootstrap that keeps migrations and settings hydration fail-closed while containing recoverable image faults.

RG-011 is small and independent: re-hydrate `useThemeStore` from **committed SQLite** after an `applied` result, and carry `photosNeedingAttention`/`photoCleanupPending`/`scheduleResyncPending` through `toRestoreResultParams` into both `RestoreResult` param types and the screen.

**Primary recommendation:** Build the photo-ownership primitives first: pure path builders, idempotent journal intents, the reference-safe drain, the per-path lock, and a hardened sweep runner. Then restructure `applyRestore` once for RG-009 (graph) and RG-010 (media) in sequence, owned by one plan at a time. Merge re-homing and deletion-path cleanup follow as separate plans. **No backup format bump is needed; no owner escalation is triggered by B or D**, apart from the risk-posture questions listed under Open Questions.

## RG-009 — Restore reconciliation and committed graph integrity

### Root causes (confirmed)

1. **DPI-003 (stale plan):** Winners come from reads taken before the mutex, and staging awaits create an explicit window in which an independent writer can commit. The notification/headless `snoozeContact` path is one such writer, and it uses the same mutex (`src/db/snooze-dao.ts:125,171`). The transaction makes the stale plan atomic but not current.
2. **DPI-006 (tombstone-only no-op):** The early return at `:1440` counts row mutations and newer settings only. Tombstones reach the DB only through `importTombstones` inside the apply transaction.
3. **DPI-002 (pair matrix):** Only `createContactFullCore` (`contacts-dao.ts:275-286`, global defs incl. quarantined), `createField` (`field-ddl.ts:87-99`, every contact incl. archived) and `promoteFieldToGlobal` (`field-defs-dao.ts:217-235`) seed pairs. Restore Merge is the **only production path that creates contacts or definitions without seeding**. Verified: the writers of `contacts` are `contacts-dao.ts:244`, `recency-dao.ts:456` (test-only helper, documented as not seeding pairs at `recency-dao.ts:425-432`), `benchmark.ts:111` (fixture) and `restore-apply.ts:656`. The writers of `custom_field_defs` are `field-ddl.ts:66` and `restore-apply.ts:551`.

### Recommended fix design

**A. Authoritative planning inside the transaction (DPI-003).** Restructure `applyRestore` into three phases:

1. *Outside the lock (unchanged guards first):* `assertCompleteIncomingPairs`, Replace-all verified pre-restore snapshot (`createVerifiedPreRestoreSnapshot` takes `inReadSnapshot`, so it **must** stay outside), then **stage bytes for every incoming photo-bearing row and background** (over-stage) under one session token. Staging needs only the manifest, never local state.
2. *One `inWriteTransaction`:* read settings/local rows/tombstones, reconcile, `normalizePlan`, `suppressCategoryTombstoneDependents`, `retainAssignedCadence`, visible-name collision gate, totals and the no-op test. Then apply exactly as today, write journal rows **only for staged files whose rows won**, complete pairs (C), and bump `data_revision`. Incompatibility and no-op returns happen inside the transaction and commit an empty transaction.
3. *Post-commit:* finalize, cleanup, schedule reconcile (unchanged ordering except the RG-010 cleanup predicate), and best-effort deletion of unused staged files (or leave them to the orphan drain once the session is released; see Pitfall 3).

Over-staging removes any need for an abort/replan loop. The alternative, staging only the pre-plan's winners, relies on local writes only ever making incoming rows *lose*, which is true for monotonic clocks and false under a device clock rollback. If the planner chooses it, an in-transaction winner without staged bytes must roll back with a truthful retryable status, never apply without the photo.

*Do not* use `data_revision` as a change detector. Several writers never bump it: `grep -L bumpDataRevisionCore` over files that call `inWriteTransaction` lists `src/db/purge-dao.ts`, `src/db/merge-dao.ts`, `src/db/capture-dao.ts`, `src/db/import-session-dao.ts`, `src/db/imported-contact-dao.ts` and others [VERIFIED: grep]. A fingerprint check would miss those commits.

*Alternative considered:* hold the mutex across planning **and** staging (the export precedent `inReadSnapshot` already holds the mutex during photo reads, per `transaction.ts:65-72`). It is simpler, but it puts decode-and-write file I/O under the write mutex, against ADR-112's stated rejection of "filesystem work inside the SQLite transaction", and it blocks headless notification writers for the whole staging time. **Recommend the in-transaction replan design.**

**B. Tombstone-aware no-op test (DPI-006).** Inside the transaction, count incoming tombstones that are *novel*: no local `(entity_type, entity_uid)`, or incoming `deletedAt >` local `deleted_at` (exactly the `importTombstones` upsert predicate at `:1301`). Proceed to apply when that count is > 0. This keeps "equal-second ties favour deletion" and indefinite typed tombstones intact, and it bumps `data_revision` so the next automatic backup carries the evidence. Optionally surface the count in the result (cosmetic; not required).

**C. Global pair completion (DPI-002).** Add one non-mutexed core (e.g. `completeGlobalPairsCore(exec)` in `src/db/field-values-dao.ts` or a new `src/db/pair-matrix.ts`). Run it after `upsertChildren` and before recency/journal work, inside the restore transaction:
- Scope: every contact (**including archived**) × every `custom_field_defs` row with `scope = 'global'` (**including quarantined**), where no `(contact_id, field_def_id)` row exists. Contact-scoped defs are excluded, matching `createContactFullCore`'s filter and ADR-090.
- Value `NULL`; never touch existing rows (INSERT … WHERE NOT EXISTS only).
- **Identity (planner call under D-11; recommendation):** use a **deterministic** UID derived from the pair's portable identity, e.g. `pair:<contactUid>:<fieldDefUid>`, and a deterministic timestamp `created_at = modified_at = max(contact.created_at, def.created_at)`. Reasoning:
  - ADR-056 rejects pair-key alias merges, so reconciliation throws a `pair-key-collision` incompatibility and **refuses the entire restore** when local and incoming carry the same pair under different UIDs (`reconciliation.ts:416-454`). Random `newUid()` seeding on two devices that each union the same graph would therefore make those devices *permanently unable to Merge each other's backups*. Deterministic identity makes independent seeding converge.
  - A seeded NULL can never beat a real edit, because every real value is written after both parents exist, so `modified_at ≥ max(created_at)`. On a same-second tie `newestRow` keeps local (strict `>` at `reconciliation.ts:294-302`).
  - Precedent: the wire already carries derived UIDs (`legacy-method:${uid}:${methodType}`, `backup-schema.ts:51`), and wire UIDs need only be non-empty strings.
  - D-11 says "fresh UIDs". Deterministic UIDs are fresh, non-colliding identities, so this reading stays inside the recorded call. If the planner reads "fresh" as random `newUid()`, the plan must record the cross-device refusal risk as an accepted tradeoff.
- Contacts' and defs' `created_at` are portable: exported (`export-manifest.ts:109,133`), inserted from the wire, and not rewritten on conflict (`restore-apply.ts:537-656`). The derivation is therefore stable across devices.

**D. Forward repair: migration 031 (D-11).** A new `src/db/migrations/031-<slug>.ts` performs the same completion as one frozen SQL statement, e.g. `INSERT INTO custom_field_values (uid, contact_id, field_def_id, value, created_at, modified_at) SELECT 'pair:' || c.uid || ':' || d.uid, c.id, d.id, NULL, max(c.created_at, d.created_at), max(c.created_at, d.created_at) FROM contacts c CROSS JOIN custom_field_defs d WHERE d.scope = 'global' AND NOT EXISTS (SELECT 1 FROM custom_field_values v WHERE v.contact_id = c.id AND v.field_def_id = d.id)`. When rows were inserted, bump `app_settings.data_revision` inline so the next automatic backup captures the repair. Per runbook pitfall 9 (`docs/runbooks/sqlite-migration-pipeline.md`), the migration must **not import** the runtime core. Its literal derivation is **test-pinned equal** to the runtime derivation, because a shipped migration must never change behaviour when runtime code evolves. It is idempotent on healthy databases.

ADR-056 (tombstones, pair-key collision refusal, tie → deletion) — **EXTRACTED** (`restore-apply.ts` cites it; graph flags ADR-056 as ⚠ partially superseded by ADR-060, which concerns method normalization and leaves the tombstone/pair policy intact). ## RG-010 — Canonical photo ownership across restore, merge and deletion

### Root causes (confirmed)
- **DPI-001:** The restore target needs `fieldType`/`colName`, which the exporter deliberately strips.
- **REL-001:** Cleanup is computed against the *pre-restore* graph and executed after new files land at the same ID-derived names, and delete intents are not idempotent.
- **REL-003:** Journal intents are never superseded by later normal writes, and the drain re-checks only target existence.
- **DPI-004:** Merge transfers path *strings*, not file ownership, and omits a sole absorbed main photo.
- **DPI-010:** Delete actions without a row, definition deletion/expiry, and purge after a photo→text type change never enumerate the files they orphan.

### Format question (D-10) — **no bump required**
Restore-side resolution fixes DPI-001 entirely within format 7, and it is needed **anyway**: backups already on users' SAF folders lack the metadata, and no wire change can repair them. Everything required is on the wire. A custom value row carries `uid`, `contactUid`, `fieldDefUid` and `photoBase64`, which the exporter sets only for defs of type `photo` at export time (`export-manifest.ts:203-212`). The incoming `customFieldDefs` rows carry `uid`, `colName` and `type` (`export-manifest.ts:133`). Every other RG-010 fix is local (DB + filesystem). **No owner escalation is triggered by B/D on format.** A planner who proposes adding `fieldType`/`colName` to exported value rows is making a wire-shape change (`types.ts:13`: "Bump only when the portable JSON wire shape changes") and must stop and escalate under D-10. It is also unnecessary.

### Recommended design (filenames unchanged per D-09)

**0. Pure path module.** Move `contactPhotoRelPath`, `customFieldPhotoRelPath`, `profilePhotoRelPath` and `restorePendingRelPath` (all pure string builders plus `isSafeColName`/`assertSafe*` checks) into a node-pure module, e.g. extend `src/db/photo-relative-path.ts`, and re-export them from `photo-storage.ts` for compatibility. `merge-dao.ts`, `purge-dao.ts` and `field-ddl.ts` are node-pure DAOs and must not import `photo-storage.ts`, which imports `expo-file-system` at module top (`photo-storage.ts:41`).

**1. Idempotent, reference-safe delete intents (REL-001, DPI-010, DPI-004).**
- Journal delete inserts become idempotent: `INSERT … ON CONFLICT(relative_path) DO NOTHING` for `delete:<path>` keys, and callers dedupe by canonical path.
- **Deletion predicate**, used identically by restore's immediate post-commit cleanup and by the foreground drain: delete a canonical file only if (i) no live row references it (`contacts.photo`, `profile.photo`, `custom_field_values.value`, compared as exact strings), **and** (ii) no pending `finalize` journal row targets the same canonical path. Otherwise retire the intent without deleting. The rule is "**delete by derivation, protect by any reference**". Deletion targets come only from ID-derived builders or from DB reference strings that pass `SAFE_RELATIVE`, never from free text. A text-typed value that happens to equal a path can only *protect* a file, never cause its deletion.
- Evaluate restore's immediate cleanup **after** the finalize loop, against the committed graph. This fixes REL-001's delete-after-persist without relying on loop order, which the RG notes forbid as the sole fix.

**2. Single owned-master write path (REL-003).** Add `persistOwnedMaster(sourceUri, canonicalRelative, { exec })` (name illustrative). It runs inside a **process-local per-canonical-path async lock**, the same pattern as `withBackgroundFinalizationLock` in `background-finalization.ts:20-37`:
  1. In a short `inWriteTransaction`, delete every journal row whose `canonical_relative_path` equals the target (both `finalize` and `delete`). This is the supersession.
  2. Call `persistMaster` (unchanged `.tmp`/`.bak` swap).

  Route every canonical writer through it: `CropPhotoScreen` (contact/profile/customField via `persistCroppedMaster`), `import-photo.ts:111-115`, `reconcile-photo.ts:78-86`, the merge re-home finalize, and restore finalize. The journal drain's finalize takes the **same lock** and re-reads that its journal row still exists before touching bytes. A newer crop then always wins in either interleaving. Custom-field picks persist at crop time and commit the value only on form Save; supersession at *persist* time covers them, and the documented cancel-path tradeoff (`docs/systems/photos.md` Gotcha 4) is unchanged.
  - Callers must not already hold a transaction. All listed writers call persistence outside/post-commit (verified: `CropPhotoScreen.tsx:268-285`, `reconcile-photo.ts:77` "Promote after the main DB apply transaction has committed", `import-photo.ts` post-commit per ADR-065, `restore-apply.ts:1601+`).
  - Normal *removal* flows (`PhotoSourcePicker.tsx:169-185`) should also supersede intents for the path they clear.

**3. Restore target resolution (DPI-001).** In `targetFor`/staging, treat a `custom_field_values` row with `typeof row.photoBase64 === "string"` as a custom-photo candidate. Resolve `colName` from the incoming `customFieldDefs` row with `uid === row.fieldDefUid` (fall back to the local def). `canonicalFor` keeps deriving `cv-<destinationContactId>-<col_name>` from the **destination** IDs inside the transaction, so changed/reused integer IDs are handled.
  - ⚠ **Edge to decide and test:** the winning final def is *not* type `photo` (local def newer and type-changed). Today `canonicalFor`'s `d.type='photo'` filter returns null and the transaction **throws** (`:1554-1555`), failing the whole restore. Recommended: derive the `cv-` path regardless of the current def type and write the path as the raw value. That mirrors what a local photo→text change leaves behind (ADR-001 raw TEXT), and the drain's `targetIsLive` gets the same relaxation. The alternative is to skip the bytes and count them in `photosNeedingAttention`. Either way, **never abort the restore and never silently drop bytes**.

**4. Row-less and cascaded restore deletes (DPI-010).** Inside the transaction, **before** `deleteActions`, enumerate delete intents from *local* state:
  - contact delete action → the stored `contacts.photo`, `contact-<id>.jpg`, and `cv-<id>-<col>` for **every** def. The cascade removes value rows without row-level actions (`ON DELETE CASCADE`, migration 006:45).
  - custom value delete → the stored value if `SAFE_RELATIVE` plus the derived `cv-<contactId>-<col>`.
  - def delete (tombstone) → the derived `cv-` path for every value row of that def.

  All are idempotent intents drained under the predicate.

**5. Merge re-homing (DPI-004, D-09).** Use restore's commit-then-finalize boundary. This is exactly the SYNTHESIS constraint "recovery ownership before canonical file mutation".
  - *Before the transaction* (UI layer or a service wrapper around `mergeContacts`): stage copies of the absorbed main photo and of absorbed photo-typed custom values into the pending namespace. `stageRestorePending(srcUri, relative)` already exists at `photo-storage.ts:178-196`; the target is `{ kind: "contact", uid: survivorUid }` or the custom form, with a merge session token.
  - *Inside `mergeContacts`' transaction:* re-verify that the staged source strings still equal the absorbed rows. On mismatch, throw so the UI shows the existing "Nothing was changed" message. Set the survivor's reference to its **own derived path**: `contact-<S>.jpg` via `setContactPhotoCore`, or the pair value `cv-<S>-<col>` via `upsertValueCore`, which never rewrites the pair UID. Insert `finalize` journal rows (target = survivor UID / survivor pair UID). Insert `delete` intents for the absorbed identity's derived files: `contact-<A>.jpg` and `cv-<A>-<col>` for all defs.
  - *Post-commit:* finalize through `persistOwnedMaster`, then drain the deletes under the predicate. On crash, the existing foreground drain completes both.
  - **Sole-absorbed adoption:** when `survivor.photo IS NULL`, `absorbed.photo IS NOT NULL` and there is no explicit `"keep-survivor"` resolution, adopt and re-home. This mirrors the scalar auto-combine at `merge-dao.ts:453-472` and ADR-069's non-conflicting combine requirement.
  - **Harden the input contract:** derive the absorbed path from the DB row inside the transaction. Treat `resolutions.photo` as a *choice* only, never as a path. Today a navigation param `relative` flows straight into `setContactPhotoCore` guarded only by `SAFE_RELATIVE` (`merge-dao.ts:109-120,483-489`).
  - Custom photo re-homing applies to defs whose **current type is `photo`**. Rewriting a type-changed (text) value that happens to hold a path would rewrite raw TEXT, which ADR-001 forbids. Leave it, and let the delete predicate protect the file. Treat any proposal to rewrite it as owner-bucket.
  - If the absorbed canonical file is missing, "no bytes to adopt" should keep the survivor's current photo and proceed rather than refuse the merge. This is a planner call; document it.

**6. Purge and definition lifecycle (DPI-010).**
  - `purgeContact` (in its transaction) enqueues idempotent delete intents for `contact-<id>.jpg`, the stored `contacts.photo`, and `cv-<id>-<col>` for **every** def (any type, incl. quarantined and contact-scoped). This covers photo→text-then-purge. The post-commit `onPurgeExtensions` photo adapter then drains immediately (best effort), and the foreground drain retries. This makes ADR-021's best-effort cleanup durable without changing its semantics.
  - `dropFieldValues` (`field-ddl.ts:112-189`, shared by `dropField`, `deleteOrQuarantineField` and `expireFieldIfStale`) enqueues intents for the derived `cv-<contact_id>-<col_name>` of every value row it deletes, in the same transaction as its existing `field_history` snapshot and tombstones.
  - `applyTypeChange` must **not** delete anything (raw TEXT stays; the reference-protect rule covers the file).

**7. Legacy aliased references (existing damaged data).** Merges performed before this fix left survivors referencing `contact-<absorbedId>.jpg` / `cv-<absorbedId>-<col>`. Fixes 1–6 prevent *new* aliasing, and the delete predicate stops purge from deleting a file another row references. A new contact that reuses the absorbed ID can still **overwrite** the aliased bytes on its first photo save. A one-shot foreground re-home sweep would close that: detect `contacts.photo != contact-<id>.jpg`, stage, journal and finalize. See Open Questions. It is enforcement, not a filename change, but it mutates canonical files on existing devices.

### Journal reuse (no schema change)
Reuse `restore_photo_journal` for merge, purge and definition-deletion intents. Its columns are generic (target kind + UIDs + canonical path + action), the `target_kind` CHECK already admits `contact`/`profile`/`customField`, and pending paths reuse `SAFE_RESTORE_PENDING_RELATIVE`. The name becomes a misnomer; document the widened semantics in `docs/systems/photos.md` / `backup-restore.md` (and a superseding ADR at KB extraction). A generic new table in migration 031 is possible but adds churn with no capability gain.

### Governing ADRs
ADR-021 (derived filenames, `.bak` swap, best-effort cleanup — INFERRED via `photo-storage.ts`/`purge-photo-cleanup.ts` Key files). ADR-058 (committed journal recovery — INFERRED). ADR-069 (atomic merge — INFERRED for `merge-dao.ts`). ADR-112 (DB-aware reconciliation; prefer a bounded leak over deleting a possibly referenced file; no filesystem work inside the SQLite transaction — INFERRED). ADR-001 (raw TEXT; accepted definition-deletion orphan — INFERRED). ADR-065 (import photo retry input — INFERRED; touched by persistence routing). `docs/systems/photos.md` Gotchas 3, 4, 7, 8, 11, 12.

### Decision-reversal risk
- **None as designed.** Filenames are unchanged, raw TEXT is preserved, the cancel tradeoff is kept, and there is no format bump.
- ⚠ Any of the following comes back to the owner: random/UID filenames (ADR-021 rejected; D-09); rewriting type-changed raw values; deleting a file on a type change; adding wire fields (D-10).

### Sizing
Primitives (0–2) **M**; restore media (3–4, on top of the RG-009 restructure) **M**; merge re-home (5) **M–L**; purge/definition deletion (6) **S–M**; legacy alias sweep (7) **S–M**, only if the owner opts in.

## RG-016 — Bootstrap and foreground maintenance failure boundaries

### Actual sequence (verified)

**Cold start (`App.tsx:169-211`):** `openAndMigrate(getDeviceRegion())` → then `Promise.all([hydrateThemeAtBoot(...), loadAppFonts(), runBackgroundReconciliation(getExecutor())])` → `useThemeStore.getState().hydrate(...)` → `setReady(true)`. |---|---|---|---|
| 1 | field sweep (quarantine expiry + `field_history` prune) | 224-227 | per-def catch only; candidate read + prune **uncaught** |
| 2 | memory/relationship trash | 231-234 | per-item catch; candidate scans **uncaught** |
| 3 | interaction-assist prune | 238-241 | **none** |
| 4 | photo `.tmp/.bak` reconcile | 245-248 | whole-hook catch |

| 7 | restore-photo journal drain | 266-269 | whole-hook catch |

Then it awaits `ensureChannels()` + `ensureNotificationCategories()` (caught), then `installSweepTrigger(AppState)` (`:331`), which fires `void runLaunchSweep()` immediately and on each real `background→active`.

### Genuine dependencies (the RG asks to establish them)
- **Backup requires background reconciliation.** Recorded at `App.tsx:257-259`: a committed restore marker must never be exported. Today hook 5 swallows its own failure, so hook 6 runs anyway. It then fails inside the export: `readStoredPhotoBase64` → `resolveBackgroundUri` → `assertBackgroundRelative` rejects the pending path. `writeVerifiedSnapshot` catches and returns `failed`, and `backup-sweep.ts:66-75` records the **misleading** health diagnostic "Unable to access the backup folder."
- **Backup should also follow restore-photo finalization (new finding, in scope as sequencing).** Hook 7 runs *after* hook 6. With finalize rows pending, export reads the canonical avatar file, which is either missing (→ backup failed with the misleading folder diagnostic) or holding **older bytes** (→ the automatic backup silently captures a stale photo). Recommend moving the drain registration before backup **and** declaring it a prerequisite.
- Everything else is independent and must keep running after a failure. `photo .tmp/.bak` reconcile before the drain is a sensible order but not a hard prerequisite: `persistMaster` tolerates a stale `.bak`.

### Recommended design
1. **Runner contract (`launch-sweep.ts`).** `registerSweepHook(fn, { id?, requires?: string[] })` stays backward compatible. Each hook runs in its own `try/catch`. Failures are recorded per pass and logged content-free through `Logger`. A hook whose `requires` includes an id that **failed or was skipped in this pass** is skipped (logged), not run. `pendingRerun` must survive a failing hook: the pass completes, then the `do…while` drains the queued rerun. Keep the `running` reset in `finally`. Both trigger sites attach `.catch(Logger…)` so there are no unhandled rejections. Order stays sequential, with no parallelization and no timers.
   - This is not the "blanket catch / unconditional continuation" the RG forbids: continuation is conditional on declared dependencies, failures stay observable, and bootstrap integrity handling is untouched.
2. **Background reconciliation reports failure instead of masking it.** Per-candidate/per-action `try/catch` inside `runBackgroundReconciliation` (plan actions loop `:43-49`, pending loop `:55-63`) lets one bad artifact stop blocking the others. It returns a summary (e.g. `{ failed: n }`). The registered hook rethrows or returns a failure status the runner records, so backup (`requires: ["background-reconcile"]`) is held for that pass. Ownership checks, exact pending markers and CAS finalization stay unchanged (`background-finalization.ts`). `deleteBackgroundRestorePending` failures are contained at the call site; stale pending debris is an accepted bounded leak (ADR-112 Consequences).
3. **Bootstrap split (release-readiness/AUD-REL-001).** Extract the chain into a node-testable orchestrator (e.g. `src/app/bootstrap-sequence.ts` with injected `openAndMigrate`, `hydrateTheme`, `loadFonts`, `reconcileBackgrounds`). Migration and settings/theme hydration stay **fail-closed**: their rejection still sets the error state, and the 006-integrity branch is untouched. Background reconciliation still runs **before** `ready` ("keep successful recovery before presentation"), but its rejection or partial failure is logged and readiness proceeds. Presentation already falls back safely: `profile-presentation-read.ts:72` excludes `profile-backgrounds/_restore_pending/*/*.jpg` from visible templates, and `resolve-presentation.ts` falls through missing references (audit counterevidence). The cold-start sweep retries right after `ready`.
4. **Hook hygiene (optional, low risk).** Once the runner isolates hooks, the uncaught internals in field/memory/assist/backup no longer starve others. Still consider catching `backup-sweep`'s health-write failure so it does not mask the backup result. Keep `field-sweep`'s documented non-nesting (`field-sweep.ts:13-35`).

### Governing ADRs
None recorded for `launch-sweep.ts`/`App.tsx` (graph: "NOBODY WROTE IT DOWN"). The contract lives in `docs/systems/persistence-core.md` "Running launch maintenance" (`:152-156`), ADR-112 (sweep after migration readiness; bounded debris; fallback — INFERRED for `background-reconcile-sweep.ts`), ADR-083 (restore-before-paint) and ADR-001 (bootstrap failure states keep navigation unmounted with accurate guidance — must stay).

### Decision-reversal risk
- None as designed.
- ⚠ **Risk-posture question (owner):** *state-based* backup holding — skipping automatic backups whenever any restore finalize row or pending background marker exists, not just when a prerequisite failed in the current pass. It protects backup fidelity but can **block automatic backups indefinitely** if one artifact never recovers. That changes the user's protection posture, so it is the owner's call. The per-pass dependency hold recommended above does not have this failure mode.

### Sizing
**M** (runner + tests, background containment + tests, bootstrap extraction + tests, App wiring).

```
│ reconcile → normalize → category fallout → cadence → name-collision gate │
│ no-op? (rows=0 AND settings not newer AND novel tombstones=0) → return   │
│ capture delete intents from LOCAL state (incl. row-less + cascades)      │
│ deletes / importTombstones / upserts                                     │
│ completeGlobalPairsCore (deterministic pair identity)                    │
│ recency recompute                                                        │
│ journal: finalize (winning staged files only) + idempotent delete intents│
│ settings (if newer / replace-all) ; bump data_revision                   │
└──────────────────────────────────────────────────────────────────────────┘
        ▼ commit
Finalize (per-path lock, re-check journal row) ──► canonical avatars (.tmp/.bak swap)
        ▼
Delete intents: delete iff no live reference AND no pending finalize for path
        ▼
Release session; unused staged files → deleted (or orphan drain)
        ▼
Schedule/digest reconcile ──► result {counters…} ──► RestorePreview:
        publish committed theme from SQLite ──► navigate RestoreResult (qualified outcome)
```

```

        │  persistOwnedMaster(canonical)
        ▼

                                    ▲
Journal drain (foreground) ─────────┘ same lock; re-read row; finalize or reference-safe delete
```


### Anti-patterns to avoid
- **Fixing REL-001 by reordering loops.** The RG says explicitly this does not establish ownership.
- **Opening `inWriteTransaction` inside `mergeContacts`/`applyRestore` for journal work.** Use `*Core` bodies within the one outer transaction.
- **Bare journal `DELETE`s outside a transaction on the shared connection.** Existing code does this at `restore-apply.ts:1610,1619,1646` and `restore-photo-finalize-sweep.ts:46,58,63,69`. A bare statement issued while another writer's `BEGIN` is open joins that transaction (the P4 capture pitfall `mutex.ts` exists to prevent). New code should wrap journal mutations in `inWriteTransaction` (never nested).
- **Deleting a file because its field's current type is not `photo`** (DPI-010 planning note; ADR-001).
- **Trusting UI-supplied paths** (merge `resolutions.photo.relative`).

## Common Pitfalls

### Pitfall 1: Orphaned test consumers pinned to schema 30
**What goes wrong:** Adding migration 031 breaks tests that assert the literal head.
**Where:** `src/db/migrations/full-chain.test.ts:87` (`expect(TARGET_VERSION).toBe(30)`), `src/db/migrations/029-ai-configuration.test.ts:22,28`, `src/db/migrations/030-your-week-period.test.ts:25`, and **source-text pins** in `src/category-identity-audit.test.ts:215-225` (`"TARGET_VERSION = YOUR_WEEK_PERIOD_SCHEMA_VERSION"`, `"migration030"`, `"expect(TARGET_VERSION).toBe(30)"`, `BACKUP_FORMAT_VERSION\s*=\s*7`).
**Avoid:** Update every one in the same plan as the migration (memory: orphaned-test-consumer build-breaker). Run `npx tsc --noEmit` **and** the full vitest suite in the post-merge gate.

### Pitfall 2: Source-text pins on `restore-apply.ts`
`category-identity-audit.test.ts:234-241` requires `restore-apply.ts` to contain `if (entity === "categories") continue` and `clearLiveCategoryTombstones`, and not `SEED_CATEGORIES`. `src/db/lifecycle-consumer-ledger.test.ts` maps every production file referencing `interval_days` / `tracking_enabled = 0|1` to an owner (`restore-apply.ts`, `merge-dao.ts` entries at `:106-117`). Extracting restore planning into a **new** module that references `interval_days` requires a new ledger entry.

### Pitfall 3: The journal drain deletes in-flight staging
`drainRestorePhotoJournal` deletes every pending file not in the journal (`restore-photo-finalize-sweep.ts:88-93`). A `background→active` transition during restore or merge staging (before commit) deletes the staged bytes. After commit, finalize fails and the next drain's "pending absent ⇒ finalization succeeded" branch (`:61-65`) retires the journal row, so **the photo is never written**. This is an existing latent defect, and it becomes more likely once merge also stages. **Avoid:** a process-local registry of in-flight session tokens that the orphan cleanup skips, released in `finally`.

### Pitfall 4: Nested mutex
`mergeContacts` and `applyRestore` already own `inWriteTransaction`. Journal inserts, pair completion and intent capture must be `*Core` calls. `persistOwnedMaster` opens its own transaction and therefore must be called only post-commit/outside.

### Pitfall 5: Node-pure DAOs importing native modules
`merge-dao.ts`, `purge-dao.ts` and `field-ddl.ts` are tested without Expo mocks (`merge-dao.test.ts` runs the real chain). Importing `photo-storage.ts` drags in `expo-file-system`. Move the builders to a pure module (design step 0).

### Pitfall 6: Throwing inside the restore transaction for photo-target anomalies
`canonicalFor` returning null currently throws "restore photo target disappeared before commit" (`restore-apply.ts:1554-1555`), aborting the whole restore. Once DPI-001 makes custom photos reach this path, a type-changed local def would turn valid restores into failures. Decide the rule (RG-010 §3) and test it.

### Pitfall 7: Seeding pairs with random UIDs
See RG-009 C: this creates future `pair-key-collision` refusals between devices. If random UIDs are chosen, document the tradeoff.

### Pitfall 8: Migration importing runtime derivation
Runbook pitfall 9: a shipped migration must not change behaviour when runtime code evolves. Inline the SQL and test-pin its equality to the runtime core.

### Pitfall 9: Theme publication claiming failure after commit
If `getAppSettings`/`hydrate` throws after `applied`, show the committed result anyway. Never route to `restoreApplyRecovery` ("Your local data hasn't changed") after commit.

### Pitfall 10: `pendingRerun` loss on failure
The fix must keep the rerun even when a hook in the current pass fails. Test with a failing first hook plus an overlapping `runLaunchSweep()` call.

### Pitfall 11: Wrong-identity bytes during a failed Replace-all finalize
When a Replace-all finalize fails and the canonical path is referenced by the new graph, the old file (possibly a *different person's* photo, because of ID reuse) stays visible until recovery. Planner discretion: on finalize failure, best-effort delete the canonical file when the pre-restore owner UID differs from the post-restore owner (initials fallback), keeping the journal finalize row for retry. This needs a pre-write owner snapshot inside the transaction.

### Pitfall 12: Timestamp helpers
Journal `created_at`, merge `now` and migration seeds use `localDateTime()` / existing row stamps, never `toISOString()`.

## Open Questions (owner-bucket items surfaced up front)

1. **Existing incomplete-pair backup files stay unrestorable** (the completeness guard is correctly unchanged). Recommendation: after migration 031 ships, tell the user to re-export. Relaxing the guard is out of scope and would be an owner decision (RG-009 "Explicitly Out of Scope").
2. **Legacy aliased photo references from pre-fix merges.** Should a one-shot foreground re-home sweep repair them, mutating canonical files on existing devices? It is enforcement of ADR-021, not a filename change, but it is a one-way file mutation on devices we cannot reach, so it is the owner's risk call. Recommendation: yes, bounded and journaled, with the reference-safe predicate; otherwise document the residual overwrite-on-ID-reuse risk.
3. **State-based holding of automatic backup** while restore recovery is pending (versus the recommended per-pass prerequisite hold). This is a backup-protection posture change (could block backups indefinitely), so it is owner-bucket if proposed.
4. **Type-changed winning def with incoming photo bytes** (RG-010 §3): write the derived path as raw TEXT (recommended) or count as `photosNeedingAttention`. This is a planner call within the raw-TEXT rule. Rewriting *existing* raw values is owner-bucket.
5. **D-11 identity reading:** recommend deterministic pair UIDs (see RG-009 C). This is a planner call; if random UIDs are chosen, record the cross-device Merge-refusal tradeoff in the plan.
6. **Out-of-scope observations (not fixed here; note for triage):** `MergeConflictsScreen.tsx:92-107` shows photo-typed custom fields as text conflicts of raw path strings. `merge-dao.ts:298` deletes a losing survivor method without a tombstone (mitigated by restore `normalizePlan`). `backup-sweep.ts:66-75` reports "Unable to access the backup folder." for export failures that are not folder problems.
