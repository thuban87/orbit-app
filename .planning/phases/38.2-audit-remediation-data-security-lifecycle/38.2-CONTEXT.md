Harden persistence, native trust boundaries, restore/merge, file ownership, import/export
lifecycle, notification lifecycle, and transactional edit semantics across failure, retry,
deletion, restore, and process-lifecycle boundaries — without weakening any existing
privacy/security/integrity control.

reconciliation (RG-017, RG-018, RG-043).

<decisions>
## Implementation Decisions

Restated from the dossier and the audit synthesis — not new owner rulings. Owner rulings from the
discuss session get appended here as D-07+.

- **D-01:** The authoritative contract is the 38.2 dossier. Per-group detail is
  `docs/audits/2026-09-pre-release/synthesis/REMEDIATION-GROUPS.md` (RG sections listed above);
  finding evidence is in the linked `*/DOMAIN-AUDIT.md` packets. Plan against the dossier; use the
  RG sections for outcomes, constraints, and verification expectations.
- **D-02:** Preserve original RG and **packet-qualified** finding IDs in every plan
  (e.g. `security/AUD-SEC-006`, never bare `AUD-REL-00N` — reliability-testing and
  release-readiness collide on REL-001..003). One phase, several plans — not eighteen mini-phases.
- **D-03:** The synthesis "Constraints that must survive remediation" list is binding: local/offline
  reads, no backend or content telemetry, explicit configured AI invocation, SecureStore and
  endpoint binding, optional backup encryption + Android backup opt-out, raw-TEXT normalized custom
  values with stable pairs, immutable shipped migrations, transactional history/recency and
  deletion evidence, non-reentrant write composition, foreground-only sweeps, recovery ownership
  before canonical file mutation, preserved user-controlled external backups. A fix that weakens
  any of these is a decision reversal, not a bug fix — stop and ask.
- **D-04:** Schema changes are forward-only. Never write a literal migration number — verify head+1
  against `src/db/migrations/` + `TARGET_VERSION` at plan time (as of 2026-09-23: head 030,
  `TARGET_VERSION` 30, `BACKUP_FORMAT_VERSION` 7). Any backup wire-format change (plausible under
  RG-009/RG-010) is an owner decision, not a side effect.
- **D-05:** Investigation gate — **RG-005** (`security/AUD-SEC-006`) is INVESTIGATE: reproduce
  legacy-key → migration/restore → readiness → generation with synthetic keys and a recording
  transport (never real credentials). Disproven → document and close; confirmed → remediate here.
- **D-06:** RG-009 and RG-010 are coordinated but not interchangeable: never solve media ownership
  by weakening graph integrity or vice versa; both need explicit regression coverage.
- **D-07 (owner, 2026-09-23) — RG-007 retrospective consent: leave existing rows as-is.** Fix is
  forward-only: every imported-note creation path (single, bulk, consolidated) writes `allow_ai=0`
  regardless of the general Memory default. No migration or sweep touches existing imported rows'
  `allow_ai` — no blanket reset, no `modified_at == created_at` heuristic reset. The per-item toggle
  remains the correction path.
- **D-08 (owner, 2026-09-23) — RG-005 remediation policy if the investigation confirms reachability: preserve provenance, else require re-entry.**
  Bind a legacy unbound Custom key to its original
  endpoint before restore replaces endpoint metadata; where that original endpoint cannot be
  established, the legacy key fails closed and the user must re-enter it. Never blanket-delete
  credentials; bound keys and other providers' keys are untouched. If the investigation disproves
  reachability, document and close (D-05) — D-08 then does not apply.
- **D-09 (owner, 2026-09-23) — RG-010 keeps ADR-021 identity-derived photo filenames.** No
  filename-policy change (random/UID naming stays rejected per ADR-021). Merge must re-home absorbed
  main/custom photo bytes into the survivor's derived paths (`avatars/contact-<survivorId>.jpg`,
  `avatars/cv-<survivorId>-<col>.jpg`) with ADR-021's crash-safe swap/reconcile discipline, so ID
  reuse can never alias a live file. Any plan that needs a different naming scheme stops and asks.
- **D-10 (owner, 2026-09-23) — No backup wire-format change is pre-approved.** Plan RG-009/RG-010
  within `BACKUP_FORMAT_VERSION` 7 (e.g. resolve custom-photo restore targets from the contact/
  definition UIDs already on the wire). If research or planning finds a format bump is genuinely
  required, STOP and escalate to the owner before planning it.
- **D-11 (planner call, 2026-09-23) — RG-009 forward repair.** Existing databases left without
  complete global custom-field pairs by a prior Merge may be repaired by a new forward-only
  migration that seeds the missing NULL pairs (fresh UIDs, never touching existing pairs/values).
  This enforces ADR-001's invariant — it is not a reversal — so it is in scope at planner
  discretion; migration number = verified head+1 (D-04).
- **D-12 (2026-09-23) — Triage record.** The dossier's Coverage list is the owner's selection for
  38.2; recorded in `docs/audits/2026-09-pre-release/synthesis/TRIAGE.md` "Selected for Remediation".

Owner rulings from the plan-phase research batch (2026-09-23, surfaced by `38.2-RESEARCH-{A,BD,CE}.md`):

- **D-13 (owner) — RG-014 export staging lifetime:** a handed-off manual export is retired at the
  first foreground sweep ≥ 24 h after its creation, or on the next manual export, whichever comes
  first. User-owned backups (SAF folder and external destinations) are never touched.
- **D-14 (owner) — RG-012 photo-retry surface is minimal:** reuse the existing ImportComplete Retry
  with photo-only eligibility, and add one explicit "Skip remaining photos" discard action. 38.2
  provides the capability and this minimal surface; fatal-state presentation remains RG-035 (38.3).
- **D-15 (owner) — RG-043 bulk reconcile:** multi-option scalar fields (birthday/name with more than
  one source value) are excluded from bulk "Use contact values"/"Apply recommendation". The card
  stays `partial` for explicit per-field review, and bulk apply never writes NULL for them.
- **D-16 (owner) — RG-013 scope:** generated derivatives **plus** the `contact-picker-*.photo` raw
  source copies. `expo-image-picker` cache copies and `photo-dl` downloads are recorded follow-ups
  unless trivially co-located, and `photo-dl` belongs to RG-003's file.
- **D-17 (owner) — RG-010 legacy alias repair:** yes. A one-shot, bounded, recovery-journaled,
  idempotent foreground re-home sweep repairs custom-photo references that aliased another
  contact's derived file after pre-fix merges. It re-homes only where the reference-safe ownership
  predicate proves ownership. ADR-021 filenames are unchanged.
- **D-18 (owner) — RG-016 backup hold is per-pass:** within each launch/foreground pass, restore-
  photo recovery runs before auto-backup. A recovery failure in one pass does not suppress backup
  in later passes. There is no state-based indefinite hold.
- **D-19 (owner) — RG-002 ingress ceiling is measured, then signed off:** the plan includes a
  measurement task covering real export sizes and Hermes parse memory, which proposes
  `MAX_BACKUP_INGRESS_BYTES` and a stall deadline, then stops at a `checkpoint:decision` for owner
  sign-off before the cap is enforced. Moving the copy off the main/JS thread, the stall deadline,
  and cleanup of both copies are not gated on that checkpoint.
- **D-20 (owner) — RG-003/RG-004 device proof:** a third-party public HTTPS test host
  (httpbin-style) may be used during device UAT with synthetic payloads only. No contact data is
  sent, no AI provider is involved, and no real credentials are used.
- **D-21 (planner call, enforcement) — D-11 pair identity:** seeded missing pairs use deterministic
  UIDs derived from `(contactUid, fieldDefUid)` rather than random UIDs, so that independent repairs
  on two devices do not create ADR-056 Merge collisions. Migration 031 embeds the same SQL frozen,
  with a test pinning its equality to the runtime seeding. The existing-damaged backup files remain
  refused by the (unchanged) completeness guard; the remedy is to re-export after 031.
</decisions>
