## Summary

All eleven source findings behind these seven RGs are confirmed against current HEAD (`1bb2044`). Every cited file:line still points at the described code. `reliability-testing/AUD-REL-011` was reproduced in the scratchpad with the real helpers: due=2026-09-22, now=2026-09-22 12:00, delivery 09, quiet 21→08, stagger 5 gives **2026-09-23 09:05**, not the next weekly tick. None of the fixes requires a new package, a backup-format change or (as recommended) a schema migration. The shared theme is **lifecycle ownership**. Each copy of sensitive data (import payloads, staged photos, ImageManipulator cache files, picker cache copies, export staging, presented notifications) needs an explicit owner. That owner retires the copy on success, failure, restart and purge. It must never retire a copy that live work still needs.

Workstream E is about **write-semantics parity** and **committed-baseline discipline**. The rapid editor and the complete editor must apply the same atomic domain semantics: retained-value history and Bind/Unbind events. After any committed write, the editor coordinator must advance its diff baselines from what the write *returned*. It must not re-derive them from a later read that can fail. RG-043 is a transport bug: the classifier collapses several source options into `sourceValue: null`, and the UI gives every option `id: 'source'`. The chosen option's identity is lost, so apply writes NULL.

**Primary recommendation:** Keep every fix schema-free and inside the existing DAO/`*Core` composition rules:
- Put every new cleanup behind a namespace-guarded delete helper.
- Register every new sweep through `launch-sweep` under Workstream D's failure-containment contract.
- Extract the EditContactScreen save sequence and the reconcile selection builder into node-testable modules, so the audit's "run the actual coordinator" verification is automatable in vitest.

## Owner-bucket flags (surface once, batched — do not drip-feed)

1. **RG-014 staging grace period (privacy retention vs. backup-delivery reliability).** Android gives no "receiver finished reading" signal: `shareAsync` resolves identically for shared and dismissed. So retiring a handed-off export needs a time-based grace constant. Too short can silently break a queued Drive/Gmail read of a backup the user believes they saved. Too long retains a plaintext snapshot. **Recommend** default = retire at the first foreground sweep ≥ 24 h after creation, plus on the next manual export. The owner should confirm the number. This is a risk/privacy posture choice, not a pure engineering call.
2. **RG-012 photo-retry user surface.** Making photo work durably retryable needs a user-visible path: an extended Retry on ImportComplete and possibly the resume prompt. It also needs an explicit "Skip remaining photos" discard. That is new copy and flow. RG-035 (38.3) owns fatal-state *presentation*, but 38.2 must provide the retry/discard *capability*. **Recommend** the minimal variant: reuse the existing Retry button with photo-only eligibility and add one explicit discard action. Owner confirms copy.
3. **RG-043 bulk-grid ambiguity.** Today "Use contact values"/"Apply recommendation" in `ReconcileGridScreen` silently no-ops multi-option scalar fields, writes a NULL reviewed snapshot and can mark the card resolved. **Recommend** excluding multi-option scalars from bulk source-apply (the card stays `partial` for explicit detail review). This enforces ADR-068's "deliberate selections"; it does not reverse it. It is still a visible behavior change, so name it to the owner.
4. **RG-013 scope edge.** The cited finding covers generated *derivatives*. The same unmanaged-copy pattern exists for raw *source* copies:
   - `contact-picker-*.photo` in the app cache (Orbit's own native module)
   - `expo-image-picker` cache copies
   - `Paths.cache/photo-dl` downloads, which are RG-003's file in Workstream A

   **Recommend** including the contact-picker temp copies, which are clearly in the import/reconcile lifecycle, and recording the other two as follow-ups unless the planner finds them trivially co-located. This is a scope call.
5. **No decision reversals are required by any recommended fix.** Reversal traps are listed per RG ("Decision-reversal risk") so the planner/checker can police them.

## RG-012 — Import workflow retention, purge and photo retry

### Verified code locations
- Row schema [VERIFIED: src/db/migrations/012-import-sessions.ts, read this session]:
  `row_status TEXT NOT NULL DEFAULT 'pending' CHECK (row_status IN ('pending', 'imported', 'linked', 'skipped', 'failed', 'needs_review'))`;

  `contact_id INTEGER REFERENCES contacts(id) ON DELETE SET NULL`;
  `photo_failed INTEGER NOT NULL DEFAULT 0 CHECK (photo_failed IN (0, 1))`;
  `session_id INTEGER NOT NULL REFERENCES import_sessions(id) ON DELETE CASCADE`.
- Payload contents: `acceptPickedContacts` stores `JSON.stringify({ displayName, methods, birthday, note })` in `source_payload` [VERIFIED: src/services/import/import-acquire.ts:91-96].
- Commit-then-photo: `importRowAsNew` → `importContactRecord` → `persistImportedPhotoPostCommit` → `markRowPhotoFailed` on failure [VERIFIED: src/services/import/import-driver.ts:88-117]. The same pattern appears in `commitSingleImport` [import-acquire.ts:137-161] and `combineCluster` [source-consolidation.ts:269-287].
- `markRowPhotoFailedCore` sets only `photo_failed = 1` [VERIFIED: import-session-dao.ts:256-266]. Success path: `retireRowStagedPhoto` sets `photo_rel_path = NULL` [import-session-dao.ts:278-290; import-photo.ts:116].
- Sweep liveness `r.row_status IN ('pending', 'needs_review', 'failed') AND r.photo_rel_path IS NOT NULL` in a non-discarded session [VERIFIED: contact-import-resume-sweep.ts:93-100]. Imported rows with unfinished photos are **not live**, so their staging is deleted.
- Retry: `eligibleStatuses: ["pending", "failed"]` [ImportCompleteScreen.tsx:92]. The driver skips `row.contactId !== null` [import-driver.ts:145]. So no photo-only retry exists.
- `commitSingleImport` calls `completeSession` unconditionally [import-acquire.ts:162].
- Purge: `purgeContact` deletes canonical children + `field_history` and never touches `import_session_rows` [VERIFIED: src/db/purge-dao.ts:277-364]. Import rows are detached by `ON DELETE SET NULL` with their payload intact.

- Every SQL writer of `import_session_rows`/`import_sessions` was enumerated by grep: `import-session-dao.ts` (all transitions), `imported-contact-dao.ts` (via `setRowContactCore`/`setRowMatchOutcomeCore`), `source-consolidation.ts`, `bulk-review-dao.ts` (reads/resolutions), `restore-apply.ts:1252-1253` (Replace-all delete). ### Root cause
**CONFIRMED.**
- DPI-008/REL-004: photo liveness is keyed on `row_status`, but photo failure and interruption leave `row_status='imported'`.
- DPI-007: purge relies on FK `SET NULL`, which preserves payloads. Merged-origin rows detach at merge time, so even a correct `contact_id = X` purge filter misses them.

Additional findings (not in the audit, verified):
- (a) In `combineCluster`, only the first row with a photo is mastered. Other cluster rows keep a non-null `photo_rel_path` forever [source-consolidation.ts:200]. Any predicate like "imported AND photo_rel_path IS NOT NULL" would wrongly treat them as live.
- (b) `candidates_json` on still-pending `needs_review` rows keeps the purged contact's integer id [DuplicateReviewScreen.tsx:31 `type DurableCandidate = { contactId: number; signals?: string[] }`]. `contacts.id` is `INTEGER PRIMARY KEY` without AUTOINCREMENT [migrations/011-contact-lifecycle-schema.ts:18], so a reused id could surface a *different* person as a duplicate candidate.
- (c) A photo-only retry that calls `persistMaster(…, contactPhotoRelPath(contactId))` writes bytes to the derived path **before** any DB check [import-photo.ts:111-115]. A retry for a contact whose user has since set a photo would overwrite that file.

### Recommended fix approach (schema-free)
1. **Photo liveness predicate (separate from contact-resolution liveness):** "photo work outstanding" ⇔ `row_status = 'imported' AND contact_id IS NOT NULL AND photo_rel_path IS NOT NULL`. This covers an interruption after commit (flag still 0) and a recorded failure (flag 1). `photo_failed` stays an informational "an attempt failed" flag.
   - Make it true only for the row whose photo is actually pending. In `combineCluster`'s commit transaction, set `photo_rel_path = NULL` on every non-photo cluster row and return those paths for post-commit deletion. In `linkExistingContactToRow` (linked rows never import a photo), retire the staging reference in the link transaction.
   - Pre-fix databases can contain rows that satisfy the predicate but whose file was already swept. The retry path must treat "staged file missing" as terminal: retire the reference, contact keeps no photo.
2. **Sweep:** `reconcileOrphanStagedPhotos` keeps paths live if (existing unresolved predicate in a non-discarded session) OR (photo-outstanding predicate). Do **not** add photo-outstanding to `UNRESOLVED_ROW_STATUSES`. `src/screens/import-leave-guard-logic.ts:7-11` drives the leave-guard auto-discard ("Must stay in sync with finalizeSessionIfTerminal's unresolved-row query"), and conflating the two would make navigating away discard retry input.
3. **Photo-only retry service** (new function, e.g. `retryImportedPhoto(exec, fs, rowId, now)`):
   - Read the row plus `contacts.photo`.
   - If the contact is gone, the staging file is missing, or `contacts.photo IS NOT NULL` (the user has superseded it): retire the staging ref and delete the file (deliberate). Otherwise run `persistImportedPhotoPostCommit`.
   - Never calls `importContactRecord`, so it cannot duplicate a contact.
   - The ImportComplete Retry covers both `failed` rows (existing) and photo-outstanding rows. Plus one explicit "skip photos" discard that retires refs. See owner flag 2.
4. **Surfacing after restart:** the planner must decide how a user reaches Retry after process death. Today the resume prompt only exists for `status='pending'` sessions, and `commitSingleImport`/`finalizeSessionIfTerminal` complete sessions without photo awareness. Recommended: extend the resume description (`describeResumable`/`getResumableSession`) to also surface the newest session that has photo-outstanding rows, even if `complete`, routing to ImportComplete. Keep `finalizeSessionIfTerminal`'s contact-resolution semantics unchanged. Note that `getResumableSession` auto-discards older *pending* sessions [import-session-read.ts:123-125]. That discard must not retire photo-outstanding rows of those sessions implicitly, or it must be documented as acceptable. Resolve this explicitly in the plan.
5. **Purge retirement (DPI-007), inside `purgeContact`'s existing transaction** (non-reentrant: compose SQL directly, no nested `inWriteTransaction`):
   - `DELETE FROM import_session_rows WHERE contact_id = ? OR matched_contact_id = ?` for terminal rows (`imported|linked|skipped`). `bulk_review_resolutions` cascades from the rows [migrations/013:46].
   - For **merged/consolidated origins**, also delete terminal rows with `contact_id IS NULL` whose `external_contact_id` matches any `external_contact_links.external_contact_id` of X. X's links, including links reparented from absorbed contacts, are still readable before step (3) deletes them.
   - For **pending/needs_review rows** (unrelated pending work about a source person): keep the row, but scrub X's id out of `candidates_json`. `matched_contact_id` is already SET NULL by FK.
   - Collect `photo_rel_path`s of deleted rows and hand them to post-commit cleanup. This needs an `onPurgeExtensions` context extension; see Cross-workstream touchpoints.
   - No tombstones: import tables are local-only and never exported [migrations/012 header: "They are not backup data: Replace-all restore deletes them and the export manifest never includes them."].
6. **Forward cleanup of already-detached payloads** (existing user DBs): add a foreground, idempotent DB sweep. Recommended home: inside the existing import resume sweep hook. It deletes terminal rows with `contact_id IS NULL` (and `already_linked` skips with `matched_contact_id IS NULL`) that have no remaining `external_contact_links` row with the same `external_contact_id`. Merged-origin rows (survivor still holds the link) are therefore kept until the survivor is purged. This is a targeted workflow-row sweep, not a generic filesystem sweep. A one-time forward migration is an alternative, but it competes with B's head+1 (not recommended).

2. **Extract the coordinator** from `handleSave` into a node-testable module (e.g. `src/screens/edit-contact-save-coordinator.ts`). Inject `updateContactFull`, `applyLinkDiff`, the post-commit effects and the refresh read, and return a typed outcome (`saved` / `metadataFailed` / `linksFailed` / `canonicalDuplicate` / `refreshFailed`) plus the next baselines. The screen maps outcomes to UI. Vitest then runs the **actual sequence** against `node-sqlite` (`src/db/__testkit__/node-sqlite.ts`), which answers the audit's "not source-string presence" requirement.
3. **Pure helper**, e.g. `src/logic/committed-baseline.ts`: `advanceBaseline({ submittedDraft, committedRows, keyOf })` → `{ seed, draft }`. It remaps synthetic ids to committed ids and preserves user edits made after submission as diffs against the new seed. Name it generically; RG-019's participant editor (38.3) needs the same "committed add → failed readback → retry must not re-add" guarantee.
4. Also advance `initialTrackingEnabled` (with E-1 the DAO computes direction from stored state, so a replay records no second event, but UI effects should not re-fire), `seedInputRef`, and `committedValuesRef` (already done at 979).

## Common Pitfalls

1. **Conflating photo liveness with contact-resolution liveness.** Adding photo work to `UNRESOLVED_ROW_STATUSES` or `finalizeSessionIfTerminal` makes the leave guard (`use-import-leave-guard.ts:11-17`) discard retry input on navigation. Keep a separate predicate.
2. **Nesting the write mutex.** Every new DAO composition (purge import retirement, lifecycle event, custom-value edit, in-transaction readback) must use `*Core` functions inside the one existing `inWriteTransaction`. Nesting hangs.
3. **Deleting outside a namespace.** A cache-cleanup helper that accepts any `file://` could delete a master under `Paths.document/avatars`. Guard by resolved prefix.
4. **Foreground sweep vs. in-flight crop.** `launch-sweep` also fires on background→active (returning from the image picker or share sheet). Cache sweeps must be cold-start-once or age-guarded.
5. **Mock-defined truth.** Do not "fix" REL-010 by changing the production code to match the mock. Change the mock to the native bundle shape. Update every notification test that seeds `trigger.date` in the same plan, or tsc/vitest breaks (orphaned-test-consumer hazard).
6. **Photo retry clobbering a user photo.** Check `contacts.photo IS NULL` **before** `persistMaster` writes the derived path (ADR-021/D-09 derived names mean the same file).
7. **Advancing baselines from a post-commit read.** If that read fails, the old baseline survives and replay returns. Baselines must come from the committed write's own return.
8. **Emitting lifecycle events from shared metadata cores.** Put the event in `updateContactFull` only. `updateContactMetadataCore` also serves reconcile, bulk review and merge.
9. **Using `toISOString().split('T')[0]`.** All new date keys must use `formatLocalDate()` (fire-instant/notification-schedule already do).
