## Concerns

### 1. [38.2-09] HIGH — **OWNER DECISION NEEDED** if the credential-retargeting residual is retained

Task 2 explicitly accepts a sequence where failed adoption before restore is followed by adoption against restored endpoint metadata. That weakens **D-08’s original-endpoint-or-re-entry requirement**, specifically the requirement to fail closed when original provenance cannot be established.

There is also a simpler sequence: the original endpoint is missing or invalid, so adoption leaves plaintext untouched; restore supplies a valid endpoint; a later launch adopts the key against that replacement endpoint. This does not require repeated SecureStore failures.

The proposed adopter reads a portable setting, not durable evidence of original provenance. The endpoint is explicitly portable, and current key handling demonstrates why binding to whichever endpoint is available is dangerous.

Evidence: [Plan 09:139](/home/bwales/projects/orbit-app/.planning/phases/38.2-audit-remediation-data-security-lifecycle/38.2-09-PLAN.md:139), [backup-schema.ts:182](/home/bwales/projects/orbit-app/src/backup/backup-schema.ts:182), [ai-key-store.ts:151](/home/bwales/projects/orbit-app/src/services/ai-key-store.ts:151).

**Required revision:** preserve original provenance or durably mark the legacy credential as requiring re-entry before endpoint replacement. Test missing provenance and failed adoption through restore **and a subsequent launch**. Accepting the residual requires an owner decision; enforcing D-08 does not.

### 2. [38.2-06, 38.2-11, 38.2-12] HIGH — Persist-then-retire is not crash-safe supersession

The proposed sequence replaces canonical bytes, then retires stale journal rows in a separate SQLite transaction.

A process kill between those operations leaves:

1. New canonical bytes.
2. The old finalize row.
3. The old staged bytes.

The next drain can overwrite the newer photo with the older staged image. A process-local lock cannot survive that interruption.

The existing swap completes before `persistMaster` returns; journal retirement would happen afterward. Evidence: [photo-storage.ts:424](/home/bwales/projects/orbit-app/src/services/photos/photo-storage.ts:424), [photo-storage.ts:443](/home/bwales/projects/orbit-app/src/services/photos/photo-storage.ts:443).

**Required revision:** define durable supersession/recovery ownership before canonical mutation, preserving the failed-newer-write recovery requirement. Add kill-point tests immediately after file replacement and before journal retirement. Apply the same analysis to removal, where retiring recovery before a failed deletion can lose retry evidence.

### 3. [38.2-06] HIGH — The proposed canonical lock omits an existing filesystem writer

`reconcilePhotoWrites()` restores `.bak` files and deletes sidecars without the proposed lock. It is registered as foreground maintenance.

Consequently, the new lock does not establish “every canonical mutation serializes”: reconciliation can act on sidecars belonging to an in-progress replacement. Its directory snapshot can also become stale before mutation.

Evidence: [photo-reconcile-sweep.ts:30](/home/bwales/projects/orbit-app/src/services/photos/photo-reconcile-sweep.ts:30), [photo-storage.ts:514](/home/bwales/projects/orbit-app/src/services/photos/photo-storage.ts:514).

**Required revision:** include sidecar reconciliation in the ownership protocol, rechecking filesystem state after acquiring ownership. Test foreground reconciliation during each replacement stage.

### 4. [38.2-08] HIGH — The specified deterministic UID encoding is ambiguous

The SQL uses:

```text
pair:<contactUid>:<fieldDefUid>
```

But the parser accepts arbitrary nonempty UID strings. These distinct pairs collide:

```text
contactUid = a:b, fieldDefUid = c
contactUid = a,   fieldDefUid = b:c
```

Both produce `pair:a:b:c`. The unique constraint can therefore abort restore or the fail-closed migration for an otherwise accepted database.

Evidence: [Plan 08:125](/home/bwales/projects/orbit-app/.planning/phases/38.2-audit-remediation-data-security-lifecycle/38.2-08-PLAN.md:125), [backup-schema.ts:157](/home/bwales/projects/orbit-app/src/backup/backup-schema.ts:157), [006-normalize-custom-field-values.ts:44](/home/bwales/projects/orbit-app/src/db/migrations/006-normalize-custom-field-values.ts:44).

**Required revision:** use an unambiguous deterministic encoding and define handling of collisions with existing arbitrary value UIDs. Pin runtime/migration equivalence with these fixtures. This preserves D-21; restricting previously accepted backups would be a separate decision.

### 5. [38.2-12] HIGH — A source-path comparison cannot validate staged photo bytes

The merge service stages bytes before its transaction, then checks that the absorbed row still contains the same path. Normal photo replacement keeps that path unchanged.

A newer crop can replace the absorbed image after staging; the transaction’s path comparison still passes, and merge adopts stale staged bytes before deleting the absorbed contact. Similar revalidation is needed if the survivor gains a photo after the initial “sole absorbed photo” decision.

Current merge reads custom values as path strings, and replacement writes new bytes to the same canonical destination. Evidence: [merge-dao.ts:303](/home/bwales/projects/orbit-app/src/db/merge-dao.ts:303), [photo-storage.ts:431](/home/bwales/projects/orbit-app/src/services/photos/photo-storage.ts:431).

**Required revision:** coordinate source staging and destination publication with normal writers, using durable identity/version validation where needed. Add a barrier test that replaces the source bytes without changing its path between staging and commit.

### 6. [38.2-10] HIGH — Cancellation does not cover the native download fallback

The no-readable-stream branch starts a second transfer with `File.downloadFileAsync()`. That call has no AbortSignal argument in the existing implementation.

Aborting the first response, as planned, does not cancel this second transfer. Caller abort and the deadline therefore cannot guarantee prompt settlement or stop its disk writes.

Evidence: [url-image.ts:241](/home/bwales/projects/orbit-app/src/services/photos/url-image.ts:241), [url-image.ts:378](/home/bwales/projects/orbit-app/src/services/photos/url-image.ts:378).

**Required revision:** provide an explicitly cancellable fallback or fail safely when a cancellable transfer is unavailable. Tests must enter the no-reader branch and cancel the **second** transfer, rather than only assert that the first fetch’s signal was aborted.

### 7. [38.2-13] HIGH — Photo retry’s preflight check does not protect newer photos

The plan checks `contacts.photo` before calling the existing photo service. That service performs asynchronous resolution and resizing before persistence.

A crop can commit during that interval, after which retry overwrites it. A purge followed by integer-ID reuse presents a more serious identity race. The canonical lock alone only orders writes; it does not determine which operation remains authorized.

Evidence: [import-photo.ts:111](/home/bwales/projects/orbit-app/src/services/import/import-photo.ts:111).

**Required revision:** revalidate contact UID, workflow ownership, and photo eligibility within the ownership protocol that covers persistence and reference publication. Test a newer crop and purge/ID reuse between preflight and persistence.

### 8. [38.2-02] MEDIUM — The proposed grid starting point skips a still-future rolled slot

`nextNudgeDate()` advances past every grid date before today. However, `allowedSlotForDay()` can roll yesterday’s evening slot into this morning.

Example: a September 22 tick at 22:00, quiet hours 21→08, reconciled September 23 at 07:00. September 23 at 08:00 remains eligible, but starting from `nextNudgeDate()` jumps to the September 29 tick.

Evidence: [fire-instant.ts:102](/home/bwales/projects/orbit-app/src/services/notifications/fire-instant.ts:102), [fire-instant.ts:218](/home/bwales/projects/orbit-app/src/services/notifications/fire-instant.ts:218).

**Required revision:** consider the preceding grid tick’s rolled instant before advancing. Keep the stateless cadence and birthday behavior unchanged.

### 9. [38.2-03] MEDIUM — The baseline helper lacks inputs required by its contract

`advanceBaseline({ submittedDraft, committedRows, keyOf })` promises to preserve edits made after submission, but receives no current draft. It also lacks an explicit mapping from temporary additions to committed identities.

Current knowledge writes discard the IDs returned by add operations. Matching complete returned collections by content is ambiguous when two additions have identical content.

Evidence: [Plan 03:171](/home/bwales/projects/orbit-app/.planning/phases/38.2-audit-remediation-data-security-lifecycle/38.2-03-PLAN.md:171), [contacts-dao.ts:583](/home/bwales/projects/orbit-app/src/db/contacts-dao.ts:583).

**Required revision:** specify the current-draft input and temporary-ID-to-committed-ID mapping, or explicitly prevent concurrent editing during submission. Test identical additions and edits during an awaited save.

Also correct the retained-history assertions: that writer targets `custom_field_value_history`, not `field_history`. Evidence: [value-history-dao.ts:25](/home/bwales/projects/orbit-app/src/db/value-history-dao.ts:25).

### 10. [38.2-02, 38.2-11] MEDIUM — Forwarding `scheduleResyncPending` does not make it truthful

Restore marks resynchronization pending when reconciliation rejects. The notification reconciler catches individual scheduling failures and returns normally.

Thus, a real native schedule failure can leave `scheduleResyncPending = false`, despite the new result screen correctly forwarding the field. Tests that inject a rejecting reconciliation callback miss this production behavior.

Evidence: [notification-schedule.ts:465](/home/bwales/projects/orbit-app/src/services/notifications/notification-schedule.ts:465), [restore-apply.ts:1651](/home/bwales/projects/orbit-app/src/backup/restore-apply.ts:1651).

**Required revision:** return an aggregate reconciliation outcome and propagate incomplete scheduling into restore results. Test through the real reconciler with native scheduling failure.

### 11. [38.2-07] MEDIUM — The ingress deadline needs an acquisition and supersession contract

The proposed watchdog closes an acquired stream or descriptor, but acquisition itself calls `openInputStream()`. The plan does not specify cancellation while opening, superseded shares, queued requests behind a stalled provider, or module destruction.

Moving this work to one executor protects the UI but does not alone bound its lifetime or prevent stale results from replacing newer shares.

Evidence: [OrbitBackupDocumentPickerModule.kt:155](/home/bwales/projects/orbit-app/modules/orbit-backup-document-picker/android/src/main/java/expo/modules/orbitbackupdocumentpicker/OrbitBackupDocumentPickerModule.kt:155), [Plan 07:125](/home/bwales/projects/orbit-app/.planning/phases/38.2-audit-remediation-data-security-lifecycle/38.2-07-PLAN.md:125).

**Required revision:** define request ownership, supersession, acquisition cancellation, and cleanup. Include share A→share B, stalled acquisition, and destruction tests alongside stream-loop tests.

Spot-verification against the live repo (migration head 030/TARGET_VERSION, `applyRestore` at `restore-apply.ts:1327`, `registerSweepHook`, `updateContactFull`, `drainRestorePhotoJournal`) confirms the plans are grounded in real code, not hallucinated structure — a meaningful signal of research quality. ## 3. Concerns

- **[38.2-08] HIGH: Migration 031's deterministic pair UID and the runtime `completeGlobalPairsCore` must produce byte-identical SQL, but they're deliberately two separate code paths (one frozen literal, one importable core) that only converge via a "whitespace-normalized equality" test.** If a future change to `pair-matrix.ts` is made without a matching change to the frozen migration string (easy to miss since 031 is explicitly excluded from importing runtime code), the equality test is the only thing catching drift — and it only compares SQL text, not necessarily every edge case of `created_at` derivation (`max(c.created_at, d.created_at)`) under NULL or malformed timestamps. Worth confirming the pin test actually runs both against varied fixtures, not just one happy-path DB, since this is Plan 08's `<reversibility rating="one-way">` item.
- **[38.2-08] MEDIUM: D-11/D-21's deterministic pair UID (`pair:<contactUid>:<fieldDefUid>`) assumes `contactUid`/`fieldDefUid` are themselves stable and collision-free across devices, but nothing in the plan verifies that assumption against ADR-056's Merge-collision history that motivated D-21 in the first place.** If two devices independently generate a contact with colliding UIDs pre-merge (a scenario ADR-056 exists to handle), the deterministic pair ID could itself collide in an unexpected way. This is a "trust the invariant holds" risk rather than a demonstrated bug — flagging for explicit test coverage rather than blocking.
- **[38.2-08 / 38.2-09 / 38.2-11] MEDIUM: `restore-apply.ts` (1679 lines) is restructured in three separate plans across two waves** — Plan 08 Task 3 restructures `applyRestore` into stage→plan-in-transaction→post-commit; Plan 09 Task 2 injects legacy-credential adoption calls into the restore caller; Plan 11 Tasks 1-3 change photo-target resolution, cleanup ordering, and add `publishCommittedRestore`. Because waves are sequential (not parallel), this isn't a live merge conflict, but each plan's `<read_first>` line-number anchors (e.g., ":1327-1475") will already be stale by the time Plan 11 executes, since Plan 08 will have changed those line numbers. The plans acknowledge line numbers are "anchors, re-verify before editing" (a stated constraint), but the amount of resequencing on one safety-critical file increases the chance that Plan 11's very specific `<read_first>` pointers (e.g. ":996-1013", ":1015-1062") no longer correspond to the code Plan 08 leaves behind, which could cause an executor to misapply the task.
- **[38.2-09] MEDIUM: The INVESTIGATE-gated Task 2 depends entirely on Task 1's harness verdict, and the plan pre-writes full production code changes (`getKey` fail-closed, `adoptLegacyCustomCredential`) contingent on a `<precondition>` tag.** If the executor infrastructure doesn't reliably support conditional task skipping (this is plan-authoring convention, not something verified against actual GSD executor behavior in this review), there's a real risk Task 2 runs regardless of the verdict, silently reversing behavior (lazy binding → fail-closed) even when D-05 says disproven findings should be "documented and closed" with no code change. Recommend confirming gsd-executor actually respects `<precondition>` blocks before treating this as safe.
- **[38.2-05] MEDIUM — flag as OWNER DECISION ALREADY MADE, verify fallback path isn't quietly reachable: the widget provider-removal fix (RG-001) explicitly forbids implementing the O-2 launcher-trust fallback** ("if inline bitmaps fail on device, stop and ask the owner"). This is correctly treated as a stop condition rather than an autonomous decision, which is right — but Plan 05 is `autonomous: true` with a `<human-check>` only for verification, meaning if the Pixel test shows bitmap-memory/binder failures, there's no built-in mechanism in an autonomous run to actually pause and escalate rather than silently merging a broken (or worse, reverted-to-provider) widget. Worth confirming the executor's failure path for a failed `<human-check>` acceptance criterion actually halts rather than marks the plan "done" with a noted defect.
- **[38.2-13] LOW: Task 4 (imported-note AI-off) correctly scopes to `provenance === "import"`, but the plan doesn't verify that every call site actually supplies a `provenance` field** — if any future or existing import path calls `addMemoryCore` without setting `provenance: "import"`, it silently falls through to the general AI default, defeating D-07. The plan's tests cover the three known import paths (single/bulk/consolidated) but there's no negative test asserting *no other addMemoryCore call site* can produce an imported note without provenance set.
- **[38.2-10] LOW: Task 2's Kotlin `SecureResponseReader` extraction explicitly forbids adding new JVM test dependencies ("add NO new test dependency") and requires hand-rolled okio sources** — reasonable dependency-hygiene discipline, but hand-rolled fake sources for testing stall/cancel/truncation edge cases in a concurrent OkHttp read loop are historically a common source of flaky or incomplete coverage (e.g., missing the race between cancel-flag-check and actual read). Not a blocking concern, just worth extra scrutiny in review of the actual test file once written.
- **[38.2-06] LOW: `finalizeJournalEntryOwned` and `persistOwnedMaster` both acquire `withCanonicalPathLock`, but the lock is described as "process-local promise-tail" — this protects against races within one JS process but not against genuinely concurrent native writers (e.g., a headless background task or widget refresh running in a separate process context on Android).** The plan's own behavior spec only tests same-process interleavings. If Android ever spawns import/backup work in a separate process (not currently the architecture, per D-03's foreground-only sweeps), this lock would not protect. Worth a one-line note in `photos.md` documenting this is a same-process-only guarantee, if not already there.
