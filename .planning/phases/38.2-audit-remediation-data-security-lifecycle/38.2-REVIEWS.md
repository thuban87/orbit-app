## 3. New concerns

**1. [38.2-08] LOW-MEDIUM — D-21's deterministic pair-UID design still assumes `contactUid`/`fieldDefUid` are themselves collision-free, and ba3e52b doesn't add a fixture against the ADR-056 scenario that motivated the concern.**
File/mechanism: `.planning/phases/.../38.2-08-PLAN.md` Task 1/2 fixture list (five groups: ambiguous-separator, uid-slot collision, malformed timestamps, non-ASCII, archived/quarantined/scoped). None of these fixtures constructs two independently-generated contacts or field-defs whose *own* uids collide pre-merge (the scenario ADR-056's merge-collision handling exists for). The `pairx:` fallback added in ba3e52b handles the narrower "an arbitrary wire uid happens to occupy the deterministic slot" case, which is a different failure mode than "two devices generate the same contact/def uid independently." I could not verify from the plan text alone whether `newUid()` (used to mint contact/def uids elsewhere) has a large enough space that this is purely theoretical, or whether ADR-056's existence implies it has happened in practice. **This is downgraded from Claude's original MEDIUM to a documentation/test-coverage gap** — the plan's own stated fallback behavior ("any later cross-device identity disagreement... falls back to the existing pair-key-collision refusal — fail closed, never corruption") means the worst case is a refused merge, not corruption, which is consistent with the phase's constraints. No code change needed; recommend Plan 08 add one fixture that seeds a genuine contact/def-uid collision (or an explicit note in the SUMMARY that this was checked against `newUid()`'s uid space and found not reachable in practice) so the residual is documented rather than silently assumed.

**2. [38.2-07] LOW — A genuinely stalled Android binder call in `openInputStream()` cannot be forcibly cancelled; `BackupIngressRequests`'s mitigation is a concurrency cap, not a kill.**
File/mechanism: the plan's own action text acknowledges this ("because a blocked binder call cannot be interrupted reliably, the acquiring task re-checks ownership when `openInputStream()` returns"). This means a single stalled provider still permanently occupies one pool thread/slot until the provider eventually returns (if ever) — `MAX_CONCURRENT_INGRESS` bounds how many requests this can happen to concurrently, but does not reclaim the leaked slot. This is an honest, disclosed design tradeoff (Android provides no way to interrupt a blocked Binder transaction from Kotlin), not an oversight, and is a reasonable mitigation for the DoS finding it's answering. Not blocking — worth a one-line note in the Plan 07 SUMMARY that this residual exists (a persistently stalled malicious/broken provider degrades available ingress slots over the process lifetime rather than being fully contained), so it isn't rediscovered as a "regression" later.

No HIGH or blocking MEDIUM concerns found in the ba3e52b text.

**N1. [06/11/12] MEDIUM — Finalize-based owners don't settle older journal rows; a stale row can overwrite a newer restore/merge.**
Evidence: `restore_photo_journal` permits multiple finalize rows per canonical (only `relative_path` UNIQUE: `008-restore-photo-journal.ts:6`); the drain applies in id order (`restore-photo-journal-dao.ts:33`); `applyRestore` inserts new rows without checking/clearing old ones (`restore-apply.ts:1551-1580`) and nothing gates restore on an empty journal. **N2. [06→13] MEDIUM — Settle bumps the generation, then `authorize` compares against it: spurious refusals that discard retry data.**
