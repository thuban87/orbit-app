## Summary

All six OPEN Workstream A findings are **confirmed against current code** at or near their cited lines. Two citations have drifted:
- `performance/AUD-PERF-003` cites `PhotoSourcePicker.tsx:225–267`; the handler is actually at `:198–243`.
- `security/AUD-SEC-006` cites `ai-permissions-dao.ts:121–134`; the function is at `:118–131`.

Neither drift changes a conclusion. The investigation finding, `security/AUD-SEC-006` (RG-005), is **statically likely reachable**:
- Migration 029 never carried the pre-Phase-36 endpoint (`app_settings.ai_custom_endpoint`) into `ai_connections`.
- No current code ever binds a legacy plaintext key to that original endpoint.
- Every Custom credential read (Settings AI hub focus, Compose mount, first-use disclosure, generation) lazily binds the legacy key to whatever `ai_connections.custom_endpoint` holds at first read.
- Restore writes that column, plus `aiEnabled` and `aiActiveConnection`, with no key-binding step.

This contradicts ADR-135's stated consequence: "Restored configuration cannot incorrectly appear Ready without a newly supplied local credential." A second, non-restore path also exists: after the upgrade, saving the Custom card with a blank credential uses `previousEndpoint=""`, so the legacy key binds to the newly typed endpoint.

Research turned up several facts the audit did not record. Each materially changes the plan:
1. **RG-002 copy threads.** `OrbitBackupDocumentPickerModule` copies the provider stream *synchronously* in `OnNewIntent`/`OnCreate` (main thread) and inside the sync JS `Function("hasSharedBackup")` (JS thread). A stalled stream is therefore a UI/JS freeze, not only a memory issue.
2. **RG-002 second copy.** `expo-share-intent`'s `getDataColumn` makes a **second** unbounded copy of any non-text `EXTRA_STREAM` into `cacheDir`. The file is named from the provider's `DISPLAY_NAME` and never deleted.
3. **RG-002 retention.** Neither the second copy nor `restore-share-*.json` is deleted after use, so plaintext backups linger in cache.
4. **RG-003 cancellation.** In Expo fetch, calling `response.body.cancel()` before streaming starts does nothing natively. Only `AbortSignal` → `NativeRequest.cancel()` → OkHttp `task.cancel()` stops the pump.
5. **RG-004 exception handling.** OkHttp's `AsyncCall.run` only *logs* an `IOException` thrown from `onResponse` after the callback has been signalled, so the Expo promise is never settled. It *rethrows* any other Throwable on the dispatcher thread, which crashes the process.

**Primary recommendations:**
- Own every transport and stream end-to-end in native code (bounded bytes, a deadline, cancellation, and exactly-once settlement).
- Enforce credential and consent provenance at the single writer choke point (`ai-key-store` legacy branch; `addMemoryCore` import provenance).
- For RG-001, replace the exported ContentProvider with inline bitmaps. This makes the OS's widget binding the only authorization boundary and avoids a launcher trust policy.
- No migration, no backup-format change and no new npm package is required for Workstream A.

### Anti-Patterns to Avoid
- **Validating after acquiring.** MIME, status, JSON schema and base64 checks must not run after unbounded allocation. The byte bound belongs in the reader.
- **`body.cancel()` as the cancellation mechanism in Expo fetch.** It does nothing before streaming starts. Use `AbortController`.
- **Synchronous I/O in Expo lifecycle hooks or sync `Function`s.** `OnNewIntent`/`OnCreate` run on the main thread, and a sync `Function` runs on the JS thread.
- **Settling a native promise before consuming the body.** Settlement ends cancellation ownership.
- **Lazy "bind on first read" for legacy secrets.** A reader that also writes provenance lets any later metadata writer retarget the secret.
- **Fixing consent at every caller only.** New import creators would re-open the hole. Enforce it in `addMemoryCore`.
- **Removing the widget, or disabling rendering, to close RG-001.** Explicitly out of scope.
- **Relaxing `secureDns`, the redirect refusal or the proxy pin to make device or JVM testing easier.** That weakens ADR-051. Inject a test client instead.

## Per-RG Findings, Root Cause, and Recommended Fix

### RG-001 — Widget image access boundary (`security/AUD-SEC-001`)

**Verified code** (read this session):
- `node_modules/react-native-android-widget/android/src/main/AndroidManifest.xml` (and `AndroidManifestNew.xml`) declares `<provider android:name=".RNWidgetImageProvider" android:authorities="${applicationId}.rnwidget.imageprovider" android:exported="true" />` with no permission attribute.
- `RNWidgetImageProvider.java:18-53`: `AUTHORITY_SUFFIX = ".rnwidget.imageprovider"`. `openFile()` accepts mode `"r"`, strips `?…`, runs a canonical-path check inside `new File(context.getFilesDir(), "widget_images")`, then `ParcelFileDescriptor.open(...)`. There is **no calling-UID, permission or grant check**. [VERIFIED: Read, RNWidgetImageProvider.java:18-53]
- `RNWidget.java:148-151`: `String fileName = "widget_" + widgetId + "_mode_" + mode + ".png";` → `writeImage` → `getImageUri`. Lines 76-104 `setImageViewUri(R.id.rn_widget_image_light|dark, uri)`. [VERIFIED: Read, RNWidget.java:147-151]
- `RNWidgetCollectionService.java:76-79` uses the same URI mechanism for ListWidget items. Orbit does **not** use `ListWidget`: `widget-render.tsx` uses `ImageWidget`/`TextWidget` only (grep). The collection path is therefore unused but must not be broken silently.
- Upstream switched from `setImageViewBitmap` to `setImageViewUri` in commit `f6080a22` (2026-01-04, "feat: use setImageViewUri instead of setImageViewBitmap"). No upstream issue or fix for exported access exists (GitHub issue search, 2026-09-23).
- Orbit has no override of this provider (grep for `imageprovider`/`tools:replace` found none). `android/` is generated.

**Root cause:** Confirmed. The library exports an unauthenticated provider because the launcher process opens `content://` URIs from `RemoteViews` under its own UID.

**Recommended fix (Option C, primary): patch-package `react-native-android-widget@0.22.0`.**
1. In `RNWidget.drawWidget`, replace `setImageViewUri(..., bitmapUri)` with `setImageViewBitmap(..., bitmap)` for the light and dark images. Do the same in `RNWidgetCollectionService.getViewAt` if it is kept, so ListWidget does not silently break.
2. Remove the `<provider>` from both library manifests in the patch. An app-side config plugin with `tools:node="remove"` is equivalent if the planner prefers a plugin.
3. Delete any existing `files/widget_images/*` on the next render (stale snapshots remain in app-private storage). The provider's static `deleteImages` helper can be kept as a plain utility.

Authorization then comes from `AppWidgetService`: only hosts bound to that widget ID receive the RemoteViews. No launcher allowlist is needed, which keeps this inside "access authorization" and outside "launcher trust policy".

Capacity check:
- Android caps RemoteViews bitmap memory at about 1.5 × screen area × 4 bytes. [CITED: learn.microsoft.com AppWidgetManager.UpdateAppWidget mirror of the Android reference; openhab-android #2053; bumptech/glide #5214]

**Verified code** (`OrbitSecureFetchModule.kt`, read in full):

- `AiService.ts:580-603` checks status, then `JSON.parse(bodyText)`. `mapSecureFetchError` (`:192-213`). `AiErrorCode` includes `"invalid_response"` [VERIFIED: Read, :111-126].
- OkHttp `RealCall.AsyncCall.run` (parent-4.12.0, `RealCall.kt:512-534`): once `signalledCallback = true`, an `IOException` is only logged ("Callback failure"), and any other `Throwable` triggers `cancel()` + `throw t` on the dispatcher thread. [VERIFIED: GitHub source, square/okhttp parent-4.12.0; 4.9.2 assumed identical — ASSUMED]

**Root cause:** Confirmed:
- (a) cancellation after the headers arrive is a no-op, because `inFlight` was already cleared;
- (b) a body-read `IOException` (truncation, read timeout, cancel) leaves the JS promise **unsettled forever**;
- (c) a huge body is fully buffered as a String (`string()` doubles memory through bytes then chars), and an OOM is rethrown and crashes;
- (d) a JS cancel arriving after `settle()` leaves a permanent tombstone.

**Recommended fix:**
- Per-request `AtomicBoolean settled`. Resolve and reject only through `settleOnce`, which also removes the `inFlight`/tombstone entries.
- Keep the Call in `inFlight` until the body read finishes.
- In `onResponse`, wrap everything in `try { … } catch (e: Throwable) { rejectOnce(code) }`:
  - `call.isCanceled()` → `ERR_CANCELLED`;
  - timeout → `ERR_TIMEOUT`;
  - over cap → new `ERR_RESPONSE_TOO_LARGE`;
  - otherwise → `ERR_TRANSPORT`.
- Read the body through `res.body.source()` with a counted loop up to `MAX_RESPONSE_BYTES`, a tunable at the top of the file (the planner picks it; chat completions are small, e.g. 1 MiB). Decode with the charset from `contentType()` or UTF-8.
- For non-2xx responses, read at most a small cap or discard. `classifyHttpStatus` uses only the status (`AiService.ts:593`).
- Tombstones: store a timestamp and prune entries older than a TTL on insert, or cap the set size, so late cancels cannot accumulate.
- JS: map `ERR_RESPONSE_TOO_LARGE` → `SecureFetchError("response_too_large")` → `AiError("invalid_response")`, so no UI copy changes. **Grep every `SecureFetchErrorCode` consumer, including tests** (orphaned-consumer hazard).
- Keep `secureDns`, `Proxy.NO_PROXY`, `followRedirects(false)`, the literal-IP pre-check and `NonPublicAddresses` byte-identical (ADR-051). For JVM tests, refactor the body/settlement core so it can run against an injected `OkHttpClient`, and **never** relax the production DNS guard.

## Common Pitfalls

### Pitfall 1: Async backup copy strands the share gate
**What goes wrong:** `ShareIntentGate`'s effect runs once while the copy is still in flight. `hasSharedBackup()` returns false and the effect never re-runs.
**How to avoid:** `hasSharedBackup()` must report *pending* synchronously from intent inspection alone. `consumeSharedBackup` awaits completion.
**Warning signs:** A cold JSON share lands on Dashboard instead of Backup.

### Pitfall 2: expo-share-intent patch removes the JS JSON signal
**What goes wrong:** Once non-text intents are ignored, `isBackupShareIntent(shareIntent)` is never true, and tests asserting that arm become stale.
**How to avoid:** Route on `backupReady && !hasShareIntent`. Update `backup-share-intent.test.ts` in the same task.

### Pitfall 3: `body.cancel()` does not stop Expo fetch before streaming
**How to avoid:** Abort through the signal passed to `fetch`. In tests, model the native pump so that it continues unless `signal` is aborted.

### Pitfall 4: Loopback test servers vs the egress guard
**What goes wrong:** MockWebServer (127.0.0.1) and `adb reverse` targets are rejected by `secureDns`/literal checks. Tailscale 100.64/10 is CGNAT and also rejected.
**How to avoid:** Make the body/settlement core testable with an injected client in JVM tests. Device tests need a **public HTTPS** endpoint (owner flag O-3). Never relax the guard.

### Pitfall 5: OkHttp callback exceptions
**What goes wrong:** An `IOException` after `onResponse` begins is silently logged, so the promise is stranded. Other Throwables crash the dispatcher thread.
**How to avoid:** Catch `Throwable` around the entire `onResponse` body and settle once.

### Pitfall 6: Tests that enshrine the vulnerable behaviour
`ai-key-store.test.ts:94` asserts lazy binding. `backup-share-intent.test.ts` and `url-image.test.ts` assume current shapes. The `SecureFetchErrorCode` union has test consumers. Update each consumer in the same wave that changes the contract. Run `npx tsc --noEmit` because vitest will not catch type orphans.

### Pitfall 7: Hermes-only failures invisible to vitest
Do not use `globalThis.crypto` (memory: Hermes crypto guard). Do not rely on `AbortSignal.any/timeout` unless Expo's runtime patch is loaded; it is loaded on device, not necessarily in vitest, where Node 22 has them natively. Kotlin changes are invisible to vitest entirely, so JVM tests plus the device run are the only proof.

### Pitfall 8: Widget bitmap memory and Binder limits (RG-001 Option C)
**What goes wrong:** `IllegalArgumentException: RemoteViews for widget update exceeds maximum bitmap memory usage`, or a failed binder transaction on some launchers or older Android versions.
**How to avoid:** Verify on the Pixel at maximum resize, in dark and light, and after reboot. Consider `Bitmap.Config.RGB_565` only if needed; it is a visual change and therefore an owner call.

### Pitfall 9: Explicit intents bypass MIME filters
Tests limited to "matching JSON shares" miss `am start -n …/.MainActivity -t image/png` deliveries. Include them in device UAT.

### Pitfall 10: Presence reads write
The Settings hub, Compose and the disclosure call `getKey`, which currently mutates SecureStore. After R1, presence for a legacy key becomes `false`, so the AI state shows Needs Attention (replace key). That is the intended re-entry UX; verify the copy is sensible.

  const onCallerAbort = () => controller.abort();
  opts.signal?.addEventListener("abort", onCallerAbort, { once: true });
  const timer = setTimeout(() => controller.abort(), DOWNLOAD_DEADLINE_MS);
  let succeeded = false;
  try {
    const response = await fetch(url, { signal: controller.signal });
    // …existing checks (final URL, ok, MIME, cache prep, capped read) unchanged…
    succeeded = true;
    return destFile.uri;
  } finally {
    clearTimeout(timer);
    opts.signal?.removeEventListener("abort", onCallerAbort);
    if (!succeeded) controller.abort(); // stops the native pump on EVERY failure exit
  }
}
