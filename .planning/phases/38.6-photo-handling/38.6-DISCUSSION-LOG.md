## O-1 Photo resolution

Round 1:

| Option | Description | Selected |
|--------|-------------|----------|
| R-B: one bigger file | One file per photo, saved at 1024 for new photos; ~4× size; orrery gets a smaller copy | |
| R-A: keep 512 | No reversal; soft Profile/lightbox | |
| R-C: 512 + large copy | Second large lightbox-only file; close to rejected "512 + original" | |

**User's response:** asked why 512 was chosen (suspected backup size) and whether WebP could cut size while keeping resolution.
**Answer given:** 512 was chosen mainly for orrery GPU texture memory, then the widget Binder ceiling (since solved by
the widget's own re-encode), then backup size. WebP is available and is ~25–35% smaller than JPEG at equal quality, but
does not change decoded memory.

Round 2:

| Option | Description | Selected |
|--------|-------------|----------|
| R-BW: 1024 WebP | One file, ~2.5–3× storage | |
| R-B: 1024 JPEG | ~4× storage | |
| R-A: keep 512 JPEG | Soft | |

**User's response:** concerned about 2.5–3× "memory"; proposed 512 for most pages and 1024 only for the lightbox.
**Answer given:** working memory is flat with one 1024 file (display-size decode; orrery gets a small copy); the split
uses MORE storage (~3.5–4×) and leaves the Profile photo soft.

Round 3:

| Option | Description | Selected |
|--------|-------------|----------|
| R-BW: one 1024 WebP | Flat working memory; ~2.5–3× storage | ✓ |
| R-CW: 512 + 1024 lightbox | ~3.5–4× storage; two files | |
| R-A: keep 512 JPEG | Soft | |

Existing photos:

| Option | Description | Selected |
|--------|-------------|----------|
| Leave as-is | Stay 512 until re-picked | ✓ |
| Convert to WebP | Launch sweep; no sharpness gain | |
