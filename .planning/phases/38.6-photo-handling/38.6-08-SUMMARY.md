# Phase 38.6 Plan 08: Missing-Photo Integrity and Backup Skip Summary

This plan implements the owner's rulings on review finding WR-01, plus two leftover native-memory sites from WR-02.

- **A lost photo keeps its reference (D-23).** The ownership layer no longer drops the evidence. The Profile hero and the photo editor now show "Photo unavailable" instead of silently showing initials.
- **Backups skip unreadable photos (D-24, D-26).** Every backup (manual, automatic, Replace-all safety) now completes when a profile, contact or custom-field photo can't be read. It leaves that photo out, marks the row `photoSkipped: true`, and tells the user how many were left out.
- **Restore never removes a photo for a skipped row (D-26).** This holds in Merge and in Replace-all.
- **Manipulator memory (D-11).** The crop screen's decode fallback and the Profile background crop now release both the rendered image and its manipulator context.

Unchanged: the format stays 7, there is no migration, and profile backgrounds are still all-or-nothing (D-27).

## What changed

**Task 1: settle branch and "Photo unavailable" (tracer)**

`settleRowLocked` now handles a finalize row that still matches its reference but whose pending file is gone:
- **Canonical present:** the row retires silently.
- **Canonical missing:** the row retires and the reference is left exactly as it was. One content-free `Logger.error` line is written ("restore photo bytes lost; reference kept (D-23)"). Nothing throws and no display revision is published.

The misplaced, wrong comment was replaced with an accurate one.

`PhotoUnavailableNotice` reuses the existing warning pattern: `Icon warning/danger/sm` plus an `AppText caption`, as one accessible element labelled "Photo unavailable". It appears in two places:
- **ProfileHero:** under the name (the D-04 lines don't move), only when a photo exists and fails to load.
- **PhotoSourcePicker:** as the first child of the actions column, fed by `Avatar.onLoadErrorChange`. Change photo and Remove photo stay available.

Tests cover:
- all three target kinds;
- re-picking after a lost-bytes settle (not wedged);
- the drain reporting `{0, 0}`, so the backup hook is not skipped;
- a source guard that `owned-master.ts` contains no SQL `SET photo|value`;
- hero and picker render cases.

RED was confirmed against the old branch: the three "canonical missing" cases failed.

**Task 2: backup skip, count and marker**

- **Export report.** `buildExportReport` counts skips through one shared `readPhotoOrSkip`. `buildExportManifest` remains as a wrapper, used only by tests and tools.
- **Writers.** `backup-service` uses the report in both writers: manual `shared.skippedPhotos` and automatic/pre-restore `written.skippedPhotos`.
- **Automatic record.** `backup-sweep` writes one timestamp to both the health row and the device-local record.
- **Where the user sees the count:**
  - **Backup screen:** an "Export shared" Alert after a manual export with skips, and a "Last automatic backup: N photos couldn't be included." line in the health card. That line sits outside every RG-029 anchor; the contract tests pass.
  - **RestoreResultScreen:** the skip copy is appended to the "verified" sentence. A separate sentence reports `restoredPhotosMissing`.
- **restore-apply.**
  - Snapshot count: `PreRestoreSnapshotResult` gains an optional `skippedPhotos`. `applied` carries `preRestoreSnapshotSkippedPhotos` and `restoredPhotosMissing` in both constructions.
  - `planPhotoCandidates`: a marked winning row never queues a delete or a clear.
  - Merge: the local reference is captured before the upserts and written back afterwards, guarded by canonical identity.
  - Replace-all: `stageCandidates` stages this phone's bytes for marked rows, before the reset and before any finalize. The existing journal finalize then lands them at the row's new id-derived canonical.
  - An unmarked `photoBase64: null` still means removal.
- **Schema.** `backup-schema` accepts the optional boolean marker and rejects anything else, and changes nothing else.

**Task 3: WR-02 fold-in**

- `manipulator-derivatives.ts` follows the `master-encode.ts` pattern: lazy import, and `releaseQuietly` on the ref and the context in `finally`.
- `CropPhotoScreen` calls `renderPreviewDownscale`. `ProfileBackgroundManager` passes `cropAndResize: renderBackgroundDerivative`. Neither file imports `expo-image-manipulator` any more.
- The background `release()` now only discards the cache file.

## Surface to owner

1. **Replace-all profile with a lost photo.** Suppose the profile photo is marked in the backup and its local file is also gone. After a Replace-all, `profile.photo` keeps its dangling reference, because the profile row is never reset and D-23/D-26 forbid an automatic clear. The row is counted in `restoredPhotosMissing`, and the Settings self-photo editor shows "Photo unavailable". Contacts and custom values in the same state end with no photo, because Replace-all rebuilds those rows. This is consistent with the rulings; I'm flagging it in case you want the two to behave the same.

My recommendation is to leave it for now.
