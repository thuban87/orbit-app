# Phase 38.6 Plan 03: Display Revision on Every Writer Summary

Every change to canonical photo bytes now publishes a display revision from the ownership layer. That covers crop, remove, import, import retry, reconcile, merge re-homing, purge, definition delete, restore finalize, the replace-all restore cleanup and the launch `.bak` recovery. A source-scan contract test pins this, and the dead timestamp cache prop is gone from `Avatar` and its whole feeder chain. The authorization generation, filenames, backup format and schema are unchanged.

## What was built

**Task 1 (tracer), commit `62f1b1f`: remaining notify points**
- `owned-master.ts`:
  - `settleRowLocked` notifies right after a successful finalize `persist` (restore and merge re-homing). The superseded, unreferenced and missing-pending branches do not notify.
  - `executeDeleteIntentLocked` notifies inside the `mayDeleteCanonicalCore` branch, only after the `exists(canonical)` recheck passes. A silent `deletePhoto` failure therefore throws `PhotoRecoveryPendingError` without publishing.

## Surface to owner

1. **Can a delete, purge, merge or restore remove a contact's photo file but leave `contacts.photo` pointing at it? (the "UAT Ada" question)**
   - **Ordinary deletes: no.** Remove photo, purge, definition delete, merge cleanup, import-retry cleanup and restore delete intents all go through `executeDeleteIntentLocked` (`src/services/photos/owned-master.ts:147-185`). That function refuses to delete while `mayDeleteCanonicalCore` (`src/db/restore-photo-journal-dao.ts:98-112`) finds any `contacts.photo`, `profile.photo`, custom value or pending finalize row that references the file. Remove photo also clears the reference in the same transaction that queues the delete (`removeOwnedMasterLocked`).
   - **Restore is the only place a reference can point at a missing file, and only while recovery is pending:**
     - A restore writes the photo reference inside its transaction (`src/backup/restore-apply.ts:1819`, `writePhotoReference`) but copies the bytes after commit. If that copy fails, the file is missing until the launch recovery sweep finishes the job.
     - Replace-all's failure cleanup (`src/backup/restore-apply.ts:1896-1923`) deliberately deletes the old owner's bytes while the incoming contact's reference already points there. This avoids showing a different person's face. The pending finalize row stays and the launch sweep rewrites the file.
   - **One permanent-dangle edge:** `settleRowLocked` (`owned-master.ts:211-217`) retires a matching finalize row whose pending file is missing on the assumption that the bytes already landed. It does not check that the canonical file exists. If the pending file were lost some other way, the reference would stay broken.
   - **On the phone (read-only check today):** the restore journal is empty and `avatars/_restore_pending/` is empty, so nothing is in flight. Contact 1 (`created_at 2026-08-26 12:41:47`, `modified_at 2026-09-19 02:59:42`) has no photo file and no journal trace. The history cannot prove which path made it.
   - **Recommendation:** treat UAT Ada as leftover test data; the app already shows initials. Optionally harden later so the settle branch checks that the canonical file exists before retiring and flags the photo otherwise. That is a small change in the ownership layer, not in this plan's scope. I made no behavior change here.
