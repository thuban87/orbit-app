# Phase 38.6 Plan 04: WebP Masters up to 1024 px, Orrery Texture Gate and Sequential Widget Summary

All seven master writers now go through one encoder, `encodeMaster`. It saves a square lossy WebP (quality 0.8) with an edge of min(source square side, 1024). It never upscales. An imported thumbnail is centre-squared and kept at its own size. Files keep their identity-derived `.jpg` names, and existing 512 JPEG masters are left alone. The Skia orrery never uploads a photo texture above 512 px. The widget now encodes its tiles one at a time. No native, migration, filename or backup-format change.

## What was built

**Task 1 (tracer), commit `8548e2a`: the master encoder and the crop pipeline**
- `master-encode.ts`:
  - Tunables `MASTER_MAX_EDGE = 1024` and `MASTER_QUALITY = 0.8` sit at the top of the file. A comment explains that 1.0 means lossless WebP on Android.
  - Pure helpers `masterEdge` (throws on non-finite or non-positive sizes) and `centerSquare`.
  - `encodeMaster(sourceUri, crop?)`, which imports the manipulator lazily. With a crop, it crops and then resizes only when the crop is larger than the edge. Without a crop, it renders the base, centre-squares it when it is not square, and resizes only when the square is above 1024. Every rendered `ImageRef` (and the base) is released once in a `finally`.
- `photo-pipeline.ts`: `persistCroppedMaster` calls `encodeMaster(rawUri, cropRect)` inside the existing try, so encode failures still map to `PhotoPipelineError`. `MASTER_SIZE`/`MASTER_COMPRESS` and the direct manipulator import are gone, and the header comments are updated.
- Tests: 12 `master-encode` cases cover every `<behavior>` line, including release counts of 1 on success and on a `saveAsync` rejection in both branches. `photo-pipeline-cleanup.test.ts` now asserts the WebP save format, the unchanged persist path and the `PhotoPipelineError` mapping.
- Tracer check: re-ran the tracer's `<verify>` end to end and it passed before expansion. The plan is autonomous and frames no human-verify stop.

**Task 3, commit `9e733d1`: orrery texture gate and sequential widget**
- `use-orrery-photo.ts`:
  - `loadOrreryImage` works behind injectable deps (plain `resolvePhotoUri`, `Skia.Data.fromURI`, `MakeImageFromEncoded`, `fromBase64`, a manipulator downsample to 512 JPEG q0.9 with base64, `discardDerivative`).
  - A master of 512 px or less is returned as decoded.
  - A larger master is downsampled through a module-level FIFO semaphore (at most 1 in flight; the slot is released in a `finally`). The derivative file is always discarded, and the base64 goes into a byte-budgeted LRU (a Map in recency order plus a running byte total; a hit refreshes recency; an entry larger than the budget is not cached).
  - The large header image is disposed in a `try/finally`, whether the downsample succeeds or throws.
  - Any failure returns null.
- `createOrreryImageSlot` is the pure lifecycle helper, with `publish`, `settle(img, cancelled)`, `retire` and `discard`. Disposal goes through a WeakSet, so nothing is disposed twice.
- `useOrreryPhoto(relative)`:
  - The load effect's cleanup only sets `cancelled`.
  - The load callback publishes through `setState`.
  - A separate `useEffect(() => () => slot.retire(image), [image, slot])` disposes the replaced image after the commit, and the published image on unmount.
- `OrbitBody.tsx` / `SunBody.tsx` call `useOrreryPhoto(photo)`. The `useImage` and `resolvePhotoUri` imports are gone, and the comments in SunBody and `orrery-read.ts` now name the hook.
- `photo-writer-contract.test.ts`: in the `resolvePhotoUri` allowlist, `use-orrery-photo.ts` replaces the two bodies.
- Widget:
  - `widget-render.tsx` replaces the `Promise.all` with `encodeTileThumbs(tiles)`, a sequential `for…of` in `widget-photo.ts` that keeps the per-tile try/catch.
  - `encodeWidgetThumb` releases its rendered `ImageRef` in a `finally` around `saveAsync`. The encode parameters are unchanged (88 px JPEG q0.6).
- Tests:
  - 18 `use-orrery-photo` cases: pass-through, downsample, plain URI, revision re-derive, byte-budget LRU eviction with recency refresh, the oversize entry, max in-flight of 1 across 10 concurrent loads, a rejecting downsample freeing its slot, disposal on every error path, and N disposed only after N+1 is published and retired. Also covered: late-after-cancel, error-path discard, no double dispose, and a 20-revision stress run.
  - I checked the concurrency test by temporarily raising the limit to 3. It failed, then I restored the limit.
  - Widget: release count of 1 on success, on a save rejection and on missing base64. `encodeTileThumbs` keeps at most one encode in flight and preserves order, and a throwing tile still lets the others encode.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `orrery-render.test.tsx` broke once the bodies used the new hook**
- **Found during:** Task 3
- **Issue:** The render test mocks React's hooks and calls the bodies outside a renderer. `useOrreryPhoto` reads the zustand revision store, which uses the real React dispatcher, so the test threw `Cannot read properties of null (reading 'useCallback')`. The test is a consumer of the reshaped contract but was not in the plan's file list.
- **Fix:** Mocked `./use-orrery-photo` to `useOrreryPhoto: () => null`, the same photo-less render the old `useImage: () => null` mock gave.
- **Files modified:** src/components/orrery/orrery-render.test.tsx
- **Commit:** 9e733d1

**2. [Rule 2 - Correctness] Derivative cache hygiene beyond the plan text**
- **Found during:** Task 3
- **Issue:** A superseded revision of a path can never be requested again, and two bodies showing the same photo (for example a contact that is both sun and planet) would each run a 1024 decode.
- **Fix:** When a newer revision of a path is cached, older revisions of that path are dropped. Concurrent loads of the same path and revision share one in-flight downsample. The byte budget, the LRU and the concurrency cap work as the plan specified.
- **Commit:** 9e733d1

**3. [Rule 2] Widget-tile loop moved into `widget-photo.ts`**
- The plan offered this as an option ("export the loop as a small pure helper"). `encodeTileThumbs` lives in `widget-photo.ts` rather than `widget-render.tsx` because the render module pulls in native widget libraries that node tests cannot load. With the loop moved, `widget-render.tsx` no longer uses `Logger`, so that import was removed.

## Surface to owner

- **`MASTER_QUALITY = 0.8` is a starting value, not tuned on a device.** The plan's comment calls it "device-tuned for parity with q0.75 JPEG", but nobody has measured it on a phone yet. 38.6-07 measures real master and backup sizes against the 8 MiB encrypted-backup cap (D-20). If sizes or visual parity miss, change this one number.
- **Dev-only Fast Refresh caveat (debug builds only; release builds unaffected).** Fast Refresh re-runs every effect of an edited component. Editing `OrbitBody`, `SunBody` or `use-orrery-photo.ts` while the Orrery is open retires the live image until the reload publishes a new one. A Canvas re-record in that window can throw "Attempted to access a disposed object". Release builds are not affected. The hook cannot tell a Fast Refresh cleanup from an unmount, so I have documented this in the module header rather than weakening disposal.
