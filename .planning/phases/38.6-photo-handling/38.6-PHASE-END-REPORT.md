## Orrery memory (D-11 → D-37 → D-41)

Same fixed method each time: 3 cold starts per photo set, the same 50 photos as 512 JPEG and as 1024 WebP, `dumpsys meminfo` on the phone at 2 s, 20 s (the judged sample) and 70 s.

| Measurement | Graphics at 20 s | GL at 20 s | Result |
|-------------|-----------------:|-----------:|--------|
| First (before any fix) | +23.2 % | +31.8 % | fail |
| After D-37 (in-memory cache) | +23.0 % | +32.5 % | fail (70 s: +2.4 % / +3.3 %) |
| **After D-41 (copy on disk)** | **+2.9 %** | **+4.2 %** | **pass** (70 s: +1.9 % / +2.7 %) |

The cause was the image resizer: it loaded every 1024 photo into graphics memory on every cold start, and that memory was not freed until much later. With the small copy on disk, the 1024 photo is resized once per photo change, and every later open reads the small copy. The GL margin (0.8 points) is smaller than the run-to-run spread, so read it as "about level with the old photos", not as a precise number.

Photo loading on the phone (`screenrecord` frames; what you see, not thread timings):

| Visit | 512 JPEG photos | 1024 WebP photos |
|-------|----------------:|-----------------:|
| First open after a cold start: last photo shown | 5.6 s | 9.7 s (all photos arrive together) |
| Return to the Orrery | 5.3 s, photos arrive with the planets | 5.6 s, photos arrive with the planets |

The return visit no longer shows initials first. The ~5 s empty Orrery before the planets appear on a return is the Orrery reloading, the same as before this phase. The 1024 set's cold start is still about 4 s slower even with the copies on disk; that is logged as a follow-up (memory is not affected).
