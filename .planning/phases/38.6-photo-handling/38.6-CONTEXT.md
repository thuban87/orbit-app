<domain>
## Phase Boundary

Make every surface that shows a contact show that contact's current photo (fixing the Android image-cache staleness
and the initials-only surfaces), make the Profile, Contacts List and Contacts Grid photos bigger, rework the Grid card's
corner controls and name wrapping, and add a full-screen, zoomable lightbox for the Profile photo. No new network path.
</domain>

<decisions>
## Implementation Decisions

Owner requests, 2026-09-29 (see the dossier for detail and the grounding findings):

- **D-01:** Photos sync across the app. A changed photo updates everywhere, including the Profile and the Contacts page.
  Root cause (verified): expo-image on Android ignores `cacheKey` for `file://` URIs and each contact's photo file is
  overwritten at the same path. The fix must cover every writer of `contacts.photo` / `profile.photo` / custom photo
  fields (crop, remove, import, import retry, reconcile, merge, restore), not only the crop screen.
- **D-02:** Audit every place a contact is listed or shown and use the real photo instead of initials. Example: the
  Digest Your Week day detail (`DigestDayDetail.tsx`, `photo={null}`). Scope boundary per O-2.
- **D-03:** Tapping the Profile photo opens a full-screen lightbox, zoomable.
- **D-04:** The Profile photo is about 2× bigger (112 → ~224) and grows upwards. The content below must not move lower
  than today. Device tuning is expected.
- **D-05:** Contacts List view photos 50% bigger (48 → 72).
- **D-06:** Contacts Grid view photos about 2× bigger to start, sized from the available card width (see the dossier's
  width budget). Device tuning is expected.
- **D-07:** The Grid card favourite star and selection checkbox sit 5px from their card edges (visible glyph). The
  48×48 hit areas stay.
- **D-08:** Grid card names wrap to 2 lines: fill line 1 first; only the overflow (normally the last name) goes to line 2.
- **D-09:** Every card in a grid row shares the row's name height. If any card in the row needs line 2, all cards in
  that row reserve it; other rows are unaffected.

Discuss rulings, 2026-09-29 (dossier § Discuss Rulings is authoritative; these mirror it):

- **D-10:** Every NEW photo write (crop/picker, URL download, device import, import retry, reconcile, custom photo
  field, self photo) saves ONE square master up to 1024×1024 as **WebP** (never upscaled; a smaller source keeps its
  own size). Quality tuned for parity with today's q 0.75 JPEG. **Reverses `07-photos.md` Cluster B's 512 JPEG size**
  (owner, informed of the ≈2.5–3× storage/backup growth; accepted). Still one file per photo, no thumbnail/original.
- **D-11:** Working memory must not grow. expo-image surfaces already decode at display size. The Skia Orrery
  (`OrbitBody.tsx`, `SunBody.tsx` `useImage`) must get a downsampled image so its GPU texture memory is no higher than
  today. Verify the widget (`src/services/widget/widget-photo.ts`) still fits RemoteViews from a 1024 WebP source.
- **D-12:** Existing 512 JPEG masters are left as-is (no conversion sweep); they change only when a new photo is
  written. Every reader, backup export, restore, merge re-homing and the launch sweep must handle a mixed `.jpg`/`.webp`,
  512/1024 library.
- **D-13:** Device import already imports the phone contact's photo (`import-acquire.ts` → `import-photo.ts`); it now
  follows D-10. Import review, consolidation prompt and legacy picker already show phone photos — no change there.
- **D-14:** Real photos replace initials on every surface showing an existing Orbit contact (Digest Your Week day
  detail, duplicate/reconcile candidate grid, and anything the audit finds). **Pending confirmations gains photos.**
  History DateDetailSheet, reach-out chooser, archived contacts and merge impact summary stay text-only.
- **D-15:** Lightbox on the Profile photo only, built as a reusable component.
- **D-16:** Lightbox gestures: pinch, double-tap zoom in/out, pan when zoomed; close via Back, a labelled ✕, or
  swipe-down; near-opaque theme-token scrim; TalkBack-operable.
- **D-17:** The Profile favourite star moves into the top app bar beside ⋮; its utility row above the photo is
  removed. Keep ≥44 hit area and the Add/Remove Favorites labels. The photo may rise into the app bar's empty middle
  band (device tuning).
- **D-18:** Pulled in: todo `2026-08-26-validate-restore-progress-with-imported-photo-library` — in the device pass,
  restore a ~50-photo-contact backup and confirm progress + Back behaviour. No new code unless it finds a bug.
- **D-19:** The stale-photo fix approach is an engineering call (new filename per write preferred); it must cover every
  writer, use the 38.2 RG-010 ownership primitives, and handle D-12. Backups carry `photoBase64` with no extension or
  MIME, so restore must place WebP bytes correctly. **Any backup-format bump (today v7) → stop and ask the owner.**

Post-research rulings, 2026-09-29 (dossier § Post-research rulings is authoritative):

- **D-20:** Encrypted-backup 8 MiB cap is NOT changed in this phase. The device pass measures real encrypted and
  automatic backup sizes with a 50–100 photo-contact 1024 WebP library and reports them to the owner, who decides later.
- **D-21:** Filenames unchanged (38.2 D-09 / ADR-021): new masters are WebP bytes stored under the existing `.jpg`
  identity-derived paths; readers decode by content. D-12's "mixed library" = mixed JPEG/WebP content and 512/1024
  sizes. Supersedes D-19's "new filename per write": the stale-photo fix must not rename files. If it can only work by
  renaming → stop and ask the owner.
- **D-22:** Imported phone photos stay thumbnail-sized (native picker reads the thumbnail); no native change this phase.

Execution rulings, 2026-09-30 (dossier § Execution rulings is authoritative):

- **D-23:** A missing canonical photo file never clears the stored reference (incl. `settleRowLocked`'s missing-pending
  branch); the reference stays; the Profile hero and photo editor show a visible "Photo unavailable" state; smaller
  photos keep plain initials (M3a). Clearing it was rejected.
- **D-24:** Manual and automatic backups skip an unreadable photo instead of failing, and report the count ("1 photo
  couldn't be included"). No backup-format bump; if one seems needed → stop and ask the owner.
- **D-25:** Add Orbit photos to F-1 (import "Choose an existing contact" + "might already be in Orbit" choices), F-2 (Home
  assist banner), F-3 (Update from Contacts "keep Orbit photo" option). Not F-4 / F-5.
- **D-26:** Skipped photos carry an optional per-row backup marker (e.g. `photoSkipped: true`); restore (Merge and
  Replace-all) leaves the local photo bytes and reference untouched for a marked row. New optional key approved; no
  format bump, no migration (if required → stop and ask).
- **D-27:** Profile background images stay all-or-nothing in backups; revisit only if seen.
- **D-28:** Replace-all: a marked row whose local file was already missing gets a reference to its own new canonical
  (no file) so it shows "Photo unavailable"; never write an old path back.
- **D-29:** Export skips + counts a photo only when its file is missing/empty; other read errors fail the backup (narrows D-24).
- **D-30:** Restore result: safety-backup count keeps "N photo(s) couldn't be included."; already-missing photos read
  "N photo(s) were already missing on this phone and couldn't be restored."

Carried constraints: `docs/dossier/07-photos.md` (single master — size superseded by D-10, document dir, base64 in backup); 38.2 RG-010 photo
ownership primitives; theme tokens for every colour; any schema change is a forward-only migration at head+1 (verify on
disk; head is 032 on 2026-09-29); a backup-format bump is an owner decision; local-first.
</decisions>
