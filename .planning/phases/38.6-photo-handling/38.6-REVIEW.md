## Warnings

### WR-01: `settleRowLocked` retires a finalize row without checking the canonical exists, which can leave a permanent dangling reference that makes every backup export fail

**Fix status:** Not implemented in this pass. The owner ruled on 2026-09-30 (CONTEXT D-23, D-24):
- the reference is kept, and surfaces show a visible "photo unavailable" state;
- backups skip and count an unreadable photo.

The clearing fix suggested above is rejected by D-23. The work belongs to the plan that implements D-23 and D-24. WR-06's fix is compatible with it: WR-06 only drops the lightbox entry and never touches the reference.

**File:** `src/services/photos/owned-master.ts:211-220` (also `src/backup/export-manifest.ts:53-61`)

**Issue:** When a finalize row's reference still matches but its pending file is missing, the row is retired on the assumption that "a previous finalization reached the canonical but died before row cleanup". The canonical file is never checked. Three problems follow:

1. **The stated rationale cannot happen under the current ordering.**
   - `persist` copies the pending file; it never moves it (`persistMaster` step 1).
   - `settleRowLocked` retires the row (line 235) *before* `deleteRestorePending` (line 236).
   - So a crash in this function leaves either (row + pending) or (pending with no row), never (row with no pending).
   - The branch therefore fires only after an external loss of `avatars/_restore_pending/*`, a state left by an older ordering, or a future bug. Those are exactly the cases where the canonical may be missing too.
   - The comment at lines 219-220 is misplaced: it sits below the branch it describes.
2. **Once the row is retired, the dangle is permanent and silent.**
   - `contacts.photo` (or the profile or custom value) still names a file that does not exist. The journal row that recorded the failure is gone, so the launch sweep never sees it again.
   - The UI degrades to initials, the orrery shows nothing, and the widget falls back to initials.
3. **The worse consequence is in backups.**
   - `export-manifest.ts:55-61` throws `BackupPhotoUnreadableError` for any unreadable referenced photo, and nothing upstream catches it per contact (`backup-service.ts` has no mapping).
   - So one dangling reference fails every manual and automatic backup, with no hint of which contact is to blame, until the user happens to replace or remove that photo.
   - The "UAT Ada" contact on the test Pixel (38.6-01 / 38.6-03 SUMMARY: `contacts.photo = avatars/contact-1.jpg`, file absent) is exactly this state, whatever its origin. That phone's backups should be checked now.

**Rating:** WARNING, not BLOCKER. The branch is pre-existing (38.6 only added the adjacent notify), and it cannot be reached from this code's own crash windows. It is the only place the ownership layer knowingly throws away evidence of a lost photo, and with the all-or-nothing export the impact is "no backups", not "initials". Treat it as a priority hardening item.

**Fix (minimal, stays inside the ownership layer, no schema or format change):** in the missing-pending branch, check the canonical. If it is gone, clear the matching reference together with the row in one write transaction, then publish a display revision.

```ts
if (!listRestorePendingPhotos().some((item) => item.relative === entry.relativePath)) {
  if (!photoFileExists(entry.canonicalRelativePath)) {
    // Neither the pending bytes nor the canonical survive: the reference can
    // never resolve. Clear it with the row so export and display stay consistent.
    await inWriteTransaction(exec, async () => {
      await clearMatchingReferenceCore(exec, entry); // UPDATE … SET photo = NULL WHERE uid = ? AND photo = ? (per targetKind)
      await deleteJournalEntryCore(exec, entry.relativePath);
    });
    notifyPhotoBytesChanged(entry.canonicalRelativePath);
    Logger.error("owned-master", "finalize bytes lost; reference cleared");
    return;
  }
  // Pending already consumed and the canonical exists: the bytes landed.
  await retire(exec, entry.relativePath);
  return;
}
```

- Do **not** "fix" this by throwing `PhotoRecoveryPendingError` instead. `settleCanonicalLocked` runs before every `persistOwnedMasterLocked`, so that would wedge the path forever, and the user could never re-pick the photo.
- Clearing a lost photo's reference versus keeping it flagged is a product choice. If the owner prefers "keep and flag", the alternative is to make export skip-and-count unreadable contact photos. That touches backup semantics, so it is the owner's call.
- Separately and independently: the export's all-or-nothing policy for a single unreadable photo deserves an owner look.

### WR-02: Manipulator contexts are never released, so the "release every ImageRef" work frees almost nothing, and D-11's flat-memory claim is weaker than stated

**Fix status:** Fixed in `46084a5`. `encodeMaster` (both contexts in the no-crop branch), the orrery downsample and the widget thumbnail now release their `ImageManipulatorContext` in the same `finally` as the rendered ref. Release-count tests cover success, save failure and render failure.

**File:** `src/services/photos/master-encode.ts:104-134`, `src/components/orrery/use-orrery-photo.ts:94-114`, `src/services/widget/widget-photo.ts:69-86`

**Issue:**

- On Android, `ImageRef` is a `SharedRef<Bitmap>` with no `sharedObjectDidRelease` override (`ImageRef.kt`). So `rendered.release()` only removes the JS registry entry. It does not recycle the bitmap.
- The same final `Bitmap` is still held by the `ImageManipulatorContext`'s `ManipulatorTask` Deferred result (`ImageManipulatorContext.kt`, `task.await().get()`).
- The contexts created by `ImageManipulator.manipulate(...)` are never released: one in the crop branch, two in the no-crop branch, one per orrery downsample, one per widget tile.
- `ImageManipulatorContext` reports no additional memory pressure, so Hermes has no reason to collect these small JS wrappers soon.

Concrete retention:

- In the `encodeMaster` no-crop branch, the first context keeps the full decoded `base` bitmap. `releaseQuietly(base)` does not free it.
- The orrery downsamples up to one 512 bitmap (1 MB) per 1024 master on each Orrery focus that misses the 4 MiB string LRU. With about 40 or more 1024-photo contacts the LRU thrashes, and each focus leaves tens of MB of native bitmaps waiting on an unrelated GC.

The SUMMARY's T-04-01 mitigation ("every SkImage disposed", release counts pinned by tests) is true of the JS calls. It is not true of the native memory.

**Fix:** keep the context and release it in the same `finally` as the rendered ref. `ImageManipulatorContext extends SharedObject`, which has `release()`.

```ts
const context = ImageManipulator.manipulate(sourceUri).crop(crop);
let rendered: RenderedRef | null = null;
try {
  rendered = await (edge < side ? context.resize({ width: edge, height: edge }) : context).renderAsync();
  return await saveMaster(mod, rendered);
} finally {
  releaseQuietly(rendered);
  try { context.release(); } catch {}
}
```

- Apply the same pattern to both contexts in the no-crop branch, to `downsampleWithManipulator`, and to `encodeWidgetThumb`.
- Extend the release-count tests to assert that the context is released too.

### WR-03: The Profile app bar now comes last in TalkBack order (a regression from making it an overlay)

**Fix status:** Fixed in `2d4398e`. **The suggested fix alone did not work.** On the Pixel, `uiautomator` showed that Android does not order accessibility children by child index. `ReactViewGroup.addChildrenForAccessibility` falls through to the platform sort, which orders children by bounds: top edge, then left, then the taller view first. So moving `ProfileAppBar` before the ScrollView changed nothing: the full-height ScrollView still sorted first. The commit keeps the JSX move and also starts the ScrollView exactly one physical pixel lower (`profileScrollA11yOffset`). That same pixel comes out of the content padding (`profileScrollContentTopPadding`). On device:
- the bar is now read first;
- the photo and name bounds are identical (photo top 215 px, name 1055 px);
- the star, ⋮ and photo taps still land.

`experimental_accessibilityOrder` was rejected: it is experimental, and it would pull the ScrollView node out of the tree and turn off focus on descendants.

**File:** `src/screens/ContactProfileScreen.tsx:532-655`

**Issue:**

- `ProfileAppBar` is rendered *after* the `ScrollView` (line 646) so that it draws on top.
- Android builds the accessibility tree in child-index order. `zIndex` changes RN draw order, not accessibility traversal, and no child has a translationZ.
- So TalkBack now reaches Back, Add/Remove Favorites and More actions only after the entire Profile: hero, lifecycle card, and every module.
- Before 38.6 these three controls were the first focusable elements. The project did explicit TalkBack work in 38.4, and D-16/D-17 call these controls out.

**Fix:** render `ProfileAppBar` *before* the `<ScrollView>` in the JSX. Its existing `position: "absolute"`, `zIndex: 1` and `pointerEvents="box-none"` keep it drawn and hit-tested on top. RN honours `zIndex` for both drawing order and touch targeting among siblings. Do not use Android `elevation` for this: see the translucent-elevation hazard in `GlassSurface.tsx`.

### WR-07: `photo-writer-contract.test.ts` enforces less than it claims

**Fix status:** Fixed in `e8385a4`. The source-scan test now also enforces:
- `notifyPhotoBytesChanged` callers are exactly owned-master and restore-apply (the replace-all cleanup delete is a legitimate caller);
- only owned-master may import `reconcilePhotoWritesForCanonical`, and it counts as a raw writer;
- only `photo-display.ts` may import `resolvePhotoDisplayUri`.

Each new matcher has positive and negative fixtures. The dead `reconcilePhotoWrites` export is deleted and pinned so it cannot come back. The header was reworded to say what the scan actually checks.

**File:** `src/services/photos/photo-writer-contract.test.ts:25-56, 245-258`

**Issue:** The 38.6-03 SUMMARY says the scan pins "revision publishers are exactly owned-master.ts" and all raw byte writers. In the code:

1. **Raw writers are only `persistMaster` and `deletePhoto`.**
   - `reconcilePhotoWrites` and `reconcilePhotoWritesForCanonical` are also exported from `photo-storage.ts` (lines 492-529). They move a `.bak` onto a canonical, which changes the displayed bytes.
   - A new importer of either would change bytes without a revision and without the path lock, and the contract would stay green.
   - `reconcilePhotoWrites` has no production caller at all: it is dead, unguarded surface.
2. **Only `bumpPhotoCacheBust` is restricted.**
   - `notifyPhotoBytesChanged` is exported and already called outside `owned-master.ts` (`restore-apply.ts:1916`).
   - "Exactly owned-master publishes" is true only of the store call, not of revision publication.
3. **`resolvePhotoDisplayUri` is not restricted.**
   - A component can call `resolvePhotoDisplayUri(p, undefined)` and hand expo-image a bare `file://` URI with the default (`disk`) cache policy. That silently reintroduces the D-01 staleness, and the plain-resolver rule never sees it.
