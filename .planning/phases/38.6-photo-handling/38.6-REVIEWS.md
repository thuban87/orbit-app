# Plan 38.6-01 — Display revision tracer and device spike

## Summary

The strategy is well chosen: preserve identity-derived filenames, change only the expo-image display source, disable disk caching for local avatars, and prove the assumption on hardware before spreading it throughout the app. This directly addresses the real Android cache mechanism while respecting D-21 and the rejected filename alternatives.

## Strengths

- Correctly separates display invalidation from authorization state. `canonicalGeneration()` and `bump()` currently govern write authorization in [owned-master.ts](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:42), while canonical persistence increments that generation only after successful persistence at line 288. Creating a separate display notification avoids breaking import retry and merge authorization.
- The guarded URI composition builds on the existing safe-path boundary. `resolvePhotoUriFromDocumentUri()` calls `assertSafeRelative()` before producing a URI in [photo-storage.ts](/home/bwales/projects/orbit-app/src/services/photos/photo-storage.ts:273).
- Switching Avatar away from `memory-disk` addresses the current stale disk-cache path. Avatar presently uses a stable `file://` URI, a cache key, and `cachePolicy="memory-disk"` in [Avatar.tsx](/home/bwales/projects/orbit-app/src/components/Avatar.tsx:67).
- The real-device spike is appropriate because the query-string behavior depends on Android/Glide URI handling rather than an application-level invariant.
- The stop condition correctly identifies filename changes as an owner decision.

## Concerns

- **MEDIUM — Launch-sweep registration needs an explicit one-shot guard.** The task says to register `registerLegacyImageDiskCacheSweep()` in `App.tsx`, but does not explicitly add a module-level boolean guard. The ready-gated effect can re-enter, and the existing app deliberately guards every registration for that reason; see the explanation and flags in [App.tsx](/home/bwales/projects/orbit-app/App.tsx:117) and guarded registrations such as the derivative sweep at lines 260–263. Without the same guard, Strict Mode/remounts can register duplicate cache-clear hooks.
- **LOW — The disk-cache clear is global, not avatar-specific.** `Image.clearDiskCache()` clears expo-image’s entire disk cache. The plan should acknowledge that this may evict unrelated cached images and cause one-time decode or reload costs. It is defensible, but broader than “remove legacy avatar entries.”
- **LOW — The probe’s mean central colour is vulnerable to overlays and crop composition.** A thin grid does not ensure the central 60% is uniformly red or blue after user crop positioning. This could produce a false failure despite a correct cache fix.

## Suggestions

- Add a named `legacyImageDiskCacheSweepRegistered` module-level flag and assert registration occurs exactly once, following the existing `derivativeCacheSweepRegistered` pattern.
- Record the global eviction consequence in the plan and summary.
- Make the probe fixtures overwhelmingly monochrome across the whole crop, or compare red-vs-blue channel dominance rather than absolute RGB distance.

## Risk assessment

**MEDIUM.** The cache strategy itself is sound and safely gated, but duplicate sweep registration is a real lifecycle issue unless explicitly prevented.

# Plan 38.6-03 — Every writer and display site

## Summary

Centralizing notification at the byte-ownership layer is the right architecture. The plan also correctly removes redundant crop-screen bumps and protects the invariant with a contract scan. One restore-cleanup path, however, repeats the exact deletion-completion mistake that the ownership layer already avoids.

## Strengths

- Correctly covers journal finalization, delete intents, restore/merge finalization, and launch reconciliation at their shared choke points.
- The plan recognizes that `deletePhoto()` is best-effort. The existing ownership deletion path calls the remover and then verifies absence before completing in [owned-master.ts](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:160).
- Correctly keeps authorization `bump(canonical)` limited to the two existing locations: successful owned persistence and successful remove-owned completion at [owned-master.ts](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:288) and [owned-master.ts](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:316).
- Removing the crop-screen bumps is appropriate because those are currently the only reactive call-site notifications in [CropPhotoScreen.tsx](/home/bwales/projects/orbit-app/src/screens/CropPhotoScreen.tsx:328).
- The contract scan’s intent is valuable because SQL/file ownership edges are not visible to Graphify.

## Concerns

- **MEDIUM — The raw restore cleanup notifies without proving deletion succeeded.** The plan says to call `notifyPhotoBytesChanged()` immediately after `remove(...)` in the replace-all cleanup. But the default remover is `deletePhoto`, which swallows errors in [photo-storage.ts](/home/bwales/projects/orbit-app/src/services/photos/photo-storage.ts:384). The restore loop already has an `exists` dependency at [restore-apply.ts](/home/bwales/projects/orbit-app/src/backup/restore-apply.ts:1882), but the current cleanup does not use it after removal at line 1911. Publishing a revision in that state reloads the still-present old bytes and falsely records cleanup success.
- **MEDIUM — The source-scan import allowlist is likely too fragile for the stated guarantee.** The code already uses dependency injection and dynamic imports extensively. For example, import-photo defines its own `persistMaster` dependency and dynamically resolves the owned writer in [import-photo.ts](/home/bwales/projects/orbit-app/src/services/import/import-photo.ts:19) and [import-photo.ts](/home/bwales/projects/orbit-app/src/services/import/import-photo.ts:62). Regex-based binding analysis can detect syntax but cannot prove aliases are invoked as restricted operations without becoming a partial parser.
- **LOW — The test criterion “no expo-image file also imports resolvePhotoUri” is architectural convention, not a full display-path proof.** A file could obtain the resolver through a re-export or helper and evade that exact import condition.

## Suggestions

- In restore cleanup, call `remove()`, then require `!exists(canonical)` before notifying. If the file remains, increment cleanup-pending or throw `PhotoRecoveryPendingError`, matching `executeDeleteIntentLocked()`.
- Narrow the contract test to enforce known module boundaries and direct/dynamic imports without claiming it proves all possible future aliases.
- Prefer an exported owned-byte-writer module boundary or lint rule if the source scan grows much more complex.

## Risk assessment

**MEDIUM.** The architecture is strong, but the restore-cleanup completion check must be corrected before execution.

# Plan 38.6-04 — 1024 WebP masters, Orrery and widget

## Summary

The shared master encoder and 512-pixel Orrery gate are the correct response to D-10 and D-11. The plan handles mixed formats without renaming files and adds meaningful lifetime tests. The widget path remains incomplete for native-resource lifetime, and the proposed cache budget is not a reliable heap budget.

## Strengths

- Correctly consolidates the three duplicated 512/JPEG encoders currently present in [photo-pipeline.ts](/home/bwales/projects/orbit-app/src/services/photos/photo-pipeline.ts:40), [import-photo.ts](/home/bwales/projects/orbit-app/src/services/import/import-photo.ts:15), and [reconcile-photo.ts](/home/bwales/projects/orbit-app/src/services/photos/reconcile-photo.ts:12).
- Correctly fixes existing import/reconcile distortion and upscaling by center-cropping and conditionally resizing.
- Explicitly setting WebP quality below 1 avoids the lossless default.
- Preserving `.jpg` identity-derived names is compatible with current crash-safe storage and opaque backup bytes. Restore already writes decoded bytes verbatim in [photo-storage.ts](/home/bwales/projects/orbit-app/src/services/photos/photo-storage.ts:179).
- The Orrery plan is careful about not caching `SkImage` objects and requires exact disposal tests.
- Serializing widget thumbnail generation fixes the current `Promise.all` peak visible in [widget-render.tsx](/home/bwales/projects/orbit-app/src/services/widget/widget-render.tsx:168).

## Concerns

- **MEDIUM — The widget encoder still leaks/defers release of its rendered native image.** The plan explicitly leaves `widget-photo.ts`’s encoder unchanged, but it creates a rendered `ImageRef` at [widget-photo.ts](/home/bwales/projects/orbit-app/src/services/widget/widget-photo.ts:67) and never calls `release()`. Sequential execution caps concurrency but does not guarantee prompt native bitmap release. That undercuts D-11’s “working memory must not grow” requirement, especially with 1024 inputs.
- **MEDIUM — `base64.length` is not a reliable 4 MiB JS-heap budget.** The plan describes `ORRERY_DERIVATIVE_CACHE_BYTES` as approximately 4 MiB of JS heap but proposes accounting only by base64 string length. That is character count, not decoded-byte size, and JavaScript string storage width is runtime-dependent. The cache may consume materially more heap than claimed.
- **MEDIUM — The semaphore/reset design needs protection against resetting while work is in flight.** `resetOrreryPhotoCacheForTests()` is specified to clear both cache and queue. If implemented by mutating production module queue state rather than only isolated injected state, late completions can corrupt slot counts or strand waiters.
- **LOW — The encoder’s no-crop branch performs an initial render merely to obtain dimensions.** That may transiently decode the full source before the cropped/downsized render. It is acceptable for single imports, but should be acknowledged in D-11 discussions rather than described as universally flat memory.

## Suggestions

- Update `encodeWidgetThumb()` to release its rendered `ImageRef` in a `finally`, covering both `saveAsync` success and failure.
- Either store binary encoded data and use actual byte lengths, or conservatively charge base64 entries at two bytes per character. Rename the constant if it represents encoded-character budget rather than heap bytes.
- Put queue/cache state behind an injectable factory for tests; avoid a production reset that can run against live operations.
- Add a test that widget `release()` is called exactly once on success and failure.

## Risk assessment

**MEDIUM.** The main architecture is good, but D-11 is not fully achieved until widget native-resource lifetime and cache accounting are corrected.

**Suggestion:** add a Grid scroll jank reading (gfxinfo) to Plan 01's spike or Plan 07 Task 3, on whichever strategy is chosen.
