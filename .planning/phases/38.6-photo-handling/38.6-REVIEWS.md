# Cross-AI Plan Review — Phase 38.6

# Cross-AI Plan Review — Phase 38.6

## Overall assessment

The plans are strongly grounded in the current implementation and preserve the critical owner decisions: identity-derived filenames, RG-010 ownership, backup format v7, local-only reads, and separate authorization/display generations. The decomposition and ordering are mostly sound.

However, I would not execute the phase unchanged. Two issues are high risk:

1. Plan 04’s proposed Orrery hook does not specify complete `SkImage` disposal and introduces a potentially large process-lifetime encoded-image cache, undermining D-11.
2. Plan 07 is too large for one executor and still does not explicitly exercise import retry, despite claiming every writer is covered.

There are also several test and measurement claims that are stronger than the mechanisms described.

Graph queries could not run in this environment because `tsx` failed to create its IPC socket (`EPERM` under `/tmp/tsx-1000`), so ADR relationships below rely on the supplied dossiers plus direct source inspection rather than graph output.

# 38.6-01 — Display-revision tracer and device spike

## Summary

This is a well-designed risk-first plan. It validates the uncertain Glide query behavior before spreading the mechanism through the app, while respecting D-21’s fixed filenames. Separating display revision from `canonicalGeneration` is especially important and matches the current ownership architecture.

## Strengths

- The plan correctly preserves authorization state. `canonicalGeneration()` and its private `bump()` currently protect retry and merge behavior, and are updated only after canonical persistence or successful owned removal ([owned-master.ts:42](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:42), [owned-master.ts:274](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:274), [owned-master.ts:302](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:302)).
- The URI composer is placed beside the existing guarded boundary. `resolvePhotoUriFromDocumentUri()` already validates the relative path before joining it to the document URI ([photo-storage.ts:273](/home/bwales/projects/orbit-app/src/services/photos/photo-storage.ts:273)).
- Moving local avatars away from `memory-disk` directly addresses the current stale-disk risk. Avatar currently sends the same bare `file://` URI and relies on a cache key that Android ignores for local files ([Avatar.tsx:67](/home/bwales/projects/orbit-app/src/components/Avatar.tsx:67)).
- The device spike is justified. The central assumption—query retained in Glide’s model but ignored while opening the file—is not proved by repository code and should be tested before broad rollout.
- The owner stop is correctly scoped: neither fallback authorizes renaming.

## Concerns

- **MEDIUM — Task 1 lands a deliberately incomplete ownership notification contract.** It notifies only `persistOwnedMasterLocked`, while finalize, delete, restore cleanup, and crash recovery remain uncovered until Plan 03. That is acceptable by ordering, but the new function’s documentation must not imply completeness during the interval. The current ownership layer has several independent byte-change mechanisms ([owned-master.ts:133](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:133), [owned-master.ts:180](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:180), [owned-master.ts:349](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:349)).
- **MEDIUM — The probe’s mean-color check can produce false confidence.** An avatar may contain status rings, clipping, overlays, antialiasing, or crop offsets. A central 60% average is useful evidence, but it does not prove that the exact expected source was decoded.
- **LOW — The plan changes a global production strategy constant based on one Android device.** That is reasonable for Android-first v2, but the spike report should record OS version, Expo Image version, and whether both strategies were tried only when needed.
- **LOW — Plan size is high for a two-task spike.** The 95k estimate is close to an executor-sized plan by itself. Device automation and picker handling are the likely context sink.

## Suggestions

- Add an explicit temporary comment to `notifyPhotoBytesChanged`: “Plan 01 covers owned persist only; Plan 03 completes the byte-change matrix.”
- Supplement RGB probing with a before/after screenshot hash over the avatar interior, or include the grid pattern’s variance/edge evidence so a solid fallback swatch cannot accidentally pass.
- Record the selected strategy in a machine-readable export from the module or test, not only `38.6-SPIKE.md`.
- Require the spike to confirm the bare URI after process restart, not merely that the photo looks correct.

## Risk Assessment

**MEDIUM.** The uncertainty is appropriately isolated, but the core strategy still depends on platform behavior that only the spike can validate.

# 38.6-02 — Photo coverage

## Summary

This plan accurately targets the data gaps and the two raw-image bypasses. The SQL additions are small and well bounded. The code-derived coverage audit is valuable, provided it does not silently expand D-14.

## Strengths

- The Your Week defect is correctly traced through the whole data path: the current row type has no photo field, both UNION arms lack it, and the component consequently passes `photo={null}` ([your-week-read.ts:30](/home/bwales/projects/orbit-app/src/db/your-week-read.ts:30), [your-week-read.ts:117](/home/bwales/projects/orbit-app/src/db/your-week-read.ts:117)).
- The plan preserves UNION shape by adding the field to both arms.
- Pending confirmations currently selects only the name and renders text without an Avatar, so the proposed change is grounded ([interaction-assist-read.ts:33](/home/bwales/projects/orbit-app/src/db/interaction-assist-read.ts:33), [PendingConfirmationsSheet.tsx:193](/home/bwales/projects/orbit-app/src/components/PendingConfirmationsSheet.tsx:193)).
- The pending-assist query intentionally has no archived-contact exclusion, which supports the plan’s “archived-but-not-purged” expectation ([interaction-assist-read.ts:38](/home/bwales/projects/orbit-app/src/db/interaction-assist-read.ts:38)).
- Routing canonical photos through Avatar is the right abstraction; staging URIs remain a separate concern.

## Concerns

- **MEDIUM — Task 3 permits unreviewed implementation scope growth.** “If the audit finds an existing-contact surface that renders initials … fix it in this task” can add unknown component and data-layer changes after plan approval. That conflicts with accurate file ownership and executor sizing.
- **MEDIUM — `CandidateItem.photo` and `photoUri` create an ambiguous two-source contract.** The render precedence is specified, but callers can accidentally provide both. TypeScript should make canonical and staging sources mutually exclusive.
- **LOW — The coverage audit grep strategy will overproduce and underproduce.** Searching `.name}` and related tokens finds many non-contact names, while indirect contact renderers may not contain those strings. It remains a manual audit rather than a complete proof.
- **LOW — Pending-confirmation layout risk is understated.** Adding a 40dp avatar while keeping a one-line question can reduce usable text width substantially on small screens and large font scales.

## Suggestions

- Replace the optional dual fields with a discriminated union, for example:
  - `{ photoKind: "canonical"; photo: string }`
  - `{ photoKind: "staging"; uri: string }`
  - `{ photoKind: "none" }`
- Change Task 3’s discovered-gap rule to: document and assign the gap unless it is contained entirely within the already-listed files and executor budget.
- Add a large-text render/device check for Pending confirmations; otherwise avoid asserting the one-line layout is preserved.
- Have the audit enumerate callers of shared contact-card components in addition to JSX/string grep results.

## Risk Assessment

**LOW–MEDIUM.** The concrete changes are small and correct; most risk lies in the open-ended audit task.

# 38.6-03 — Complete writer synchronization and retire cache props

## Summary

This plan correctly centralizes display invalidation in the ownership layer and removes the misleading timestamp-based image identity. It is the strongest architectural plan in the set, but some proposed notification assertions do not match the current best-effort file APIs.

## Strengths

- The plan correctly identifies the remaining byte-changing paths:
  - journal finalization persists canonical bytes ([owned-master.ts:180](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:180));
  - delete intents call the canonical remover ([owned-master.ts:133](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:133));
  - launch reconciliation may restore `.bak` ([photo-storage.ts:403](/home/bwales/projects/orbit-app/src/services/photos/photo-storage.ts:403));
  - restore has one direct cleanup removal ([restore-apply.ts:1886](/home/bwales/projects/orbit-app/src/backup/restore-apply.ts:1886)).
- It correctly retains the two existing authorization bumps. `removeOwnedMasterLocked` already distinguishes successful removal using before/after existence checks ([owned-master.ts:314](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:314)).
- Removing `modified_at` only from presentation prop chains, while retaining database columns, is the right boundary. Avatar currently combines `modified_at` and the process-local revision ([Avatar.tsx:41](/home/bwales/projects/orbit-app/src/components/Avatar.tsx:41)).
- The contract scan is a useful regression barrier because the graph cannot discover string-based filesystem/SQL relationships.

## Concerns

- **MEDIUM — Delete notification is placed before successful deletion is established.** `deletePhoto()` swallows errors and logs them ([photo-storage.ts:380](/home/bwales/projects/orbit-app/src/services/photos/photo-storage.ts:380)). The plan says to notify immediately after `remove(canonical)`, before `exists(canonical)` verifies success. That contradicts the claimed behavior “whose delete predicate forbids removal does not” and can publish a revision when the bytes remain unchanged.
- **MEDIUM — Launch reconciliation notification is too broad.** `reconcilePhotoWritesOwned()` iterates every canonical that has a sidecar ([owned-master.ts:349](/home/bwales/projects/orbit-app/src/services/photos/owned-master.ts:349)). The plan notifies after reconciliation without knowing whether the action was `restoreBak`, `deleteBak`, or `deleteTmp`. Only `restoreBak` changes canonical bytes.
- **MEDIUM — The source-scan allowlist is brittle.** A regex importer scan can miss re-exports, aliases, namespace imports, or dynamically imported writers. It is useful as a tripwire, not a proof that every writer is covered.
- **LOW — The task touches many unrelated-looking consumers.** Although the changes are mechanical, Plan 03 is estimated at 100k and updates more than twenty source files. This is at the executor-budget edge.

## Suggestions

- Make byte-changing functions return an outcome:
  - `executeDeleteIntentLocked(): Promise<{ removed: boolean }>`
  - `reconcilePhotoWritesForCanonical(): Promise<ReconcileAction[]>`
  
  Notify only when the canonical bytes were actually deleted or restored.
- At minimum, notify delete only after `!exists(canonical)`, while preserving the pending-error branch.
- Separate “contract tripwire” terminology from “complete proof” in tests and summaries.
- Add an assertion that reference-only changes do not increment the display revision.

## Risk Assessment

**MEDIUM.** The architecture is correct, but imprecise notifications can make the tests pass while overstating exactly-on-byte-change semantics.

# 38.6-04 — WebP masters, Orrery and widget

## Summary

The shared encoder and unchanged filename policy are well planned. The Orrery implementation, however, has a serious lifecycle problem: the plan does not fully dispose native `SkImage` objects, and its 128-entry encoded derivative cache conflicts with D-11’s “working memory must not grow” requirement.

## Strengths

- The plan correctly consolidates three currently duplicated 512/JPEG encoders:
  - crop pipeline ([photo-pipeline.ts:40](/home/bwales/projects/orbit-app/src/services/photos/photo-pipeline.ts:40));
  - import ([import-photo.ts:15](/home/bwales/projects/orbit-app/src/services/import/import-photo.ts:15));
  - reconcile ([reconcile-photo.ts:12](/home/bwales/projects/orbit-app/src/services/photos/reconcile-photo.ts:12)).
- It correctly fixes current import distortion/upscaling. Import currently forces every input to 512×512 regardless of source dimensions ([import-photo.ts:34](/home/bwales/projects/orbit-app/src/services/import/import-photo.ts:34)).
- WebP-in-`.jpg` is compatible with the current opaque byte pipeline. Restore writes decoded base64 bytes verbatim ([photo-storage.ts:179](/home/bwales/projects/orbit-app/src/services/photos/photo-storage.ts:179)), and canonical filenames remain derived later ([restore-apply.ts:1108](/home/bwales/projects/orbit-app/src/backup/restore-apply.ts:1108)).
- Sequential widget thumbnail generation directly reduces peak transient decode count. The current implementation launches all tile encodes via `Promise.all` ([widget-render.tsx:165](/home/bwales/projects/orbit-app/src/services/widget/widget-render.tsx:165)).
- Replacing `useImage` at both Orrery sites is correctly scoped ([OrbitBody.tsx:79](/home/bwales/projects/orbit-app/src/components/orrery/OrbitBody.tsx:79), [SunBody.tsx:100](/home/bwales/projects/orbit-app/src/components/orrery/SunBody.tsx:100)).

## Concerns

- **HIGH — Proposed `SkImage` lifetime handling is incomplete and can leak GPU/native memory.** The new hook is described as loading into React state with only a cancellation flag. It does not require disposal of:
  - the prior state image when path/revision changes;
  - the current image on unmount;
  - a newly loaded image when the effect has already been cancelled;
  - the large decoded image when downsampling throws;
  - a newly decoded cached derivative when later processing fails.
  
  This directly threatens D-11, whose purpose is to prevent memory growth.
- **HIGH — The 128-entry encoded derivative cache itself grows working memory relative to today.** Today `useImage` does not maintain a module-level 128-photo base64 cache. Even if it stores strings rather than textures, it adds potentially many megabytes of JS heap and therefore violates the literal “working memory must not grow” contract.
- **MEDIUM — The cache test “stores strings, never SkImage objects” does not prove absence of retained native images.** State, closures, cancelled promises, and un-disposed returned images can retain native resources independently of the Map.
- **MEDIUM — `encodeMaster` resource cleanup is underspecified for the crop branch.** The plan explicitly releases base/intermediate refs in the no-crop path, but does not explicitly require releasing the rendered crop-path `ImageRef` after `saveAsync`.
- **MEDIUM — The Orrery downsample always requests 512×512.** That is safe for the decided square master, but the loader should still derive dimensions defensively from the actual raster and preserve aspect ratio if malformed or legacy data is not square.
- **LOW — D-12 merge coverage is deferred entirely to the device plan.** The restore round trip is automated, but merge re-homing mixed bytes should also have an automated byte-preservation test.

## Suggestions

- Specify a strict ownership contract for `SkImage`:
  - every `loadOrreryImage` result has exactly one owner;
  - effect cleanup disposes the currently published image;
  - cancelled loads dispose their result immediately;
  - every error path disposes any locally created images.
- Replace the 128-entry base64 cache with one of:
  - no module cache;
  - a very small byte-budgeted LRU;
  - a cache scoped to currently visible Orrery bodies and cleared on blur/unmount.
- Add a stress unit test that repeatedly changes revisions and asserts every fake image is disposed exactly once.
- Release all `ImageRef` instances in `encodeMaster` in `finally` blocks, including crop mode.
- Add an automated merge re-home test containing JPEG and WebP magic bytes under `.jpg` canonical names.

## Risk Assessment

**HIGH.** The master-format design is sound, but the planned Orrery implementation can introduce the exact memory regression D-11 prohibits.

# 38.6-05 — Profile and lightbox

## Summary

The plan correctly traces the profile geometry and uses the existing single-overlay model. The gesture design is plausible and uses the right libraries. The main risks are hook ordering, app-bar overlay interaction, and insufficient lifecycle details for accessibility and image state.

## Strengths

- The app-bar/hero geometry is based on current source, not guesswork. The bar is currently 56dp and the hero contains a 44dp favorite row, 112dp Avatar, and 16dp gaps ([contact-profile-logic.ts:85](/home/bwales/projects/orbit-app/src/screens/contact-profile-logic.ts:85), [ProfileHero.tsx:37](/home/bwales/projects/orbit-app/src/components/profile/ProfileHero.tsx:37)).
- Moving the favorite toggle into `ContactProfileScreen` retains its current async guard and database behavior ([ContactProfileScreen.tsx:291](/home/bwales/projects/orbit-app/src/screens/ContactProfileScreen.tsx:291)).
- Extending `ProfileOverlay` is consistent with the screen’s existing one-overlay design ([contact-profile-logic.ts:65](/home/bwales/projects/orbit-app/src/screens/contact-profile-logic.ts:65)).
- Modal `onRequestClose` is the appropriate Android Back path.
- The gesture math is separated and covered by the existing worklet-order guard, addressing a known Hermes-specific risk.
- The plan honors D-15 by placing the entry point only in `ProfileHero`.

## Concerns

- **MEDIUM — Hook ordering is not explicit.** The component is told to “Return null when `photo` is null” and also to call `usePhotoDisplay(photo)`. If the return occurs before the hook, changing between null and non-null photos violates React’s hook-order rule.
- **MEDIUM — The app-bar scrim uses React state from a 16ms scroll callback.** The plan mitigates this by updating only on threshold crossings, but it should use a ref comparison inside the handler; relying on captured state can still enqueue redundant updates.
- **MEDIUM — The circle-clearance calculation models glyph boxes, not actual Pressable/Button geometry.** The existing icon-only Button is wider than the 44dp touch target because of horizontal padding; source currently uses two `Button role="iconOnly"` controls ([ContactProfileScreen.tsx:434](/home/bwales/projects/orbit-app/src/screens/ContactProfileScreen.tsx:434)). The plan’s star uses a custom 44dp Pressable while overflow retains Button geometry, so the arithmetic must match actual layout.
- **MEDIUM — Modal accessibility restoration is absent.** Focus is moved to close on open, but the plan does not restore focus to the Profile photo trigger after close.
- **LOW — `visible=false` behavior is unclear.** Returning Modal markup while invisible is fine, but gesture shared values and image source should be reset without racing a close animation.
- **LOW — The profile’s top safe-area contract is assumed rather than tested.** The current app bar is a normal-flow sibling ([ContactProfileScreen.tsx:432](/home/bwales/projects/orbit-app/src/screens/ContactProfileScreen.tsx:432)); converting it to absolute positioning can expose device-specific inset issues.

## Suggestions

- Require `usePhotoDisplay(photo)` unconditionally before any null return.
- Capture and restore accessibility focus to the photo trigger on lightbox close.
- Test the actual app-bar child frames on device, not only a pure glyph approximation.
- Use a ref-backed threshold transition:
  `if (next !== scrolledRef.current) { scrolledRef.current = next; setScrolled(next); }`.
- Add device checks for status/navigation bar insets on both target phones.

## Risk Assessment

**MEDIUM.** The design is coherent, but full-screen gesture overlays and absolute app bars are device-sensitive.

# 38.6-06 — Contacts List and Grid

## Summary

The geometry-first approach is strong, and using FlatList row stretch plus bottom-pinned secondary content is a clever way to satisfy D-09 without measurement. The primary weakness is that the plan assumes nested flex behavior will produce equal card heights without explicitly testing the rendered row structure.

## Strengths

- The responsive column thresholds are taken from current code ([CardGrid.tsx:46](/home/bwales/projects/orbit-app/src/components/CardGrid.tsx:46)).
- The card-width formula matches current content padding and inter-column gap ([CardGrid.tsx:168](/home/bwales/projects/orbit-app/src/components/CardGrid.tsx:168)).
- The plan preserves 48×48 hit areas and keeps controls inside the clipped GlassSurface. GlassSurface currently has `overflow: "hidden"` ([GlassSurface.tsx:180](/home/bwales/projects/orbit-app/src/components/ui/GlassSurface.tsx:180)).
- `textBreakStrategy="simple"` is an appropriate Android-specific way to request greedy line filling.
- Adding optional `contentStyle` is a reasonable shared-component extension; the existing wrapper currently exposes no such layout hook ([GlassSurface.tsx:169](/home/bwales/projects/orbit-app/src/components/ui/GlassSurface.tsx:169)).
- The List change is low risk because current height is a minimum and there is no stated `getItemLayout` dependency.

## Concerns

- **MEDIUM — D-09 depends on a nested flex chain that the proposed shallow tests may not prove.** FlatList stretches the outer GridCard/Pressable, but equal visible GlassSurface height requires the outer Pressable, GlassSurface container, GlassSurface content wrapper, and layout child all to propagate the stretched height. `flexGrow: 1` alone at selected levels may not fill an already-stretched parent consistently.
- **MEDIUM — The plan’s stated current Avatar size is inconsistent.** The interface section says “GridCard after 38.6-03: `AVATAR_SIZE = SPACING["2xl"]` (72),” but `SPACING["2xl"]` is 48 and the current source renders `size={AVATAR_SIZE}` from that token. This is likely a documentation typo, but geometry tests must use 48 as the baseline.
- **MEDIUM — The nominal-width rule intentionally ignores last-row stretching, but this requires a stable fixed width.** If GridCard remains `flex: 1`, a partial last row becomes wider while its photo remains based on the nominal width. That matches the plan’s stated intent, but the card’s visual centering and corner clearances should be device-checked for one- and two-item final rows.
- **LOW — Optical “5px” cannot be established from layout constants alone.** Ionicon artwork has internal whitespace; the plan recognizes this but should not make automated acceptance depend only on style padding.
- **LOW — List row expansion may materially reduce visible density.** This is owner-approved in principle, but a 96dp row is a large change from the current minimum.

## Suggestions

- Add `flex: 1` or `height: "100%"` where needed after a small render experiment; do not rely solely on `flexGrow`.
- Add an integration-style layout test or device screenshot comparison containing:
  - one one-line/one two-line row;
  - a fully one-line row;
  - a partial final row.
- Correct the plan’s 48/72 token wording before execution.
- Treat screenshot-measured optical inset as the authoritative D-07 result; pure geometry should prove collision avoidance only.

## Risk Assessment

**MEDIUM.** The pure geometry is good, but the row-height mechanism depends on real React Native layout behavior that shallow tests cannot fully establish.

# 38.6-07 — Device pass, measurements and release

## Summary

The verification goals are appropriate and unusually comprehensive, but this plan is not executable within the stated one-executor budget. It combines fixture tooling, extensive device setup, dozens of manual flows, memory experiments, backup encryption tests, an owner checkpoint, source tuning, a remote release build, release smoke tests, and reporting. It also omits a required writer from the device matrix.

## Strengths

- It correctly places code review before device validation and the release build last.
- D-20 is handled as measurement and owner reporting, not an unauthorized encryption-posture change.
- It distinguishes physical-phone memory evidence from emulator evidence.
- Mixed-library checksum verification is stronger than merely observing images render.
- It preserves the no-push/no-Drive rules and uses the existing remote build route.
- Owner-taste decisions are correctly placed behind a blocking checkpoint.
- The source-tuning allowlist is explicit, limiting post-sign-off mutation.

## Concerns

- **HIGH — The plan exceeds the mandated executor budget.** At 180k estimated tokens and five extremely large tasks, it is not realistically completable by one executor around the project’s ~50% context target. The plan itself anticipates handing back to fresh executors mid-plan, which confirms the size problem. Because the seven-plan structure has already been shown to the owner, splitting Plan 07 now triggers the explicit owner gate.
- **HIGH — Import retry is missing from the device writer matrix.** D-01 explicitly includes import retry. Task 3 covers self photo, custom field, remove, merge, restore, import, and reconcile, but never creates a failed import photo and exercises the retry path. Yet the plan claims “every writer.”
- **HIGH — The release smoke test is destructive to the signed release baseline without defining recovery.** It installs the release and then performs another crop-replace write. That is acceptable on a test phone, but the plan should specify preservation/restoration of the fixture state used for final screenshots and owner checks.
- **MEDIUM — D-11’s comparison is confounded by the proposed Orrery cache.** The 1024 path creates cached 512 derivative base64 strings, while the 512 path passes through without those cached strings. Whole-process PSS can therefore increase because of JS/cache behavior even if GPU texture size stays flat. The report must separate GPU-related metrics from total process memory and clear/warm caches consistently.
- **MEDIUM — “No higher beyond sample noise” has no defined threshold.** Three samples do not establish a noise band by themselves. Without a predeclared tolerance or repeated alternating runs, the pass/fail conclusion can be subjective.
- **MEDIUM — The automatic-backup test is underspecified.** It does not state how the automatic backup is triggered deterministically or how the resulting file is identified separately from manual exports.
- **MEDIUM — Generated fixture realism is not equivalent to app encoding.** PIL-encoded WebP fixtures exercise restore and size pressure, but not the app’s ImageManipulator encoding behavior. The plan partially addresses this with three app-written masters, which should be clearly separated in the report.
- **MEDIUM — Task 3’s Pending confirmation recipe may not reliably create eligibility.** The current eligibility query requires a durable pending assist to age past `ELIGIBLE_AFTER_SECONDS` ([interaction-assist-read.ts:28](/home/bwales/projects/orbit-app/src/db/interaction-assist-read.ts:28)). Backing out of the dialer alone does not guarantee the banner is immediately eligible.
- **LOW — `$HOME` paths in verification commands conflict with the general command-safety preference.** They are non-destructive, but named task-specific variables would make the scripts more robust.
- **LOW — The device plan says “no source changes” on mismatches, then later permits owner-signed tunable changes.** This is logically distinguishable by task, but the reports should state the exact commit boundary.

## Suggestions

- Stop and ask the owner to split the agreed Plan 07. A natural split would be:
  1. fixtures + D-10/D-11/D-18/D-20 measurements;
  2. writer/surface/layout UAT + owner checkpoint;
  3. signed tuning + release build.
  
  This is required by the repository’s hard plan-sizing gate.
- Add an explicit import-retry scenario:
  - induce or seed a `photo_failed` import row;
  - repair the source condition;
  - invoke retry;
  - verify revision and surfaces without restart.
- Define memory methodology before execution:
  - cold start each corpus;
  - same camera/zoom and visible contact set;
  - wait for steady state;
  - clear app process between corpus runs;
  - alternate 512/1024 order if possible;
  - report medians and a predetermined tolerance.
- Add an automated debug hook or documented deterministic trigger for automatic backup rather than waiting on scheduler behavior.
- Separate evidence labels:
  - “app-encoded master”;
  - “PIL fixture restored into app”;
  - “runtime Orrery derivative.”
- Specify how Pending confirmation eligibility will be awaited or seeded without changing the clock.
- Preserve a final known backup before release smoke testing and restore it afterward if owner checks depend on fixture state.

## Risk Assessment

**HIGH.** The verification scope is correct, but the plan is too large and misses a required writer path. Execution without replanning is likely to exhaust context or produce incomplete evidence.

# Final recommendation

**Verdict: REVISE BEFORE EXECUTION.**

Required changes:

1. Fix Plan 04’s `SkImage` ownership/disposal contract and replace or tightly constrain the 128-entry encoded cache.
2. Correct Plan 03 so notifications correspond to actual canonical-byte changes.
3. Add import-retry device verification to Plan 07.
4. Invoke the owner’s hard gate to split the already-agreed Plan 07, because its 180k estimate and built-in multi-executor resume points demonstrate that it exceeds one executor’s budget.
5. Tighten Plan 06’s equal-row-height proof with real layout/device evidence.
6. Make Plan 05’s hook ordering and accessibility focus restoration explicit.

With those changes, the phase architecture is strong and should achieve D-01 through D-22 without reversing ADR-021/D-21 or widening Orbit’s privacy boundary.

# Cross-AI Plan Review: Phase 38.6 (Photo Handling)

I checked the plans against the repo where it mattered: `GridCard.tsx`, `GlassSurface.tsx`, the Skia body files, and which files import both `expo-image` and `resolvePhotoUri`. I did not re-read every file the plans cite.

## Overall summary

The spike-first ordering is right, since the `?v=` approach rests on Glide behaviour nobody has confirmed. The owner-stop conditions are explicit. Authorization state (`generations`) is kept apart from display state (the revision), which avoids a real trap. The wave ordering and file-overlap handling look sound.

The main gaps are:
- **Plan 06:** a layout assumption that doesn't match `GridCard.tsx`.
- **Plan 04:** unbounded concurrency in the orrery downsample.
- **Plan 05:** a touch-blocking scrim.
- **Plan 07:** the D-20 backup-cap risk reaches the owner's real data before the owner has decided.

**Suggestion:** In the spike, also confirm a cold start with the bare URI (no revision) shows the correct photo. That is the "restart" claim. Also record the Glide disk-cache state, or run `Image.clearDiskCache()` once before the test so leftovers from the old `memory-disk` policy can't mask a failure.

## 38.6-04: 1024 WebP master, orrery and widget

**Strengths**
- One shared `encodeMaster` replaces three duplicated 512-JPEG encoders.
- `MASTER_QUALITY < 1` is pinned by a test. This is a non-obvious trap: quality 1.0 gives lossless WebP on Android.
- It fixes a latent bug in the old import path, which upscaled and distorted non-square thumbnails.
- The orrery gate caches encoded bytes (not `SkImage`s), which avoids pinning GPU textures.
- The RIFF/WEBP-under-`.jpg` restore round-trip test proves D-19/D-12 without a format bump.

**Concerns**
- **MEDIUM:** `useOrreryPhoto` runs an async manipulator downsample per body. With ~50 planets on 1024 masters, first mount launches ~50 concurrent full decodes plus resizes. The peak memory and CPU transient could exceed today's behaviour, which contradicts D-11 ("working memory must not grow"). The widget gets sequential encoding, but the orrery has no concurrency limit. Add a small queue (1–2 in flight), or a module-level semaphore.
- **MEDIUM:** The "no higher than today" claim is measured in plan 07 by whole-process `dumpsys meminfo`. The transient peak wouldn't show up in three samples taken after settling. Sample during initial mount too, or use `Debug.MemoryInfo` peak.
- **LOW:** `manipulate().saveAsync({format: WEBP})` isn't supported by expo-image-manipulator on iOS. Orbit is Android-first, but a guard or a comment would prevent a surprise if iOS is ever targeted.
- **LOW:** PNG sources with transparency now keep alpha as WebP, where JPEG flattened it. Avatars over a themed surface could show through. Edge case.
- **LOW:** D-22 leaves imported photos as ~96–144 px thumbnails, so the "bigger photos" goal doesn't apply to imported contacts. The plan records this as an owner FYI, which is right.

**Risk: MEDIUM.**

## 38.6-05: Profile lightbox, 224 hero, star in app bar

## Source-grounding pass (review agent)

Per CLAUDE.md "Review the code, not the diff", I read the full files the plans cite, plus the files in the same subsystem that share data: `owned-master.ts` (all), `photo-cache-bust-store.ts`, `Avatar.tsx`, `photo-storage.ts` (composer, `deletePhoto`, `reconcilePhotoDir`), `restore-apply.ts:1880-1945`, every writer of photo bytes (`photo-pipeline.ts`, `import-photo.ts`, `import-photo-retry.ts`, `reconcile-photo.ts`, `merge-photo-rehome.ts`), `your-week-read.ts`, `interaction-assist-read.ts`, `CandidateCardGrid.tsx`, `PhotoChoice.tsx`, `ProfileHero.tsx`, `ContactProfileScreen.tsx` (app bar and styles), `contact-profile-logic.ts`, `GridCard.tsx`, `CardGrid.tsx`, `GlassSurface.tsx`, `ScopedPalette.tsx`, `backup-schema.ts` (`validBase64`), `share-export.ts`, `encryption.ts`, and the native and library sources (`SourceMap.kt`, `ExpoImageViewWrapper.kt`, `ImageManipulatorArguments.kt`, `JsiSkImageFactory.h`, Skia `Data.ts`, `FlatList.js`).

### Findings of the grounding pass

- **Confirmed (H1): concurrency.** Skia `useImage` today (`@shopify/react-native-skia/src/skia/core/Data.ts` `useLoading`) never calls `dispose()`; it relies on GC plus the memory-pressure host object (`JsiSkImageFactory.h:34-41`). So the missing dispose in Plan 04 is parity with today, not a regression. The **new** costs are two:
  - Up to N concurrent manipulator decodes of 1024² masters when the Orrery first mounts. At about 4 MB of RGBA each, 50 planets is a transient spike of about 200 MB.
  - The process-lifetime base64 cache.
- **Confirmed (L2).** The codebase routinely uses dynamic destructured imports of `photo-storage` / `owned-master`: `owned-master.ts:350`, `import-photo.ts:56-58,66`, `reconcile-photo.ts:80-83`. A static-import regex would miss a future dynamic writer.
- **Confirmed (L1).** `deletePhoto` swallows errors (`photo-storage.ts:383-393`). A notify placed before the `exists` recheck at `owned-master.ts:161-165` fires even when the file is still there.
- **New (L3).** Plan 06 has two arithmetic errors:
  - The interface says GridCard's `AVATAR_SIZE` is 72 and `RING_BOX` is 78. They are actually 48 and 56 (`GridCard.tsx:72,78`; `SPACING["2xl"]` = 48 at `spacing.ts:18`).
  - The worked example claims `gridCardWidth(393, 3) ≈ 114.9` with avatar 88 and ringBox 96. For integer 393 the formula gives exactly 115, so avatar 89, ringBox 97 and avatarTop 18. The quoted numbers only hold at ≈392.7 dp.
- **New (L5).** At 360 dp the star's 44×44 hit box (x 248..292, y 6..50) sits about 106.5 px from the photo centre (180, 132). The radius is 112, so the hit box overlaps the circle, and a tap on that sliver of the photo toggles Favourite.
- **New (L6).** Today's `cachePolicy="memory-disk"` has left Glide disk-cache entries for local avatars, including photos of since-deleted contacts. With `"memory"`, which disables the disk cache per `ExpoImageViewWrapper.kt:444`, those entries are never read and never overwritten, so they persist in the app cache. Claude also suggested clearing the disk cache before the spike.
- **Confirmed (M3).** In React Native, touches that hit the app bar's scrim backing `View` (a child of a `box-none` parent) do not reach the sibling `ScrollView` underneath. The backing needs `pointerEvents="none"`.
- **Refuted (claude HIGH, Plan 06 Pressable).** See Divergent Views.
- **Verified sound.** No magic-byte validation blocks WebP in backups: `backup-schema.ts:382-393` checks base64 shape only. `share-export.ts:69-74` reads bytes without regard to format. Every production byte writer already goes through `persistOwnedMaster(Locked)`: `photo-pipeline.ts:113-116`, `import-photo.ts:62-69`, `reconcile-photo.ts:79-85`, `import-photo-retry.ts:122`. `restore-apply.ts:1911` is the single raw delete, exactly as Plan 03 says.
