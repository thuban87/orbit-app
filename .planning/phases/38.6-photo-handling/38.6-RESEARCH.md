# Phase 38.6: Photo Handling — Sync, Sizes & Lightbox - Research

**Researched:** 2026-09-29
**Domain:** Android image caching (expo-image/Glide), on-device photo master pipeline (expo-image-manipulator, expo-file-system), Skia texture memory, RN layout (FlatList grid, Profile hero), gesture lightbox (RNGH 2.32 + Reanimated 4.5.1)
**Confidence:** HIGH on code facts (everything read on disk this session); MEDIUM on the D-01 display-token mechanism until the Wave-0 device spike passes; LOW on WebP quality/size numbers (need device measurement)

## Summary

The stale-photo bug is real and exactly as the dossier says: `SourceMap.kt:133-135` returns `RawModelProvider(parsedUri!!.toString())` for any `file://` source, before `cacheKey` is ever read (`cacheKey` is only used at lines 137-140 for network URLs). Because every contact's master lives at a fixed identity-derived path, Glide's memory cache (and, with `cachePolicy="memory-disk"`, its disk RESOURCE cache) serves the old decode. **But the dossier's preferred fix — a new filename per write — collides with a recorded owner decision:** 38.2 D-09 (owner, 2026-09-23) says *"RG-010 keeps ADR-021 identity-derived photo filenames. No filename-policy change (random/UID naming stays rejected per ADR-021) … Any plan that needs a different naming scheme stops and asks."* ADR-021 lists *"Random per-file names — rejected"* and ADR-158 lists *"Change to random photo filenames — rejected by D-09"*. The 38.6 dossier calls the filename scheme "left to phase planning by 07-photos.md". That is out of date. ADR-021 decided it, and 38.2 D-09 reaffirmed it behind an owner gate.

**This research recommends a fix that changes no filenames**, so no owner stop is needed. The URI handed to expo-image gets an in-process revision query (`file://…/avatars/contact-12.jpg?v=3`), and local avatars switch from `cachePolicy="memory-disk"` to `"memory"`. Glide keys its memory cache on the model string, so a new `?v=` means a fresh decode. Android's `ContentResolver` opens `file://` URIs by `getPath()`, which drops the query. Memory-only caching makes a restart start clean. The revision is bumped at every point where canonical bytes change, all of which already sit inside the 38.2 ownership primitives in `owned-master.ts`. It is published through the existing reactive `photo-cache-bust-store`, so every mounted Avatar on every screen reloads without a restart. The query trick depends on Glide/ContentResolver internals, so it must pass a **device spike first**. The fallback that still keeps filenames is `cachePolicy="none"` plus the existing cache-key bump (HIGH confidence from code, but it costs scroll performance). Only if both fail does the phase need versioned filenames, and that is an owner stop against 38.2 D-09.

D-10 (1024 WebP master) is supported by the installed `expo-image-manipulator@57.0.10` (`SaveFormat.WEBP` → `Bitmap.CompressFormat.WEBP`). Its default `compress` is `1.0`, which Android treats as **lossless** WebP (large files), so the quality must be set below 1. The recommended storage choice is **WebP bytes under the unchanged `.jpg` identity-derived names**. Every decoder in the app sniffs content (Glide, BitmapFactory, Skia's `SkWebpCodec`, which is verified present in `libskia.a`, and the manipulator). The whole RG-010 machinery (restore canonical paths, restore-pending names, staging-session matcher, merge destination checks, purge/definition-delete derivation) keeps working unchanged, and restore places WebP bytes correctly with **no backup-format bump** (`BACKUP_FORMAT_VERSION = 7` stays). Real `.webp` extensions would change the D-09 naming scheme and touch every RG-010 path, so that option belongs to the owner.

Two owner-bucket **risk** items are not blockers for planning, but the orchestrator must raise them before execution. (1) The approved encrypted-backup profile caps ciphertext at `8_388_608` bytes (8 MiB). D-10 roughly triples each photo's base64 payload, so encrypted manual and automatic backups start failing at roughly 40–85 photo contacts instead of roughly 100–200. (2) Imported phone photos come from the contact's `DATA15` thumbnail (about 96–144 px) first. Under D-10's never-upscale rule they will be stored at thumbnail size, so D-13 does not make imported photos sharper.

**Primary recommendation:** Keep ADR-021 filenames. Fix D-01 with a revision query on the display URI plus memory-only caching, driven from the ownership layer, and device-spike it first. Encode every new master as ≤1024 square lossy WebP (quality below 1.0) under the existing `.jpg` names. Downsample only the Skia orrery textures to ≤512. Build the lightbox on RNGH Gesture + Reanimated (no new native module). Handle the grid's D-09 with row-stretch plus bottom-pinned secondary lines (no text measurement).

### Pattern 1: Display revision token (D-01/D-19)

**What:** Canonical filenames never change. The display URI gets `?v=<rev>`, where `rev` is the in-process revision of that canonical path. Local avatars use `cachePolicy="memory"`. Every canonical byte change calls `notifyPhotoBytesChanged(P)` → `bumpPhotoCacheBust(P)`.

**Why it works:**
- expo-image passes the whole string as the Glide model for `file://`: `if (isLocalFileUri()) { return RawModelProvider(parsedUri!!.toString()) }` [VERIFIED: SourceMap.kt:133-135]; `data class RawModelProvider(private val data: String) … getGlideModel() = data` [VERIFIED: GlideModelProvider.kt:27-31]. A new query means a new model, a new memory-cache key, and a fresh decode.
- Glide opens `file` URIs through `ContentResolver`, which reads `uri.getPath()` (query dropped) [ASSUMED: Glide StringLoader→UriLoader/LocalUriFetcher and Android ContentResolver.openInputStream behaviour, from training knowledge; **must be device-spiked**]. expo-image registers no custom String/file loader (only SVG/base64/blurhash/thumbhash/decoded modules) [VERIFIED: grep of `registerComponents` in expo-image android].
- `cachePolicy` mapping: `.customize(\`when\` = cachePolicy != CachePolicy.MEMORY_AND_DISK && cachePolicy != CachePolicy.MEMORY) { skipMemoryCache(true) }` and `.customize(\`when\` = cachePolicy == CachePolicy.NONE || cachePolicy == CachePolicy.MEMORY) { diskCacheStrategy(DiskCacheStrategy.NONE) }` [VERIFIED: ExpoImageViewWrapper.kt:440-445]. `"memory"` therefore keeps the memory cache and disables the disk cache. With no disk cache, a process restart cannot resurrect a stale decode. Today's `"memory-disk"` uses Glide's default disk strategy, keyed on the model string with no file signature, so the dossier's "stale after restart (LIKELY)" is supported by code reasoning [ASSUMED Glide internals].
- In-process monotonic revision per path means a display URL string is never reused for different bytes within a process, including ID reuse after purge, because the purge delete also notifies.

### Anti-Patterns to Avoid
- **Versioned/random filenames** without owner sign-off (F-1).
- **Repurposing `canonicalGeneration` as the display token.** It breaks retry/merge authorization.
- **Putting `?v=` on anything but the expo-image source** (File, Skia, manipulator, backup).
- **`compress: 1` or omitted `compress` with `SaveFormat.WEBP`** produces a lossless WebP (`ManipulateOptions.compress` defaults to `1.0`, ImageManipulatorArguments.kt:48). Android: "As of Q, a value of 100 results in a file in the lossless WEBP format" [CITED: developer.android.com/reference/android/graphics/Bitmap.CompressFormat].
- **Caching SkImages** in a module map. It pins textures across orrery unmounts, which raises memory above today. Cache encoded small bytes instead.
- **Same-file worklet forward references** (Hermes crash that vitest cannot see).
- **onTextLayout-driven row heights** (two-pass flicker).
- **Hardcoded colours** in the lightbox (`'black'`/`'transparent'` literals fail `check:colors`).

## Common Pitfalls

### Pitfall 1: The `?v=` query is not honoured on some load path
**What goes wrong:** The avatar shows initials (load error) or still shows the stale image.
**Why:** It relies on Glide's String→Uri→ContentResolver path ignoring the query [ASSUMED].
**How to avoid:** Wave-0 device spike on the debug dev client (JS-only change): replace a photo via crop → Profile, List, Grid and the Digest update without a restart; kill and relaunch → still the new photo; `adb logcat` shows no `FileNotFoundException`.
**Fallback:** `cachePolicy="none"` + keep the cacheKey bump (reload forced by `SourceMap` data-class equality, ExpoImageViewWrapper.kt:529). Only then consider F-1.

### Pitfall 2: Silent writers that skip the notification
**What goes wrong:** Restore, merge, import or purge changes bytes, but the screens still show the old image until a restart.
**How to avoid:** Notify inside `owned-master.ts` (Pattern 1 table), not at call sites. Add a contract scan that forbids new raw `persistMaster`/`deletePhoto` callers. Remove the now-redundant call-site bumps in CropPhotoScreen (harmless but noisy).

### Pitfall 3: Breaking RG-010 authorization by touching `generations`
Covered in Pattern 1. Tests: `import-photo-retry` succeeds when settle retires stale journal rows; `merge-photo-rehome` transfer identity checks unchanged.

### Pitfall 4: Lossless WebP by default
`compress` omitted ⇒ `1.0` ⇒ lossless ⇒ several-hundred-KB masters. Pin `MASTER_QUALITY < 1` with a unit test.

### Pitfall 5: Orphaned test consumers of changed contracts (memory: recurred 4× in P35)
Known consumers to update in the same plan that changes the contract:
- `src/services/import/import-photo.test.ts:74` ("persists a stable 512px master…"; mocks `SaveFormat: { JPEG: "jpeg" }` at :6).
- `src/db/your-week-read.test.ts:246-266`: `LEGACY_DAY_SQL` parity query compares row shapes with the new reader, so add the photo column there too.
- `src/db/interaction-assist-read.test.ts` (row fields).
- `src/components/grid-card-render.test.tsx` and `src/components/digest/DigestDayDetail.test.tsx` (shallow render assertions).
- Any `Avatar` `cacheBust` prop removal hits ~10 call sites; run `npx tsc --noEmit`, because vitest does not type-check.

### Pitfall 6: Profile photo cannot rise into the app bar
The ScrollView clips on Android, so a negative margin will not work. The app bar must overlay (Pattern 5). Keep today's safe-area/top inset behaviour exactly.

### Pitfall 7: Grid corner glyphs overlapping the bigger photo
Covered by the geometry solve in Pattern 6. Assert it in tests; confirm with a device screenshot at 2/3 columns and font scale 1.4+.

### Pitfall 8: WebP decode of untrusted bytes on an unpatched OS
The Pixel 3a reports security patch `2022-05-05` (Android 12) [VERIFIED via adb], which predates the libwebp CVE-2023-4863 fix. This attack surface **already exists** (restore and URL download already accept WebP bytes). This phase only makes Orbit *produce* WebP, so it adds no untrusted input path. Note it; no action.

### Pitfall 9: Encrypted backup cap (F-3)
A device pass with about 50 WebP-1024 photo contacts must include an **encrypted** export and an automatic backup, and must record the plaintext/ciphertext sizes for the owner.

// src/components/photo-lightbox-logic.ts — tunables at top (CLAUDE.md)
export const LIGHTBOX_MAX_ZOOM = 4;
export const LIGHTBOX_DOUBLE_TAP_SCALE = 2.5;
export const LIGHTBOX_DISMISS_DISTANCE = 120; // dp
export const LIGHTBOX_DISMISS_VELOCITY = 1000; // dp/s

export function clampScale(s: number): number {
  "worklet";
  return Math.min(LIGHTBOX_MAX_ZOOM, Math.max(1, s));
}
export function maxTranslate(side: number, scale: number, viewport: number): number {
  "worklet";
  return Math.max(0, (side * scale - viewport) / 2);
}
export function clampTranslate(t: number, side: number, scale: number, viewport: number): number {
  "worklet";
  const m = maxTranslate(side, scale, viewport); // callee defined ABOVE
  return Math.max(-m, Math.min(m, t));
}
/** Keep the focal point fixed while scaling from `prev` to `next` (offsets from viewport centre). */
export function focalTranslate(t: number, focalFromCentre: number, prev: number, next: number): number {
  "worklet";
  return focalFromCentre - (focalFromCentre - t) * (next / prev);
}
export function shouldDismiss(scale: number, ty: number, vy: number): boolean {
  "worklet";
  return scale <= 1.01 && (ty > LIGHTBOX_DISMISS_DISTANCE || vy > LIGHTBOX_DISMISS_VELOCITY);
}

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Path traversal via stored photo value | Tampering | Existing `SAFE_RELATIVE` allowlist at DAO + FS boundary; the display composer calls the guarded composer first |
