# Phase 38.5 Plan 06: Per-combination art treatment machinery Summary

**What this adds:** a pure per-combination table keyed by package × mode × rendered background × v2 component. It drives five things: the Contacts List rows, the Contacts Card-view cards, the "N contacts" label, the Contacts header and the Digest header. The components opt in through literal props. The production table reproduces today's treatment in all 16 combinations. A DEV-only override file, which is absent from release bundles, lets the re-sign-off render the owner's v2 choices.

## Performance

- **Duration:** about 25 minutes
- **Tasks:** 3 (1 tracer + 2 auto), all TDD with RED then GREEN commits
- **Files:** 25 changed (7 created, 18 modified)

## Accomplishments

- **Table (`art-treatments.ts`).**
  - `ART_COMPONENTS` is the v2 JSON's 11 field names. The test reads the JSON.
  - There are 16 combination keys (`galaxy-light-quiet` … `standard-dark-none`).
  - `ART_TREATMENTS` is built from `currentArtCell`, which encodes today's rule:
    - List rows are full.
    - Cards, the count label and both headers are see-through when `cardMatchesMode`, otherwise full.
    - Top buttons and search are full.
    - Digest content is none.
    - The foreground is `mode`.
  - The module contains no opacity numbers (the test greps it for `0.x`).
- **Tokens (`surface.ts`).**
  - `ArtOpacityGroup` has three groups: `listEntry`, `cardEntry` and `artChrome`.
  - `ART_SEE_THROUGH_OPACITY` holds only today's two shipped see-through values, by reference. Every other cell is `null` with an "owner-unsigned (D-06)" comment.
  - `artBackingOpacity` returns:
    - for full: 1 for List rows, and the densest opaque band for cards and chrome;
    - for see-through: the signed value, or the full value when it is null;
    - for none: `null`.
- **Identity proof.** For every combination:
  - count label, Contacts header and Digest header = `chromeScrimOpacity(pkg, mode)`;
  - cards = `cardTintOpacity(pkg, mode, "dense")`;
  - List rows are full at 1;
  - Digest content is none.

  No see-through cell in the production table has an unsigned opacity.
- **Opt-ins (D-28).**
  - `ChromeScrim artComponent="contactsCountLabel"` is on the HomeScreen count label.
  - `ShellAppBar artComponent` is on the Contacts header (`contactsHeader`) and the Digest header (`digestHeader`). With backing `none` there is no scrim, the title and Back read the root palette, and trailing and overflow are unscoped. The ⋯ local-backing path is off in production.
  - `GlassSurface treatment="contact-entry"` is on GridCard only.
  - `ListRow` is table-driven through `listRowBacking`. Every colour read (ring, name, meta, snippet, highlight) goes through a `ScopedPalette` render prop, and the whole row sits inside the scope only when the backing is see-through. The opaque category chip reads `useUnscopedTheme()` (C2-L4).
- **Blast-radius contract.**
  - `artComponent=` appears exactly 3 times.
  - `treatment="contact-entry"` appears exactly once (GridCard).
  - `useArtTreatment(` is called only by ChromeScrim, ShellAppBar, GlassSurface, ListRow and the control row's active state.
  - No Orrery file and no other control-surface file references the table.
  - The HomeScreen empty panel and the Digest message and notice scrims have no opt-in.
- **Glass-scope analyzer.**
  - `scopeRegions()` gains a `GlassForegroundScope` children branch.
  - Regions are de-duplicated by range.
  - `SCOPE_REGION_SCOPES` is exported, and a new fixture checks that each handled element yields a region.
  - `SCOPE_ELEMENTS` is unchanged (38.5-01's backed set).
  - `EXPECTED_SCOPE_SLOTS` is unchanged, and `GLASS_SCOPE_READ_ALLOWLIST` is still empty.
- **DEV override.**
  - `art-treatment-dev-overrides.json` is committed as `{ "enabled": false }`. Its schema is documented in `use-art-treatment.ts`.
  - The pure `applyArtDevOverrides` validates every field.
  - `ArtSheetComboSync` applies the combo through the store's in-memory setters and never writes the database. RootNavigator mounts it behind `__DEV__ ? require(...) : null`.
  - A release-guard source scan checks the rule, with pass and fail fixtures.
  - A real production `expo export` sourcemap contains neither DEV module. ThemePreviewScreen, the precedent, is also absent.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The hook reads the stored background from the theme context, not a store subscription**
- **Found during:** Task 2 (full suite).
- **Issue:** The plan's `useArtTreatment` read the theme store directly. It runs in every GlassSurface, ChromeScrim and ShellAppBar (about 90 instances). A zustand hook there broke render harnesses that call components as plain functions (the Orrery controls test failed with "Cannot read properties of null (reading 'useCallback')"). It also added a store subscription per instance.
- **Fix:**
  - `ThemeProvider` puts the active package's stored background id on `ResolvedTheme` as an optional `backgroundId`. It is the same store value, and the provider already depends on it.
  - The hook calls only `useTheme()`, unconditionally.
  - The table key still comes from `resolveBackground`, so retired or unknown ids use the default slot's row.
- **Files:** `src/theme/theme-types.ts`, `src/theme/theme-provider.tsx`, `src/theme/use-art-treatment.ts`.
- **Commit:** `b46e33d`.

**2. [Rule 1 - Analyzer false positive] Scope primitives excluded from wrapper discovery**
- **Found during:** Task 2.
- **Issue:** With the new `GlassForegroundScope` branch, discovery would re-derive `GlassSurface.children` from GlassSurface's own body without its orrery-overlay exception. It would also re-derive `ChromeScrim.children`.
- **Fix:** `HARD_CODED_SCOPE_OWNERS` (GlassSurface, ChromeScrim, ShellAppBar, GlassForegroundScope) are skipped in discovery, and regions are de-duplicated by range. A fixture proves that an orrery overlay with an outer `danger` read still passes.
- **Commit:** `b46e33d`.

**3. [Rule 3 - Blocking] Test harnesses for the new opt-ins**
- **Issue:** Four existing test files depended on the old component shape:
  - `grid-card-render.test.tsx` mocks `@/theme` with only `useTheme`, but ListRow now also uses `useUnscopedTheme` and `GlassForegroundScope`, plus the hook.
  - `DigestScreen.test.tsx` checks the exact header props.
  - `tab-root-chrome-contract.test.ts` matches the exact Digest header source.
  - `orrery-controls-render.test.tsx` renders the real GlassSurface, whose hook module holds the module-level `__DEV__` guard, and `__DEV__` is undefined under node.
- **Fix:**
  - The mocks were extended.
  - The Digest expectations now include `artComponent: "digestHeader"`.
  - The Orrery harness stubs `useArtTreatment` to return null. That is the real result for a component that never opts in (D-12).
- **Commits:** `b46e33d`, `3bd407d`.

**4. [Plan text] Fixture token.** The acceptance criterion names an outer `colors.textPrimary` read inside a direct `GlassForegroundScope`. `textPrimary` is not a glass-overridden token, so by design the analyzer never reports it; an existing "passes" fixture pins that. The new fixture uses `colors.textSecondary`, which is overridden, and a second fixture covers a ring hand-off (`ring(colors)`).

**5. [Orchestrator addition] Active control-row triggers**
- The plan's must-have said the Population/Filters/Sort buttons are never table-driven. The orchestrator addition asked for the ACTIVE state to be covered.
- **How it is expressed without a look decision:**
  - `ArtCell.activeTriggerBacking`, which is `full` | `none` and set only on `contactsTopButtons`;
  - production `none`, which is today's border-only look;
  - the pure `controlTriggerBacking(active, …)`, which always returns `full` for an inactive trigger (D-04).
- `DashboardControlRow` reads only that field. The menus are untouched (D-12).
- The scope contract pins the single call and bans the table from every other control-surface file and every Orrery file.

**6. [Placement] Helper locations.** `listRowBacking` lives in `art-treatments.ts`, not `ListRow.tsx`, so it is node-testable. The added pure helpers are `artScrimBacking`, `controlTriggerBacking`, `resolveArtTreatment` and `artDevCombo`.

**Total deviations:** 3 auto-fixed (2 blocking, 1 analyzer false positive), 1 plan-text correction, 1 orchestrator-directed scope change and 1 placement choice. **Impact:** production output is unchanged. The identity tests and the full suite prove it.
