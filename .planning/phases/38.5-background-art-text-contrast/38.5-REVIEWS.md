## Codex Review

**Assessment: revise before execution. Overall risk: HIGH.**

The phase has a sound overall sequence: inventory → tooling → owner-approved art → wiring → scrim re-sign-off → implementation → device verification. Restore compatibility and shared-component scope are handled thoughtfully. However, several acceptance paths remain incomplete: an owner-approved broad art exception cannot pass the planned checker, inverse foregrounds would not reliably reach rendered text, and the inventory becomes inaccurate once scrims become conditional. These are fixable plan defects, but they affect the phase’s central contrast guarantee.

This is a source-grounded review of the core rendering, proof, validator, persistence, and decision paths—not an exhaustive verification of every referenced file. I did not run the application or full test suite. The working tree is clean.

**Strengths**

- **Retired-id compatibility addresses a real restore failure.** Restore passes settings into `updateAppSettingsCore` at `src/backup/restore-apply.ts:1779`; that function validates at `src/db/app-settings-dao.ts:1481`, and `assertBackgroundId` rejects unknown IDs at `src/db/app-settings-dao.ts:1185`. Plan 05 correctly preserves a closed accepted set containing retired IDs instead of relying solely on render-time fallback.
- **No migration is necessary for mode-aware assets.** Migration 015 stores nullable background IDs without an enumerated SQL constraint (`src/db/migrations/015-theme-settings.ts:45`). Plans 02/05 preserve that storage contract and change resolution.
- **The mode-keyed failure latch fixes a concrete edge case.** The existing key omits mode (`src/components/ui/background-host-model.ts:27`), while the failure state lives in `BackgroundHost` (`src/components/ui/BackgroundHost.tsx:107`). Plan 02 correctly resets the latch when the selected variant changes.
- **The proof/decoder synchronization is valuable.** The current decoder explicitly checks composite extrema because tinting can reorder pixel luminance (`scripts/measure-background-extrema.py:17`). Extending its regime table alongside the TypeScript proofs is the right architecture.
- **Opt-in treatments respect the recorded scope.** Existing `GlassSurface` separates ordinary cards from Orrery treatment (`src/components/ui/GlassSurface.tsx:94`). Plan 06 builds on that boundary rather than globally changing the protected opacity rules, consistent with dossier D-28 (`docs/dossier/milestone-2/phase-38.5-background-art-text-contrast-dossier.md:347`).

**Concerns and specific changes**

1. **HIGH — Plans 07/08: the inverse-foreground implementation can pass a palette proof while rendering different colours.**

   Plan 08 proposes wrapping content in `ArtForegroundScope` and adding that component to `SCOPE_ELEMENTS` (`38.5-08-PLAN.md:177`). That alone is insufficient:

   - GridCard resolves `colors` above its surface at `src/components/GridCard.tsx:142`.
   - Its name and highlighted snippet still use that outer `colors.textPrimary` at lines **328** and **365**.
   - The scope analyzer derives its watched keys exclusively from `resolveGlassForegroundPalette` (`src/theme/__contract__/glass-scope-reads.ts:105`). Its tests explicitly permit outer `textPrimary` reads (`src/theme/glass-scope-read-contract.test.ts`, “a non-overridden token” fixture).

   Consequently, adding the new scope name does not make the analyzer catch primary text bypassing an inverse palette. There is another boundary to preserve: ListRow contains an opaque category chip (`src/components/ListRow.tsx:231`), whose text must not blindly inherit a colour intended for the art while its fill remains unchanged.

   **Change:** specify scope-specific overridden-key sets, move every affected foreground read inside the appropriate scope, and test actual consumer resolution—including primary text, highlighted text, and opaque descendants. Include inverse **full-backed** cells in validation too, or prohibit that combination explicitly in the sheet.

2. **HIGH — Plans 03/04/05: the broad-feature approval branch has no executable checker path.**

   Plan 04 explicitly offers approval of a broad failing feature through a written slot/mode/colour exclusion (`38.5-04-PLAN.md:217`). But its finalization then requires both checker runs to pass using only the small-component allowance and Galaxy Dark danger flag (`38.5-04-PLAN.md:255`).

   Plan 03’s checker interface provides those same mechanisms (`38.5-03-PLAN.md:127`); it provides no broad, token-scoped exception input. Plan 05 adds the exception only to the TypeScript proof (`38.5-05-PLAN.md:241`).

   The existing checker combines per-token failure masks and returns failure when either bare or card checks fail (`.planning/phases/38.4-audit-remediation-ui-performance-release/38.4-art-brief/check_art.py`, `check()` and `main()`).

   **Change:** define one machine-readable, owner-approved exception contract consumed by both Python acceptance and TypeScript proofs. Otherwise, explicitly stop for replanning when such an approval occurs. Do not offer a supported shipping choice that the next task cannot encode.

3. **HIGH — Plans 06/07/09: “top controls stay full” is false for active controls.**

   Population, Filters, and Sort remove their background fill when active:

   - `src/components/control-surface/DashboardControlRow.tsx:317`
   - `src/components/control-surface/DashboardControlRow.tsx:352`
   - `src/components/control-surface/DashboardControlRow.tsx:389`

   Their active branches set only `borderColor`; the common trigger style supplies no background. This conflicts with Plan 09’s “stay full” acceptance (`38.5-09-PLAN.md:24`) and Plan 07’s fixed-full presentation. Plan 06 simultaneously prohibits changing these controls.

   **Change:** surface this existing-code/decision mismatch before sign-off. Capture active and inactive states and record the owner’s resolution under D-28. Neither a table entry labelled `full` nor screenshots of inactive controls demonstrate full backing in all states.

4. **HIGH — Plans 01/06/09: the inventory classifier becomes invalid during this phase.**

   Plan 01 classifies all text beneath `GlassSurface`, `ChromeScrim`, or `ShellAppBar` as backed (`38.5-01-PLAN.md:111`). Plan 06 subsequently permits those very components to render without a backing. Plan 09 reruns the original analyzer without scheduling a treatment-aware update (`38.5-09-PLAN.md:169`).

   The current primitives do unconditionally draw backing layers—for example, `ShellAppBar` at `src/components/ShellAppBar.tsx:108`—so the initial rule is understandable. It will no longer describe the completed implementation.

   **Change:** make backing classification aware of treatment branches and combination-dependent states. Preserve a clearly defined initial D-24 counting population, and distinguish it from the final inventory. Add fixtures for `none`, conditional fills, and components backed in some combinations but bare in others.

5. **MEDIUM — Plans 03/05: the Profile proof lacks its decoder regime.**

   Plan 05 adds a contrast proof using `profileBackgroundScrim` (`38.5-05-PLAN.md:241`), but Plan 03 adds only ordinary card, chrome, and veil regimes (`38.5-03-PLAN.md:158`). Plan 08 adds contact-entry/chrome regimes, still not Profile.

   Profile uses a different tint and alpha from the ordinary veil (`src/components/ui/BackgroundHost.tsx:131`; `src/theme/theme-presets.ts:37`). The extrema script warns that a different tint can change the composite extrema (`scripts/measure-background-extrema.py:17`).

   **Change:** add the Profile tint/alpha tuples to the decoder and sync guard when adding the Profile proof. Existing representative bounds cannot simply be assumed to enclose an unmeasured regime.

6. **MEDIUM — Plans 03/05/08: “the same feature allowance” is not fully specified across validators.**

   The proposed checker measures connected components in the **union of foreground contrast failures** (`38.5-03-PLAN.md:127`). The extrema validator instead measures pixels outside declared bounds **for each regime** (`38.5-03-PLAN.md:165`).

   These masks need not coincide. Separately acceptable components or percentages in individual regimes can exceed the signed allowance when combined. The existing measure loop validates regimes independently (`scripts/measure-background-extrema.py:229`).

   **Change:** define whether the allowance applies separately or to a union across tokens/treatments/densities, and record that meaning at sign-off. Add cross-validator fixtures with overlapping and disjoint failure regions. Also assert that manifest allowance values equal the signed record.

7. **MEDIUM — Plan 07: the capture/export contract does not fully support informed sign-off.**

   - Ladder capture explicitly requests List and Card views (`38.5-07-PLAN.md:166`), although `artChrome` also controls the Digest header.
   - The inverse mock changes name/meta text only (`38.5-07-PLAN.md:179`), while Plan 08 changes danger, status, rogue, placeholder, and accent roles too (`38.5-08-PLAN.md:177`).
   - The answer validator checks keys and values but does not require every combination’s `reviewed` flag to be true (`38.5-07-PLAN.md:244`).

   **Change:** capture Digest for chrome ladders, preview all roles affected by an inverse choice, and reject unreviewed combinations. Any typed opacity should be re-rendered and contrast-checked before it becomes the signed production value.

8. **MEDIUM — Plans 01/04/06/07/08/09: executor sizing needs an explicit justification.**

   Estimates range up to 160,000 tokens, with low confidence—for example, Plan 07 at `38.5-07-PLAN.md:23`. That plan includes a candidate solver, device automation, page generator, owner checkpoint, and decision-record updates. Plan 01 includes a cross-component analyzer plus substantial manual verification.

   The task counts alone do not establish that these fit the repository’s approximately 50% context-budget target.

   **Change:** document the executor context assumption and checkpoint/resume boundaries. First reduce duplication or tooling ambition within the existing plans. Any split of these owner-visible plans requires the owner’s approval under the supplied sizing rule.

## 3. Concerns

**HIGH**

- **Plan 01, D-24 sample size.** The threshold flips if the true bare denominator drops below about 240, which is 54 false-bare rows out of 294, or 18%.
  - The plan hand-verifies only ≥30 of about 194 ESTIMATED rows. A 30-row sample bounds an 18% error rate only loosely, and about 5 of the 194 are already known to be unstable.
  - The analyzer must trace every render site across files, and a wrong "backed or bare" call changes the denominator.
  - Fix in Task 2: stratify the sample by route and file (not random), scale it to at least 60, or hand-verify every row that sits in a component with more than one render site. Report a confidence interval alongside the "flip denominator" in Task 3.
- **Plan 01, sizing.** Task 1 builds a full compiler-API classifier: backing-ancestor walk, cross-file render-site fixpoint, `AppText` role defaults, and `Button` roles, with tests. That is heavier than `glass-scope-reads.ts` (855 lines), which only does intra-file work plus wrapper discovery.
  - 140k tokens and `confidence: low` look optimistic for Task 1 alone.
  - Consider splitting the tracer from the full corpus run, or scoping the analyzer to reproduce the brief's CSV columns and letting hand verification carry the rest.
- **Plan 08, the D-09/D-10 reinterpretation.** The owner's rulings say the text on see-through Galaxy Light entries "flips to light" and "should remain white" where the art is dark.
  - The plans decide (research A7, Plan 05 and Plan 08) that on the new mode-matched art the art-suited colour is the mode default. So `inverse` is "conditional".

    - Make `art-foregrounds.ts` and `ArtForegroundScope` an unconditional deliverable, or state a budget for the case where the owner says "flip".
    - Make 08 halt if the owner answers "flip" but the art is mode-matched, because then bare text on all 294 sites would not follow the flip (D-28).

  - The v2 sheet already exposes controls for `digestSectionHeadings`, `digestUpNextItems`, `digestHorizonItems` and `digestYourWeek`, none of which has an opt-in path.
