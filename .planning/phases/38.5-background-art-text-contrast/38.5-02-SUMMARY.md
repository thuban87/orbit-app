# Phase 38.5 Plan 02: Slot x mode background variants Summary

**Every background slot is now a light/dark variant pair. The resolver, the BackgroundHost fallback latch, the
picker preview and highlight, the extrema script and the card/chrome proofs all resolve by slot x mode. Both
variants still point at today's file and today's declared pixels, so nothing on screen changes (D-13).**

## Accomplishments

- **Manifest and resolver (`src/theme/backgrounds.ts`).**
  - New `BackgroundVariant` (`source`, `brightestPixel`, `darkestPixel`). `BackgroundAssetSlot` is now
    `{ package, variants: Record<ResolvedMode, BackgroundVariant> }`.
  - All 8 slots use the fixed nested layout the script parses (`grep -c "variants: {"` = 8).
  - `resolveBackground(pkg, slotId, mode)` and `resolveRenderableBackground(pkg, slotId, mode, renderFailed)` return
    that mode's variant. `ResolvedBackground`'s asset branch carries `mode`. The NULL, `none` and unknown-id rules
    (ADR-113) are unchanged, only now mode-aware.
  - The stored value is still the slot id. No migration, no new setting, no DAO or restore change (D-23).
- **Callers.**
  - `BackgroundHost` passes `useTheme().mode` to the resolver and to `backgroundHostSelection`, whose key is now
    `package:slot:mode:uri`. A failed variant no longer pins the solid fallback after a mode switch (Pitfall 4).
  - `ThemeProvider` passes `resolved`. The glass-scope `kind === "asset"` answer is mode-independent.
  - `BackgroundThumbnail` takes the screen's `mode`, so the picker previews the version the user will see.
- **Picker highlight (`selectedBackgroundTile`).** It returns `none` when the resolver renders solid, else the
  resolved slot id. An unknown stored id now highlights the default tile it falls back to (Pitfall 7). Each
  thumbnail's `key` includes the mode, so its local failure latch resets on a mode switch.
- **Extrema script.** The flat `SLOT_RE` parse is replaced by `parse_slot_source`, which yields one row per
  (slot, mode) and raises on a missing variant block or field; `parse_slots` turns that into exit 2. `run` filters
  regimes by package AND mode and prints `slot/mode` labels (16 rows). The self-test adds a two-variant fixture and a
  missing-variant rejection. Each distinct file is decoded once and reused across its variants.
- **Proof loop (`surface.test.ts`).** The card and chrome suites take `entry.variants[mode]` in its own mode. The
  helpers take a `BackgroundVariant`. Test names read `slot/mode`. Coverage is the same 96 cases, because today both
  variants carry the same file and pair.

## Decisions Made

- **Promote, not add alongside.** The single-asset fields moved into each variant. No parallel single-asset path
  remains, so the proof chain has one truth.
- **Per-variant regime filter.** A variant is checked only against its own package AND mode regimes. With today's
  data (identical variants) the union over both variants is exactly the old per-package check, so no coverage was
  lost.

## Out-of-scope observations (for the orchestrator, not decisions)

- **A cross-package stored id renders the other package's art.** `assertBackgroundId` accepts any id in
  `BACKGROUND_SLOT_IDS`, and `resolveBackground` does not check that a known slot belongs to the package. So a
  tampered or hand-edited `standard_background = "galaxy-aurora"` renders Galaxy art under Standard, and the picker
  highlights no tile (truthfully, since that slot is not offered). This predates the plan and the plan did not change
  it. Whether to tighten it (fall back to the package default for a foreign-package id) is a behaviour change to the
  ADR-113 fallback. It is a natural fit for 38.5-05, which already changes the lineup and adds the retired-id
  invariant. Recommendation: fold a "foreign-package id resolves to the package default" case into 38.5-05.
