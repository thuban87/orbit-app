# Phase 38.7: Code Review Report

**Reviewed:** 2026-10-04

## Summary

I read the production code in full: the Skia patch, the V2 canvas and
`draw-*` modules, the generation ledger, the photo, text and warm caches, the
sky and base bake owners, the spec and text publishers, the switch runtime and
lead-in, the camera and gesture worklets, OrreryScreen, the System Preview, and
the stores. I also wrote a TypeScript-AST scan
(`scratchpad/worklet-scan.cjs`) over every non-test file in scope plus
`src/logic/orrery-*`. It found no worklet that calls a same-file, hook-local
or imported non-worklet function. It found no module-level worklet that
captures a later-declared binding. Every worklet default parameter is a
literal or a parameter reference. There is no `crypto` use and no colour
literal outside `src/theme/**`.

The ledger contract holds under coalesced and unwritten generations, patch
rejection, re-pin before confirm, and teardown after hand-off. I traced each
of these. It has one hole: OrreryWorld can re-mount the shared photo-cache
owner and the ledger AFTER its own teardown (CR-01). That leaks pinned photos
permanently and degrades photos in later visits.

Separately, the canvas `busy` signal never clears after a tap or a pinch
(CR-02). After the most common interaction, this silently turns off the
D-65 FR-B 30 Hz vote and the D-49 still-base bake.

The native patch looks sound. Its API-level guards are correct. Every
callback runs on the main looper. The probe and latch are bounded by
4000 ms and 600 ms on the native side and by 3000 ms and 6000 ms on the JS
side. Bitmaps are recycled on every path. A detached view answers
"detached". Events emitted after unmount go to a listener that has already
been removed, so they are dropped.

## Critical Issues

### CR-01: A visibility report that lands after unmount re-mounts the photo-cache owner and a new ledger epoch, so photos stay pinned for the rest of the process

**Status: fixed in `7800fe20`.** OrreryWorld sets a `released` ref and an
`alive` SharedValue (via `runOnUI`) first in its teardown. `sendVisibility`,
`requestPhotos`, the photo `onReady` callback, the eligibility reaction and
its trailing UI timer all check them. `createOrrerySpecPublisher` is terminal
after `detach()`: every setter, `compose`, `publishLabels` and `resync` are
no-ops, and `ensureEpoch` returns -1 without beginning an epoch. The old
"detach, then the next publish starts a new epoch" test was replaced, because
no production caller re-used a detached publisher. New tests: the
orrery-render test fires a trailing visibility timer after the effect
cleanups and asserts no photo-cache mount or request (it fails without the
fix), and the scene-specs test feeds every setter after `detach()`.

**File:** `src/components/orrery/OrreryWorld.tsx:1111-1119`, `:1149-1181` (UI `setTimeout(run, wait)` at 1178), `:990-1006`, `:1063-1070`; `src/components/orrery/v2/scene-specs.ts:1365`, `:1475-1479`; `src/components/orrery/resources/orrery-photo-cache.ts:398-424`, `:688-712`, `:783-801`

**Issue:**
- **The trigger.** The eligibility reaction arms a UI-runtime `setTimeout(run, wait)`, up to `ORRERY_TEXT_ELIGIBILITY_INTERVAL_MS` = 250 ms. When a frame arrives within 250 ms of the last report, it does this on every frame of a pan, coast, focus fly or switch.
  - Nothing cancels that timer when OrreryWorld unmounts.
  - Blur, background and Profile all unmount the world (`visible && scene && …` in OrreryScreen.tsx:1584-1586).
  - When the timer fires, it calls `runOnJS(sendVisibility)`. A plain `runOnJS(sendVisibility)` already queued in the unmount frame has the same effect.
- **What `sendVisibility` does.** It is not guarded by `mounted`. It calls `requestPhotos()`, and `requestPhotos()` sees `photoEpoch.current === null` because the cleanup at 1068-1069 just cleared it. So it calls `orreryPhotoCache.mount(owner, onReady)` again under the same owner id and then `request(owner, …)`.
- **What happens in the cache.** `setDrawn` (photo-cache 416-421) re-pins every current image for that owner and deletes its retirement mark.
  - The later `retainOnBlur` → `handOffWarm(owner, oldEpoch)` then finds nothing to hand off.
  - The teardown's `confirmRetired(…, {dispose:true})` skips the images too, because they no longer carry the old epoch mark.
  - The images stay pinned by a zombie owner that nothing will ever release. `clearUnheld` on background, idle and memory never touches pinned entries.
- **The ledger.** The zombie `onReady` calls `specPublisher.setPhotos`. `compose()` then sees `epoch === null` after `detach()` and calls `ledger.beginEpoch()` (scene-specs.ts:1365), so a new epoch starts that is never torn down.
- **Failure scenario.** Pan the All Contacts Orrery, then tap another tab, or tap a body and then "Open Profile" during the fly, within 250 ms of the last frame change.
  - Up to `ORRERY_PHOTO_CACHE_MAX_IMAGES` (120) images / 96 MiB stay pinned until the process dies.
  - The zombie's wants keep competing in `pass()`. On equal priority its older `owner.serial` ranks first. So on later visits to other Systems, admission refuses photos and bodies fall back to swatches and initials.
  - The zombie also keeps re-decoding on every revision bump.
- **Contract breach.** This breaks the `<resource_lifetime_contract>` (no object may outlive its owner's teardown) and the D-58 warm-cache bounds.
- **Compare the Preview.** The System Preview's controller has the guard the world lacks (`released` in system-preview-resources.ts:161-175).

**Fix:** Close the epoch at teardown and refuse everything after it:
```ts
// OrreryWorld
const released = useRef(false);
const alive = useSharedValue(true);
// teardown effect, first lines:
released.current = true;
runOnUI(() => { "worklet"; alive.value = false; })();
// requestPhotos / sendVisibility:
const requestPhotos = useCallback(() => {
  if (released.current) return;
  ...
}, [...]);
// textReport `run` (UI): if (!alive.value) return;
```
Also make `createOrrerySpecPublisher` terminal after `detach()`: a `detached` flag that makes `compose`, `publishLabels` and `ensureEpoch` no-ops, so no late callback can begin a ledger epoch. Add a node test that runs `release()` + `detach()`, then `requestPhotos()` and `setPhotos()`, and asserts `orreryPhotoCache.stats().pinned === 0` after the hand-off.

### CR-02: `busy` stays true forever after a tap or a pinch, so the FR-B frame-rate vote is withdrawn and the base is never baked

**Status: fixed in `48caae92` (adapted).** The suggested tap `onFinalize`
→ `cancelInput` was not applied. The tap is finalized (cancelled) when the
pan or hold wins the race, while the owner is still `"pending"`. Cancelling
there would strand the pan's `moveInput` and the hold's `onStart` (both
require pending). Instead, each recognizer (tap, pan, pinch, rotation, tilt,
hold) sets a bit in `samples.tracking` on begin/start and clears it on
finalize. When the last bit clears, `input.pointers` returns to 0. The
owner and generation are left alone. A new gesture-logic test covers a tap,
a tap cancelled by a winning pan (the pan still moves), a pinch with a
rotation, a rotation alone, and the hold. It fails without the fix.

**File:** `src/components/orrery/OrreryWorld.tsx:538-545`; `src/components/orrery/use-orrery-camera.ts:315-336`, `:406-411`, `:441-444`, `:475-478`, `:544-547`; `src/logic/orrery-gesture-logic.ts:33-40`, `:75-78`; consumers `src/components/orrery/v2/OrreryV2Canvas.tsx:472-487`, `:775-780`

**Issue:**
- **What `busy` reads.** It includes `cameraInput.value.pointers > 0`. `pointers` returns to 0 only through `cancelInput`, and that runs only in these places:
  - Pan `onFinalize` when the owner is `"pan"`.
  - Hold paths when the owner is `"reorder"`.
  - The `enabled` effect.
- **After a tap.** Tap `onBegin` runs `beginInput(…, 1)`, which sets `{owner: "pending", pointers: 1}`. No tap `onEnd` or `onFinalize` resets it. Pan's `onFinalize` sees owner `"pending"`, not `"pan"`, and does nothing. So after a tap, `pointers` stays 1.
- **After a pinch or rotation.** `touch(2)` sets `{owner: "multi", pointers: 2}`, and none of the multi-touch `onFinalize` handlers reset it.
- **Scope.** From the first body tap, which is the core focus flow, until the user happens to make a one-finger pan, `busy` is true even at idle.
  - `ambientFrameRateVote(reduced, busy)` returns 0, so the 120 Hz panel is not voted down to 30 Hz (D-65 FR-B).
  - `nextBakeState` treats every tick as busy, so the ~1,000-ring base is never baked (D-49; the spike measured −28 % of a core at idle).
- **Measurement risk.** Plan 16's release idle and battery measurements become wrong whenever a scripted path taps first.

**Fix:** Make the pointer count follow real touches, or stop deriving `busy` from it:
```ts
// use-orrery-camera.ts — end of every recogniser that can own input
.onFinalize(() => {
  "worklet";
  const s = input.value;
  if (s.owner === "pending" || s.owner === "multi")
    input.value = cancelInput(s);          // pointers → 0
})
```
Add this to the tap, pinch, rotation and tilt recognisers. Alternatively, track pointers from `onTouchesUp` (`event.numberOfTouches` after the change) and set `pointers: 0` once every touch is up. Add a test that a tap, then a pinch, each leave `busy` false once the touches end.

## Warnings

### WR-01: The frame-clock ambient driver runs a per-vsync frame callback under reduced motion

**Status: fixed in `40511b24`.** The canvas passes `useReducedMotion()` (the
state twin) to `ambientNeeded`, so no driver is mounted under reduced motion.
Both drivers now write `AMBIENT_STILL` on unmount, so the value holds at -1
rather than at its last tick. A new render test checks the default
frame-clock host under reduced motion: `useClock` is never called and the
glow holds still.

**File:** `src/components/orrery/v2/OrreryV2Canvas.tsx:354-358`; `src/components/orrery/v2/ambient-clock.ts:81-96`, `:179-191`

**Issue:**
- `useOrreryAmbient(host, reducedMotion, ambientNeeded(false, AMBIENT_CONSUMERS))` passes a hard-coded `false` as `reduced`. So `needsAmbient` is always true and the driver is always mounted.
- The default driver is `"frame-clock"` (D-64). Skia's `useClock` is `useFrameCallback` writing `clock.value` on every vsync, so its quantise reaction runs every frame while the Orrery is visible, even under reduced motion. That holds even though `ambient` stays −1 and nothing re-records.
- `ambientNeeded`'s own doc says that under reduced motion "no driver needs to run at all". The interval driver does stop under reduced motion; the frame-clock driver does not.
- **Impact:** a needless UI-thread wake per vsync, and battery drain, for reduced-motion users on the default host.

**Fix:** Feed the JS twin of the reduced-motion signal into `ambientNeeded` so the driver element unmounts:
```ts
const reducedJs = useReducedMotion();
const { ambient, driver } = useOrreryAmbient(host, reducedMotion,
  ambientNeeded(reducedJs, AMBIENT_CONSUMERS));
```
The value then holds at `AMBIENT_STILL`.

### WR-02: The sky shader's time wraps every 1,000 s and the nebula visibly jumps

**Status: fixed in `c70e4f0c`.** `skyNebulaUniforms` no longer wraps time.
It passes the two domain-warp phases already wrapped mod 2π (`skyPhase`) in
`uMotion.y` and `uMotion.w`. `uMotion.w` was previously an unused 0. The
rates moved to `SKY_WARP_RATE_A/B`, with the values unchanged (0.21 and
0.17). The breath term wraps by its own 40 s period. `uMotion.y` was the only
shader input derived from that time. The sun pulse, twinkle, drift and orbit
pulses read the ambient milliseconds directly in JS doubles and never
wrapped. A new draw-sky test checks continuity at 1,000 s, 2,000 s, 2 h and
24 h, and that the phases equal rate × time. The real SkSL compile test still
passes.

**File:** `src/components/orrery/v2/draw-sky.ts:183-186`; `src/components/orrery/v2/shaders.ts:497-498`

**Issue:**
- `t = (ambientMs / 1000) % 1000` resets from ~999.97 s to 0 after 16 min 40 s of continuous display. Ambient is ms since the canvas mounted.
- The breath term is continuous across the wrap because `SKY_BREATH_S = 40` divides 1000.
- The shader's domain warp is not. It uses `sin(p.y*0.011 + t*0.21)` and `cos(p.x*0.013 - t*0.17)`. At the wrap these phases jump by 210 mod 2π ≈ 2.66 rad and 170 mod 2π ≈ 0.35 rad.
- Result: the whole nebula shifts abruptly by up to ~±9 dp (`SKY_BREATH_DP`) every 1,000 s of an open Orrery.

**Fix:** Pass the shader wrapped phases instead of a wrapped time. Compute `phaseA = ((ambientMs/1000) * 0.21) % (2π)` and `phaseB = ((ambientMs/1000) * 0.17) % (2π)` in `skyNebulaUniforms` from the unwrapped value, and use `sin(p.y*0.011 + uPhaseA)` / `cos(p.x*0.013 - uPhaseB)`. The same applies to any other periodic term that reads `t`.

## Info

### IN-01: The idle-release timer can be armed for a world that is already mounted again

**Status: fixed in `281fe8b1`.** The warm cache counts mounted worlds. Each
`resumeOnFocus` adds one and each world's `retainOnBlur` removes one. A
hand-off that runs while another world is mounted keeps the warm set (state
`resumed`) and arms no idle timer. Test added.

**File:** `src/components/orrery/OrreryWorld.tsx:660-668`, `:1071-1103`; `src/components/orrery/resources/orrery-warm-cache.ts:238-268`

**Issue:** The old world's `finish` runs after `setTimeout(0)` + one UI frame. If a new world mounts inside that window (any unmount→mount flip of the World predicate), the new world's `resumeOnFocus()` runs first. The old `retainOnBlur` then sets `state = "warm"` and arms the 5-minute idle release while the Orrery is on screen. Five minutes later `release("idle")` empties the warm caches, which costs only cache misses (no use-after-free, since unheld entries only).

**Fix:** Have `retainOnBlur` arm the idle timer only when no world is mounted, for example with a mount counter maintained by `resumeOnFocus` and a matching blur call.

### IN-02: The text service's `owners` map grows without bound

**Status: fixed in `ecdd14dc`.** `OwnerState` gains a `mounted` flag (set by
`mount`, cleared by `release`). A released owner with no pin and no
retirement mark left is deleted in `confirmReleased`, `handOffWarm` and
`confirmRetired`. `acquire` no longer recreates an unknown owner, whose
epoch could never match anyway. `stats().owners` reports the count. Test
added: 50 visits leave 0 owners, and a mounted owner is never pruned.

**File:** `src/components/orrery/resources/orrery-text-service.ts:285`, `:297-304`, `:481-494`

**Issue:** Every OrreryWorld mount (`orrery-world:N`) and every Preview mount (`system-preview:N`) adds an `owners` entry, and nothing deletes them. The photo cache does delete them (`confirmReleased` / `handOffWarm`). This is a small, slow leak per tab visit.

**Fix:** Delete the owner in `confirmReleased` / `handOffWarm` once its pins are empty and the epoch has ended.

### IN-03: The warm cache is released twice on every background, which double-counts the stats

**Status: fixed in `55446cda`.** The explicit
`orreryWarmCache.release("background")` was removed from OrreryScreen's
AppState listener; `attach` covers it. The cache still clears on every
non-active change, which is idempotent. It now counts `releases.background`
only on the edge from active, so iOS inactive → background is one release.
Test added.

**File:** `src/screens/OrreryScreen.tsx:683`, `:688`; `src/components/orrery/resources/orrery-warm-cache.ts:271-281`

**Issue:** `orreryWarmCache.attach(AppState)` already releases on a non-active `change`. The screen's own AppState listener calls `release("background")` again, so `stats().releases.background` counts 2 per background. Plan 16 evidence that reads this stat would be off.

**Fix:** Drop the explicit `orreryWarmCache.release("background")` from the screen listener and rely on `attach`.

### IN-04: A failed sky bake marks the new key live but keeps drawing the old key's image

**Status: skipped (not a defect).** The baked image is a neutral density
texture (H9). Its bake inputs are only `SKY_NEBULA_TEX`, `SKY_NEBULA_PERIOD`
and the package seed (OrreryWorld.tsx and SystemPreviewCanvas.tsx
`requestSky`). The mode and the size bucket are part of the cache key but
never of the pixels. So after a failed bake for a mode or size change, the
image still drawn is exactly the image the new key would have baked. After
a package change it is the other package's cloud layout, coloured with the
current theme's tokens at draw time. Either way the sky renders correctly
coloured. The image stays tracked by the ledger and is retired at teardown,
so nothing leaks. The suggested fix (publish `{ image: null }`) would
replace a correct nebula with the plain gradient. Not retrying a failed key
is the documented intent ("do not retry this key").

**File:** `src/components/orrery/v2/nebula-bake.ts:366-371`

**Issue:** When `bake()` returns null, `liveKey = input.key` is set but nothing is written. The sky keeps drawing the previous key's image, for example the other mode's or the old size bucket's nebula after a theme change. The `liveKey` guard then blocks any retry. This is reachable only when the runtime cannot bake.

**Fix:** On failure, write `{ image: null }` as a new sky generation, so the old image retires and the plain gradient shows.

### IN-05: After `SWITCH_LEAD_MAX_MS` (60 s) the lead's spin freezes while the warp, streaks and breath stay at full plateau

**Status: fixed in `bfb277cd`.** In the last `SWITCH_LEAD_REST_MS` (2 s)
before the ceiling, the lead's velocity eases to 0 as r², the accelerate
phase mirrored (`switchLeadMotion`). The rotation integral matches, so the
spin decelerates smoothly with no jump. Warp and trail scale with the
velocity, and the breath scales by the same ease. At the ceiling everything
is at rest. `busy` now uses `switchLeadMoving` (active and below the
ceiling), so a lead at rest no longer blocks the bake or the 30 Hz vote. A
hand-off at any moment still inherits exactly what is drawn. Test added.

**File:** `src/logic/orrery-switch-lead-logic.ts:144-177`; `src/components/orrery/use-orrery-switch-runtime.ts:491-498`

**Issue:** The lead clock stops at 60 s, but `sampleSwitchLead` still reports `velocity = 1`, full warp and full trail. A very slow load shows streaks and a star warp over a world that no longer turns, and `busy` stays true. This is an edge case, but a visual inconsistency.

**Fix:** Taper `velocity`, `warp`, `trail` and `breath` to 0 as `clockMs` approaches `SWITCH_LEAD_MAX_MS`, or cap the lead at the plateau and leave the clock running.
