# Phase 38.7 Plan 07: Contacts, sun, moons and labels as picture layers; shared photo cache; the generation ledger Summary

**The whole Orrery canvas is now seven fixed Skia pictures for any System size. Contacts, the sun and moons are drawn from immutable JS specs in projected-depth order around the sun; labels are a picture of backplates and Paragraphs. Photos come from one bounded, shared cache that publishes without a React render. Every Paragraph and SkImage is disposed only under the new per-layer generation ledger (H3). All legacy declarative Orrery components are gone.**

## Accomplishments

### Task 1 (tracer): contacts and the sun as pictures, the photo cache, the ledger
- **Generation ledger** (`resources/orrery-generation-ledger.ts`, pure JS). `beginEpoch`, `publish(generation, layerIds, objects)` (the full reference set of those layers), `ack(layerId, generation, mountEpoch)`, `retirable()` (drains each object once), `teardown(dispose, epoch)` (reverse creation order, ends the epoch), `admitResult` (a late result of a stale epoch is disposed at once), `isCurrent`, `holds`, `stats`. Several epochs can coexist (a remount before the old teardown); acks of a non-current epoch are discarded.
- **Photo cache** (`resources/orrery-photo-cache.ts`). See the frontmatter `provides`. Highlights:
  - one decode per key across bodies and owners through the unchanged `loadOrreryImage` (38.6 derivatives, 512 cap);
  - pinned (drawn by an owner's published generation), retired (awaiting the owner's ledger) and warm (evictable) images, all counted with in-flight decodes against both caps before any decode starts;
  - a refused photo starts no decode and its body draws the fallback;
  - replacements and the focused photo use the reserve; past it a fallback generation drops off-screen photos first, and the freed images go only after every body layer acked;
  - `subscribePhotoCacheBust` cancels a superseded in-flight decode, keeps the old image drawn until the new one lands (or publishes null on deletion) and retires the old one through the ledger.
- **Spec publisher** (`v2/scene-specs.ts`). It composes the static looks with initials and photos into one body spec array and writes it with a monotonically increasing shared generation. It tells the ledger which handles that generation references for `bodiesBehind`, `sun` and `bodiesFront`. An unchanged input writes nothing.
- **Canvas.** The `bodiesBehind`, `sun` and `bodiesFront` pictures share one depth order per frame (`orderBodies`). The sun pulse comes from the canvas clock as a primitive that is constant under reduced motion. Each layer acks separately (`useLayerAck` → `ackRecorded`). On unmount: pins retire and the epoch ends; after `setTimeout(0)`, a UI round trip and one frame, the ledger hands every object back in reverse creation order.
- `OrbitBody.tsx`, `SunBody.tsx` and the `useOrreryPhoto` hook / `createOrreryImageSlot` were deleted. The hook test was retargeted to the cache through the production loader. Every loader and derivative test was kept.

## C3-L1: does a recorded SkPicture own its drawImageRect SkImages and drawParagraph contents? (installed @shopify/react-native-skia 2.6.2)

**Yes for both. The only hazard is a layer re-recording with a disposed JS host object, and that is exactly what the ledger gates.**

1. **Recording path.** `createPicture` records into `Skia.PictureRecorder().beginRecording(bounds)` and returns `finishRecordingAsPicture()` (`src/skia/core/Picture.ts:11-24`). The canvas is a `JsiSkCanvas` over the `SkPictureRecorder`'s canvas (`cpp/api/JsiSkPictureRecorder.h:29-41`).
2. **Images.**
   - `JsiSkCanvas::drawImageRectOptions` (`cpp/api/JsiSkCanvas.h:164-178`) takes the image via `JsiSkImage::fromValue`. That returns an `sk_sp<SkImage>` copy (`cpp/api/JsiSkHostObjects.h:244-248`) and draws `_canvas->drawImageRect(image.get(), …)`.
   - `SkImage` is reference-counted (`class SK_API SkImage : public SkRefCnt`, `cpp/skia/include/core/SkImage.h:270`).
   - An `SkPicture` is an immutable command stream that "may be played in whole or in part at a later time" (`cpp/skia/include/core/SkPicture.h:33-34`). Skia's picture recorder therefore keeps its own reference to every image it records.
   - Caveat: the `SkRecords` command type itself is in Skia's compiled sources (`src/core/SkRecords.h`), which the package does not ship. The ownership is established from the public headers above and Skia's documented replay contract.
   - `dispose()` only drops the host object's own reference: `releaseResources()` calls `setObject(nullptr)` (`JsiSkHostObjects.h:147-161, 251-254`). A recorded picture keeps the image alive.
3. **Paragraphs.** `JsiSkParagraph::paint` (`cpp/api/JsiSkParagraph.h:43-50`) paints into the recording canvas. skparagraph paints ref-counted `SkTextBlob`s (38.7-04 SUMMARY: `ParagraphPainter.h:46`, `SkTextBlob.h:42`), so the picture owns the shaped text.
4. **What the ledger protects.** A disposed object throws only when it is accessed through its host object: `getObject()` → "Attempted to access a disposed object" (`JsiSkHostObjects.h:181-185`). That happens only when a layer mapper re-records a spec that still references it. The in-flight native draw is protected by `sk_sp<SkPicture> picture = _picture` (`cpp/rnskia/RNSkPictureView.h:63-65`).

Disposal therefore shipped for both content types.

## Deviations from Plan

### Auto-fixed issues

1. **[Rule 1 - Bug] Per-object retirement routing broke the C3-L3 bound** (Task 2).
   - **Issue:** routing each ledger handle back to the text publisher separately freed capacity one key at a time. Each confirmation re-ran the waiting publish, so a whole-set re-key took 17 generations instead of 3 or fewer.
   - **Fix:** retirement is routed in one batch per holder and epoch (`routeRetired` in OrreryWorld, mirrored in the test harness).
   - **Verification:** the C3-L3 test passes within 3 generations.
   - **Commit:** `251aaa72`
2. **[Rule 1 - Bug, test] The moon render test was flaky** (Task 3).
   - **Issue:** the moon's angle follows its random relationship uid, so in about 1 run in 3 the moon landed above a 500×700 viewport and was correctly not drawn. The old billboard assertion could not see this.
   - **Fix:** the test now uses a 1200×1600 viewport.
   - **Commit:** `2c573ffe`

### Interpretations and structure (inside the plan's latitude)

- **Ack mechanism.** The ack is a reaction chained on each layer's picture value, not a SharedValue write inside the picture mapper. The ordering guarantee is the same (it runs after `createPicture` returned, in the same mapper pass) and avoids a self-input loop. It is one ack per layer, with no shared `recordedGeneration`; the grep prints nothing.
- **Photo admission split.** The reserve policy applies to the desired set, and the physical pre-decode check uses the hard caps. A physical check at cap − reserve could deadlock an admitted ordinary photo behind a focused one. The bound is still checked at every step against physical truth: live fake images plus unsettled loads.
- **The focused photo uses the reserve, not ordinary room.** This is the plan's "may use the reserve", read so that a focus change never drops another photo while the reserve has room.
- **`buildBodySpecs` split.** It is `buildBodyLooks` / `buildSatelliteLooks` (static) plus `createOrrerySpecPublisher` (composition with initials and photos), so a photo arrival never rebuilds looks.
- **`onReady`** is the `mount(owner, onReady)` callback.
- **Request entries** carry `key` and `relativePath`; the V2 world uses the path for both.
- **Task ordering.**
  - The `useOrreryPhoto` hook and slot were removed in Task 1, where they became unused (the plan listed them under Task 3's files).
  - The C3-L3 per-layer-ack text test lives in Task 2, where the text service adopted the ledger.
- **Body order.** Computed once per frame in a shared derived value with an ordinary sort. The plan's optional insertion-sort optimisation was not needed for correctness; Plan 08 measures.
- **Accent colour.** The moon focus ink is `tokenInk(colors.accent)` in a spec builder. It is not a `color=` prop, so the accent analyzer needs no entry.
- **Tracer gate.** Task 1's `<verify>` was re-run green before Task 2. Per `autonomous: true` and the owner's standing direction (as in Plans 03–06), execution continued without a human-verify stop.

**Total deviations:** 2 auto-fixed (both Rule 1), plus the interpretation notes above. Nothing architectural; no owner-bucket item was decided.
