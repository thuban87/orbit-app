## Concerns

### 1. HIGH — Plans 08/09/12/13 — H6 carry-over: the fallback update contract is infeasible as written

**Evidence:** Plan 08:52 forbids per-frame Picture recording while requiring changing shader parameters; Plan 08:225 proposes an in-place parameter buffer/data texture. Plans 09:106 and 13:170 repeat that requirement.

Installed Skia’s `cpp/api/JsiSkRuntimeEffect.h:213` allocates new uniform storage, and `:225` copies values into it. `makeShader` creates a shader from that storage at `:42`. `src/skia/core/Picture.ts:21` records the drawing callback and finishes a Picture at `:23`. Updating the original JS array therefore cannot change uniforms already captured by that Picture. The inspected `SkImage` interface also provides no ordinary pixel-update operation for the proposed mutable data texture.

**Required PLAN.md change:** Replace “no Picture re-record” with a feasible contract permitting bounded UI-thread recording during animated updates while preserving fixed React nodes, cached geometry and static lookup tables. Specify the concrete API for high-count parameter updates and measure its allocation/upload cost. Extend parity tests to inspect consecutive rendered parameter values, not merely shared input fixtures.

Freezing fallback rings would weaken **D-32** and would be **[OWNER-DECISION]**; it must not become the workaround.

### 2. HIGH — Plans 04/07/08/09/14/15 — H3 carry-over: the lifetime protocol is not consistently adopted

**Evidence:** Plan 07:145–148 supplies the canonical ledger. However:

- Plan 08:139 still retires base snapshots through `recordedGeneration`.
- Plan 09:149 describes sky-image disposal on unmount without specifying ledger publication/acknowledgement.
- Plan 14:158 introduces Preview photo/text owners with only “released on unmount.”
- Plan 04:123 confirms a spec SharedValue reaction, which does not itself prove the legacy drawing consumers have finished recording it.

The existing ownership explanation in `use-orrery-photo.ts:35` specifically warns that disposed host objects can still be read during recording.

**Required PLAN.md change:** Explicitly route base snapshots, neutral skies and Preview resources through the canonical ledger. Give Preview its own epoch and layer acknowledgements, with the same ordered teardown. For Plan 04’s intermediate renderer, require confirmation after actual consumer recording rather than merely observing spec publication. Add delayed-consumer, replacement and unmount tests for these holders.

Also reconcile Plan 07:147/Plan 15:43’s “re-pinned under the warm owner” with Plan 15:44/126’s “warm owner never pins.” Define warm ownership as evictable retention, distinct from render pins.

### 3. HIGH — Plans 04/07/15 — H4/M5 carry-over: saturated caches cannot complete replacements reliably

**Evidence:** Plan 07:167 counts pinned, in-flight and retired images against hard caps, refuses admission when full, and retries only when pins drop. The same paragraph requires keeping a currently drawn image pinned until its replacement publishes.

At a full image-count cap, replacement cannot begin decoding; the old pin cannot drop until replacement publishes. Text has a related progress gap: Plan 04:121 refuses preparation when all entries are pinned/retired, while Plan 04:122 prepares the next generation before replacing the pinned set. A focused label requested after saturation is not guaranteed admission despite Plan 04:125 requiring it.

**Required PLAN.md change:** Define a bounded replacement protocol: either reserve replacement capacity within the cap, or publish a fallback generation that removes selected old references, await acknowledgements, then admit queued replacements. Trigger retries when capacity becomes safely available and discard superseded requests.

Add full-cap tests for same-path replacement/deletion, focus changes, theme/font changes and repeated tier transitions. Tests must prove eventual publication as well as bounded memory.

### 4. HIGH — Plan 11 — NEW, introduced by the H5 fix: the focus card becomes its own placement obstacle

## Summary

The cycle-1 fixes mostly hold against the code. The tap path, the horizon sites, the M9 inset source and the photo-invalidation hook all check out. The plan set is still reasonably consistent. The remaining risks are all in places where a fix leans on something that is asserted, not demonstrated:

- **H6:** the ring-field "in-place param buffer" may not be implementable in Skia 2.x. If it isn't, a switch on a ring-field build would have to freeze rings.
- **H8:** the fixture manifest omits Orrery preferences and ring order, which the debug passes change.
- **H3:** use-after-free safety rests on an acknowledgement signal that doesn't prove the old picture has stopped drawing.

Plans 05, 07 and 09 are larger than their estimates, and Plan 04 grew.

## Strengths

- The horizon fix correctly identifies the real throwing sites (`orrery-camera-logic.ts:509,517,393`). It centralises them on one non-throwing primitive and tests a 1,000-ring world at extreme poses.
- The tap fix keeps the existing `named` rule as an OR, so no case that opens Profile today stops doing so. A single end-to-end test pins the path, including UID and generation validation.
- Plan 07's `<resource_lifetime_contract>` is one place that Plans 13 and 15 cite instead of redefining. It lists the required scenarios: out-of-order acks, remount, teardown order, late decode.
- The measurement method now defines outcomes (truncated, no-present, unlabelled, insufficient) and says none of them is ever converted into a number. The fixture compare is a hard stop before release numbers.
- Admission before shaping or decoding makes the caps real bounds. The over-cap tests assert `built − disposed ≤ cap` at every step.
- The D-59 implementation is gated cleanly: the selector is compiled in only under an env flag, and a normal-build bundle grep proves it is absent.

## Concerns

### C1. HIGH, Plan 08 Task 3/4, Plans 09/12/13: ring-field "in-place param buffer" may be unimplementable. Cycle-1 H6 carry-over, partial.

The fallback contract allows an in-place write of a pre-sized buffer (a data texture) each frame, but names no Skia 2.6 API that does this. RN-Skia images are immutable. Lab B's own audit lists "two `Skia.Image.MakeImage` calls on every switch frame" as a cause of switch jank (`LAB-B-AUDIT.md` §3 item 2). SkSL uniform arrays for ~1,000 `float4` rings may also exceed Mali fragment-uniform limits. Plans 09, 12 and 13 all assume the capability. If it doesn't exist, the "never freeze rings during a switch" rule (D-32) cannot be met on a ring-field fallback at All Contacts scale.

- **Change:** add a Plan 08 Task 1 sub-step that proves one of two mechanisms on a phone: a fixed-size uniform array of at most N animated rings, or a reusable image whose pixels are updated without reallocation. The contract should then be written against the proven mechanism.
- **Owner-decision flag:** if no mechanism exists, any "freeze or simplify ring animation on the fallback" outcome weakens **D-32**. **[OWNER-DECISION]**
- This is a distinct risk from pending item (b). That item is about measurement, not feasibility.

### C2. MEDIUM-HIGH, Plans 04 and 07: the use-after-free signal is weaker than stated. Cycle-1 H3 carry-over, partial.

- **Plan 04.** For today's declarative renderer, a UI reaction on the spec SharedValue firing does not prove Skia has re-recorded without the old Paragraph. The declarative sksg tree reconciles on its own schedule, so there is a window between the reaction and the repaint. Plan 04's own constraint text calls the echo "a UI reaction on the spec SharedValue → `runOnJS`".
- **Plan 07.** Acks are written after `createPicture` returns. The `<Picture>` prop update that swaps the new picture into the canvas can still lag the mapper by a frame, so the old picture may still be drawn when an old-generation resource is disposed. I have not verified the RN-Skia commit timing, so I'm treating this as unproven risk, not a confirmed defect.
- **Change:**
  - Plan 04: require that the echo fires only after one UI frame tick (a `useFrameCallback` after the reaction) before any disposal.
  - Plan 07: add "plus one frame callback after the ack" to rule 2 of the contract, and add one test with a deferred picture commit.

### C3. MEDIUM-HIGH, Plans 01/10/16: the fixture manifest and restore omit persistent inputs the debug passes change. Cycle-1 H8 carry-over, partial. NEW gap.
