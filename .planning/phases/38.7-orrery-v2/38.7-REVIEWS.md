# Review: Phase 38.7 plans (01–16)

## 1. Summary

The plan set is well structured. The baseline is built from a frozen commit and the measurement method is frozen before any numbers are taken. Defect fixes land before visuals. Every owner-ruled decision gets an explicit checkpoint, and nearly every D-NN maps to a task. The main risks are not in the ordering. Two further gaps affect the switch-smoothness gate on the 3a: the per-System sky hue is baked on the JS thread at switch time, and the ring-method decision in Plan 08 is not carried into Plan 09's ring styling. Plans 05, 07 and 09 are also large for one executor.

## 2. Strengths

- **Baseline discipline.** Plan 02 builds from `BASELINE_SHA`, greps the release bundle for dev labels, and forbids uninstall or clear-data. Plan 01 freezes the method and tests every parser on canned output.
- **Defect fixes come first and are provable.** Plan 03 adds a capture-allowlist test, equivalence tests against frozen copies of the old implementations, and bit-exact projection parity.
- **Honest spike.** Plan 08 measures both ring methods at Size 120 and All Contacts on both phones, and puts the decision in front of the owner rather than defaulting it.
- **D-12 and D-45 are decomposed correctly.** Plan 05 splits the max user tilt from the Home profile, keeps flat as a one-constant switch, and adds horizon culling plus no-throw tests at 0°, 45° and 62°. The research flagged the UI-thread throw risk, and the plan addresses it.

## 3. Concerns

**HIGH**

1. **Occlusion dim can miss the card it protects (Plans 11 and 14).**
   - Plan 11 draws the D-55 dim from "window rects" read from the shell obstacle store. The focus card is positioned by `useAnimatedStyle` over the live frame (`src/components/orrery/OrreryFocusContext.tsx:46-72`) and is never measured; the file has no `measureInWindow`.
   - The card's `left`/`top` change on every pan, pinch and focus animation, and Plan 11's `focusCardPlacement` keeps the card animated "horizontally near the body". A measured or stale rect would therefore not cover the card while it moves.
   - Plan 14's 4.5:1 proof assumes the dim fully covers the card rect, so the D-28 hard gate would be proven on paper but not met on device.
   - Fix: in Plan 11 Task 2, derive the focus-card occlusion rect from the same SharedValue placement function the card uses (`focusCardPlacement` over `frame`), not from a measured rect. Keep obstacle-store rects only for static panels.
   - Add a Plan 14 test that enumerates every Orrery text surface and asserts each has an occlusion source.

2. **Initials Paragraphs for every body break the Defect 3 fix at All Contacts (Plans 04 and 07).**
   - Plan 04 builds an initials Paragraph for every body ("prepares every body's initials Paragraph"). Tier laziness is applied only to labels.
   - At about 1,000 contacts that is about 1,000 Paragraphs charging 1 MiB of memory pressure each. The 1,200-entry cache cap is then mostly consumed by initials, which is what Defect 3 was meant to remove.
   - Fix: prepare initials only for photo-less bodies that are visible at a projected radius above a draw threshold. Alternatively draw initials as glyph runs, not Paragraphs.
   - Add a Plan 04 test asserting a 1,000-body overview builds a bounded number of Paragraphs.

3. **Canvas unmount can leak or use-after-free retired native objects (Plans 07 and 15).**
   - Disposal is gated on "confirmed recorded generation". After the canvas unmounts there is no mapper left to confirm anything.
   - Without a rule, retired entries are stuck, so the warm cache leaks or the cap is exceeded. Forcing disposal at unmount, while a UI-thread mapper may still be running, risks a use-after-free.
   - Fix: define in Plan 07 that unmount enqueues a final `confirmRecorded(∞)` only after the Picture nodes are gone, using a post-unmount UI-thread tick or the `runOnUI` surface-dispose ordering. Test it in Plan 15's blur/return sequence.

4. **Per-System sky hue baking will stall the switch the plans gate on (Plans 09 and 13).**
   - Plan 09 CPU-bakes the nebula on the JS thread per (package, mode, hue, size). The RESEARCH notes the Lab A bake was never measured on a device and may explain the 3a's sluggish open.
   - Plan 13's sky crossfade needs both the outgoing and incoming hue images, and says "both cached; no bake on the UI thread". It does not say who bakes the incoming hue, or when.
   - A bake at publish on the JS thread lands in the switch window on the 3a, the exact phone D-24 is gated on.
   - Fix: bake one neutral nebula per package×mode and apply the System hue as a draw-time uniform or colour filter. Alternatively pre-bake the incoming hue before `publish` starts the animation. State which in Plan 09, and measure the bake time in Plan 08's spike.

**MEDIUM**

5. **Ring-field hybrid is not carried into Plan 09 (Plans 08 and 09).**
   - Plan 09 Task 2 writes the thin-ring, rim, grid and pulse terms only for the world-plane shader. D-44 says the rim and pulse "are written for whichever method wins".
   - If the owner picks `hybrid` or `ring-field` in Plan 08, Plan 08 Task 4 builds a bare ring field and Plan 09 never styles it.
   - Fix: add to Plan 09 Task 2 that every term (thin width, dash, rim, pulse, grid) is implemented in both ring paths whenever `host.ringMethod` is not `world-plane`, with parity tests. Alternatively require Plan 08 Task 4 to port the Plan 09 terms.

6. **Plan 05 Task 1 depends on a field Task 3 introduces.** Task 1 says reorder reads world ring radii, "pick one" source, and names `worldRingRadius`, which Task 3 adds to `projectFrame`. Task 1's tests therefore cannot pass in order. Move the `worldRingRadius` addition to Task 1, or build Task 1's reorder on the world's own `ringRadius`. This also matters because `previewReorder` currently derives the new position from `distance - body.ringRadius + radius` (`src/logic/orrery-reorder-logic.ts:127-146`), which must simplify once the push is gone.

8. **D-40 comparison is layer-mismatched (Plans 02, 08, 16).**
