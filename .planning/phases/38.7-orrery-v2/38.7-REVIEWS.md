- **The C4-M3 authority list matches each place that writes `pose`.** That covers the publish path (forceSwitchHome), restore (:899-919), the Home reframe (:963-976) and Recenter. The progress ≥ 1 rule correctly cites why a mid-switch pose write would be invisible and then snap at settle.
- **C4-L1** does not claim proof of a native draw. It makes the executor verify, at a specific file:line, that the recorded picture owns its contents before any disposal ships. That is the right gate for a use-after-free class of bug.

## 3. Concerns

### C5-M1 (MEDIUM, NEW, cross-plan): Plan 15's warm settle bypasses Plan 13's `worldViewport` adoption

- **Plan:** 15:152 says "settle any paused switch to its destination (progress 1, `pose` = `cameraTo`…), compute the Home pose from the retained scene and the current viewport". Plan 13:179 adopts the pending viewport only "in the same JS callback as the runtime's settle commit (`finish` → `runOnJS(prune)`) or whenever progress otherwise reaches 1".
- **Source:** tab blur pauses the switch (OrreryScreen.tsx:438-440 cleanup → `pauseSwitch()`), so progress stays below 1 with no driver. The non-warm return reaches `finish` through `resumeSwitch()` (:612-614). A warm-return settle written straight into `progress`/`pose` never calls `finish`, so `prune` never runs and the adoption hook never fires.
- **Failure:**
  1. Switch to System B.
  2. The save-error banner appears mid-switch, or any other obstacle changes, so `worldViewport` holds the old value.
  3. Leave the tab mid-switch and return warm.
  4. Plan 15 computes Home from `viewport` (with the banner) and draws it through `worldViewport` (without the banner), so the first warm frame is not the Home it computed.
  5. `worldViewport` then stays stale until some later viewport change or switch. `prune` also never retires the departed resources, so the ADR-170 retirement is skipped for that switch.
- **Change to 15:152:** replace "settle any paused switch to its destination (progress 1, `pose` = `cameraTo`…)" with:

  > settle any paused switch through the runtime's own settle path (the `finish` semantics: `settleSwitchChoreography`, `pose = cameraTo`, `runOnJS(prune)`, which also performs Plan 13's pending `worldViewport` adoption; add a public `settle()` on the runtime for this), then compute the warm Home from the adopted `worldViewport` (equal to the current `viewport` after adoption).

  Add a test (d) to 15:159: a warm return after a mid-switch banner obstacle shows its first warm frame at Home under the adopted viewport, and resources are pruned to the destination.

### C5-L1 (LOW, NEW): C4-M1 settle-time projection shift is unacknowledged, and the acceptance wording does not match the code

- **Plan:** 13:179 and 13:186 say "the settled camera is destination Home clamped to it (no extra reframe)".
- **Source:**
  - `cameraTo` is derived at publish from the publish-time viewport (OrreryScreen.tsx:327-328).
  - `finish` sets `pose = cameraTo` (use-orrery-switch-runtime.ts:257).
  - The Home effect then takes the `forceSwitchHome` early return (OrreryScreen.tsx:943-950). Nothing clamps or reframes the pose to the new viewport.
  - Adopting a new obstacle at settle changes `usableCameraRect` (orrery-camera-logic.ts:115-180). The save banner is bottom-anchored, up to 25 % of the canvas (OrreryScreen.tsx:1339-1344), so the projection centre moves up by half its height and the whole map shifts once, right as the switch lands.
  - This shift is identical to what already happens today when a banner appears while the map is settled (the Home effect's "active" domain branch at :924-933 only clamps), so it is not a regression.
- **Change to 13:179 / 13:186:** replace "settled camera = destination Home clamped to it" with:

  > the settled pose equals `cameraTo` (publish-time Home; no Home reframe — `forceSwitchHome`); the only visible change at adoption is the one-time projection-centre shift from the new usable rect, the same shift a banner causes on a settled map today.

  This changes what an executor asserts, so it is worth the edit.

### C5-L2 (LOW, NEW): C4-M2's recorded refs cannot suppress the later Home effect

- **Plan:** 15:152 says "record the matching `lastHomeFrame`/`lastHomeDomain` so that when `sessionReady` arrives and the Home effect runs it lands on the same pose".
- **Source:** both short-circuits require `sessionResume === "active"` (OrreryScreen.tsx:922, :924). Under `"home"`, the effect runs the full path again: `deriveHomePose` → `pose.value = home` → `session.resumed()` (:952-976).
- **Effect:** the outcome is still correct when the reloaded world is identical, because the reassignment is the same value. If data changed while away (for example a Quick Log from the Dashboard), Home is re-derived on the reloaded world and moves once. The world moves in that case anyway, so this is acceptable. Test 15:159(a) will pass on identical fixtures.
- **Change:** in 15:152, either:
  - (recommended) after recording the refs, call `useOrrerySessionStore.getState().resumed()` in the same warm-prep step, so the later effect takes the `"active"` path (:922/:924); or
  - state plainly that the later effect re-derives Home and may move once if the reloaded world differs.

### C5-L3 (LOW, NEW): Ordering of the warm first frame is untestable in vitest

- **Plan:** 15:152 / 15:159 assert "BEFORE the warm canvas mounts (in the same commit…)" and "the first warm frame … is already Home".
- **Problem:** JS-side writes to a SharedValue reach the UI runtime asynchronously. Whether the Skia mapper's first evaluation sees the new pose depends on queue ordering that the node test harness does not model.
- **Change:** gate the warm mount on a `warmPosePrepared` flag that is set from `runOnUI(() => { pose.value = home; runOnJS(setWarmPosePrepared)(true); })()`. The first frame is then provably post-write, at the cost of one UI round-trip, which fits easily inside the G3 budget.

### C5-L4 (LOW, NEW): "useOrreryCamera occlusion" at 13:179 is ambiguous

The phrase could be read as routing Plan 11's occlusion-dim rects through `worldViewport`. That would defer the D-55 dim under translucent glass panels (selector, view options, cluster panel) that open mid-switch.

- **Change:** add to 13:179:

  > Plan 11's occlusion rects (focus card from `focusCardRect`, static panels from the obstacle store) do NOT go through `worldViewport`; they update immediately via their own SharedValues.

- Also state that the publish subscription keeps computing `destinationHome` from the live `viewport` (OrreryScreen.tsx:327-328), not from `worldViewport`. A switch published while an obstacle is pending then lands on Home for the viewport that is adopted at settle.

### C4-M1 side effect: assessment (rated LOW, acceptable)

A feedback panel that appears mid-switch reaches the camera and clamp only at settle, up to about 2.1 s later. This is acceptable:

- **No contrast or legibility risk.** The save, missing and broken-System feedback panels are opaque: `OrreryFeedback` with `backgroundColor: colors.surface` (OrreryFeedback.tsx:48-58; OrreryScreen.tsx:1243-1262), and `surface` is opaque in all four palettes (theme-presets.ts:35, :141, :209, :271). The deferral does not touch the D-28 gate for these panels.
- **No mis-tap risk.** The panel is an RN view above the canvas, so touches on it never reach the canvas gesture. Taps on bodies are gated by choreography interactivity until progress 0.82 anyway (D-32). The panel's retry button is reachable and accessible immediately, and the canvas exposes nothing to accessibility.
- **No recorded-decision conflict.** Today's code also does not reframe for an obstacle that appears after publish (`forceSwitchHome`, OrreryScreen.tsx:943-950). The systems doc's "feedback are shared framing exclusions" (docs/systems/orrery.md:99) is still honoured from settle onward. It is delayed, not removed.
- **Real cost.** For up to 2.1 s, bodies and labels may sit under the bottom banner (cosmetic), followed by the one-time centre shift at settle (C5-L1). Both are better than the mid-switch prop change C4-M1 removed.
