# Phase 38.7 — execution policy (owner, 2026-10-03)

**This file overrides Plans 09 (remainder)–16 wherever they conflict.** Executors: read it before the plan. Recorded as
CONTEXT D-66. Purpose: stop duplicating Plan 16's testing inside every plan and cut executor token spend, without
leaving a broken state for the end.

## 1. Devices

- **The Pixel 6 Pro is the target device.** All mid-phase device work runs on the 6 Pro only.
- **The Pixel 3a is out of every plan's device work** (installs, screenshots, measurements, owner rulings). It gets ONE
  end-of-phase smoke check in Plan 16: on the release build it opens the Orrery at Size 120 and All Contacts with no
  crash and no ANR. Nothing is tuned for the 3a, and no 3a number is a gate.
- Any owner ruling a plan addresses to the 3a (e.g. Plan 13 "smoothness on the Pixel 3a") is made on the 6 Pro.
- Plan text that says "both phones", or a precondition that requires the 3a to be attached, reads as "6 Pro" only.
  Verify or acceptance lines that grep for "Pixel 3a" are waived.

## 2. No performance measurement inside the plans

- DEBUG performance numbers (presents/s, per-thread CPU, idle soak, temperature, `dumpsys meminfo` D-11 runs, tab-return
  decomposition, switch stall) are **not taken in Plans 10–15**. They were "context only" there, and Plan 16's single
  release build is the measurement that counts.
- Exceptions: a single quick number only where a plan needs one to choose a tunable for an owner decision. Take one run,
  not three, and label it DEBUG.

## 3. Device checks: a smoke test, not a matrix

- **After each code plan: one 6 Pro smoke check.** Install the DEBUG build (or reload via Metro if no native change),
  open the Orrery, exercise the new feature once, and confirm there is no redbox, crash or ANR. Keep this check: it
  catches Hermes on-device crashes that vitest cannot (worklet ordering, `crypto`).
- **Screenshots only for owner decisions: one per option, one theme unless the decision is about themes.** No
  size × theme matrices and no repeat shots. A plan with no owner decision takes one screenshot.
- **The agent opens as few images as possible itself.** It lists paths in the SUMMARY; the orchestrator sends them to
  the owner.
- Screen recordings only when the decision is about motion (switch smoothness, pulses).

## 4. Tests

- **Test what can break data or crash; check visuals by eye.** Unit-test resource disposal and the generation ledger,
  switch/focus/session logic, anything touching stored data, and pure logic with real branching. Do NOT write
  fake-canvas tests that assert cosmetic draw calls, call counts or shader uniform values for looks.
- **Each must_haves truth needs evidence; long edge-case lists in task actions are guidance.** Implement them where they
  are cheap. A test is required for a must_haves truth or a data/crash/leak risk, not for every enumerated case.
- **During tasks, run only the touched tests** (`npx vitest run <paths>`). Run `npm test` (with a quiet reporter, e.g.
  `npx vitest run --reporter=dot` so a pass prints one line), `npx tsc --noEmit` and `npm run check:colors` **once at
  the end of the plan**, and before any handoff commit the plan requires. Never paste full suite output into context;
  keep failures only.

## 5. Orchestration (orchestrator-side)

- **A fresh agent runs the device pass.** The code executor stops when the plan's code tasks are committed. A new, small
  agent runs the device/smoke task and any owner checkpoint, so it does not carry the code context.
- Owner look checkpoints stay as planned (Plans 10, 13 and 14), with fewer, sharper screenshots.

## 6. Look decisions — options a person can actually see (owner, 2026-10-03, after the Plan 09 round)

Plan 09's first round failed: the grid was offered at 0 / 0.12 / 0.25 opacity on 0.8 dp hairlines (all near-invisible),
the pulses at 15 / 25 / 35 % around a guessed 0.25 (clips indistinguishable), and the All Contacts tinted option was
never captured. Cause: the owner's words ("not very obvious", "unsure about a grid") were turned into small numbers
without looking at a screen, and lab NUMBERS were copied without the lab LOOK. Rules for every owner look decision
(Plans 09-redo, 10, 13, 14; and every visual effect in 11/12):

- **Anchor to what the owner approved in the labs.** Option set = **"as in Lab X"** (reproduce the look the owner saw,
  matching it by eye against the lab's own screenshots/clips, not by copying its constants) / **clearly weaker** /
  **clearly stronger** / **off** where off is an option. Never ±0.1 around a guess. If the plan's starting value is
  below the lab look, the lab look is still an option.
- **Options must be visibly different side by side at phone size.** If two options look the same, widen the spread
  before capturing anything else.
- **Every image or clip carries a burned-in plain-words label** ("Grid: strong", "Pulses: as in Lab B") — ffmpeg
  `drawtext` is available — and the doc gives one line per item: what the setting controls, in plain terms, and the
  raw value per option.
- **Every option the decision names is captured.** A two-way choice gets both sides, side by side.
- **Motion decisions get clips long enough to show the motion several times** (≥ 10 s), side by side or labelled
  in sequence, with "off" included for reference.
- **The orchestrator looks at every image before the owner sees it.** Anything a person can't tell apart goes back.
- **Plans 11/12 (no checkpoint):** each new visual effect (focus dim, reticle, occlusion dim, corner brackets, charge
  arc, outline glow) gets one before/after screenshot. The orchestrator checks it is plainly visible. A near-invisible
  effect is tuned up to the lab look before the plan closes.
