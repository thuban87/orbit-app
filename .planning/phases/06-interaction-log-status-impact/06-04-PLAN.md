status/gravity-tier colour token set the impact/status surfaces (Plans 04/05) consume. Three parts:

1. Extend the query-time status engine with `REASON_SQL` (a CASE mirroring STATUS_SQL's branch order
   so status and reason never disagree) and add a single-contact status read that returns
   status+reason (a query-time status type that INCLUDES rogue — not the legacy OrbitStatus).
2. **ADD the status/gravity colour tokens (OWNER-APPROVED 2026-08-15)** — a `rogue` token and an
   ordered `gravityTiers` ramp on `ThemePalette` + space-dark values, mirroring EXACTLY how
   danger/avatarSwatches were added (theme-presets.ts is the sole colour-literal file). Plan 04's
   rogue label and Plan 05's GravityBar then CONSUME these tokens instead of borrowing danger/accent.
3. Render the rogue label + reason on the profile via `colors.rogue`. The "Rarely responds" label
   already renders in the scaffold — reuse it.

Purpose: LOG-05 (rogue at the shared constant or via Rarely-responds; reason recorded; in-app only)
and LOG-04's rendering half (the label + the fact that rarely_responds drives recency).

Output: `REASON_SQL` + status.test extension; `contact-status-read.ts` + test; the `rogue`/`gravityTiers`
tokens + theme-presets test extension; the profile render.

CRITICAL — do NOT redefine ROGUE_K (it lives in status.ts, value 3, OWNER-APPROVED 2026-08-15, and is
imported by orrery/notify/digest — one value, one place). Do NOT type query-time results as
`src/types.ts OrbitStatus` (it excludes rogue) and do NOT call the legacy `calculateStatus()`. Read
status from the SQL engine.
