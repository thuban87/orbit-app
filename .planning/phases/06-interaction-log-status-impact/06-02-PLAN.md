<objective>
Replace the profile's timeline stub with the real read surface: a scrollable list of the contact's
touchpoints interleaved with read-only events, newest-first (`occurred_at DESC, id DESC`). This is
the load-bearing correction surface for later slices (edit/delete land in Plan 03) and the honest
answer to the plugin's fatal mistake — a log with zero readers.

Purpose: LOG-02's read half. Success criterion 2 wants touchpoints (editable) and events
(read-only, visually distinct) in one view.

Output: `src/db/timeline-read.ts` + test (the interleaved UNION read), `src/components/TimelineRow.tsx`
(the row renderer), and the profile screen wired to load + render them.

FLAGGED DECISION (default taken — surface to owner at the pre-execution pause, do NOT block):
**LOG-02 events.** The dossier DECIDED events render read-only + visually distinct in the timeline
v1, but the code deliberately DEFERRED the events WRITER — there is no events writer and no `type`
vocabulary yet (`contacts-dao.ts:382-386`; the `events` table exists from migration 1 but is empty
in the running app). DEFAULT for this plan: build the interleaved timeline READ correctly (it UNIONs
interactions + events and orders both), with events EMPTY in practice in v1 because no writer exists
yet (writers arrive with the phases that own each event type — snooze is Phase 11, etc.). Do NOT
invent an events `type` vocabulary and do NOT retrofit Phase-4 archive/restore to emit events.
The test seeds an events row directly to prove the interleave ordering is correct.
</objective>
