## Summary

Phase 38.1 is entirely a **read/render/routing polish** over shipped Milestone-2 code. Every capability it touches already exists; nothing needs a new library, and the one net-new piece of persisted behaviour it might have wanted (a 12/24h preference) is explicitly deferred to keep D-02 (no schema) intact. The work splits cleanly along the dossier §Q ownership lines and the code confirms each seam is reachable without inventing new data.

The two genuinely non-trivial engineering questions are: (1) **D-04's AA proof** — the orrery backdrop is a Skia render, not a flat asset, so the plan must declare a *worst-case brightest orrery pixel* (the star/sun palette) and prove text-over-`alphaComposite(tint, brightestPixel, opacity)` meets AA in all four palettes, exactly mirroring the existing per-asset proof pattern already in `surface.test.ts`; and (2) **§F Most Recent/Previous**, where the Profile snapshot currently reads only the `is_current = 1` row and must gain a *new bounded read of prior rows from the same `current_state_entries` table* (a query change, not a schema change).

The single highest-risk landmine is **D-06 Off Limits editor reuse**: `FuelEditor` is a *general* fuel editor covering all five kinds and its draft defaults to `recent` (never `off_limits`). `EditContactScreen` already solved the kind-scoping with a documented DATA-LOSS guard (a prior review caught this). Any extraction MUST carry that guard forward verbatim, or an Off Limits edit will silently write/clobber other fuel kinds.

**Primary recommendation:** Follow the dossier §Q six-group shape. Do D-04 as a new `orreryOverlayTintOpacity()` token + a `treatment` prop on the existing `GlassSurface` (no fork). Do §F by extending the Profile knowledge read with a capped prior-entries query keyed on `is_current`. For D-06, prefer the lowest-risk reuse that preserves `EditContactScreen`'s kind-scoped off-limits guard — either navigate to `Edit`, or extract a screen that lifts that guard wholesale. Route the temporal edit affordances (Last Talked About / Current Location) to the already-correct `MemoryHistory` screen.

## Architecture Patterns

### D-04 — Orrery overlay treatment (the hardest token question)

**Current mechanism (verified):** every named Orrery overlay renders through `GlassSurface` with `density="dense"`.
- `[VERIFIED: src/components/orrery/OrreryControls.tsx:89]` `<GlassSurface density="dense">`
- CONTEXT lists the other overlays: `OrrerySystemSelector.tsx:142,170`, `OrreryClusterPanel.tsx:49`, `OrreryFocusContext.tsx:87`, `OrreryViewOptions.tsx:104,123`.
- `[VERIFIED: src/components/orrery/OrreryContactsSheet.tsx:12,54]` `OrreryContactsSheet` uses `Sheet variant="detail"`, **NOT** `GlassSurface` — it is a modal bottom sheet, not a floating orrery control. **Recommendation: exclude it from the treatment** (it does not "reveal the orrery behind it"); confirm at plan time (§R item 1).

**Why the overlays read near-transparent today (the §B complaint):** `GlassSurface` computes its tint opacity as `cardTintOpacity(themePackage, mode, density)`.
- `[VERIFIED: src/components/ui/GlassSurface.tsx:66]` `const tintOpacity = cardTintOpacity(themePackage, mode, density);`
- `[VERIFIED: src/theme/tokens/surface.ts:173-181]` in the **matched** regime (galaxy↔dark, standard↔light) this returns `CARD_GLASS_OPACITY[pkg]` = galaxy `0.05` / standard `0.5`; in the **mismatched** regime it returns the opaque density band. So galaxy overlays render at `0.05` (the near-transparent complaint) and density is ignored in the matched regime.

**Prescribed design (no fork — satisfies D-04 + ADR-087):**
1. Add to `src/theme/tokens/surface.ts` a **new named treatment**, e.g. `ORRERY_OVERLAY_TINT_OPACITY: Record<ThemePackage, number>` + a pure helper `orreryOverlayTintOpacity(pkg, mode): number`. It returns a **translucent** value in **all four** combos — it must NOT fall back to the opaque `densityOpacity` band in the mismatched combos (D-04: the orrery canvas is a controlled dark render surface, not mismatched wallpaper). It is fully decoupled from `CARD_GLASS_OPACITY`/`cardTintOpacity`, which stay byte-for-byte unchanged.
2. Add a `treatment?: "card" | "orrery-overlay"` prop to the existing `GlassSurface` (default `"card"`). When `"orrery-overlay"`, source opacity from `orreryOverlayTintOpacity(pkg, mode)` instead of `cardTintOpacity(...)`. This is ONE component, ONE new token treatment — exactly ADR-087's "one semantic surface API, no parallel families." The tint colour stays the `surface` token (`[VERIFIED: surface.ts:100,112]` `tintTokenKey: "surface"`).
3. Apply `treatment="orrery-overlay"` at the six `GlassSurface` call sites above.

**AA-proof recipe against the Skia orrery backdrop (the crux):**
- The orrery draws stars from `[VERIFIED: src/components/orrery/OrreryWorld.tsx:272-273]` `starColors = [colors.textSecondary, colors.textPrimary, ...colors.starPalette]` over `[VERIFIED: OrreryWorld.tsx:521]` `background={colors.background}`; sun/Polaris use `[VERIFIED: src/components/orrery/Polaris.tsx:30]` `colors.starPalette[0] ?? colors.textPrimary`.
- So the **worst-case (brightest) orrery pixel** per palette is the max-luminance member of `{colors.textPrimary, ...colors.starPalette}` (a bright star / the sun core), analogous to the existing `slot.brightestPixel`.
- The existing test infra already does exactly this composite proof: `[VERIFIED: src/theme/tokens/surface.test.ts:186-206]` composites text/status foregrounds over `alphaComposite(tint, slot.brightestPixel, cardTintOpacity(...))` and asserts `>= AA_NORMAL`/`AA_LARGE`. Primitives exist: `[VERIFIED: src/theme/contrast.ts:20,22,67]` `AA_NORMAL = 4.5`, `AA_LARGE = 3.0`, `contrastRatio()`; and `[VERIFIED: surface.ts:324]` `alphaComposite(fg, bg, alpha)`.
- **New test block:** for each of the 4 `pkg×mode` palettes, compute `brightestOrreryPixel = max-luminance({palette.textPrimary, ...palette.starPalette})`, then assert `assertForegroundsAA(alphaComposite(palette.surface, brightestOrreryPixel, orreryOverlayTintOpacity(pkg, mode)), palette, ...)`. Because the tint dominates as opacity rises, the tuning problem is: pick the **lowest** opacity that still clears AA over the brightest star in the adverse (mismatched) palettes while still visibly revealing the orrery (§B). That is the on-device discretion tuning (D-04).

**Pattern: the opacity-ordering/monotonic guards.** The existing tokens keep `liveGlassTintOpacity >= fallbackTintOpacity` and monotonic density bands, asserted in tests (`[VERIFIED: surface.test.ts:135-151]`). Keep the new treatment consistent (single scalar per package is fine; no density variance needed for overlays).

### D-07 — heading/caption ownership (§D)

The Profile section chrome renders a `role="heading"` label **and** a `role="caption"` summary:
- `[VERIFIED: src/components/profile/ProfileModuleHost.tsx:166-169]` `<AppText role="heading">{label}</AppText>` then `<AppText role="caption">{pending ? "Saving…" : summary}</AppText>`.
- The `summary` for top-level sections comes from `topLevelSummary()` `[VERIFIED: ProfileModuleHost.tsx:106-128]`. The `things-to-remember` case returns `PROFILE_MODULE_EMPTY_SUMMARIES[id] ?? "Things to Remember"` **unconditionally** (never inspects `knowledge.data` counts) — the confirmed D-07 bug (CONTEXT cited `:106-116`; the case is at `:114-116`).
- The baked strings: `[VERIFIED: src/profile/module-host-model.ts:11-15]` `PROFILE_MODULE_EMPTY_SUMMARIES = { "things-to-remember": "Things to Remember · Nothing added yet", "contact-methods": "Contact Methods · None", "interaction-history": "Interaction History · No interactions yet" }`.
- Child summaries come from `knowledgeChildSummary()` `[VERIFIED: ProfileModuleHost.tsx:62-104]` (e.g. `off-limits` → `"Nothing added yet"` / `` `${n} saved` ``) AND independently from `knowledge-presentation.ts` `summary()` `[VERIFIED: src/profile/knowledge-presentation.ts:116-122]` (`"Nothing added yet"` / `` `${shown} shown · ${remaining} more` ``), which is rendered by the nested renderer.

**The duplicate-heading pair (D-07):** the nested `ThingsToRemember` renderer emits its OWN heading+caption per child: `[VERIFIED: src/components/profile/ThingsToRemember.tsx:184-188]` `<AppText role="heading">{child.title}</AppText>` + `<AppText role="caption">{child.summary}</AppText>` + optional `child.helper`. When a child (e.g. `last-talked-about`) is placed as its own `ProfileSection`, the section header label AND the nested `KnowledgeChild` heading can both render the same title string → the duplicate headings.

**Prescription:**
1. Make section captions **identifiers only**: strip content-state from `topLevelSummary`/`knowledgeChildSummary` and the `PROFILE_MODULE_EMPTY_SUMMARIES` metadata class. Keep transient `"Saving…"` (pending state) — it is not content metadata. Note: removing the caption means a collapsed section shows only its title (intended by §D; content state moves to the body empty-state).
2. Establish single ownership: the **parent** `ProfileSection` owns the visible section heading; the nested `KnowledgeChild` must not re-emit a heading its container already supplied (suppress the `role="heading"` at `ThingsToRemember.tsx:184` when the child is hosted as its own section). Meaningful subsection headings that are NOT duplicated by a container stay (§D "do not flatten").
3. Move any real empty-state text ("Nothing added yet") into the section **body** (`role="body"`/`role="caption"` inside `sectionBody`), not the header.

### §F — Most Recent & Previous (data gap + dedup)

**The gap (verified):** the Profile snapshot carries **current-value-only**. `[VERIFIED: profile-knowledge-read.ts:112-118]` `readCurrentState` selects `WHERE contact_id = ? AND is_current = 1`. `ProfileKnowledge.currentState` is `Partial<Record<CurrentStateFieldKey, ProfileCurrentStateEntry>>` (`[VERIFIED: profile-knowledge-read.ts:66-74]`). The presentation builder emits a single item: `[VERIFIED: knowledge-presentation.ts:199-230]` `formatCurrentState` sets `items: entry ? [<one current item>] : []`.

**The data already exists (no schema — D-02):** `[VERIFIED: src/db/current-state-history-read.ts:67-79]` `getCurrentStateHistory(exec, contactId, fieldKey)` does `SELECT ... FROM current_state_entries WHERE contact_id = ? AND field_key = ? ORDER BY created_at DESC, id DESC` — the full history from the SAME table.

**Dedup / canonical identity (§R item 5 — solved):** `is_current` is the discriminator. The existing full-history screen already does exactly the split: `[VERIFIED: src/screens/MemoryHistoryScreen.tsx:75-78]` `priorEntries = history.filter((row) => row.is_current === 0)` (Previous), with the current value read separately via `getCurrentStateValue` (Most Recent). So **Most Recent = the `is_current = 1` row; Previous = `is_current = 0` rows, `created_at DESC`, capped at 5.** This structurally guarantees Most Recent ∉ Previous.

**Prescription:** extend the Profile knowledge read (or add a small sibling read) to fetch, for the temporal fields only, up to `PREVIOUS + 1` prior rows keyed on `is_current = 0` (a bounded query against the existing table — a read change, NOT schema). Cap Profile preview at exactly 5 Previous (dossier §F line 116). Wire `formatCurrentState` to emit Most Recent + Previous[0..5]. Empty/single-record states: 0 records → neutral in-body empty state, no `MOST RECENT`/`PREVIOUS` shells; 1 record → Most Recent only, omit Previous (UI-SPEC).
- **Full-history destination:** `MemoryHistoryScreen` (route `MemoryHistory: { contactId, fieldKey }`, `[VERIFIED: src/navigation/types.ts:75]`) is the complete-history editor (§F line 118). Note it labels the latest "most recent" and older "Earlier entries" `[VERIFIED: MemoryHistoryScreen.tsx:137,165]` — §F wants labels `Most Recent` / `Previous`; align copy on Profile (the dedicated screen's internal copy is out-of-scope unless the audit flags it).

## Common Pitfalls

### Pitfall 1: Off Limits editor clobbers other fuel kinds
**What goes wrong:** mounting `FuelEditor` scoped to off-limits without the kind guard; the draft defaults to `recent`, and a kind change/add writes a non-off_limits row or the diff drops other kinds.
**Why:** `FuelEditor` is a general 5-kind editor (`FuelEditor.tsx:59-68`); `DEFAULT_KIND` is never `off_limits`.
**How to avoid:** reuse `EditContactScreen`'s exact guard — filter `kind === "off_limits"`, force draft kind, defensive re-filter on write (`EditContactScreen.tsx:32-36,520,806-808`). Add a test asserting other kinds survive an off-limits add/edit/delete.
**Warning signs:** a "Recent" row appears after editing Off Limits; other fuel disappears.

### Pitfall 2: D-04 AA fails in the mismatched combos
**What goes wrong:** an opacity tuned only in galaxy-dark looks great but fails AA in galaxy-light / standard-dark over a bright star.
**How to avoid:** prove all 4 palettes over the brightest orrery pixel in `surface.test.ts`; the mismatched palettes are the binding constraint. Tune the single opacity to the worst case, then confirm on-device (memory: Phase-23 style AA flag-for-owner is expected if a combo is marginal).

### Pitfall 3: Removing captions breaks collapsed-section previews
**What goes wrong:** stripping the `role="caption"` summary leaves collapsed sections showing only a title.
**Why:** the caption doubles as the collapsed preview today.
**How to avoid:** this is the intended §D behaviour (identifiers only); confirm with UI-SPEC. Keep the transient `"Saving…"` state (not content metadata).

### Pitfall 4: Reanimated worklet hazard when splitting Orrery controls
**What goes wrong:** the north control uses `useAnimatedProps`; restructuring can reorder helpers and produce an on-device Hermes crash vitest can't catch.
**How to avoid:** keep helper definitions above callers (memory: worklet-forward-ref-hazard); verify on the Pixel, not just tests.

### Pitfall 5: Year heatmap weekday misalignment after the flip
**What goes wrong:** rendering year cells as a naive flat wrap breaks Sun..Sat column alignment.
**How to avoid:** reuse the Month branch's `chunkWeeks`→`dayRow` rows verbatim; each chunk is already one calendar week, so rows give aligned columns for free.
