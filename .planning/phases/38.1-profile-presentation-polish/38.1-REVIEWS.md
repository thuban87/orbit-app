# Cross-AI Plan Review — Phase 38.1

Two independent source-grounded lanes: **codex** (gpt-5.6-sol) via gsd-review, and **claude** (opus-4-8) reviewing the code on disk directly. Both lanes opened the referenced files and verified claimed file:line references and behavior. The two lanes converged strongly.

## Consensus Summary

The plan set is **architecturally sound and fully respects the phase's non-negotiable boundaries** — no migration/schema/backup-format change (D-02), no network on any read path (local-first), colours stay token-owned, animation stays on Reanimated (no React-state driving), and Plan 05→06 correctly serialize the shared Profile files. **No plan deletes, weakens, or inverts an ADR, HANDOFF, or D-NN decision** — every HIGH finding below is an *executable-correctness* defect caught pre-execution, not a decision reversal. That is the good news.

The bad news: several plans describe mechanisms that **do not match the code on disk**, and would fail at execution as written. Overall risk is **HIGH until the five blockers are corrected.**

### Agreed Strengths (both lanes)
- D-02 respected everywhere: no migration, no schema, no `BACKUP_FORMAT_VERSION` bump. Plan 06's temporal read is a bounded SELECT against the existing `current_state_entries` table (verified: it already carries `is_current` + `created_at`, `current-state-history-read.ts:9-18,67-79`).
- The D-07 false empty-state bug is real and correctly located: `ProfileModuleHost.tsx:113-116` returns `PROFILE_MODULE_EMPTY_SUMMARIES` unconditionally, unlike the conditional `contact-methods` sibling at `:117-120`.
- The Off Limits data-loss guard being ported is real and load-bearing (`EditContactScreen.tsx:289-296` forced kind, `:520` seed filter, `:804-808` defensive-re-filter comment).
- Timestamp foundation is correct: `parseLocalMs` (`dates.ts:25-72`) is UTC-safe; the three display offenders are accurately located (`profile-history-read.ts:72,81`; `interaction-detail-logic.ts:96`; `MemoryHistoryScreen.tsx:172`).
- Orrery surface seam (Plan 01/03) is correct: `GlassSurface.tsx:66` obtains opacity via `cardTintOpacity`; the treatment prop preserves the single ADR-087 component.

### Agreed Concerns (2+ lanes — highest priority)
1. **Plan 06 (HIGH):** the new `OffLimitsEditorScreen` route is added only to `navigation/types.ts` (typed), never registered as a `<Stack.Screen>` in the navigators that host Profile → route unnavigable, runtime throw.
2. **Plan 06 (HIGH):** the off-limits preservation test is placed at `fuel-dao.test.ts`, but the DAO is kind-agnostic; the data-loss control lives in the *screen*, so a DAO test cannot prove it.
3. **Plan 08 (HIGH):** `selectLine3` is the **List** selector; the Grid uses `selectCardLine3`, and `GridCard` consumes a precomputed `line3` prop (never calls a selector). The plan targets the wrong function and omits the host that computes `line3`.
4. **Plan 07 (HIGH):** orphan-stretch is scoped to the "trailing" orphan in a 2-column mental model, but `pack-overview` yields up to 3 columns and the dossier requires *any* row-local orphan (incl. before an intervening full-width card) to stretch.
5. **Plan 05 (HIGH):** the plan's verification names a nonexistent test file and proposes to unit-test private functions.

### Divergent Views
- **Plan 09 autonomy:** codex rated "cannot be reliably autonomous" (needs a physical Pixel + owner USB-auth) as HIGH. In *this repo's* context that is only MEDIUM — the owner has a documented agent-driven device pipeline (MEMORY: verify-ui-on-pixel-yourself, device-UAT run-as pattern). The residual actionable part is the `files_modified: []` vs declared outputs conflict, and framing the device leg as a checkpoint.
- **Plan 09 Metro port:** codex flagged the "8082 remap" as an unverified assumption. This is a **codex false-positive** — the port remap is a documented repo fact (MEMORY: orbit-metro-port-8082-remap; quest-board owns :8081). No plan change needed for the port.

# Findings requiring changes

## HIGH — Plan 06’s adapter test still does not prove the Off Limits write path is safe

The proposed pure adapter is the right layer for testing filtering and kind coercion, but the plan overclaims what that test proves.

`FuelEditor` delegates mutations through three callbacks supplied by the parent screen:

- `onAdd(draft)`
- `onEdit(id, patch)`
- `onDelete(id)`

See [FuelEditor.tsx](/home/bwales/projects/orbit-app/src/components/FuelEditor.tsx:97) and [FuelEditor.tsx](/home/bwales/projects/orbit-app/src/components/FuelEditor.tsx:494).

The new screen will then call standalone DAO functions directly. Those DAO operations mutate one row per transaction, including deletion by supplied `id` and `contactId` ([fuel-dao.ts](/home/bwales/projects/orbit-app/src/db/fuel-dao.ts:232)). A pure test of:

- `seedOffLimitsDraft`
- `forceOffLimitsKind`
- `filterOffLimitsWrite`

cannot prove that `OffLimitsEditorScreen`:

- applies `forceOffLimitsKind` before every `addFuel`/`editFuel`,
- only exposes IDs obtained from the filtered off-limits read,
- passes the correct `contactId`,
- reloads from the filtered result after each mutation,
- never calls `deleteFuel` for a non-off-limits ID.

The existing guarded implementation is safe because filtering, coercion, and the later diff input are joined inside the actual form path: filtering occurs in [EditContactScreen.tsx](/home/bwales/projects/orbit-app/src/screens/EditContactScreen.tsx:520), and add/edit mutations force `kind: "off_limits"` in [EditContactScreen.tsx](/home/bwales/projects/orbit-app/src/screens/EditContactScreen.tsx:806).

Plan 06 instead proposes a different persistence architecture—immediate standalone DAO writes—but tests only isolated transformations. The assertion that this “proves other fuel kinds survive an Off Limits add/edit/delete” is therefore false.

**Required change:** extract a node-testable Off Limits controller/handler layer used by `OffLimitsEditorScreen`, with injected read/add/edit/delete dependencies. Test the actual add/edit/delete handlers against a mixed-kind fixture and assert:

1. rendered/editor rows contain only `off_limits`,
2. add/edit DAO inputs always have `kind: "off_limits"`,
3. delete can only receive an ID from the filtered off-limits set,
4. non-off-limits records remain unchanged after all three operations.

A rendered-screen test with mocked DAOs would also work. Keep the physical-device DB check as a backstop, not the only end-to-end proof.

## MEDIUM — Plan 05’s stated tests cannot verify the header behavior

The source of the bug is private render logic:

- Their result is rendered directly as the header-adjacent caption in [ProfileModuleHost.tsx](/home/bwales/projects/orbit-app/src/components/profile/ProfileModuleHost.tsx:169).

- the header caption was removed,
- the header does not repeat its identifier as a caption,
- a nested heading is suppressed only when the parent owns the same heading,
- content state moved into the body.

The existing source-contract test only checks broad source tokens and does not cover heading ownership ([profile-knowledge-contract.test.ts](/home/bwales/projects/orbit-app/src/components/profile/profile-knowledge-contract.test.ts:11)).

The plan is also internally ambiguous: it says to remove header-adjacent metadata, but then says `topLevelSummary` and `knowledgeChildSummary` should return “an identifier (or empty).” Returning the section identifier while leaving the caption node intact would render, for example, “Things to Remember” as both heading and caption.

## MEDIUM — Plan 02 cannot test an unexported helper as written

Plan 02 says:

Avoid test-only mutable module state.

## LOW — Plan 01’s visibility ceiling is a policy assertion, not a perceptual proof

Keep the ceiling as a regression guard, but phrase the device UAT as the actual “still reveals the orrery” proof.
