<assumption_delta_decision>
Noun now primary: the contact-acquisition/SDK-routing seam (singular picker → plural "system | legacy" pickers).
Decision: **PROMOTE** a single shared seam. `contactImportMode(): "system" | "legacy"` (new `src/screens/use-contact-import-mode.ts`) replaces the boolean `useImportUnsupported()`; a single `startContactImport()` handler (new `src/services/import/start-contact-import.ts`) is the one dispatch site both entry points call. Neither entry point re-implements the `Build.VERSION.SDK_INT` branch.
Rationale: One branch in one place is the only way to keep the two pickers from drifting (the exact class of bug D-03/D-14 fix in the 17+ module). D-15 explicitly prefers a single shared seam over duplicating the branch.
Invariant test (this plan, Task 3), split to match the real path: (i) DISPATCH (unit-tested) — `startContactImport` calls `routePickedImport` for `mode==="system"` and `navigate("LegacyContactPicker", {})` for `mode==="legacy"` (it does not call the sink for legacy), proven in `start-contact-import.test.ts`; (ii) LEGACY HANDOFF — the legacy picker's Import action calls `routePickedImport` with the same `PickedContact[]` sink so both readers converge on one sink; the picker is a React component wiring an executor + navigation, so this handoff is NOT unit-provable here and is verified in device UAT (plan 05) — the unit test does not claim to cover it.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Android Contacts Provider → Orbit (native reader) | Untrusted external contact data crosses into Orbit under the OS READ_CONTACTS access-control boundary. |
| Native module → JS (`PickedContact[]`) | Contact fields + a `file://` cache photo path cross into JS; must carry no provider-internal URIs. |
| Orbit → (no network) | There is deliberately no egress boundary on this path; local-first. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-19.1-01 | Elevation/Policy | READ_CONTACTS declaration (module manifest) | high | mitigate | Declared `android:maxSdkVersion="36"` so it is inert on API-37 (D-02); requested only at the value moment (import). Generated-manifest drop verified at plan 19.1-05 (A3). |
| T-19.1-02 | Information disclosure | Contact PII / photos leaving device | high | mitigate | No network on the read/import path; reader is on-device ContentResolver only; no telemetry or content-carrying log (D-06, local-first). |
| T-19.1-03 | Tampering | Untrusted Event row poisoning `contacts.birthday` | medium | mitigate | Event branch gated on `Event.TYPE == TYPE_BIRTHDAY` (D-03); calendar validity enforced downstream by the strict birthday parser. |
| T-19.1-04 | Denial of service / correctness | Read failure silently swallowed → wrong/empty import mistaken for cancel | high | mitigate | ≤16 reader rejects on read error (D-14); the JS entry-point catch shows "Couldn't import contacts"; a genuine cancel returns `[]` (a no-op via routePickedImport). |
| T-19.1-05 | Information disclosure | Temp photo cache left readable | low | mitigate | Photos staged to app-private `context.cacheDir`, then moved to app-private staging by acceptPickedContacts; `allowBackup=false` already keeps them off adb backup. |

No new npm/pip/cargo packages are installed (native-extension path reuses the installed toolchain); no supply-chain (T-*-SC) gate applies.
