# Phase 19.1 — Seed context for discussion

> Read this before `/gsd-discuss-phase 19.1`. It captures everything decided so far so the discussion
> can focus on the open design questions, not re-derive the decision. Authoritative decision:
> **`docs/decisions/ADR-002-hybrid-two-picker-contact-import.md`**.

## The decision (already made — ADR-002)

Contact acquisition becomes a **hybrid two-picker**, routed on `Build.VERSION.SDK_INT`:
- **Android 17+ (API ≥ 37):** existing permissionless system picker (`modules/orbit-contact-picker`). No `READ_CONTACTS`. *(Stays in Phase 19; not this phase.)*
- **Android ≤ 16 (API < 37) — THIS PHASE:** `READ_CONTACTS` scoped `android:maxSdkVersion="36"` + a **custom in-app picker** over `ContactsContract`, reading full fields → the same `PickedContact[]`.

This **reverses** the Phase-19 "Android 17+ only / no `READ_CONTACTS`" locked decision. The reversal was the owner's call; rationale, rejected alternatives (pure-no-permission = too thin; broad `READ_CONTACTS` everywhere = Play-policy risk), and Play-policy compliance are all in ADR-002.

## Scope of Phase 19.1 (tight)

**In:** the ≤16 acquisition path only —
1. Manifest `READ_CONTACTS` with `maxSdkVersion="36"` (via app.config.ts / config plugin) + runtime permission request/handling. *(Native change → one desktop rebuild.)*
2. A custom picker UI: browse / search / **multi-select** over the device address book.
3. A native/JS read of the picked contacts' full data → `PickedContact[]` (shape in `src/services/import/import-acquire.ts:89` — `{displayName, methods:[{type,value}], birthday}` + photo staging). **Birthday must come only from `Event.TYPE == TYPE_BIRTHDAY`** (don't repeat the Android-17 module's bug of storing any Event as birthday).
4. SDK-level routing (17+ → system picker; ≤16 → custom picker); retire the `use-import-unsupported` "requires Android 17+" state.

**Done in Phase 19 (no longer pending):** the Android-17 picker path (19-12→19-20) and its device UAT (19-17) are **COMPLETE + verified** (2026-08-30). The picker dead-end was an orbit intent bug (wrong `USE_SYSTEM_CONTACTS_PICKER` extra namespace), fixed in gap plan 19-20 — see `../19-system-contact-import/19-ANDROID17-PICKER-ROOTCAUSE.md`. So there is no Android-17 work left to inherit; only the shared pipeline is reused.

**Carried-forward open items — FOLDED INTO 19.1 (owner call 2026-08-30):** see the dedicated section below.

**SHARED & unchanged (reused as-is):** the whole downstream pipeline — `import_sessions`/`import_session_rows`, review, cluster consolidation, complete, resume/discard, photo staging, birthday validation (Phase-19 plans 19-13→19-16 + the Import* screens). A session is picker-agnostic, so this path feeds the exact same flow.

## Carried-forward open items from Phase 19 (fold into 19.1 scope)

These are import-subsystem items left open when Phase 19 closed. They live in the **shared** pipeline / picker modules that 19.1 extends, so 19.1 is the right place to fix them. Full write-ups + verified file:line evidence: `../19-system-contact-import/19-DEVICE-UAT-FINDINGS.md`. Address them in the 19.1 plans (they are not new design, just known fixes):

1. **[MED-HIGH] #1 — Non-birthday Android Events stored as `contacts.birthday`.** `OrbitContactPickerModule.kt:149-150` (+ projection `:117-123`) maps **any** Event `DATA1` to `birthday` with no `Event.TYPE`/`DATA2` filter, so an anniversary can be stored as (and beat) the real birthday. **The new ≤16 custom reader MUST only accept `Event.TYPE == TYPE_BIRTHDAY`** (already flagged in Scope item 3) — and while here, fix the Android-17 module the same way so both readers are correct. Pairs with #6 below (under-inclusive birthday *formats*) — fix together.
2. **[MED] #2 — A picker read-exception silently discards the whole selection.** `OrbitContactPickerModule.kt:107-113` catches read failures into `resolve(emptyList())`; `routePickedImport` (`import-acquire.ts:161`) then treats `length===0` as a cancel — a degraded read looks like "nothing selected". Distinguish read-failure from cancel and surface an error. Applies to BOTH readers (the new ≤16 reader must not repeat it).
3. **[LOW-MED] #3 — Permanently-`failed` rows nag the resume prompt every launch.** `import-session-dao.ts:418-423` + `import-session-read.ts:101-108`: `finalizeSessionIfTerminal` counts `'failed'` as unresolved, so a name-required (nameless) row keeps the session `pending` forever and `getResumableSession` re-offers it every launch — only Discard exits. Provide a skip/terminalize path (or auto-terminalize name-required). Shared logic, so it affects both pickers.
4. **[LOW / UX] Single-import "Already in Orbit" terminal screen dead-ends.** Observed in the 19-17 UAT: a single import that resolved to already-linked showed only "VIEW CONTACT" with no Done/close, and hardware Back did not dismiss it. Give it a clear exit. Shared Import* screen.

*(Also see the reviewer-reported LOW items #4-#7 in `19-DEVICE-UAT-FINDINGS.md` — e.g. #6 unparseable birthday formats, which pairs with #1 — worth a conscious decision during 19.1 planning.)*

## Open questions for the discussion (the real design work)

1. **Custom picker UX:** full custom list/search UI vs. a lighter approach? Multi-select interaction, selection cap (the pipeline handles bulk; any UI limit?), empty/loading/large-address-book performance.
2. **`READ_CONTACTS` denial handling:** if the user denies, what happens? Options: fall back to the permissionless **single-field `ACTION_PICK`** (name + one phone — see spike), show a calm "permission needed" state, or a re-request rationale. Decide the graceful path.
3. **Permission rationale copy** (pre-prompt explainer) — theme-tokened, honest about "reads your contacts to import the ones you pick; nothing leaves the device."
4. **Reader implementation:** native (extend/add to `orbit-contact-picker`, or a new module) vs. a JS `ContactsContract` read via an existing bridge — and how to read multiple methods + birthday(Event TYPE) + photo efficiently, mapping to `PickedContact[]`.
5. **Routing seam:** where the SDK gate lives (currently `isContactPickerAvailable` returns SDK≥37) and how `AddSpeedDialFab` / Settings entry points call the right picker.
