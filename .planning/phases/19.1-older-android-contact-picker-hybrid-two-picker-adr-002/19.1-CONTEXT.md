# Phase 19.1: Older-Android Contact Picker (Hybrid two-picker, ADR-002) - Context

**Gathered:** 2026-08-30
**Status:** Ready for planning

<domain>
## Phase Boundary

Build **only** the Android ≤ API 36 half of the hybrid two-picker contact acquisition
decided in **ADR-002**, so contact import works on Android 14/15/16 (e.g. the Pixel 3a),
not only Android 17.

On ≤16: declare `READ_CONTACTS` scoped `android:maxSdkVersion="36"` (inert on API-37,
Play-policy compliant) + a **custom in-app picker** — our own searchable, multi-select list
UI over `ContactsContract` — that reads full fields (multiple phones/emails, birthday **only**
from `Event.TYPE == TYPE_BIRTHDAY`, photo) and maps them to the **same `PickedContact[]`**
the existing pipeline consumes. Route by `Build.VERSION.SDK_INT` (17+ → existing system
picker; ≤16 → custom picker) and retire the "requires Android 17+" unsupported state.

**Explicitly in scope:** the ≤16 acquisition path (manifest permission + runtime request/handling,
custom picker UI, the `ContactsContract` reader → `PickedContact[]`, SDK routing) **plus** the four
carried-forward Phase-19 import-subsystem items folded in by owner call (see Decisions D-11..D-14).

**Explicitly out of scope (LOCKED, do not touch):**
- The **Android-17 system-picker path** — Phase 19 owns it; its CODE is complete, but the API-37 system
  picker is **NON-FUNCTIONAL on the Pixel 6** — an OS-level dead-end (per the device UAT / ADR-002), NOT
  "verified working on the Pixel 6". It remains **out of 19.1 scope** either way. (One code-quality fix to
  the Android-17 Kotlin module's birthday filter is docketed to the Phase-19 finish per ADR-002; 19.1 only
  guarantees the *new* ≤16 reader is correct from the start — see D-13.)
- The **entire downstream import pipeline** (import sessions, review, cluster consolidation, completion,
  resume/discard, photo staging, birthday validation — Phase-19 plans 19-13→19-16). It is SHARED and
  consumes `PickedContact[]` regardless of source; changes here are limited to the fix-call items below,
  which live in that shared pipeline by owner ruling.
- iOS (v1 deferral stands).

</domain>

<decisions>
## Implementation Decisions

Decisions D-01..D-08 come from ADR-002 / the SEED and are recorded here as the locked
frame the discussion built on; D-09..D-14 are the choices made in this discussion.

### Locked by ADR-002 / SEED (not re-litigated)
- **D-01:** Hybrid two-picker routed on `Build.VERSION.SDK_INT` — 17+ → existing system picker; ≤16 → custom picker. — **Reversibility:** one-way — recorded in ADR-002, which itself reverses the Phase-19 "Android 17+ only" decision; reversing again is an owner-only ADR action.
- **D-02:** `READ_CONTACTS` declared scoped `android:maxSdkVersion="36"` (inert on API-37). — **Reversibility:** one-way — Google Play Contacts policy (effective 2027-01-27) is the reason for the scoping; broadening it is a distribution-risk decision, owner-only.
- **D-03:** Birthday accepted **only** from `Event.TYPE == TYPE_BIRTHDAY` (never any Event row). Locked by ADR-002 + carried-forward fix #1.
- **D-04:** Reader maps to the **same `PickedContact[]`** shape (`{ lookupKey, displayName, methods:[{type,value}], birthday, photoTempUri }`) so the shared pipeline is unchanged.
- **D-05:** The "Contact import requires Android 17+" unsupported state is retired; ≤16 is now supported.
- **D-06:** Local-first preserved — no network on any import path; the permission only reads on-device.

### Custom picker UX
- **D-09:** **Multi-select via a checkbox list + a persistent "Import (N)" button.** No selection cap — honor the incremental pipeline (Phase-19 criterion: no arbitrary app-level cap; the Android-17 path's `SELECTION_LIMIT 100` is an OS constraint there, not our policy). Search-as-you-type matches **name + phone/email**. Rows show **avatar (photo or initials) + display name + primary method** as subtitle; photo loading is virtualized (FlatList) to keep the list smooth on a large address book. — **Reversibility:** reversible — one screen.
- **D-10:** **Build the picker standalone on theme tokens**, as a functionally distinct *utilitarian* selectable list — NOT coupled to today's dashboard/orrery components (the dashboard is being redone next milestone). Keep the **data source (`ContactsContract` read) and selection state as plain logic, decoupled from presentation**, so a later reskin is a single-screen, token-level change and the dashboard redesign neither drags this along nor is blocked by it. Same visual language (tokens), different layout pattern. — **Reversibility:** reversible — decoupling is the whole point.

### Permission handling
- **D-11a:** **On deny → calm in-app state + re-request.** Show a friendly, non-blocking explainer with a "Grant access" button that re-requests `READ_CONTACTS`. **No single-field `ACTION_PICK` fallback** — the thin name+one-phone path was rejected (guts methods/birthday/photo, adds a confusingly degraded second code path).
- **D-11b:** **On permanent denial** ("Don't ask again" / OS won't re-prompt) → detect it and switch the action to **"Open Settings"**, deep-linking to Orbit's app-info permissions page (standard Android pattern).
- **D-11c:** **Prime before the OS dialog on first request** — show an in-app pre-permission explainer ("Continue" → OS dialog) to reduce accidental permanent denials. Copy is **plain + privacy-forward** ("Orbit reads your contacts so you can pick which to import — nothing leaves your device"), theme-tokened; **final wording tuned during build.**

### Carried-forward fix calls (shared pipeline; apply to both pickers)
- **D-12:** **Nameless (name-required) rows auto-terminalize as "skipped".** A picked contact with no usable name is automatically moved to a terminal skipped state so the session can finalize (fixes the resume-prompt nag: `import-session-dao.ts:418-423` / `import-session-read.ts:101-108` count `failed` as unresolved forever). Report the count in the completion summary ("N skipped — no name"). No user action required; no dead-end.
- **D-13:** **Birthday parsing broadened + still-unparseable flagged.** Broaden the birthday parser to accept common Android formats including **year-less `--MM-DD`**; anything still unparseable produces a **review-screen error state** (flag, not silent-drop, not coerce — consistent with 19-13's typed-birthday handling and the custom-fields "flag, don't coerce" philosophy). Pairs with D-03 (`Event.TYPE` gating). Applies to both readers; the new ≤16 reader implements it from the start.
- **D-14:** **A picker read-exception must be distinguishable from a cancel.** (Carried-forward #2.) The ≤16 reader must NOT collapse a read failure into an empty result the way `OrbitContactPickerModule.kt:107-113` → `routePickedImport` (`import-acquire.ts:161`, `length===0` = cancel) does — surface a read error instead of silently discarding the selection.
- **D-14b (UX, carried-forward #4):** The single-import "Already in Orbit" terminal screen must have a clear exit (Done/close + working hardware Back); it currently dead-ends. Shared Import* screen.

### Claude's Discretion (delegated to research/planning)
- **Reader implementation:** native (extend the existing `orbit-contact-picker` Kotlin module — its `ContactsContract.Data` read logic is ~90% reusable, just swap the session-URI query for a full-provider query + add the `Event.TYPE` filter) **vs.** a new module **vs.** a JS `ContactsContract` read. Owner accepts the one-desktop-rebuild cost of a native change. Researcher/planner to choose on merit (perf of reading multiple methods + birthday + photo efficiently, maintenance).
- **Routing seam:** where the SDK gate lives (today `isContactPickerAvailable()` returns SDK≥37; `useImportUnsupported()` gates the two entry points) and exactly how `AddSpeedDialFab.tsx` and `SettingsScreen.tsx` dispatch to the right picker. Prefer a single shared seam over duplicating the branch in two components.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`PickedContact[]` contract** (`modules/orbit-contact-picker/index.ts`): the fixed integration boundary — the ≤16 reader must produce exactly this shape; everything downstream is then free.
- **Existing Kotlin read logic** (`OrbitContactPickerModule.kt`): projection + mimetype grouping (`Phone`/`Email`/`Event`/`Photo`) + `file://` cache-photo staging is directly reusable for a full-provider query.
- **`routePickedImport` / `acceptPickedContacts`** (`import-acquire.ts`): picker-agnostic session acceptance + cardinality routing (single → `ImportReview`, bulk → `BulkImportSetup`). The ≤16 picker plugs in here unchanged.
- **`dashboard-search-row-logic.ts`** exists — a search-row pattern to mirror for the picker's search field.

### Established Patterns
- **Theme tokens are mandatory** — no hardcoded colors anywhere (CLAUDE.md); the picker is fully token-driven (enables the cheap-reskin decision D-10).
- **`useImportUnsupported()`** is the single capability gate both entry points share; the routing seam should stay single-sourced (D-15 discretion).
- **`use-import-leave-guard` defines "unresolved" by `row_status`** (19-14) — the D-12 auto-terminalize must set a `row_status` the leave-guard and `finalizeSessionIfTerminal` treat as terminal.
- **Migrations are forward-only, code-shipped, irreversible** (CLAUDE.md). If D-12's "skipped" state needs a new `row_status` value or the reader needs schema, add a new migration (as of P19, head is 011 / TARGET_VERSION 11 — verify vs disk, never assume head+1).

### Integration Points
- Manifest `READ_CONTACTS` (`maxSdkVersion="36"`) via `app.config.ts` / config plugin → native change → one desktop rebuild.
- SDK routing at `AddSpeedDialFab.tsx` + `SettingsScreen.tsx` (via a shared seam replacing `useImportUnsupported`).
- The ≤16 reader → `PickedContact[]` → `routePickedImport` → the shared pipeline.

</code_context>

<specifics>
## Specific Ideas

- Owner initially assumed "custom picker" meant wiring Orbit to a Google-provided picker; clarified that below API 37 no rich system picker exists, so the picker UI is genuinely ours over `ContactsContract` data. Owner accepted the added scope.
- Owner's framing on distinctiveness: the picker should be **clearly Orbit** (tokens) but **functionally distinct** from the dashboard (a "tool" list, not the home/orrery experience), and must not be coupled to dashboard components that change next milestone.
- Testing device: the **Pixel 3a (Android 14/15)** is the primary UAT device for this path; build/install per `docs/runbooks/desktop-build-pipeline.md`. This path's 3a UAT also validates Phase-19 19-17 Tasks 2–3 (shared downstream flows) for real.

</specifics>

<deferred>
## Deferred Ideas

- **Bulk unparseable-birthday review items → Phase 20 (Contact Reconciliation & Merge).** Added
  after planning (2026-08-30, owner ratification of plan-checker Warning 1). D-13 says an unparseable
  birthday is flagged, never silently dropped. Phase 19.1 delivers this on the single-import review
  path (`birthdayInvalid`) and, on the bulk path — which has no per-row review screen yet — surfaces a
  distinct "N birthdays couldn't be read" count on the completion summary (read-only over the raw
  `source_payload`, no migration). The owner's desired end-state — surfacing each unparseable birthday
  as a per-item review case *alongside* other review cases so the user can fix it — needs a durable
  bulk review surface (the raw value is already retained in `source_payload`; the resolve UI is not
  built). That is Phase-20 scope. **This is a recorded, owner-approved deferral, not a silent gap.**

No single-field `ACTION_PICK` fallback was adopted; it was considered and rejected in D-11a, not
deferred.

</deferred>
