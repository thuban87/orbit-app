# Cross-AI Plan Review — Phase 19.1

## Consensus Summary

Both source-grounded reviewers (Codex and Cursor) independently verified the five plans against the
actual repo and reached the same top-line verdict: the plan set is unusually well grounded — file
references, line numbers, and defect diagnoses match what is on disk, the wave ordering is coherent,
and scope boundaries respect ADR-002 (≤16 acquisition + shared-pipeline fixes, not a pipeline
rewrite). Overall risk is **MEDIUM** by both accounts, concentrated in native Kotlin correctness,
permission UX on real Android 14/15 hardware, and the device-UAT gate — not in the design itself.

### Agreed Strengths

- **Accurate defect diagnosis.** Both confirmed the two Kotlin bugs (untyped `Event`→birthday at
  `OrbitContactPickerModule.kt:158`, and the read-error swallow at `:116`) and the D-12 resume-nag
  chain (`import-driver.ts` marking nameless rows `failed` vs `finalizeSessionIfTerminal` /
  `UNRESOLVED_ROW_STATUSES` treating `failed` as unresolved).
- **Shared routing seam is the right abstraction.** Both endorsed replacing `useImportUnsupported()`
  with `contactImportMode()` + `startContactImport()` to prevent two-entry-point drift.
- **Two-query summary read (plan 03) is necessary, not over-engineering.** Both agreed a Data-table-only
  query cannot return name-only contacts, so the Contacts.CONTENT_URI + phone/email merge is correct.
- **D-13/G1 birthday-seed fix and D-14b already-linked dead-end fix are verified real bugs** with sound fixes.
- **Manifest-policy verification split (A3a packaging grep vs A3b API-37 runtime) is well designed.**
- **Honest scoping / explicit deferrals** (Phase-20 bulk birthday review, no ACTION_PICK fallback,
  Vitest vs device-UAT split) reduce scope creep.

### Agreed Concerns

- **HIGH — Session finalization / resume-nag not actually closed by a status string alone (D-12).**
  Codex: `runImportBatch()` never calls `finalizeSessionIfTerminal()`; a crash before ImportComplete
  loads recreates the re-nag. Cursor frames the adjacent risk as the nameless-photo staging leak.
  Both converge on: the fix must be enforced structurally, not left to a status change / executor choice.
- **HIGH — Nameless bulk photo staging is a live PII leak today (F12).** Cursor: `acceptPickedContacts`
  stages photos for every picked contact before nameless classification; "classify-before-staging"
  should be a hard requirement, not optional cleanup. Codex raises the same staged-photo cleanup gap
  (MEDIUM) with no concrete atomic ordering in the task.
- **HIGH/MEDIUM — Native chunking + selected-order preservation is under-specified and untested.**
  Codex: chunking ownership is internally inconsistent (JS vs native) and must be made singular.
  Cursor: cross-chunk ordering / dropped keys only surface on large multi-select on the 3a (the D-09
  "no cap" scenario) and are deferred to device UAT.
- **MEDIUM — Permission permanent-denial state model is incomplete (plan 04).** Both note that relying
  on `PermissionsAndroid.check()` / `NEVER_ASK_AGAIN` alone leaves a re-request loop after "Don't ask
  again" or on OEM builds that return `DENIED`; needs durable prior-result state or a fallback UX.
- **MEDIUM — Plan 01 tracer's full-book `readAllContacts()` is a privacy/perf hazard until plan 03 lands**
  (OOM / JS-thread block on a large book on the Pixel 3a); acceptable only if waves merge quickly.
- **MEDIUM — Device-UAT determinism / fixtures (plan 05).** Codex: the in-flight-revoke read-failure
  test is race-dependent (proposes load→revoke→Import instead); one address book can't be
  simultaneously empty and hold all fixtures. Both want measurable thresholds for "large book / no cap."
- **MEDIUM — Settings error parity (F7).** Both note Settings only `Logger.error`s while the FAB shows
  an Alert; parity should be centralized in `startContactImport` or API-37 silent failures persist.

### Divergent Views

- **Cursor uniquely flags a doc contradiction:** `19.1-CONTEXT.md` line 25 claims the Android-17 path
  is "COMPLETE + verified on the Pixel 6," contradicting ADR-002 / device-UAT findings that record it
  non-functional on the owner's API-37 device — a risk to executors who read CONTEXT before the ADR.
  Codex did not raise this.
- **Cursor uniquely warns the HANDOFF.md supersession target may be thin** (no "Android 17+ /
  READ_CONTACTS" wording found there; the locked decision may live only in phase-19 artifacts), so
  plan 05's supersession note may need a wider search. Codex did not raise this.
- **Codex uniquely flags** `startContactImport` **duplicating region/time acquisition** in the legacy
  screen (behavior drift between system and legacy entry paths). Cursor did not raise this.
- **Codex weights the D-12 finalization gap as the central HIGH risk** (plan 02 "not achieved by
  changing one status string"); Cursor's top HIGH is the F12 photo-staging PII leak. Complementary
  rather than contradictory — different facets of the same execution-discipline concern.

## Codex Review

# Plan Review — Phase 19.1

## Overall summary

The plan set is unusually well grounded in the existing import architecture: it preserves the established `PickedContact[] → routePickedImport()` boundary, reuses the native reader, and correctly identifies several real defects. The primary issues are execution gaps around bulk-session finalization, native selected-key chunking, permission-state persistence, and making device UAT reproducible.

## Plan 01 — Tracer

### Strengths

- Correctly preserves the picker-agnostic handoff: `routePickedImport()` already routes empty selections as cancel and creates a single or bulk session by cardinality ([import-acquire.ts:153](src/services/import/import-acquire.ts:153)).
- The birthday defect is real: the current reader maps every `Event` row to `birthday` without checking `Event.TYPE` ([OrbitContactPickerModule.kt:158](modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:158)).
- The read-error defect is real: the Android-17 path currently converts any native reader error to an empty result ([OrbitContactPickerModule.kt:116](modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:116)), which the router treats as cancellation ([import-acquire.ts:161](src/services/import/import-acquire.ts:161)).
- Using a module manifest is appropriately localized; the existing module manifest is already merged into the app ([AndroidManifest.xml:1](modules/orbit-contact-picker/android/src/main/AndroidManifest.xml:1)).

### Concerns

- **MEDIUM — The plan calls this a “selected contact(s)” reader, but its tracer reads the entire provider, including full photos, before the user selects anything.** The current acceptance path stages each returned photo into durable document storage before creating the import session ([import-acquire.ts:69](src/services/import/import-acquire.ts:69), [import-acquire.ts:77](src/services/import/import-acquire.ts:77)). This is acceptable only as a short-lived tracer; it needs an explicit cleanup/replacement condition before Plan 03.
- **MEDIUM — `startContactImport` duplicates region/time acquisition in the legacy screen.** Current callers correctly get settings and snapshot the time once immediately around acquisition ([AddSpeedDialFab.tsx:63](src/components/AddSpeedDialFab.tsx:63)). Re-fetching it in a later screen can cause behavior to differ between system and legacy entry paths, especially if settings change while the picker is open.

### Suggestions

- Define the tracer as intentionally temporary and require Plan 03 to remove full-book photo staging before phase completion.
- Pass `effectivePhoneRegion` and a capture timestamp via the legacy route, or define why the fresh value is preferable and test parity with the system route.

### Risk assessment

**MEDIUM.** The vertical slice is sound, but its temporary all-contact full read is privacy/performance-expensive until Plan 03 lands.

## Plan 02 — Shared pipeline fixes

### Strengths

- It correctly recognizes that `skipped` is already terminal: the session finalizer treats only `pending`, `needs_review`, and `failed` as unresolved ([import-session-dao.ts:418](src/db/import-session-dao.ts:418)); the leave guard uses the same set ([import-leave-guard-logic.ts:7](src/screens/import-leave-guard-logic.ts:7)).
- The current bug is confirmed: nameless bulk rows are marked `failed` ([import-driver.ts:76](src/services/import/import-driver.ts:76)).
- The birthday validation boundary is good: `isValidStoredBirthday()` uses strict calendar parsing ([birthday-logic.ts:79](src/logic/birthday-logic.ts:79)), while the current import mapper only accepts hyphenated formats ([picked-contact-map.ts:28](src/logic/picked-contact-map.ts:28)).
- The already-linked dead-end diagnosis is accurate: the review screen routes only through an Alert ([ImportReviewScreen.tsx:231](src/screens/ImportReviewScreen.tsx:231)), while the existing completion screen already provides a reset-to-Home Done action ([ImportCompleteScreen.tsx:234](src/screens/ImportCompleteScreen.tsx:234)).

### Concerns

- **HIGH — Changing the row to `skipped` does not itself finalize the session.** `runImportBatch()` finishes by returning summary counts and never invokes `finalizeSessionIfTerminal()` ([import-driver.ts:123](src/services/import/import-driver.ts:123), [import-driver.ts:198](src/services/import/import-driver.ts:198)). Today the finalizer is called later, when `ImportCompleteScreen` loads ([ImportCompleteScreen.tsx:33](src/screens/ImportCompleteScreen.tsx:33)). If the process exits after the driver runs but before that screen runs, `getResumableSession()` selects any pending session without inspecting rows ([import-session-read.ts:97](src/db/import-session-read.ts:97)), recreating the exact re-nag risk this plan claims to solve.
- **MEDIUM — The required staged-photo cleanup has no concrete implementation path in the task.** Staging happens before a row is inserted ([import-acquire.ts:76](src/services/import/import-acquire.ts:76)); cleanup exists as `deleteImportStaging()` ([photo-storage.ts:267](src/services/photos/photo-storage.ts:267)), but the task neither includes that module nor specifies an atomic ordering for deleting/clearing `photo_rel_path`.
- **LOW — Completion counts need a row-level partition test, not just separate count tests.** The current summary query groups by only status and match outcome ([import-session-read.ts:216](src/db/import-session-read.ts:216)); adding name-required and unreadable-birthday categories requires testing that categories remain mutually exclusive.

### Suggestions

- Make `runImportBatch()` call `finalizeSessionIfTerminal()` after processing rows, before returning. Test a process-restart simulation: bulk driver completes, then `getResumableSession()` returns `null` without opening `ImportComplete`.
- Choose one explicit PII-safe design: classify nameless bulk contacts before staging, or delete staging and retire/clear the database path in a defined order.
- Add a summary-partition fixture covering imported, already-linked, user-skipped, name-required-skipped, failed, and birthday-unreadable rows.

### Risk assessment

**HIGH** until session finalization is moved into the batch completion path. This is the central D-12 promise and is not achieved merely by changing one status string.

## Plan 03 — Custom picker

### Strengths

- The two-query summary design addresses a real provider-shape issue. A `Data`-table-only query cannot include contacts that have no matching data rows; the existing native reader is entirely Data-row based ([OrbitContactPickerModule.kt:125](modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:125)).
- The proposed separate pure source/selection modules are well scoped and testable, consistent with existing pure mapping logic ([picked-contact-map.ts:44](src/logic/picked-contact-map.ts:44)).
- The plan correctly avoids passing external thumbnail URIs into the existing persisted-photo flow, whose documented contract expects a staged cache value to be moved before persistence ([index.ts:13](modules/orbit-contact-picker/index.ts:13)).

### Concerns

- **HIGH — The chunking ownership is internally inconsistent.** The task says native `readAllContacts(lookupKeys)` must chunk and execute provider reads, but also says JS forms chunk boundaries and native executes one read “per chunk boundary.” Neither the proposed public wrapper nor the route contract states which layer loops, merges results, deduplicates keys, or restores selected order. This is essential because the existing wrapper exposes only `pickContacts()` ([index.ts:35](modules/orbit-contact-picker/index.ts:35)).
- **MEDIUM — The full-reader behavior for a selected contact missing from the provider is unspecified.** A contact may disappear between summary read and import. The plan must say whether it is omitted, reported as an error, or converted to a row failure; otherwise selection count and imported count diverge silently.
- **MEDIUM — The plan needs a list-load cancellation guard.** A `listContactsSummary()` promise can resolve after navigation away or after a permission state changes; the existing codebase uses mounted/active guards around async screens ([ImportProgressScreen.tsx:22](src/screens/ImportProgressScreen.tsx:22)). The plan does not mention one for the new screen.

### Suggestions

- Select one design:
  - JS chunks keys and calls a native `readContactsByLookupKeys(chunk)` function; JS performs ordered merge; or
  - native receives all keys and wholly owns chunking/merge/order, with native instrumentation/UAT evidence.
  
  Do not split the same responsibility across both.
- Define source-disappearance semantics explicitly and surface a calm count/error.
- Require a cancellation/active guard for permission and summary-load effects.

### Risk assessment

**HIGH** until the chunking contract is made singular and testable. It is a correctness and scalability boundary for the no-cap requirement.

## Plan 04 — Permission UX and routing cutover

### Strengths

- It correctly removes the obsolete gate used by both entry points: the FAB currently blocks on `useImportUnsupported()` ([AddSpeedDialFab.tsx:55](src/components/AddSpeedDialFab.tsx:55)), and Settings disables its row ([SettingsScreen.tsx:755](src/screens/SettingsScreen.tsx:755)).
- It improves an actual error-parity gap: the FAB shows an alert on acquisition failure ([AddSpeedDialFab.tsx:78](src/components/AddSpeedDialFab.tsx:78)), while Settings only logs it ([SettingsScreen.tsx:172](src/screens/SettingsScreen.tsx:172)).
- Avoiding a fabricated rationale API in TypeScript is prudent, and a narrow classifier is easy to unit-test.

### Concerns

- **MEDIUM — The plan has no durable state that distinguishes first entry, ordinary denial, and a previously observed permanent denial after the screen is reopened.** `PermissionsAndroid.check()` only answers granted/not-granted in the proposed shape. Without persisting at least the prior request result, returning later after “Don’t ask again” will re-show the primer and require another request before the screen can show “Open Settings,” rather than immediately rendering the permanent-denial state.
- **LOW — “Ask once, no nag loop” conflicts with the required explicit re-request affordance unless the wording is narrowed.** D-11a intentionally allows a user-initiated retry. The plan should define “no automatic re-prompt,” not prohibit deliberate retries.

### Suggestions

- Persist the last request classification, or document an intentional transient-only policy and ensure an immediate re-request result transitions deterministically to Open Settings.
- Use `useFocusEffect` for the Settings-return check, matching the project’s established focus-refresh pattern ([SettingsScreen.tsx:4](src/screens/SettingsScreen.tsx:4)).

### Risk assessment

**MEDIUM.** The proposed visible states work in one screen session, but reopening after denial needs a defined state model.

## Plan 05 — Build and device UAT

### Strengths

- Separating generated-manifest packaging from API-37 runtime behavior is excellent. It avoids treating a manifest grep as proof of effective permission behavior.
- It appropriately requires real hardware for native provider, permission, and rendering/performance claims.
- It correctly retains `TARGET_VERSION = 12` as the migration invariant ([database.ts:47](src/db/database.ts:47)).

### Concerns

- **HIGH — The read-failure test is not reliably reproducible as written.** “Revoke while a read is in flight” is race-dependent. The legacy screen’s full read occurs only after selection, unlike its initial list read; a precise sequence—load list, revoke permission, press Import—would be deterministic. A debug-only fault hook would require code changes, but Plan 05 lists documentation files only.
- **MEDIUM — The same physical address book cannot simultaneously be empty and contain the required birthday, nameless, name-only, and large-book fixtures.** The UAT plan needs a concrete isolation/reset procedure, second user profile/device, or explicitly separate runs.
- **MEDIUM — “Large book scrolls smoothly” and “no selection cap” need measurable test conditions.** Define approximate fixture size, selected count, and an observable threshold or at least a reproducible manual protocol.

### Suggestions

- Replace the in-flight revoke race with: load the summary list while granted → select one contact → revoke `READ_CONTACTS` via adb → press Import → assert the full-read error surface. This directly exercises the D-14 catch path.
- Add fixture lifecycle instructions: temporary account/profile, creation steps, cleanup, and how the empty-book case is run independently.
- Record only redacted/pass-fail evidence in committed UAT documents; birthday values and contact names should not be captured.

### Risk assessment

**MEDIUM.** The gate is well designed, but D-14 and empty-book UAT are not yet deterministic enough to be credible release evidence.

# Cross-AI Plan Review: Phase 19.1 — Older-Android Contact Picker (ADR-002)

## 1. Summary

These five plans are unusually well-grounded in the actual codebase: file references, line numbers, and defect descriptions match what is on disk (verified against `OrbitContactPickerModule.kt`, `import-driver.ts`, `import-acquire.ts`, `picked-contact-map.ts`, `ImportReviewScreen.tsx`, `AddSpeedDialFab.tsx`, `SettingsScreen.tsx`, and related import-session code). The wave ordering (tracer → parallel pipeline fixes → rich picker → permission/routing → device UAT) is coherent, scope boundaries respect ADR-002, and the plans correctly treat Phase 19.1 as ≤16 acquisition plus shared-pipeline fixes—not a rewrite of the downstream import pipeline. Residual risk is concentrated in native Kotlin correctness, permission UX edge cases on real Android 14/15 hardware, and the heavy device-UAT gate in plan 05; the plans acknowledge these explicitly rather than papering over them.

---

## 2. Strengths

- **Accurate diagnosis of existing defects.** Plan 01 correctly identifies the two Kotlin bugs to avoid reintroducing: untyped Event→birthday at `OrbitContactPickerModule.kt:158-159` and read-error swallow at `:116-121`. Plan 02 correctly traces the resume nag to `importRowAsNew` marking nameless rows `"failed"` (`import-driver.ts:79-80`) while `finalizeSessionIfTerminal` treats `"failed"` as unresolved (`import-session-dao.ts:418-420`), matching `UNRESOLVED_ROW_STATUSES` in `import-leave-guard-logic.ts:7-11`.

- **Shared routing seam is the right abstraction.** Replacing `useImportUnsupported()` (currently `!isContactPickerAvailable()` at `use-import-unsupported.ts:8-9`, gating both `AddSpeedDialFab.tsx:56-58` and `SettingsScreen.tsx:156/759-769`) with `contactImportMode()` + `startContactImport()` prevents the two-entry-point drift called out in ADR-002 and 19.1-CONTEXT D-15.

- **Two-query summary read (plan 03) is necessary and well-motivated.** A single `MIMETYPE IN (...)` pass over `ContactsContract.Data` cannot return name-only contacts (no Data rows). The plan’s Query (1) `Contacts.CONTENT_URI` + Query (2) phone/email merge is the correct fix for F11/G3; this is not over-engineering.

- **D-13 birthday fix targets a real G1 regression.** `ImportReviewScreen.tsx:145` currently seeds `birthdayInput` from `mapped.birthday ?? ""`. When `mapBirthdayForStorage` (`picked-contact-map.ts:28-38`) returns `null` for slash OEM formats, the review screen shows an empty field instead of flagging the raw value—because `normalizeEditedBirthday` only accepts hyphenated forms (`birthday-logic.ts:33-34`). The proposed `mapped.birthday ?? snapshot.birthday ?? ""` seed is the correct fix, verified against the parser chain.

- **D-14b addresses a verified dead-end.** The already-linked branch (`ImportReviewScreen.tsx:231-248`) shows a single-button Alert while `load()` selects `rows.find(candidate => candidate.contactId === null)` (`:117`)—`resolveAlreadyLinked` leaves `contact_id` NULL, so dismissal reloads the same state. Routing to `ImportComplete` with a scoped “View contact” action is sound.

- **Policy verification is split correctly (A3a vs A3b).** Plan 05’s distinction between generated-manifest packaging grep and runtime permission-state on API 37 (`dumpsys package` / `pm`) avoids a known false-failure mode when `maxSdkVersion` metadata still appears in package listings.

- **Explicit deferrals and prohibitions reduce scope creep.** Phase-20 deferral for durable unparseable-birthday bulk review, explicit non-fix of the 17+ read swallow (plan 02 `<deferred>`), no `ACTION_PICK` fallback (plan 04), no dashboard coupling (plan 03 D-10), and the plan 01 blocking checkpoint for one-way ADR decisions are all appropriate guardrails.

- **Test strategy matches what Vitest can actually prove.** Plans consistently separate unit-testable dispatch logic (`start-contact-import.test.ts`) from React handoff and native chunk merge (deferred to plan 05 device UAT)—honest scoping, not false confidence.

## 3. Concerns

### HIGH

- **Bulk nameless photo staging is a live PII leak today and easy to miss in execution.** `acceptPickedContacts` (`import-acquire.ts:77-84`) stages photos for every picked contact before any nameless classification. Plan 02 Task 1 flags F12 but leaves “classify before staging OR clean up on skip” to executor choice. If implementers pick the cleanup path and miss edge cases (partial staging failure, retry paths), orphaned staged photos remain on disk for terminal nameless bulk rows. This should be treated as a hard requirement, preferably “classify name before staging” in `acceptPickedContacts` or a dedicated pre-pass—not optional cleanup.

- **API-37 import remains broken on the owner’s hardware; phase success must not be misread.** ADR-002 and plan 05 correctly scope sign-off to ≤16 IMP-01 + A3b—not “import works everywhere.” However, plan 04 retires the unsupported state on all devices and routes API ≥37 to the system picker (`isContactPickerAvailable()` → SDK ≥37 at `OrbitContactPickerModule.kt:63-64`). On the owner’s Pixel 6 Pro the system picker is OS-dead; users still get silent failure via empty resolve or the unfixed `:118-120` swallow. Plans document this, but executors must not conflate “phase complete” with “IMP-01 satisfied on API 37.”

- **Plan 01 tracer uses full-book `readAllContacts()` before plan 03’s two-tier read.** Between plans 01 and 03 landing, the minimal picker reads the entire provider for list rendering. On a large address book this could OOM or block the JS thread on the Pixel 3a. Acceptable for a short-lived tracer if waves merge quickly; risky if plan 03 slips.

### MEDIUM

- **Permanent-denial detection relies solely on `NEVER_ASK_AGAIN` (plan 04).** The plan correctly avoids `shouldShowRequestPermissionRationale` (absent from installed RN typings) but on some OEM Android 14/15 builds the second deny may still return `DENIED`, not `NEVER_ASK_AGAIN`, leaving users in a re-request loop until the OS escalates. A1 device confirmation is scheduled but the plan has no fallback UX if A1 fails (e.g., surfacing Settings after N denies without calling it “permanent”).

- **Plan 02 double-count partition is subtle.** `sessionSummaryCounts` (`import-session-read.ts:238-243`) already buckets non-`already_linked` `"skipped"` rows into `failedOrSkipped`. Adding distinct “N skipped — no name” and “N birthdays couldn’t be read” lines requires careful exclusion logic; the plan specifies this (F9/G12) but a naive implementation will double-count or accidentally wire birthday-unreadable into `hasFailures` (`ImportCompleteScreen.tsx:45`, driven by `rawCounts.failed > 0`).

- **Native chunk merge + selected-order preservation is untested in Vitest (G6).** Plan 03 correctly defers to device UAT, but a bug in cross-chunk ordering or dropped keys in Kotlin would only surface on large multi-select imports on the 3a—exactly the D-09 “no cap” scenario.

- **19.1-CONTEXT.md line 25 contradicts ADR-002.** CONTEXT claims the Android-17 path is “COMPLETE + verified on the Pixel 6,” while ADR-002 and device UAT findings record it as non-functional on the owner’s API-37 device. Plans inherit the correct ADR framing, but downstream executors reading CONTEXT first may be misled.

- **Settings error parity (F7) is easy to under-implement.** Today `SettingsScreen.tsx:172-174` only `Logger.error`s on failure; FAB shows an Alert (`AddSpeedDialFab.tsx:78-79`). Plan 04 requires parity but allows implementation in either `startContactImport` or the Settings caller—if only legacy-path errors are handled, API-37 silent failures persist.

### LOW

- **Plan 05 frontmatter lists `ADR-002` under `files_modified` while the task forbids editing the decision body.** Harmless if executors follow the task text, but the manifest is inconsistent.

- **Plan 01 `autonomous: false` due to blocking checkpoint is correct**, but nothing prevents wave-1 plan 02 from merging before owner ratifies D-02 in plan 01 Task 1. Orchestration should enforce checkpoint-before-native-manifest ordering.

- **HANDOFF.md supersession target may be thin.** Grep shows no “Android 17+ / READ_CONTACTS” wording in `HANDOFF.md`; the locked decision may live only in phase-19 artifacts. Plan 05’s supersession note may need to search `.planning/phases/19-system-contact-import/` and CLAUDE.md import references, not only HANDOFF.

## 4. Suggestions

- **Make F12 (nameless bulk photo staging) a single mandated approach in plan 02**, e.g. extend `acceptPickedContacts` to skip `stageImportPhoto` when `mapPickedContact(...).nameRequired` is true, with a DAO test asserting zero staged files for nameless bulk rows.

- **Centralize user-visible import errors in `startContactImport`** (plan 04 Task 3) so FAB, Settings, and future entry points inherit identical Alert copy for system-path failures—not just Settings catch-up.

- **Add an explicit orchestration note**: plan 01 Task 1 checkpoint must complete before any commit touching `AndroidManifest.xml` READ_CONTACTS or shipping builds to devices.

- **In plan 03 Task 2**, name the pure JS chunk-boundary function in the plan artifacts (e.g. `chunkLookupKeys(keys, limit)`) so SUMMARY/convergence passes can verify it exists without grep archaeology.

- **For plan 04**, document a pragmatic fallback if A1 fails on the 3a: after two `DENIED` results, show copy like “If the dialog stopped appearing, open Settings” with the Open Settings action—even when classification is still `"denied"`, not `"permanent"`.

- **Update 19.1-CONTEXT.md** (outside plan execution, or as plan 05 doc task) to remove “COMPLETE + verified on the Pixel 6” for the API-37 picker path; align with ADR-002 device-blocker language.

- **Plan 02 Task 3**: specify reading `session.mode === 'single'` from `getSessionById` (migration 012 already has `mode TEXT NOT NULL CHECK (mode IN ('single', 'bulk'))`) and exactly one row with `match_outcome='already_linked'` for G10 scoping— the schema supports this; making the condition explicit reduces implementer guesswork.

- **Plan 05 UAT matrix**: add one row for “select >900 contacts” or document why the chunk-boundary JS test plus a smaller multi-select spot-check is sufficient, so the uncapped D-09 claim has proportional device evidence.

## 5. Risk Assessment

**Overall: MEDIUM**

**Justification:** The plans are technically sound, tightly aligned with ADR-002, and grounded in verified code defects—the highest-value work (D-03 Event.TYPE gate, D-14 reject-on-error for ≤16, D-12 resume nag, D-13/G1 birthday seeding, D-14b dead-end, two-query picker) addresses real bugs with clear acceptance criteria. Risk is elevated not because the design is wrong, but because (1) native Kotlin + manifest merge + API-level permission behavior are irreversible and device-dependent, (2) plan 05 is a blocking human checkpoint with a large UAT matrix and fixture setup burden, and (3) a few cross-cutting edges (orphaned staged photos, summary-count partitioning, API-37 vs ≤16 success criteria) will cause user-visible regressions if executed loosely despite good plan text.

**Phase-goal achievability:** **Yes**, for the stated goal—“contact import works end-to-end on Android ≤16 (Pixel 3a) via hybrid picker, shared pipeline unchanged, READ_CONTACTS scoped and inert on API 37”—assuming plan 05 device UAT runs with the documented fixtures and A3b is performed or explicitly BLOCKED, not assumed from packaging alone. **No**, for full IMP-01 on API 37 until Phase 19 resolves the system-picker device blocker; the plans say this explicitly and should keep saying it at phase sign-off.
