# Cross-AI Plan Review — Phase 19.1

## Consensus Summary

Both reviewers (Codex and Cursor) independently verified the plans against on-disk source and agree the phase is architecturally sound: it is tracer-first, correctly preserves the shared `PickedContact[] → routePickedImport()` boundary, anchors on real, verified defects (Kotlin `OrbitContactPickerModule.kt:116-121` swallowing read errors and `:158-159` accepting any Event row as a birthday), and needs no new migration. They diverge on overall severity — Codex rates the phase **HIGH** risk, Cursor rates it **MEDIUM** — but the substance of their concerns overlaps heavily, concentrated in a handful of underspecified paths rather than structural problems.

### Agreed Strengths

- **Shared-pipeline seam is preserved.** `routePickedImport()` is picker-agnostic and branches only on result cardinality (`src/services/import/import-acquire.ts:153-173`), so reusing it avoids duplicated session logic (both reviewers).
- **Accurate defect targeting.** Both confirm Plan 01 correctly fixes the two real Kotlin defects — the Event.TYPE birthday gate (`:158-159`) and reject-on-error instead of `resolve(emptyList())` (`:116-121`).
- **D-12 handled without a migration.** `skipped` is already a terminal status (Codex: `import-session-dao.ts:418-425`; Cursor: `import-session-dao.test.ts:178-183`); marking nameless rows `skipped` fixes finalization without widening invariants.
- **Birthday strict boundary kept.** The storage validator / `parseStoredBirthday` gate is left unchanged; only the mapping layer is broadened (both reviewers).
- **Tracer-first wave ordering is coherent** (Wave 1 parallel 01+02 are orthogonal; 03→04→05 chain correct).

### Agreed Concerns

- **Single-import nameless routing gap (HIGH / HIGH).** Both reviewers independently flag that `routePickedImport()` always navigates a single pick to `ImportReview` (`import-acquire.ts:161-171`); merely marking the row `skipped` does not finalize the session or route to `ImportComplete`, so a lone nameless contact can still land on a review screen and leave a lingering resumable/pending session. This is the top priority for both.
- **Search coverage vs D-09 (Codex HIGH / Cursor MEDIUM).** The two-tier summary read exposes only one primary phone/email per contact, but the search logic is specified to match every method value — secondary phones/emails are not available to search until a full read on selection.
- **Uncapped selection + `LOOKUP_KEY IN (…)` (Codex HIGH / Cursor MEDIUM).** An uncapped multi-select against a SQL `IN` clause can exceed SQLite bind-variable limits; both call for chunking and a large-selection test on the Pixel 3a.
- **Permanent-denial classifier (Codex HIGH / Cursor MEDIUM).** The pure classifier cannot reliably distinguish `NEVER_ASK_AGAIN` from a repeated silent `DENIED`; misclassification strands users in a false "go to Settings" state.
- **D-14 read-error UAT not reproducible as written (both MEDIUM).** Plan 05 requires forcing a provider read failure but no plan supplies an injectable hook or reproducible recipe, risking a superficial "pass."
- **API-37 / 17+ scope not proven by a Pixel 3a UAT (Codex HIGH / Cursor LOW).** A generated manifest with `maxSdkVersion="36"` proves packaging, not runtime permission absence on API 37; the UAT device cannot validate the policy-sensitive claim.

### Divergent Views

- **Overall risk rating.** Codex: **HIGH** (the plans can fail user-visible requirements — search coverage, large-selection imports, clean permanent-denial — and the API-37 policy claim lacks a valid verification path). Cursor: **MEDIUM** (same gaps, but judged fixable in plan text before execution without structural rework).
- **Avatar thumbnail contract (Codex only, MEDIUM).** Codex flags that `Avatar` expects a durable project-relative path via `resolvePhotoUri()` (`src/components/Avatar.tsx:67-80`) and will reject the `content://`/`file://` URIs a native picker thumbnail produces; recommends a dedicated `expo-image` thumbnail component. Cursor only lightly notes an Avatar-vs-Image dual-path inconsistency.
- **Data-table query omitting method-less contacts (Codex only, MEDIUM).** Codex flags that a `MIMETYPE IN (…)` query will not list contacts with only a display name, conflicting with the expectation that method-less rows still render.
- **Settings/legacy error-UX surfacing (Cursor emphasis).** Cursor gives more weight to the asymmetry where `AddSpeedDialFab.tsx:78-79` shows an Alert on failure but `SettingsScreen.tsx:172-174` only logs, and to the unspecified error handling on `LegacyContactPickerScreen`.

# Plan Review — Phase 19.1

## Summary

The phase is well structured around a sensible tracer-first approach and correctly preserves the existing `PickedContact[] → routePickedImport()` boundary. The most material gaps are in the legacy picker’s two-tier data contract, unbounded SQL selection handling, permanent-denial detection, and the Plan 5 claim that a generated manifest alone proves API-37 runtime scoping.

## Strengths

- The shared-pipeline focus is sound. `routePickedImport()` is picker-agnostic and only branches on result cardinality, so preserving that seam avoids duplicated session logic ([src/services/import/import-acquire.ts:153]( /home/bwales/projects/orbit-app/src/services/import/import-acquire.ts:153)-[172]( /home/bwales/projects/orbit-app/src/services/import/import-acquire.ts:172)).

- Plan 01 correctly targets two real native defects: the current Android-17 reader assigns any Event row as a birthday ([OrbitContactPickerModule.kt:158]( /home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:158)-[159]( /home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:159)), and swallows reader errors as an empty selection ([116]( /home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:116)-[121]( /home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:121)).

- Plan 02 correctly recognizes that `skipped` is already terminal. The terminal query only treats `pending`, `needs_review`, and `failed` as unresolved ([src/db/import-session-dao.ts:418]( /home/bwales/projects/orbit-app/src/db/import-session-dao.ts:418)-[425]( /home/bwales/projects/orbit-app/src/db/import-session-dao.ts:425)); the leave guard matches that same set ([src/screens/import-leave-guard-logic.ts:7]( /home/bwales/projects/orbit-app/src/screens/import-leave-guard-logic.ts:7)-[17]( /home/bwales/projects/orbit-app/src/screens/import-leave-guard-logic.ts:17)). No migration is needed for D-12.

- The birthday plan preserves the right strict boundary: the storage validator rejects invalid calendar dates rather than relying on JavaScript date normalization ([src/logic/birthday-logic.ts:73]( /home/bwales/projects/orbit-app/src/logic/birthday-logic.ts:73)-[114]( /home/bwales/projects/orbit-app/src/logic/birthday-logic.ts:114)).

- Plan 02’s already-linked redirect is appropriately grounded in existing behavior: `skipDuplicate()` already replaces the review screen with `ImportComplete` ([src/screens/ImportReviewScreen.tsx:304]( /home/bwales/projects/orbit-app/src/screens/ImportReviewScreen.tsx:304)-[318]( /home/bwales/projects/orbit-app/src/screens/ImportReviewScreen.tsx:318)), and that screen’s Done action resets to Home ([src/screens/ImportCompleteScreen.tsx:234]( /home/bwales/projects/orbit-app/src/screens/ImportCompleteScreen.tsx:234)-[244]( /home/bwales/projects/orbit-app/src/screens/ImportCompleteScreen.tsx:244)).

## Concerns

- **HIGH — Plan 02’s single nameless-contact flow still navigates into review.** `routePickedImport()` always navigates a one-contact selection to `ImportReview` after acceptance ([src/services/import/import-acquire.ts:161]( /home/bwales/projects/orbit-app/src/services/import/import-acquire.ts:161)-[171]( /home/bwales/projects/orbit-app/src/services/import/import-acquire.ts:171)). Merely changing the new row to `skipped` at acceptance does not alter this. `ImportReviewScreen` selects rows by `contactId === null` ([src/screens/ImportReviewScreen.tsx:117]( /home/bwales/projects/orbit-app/src/screens/ImportReviewScreen.tsx:117)), and skipped rows retain a null `contact_id`. This can still present a nameless review row rather than a clean terminal result.

- **HIGH — Plan 03’s two-tier contract cannot satisfy search by all phone/email values.** The plan says the native summary read returns “one primary phone/email value,” while its pure search logic is required to match “every method value.” A non-primary email/phone is not available to search. The existing picker payload does preserve all methods ([modules/orbit-contact-picker/index.ts:8]( /home/bwales/projects/orbit-app/modules/orbit-contact-picker/index.ts:8)-[18]( /home/bwales/projects/orbit-app/modules/orbit-contact-picker/index.ts:18)); the proposed summary shape must do so too.

- **HIGH — An uncapped picker combined with `LOOKUP_KEY IN (?, …)` needs chunking.** Plan 03 promises no app-level selection cap, but an SQL statement has a finite bind-variable limit. Large selection sets can make the selected-key query fail, turning a valid bulk import into a read error. The plan must require chunked full reads, aggregation by lookup key, and stable output ordering.

- **HIGH — Plan 04’s permanent-denial classifier lacks the information it claims to use.** `PermissionsAndroid.request()` returns a permission result, but the proposed pure function takes only that result and `hasRequestedBefore`; it cannot know whether an OS dialog was actually shown. Treating a repeated `DENIED` result as permanent will falsely route users to Settings when they simply denied again. The plan needs a reliable native/rationale signal, or it should only classify `NEVER_ASK_AGAIN` as permanent and leave ambiguous denial recoverable.

- **HIGH — Plan 05 does not actually verify the “dropped on API-37” claim.** A generated manifest containing `android:maxSdkVersion="36"` proves the declaration is packaged, not that permission state is absent on an API-37 runtime. The stated UAT device is a Pixel 3a on Android 14/15, so it cannot validate API 37 behavior. This is a policy-sensitive claim and needs an API-37 device/emulator or an explicitly narrower acceptance statement.

- **MEDIUM — The Plan 01 shared-sink test is not aligned with the described dispatch.** `startContactImport()` is specified to call `routePickedImport()` for `"system"`, but for `"legacy"` it navigates to `LegacyContactPicker`; the picker later calls the sink. A unit test claiming both synthetic modes reach the same sink through `startContactImport()` cannot represent the actual execution path. Test the dispatch separately, then test the legacy picker confirmation handoff separately.

- **MEDIUM — The proposed use of `Avatar` for picker thumbnails is incompatible with its input contract.** `Avatar` expects a safe project-relative stored path and passes it through `resolvePhotoUri()` ([src/components/Avatar.tsx:67]( /home/bwales/projects/orbit-app/src/components/Avatar.tsx:67)-[80]( /home/bwales/projects/orbit-app/src/components/Avatar.tsx:80)). Native picker thumbnails would be `content://` or temporary `file://` URIs, not durable `avatars/...` paths. Passing them to `Avatar` is likely to fail validation or produce an invalid URI.

- **MEDIUM — The native Data-table query omits contacts with no matching Data row.** The intended `MIMETYPE IN (phone,email,event,photo)` query will not list contacts with only a display name and no relevant data. That conflicts with the plan’s expectation that method-less rows still render and makes the D-12 nameless/edge-case coverage incomplete.

- **MEDIUM — Acceptance-time skipping should avoid staging a photo first.** `acceptPickedContacts()` stages a photo before inserting the session row ([src/services/import/import-acquire.ts:69]( /home/bwales/projects/orbit-app/src/services/import/import-acquire.ts:69)-[109]( /home/bwales/projects/orbit-app/src/services/import/import-acquire.ts:109)). If a nameless contact is terminalized only afterward, it may create needless staged PII that a completed skipped row will not consume. Classify before staging, or ensure cleanup is explicit.

- **MEDIUM — Read-error UAT is not reproducible as written.** Plan 05 says to “simulate/force” a provider failure, but Plans 01–04 do not provide an injectable resolver, native test hook, or instrumentation test. This can become an unverified manual assertion.

- **LOW — Plan 05’s declared modified-file list is incomplete.** Its task edits `HANDOFF.md` and `CLAUDE.md`, but the plan header lists only the ADR and UAT document. That weakens change ownership and review scope.

## Suggestions

- Update Plan 02 so acceptance returns row IDs/statuses or otherwise recognizes an all-terminal single session; immediately finalize it and route to `ImportComplete`, rather than `ImportReview`.

- Define the summary contract as:
  `lookupKey`, `displayName`, `primaryMethod`, `searchMethods[]`, and `photoThumbnailUri`.
  Keep all phone/email values in `searchMethods`; use only `primaryMethod` for the subtitle.

- Require selected-key reads to chunk keys below a conservative SQLite bind limit, merge results by lookup key, and preserve original selected-key order. Add a pure test for a selection larger than one chunk.

- Use a dedicated thumbnail component that accepts external `content://`/`file://` URIs with `expo-image`; retain `Avatar` only for the initials fallback. Do not pass external URIs to the persisted-photo `Avatar` API.

- Resolve permanent denial with a concrete platform mechanism. If an unambiguous mechanism is unavailable, expose only `granted | denied | never_ask_again`, retain a “Grant access” path for ambiguous cases, and validate actual OEM behavior during UAT.

- Split Plan 05’s policy evidence:
  - Generated-manifest inspection verifies correct packaging.
  - API-37 runtime testing verifies effective permission absence.
  - If no API-37 target is available, record that runtime check as blocked rather than marking it passed.

- Add a native/instrumented failure test or a debug-only fault-injection mechanism for the legacy reader; ensure it is removed or unavailable in production.

## Risk Assessment

**Overall: HIGH.** The core architecture is strong and much of the plan accurately builds on existing seams, but the current plan can fail key user-visible requirements: complete search coverage, uncapped large selection imports, and clean permanent-denial behavior. The API-37 permission-policy claim also lacks a valid verification path. Addressing these before execution would substantially reduce delivery and distribution risk.

Appropriate phase gate: full vitest suite, droid prebuild, generated-manifest A3 verification, comprehensive UAT matrix mapping D-01–D-14b, ADR supersession note for HANDOFF/CLAUDE.md (per ADR-002 `:43`), owner sign-off. Correctly treats emulator as invalid for perf claims (CLAUDE.md).

### Strengths

- **A3 backstop:** Verifying *generated* `android/app/src/main/AndroidManifest.xml` for `maxSdkVersion="36"` addresses the MEDIUM-confidence manifest-merge assumption — essential for Play policy (ADR-002 `:36-37`).
- **UAT matrix completeness:** Covers routing, permissions, picker UX, reader gates, pipeline fixes, and shared downstream (ADR-002 `:47`).
- **Precondition realism:** Pixel 3a via `emu-connect`, droid prebuild per runbook — matches project hardware constraints.
- **Privacy during UAT:** Prohibition on logging contact content aligns with local-first commitment.
- **Migration guard:** Asserts `TARGET_VERSION===12` — matches `database.ts:47`.

### Concerns

- **MEDIUM — D-14 read-failure UAT may be hard to simulate:** Matrix requires forcing a read failure on device; plan doesn’t specify a reproducible method (e.g., revoke permission mid-read, corrupt provider, debug hook). Without a recipe, D-14 may be marked “pass” superficially.
- **MEDIUM — Test fixture dependencies:** Precondition requires address book with anniversary+birthday, nameless, OEM birthday formats — may need setup steps documented in UAT doc.
- **LOW — 17+ path still unverified:** UAT is ≤16 only; Android 17 system picker remains broken per ADR-002 `:12-13` — phase success shouldn’t imply full IMP-01 on API 37.

### Suggestions

- Add a UAT appendix: steps to force native reader rejection (or accept “manual code injection” as last resort with owner witness).
- Record manifest grep output verbatim in `19.1-DEVICE-UAT.md` (permission line + effective SDK).
- Split UAT sign-off: “≤16 IMP-01 satisfied” vs “API 37 system picker (Phase 19 finish).”

### Risk Assessment

**MEDIUM** — Good gate structure; execution risk is fixture setup and forcing negative paths on device.
