# Cross-AI Plan Review — Phase 19.1

## Consensus Summary

Both reviewers ran source-grounded against the repo (Codex 20+ `file:line` citations, Cursor 22) and both endorse the overall architecture: the picker-agnostic `PickedContact[]` boundary, extending the native module rather than forking a parallel downstream pipeline, the no-migration approach to the terminal-status fixes, and the tracer-first wave ordering (01 ∥ 02 → 03 → 04 → 05). They disagree sharply on execution risk: **Codex rates the phase HIGH** on three claimed hard blockers, while **Cursor rates it MEDIUM** and explicitly validates two of the mechanisms Codex flags as broken. That divergence is the single most important thing to resolve before execution.

### Agreed Strengths
- Shared-pipeline / `PickedContact[]` boundary is the correct integration seam; downstream `routePickedImport()` is picker-agnostic and unchanged (both cite `import-acquire.ts:153–173`).
- Plan 01 targets the two real Android-17 defects at the right lines: read-error-swallow (`OrbitContactPickerModule.kt:116–121`) and untyped Event→birthday (`:158–159`).
- No migration needed: `skipped` is already terminal and excluded from `finalizeSessionIfTerminal()`'s unresolved set (`import-session-dao.ts`) and from the leave guard (`import-leave-guard-logic.ts`); `TARGET_VERSION === 12` (`database.ts:47`).
- Plan 02's already-linked dead-end fix (route to `ImportComplete` instead of the single-button Alert) is correctly rooted in current behavior (`ImportReviewScreen.tsx` matched-null re-entry).
- Local-first preserved: scoped `READ_CONTACTS`, no network on the read path, app-private cache for temp photos.

### Agreed Concerns
- **Native browse-list / name-only enumeration (Plan 03) is the highest-risk Kotlin task.** Both flag that a `Data`-table query filtered to phone/email/event/photo cannot surface name-only contacts, and that the two-tier read + chunked `LOOKUP_KEY IN (...)` design needs careful device proof. (Codex rates this HIGH as internally inconsistent; Cursor rates it MEDIUM but wants the chosen URI/projection documented and device-verified.)
- **Permanent-denial detection needs real-device confirmation (Plan 04).** OEM variance on first-prompt `NEVER_ASK_AGAIN` vs `DENIED`+rationale is real; both want the conservative default and Pixel confirmation in Plan 05.
- **Plan 05 device dependency / sign-off.** Both note the A3b Play-policy check depends on the Pixel and that owner sign-off must be a genuine recorded human gate, not implied by an `autonomous` flag.

### Divergent Views
- **Plan 02 birthday seeding (D-13) — direct contradiction.** Codex rates it **HIGH**: seeding the single-review input from raw `snapshot.birthday` will fail `normalizeEditedBirthday()` (`ImportReviewScreen.tsx:170`, `birthday-logic.ts:121`), so a valid OEM slash date like `04/13/1990` renders `birthdayInvalid=true` and blocks import; it recommends seeding the canonicalized form and only falling back to raw text when canonicalization fails. Cursor rates the **same fix "correct"** (seed from `snapshot.birthday` to stop silent loss of raw OEM strings). These cannot both be right — the interaction between the seed source and the review-screen validator needs to be traced before execution.
- **Plan 04 rationale API — contradiction.** Codex rates **HIGH**: `PermissionsAndroidStatic` exposes only `check()`/`request()` and has no `shouldShowRequestPermissionRationale()` (`PermissionsAndroid.d.ts:123`), so the proposed hook will not typecheck and needs a native bridge or a `NEVER_ASK_AGAIN`-only policy. Cursor describes the classifier as "uses `shouldShowRequestPermissionRationale` after request" approvingly and does not flag the missing API.
- **Overall risk rating:** Codex HIGH (blockers must clear first) vs Cursor MEDIUM (mitigations already present). Codex-only additional findings: Plan 01 missing `use-contact-import-mode.test.ts` in `files_modified` + web shim parity; JS tests overclaiming coverage of native chunking/handoff (Plans 01/03); Plan 05 API-37 assertion should be permission-state based (`maxSdkVersion` can still appear in metadata). Cursor-only additional findings: Plan 01 `<success_criteria>` "both entry points" overstates scope (only the FAB is rewired; Settings waits for Plan 04); interim full-book read window between Plans 01 and 03.

## Codex Review

# Plan Review: Phase 19.1

## Summary

The five plans have strong scope control and trace the shared import pipeline well. They correctly preserve the `PickedContact[]` boundary and avoid a migration for existing terminal-state fixes. However, three execution blockers need correction before implementation: Plan 02’s raw birthday loading rejects valid OEM slash dates, Plan 03’s proposed one-pass summary query cannot reliably include name-only contacts while collecting all methods, and Plan 04 relies on a React Native permission API that is not present in this repository’s installed typings.

## Strengths

- The shared-pipeline approach is sound. The existing routing is picker-agnostic: `routePickedImport()` accepts `PickedContact[]` and creates the session before choosing `ImportReview` or `BulkImportSetup` ([src/services/import/import-acquire.ts:153](/home/bwales/projects/orbit-app/src/services/import/import-acquire.ts:153)). Extending the native module rather than creating a parallel downstream pipeline is appropriate.

- Plan 01 correctly targets the two existing Android-17 defects. The current reader maps every `Event` data row as a birthday ([OrbitContactPickerModule.kt:158](/home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:158)) and turns provider read errors into an empty list ([OrbitContactPickerModule.kt:116](/home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:116)). Adding `DATA2`/`TYPE_BIRTHDAY` and rejecting legacy-read errors directly addresses them.

- Plan 02 correctly recognizes that `skipped` is already a terminal status. `finalizeSessionIfTerminal()` treats only `pending`, `needs_review`, and `failed` as unresolved ([src/db/import-session-dao.ts:403](/home/bwales/projects/orbit-app/src/db/import-session-dao.ts:403)); the leave guard mirrors that exact set ([src/screens/import-leave-guard-logic.ts:4](/home/bwales/projects/orbit-app/src/screens/import-leave-guard-logic.ts:4)). No migration is needed.

- The plan identifies a real PII cleanup ordering issue. Current acceptance stages a photo before inserting the session row ([src/services/import/import-acquire.ts:69](/home/bwales/projects/orbit-app/src/services/import/import-acquire.ts:69)), while namelessness is only known after `mapPickedContact()`. Requiring classification before staging, or explicit cleanup, is necessary.

- Plan 02’s already-linked exit is correctly based on current behavior: `resolveAlreadyLinked()` sets `matched_contact_id` while leaving `contact_id` null ([src/db/import-session-dao.ts:301](/home/bwales/projects/orbit-app/src/db/import-session-dao.ts:301)), and `ImportReviewScreen` selects the first row with null `contactId` ([src/screens/ImportReviewScreen.tsx:117](/home/bwales/projects/orbit-app/src/screens/ImportReviewScreen.tsx:117)). Replacing the alert with `ImportComplete` fixes the loop; the row reader already exposes `matchedContactId` ([src/db/import-session-read.ts:147](/home/bwales/projects/orbit-app/src/db/import-session-read.ts:147)).

## Concerns

- **HIGH — Plan 02’s birthday UI instruction breaks valid slash-format imports.** The plan says to seed the single-review input from raw `snapshot.birthday`. But the form validates with `normalizeEditedBirthday()` ([src/screens/ImportReviewScreen.tsx:170](/home/bwales/projects/orbit-app/src/screens/ImportReviewScreen.tsx:170)), which only accepts persisted hyphenated forms after stripping an optional `--` prefix ([src/logic/birthday-logic.ts:121](/home/bwales/projects/orbit-app/src/logic/birthday-logic.ts:121)). Thus a valid new canonicalizer result such as `04/13/1990` would still render `birthdayInvalid=true` and block import ([src/screens/ImportReviewScreen.tsx:174](/home/bwales/projects/orbit-app/src/screens/ImportReviewScreen.tsx:174)). The plan’s own UAT claim that `MM/DD/YYYY` imports cannot succeed with this implementation.

- **HIGH — Plan 03’s summary-reader design is internally inconsistent for name-only contacts.** The existing native implementation queries `ContactsContract.Data` and groups only returned data rows ([OrbitContactPickerModule.kt:125](/home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:125)). A `Data` query filtered to phone/email/event/photo cannot include a contact with no matching data rows. Conversely, querying `Contacts.CONTENT_URI` can enumerate name-only contacts but does not return every phone/email data row in the same cursor. The plan requires both “single cursor pass” and universal name-only inclusion without selecting one viable mechanism; it needs a defined two-query merge (contacts index + grouped method query) or an explicitly validated provider query that guarantees both.

- **HIGH — Plan 04 calls a nonexistent React Native API.** The installed `PermissionsAndroidStatic` provides `check()` and `request()` ([PermissionsAndroid.d.ts:123](/home/bwales/projects/orbit-app/node_modules/react-native/Libraries/PermissionsAndroid/PermissionsAndroid.d.ts:123)), but no `shouldShowRequestPermissionRationale()` method. The proposed hook will not typecheck. A real permanent-denial signal requires a small native bridge using Android’s rationale API, or the UX must rely only on `NEVER_ASK_AGAIN` and conservatively continue showing the re-request state for ambiguous denies.

- **MEDIUM — Plan 01 omits required test and platform-parity files.** It verifies `src/screens/use-contact-import-mode.test.ts`, but that test file is absent from `files_modified`. Also, the web native-module shim only implements `isContactPickerAvailable` and `pickContacts` ([OrbitContactPickerModule.web.ts:7](/home/bwales/projects/orbit-app/modules/orbit-contact-picker/src/OrbitContactPickerModule.web.ts:7)); adding methods to the typed native interface without updating this shim risks web/test module parity failures.

- **MEDIUM — Plan 01’s shared-sink test cannot prove the picker component’s later handoff as currently shaped.** `startContactImport()` can unit-test system dispatch and legacy navigation, but it cannot prove that `LegacyContactPickerScreen` calls `routePickedImport()` unless the confirmation action is extracted into a pure function or the component is rendered in a UI test. The stated test assertion overclaims coverage.

- **MEDIUM — Plan 03’s chunking verification does not test the implementation it describes.** The plan puts selection chunking in Kotlin but permits a pure JS-helper or wrapper test as evidence. A JS test cannot prove native query chunking, merging, or selected-order preservation. This is especially relevant because the current native code has no selected-key path at all ([OrbitContactPickerModule.kt:137](/home/bwales/projects/orbit-app/modules/orbit-contact-picker/android/src/main/java/expo/modules/orbitcontactpicker/OrbitContactPickerModule.kt:137)).

- **MEDIUM — Plan 05 needs a more precise API-37 permission assertion.** `maxSdkVersion` may still appear in package metadata, so checking merely for a listed requested permission can give a false failure despite correct runtime behavior. The plan should define the exact successful observation: permission not grantable/active via `check-permission` or relevant `dumpsys package` flags on API 37, while separately recording the generated manifest packaging evidence.

- **LOW — Plan 05 is marked autonomous while requiring owner sign-off and physical-device fixtures.** It should explicitly use a blocking human checkpoint rather than imply that an executor can finish the phase independently.

## Suggestions

- Amend Plan 02’s single-review loading rule:

  - If `mapBirthdayForStorage(raw)` succeeds, seed the editor with its canonical stored/form representation.
  - Only seed raw text when canonicalization fails, so the existing invalid state flags it.
  
  This preserves both valid OEM imports and “flag, don’t drop.”

- Amend Plan 03 to explicitly use a two-query native summary read:

  1. Enumerate all contacts from `Contacts.CONTENT_URI` for lookup key/name/photo reference.
  2. Query phone/email data rows and merge all values by lookup key.

  This makes name-only inclusion and complete search indexing deterministic.

- Replace Plan 04’s proposed rationale call with either:

  - a native module method backed by Android’s `shouldShowRequestPermissionRationale`, with Android instrumentation/device verification; or
  - a conservative JS-only policy using `NEVER_ASK_AGAIN` only, treating ambiguous denial as recoverable.

- Add the missing mode test and update the web module whenever adding native-interface methods. Extract the legacy confirmation operation to a pure function if its shared-sink behavior must be unit-tested.

- For Plan 03, factor native selected-key chunking into a Kotlin helper with native/instrumentation coverage, or reduce the claim: test JS argument formation in Vitest and verify actual chunking/order in device UAT.

- Make Plan 05’s API-37 check explicitly permission-state based, and change owner approval to a blocking checkpoint.

## Risk Assessment

**Overall: HIGH until the three HIGH findings are resolved.** The architecture and sequencing are otherwise solid, but the current Plan 02 implementation would block valid birthday imports, Plan 03 has no implementable single-pass route to one of its required data sets, and Plan 04 cannot compile against the installed React Native permission API.
