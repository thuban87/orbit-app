# Phase 38.14 Plan 08: Events Search, Event Detail Actions and Participant Wording Summary

**The Events search now shows only the latest result. Back closes the search and closing clears it. The term survives opening a result. Event detail shows Edit Event and Add participants as visible buttons, confirms adds and removes by name (D-84), never shows a stale participant sheet, and no longer offers View Event on its own event. The participant editor and cards name the fields that differ from the event.**

## Performance

- **Duration:** about 21 min (15:36 to 15:57)
- **Tasks:** 4 (the plan's 3, plus the D-84 task the coordinator added mid-plan)
- **Files:** 16 changed (6 created, 10 modified)

## Accomplishments

- **Events search (D-25, D-48).** `runEventsSearch` begins a token for each read and publishes `loading: true` only on the first load. A current settle always publishes `loading: false`, and a stale one publishes nothing. The screen has two separate effects. The first is a focus-lifecycle `useFocusEffect` with stable deps that invalidates the authority on blur. The second is a term load in `useEffect([isFocused, term, load])`, so a refocus rereads the current term exactly once. A `hardwareBackPress` listener lives inside its own `useFocusEffect`, gated on `searchOpen`: Back closes search and clears the term, including after a blur and refocus. The search toggle's close also clears the term. "Try again" still calls `load(term)`.
- **Screen-level proof.** `group-events-search-render.test.tsx` uses a mocked React with real state, deps-aware effects (each effect's previous cleanup runs first) and blur/refocus simulation. It covers seven cases, including the plan's R4-02 and R4-03 cases. I mutation-checked the harness: putting `term` in the focus deps, dropping the blur invalidate, invalidating on close, and always treating loads as first loads each fail at least one case.
- **Event detail snackbars (D-84, owner).** Adds now confirm with "Added Maya" / "Added Maya and Sam" / "Added 3 people", with the names taken from the readback after the commit; if the readback fails, the snackbar gives a count. Removes show "Removed Maya", or "Removed Maya and deleted the interaction" in the warning style. Writes stay immediate. The glue is the new shared `createParticipantAddAnnouncer`, and Edit Event uses it too.
- **Event detail (D-71, D-28, D-30).** Edit Event and Add participants are visible secondary Buttons in the summary card, and the ⋯ keeps only Dissolve and "Delete Event & Interactions". The empty participant state is the one `EmptyState`, with an Add participants action and no "save now" wording. The interaction sheet now stores `detailInteractionId` and re-derives the participant each render through `resolveDetailParticipant`, closing when that participant is gone. `onViewGroupEvent` is no longer passed on this screen.
- **Participant wording (D-29).** Every follow line names its field. The card caption names what is changed for that person, or reads "Same as event".
- **Edit participant load (D-25).** The load goes through a memoised `createLatestRequestAuthority()`, publishes loaded data or the error only while current, and invalidates on unmount. Save and plan 07's publication are unchanged.
