### A-WR-01: "No, don't log" claims "Didn't log …" for a record already logged elsewhere

**File:** `src/screens/ComposeScreen.tsx:1342-1379`; `src/logic/compose-assist-panel.ts:67-81`; `src/db/interaction-assist-dao.ts:160-172`

**Issue:** D-23 releases the panel claim on blur, so the banner and the pending list offer the record whenever Compose is not focused. That happens on the normal Compose paths: "Things to Remember · N" → ComposeResearch, and "Add a phone number or email" → Edit. If the user answers Yes on the banner there, then returns, refocus re-claims the uid and the panel is still showing (`confirm` is per-mount state). Tapping "No, don't log" then runs `markAssistDismissed`. That is a `WHERE status = 'pending'` no-op that resolves `void`, so the runner returns `"done"` and the screen shows the success snackbar "Didn't log Message with Maya", even though an interaction *was* logged. This is a new false statement introduced by the D-78 dismissed snackbar, on a data-truth surface. (Yes on the same panel is safe: `markAssistLogged` returns `already-logged` and the snackbar is true. The banner and list dismiss paths act only on rows they just read as pending, so the window there is negligible.)

**Fix:** Do not show the panel for a record that is no longer pending. Re-check its status when the claim effect re-claims on refocus, and close the panel when the status is not pending. D-23 says "No DAO or migration change", so a read-only status helper needs a planner ruling on whether it counts as a DAO change. If it is ruled out, close the panel on blur as well, which D-23 already allows ("leaving Compose unanswered → they ask as today"). Example sketch with a read helper:

```ts
useFocusEffect(useCallback(() => {
  if (confirm === null) return undefined;
  const { assistUid } = confirm;
  useAssistBanner.getState().setPanelOwned(assistUid);
  let live = true;
  void readAssistStatus(getExecutor(), assistUid).then((status) => {
    if (live && status !== "pending") setConfirm(null); // answered elsewhere
  });
  return () => { live = false; useAssistBanner.getState().releasePanelOwned(assistUid); };
}, [confirm]));
```

### A-WR-02: Tapping bulk "Edit" and then closing the sheet loses the batch's Undo

**File:** `src/screens/HomeScreen.tsx:1455-1459`, `src/screens/HomeScreen.tsx:2923-2936`; `src/stores/snackbar-store.ts:21-27`

**Issue:** D-62 gives bulk Quick Log's snackbar two actions, **Undo · Edit**, both available during the Undo window. Snackbar actions are mutually exclusive: tapping either one dismisses the snackbar. "Edit" opens the channel `OptionSheet`, and its `onRequestClose` just runs `setRechannelTarget(null)`. A user who taps Edit, changes their mind and closes the sheet has lost Undo for a multi-contact write, with no way back short of deleting the rows one by one in History. A cancel should not turn a reversible bulk write into an irreversible one. A related point: the sheet can be held open indefinitely, so "Edit" outlives the 6 s window D-62 describes.

**Fix:** When the sheet closes without a pick, re-show the original bulk snackbar with the same receipt (a fresh Undo · Edit window):

```tsx
onRequestClose={() => {
  const target = rechannelTarget;
  setRechannelTarget(null);
  if (target) showBulkLoggedSnackbar(target.receipt, target.channel, target.ids);
}}
```

(Factor the existing success-snackbar block in `performBulkQuickLog` into `showBulkLoggedSnackbar` so both paths stay identical.)

### A-WR-03: The re-channel silently skips rows whose contact was merged, a third skip D-82 does not allow

**File:** `src/db/bulk-actions-dao.ts:150-167`; `src/db/merge-dao.ts:531-545`

**Issue:** `rechannelBulkQuickLog` reads each receipt row with `WHERE id = ? AND contact_id = ?` and treats "no row" as "deleted since the log" (D-82). A contact merge, however, reparents `interactions` to the survivor (`merge-dao.ts` loop over `"interactions"`). The row still exists and is still part of the batch, but the lookup by the old `contact_id` misses it, so it is skipped and never re-channelled. D-62 ("re-channels every interaction from that batch") and the plan's acceptance criterion ("skips only deleted and converted rows") allow exactly two skips. The returned count stays truthful, so the user sees "Changed 3 interactions" for a 4-person batch with no reason given.

**Fix:** Look the row up by id alone and drive the core with its *current* contact, so the recency recompute hits the right person:

```ts
const row = await exec.getFirstAsync<{ contact_id: number; /* … */ group_event_id: number | null }>(
  `SELECT contact_id, occurred_at, direction, connected, quality, note, duration,
          allow_ai, group_event_id
     FROM interactions WHERE id = ?`, [interactionId]);
if (!row || row.group_event_id !== null) continue; // D-82's two skips only
await editTouchpointFullCore(exec, { interactionId, contactId: row.contact_id, /* … */ });
```

### A-WR-04: Removing the "None" readout means a rejected custom duration now fails silently

**File:** `src/components/TouchpointRefineForm.tsx:499-533`; `src/components/touchpoint-refine-logic.ts:203-220`

**Issue:** `onChangeText` stores `parseCustomDurationMinutes(t)`, which returns `null` for "0", for any value above `MAX_DURATION_SECONDS` (24 h, e.g. "1500"), and for other invalid input. `customMinutesDisplay` then keeps the typed text, because `parse(typed) === seconds` (null === null). Before D-31 the readout under the field read "None", which was the only sign that the entry had not been accepted. Now the box still shows "1500", nothing on screen says it was refused, and Save writes no duration. That is a silent data drop on the same surface D-31 meant to make truthful, and it affects all five form hosts.

**Fix:** Keep the readout hidden for a genuine "none", but show an inline error when typed text was refused:

```tsx
const customRejected =
  customMinutes.trim() !== "" && parseCustomDurationMinutes(customMinutes) === null;
<FieldError testID={`${testID}-duration-error`}
  message={customRejected ? "Enter 1 to 1440 minutes" : null} />
```

### A-WR-05: A race in the draft-switch prompt can silently redirect Compose to the other person

**File:** `src/screens/ComposeScreen.tsx:889-923`; `src/navigation/discard-keep-guard.ts:139-152`

**Issue:** `confirmDiscard()` is single-flight. While a discard prompt is already queued, it resolves `false` at once. The D-72 branch treats `false` as "Keep editing" and runs `navigation.setParams({ contactId: storedContactId, origin: undefined })`. Two paths reach that branch with no user choice:

1. **Re-entry while the prompt is open.** The focus effect re-runs while the prompt is still queued (a widget or notification entry resets the stack to a new Compose, or the effect re-subscribes). The new run gets an immediate `false` and redirects to the stored person without asking.
2. **Cancelled first run.** The first run's `cancelled` flag drops the user's real answer. A later "Discard" on the still-visible prompt does nothing.

There is no data loss (the draft is kept), but Compose can switch person behind the user's back, and the visible prompt stops working.

**Fix:** Tell "the user chose Keep editing" apart from "a prompt is already pending". For example, check the confirm queue first and, if a discard prompt is already pending, `await` the same answer (or re-run the effect after it settles) instead of acting on the immediate `false`:

```ts
if (discardPromptPending()) return; // the open prompt's answer will drive this screen
void confirmDiscard().then((discard) => { if (cancelled) return; /* … */ });
```

Alternatively, have the cleanup dequeue its own prompt so the next run's prompt is a real one.

### B-CR-01: The event-detail interaction sheet stays open over the editor it navigates to

**File:** `src/screens/GroupEventDetailScreen.tsx:406-430`

**Issue:** `InteractionDetail` is a `Sheet`, which is a `BaseOverlay` built on an RN `Modal` (`overlay-base.tsx`). It has no focus or blur handling, so it stays on top of the navigator until something closes it.

On this screen `visible` is hard-wired, and the sheet only closes when `detailInteractionId` is cleared. Three callbacks navigate without clearing it:
- `onEditParticipant` (`:424-430`), reached through the scope prompt's "Edit for this person";
- `onEditGroupEvent` (`:421-423`);
- `onEdit` (`:406-412`).

So the pushed `EditParticipant` / `EditGroupEvent` screen opens underneath the still-visible sheet. The user sees no response until they dismiss the sheet. Since D-68 made `EditParticipant` the only participant editor, this is now the main edit route from this sheet.

The code knows a modal must close before a push:
- `closeThenOpenParticipantProfile` exists in `group-event-detail-logic.ts:13-21` precisely to "Close the modal surface before pushing Profile onto the current Events stack".
- Every equivalent callback in `HistorySection.tsx:1244-1271` calls `setDetailId(null)` before `navigation.navigate`.

The behaviour predates the phase (the `3cc3ce2f` version has the same callbacks). It is still in this lane: D-28 reworked this sheet's lifecycle, and D-68 routes all participant edits through it. Confirm on device in plan 09.

**Fix:**
```tsx

onEditGroupEvent={() => { closeDetail(); navigation.navigate("EditGroupEvent", { groupEventId }); }}
onEditParticipant={() => { const target = detail; closeDetail(); navigation.navigate("EditParticipant", { groupEventId, interactionId: target.interactionId, contactId: target.contactId }); }}
```
Capture `detail` before `closeDetail()`, or route through a `closeThenOpen…` helper like the Profile one. Add a source pin in `event-screens-contract.test.ts` that each navigating callback calls `closeDetail` first.

### B-WR-01: The Intensity share counts future days in the current Month and Year windows, so the current period always reads behind

**File:** `src/components/intensity-line-caption.ts:68-77`, `src/components/history/IntensityChart.tsx:72-82`, `src/components/IntensityLine.tsx:56-63`

**Issue:** `intensityShare = count × cadence ÷ periodDays`. Here `periodDays` is the full window span from `intensity-window.ts:83-86`. For the Month and Year lenses, `window.end` is the last day of the month or year (`services/history/window.ts:128, 147`), even when that day is in the future. `window.ts:33` says future days are "rendered, never counted".

Example: on Oct 20, the Year lens for a Monthly contact with 8 logs reads "8 logs · about ⅔ of your monthly rhythm" (8 × 30 / 365 = 0.66). The bar is two-thirds full, although the contact is on rhythm for the ~293 days that have elapsed (8 × 30 / 293 = 0.82). The in-progress period therefore always shows below rhythm.

That works against the "frequency is a floor, never a scold" contract the caption module cites. It is new behaviour from D-65; the old "N×" was a plain count.

**Fix:** Compute the share over the elapsed span, `min(window.end, today) − window.start + 1`. Do it in the caption layer (D-35 keeps `computeIntensity` / `intensity-window` unchanged). For example, pass `window` and `today` to `IntensityChart`, or carry an `elapsedDays` beside the result in `HistorySection`, and use that in both the caption and the bar. If the owner reads D-65's "over the lens window" literally as the full calendar window, treat this as a one-line owner wording question for plan 09 rather than a fix.

### B-WR-06: The destructive confirms on these screens have no synchronous single-flight guard, so a double tap runs two deletes

**File:**
- `src/screens/GroupEventDetailScreen.tsx:206-231, 391-399`
- `src/components/history/InteractionDetail.tsx:129-134, 270-278`

**Issue:** `lifecycle()` (Dissolve / Delete Event & Interactions) has no latch, and its `ConfirmDialog` gets no `confirmDisabled`. `InteractionDetail.onConfirmDelete` guards with the `deleting` React state, read from the render closure. The `ConfirmDialog` it opens gets no `confirmDisabled={deleting}`. `src/utils/single-flight.ts:1-15` documents exactly this as the double-submit anti-pattern.

A double tap on "Delete Event & Interactions" or "Delete interaction" runs two write transactions. They run one after the other, so the DAO guards keep the data safe (`loadGroupEventUid` / `deleteInteractionCore` throw "no longer exists" / "changed 0"). But the second rejection then sets `writeError` or `error` after the first has navigated away or closed the sheet. This is the "double delete" path the lane brief named; it is robustness, not data loss.

**Fix:** Use a `useRef<InFlightRef>` with `beginInFlight` / `endInFlight` around `lifecycle()` and `onConfirmDelete`, as `runParticipantRemove` and `confirmThenDelete` already do. Also pass `confirmDisabled` to both `ConfirmDialog`s while the write runs.

### B-WR-07: The "Added …" snackbar is lost if the screen unmounts before the readback, and can fire over another screen

**File:**
- `src/screens/EditGroupEventScreen.tsx:145-168, 261-269`
- `src/screens/GroupEventDetailScreen.tsx:99-124, 148-156`

**Issue:** `createParticipantAddAnnouncer` announces only from the refresh controller's settle.
- **Lost on unmount.** Both screens invalidate the controller on unmount (`:167`, `:124`). On Edit Event, adding participants and then tapping Save or Back before the post-add readback settles invalidates that read, so the D-67 "Added Maya" confirmation never shows. The write committed, but nothing confirmed it.
- **Fires on another screen.** Neither controller is invalidated on blur. A readback that settles after a push (for example, an add followed immediately by Edit for a participant) shows its snackbar on the next screen. ADR-162 / `latest-request.ts:25-26` say to invalidate on blur and on unmount.

**Fix:** On unmount, flush a pending announcement by count before invalidating, for example an `announcer.flush()` that announces `participantsAddedSnackbar([], n)`. Or announce from `onCommitted` by count and upgrade to names only when the readback is still current. Decide explicitly whether a blur should invalidate. If it should, add a `useFocusEffect` cleanup and keep the focus refresh.
