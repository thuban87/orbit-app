# Phase 38.14 Plan 07: Edit Event rename, one participant editor, Remove from event and group-event publication Summary

**You can now rename an event on Edit Event. A blank title shows "An event needs a title." under the field, and the DAO trims the title and refuses a blank one again. Edit Event no longer has its own participant sheet: Edit opens the Edit participant screen, and coming back re-reads the participants without touching unsaved event edits. Adding or removing someone confirms by name. Remove from event offers Keep first and asks before Delete. Every group-event write now updates the widget and refreshes the rest of the app.**

## Accomplishments

- **D-69 / D-48 (DAO).** `UpdateGroupEventPatch.title?: { value: string }`.
  - `updateGroupEvent` rejects a blank title (after trim) before it opens the transaction: "updateGroupEvent: title must not be blank".
  - The exported `updateGroupEventCore` refuses a blank title again, before any statement runs.
  - The core runs `UPDATE group_events SET title = ?, modified_at = ? WHERE id = ?` with the trimmed value as a bound parameter, asserts `changes === 1` and sets `changed`, so the wrapper bumps the revision once.
  - No child row is touched and there is no schema change (head stays 034).
  - Five DAO cases cover this: trim with modified_at, one bump and children untouched; blank "" and "   " refused with no bump; the core guard; an unknown id; rollback when a later write in the same save fails.
- **Writers of `group_events.title` read before the change:** `createGroupEvent` (:366), `convertInteractionToGroupEvent` (:945), the restore upsert (`restore-apply.ts:861`), and now `updateGroupEventCore`. No other `UPDATE group_events` touches the title.
- **D-69 (screen).** `EventDraft.title` is seeded by `eventDraft()`. Edit Event has a Title field, a raw `TextInput` like Group Log's, with "Name this event" as its placeholder. It updates the draft through `type: "draftChanged"`.
  - When Save is pressed with a blank title, `FieldError` shows the rule under the field and `useFirstErrorReveal` scrolls to it and focuses it. Save stays pressable.
  - `saveEvent` sends `patch.title` only when the trimmed title differs from the saved one.
  - The discard guard covers the title through dirty detection.
- **D-68.** The inline participant `<Sheet>` is gone, along with `ParticipantOverrideEditor`, `saveParticipant` and its state (`editing`, `participantDraftState`, `participantSavingRef`, `participantFieldErrors`). The row's Edit button navigates to `EditParticipant`.
  - A skip-first `useFocusEffect` calls `refreshEvent()` on later focuses. `eventRefreshed` replaces only the event, so the draft and its baseline survive (D-07; ADR-167).
  - The `:388-404` pin still holds (three `refreshEvent` references).
- **D-67.** After a committed add, the next readback names the new people in a success snackbar. After a committed remove: "Removed Maya" (success look) or "Removed Maya and deleted the interaction" (warning look). The writes stay immediate (R6 is still rejected).
- **D-70 / D-27 / D-05.** `REMOVE_PARTICIPANT_CHOICES` lists Keep, then Delete, then Cancel.
  - `confirmThenDelete(latch, confirmFn, onDelete)` is single-flight: a double tap opens one confirm and deletes at most once. It releases its latch in `finally`.
  - The sheet confirms Delete with the standard destructive `confirm()`, and the host's `onDelete` runs only on true.
  - The heading now reads "…from this event?".
  - Both hosts (Edit Event and the event screen) get this without any host change.
- **D-27 / D-81 publication.** `publishInteractionWrite()` calls `notifyWidgetDataChanged()`, then `bumpShellRefresh()`. Each call has its own try/catch with a content-free log, and nothing is rethrown. It runs after:
  - on the event screen: participant add and remove (inside `onCommitted`), dissolve, and delete event;
  - on Edit Event: save, participant add and participant remove;
  - Group Log save;
  - EditParticipant save;
  - "Make this an event" (the conversion's `onCreated`).
