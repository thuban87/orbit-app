## Summary

Every decision in this phase lands on existing seams. No new package, migration or schema change is needed (D-17). The hardest parts are four seams.

The first is the **assist seam** (D-23 / D-77). `useAssistBanner` today publishes `queue`, `newest` and `morePendingCount` straight from the DB read. The clean design stores the raw eligible read plus two in-memory skip inputs: a panel-owned assist **uid** and a Later set of uids. Every publication re-derives the visible queue through one pure function. The Later set is released only in `subscribeAppState`'s background→active branch and on launch, never inside `refresh()`, because `refresh()` also runs on every assist publication and on the Settings toggle.

The second is the **Compose pinned bar** (D-75). No screen in the repo pins an action bar above the keyboard yet. The closest pattern is the resting-frame keyboard lift that `CaptureScreen` and `Sheet` compute with `sheetKeyboardLayout`. The third is the **bulk re-channel** (D-62). It composes `editTouchpointFullCore` per receipt row inside one `inWriteTransaction` with one revision bump, reading each stored row first the way `editInteractionNoteCore` does.

The fourth is **Profile S2 typography** (D-52 / D-56). The global `TYPOGRAPHY` table is pinned by a test that reads "exactly five roles over exactly four sizes (28/20/16/14)" (dossier §H). A 26-size H1 added to `TYPOGRAPHY` would break that recorded contract. A separate, Profile-scoped heading-scale token in the same file avoids reversing it.

The repo has **no react-test-renderer**. Screen tests are function-call renders with a mocked React (`useState` slots seeded by call order). That makes a full ComposeScreen render test (25+ state slots) brittle. Pure-logic extraction plus a small panel component is the practical way to meet D-48.

**Primary recommendation:** about 8 plans grouped by area: assist and "Did you send it?", Compose screen UX, one-tap logging, logging forms, interaction sheet and History, Profile layout, Group Events, and a final device plan. Each D-NN maps to exactly one area (§ Natural Grouping).

### Pattern 1: Assist store with derived visibility (D-23, D-77)

**What exists** [VERIFIED: `src/stores/assist-store.ts:19-24, 38-48, 52-67`]:
```ts
type AssistBannerStore = {
  queue: EligiblePendingAssist[];
  newest: EligiblePendingAssist | null;
  morePendingCount: number;
  refresh: () => Promise<void>;
};
...
    const queue = await listEligiblePendingAssists(getExecutor(), now);
    if (!queueRefreshAuthority.isCurrent(token)) return;
    const { newest, morePendingCount } = selectBannerState(queue, now);
    set({ queue, newest, morePendingCount });
...
    if (previous === "background" && next === "active") {
      useAssistBanner
        .getState()
        .refresh()
```
- Who reads it [VERIFIED by grep]. `AssistBanner` reads `newest`, `morePendingCount` and `refresh`. `PendingConfirmationsSheet` reads `queue` and `refresh`, and lists **all** eligible rows, including the banner's newest. `ComposeScreen` (:1116, :1148), `SettingsInteractionsScreen` (:104) and `App.tsx` call `refresh()`. `countPending` (`interaction-assist-read.ts:53`) has no non-test consumer.
- The row identity Compose holds is the **uid**: `ComposeScreen.tsx:268` `const [confirm, setConfirm] = useState<{ assistUid: string } | null>(null);` [VERIFIED]. Key the skips on `uid`. The CONTEXT says "record id"; uid is the identifier Compose actually has, and the banner and list already key on `uid`.

**Recommended shape** (this research only):
- Add `rawQueue`, `panelOwnedUid: string | null`, `laterUids: ReadonlySet<string>`, and setters `setPanelOwned(uid | null)`, `deferUntilReturn(uid)` and `releaseDeferred()`.
- `refresh()` stores `rawQueue`. The setters and `refresh` all publish through one derive step: `visible = applyAssistSkips(rawQueue, { panelOwnedUid, laterUids })`, then `selectBannerState(visible, localDateTime())`, then `set({ queue: visible, newest, morePendingCount })`. The banner and sheet then need no change to their selectors. The sheet's `queue` becomes the visible list automatically.
- Put `applyAssistSkips` in `src/logic/assist-eligibility.ts`, next to `selectBannerState`. It is pure and node-testable.
- `subscribeAppState`: call `releaseDeferred()` synchronously **before** `refresh()` in the `background → active` branch. `App.tsx` launch (`void useAssistBanner.getState().refresh()` at the `ready` effect): release first as well. A cold start has an empty set anyway, but D-77 names launch.
- **Do not release inside `refresh()`.** Refresh runs on every assist publication (`publishAssistCommit` / `publishAssistDismissal` `refreshQueue`) and on the Settings toggle. Releasing there would re-ask within seconds, which is the rejected Q17-A/B (CONTEXT `<specifics>`).
- Nothing watches a timestamp (CLAUDE.md "Nothing watches a timestamp"; D-09). The 15 s eligibility stays in SQL (`interaction-assist-read.ts` `ELIGIBILITY_SQL`) and in `isAssistEligible`, unchanged.

**Compose wiring** (this research only):
- Set the owner where `setConfirm({ assistUid })` runs (`onTransmit`). Clear it in `onConfirmYes` (done or closed), in the new No handler, and in Later. Clear it in the focus effect's cleanup (blur/unmount: `useFocusEffect` cleanup near :789-796). In the focus effect, set it again when `confirm !== null`.
- Pitfall: app background does **not** fire a `useFocusEffect` blur, so the owner survives the trip to the SMS or email app. That is the desired behaviour for email, where the panel appears at once.
- The panel's answers become **Yes, log it / No, don't log / Later** (D-01). The panel is Text/Email only, so "No answer" never appears there.
- `ComposeExit` (`compose-logic.ts:248-253` `"back" | "transmit-pending" | "not-yet" | "logged" | "copy"` [VERIFIED]) gains or renames entries for Later and Dismissed. `compose-logic.test.ts:319-341` is rewritten (CONTEXT `<verification>`).

**Answer order (D-73)** [VERIFIED: `AssistConfirmation.tsx:75-127` renders Yes, then No answer (call only), then Don't log, in a `flexDirection: "row", flexWrap: "wrap", justifyContent: "flex-end"` row at `:167-172`]. Reorder to Don't log, [No answer], Yes so Yes sits on the right. The row uses plain `flexWrap`, the alternative D-11 / ADR-174 rejected. Whether to convert it to measure-and-stack while touching it is an open question (Q3 below).

### Pattern 3: Compose pinned actions above the keyboard (D-75)

What exists [VERIFIED]:

## Common Pitfalls

### Pitfall 1: No react-test-renderer
**What goes wrong:** a planner asks for "ComposeScreen render tests" (D-48) as if RNTL existed.
**Why:** `vitest.config.ts` runs `environment: "node"`. Screen tests mock `react` hooks and seed `useState` slots by call order (`group-log-save-render.test.tsx`; `YourWeekSection.test.tsx` says "the repo has no react-test-renderer").
**How to avoid:** extract the panel state machine to a pure module plus a small `ComposeConfirmPanel` component. Test those, and the assist-store derive, in node. Keep any ComposeScreen-level test to a source scan or a narrow slot-seeded render.

### Pitfall 2: Orphaned test consumers break tsc
**What goes wrong:** changing `QuickLogSnackbar.action`, `ComposeExit`, `EventDraft` or `bulkQuickLog`'s signature leaves `*.test.ts` asserting the old contract, and `tsc --noEmit` fails while vitest passes (memory `orphaned-test-consumer-build-breaker`, `tsc-in-post-merge-gate`).
**How to avoid:** grep every consumer, tests included, and put each in the plan that changes the symbol. The CONTEXT `<verification>` list names the known ones.

### Pitfall 3: Source-scan tests pin current code shape
Known pins: `group-event-refresh.test.ts:388-404, 607-631`; `overview-geometry.test.ts:159-182` (regexes on three style sites); `sheet-consumers-contract.test.ts` (`EXPECTED_OPT_OUTS`); `typography.test.ts:40-51`; `control-a11y-contract.test.ts:259` (D-39). Update them in the same plan that changes the code.

### Pitfall 4: AppState on handoff (LIKELY)
Opening the SMS composer or mail app moves Orbit to `background`. Returning fires `background → active`, which releases the Later set and refreshes. That matches D-77 ("until the next time the user returns to Orbit"). A Later tapped **before** leaving is released on the way back. The device plan should check SMS and email both ways, as the CONTEXT already lists.

### Pitfall 5: The settings read throws in a one-tap path
`getAppSettings` throws when the row is missing. In the headless widget and notification paths an uncaught throw drops the user's tap. Always fall back to "Message", the documented fallback (`log-interaction-logic.ts` `REMEMBERED_FALLBACK`).

### Pitfall 6: Heatmap labels versus fit-to-width
New labels change the available width and height for cells. Reserve them in the fit math, or the Year grid clips at large text (ADR-174).

### Pitfall 7: Worklet forward references
Not directly relevant; no worklets are planned. If the Compose bar uses Reanimated, define helpers above their callers (memory `worklet-forward-ref-hazard`).

### Pitfall 8: Hermes `crypto`
Not touched. `newUid` is already in use (memory `hermes-crypto-guard`).

export function rechannelBulkQuickLog(exec: SqlExecutor, receipt: QuickLogBatchReceipt, channel: string, now: string): Promise<void> {
  if (receipt.length === 0) return Promise.resolve();
  return inWriteTransaction(exec, async () => {
    for (const { contactId, interactionId } of receipt) {
      const row = await exec.getFirstAsync<{ occurred_at: string; direction: string | null; connected: number; quality: string | null; note: string | null; duration: number | null; allow_ai: number; group_event_id: number | null }>(
        `SELECT occurred_at, direction, connected, quality, note, duration, allow_ai, group_event_id
           FROM interactions WHERE id = ? AND contact_id = ?`, [interactionId, contactId]);
      if (!row || row.group_event_id !== null) continue; // planner decides (a)/(b)
      await editTouchpointFullCore(exec, { interactionId, contactId, now, occurredAt: row.occurred_at,
        channel, direction: row.direction, connected: row.connected, quality: row.quality,
        note: row.note, duration: row.duration, allowAi: row.allow_ai });
    }
    await bumpDataRevisionCore(exec);
  });
}
