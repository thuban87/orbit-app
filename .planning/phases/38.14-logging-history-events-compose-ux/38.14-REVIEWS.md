**R4-03 · LOW · CODE · plan 08 Task 1 step 2 (`38.14-08-PLAN.md:138`) · codex (rated MEDIUM; orchestrator LOW, see note) · my-bucket · neighbour of R3-05**
Step 2 says closing search clears `term` "(and invalidate[s])". When the term is already blank (search opened and closed without typing), `setTerm("")` changes nothing. The term-load effect's deps `[isFocused, term, load]` do not change, so no new read starts. The invalidation discards the read in flight: `invalidate()` only advances the generation (`src/utils/latest-request.ts:45`).
- If that read was the first load, `loading` stays `true` (initial value, `GroupEventsScreen.tsx:39`) and the spinner sticks until the next refocus.
- If it was a refocus read, the list misses the rename, dissolve or delete it was fetching.

R3-05's fix covers an invalidated first read followed by another read. It does not cover an invalidation with no replacement.

*Severity note:* the window is the length of one local SQLite read, so it is hard to hit. The outcome when hit (a stuck spinner) is why it still counts.

**Plan edit (step 2):** closing search clears `term` but does not invalidate. A changed term starts a new read, which supersedes the old one through the latest-request authority (`begin()`). An unchanged blank term lets the in-flight read publish, which is correct because it is already a read of the blank term. Add a harness case: initial read pending → open search → close with an empty term → resolve the read → rows publish and `loading` is false.
