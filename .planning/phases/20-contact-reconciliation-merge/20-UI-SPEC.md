# Phase 20 — Contact Reconciliation & Merge — UI Design Contract

> Visual and interaction contract for Phase 20's net-new reconciliation and merge surfaces.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker. This app is a mature React
> Native / Expo, Android-first, portrait-locked application (19 phases shipped). This spec fits
> the EXISTING `src/theme` token system and reuses shipped `src/components` / `src/screens`
> patterns — it invents no new design system. Every value below was read out of shipped code,
> not assumed. The dossier (`docs/dossier/20-contact-reconciliation-merge.md`) is the
> authoritative product source; its `[DECIDED]`/`[REJECTED]` statements are locked constraints.

## Scope of this contract

The dossier already prescribes the reconciliation grid (reused from Phase 19). This spec's
highest-value contribution is the **net-new merge surfaces**, the reconciliation **detail** view,
and the **carried-forward bulk-review** surface. Numbered surfaces (E-prefixed for the UI probe):

**Reconciliation (System Contacts → Orbit, one-way, user-triggered)**
1. Entry points — per-contact `Update from Contacts` (profile overflow) + Settings `Check linked contacts`.
2. Scanning / progress state during `Check linked contacts` (Cluster F).
3. Reconciliation **card-grid workspace** (Cluster H) — reuses the shipped `CandidateCardGrid` unchanged, now wiring the `onInspect` detail and the `apply-recommendation` / keep-Orbit bulk actions Phase 19 reserved.
4. Reconciliation **detail** view (Cluster C/I/M/N) — per-field change list, recommendation states, multi-source attribution, per-field A-vs-B(-vs-C) resolution.
5. Per-field **scalar choice widget** (Cluster C conflict, W merge fixed-field, Z custom-field scalar) — one reusable renderer.
6. **Photo** reconciliation — side-by-side choice when no reliable fingerprint (Cluster Q).
7. **Missing source** state + **Relink** (Cluster G, L).
8. Reconciliation **completion summary** (Cluster S).
9. Durable **Resume / Discard** prompt for an unresolved reconciliation session (Cluster R).

**Orbit-to-Orbit Merge (explicit, serious, atomic, no simple undo)**
10. Merge entry points — reconciliation/duplicate detail + profile overflow `Merge with another contact` (Cluster U).
11. **Survivor selection** (Cluster V) — user picks survivor; Orbit badges a recommended survivor with advisory continuity signals.
12. Merge **field-conflict resolution** (Cluster W, Z) — reuses the #5 scalar choice widget; primary-method contention (Cluster X).
13. Merge **impact-summary confirmation** (Cluster AC) — counts, "X will be retired", "cannot be simply undone", one atomic confirm.

**Carried forward from Phase 19.1 (owner-approved 2026-08-30)**
14. **Bulk review surface** — per-item unparseable-birthday flags (and other bulk-review cases) the user resolves, living alongside the reconciliation workspace.

**Out of scope of this contract (dossier-locked deferrals):** background polling, source write-back,
generic sync/versioning UI, visual-similarity photo matching, Interaction Assist. Do not design surfaces for these.

## ⚠ Code-grounded corrections / constraints the planner must honor

1. **`CandidateCardGrid` is already the reusable contract.** It ships with `onInspect(item)`,
   an `apply-recommendation` bulk action that filters out `recommendationExcludes` items, a
   `scoring` progress state, per-card long-press multi-select, per-card failure isolation
   (`failedIds`), and a bottom action bar. Phase 20 **consumes these seams**; it must not
   re-implement grid mechanics. The `recommendationExcludes: "needs_review"` prop is the locked
   safety gate that keeps a bulk "apply recommendation" from ever resolving a genuine conflict
   card — reconciliation's "conflicts require manual review" invariant (Cluster I/J) maps onto it.
2. **`Use Contact Values` is additive-only (Cluster J, locked).** A bulk source-wins action must
   be **absent or disabled** for any selection containing a conflicting/removal card. The grid's
   `bulkActions` prop is caller-controlled — pass `Use Contact Values` only when every selected
   card is additive-only. Never let a bulk source-wins action overwrite a name/birthday.
3. **No new "caution/warning" colour token.** Recommendation states are **advisory**, not
   identity or destruction. Render them exactly like the confidence ladder: a `surfaceElevated`
   chip with a `13px/600 textSecondary` label, **colourless**. Do not borrow `rogue`,
   `statusWobble`, `statusDecay`, or `accent` to color-code a recommendation. (Same rule the
   Phase 19 checker locked.)
4. **`danger` (red) is destructive-action emphasis only.** Merge is a serious no-undo operation,
   but it *consolidates* data rather than deleting it, so the confirm button is **accent** (the
   intended primary action) while the "this can't be simply undone" / "X will be retired" warning
   line carries the `danger` emphasis. Discard-of-a-session stays `danger` (matches the shipped
   `ResumeImportPrompt` discard button). See Color.
5. **Photos and staged paths never go to `Avatar`.** `Avatar`'s resolver throws synchronously on a
   raw/staged path. Every photo (Orbit-owned or source) must be a **pre-resolved file URI** passed
   to `expo-image`'s `Image` with an `onError` fall-through to `Avatar photo={null}`. This bit
   Phase 19; do not regress it in the photo-choice surface.
6. **Spacing/typography have no central token module** — they are inline per-`StyleSheet`. Match the
   de-facto shipped scales below; do not introduce a divergent scale or new font sizes.

## Color

All values are `space-dark` dark-palette tokens (`theme-presets.ts`). Consume via
`useTheme().colors.*`. **Never** write a hex literal in a screen/component (`check:colors` gate + CLAUDE.md).

| Role | Token → value | Usage |
|------|---------------|-------|
| Dominant (60%) | `background` `#0B0E1A` | Screen roots, on-accent button-label text, modal scrim (at 0.85 opacity) |
| Secondary (30%) | `surface` `#141828`, `surfaceElevated` `#1D2235` | Cards, rows, inputs, count rows (`surface`); modal sheets + advisory chips (`surfaceElevated`) |
| Accent (10%) | `accent` `#6C8CFF` | See reserved list below |
| Destructive | `danger` `#E5484D` | Destructive-action emphasis ONLY (see below) |
| Borders | `border` `#2A3048`, `borderStrong` `#3C4568` | Default 1px borders; `borderStrong` on selected/active outlines |
| Text | `textPrimary` `#E6E9F5`, `textSecondary` `#8B93B0` | Primary content; labels/helpers/secondary lines/advisory chip labels |

**Accent (`#6C8CFF`) is reserved for, and ONLY for:**
- primary CTA fills (`Update from Contacts` when it is the recommended action, `Apply`, `Continue`, `Merge contacts`, `Done`, `Resume`),
- the **selected** option in a `FieldChoiceGroup` / `PhotoChoice` / survivor card (selected outline `borderStrong`, selected fill or check accent),
- the **recommended-survivor** badge and the **recommended-value** marker in a choice group,
- pressed-state text links and the progress/scan spinner tint.

Accent is **never** applied to every interactive element, never to advisory recommendation chips,
and never to the overflow `⋯` trigger.

**`danger` (`#E5484D`) is used for, and ONLY for:**
- the `Discard` session button (matches shipped `ResumeImportPrompt`),
- the merge warning line — `This can't be simply undone.` and `{name} will be retired.` (text emphasis),
- the `Remove` (source-removal) option label inside a choice group, which is never the recommended pick.

The merge **confirm button itself is `accent`**, not `danger` (merge consolidates, it does not
delete). The seriousness is carried by copy + the `danger` warning line + the impact counts, and by
the OS-native `Alert.alert({ style: "destructive" })` final tap-guard (see surface #13).

**Recommendation-state rule (locked):** reconciliation recommendations (`Add` / `Use Contact Value`
/ `Keep Orbit` / `Manual review` / `Source missing`) render as **colourless** `surfaceElevated`
chips with `textSecondary` labels. Colour carries no recommendation meaning. If the owner later
wants a caution hue, that is a **new token** and an owner decision — flag it, do not inline a hex.

## Reusable widget contract — `FieldChoiceGroup` (surfaces #5, #12)

The single scalar A-vs-B(-vs-C) resolver. One renderer, three call sites (reconciliation conflict,
merge fixed field, merge custom-field scalar) — do not fork per call site (Cluster Z requires reuse).

- **Shape:** a labeled field group. Header = the field label (`13px/600 textSecondary`, e.g. `Name`,
  `Birthday`, `Category`, or a custom-field label). Below it, **2..N option rows**, each a `Pressable`
  (`≥44px`, radius 10, `surface` bg, `border`). Exactly one option is selected at a time
  (single-select radio semantics); the selected row gets a `borderStrong` outline + an accent check `✓`.
- **Each option row shows:** the value (`15px/400 textPrimary`) + a provenance/source label
  (`13px/400 textSecondary`) — `Orbit`, `Contacts (Pixel · Google)`, `Contacts (Work)`, etc. For
  multi-source disagreement (Cluster N) each disagreeing source is its own option with its own label;
  Orbit never auto-picks (dossier N).
- **Recommendation marker:** the recommended option carries a small colourless `Recommended` chip
  (advisory, `surfaceElevated`/`textSecondary`) and is **preselected**:
  - additive → source value preselected, deselectable (user can fall back to Orbit / no-value) (Cluster C/I),
  - conflicting → **no** preselection; user must choose explicitly (Cluster C — "explicit manual choice"),
  - removed-from-source → Orbit value preselected + recommended; a `Remove` option exists but is `danger`-labeled and never recommended (Cluster C — never auto-delete).
- **Never destroys the non-chosen value silently** — a merge/reconcile write only applies the
  selected value; unselected values are simply not written (they still live on their own record until
  a tombstone/retire, per the data layer). The widget itself performs no DB writes; it returns the
  user's selection to the screen.
- **Empty/degenerate:** if only one value exists (no conflict), the field does **not** render as a
  choice group at all — non-conflicting data combines automatically (Cluster W/Z) and is shown, if at
  all, as a read-only combined line. `FieldChoiceGroup` appears only where a genuine scalar conflict exists.

`PhotoChoice` (surface #6) is a photo-specialized sibling: two (or N) photo thumbnails side by side
(`expo-image`, resolved URIs, `Avatar` fallback), each tappable to select, plus an explicit
`No meaningful change — keep Orbit photo` option (Cluster Q). Same selected-outline idiom.

## Screen-by-screen interaction contract

### 1. Entry points (Cluster E, U)
- **Profile overflow `⋯`** gains two rows via `OverflowMenu`: `Update from Contacts` (only shown when
  the contact has ≥1 active system link) and `Merge with another contact` (always available). Neither
  is styled destructive at the menu level (the merge seriousness lives on its confirmation screen).
- **Settings → Contacts Integration** gains one row: `Check linked contacts`, beside the existing
  `Import contacts`. Reuse the shipped `section` / `sectionHeading` idiom verbatim.
- All reconciliation is **user-triggered** — no passive/scheduled affordance anywhere (Cluster E, locked).

### 2. Scanning / progress (Cluster F)
- `Check linked contacts` shows a determinate/in-progress scan surface while linked contacts are
  compared. Reuse `CandidateCardGrid`'s `scoring` state, relabeled `Checking linked contacts…`
  (`textSecondary`, centered). Never a frozen blank. Per-contact `Update from Contacts` scans one
  contact inline (brief spinner on the invoking control), then routes to the detail (#4) if there are
  changes, or shows a calm `No changes from Contacts.` inline message if none.

### 3. Reconciliation card grid (Cluster H) — REUSE `CandidateCardGrid` unchanged
- `FlatList numColumns={2}`, portrait pairs. Each card: the Orbit person's photo (resolved URI →
  `Image`, else `Avatar`), name (`15px`), an advisory **recommendation chip** (colourless), and a
  one-line change summary hint (`13px textSecondary`, e.g. `2 additions · 1 conflict` or `Source
  missing`). Card `surface` bg, `border`, radius 10, `≥44px`.
- **Tap** → detail (#4) — wire `onInspect` (Phase 19 left it a no-op). **Long-press** → multi-select;
  selected cards get the shipped `borderStrong` outline. In multi-select a bottom action bar offers
  the caller-enabled bulk actions:
  - `Apply Recommendations` (uses `apply-recommendation`; the `recommendationExcludes: "needs_review"`
    gate keeps conflicts unresolved) (Cluster I/J),
  - `Keep Orbit Values` (Cluster J),
  - `Use Contact Values` — **only present when every selected card is additive-only** (Cluster J, locked).
- **Unchanged contacts never appear as cards** (Cluster F) — they exist only in the summary count.
- **Partially-resolved cards remain** in the grid until all actionable differences resolve (Cluster K);
  their hint reflects the remaining unresolved count (e.g. `1 of 3 left`).
- Multiple source links for one Orbit person combine into **one** card (Cluster M) — never `Sarah —
  source A` / `Sarah — source B`.

### 4. Reconciliation detail — `ReconcileDetailScreen` (Cluster C/I/M/N)
- Header (Back + `24px` title = the contact's name). Below: a scrollable per-field change list. Each
  changed field renders a `FieldChoiceGroup` (#5) or `PhotoChoice` (#6). Non-conflicting additive
  values render as a preselected-source choice; direct conflicts render unselected (manual);
  removed-from-source render Orbit-preselected.
- **Multi-source attribution (Cluster M/N):** every proposed value shows which source record
  contributed it via the option's provenance label. When two source records disagree, both appear as
  separate options with their source labels; Orbit is also an option; nothing is auto-chosen.
- Primary CTA `Apply` (accent) applies the selected values for this contact through the existing
  authoritative write/recompute paths; it stays disabled until every conflict field has a selection
  (additive/removal fields are preselected so they never block). Derived values (`last_contact`,
  gravity, status…) are **recomputed, never shown as a choosable field** (Cluster AA).
- The card returns to the grid marked resolved (or partially resolved if the user leaves early —
  Cluster K/R).

### 5. Per-field scalar choice — `FieldChoiceGroup`
- Contract above. Used inline in #4 and #12.

### 6. Photo reconciliation — `PhotoChoice` (Cluster Q)
- When the source fingerprint changed (or no reliable fingerprint exists), show Orbit photo and source
  photo(s) side by side, each tappable, plus `No meaningful change — keep Orbit photo`. No AI/visual
  similarity (locked). Resolved URIs only; `Avatar` fallback on decode error.

### 7. Missing source + Relink (Cluster G, L)
- A missing/unresolvable linked source is a **distinct** card/detail state (not "all fields removed").
  Its recommendation chip reads `Source missing`. The detail offers exactly three actions — `Keep as
  is` (default, accent-neutral), `Relink to another contact` (opens the system picker; on selection,
  retire the stale link, attach the new source, and immediately re-run reconciliation against it —
  Cluster L), `Unlink source` (removes the link only). **Never** deletes/archives/unbinds the Orbit
  contact or clears its fields (Cluster G, locked). No Orbit relationship data resets on relink.

### 8. Reconciliation completion summary — reuse the `footerEntry` idiom (Cluster S)
- Header `Check complete`. Count rows (reuse `ImportComplete`'s `footerEntry`): `Checked (n)`,
  `Changed (n)`, `Updated (n)`, `Kept Orbit values (n)`, `Source missing (n)`. Actions: `View
  unresolved` (→ grid, shown only when unresolved > 0), `Done` (accent). Zero-change run still shows
  the summary with `Changed (0)` — a calm confirmation, not an error.

### 9. Resume / Discard reconciliation session — reuse `ResumeImportPrompt` idiom (Cluster R)
- On app return with an unresolved reconciliation session, present the same non-tap-dismissable Modal
  sheet: heading `Resume your check?`, body `Unresolved contacts are saved. Changes you already
  applied stay applied.` Buttons `Resume` (accent) / `Discard` (`danger` — discards only unresolved
  review state; applied changes persist; state this in the body). Durable across process death /
  reboot / long absence; already-applied resolutions remain applied (Cluster R, locked).

### 10. Merge entry (Cluster U)
- From reconciliation/duplicate detail: a `Merge with another contact` affordance. From a profile:
  the overflow row (#1). Both route into survivor selection (#11) with the two candidate contacts.

### 11. Survivor selection — `SurvivorSelect` (Cluster V)
- Header (Back + title `Which contact survives?`). Two contact cards stacked (portrait), each showing
  avatar + name + a short continuity-signal line (`13px textSecondary`, e.g. `Added Jan 2024 · 23
  interactions · linked to Contacts`). Orbit **badges one as `Recommended`** (colourless advisory
  chip) using continuity signals (older creation, richer history, stronger linkage, more complete data)
  and **preselects it** — advisory, fully overridable (Cluster V). Selected card = `borderStrong` +
  accent check. Primary CTA `Continue` (accent) → field-conflict resolution (#12). Exactly one
  survivor results; the other is absorbed (Cluster V, locked).

### 12. Merge field-conflict resolution (Cluster W, X, Z)
- Only conflicting scalar fields render — non-conflicting fixed + custom values combine automatically
  (Cluster W/Z); identical canonical methods dedupe; distinct methods are all preserved (Cluster X) —
  none of that is shown as a choice. Each genuine scalar conflict (name, birthday, category, photo,
  scalar custom fields) renders a `FieldChoiceGroup` (#5) / `PhotoChoice` (#6), survivor value
  preselected but overridable.
- **Primary-method contention (Cluster X):** a primary phone/email choice appears **only when both
  contacts contribute competing primary methods**; otherwise deterministic promotion applies silently.
  Reuse `ContactMethodsEditor`'s primary-choose model for that one case.
- Child data (interactions, fuel, events, links) is **never** shown row-by-row — it consolidates
  automatically (Cluster Y). Primary CTA `Continue` (accent) → impact summary (#13).

### 13. Merge impact-summary confirmation — `MergeImpactSummary` (Cluster AC) — SERIOUS, NO SIMPLE UNDO
- Header `Confirm merge`. A one-line subject: `Merge {absorbed} into {survivor}`. Count rows (reuse
  `footerEntry`): `{n} interactions`, `{n} fuel items`, `{n} events`, `{n} contact methods`, `{n}
  external links` — the exact things moving to the survivor (Cluster AC example). Then a **`danger`
  warning block** (`15px/600`): `{absorbed} will be retired.` and `This can't be simply undone.`
- Primary CTA `Merge contacts` (**accent** fill — the intended action). On tap, an OS-native
  `Alert.alert` destructive-style final guard (`Merge` / `Cancel`) precedes the write — matching the
  app's pattern of a native destructive confirm for irreversible actions, with the rich summary on the
  screen (an `Alert` can't hold the counts).
- The merge is **atomic/transactional** — full consolidation succeeds or nothing changes; no partial
  state is renderable (Cluster AC, locked). On success → the survivor's profile. On failure → stay on
  the summary with an inline error (`Couldn't merge these contacts. Nothing was changed.`) and a
  `Try again`; the absorbed contact is untouched.
- The absorbed identity is **retired/tombstoned, not archived** (Cluster AB/RCN-04) — it does not
  appear in the Archived list and is not restorable through the normal archive lifecycle. No UI offers
  to "unarchive" or resurrect it.

### 14. Bulk review surface — `BulkReviewScreen` (carried forward from Phase 19.1)
- Lives alongside the reconciliation workspace. Surfaces **per-item flags** the bulk pipeline only
  *counted* before (Phase 19.1 counts `N birthdays couldn't be read` on the completion summary; the raw
  value is retained in the import row's `source_payload`). Header `Review flagged items`. A single-column
  list; each row shows the contact name + the raw unreadable value (`13px textSecondary`, e.g.
  `Birthday: "next tuesday" — couldn't be read`) + two affordances: `Fix` (opens the birthday
  `TextInput` + `normalizeEditedBirthday` + invalid-date error state, reusing the `ImportReview`
  idiom; on a valid value it clears the flag and stores the birthday) and `Ignore` (clears the flag,
  keeps no birthday — non-destructive of any existing data).
- The surface is generic over "bulk review cases" (birthday is the first) so a later flag type reuses
  the same row idiom. Durable: flags persist until resolved (consistent with Cluster R durability).
- **Empty state:** heading `Nothing to review`, body `No flagged items right now.`

## Notes for the checker / planner

- **Merge confirm colour (accent vs danger) is the one taste-adjacent call.** This spec prescribes
  **accent confirm + danger warning line + native destructive final guard** on the reasoning that merge
  consolidates rather than deletes, and that `danger` is reserved for destructive-action *emphasis* in
  this app (theme-types.ts documents `danger`). If the owner prefers a fully `danger`-styled confirm
  button, that is a one-line change and an owner call — flagged, not blocking.
- **`Use Contact Values` availability is a safety invariant, not styling** (Cluster J) — the planner
  must compute additive-only eligibility for the current selection and pass the action into
  `CandidateCardGrid.bulkActions` only then. Do not surface it disabled-but-present in a way that
  implies a source-wins-over-conflicts path exists.
- All six net-new components consume `useTheme().colors.*` exclusively — no colour literals
  (`check:colors` gate). The photo surfaces must resolve URIs before render and fall back to `Avatar`
  (regression guard from Phase 19).
