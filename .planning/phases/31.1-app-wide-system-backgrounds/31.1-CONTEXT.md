# Phase 31.1: App-Wide System Backgrounds — Seed Context

**Seeded:** 2026-09-10
**Discussed:** 2026-09-10
**Status:** Discussed; ready for research/planning
**Origin:** Owner-requested bounded follow-up discovered during Phase 31 physical-device testing

<domain>
## Phase Boundary

Finish the already-designed bundled background system as a production feature.
The user selects a persistent **System background** from the eight approved
local WebPs (or None/Solid). That background appears behind every regular Orbit
page, remains fixed while content scrolls, and uses the existing density-aware
surface system for readability.

There are exactly two rendering exceptions/precedence rules:

1. **Orrery is excluded.** It keeps its specialized visualization canvas.
2. **A resolved Profile photo wins.** Profile's existing resolution chain remains
   `contact photo override → Category photo assignment → global Profile photo →
   System background`. If no app-owned Profile photo resolves, Profile uses the
   selected System background.

This is a focused completion/adoption phase. It does not redo Phase 31, replace
the approved artwork, or create another background storage model.
</domain>

<decisions>
## Locked Decisions and Constraints

### Product and visual behavior

- **D-01:** The selectable System library is the eight owner-approved assets
  already committed at `assets/backgrounds/*.webp`, plus the established
  `None / Solid` option. Do not generate, solicit, or substitute new art.
- **D-02:** All eight backgrounds belong to the selectable bundled library.
  Galaxy and Standard retain their own remembered selections and package
  defaults, but the picker must not hide half of the approved library merely
  because a different package is active.
- **D-03:** The canonical selection surface is **Settings → Appearance**, where
  theme, appearance mode, and accent already live. Background selection previews
  live and persists immediately through the same store-plus-DAO pattern.
- **D-04:** System backgrounds apply behind every ordinary in-app React Native
  page, including text-heavy screens. They stay fixed while page content scrolls.
  Readability is provided by the existing semantic density/surface treatment,
  not by reverting screens to opaque full-page fills.
- **D-05:** Orrery is the intentional exception defined by the theme dossier. It
  follows shared theme tokens but does not render the selected System image.
- **D-06:** Profile photo precedence is based on the already-resolved Profile
  presentation, not only on a direct contact override. A contact-, Category-, or
  global-assigned app-owned Profile photo overrides the System background; absent
  a resolved photo, the Profile falls back to the System background.
- **D-07:** Existing Profile background templates remain a separate user-photo
  system. Preserve their picker, crop, naming, contact/Category/global assignment,
  deletion, reset, app-owned storage, and render-failure behavior. Do not merge
  bundled System assets into `profile_background_templates`.

### Architecture and data

- **D-08:** No schema migration is required. Migration 015 already added
  `app_settings.galaxy_background` and `app_settings.standard_background`; the
  DAO validates them against the canonical `BACKGROUND_SLOT_IDS`, boot hydration
  reads them, and `ThemeSelection` already carries them.
- **D-09:** Add the missing live background setter to the in-memory theme store
  and persist through `updateAppSettings`; do not introduce AsyncStorage or a
  second preference source.
- **D-10:** Reuse `src/theme/backgrounds.ts` and
  `src/components/ui/BackgroundHost.tsx` as the single asset resolver and render
  primitive. Production adoption should have one deliberate shell/navigation
  strategy, with only bounded exceptions, rather than independent background
  logic copied into every screen.
- **D-11:** Existing screen roots frequently paint `colors.background` opaquely.
  Planning must inventory the actual production navigation/screen tree and make
  those roots cooperate with the shared host without weakening opaque semantic
  surfaces needed for forms, sheets, dialogs, loading, or error states.
- **D-12:** Selection and rendering remain entirely local. No URI download,
  remote pack, telemetry, or blocking network read may enter this path. Invalid
  stored IDs fall back to the package default; runtime asset/decode failure falls
  back to None/Solid.
- **D-13:** Do not change the backup wire-format schedule. The two settings keys
  already exist in the portable-settings allowlist; Phase 36 still owns their
  coordinated emission under the milestone's closing backup-format decision.
- **D-14:** Every colour and readability layer continues to resolve through theme
  tokens. Both Galaxy and Standard, light/dark/follow-system behavior, large text,
  reduced motion, and strong AA-equivalent functional contrast remain binding.

### Delivery boundary

- **D-15:** This phase is not permission to revisit Phase 31's fixed Hero,
  section layout, drawers, crop interaction, template assignment hierarchy, or
  approved background artwork. Only integration defects directly preventing the
  System-background outcome belong here.
- **D-16:** Iterate with the droid-built debug client and Orbit Metro session
  `orbit`; build the standalone release APK only for the final native gate. Use
  `emu-connect`, dynamically resolve exactly one authorized device, and verify on
  the physical Pixel. Never use a worktree and never push.

### Discussed implementation decisions (2026-09-10 discuss-phase)

These resolve the `<discussion_targets>` below. They are HOW-details within the
locked boundary above, not reversals of D-01–D-16.

- **D-17 — Picker presentation (Appearance).** The System-background picker is an
  **inline thumbnail grid inside Settings → Appearance**, rendered **grouped by
  package** — a labeled *Galaxy* subgroup (its 4 assets) and a labeled *Standard*
  subgroup (its 4 assets), plus the shared **None / Solid** option — mirroring the
  existing accent-swatch-row idiom (inline row, live preview, immediate persist).
  All eight assets are **always visible regardless of the active package** (D-02);
  the picker must not filter by active package. Thumbnails carry human-readable
  labels and an accent-border selected-state cue, consistent with the accent row.
  Selecting a slot writes it to the **active package's** remembered column
  (`galaxy_background` / `standard_background`) via the D-09 setter + `persist()`;
  ordering/defaults per `BACKGROUND_ORDER` / `PACKAGE_DEFAULT_SLOT`.

- **D-18 — Shell mounting strategy (single root).** Adopt **one shell-level
  `BackgroundHost` mount** rather than per-screen wrappers (rejects the per-screen
  copy-paste pattern D-10 warns against). The host mounts at the tab-navigator
  shell (behind the tab scenes), and **ordinary screen roots that today paint an
  opaque `colors.background` must be made to cooperate** (transparent / density-
  scrimmed) so the fixed background shows through — **without** weakening the
  opaque semantic surfaces required by forms, sheets, dialogs, loading, and error
  states (D-11). The **Orrery tab is excluded** (D-05). Planning MUST inventory
  the real navigation/screen tree (`RootNavigator` 4-tab shell → Dashboard /
  Orrery / Backup / Settings stacks; every screen currently owns its themed root)
  and choose the smallest maintainable transparent-scene approach; bounded
  per-screen exceptions are allowed only where the single-root mount cannot serve
  a screen correctly.

- **D-19 — Reveal philosophy = presentation-forward.** Presentation-density
  screens (art prominent) are the **browse/presentation surfaces** — Dashboard/
  Home, Contact Profile, and list/browse screens (e.g. Archived, Unbound,
  Recently Deleted, Group Events, Things-to-Remember, Memory History). **Dense
  (more-opaque) scrim** applies to input/reading-dense surfaces — Create/Edit
  Contact, Custom Fields, Compose, Capture, all Settings/Backup config screens,
  import/reconcile/merge flows, crop, and every dialog / bottom sheet / loading /
  error state. This classification is the product intent; the exact per-screen
  density assignment and the **physical-Pixel device-UAT matrix** proving
  presentation pages reveal the art while dense forms stay comfortably readable
  are delegated to research/planning to enumerate against the live screen tree
  (readability always wins per D-04). Contrast/AA remains binding (D-14).

- **D-20 — No Profile → System cross-navigation.** *(Owner overrode the suggested
  small-link option.)* The two background systems stay **fully independent**:
  Profile's Background manager gains **no** link or hint to the System selector,
  and the System background is reachable **only** via Settings → Appearance. This
  reinforces D-07's separation — no shared storage and now no shared navigation.

- **D-21 — Selection transition (minor, Claude's discretion).** Background changes
  **switch immediately**; no crossfade is required. Any transition is nonessential
  and, if ever added, MUST be gated by Reduced Motion (D-14). Default is the
  immediate switch — do not add animation work for this phase.
- **D-22 — Orrery exclusion is route-based, not tab-based (owner ruling,
  convergence cycle 1).** The exclusion refines D-05: suppress the System
  background only on the actual Orrery visualization (`routeName === "Orrery"`),
  NOT on the whole OrreryTab. OrreryStack's presentation browse children
  (ThingsToRemember, RecentlyDeleted, MemoryHistory) render the System
  background regardless of which tab reached them — the same screen must not
  differ by entry tab. This resolves the D-04-vs-D-05 seam in favour of D-04's
  "behind every ordinary screen." Plan 01's shell host must gate `slotId="none"`
  on the deepest focused `routeName === "Orrery"`, not on `activeTab ===
  "OrreryTab"`. The overdraw guard is unchanged for the Orrery screen itself.
- **D-23 — SystemBuilderScreen is a bounded authoring-canvas exception (owner
  ruling, convergence cycle 1).** Like the Orrery (D-05), the System-background
  authoring canvas does NOT render the app-wide System background behind it:
  revealing the currently-selected background while the user composes a new one
  would muddy the preview. `SystemBuilderScreen.tsx:209`'s opaque Skia
  `<Fill color={colors.background} />` stays as-is. Plan 03 EXCLUDES
  SystemBuilderScreen from the flip list and records it as a sanctioned
  exception. This narrows the codex HIGH on the false Plan 03 inventory: it does
  NOT reach SystemBuilder (correctly excluded), but MergeImpactSummary
  (`src/components/MergeImpactSummary.tsx:21`, opaque `flex:1` root on an
  ordinary route) is still wrongly claimed to "already cooperate" and MUST be
  flipped.
</decisions>

<current_state>
## Existing Implementation to Reuse

- `assets/backgrounds/` contains the eight owner-approved WebPs and provenance.
- `src/theme/theme-option-ids.ts` is the single accepted background-ID source.
- `src/theme/backgrounds.ts` owns the asset manifest, stable order/defaults,
  lazy local `require()` calls, None/Solid resolution, and safe fallback.
- `src/components/ui/BackgroundHost.tsx` already renders bundled or app-owned
  backgrounds fixed behind content with density/profile scrims and a latched
  render-failure fallback.
- `src/db/app-settings-dao.ts`, migration 015, `ThemeSelection`, boot hydration,
  and backup key declarations already support per-package background values.
- `src/stores/theme-store.ts` hydrates those values but currently lacks a live
  background setter.
- `src/screens/SettingsScreen.tsx` implements package, mode, and accent controls;
  its own comment explicitly says production background adoption was deferred.
- `src/screens/ContactProfileScreen.tsx` is the only current production
  `BackgroundHost` mount and already passes a resolved app-owned Profile URI.
  Most other screen roots still paint an opaque `colors.background`.
- `src/navigation/RootNavigator.tsx` is the four-tab bottom-tab shell
  (Dashboard / Orrery / Backup / Settings), each tab a native stack with
  `headerShown: false`; every screen owns its themed root. This is the mount
  surface for D-18's single shell-root strategy and the Orrery-tab exclusion.
- `src/theme/theme-option-ids.ts` (`BACKGROUND_SLOT_IDS`, all 8 + `none`) is the
  DAO validator source; `resolveBackground()` renders any slot regardless of the
  active package, so D-02/D-17's all-8 picker is feasible with no schema change.
- `src/stores/theme-store.ts` has `setModeForActivePackage` /
  `setAccentForActivePackage` but NO background setter — the D-09 gap to fill.
- The Phase 31 crop/remediation release is recorded in
  `.planning/phases/31-profile-experience/31-12-SUMMARY.md` and
  `31-REVIEW-FIX.md`; the final verified crop commits are `00d9c56` and
  `91cc837`.
</current_state>
