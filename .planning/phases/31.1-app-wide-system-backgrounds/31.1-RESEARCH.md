## Summary

Nearly every mechanism this phase needs already exists and was verified on disk. `BackgroundHost`
renders a package-resolved background fixed behind content, applies a token-sourced density scrim,
and silently latches a render failure to None/Solid. `backgrounds.ts` resolves `(package, slotId)`
purely (NULL → package default, `none` → solid, tampered id → package default). The DAO already
declares `galaxyBackground`/`standardBackground` as writable patch keys, validates them against the
**full** 9-member `BACKGROUND_SLOT_IDS` set regardless of active package, hydrates them at boot into
the theme store, and lists both in the portable-settings allowlist. Migration 015 (schema head is
now **023** on disk — verified) shipped the columns; **no migration, table, AsyncStorage key, or
backup-format bump is needed or permitted** (D-08/D-09/D-13).

The real work is three small, well-bounded additions. (1) A one-method store setter
`setBackgroundForActivePackage`, a verbatim mirror of the existing `setAccentForActivePackage`.
(2) An inline grouped thumbnail grid in Settings → Appearance, mirroring the accent-swatch row's
"tap → live setter + `void persist(...)`" idiom. (3) A single shell-level `BackgroundHost` mounted
behind the four tab scenes in `RootNavigator`, with the navigation scene layers and ordinary screen
roots made transparent so the one host shows through — while cards/sheets/dialogs/loading/error keep
their opaque surfaces.

The two precedence rules are essentially free. **Profile fallback (D-06/PROF-05) already works by
construction**: `ContactProfileScreen` mounts its own `BackgroundHost` with
`appOwnedBackgroundUri = null` when the photo chain resolves to `source: "theme"`, and a null
app-owned URI makes that host read the active package's stored System slot — no change needed.
**Orrery exclusion (D-05) is guaranteed by leaving `OrreryScreen`'s opaque root untouched**: its
full-screen opaque canvas occludes the shell host under every camera state; optionally force the
shell host to `slotId="none"` behind the Orrery tab to avoid decoding an occluded image (overdraw).

**Primary recommendation:** Add the setter (mirror of accent), add the picker (mirror of accent
row), and adopt the single-host shell mount via a **transparent NavigationContainer theme** (one
object cascades transparency to tab scenes + native-stack content) + **omitting** the opaque
`backgroundColor` on ordinary screen roots (no `'transparent'` literal — see the check:colors
pitfall). Drive the host's density from the focused leaf route via a small `onStateChange`-fed store.
Leave Orrery's root opaque. Touch nothing in the storage, backup, or Profile-template layers.

### Pattern 2 — The picker (D-17), mirror of the accent-swatch row

**What:** Inline grouped thumbnail grid in the Appearance section, directly after the Accent row.
**When:** the sole new UI. The exact idiom to mirror is `[VERIFIED: src/screens/SettingsScreen.tsx:885-957]`:
each `Pressable` calls `setAccentForActivePackage(id); void persist(themePackage === "galaxy" ? {galaxyAccent: id} : {standardAccent: id})`, selected when `activeAccent === id`, default-selected when `activeAccent === null`, border `colors.accent` when selected else `colors.border`.

```ts
// selectors to add beside the accent ones (SettingsScreen.tsx:147-155)
const galaxyBackground = useThemeStore((s) => s.galaxyBackground);
const standardBackground = useThemeStore((s) => s.standardBackground);
const setBackgroundForActivePackage = useThemeStore((s) => s.setBackgroundForActivePackage);

// per-thumbnail onPress (slot ∈ BACKGROUND_ORDER minus trailing `none`, rendered once as None/Solid)
onPress={() => {
  setBackgroundForActivePackage(slot);                       // instant live preview (ThemeProvider)
  void persist(themePackage === "galaxy"
    ? { galaxyBackground: slot }
    : { standardBackground: slot });                         // durable DB write
}}
// selected cue: (themePackage === "galaxy" ? galaxyBackground : standardBackground) === slot,
//   with null → PACKAGE_DEFAULT_SLOT[pkg] selected (mirror of accent `activeAccent === null`).
```

- Render **both** subgroups always (D-02): iterate `BACKGROUND_ORDER.galaxy` (minus `none`) and
  `BACKGROUND_ORDER.standard` (minus `none`), then one shared None/Solid. **Do not filter by active
  package.** `[VERIFIED: src/theme/backgrounds.ts:110-128]` — the order arrays are per-package and
  each ends with `NONE_SLOT_ID`.
- Thumbnail preview uses `resolveBackground(pkg, slot).source()` — the resolver renders **any** slot
  for **any** package `[VERIFIED: src/theme/backgrounds.ts:183-205]`, so every thumbnail is previewable
  regardless of active package.
- Slot ids + order + defaults are **owned by `backgrounds.ts`** — do not re-key them. Verbatim id set
  `[VERIFIED: src/theme/theme-option-ids.ts:45-55]`: `none`, `galaxy-nebula`, `galaxy-deep-space`,
  `galaxy-aurora`, `galaxy-starfield`, `standard-dawn`, `standard-dusk`, `standard-mesh`,
  `standard-paper`. Defaults `[VERIFIED: src/theme/backgrounds.ts:135-138]`: galaxy →
  `galaxy-deep-space`, standard → `standard-dawn`.
- Accessibility + ≥44px targets per UI-SPEC; labels reflow (never truncate) at large text (D-14).
- **No cross-navigation (D-20):** do not add any link to/from Profile's Background manager.

**Consequence that is intended, not a bug (D-02/D-17):** picking a `galaxy-*` thumbnail while
Standard is active stores that id in `standard_background`. `assertBackgroundId` accepts it (validates
the full id set, not a package-scoped subset) `[VERIFIED: src/db/app-settings-dao.ts:812-822]` and
`resolveBackground` renders it.

### Pattern 3 — Single shell-root mount + transparency cascade (D-18)

**What:** One `BackgroundHost` behind all tab scenes. **Mount point:** `RootNavigator`, wrapping the
existing `SafeAreaView`/`Tab.Navigator` `[VERIFIED: src/navigation/RootNavigator.tsx:177-238]`.

**Layering (proposed):**
```
RootNavigator
  <BackgroundHost density={densityForFocusedRoute} slotId={orreryFocused ? "none" : undefined}>
    <SafeAreaView edges={["top"]}>        // existing
      <Tab.Navigator …>                   // existing
```
`BackgroundHost` renders an `absoluteFill` fixed layer then a `flex:1` content container
`[VERIFIED: src/components/ui/BackgroundHost.tsx:139-183]`, so wrapping the navigator as its children
is structurally correct. `slotId={undefined}` means the host reads the active package's stored slot
from the store `[VERIFIED: src/components/ui/BackgroundHost.tsx:96-102]`; `slotId="none"` forces solid.

**Making scenes transparent — the smallest maintainable approach:**
Native-stack defaults its `contentStyle` background, and bottom-tabs defaults its `sceneStyle`
background, to the **navigation theme's** `colors.background`. `NavigationContainer` is currently
passed **no `theme` prop** `[VERIFIED: App.tsx:364]`, so it uses React Navigation's opaque
`DefaultTheme` background. Therefore:

1. **Pass `NavigationContainer` a theme whose `colors.background` is transparent** (define the theme
   object in a `src/theme/**` module so the one `'transparent'` literal lives in the check:colors-exempt
   location — see Pitfall 1). This cascades transparency to the tab scene container and all four
   native-stack content containers **in one change**. Headers are `headerShown: false` everywhere
   `[VERIFIED: src/navigation/RootNavigator.tsx:183; src/navigation/tabs/*.tsx screenOptions]`, so
   header colours are irrelevant.
2. **Make ordinary screen roots transparent by OMITTING `backgroundColor`** rather than setting
   `'transparent'`. Screens paint e.g. `style={[styles.root, { backgroundColor: colors.background }]}`
   `[VERIFIED: src/screens/HomeScreen.tsx:1562; src/screens/OrreryScreen.tsx:1011]`. A `View` with no
   `backgroundColor` is transparent by default — drop the inline `{ backgroundColor: colors.background }`
   on the outermost container of each cooperating screen. This avoids a `'transparent'` literal entirely.

**Cooperating roots to flip (34 screens paint `colors.background`** `[VERIFIED: grep src/screens — 34 files]`**):**
Flip every ordinary screen's outermost root EXCEPT the three bounded exceptions below. The cards,
input rows, `GlassSurface`, sheets, dialogs, snackbars, and loading/error overlays **inside** those
screens keep their opaque/semi-opaque surface tokens — the background shows through the gaps
*between* surfaces, never through the surfaces themselves (D-11). Concretely, only the line that
paints the full-screen root changes; nested `{ backgroundColor: colors.surface }` fills (e.g.
`[VERIFIED: src/screens/OrreryScreen.tsx:1155-1209]` feedback surfaces) stay untouched.

**The 34 screens painting `colors.background`** `[VERIFIED: grep]`: Archived, Backup, BackupSettings,
BulkImportSetup, BulkReview, Capture, Compose, CreateContact, CropPhoto, CustomFields, Digest,
DuplicateReview, EditContact, GroupEvents, Home, ImportComplete, ImportProgress, ImportReview,
LegacyContactPicker, MemoryHistory, MergeConflicts, Orrery, FabActionPlaceholders, RecentlyDeleted,
ReconcileComplete, ReconcileDetail, ReconcileGrid, RestorePreview, RestoreResult, Settings,
SurvivorSelect, SystemBuilder, SystemsManagement, ThingsToRemember, UnboundContacts.
(ContactProfileScreen is **not** in this list — it already roots in `BackgroundHost`.)

**Per-route density wiring:** the single host's `density` must track the focused **leaf** route. The
host sits **above** `Tab.Navigator`, so `useNavigationState` has no navigator context there (it would
read a parent navigator, of which there is none). Recommended mechanism (mirrors the repo's existing
runtime-shell store idiom `[VERIFIED: src/stores/tab-bar-layout-store.ts:1-25]`): add a tiny
`focused-route-store` written from `NavigationContainer`'s `onStateChange` (the container exposes
`navigationRef` already `[VERIFIED: src/navigation/linking.ts:36]`), computing the deepest focused
route name + active tab name; the shell host subscribes. Map the route name → `SurfaceDensity` via a
helper **added to `src/navigation/focused-route-classification.ts`** (the checker's explicit
non-blocking note: extend this file rather than adding a parallel map). See Pattern 5 for the map.

### Pattern 4 — Orrery exclusion (D-05), guaranteed by the opaque Orrery root

`OrreryScreen`'s root paints `{ backgroundColor: colors.background }` opaquely
`[VERIFIED: src/screens/OrreryScreen.tsx:1011]`. **Do NOT make it cooperate** — leaving its opaque
full-screen canvas in place means it occludes the shell host under **every** camera/zoom/tilt/yaw
state, so zero System-image bleed is guaranteed structurally (not by timing). Belt-and-suspenders +
overdraw win: force the shell host to `slotId="none"` whenever the Orrery tab is the focused tab
(detect via the active-tab name from the focused-route store), so a large image is never decoded and
composited behind an opaque canvas — important because the orrery is the Skia render-loop feature and
overdraw behind it is the perf-sensitive case (CLAUDE.md). `OrreryScreen` already follows shared
theme tokens; nothing in the Orrery scene changes (D-15 / out-of-scope).

### Pattern 5 — Focused-route → density map (extend the existing classification file)

**What:** one pure helper, co-located with the existing tab-bar classification. The existing file
declares `FOCUSED_WORKFLOW_ROUTES` (a *tab-bar-hiding* allow-list) `[VERIFIED: src/navigation/focused-route-classification.ts:5-32]`.
**Density is a different concern** — it includes config roots (Settings, Backup…) that are NOT
focused-workflow — so add a separate map + function in the same module rather than reusing
`isFocusedWorkflow`:

```ts
import type { SurfaceDensity } from "@/theme/tokens/surface";

// dense = input/config/flow/overlay; comfortable = reading-dense; default = presentation (browse)
const ROUTE_DENSITY: Record<string, SurfaceDensity> = {
  Create: "dense", Edit: "dense", CustomFields: "dense", Compose: "dense", Capture: "dense",
  CropPhoto: "dense", Settings: "dense", Backup: "dense", BackupSettings: "dense",
  RestorePreview: "dense", RestoreResult: "dense", LegacyContactPicker: "dense",
  ImportReview: "dense", BulkImportSetup: "dense", ImportProgress: "dense", DuplicateReview: "dense",
  ImportComplete: "dense", BulkReview: "dense", ReconcileDetail: "dense", ReconcileGrid: "dense",
  ReconcileComplete: "dense", SurvivorSelect: "dense", MergeConflicts: "dense",
  MergeImpactSummary: "dense", SystemBuilder: "dense", SystemsManagement: "dense",
  LogContact: "dense", GroupLog: "dense", UpdateContact: "dense", Memory: "dense",
  Digest: "comfortable",
  // browse/presentation routes (Home, Profile, Archived, UnboundContacts, RecentlyDeleted,
  // GroupEvents, ThingsToRemember, MemoryHistory) intentionally absent → default presentation.
};

export function densityForRoute(routeName: string | undefined): SurfaceDensity {
  if (routeName === undefined) return "presentation";
  return ROUTE_DENSITY[routeName] ?? "presentation";
}
```

Density values are the `SurfaceDensity` union `[VERIFIED: src/theme/tokens/surface.ts:57]`
(`presentation | comfortable | dense`). The full per-screen assignment is the UI-SPEC D-19 A table
(authoritative). **Readability wins (D-04):** any row may step one tier denser if device-UAT shows a
contrast miss — never looser. The route names match the stack registrations and are stable across
the stacks that re-register a shared route (the map keys on route name).

### Anti-Patterns to Avoid
- **Per-screen `BackgroundHost` wrappers** — D-10/D-18 explicitly reject the copy-paste pattern. One shell host only (plus the two pre-existing exception hosts: Profile's own host, and Orrery's opaque canvas).
- **Writing `backgroundColor: 'transparent'` in non-theme files** — trips `check:colors` (Pitfall 1). Omit the fill, or localize the literal to a `src/theme/**` module.
- **Making `OrreryScreen`'s root transparent** — reintroduces System-image bleed into the excluded scene (D-05).
- **Merging bundled System assets into `profile_background_templates`** — violates D-07; the two systems are separate storage.
- **Any new migration/column/AsyncStorage key/backup-format bump** — violates D-08/D-09/D-13; everything already exists.
- **Rewriting `custom_field_values.value` type or adding storage** — unrelated subsystem; do not touch (CLAUDE.md custom-field invariants).

## Common Pitfalls

### Pitfall 1: `'transparent'` is a blocklisted colour literal
**What goes wrong:** `check:colors` flags `['"]transparent['"]` as a named colour OUTSIDE `src/**/theme/**`
`[VERIFIED: scripts/check-colors.sh:33-35, 56-60]` — the named list literally includes `transparent`.
Writing `backgroundColor: 'transparent'` in `RootNavigator`, a stack, or a screen **fails the gate**.
**Why it happens:** the whole strategy depends on transparency.
**How to avoid:** (a) make screen roots transparent by **omitting** `backgroundColor` (a View is
transparent by default — no literal); (b) localize the one unavoidable literal (the
`NavigationContainer` theme's `colors.background`) to a `src/theme/**` module, the sanctioned exempt
location. Existing bare `transparent` occurrences are JSX **props** (e.g. `<Modal transparent>`), not
quoted colour literals `[VERIFIED: src/components/ui/overlay-base.tsx:90; SettingsScreen.tsx:1075]`, which is why they pass.
**Warning signs:** `npm run check:colors` red after adding a nav/scene style.

### Pitfall 2: Native-stack scenes may not go transparent on Android
**What goes wrong:** `react-native-screens` (~4.26.0) backs native-stack scenes with native
containers that have an opaque window background; transparency can fail to composite even when JS
`contentStyle`/theme background is transparent, or show opaque during the `animation: "fade"` tab
transition `[VERIFIED: RootNavigator.tsx:185 animation: "fade"]`.
**Why it happens:** native fragment/window background is not the JS view background.
**How to avoid:** set transparency via the NavigationContainer theme (cascades to the native-stack
`contentStyle` default) AND verify on the **physical Pixel** (UAT rows 1, 4, 5). If a scene still
paints opaque, the bounded fallback is an explicit transparent `contentStyle` on the affected stack
(literal localized per Pitfall 1) or, last resort, a thin per-scene transparent wrapper — but never
per-screen `BackgroundHost` copies (D-10).
**Warning signs:** background invisible on a scene that should reveal it, or a white/grey flash on tab switch.

### Pitfall 3: Overdraw behind the Orrery (perf)
**What goes wrong:** a full-screen image mounted behind the opaque Orrery canvas is decoded and
composited every frame but never seen — wasted GPU on the perf-sensitive Skia feature.
**How to avoid:** force the shell host `slotId="none"` when the Orrery tab is focused (Pattern 4).
**Warning signs:** frame drops on the Orrery after the shell host lands (assess on the **physical
Pixel only** — the emulator cannot judge Orrery perf per CLAUDE.md).

### Pitfall 4: Unknown/new routes default to `presentation`
**What goes wrong:** a future screen not added to `ROUTE_DENSITY` gets the light presentation scrim;
if it is actually a dense form, text may under-contrast.
**Why it happens:** `densityForRoute` defaults unknown → `presentation` (consistent with the existing
"unknown route → browse" tab-bar philosophy).
**How to avoid:** document in the map that new input/config routes must be added as `dense`; readability
wins (D-04). Consider a unit test asserting every currently-registered route resolves to the
UI-SPEC-assigned tier.

### Pitfall 5: `sceneStyle` vs `sceneContainerStyle` (v6→v7 rename)
**What goes wrong:** bottom-tabs v7 uses `sceneStyle` (in `screenOptions`), not v6's
`sceneContainerStyle` `[VERIFIED: node_modules/@react-navigation/bottom-tabs/.../types.d.ts:226]`. The
UI-SPEC phrasing ("tab-navigator scene area") implies the v6 name.
**How to avoid:** prefer the NavigationContainer-theme cascade (no per-nav scene style needed). If an
explicit scene style is used, use `sceneStyle` under `screenOptions`.

### Pitfall 6: Breaking the per-package memory contract
**What goes wrong:** writing to the wrong column (e.g. always `galaxyBackground`) or filtering the
picker by active package (D-02 violation).
**How to avoid:** branch on `themePackage` exactly as the accent setter does (Pattern 1/2). Device-UAT
row 11 proves "active=Standard, pick Galaxy asset → Standard renders it; Galaxy keeps its own."

### Pitfall 7: Full-bleed vs safe-area for the host
**What goes wrong:** if `BackgroundHost` is placed *inside* the existing `SafeAreaView edges={["top"]}`
`[VERIFIED: RootNavigator.tsx:178]`, the background stops at the top inset, leaving an untinted strip
under the status bar (UAT row 5: "no black/untinted corner").
**How to avoid:** mount `BackgroundHost` as the **outermost** element (full-bleed) with `SafeAreaView`
**inside** it, so the fixed background fills behind the status-bar inset while content still respects
insets. This is a visual call for the planner; present to owner only if it changes product look.
