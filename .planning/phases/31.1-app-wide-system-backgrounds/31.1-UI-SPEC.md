# Phase 31.1 — UI Design Contract

> Visual and interaction contract for App-Wide System Backgrounds. Generated by gsd-ui-researcher,
> verified by gsd-ui-checker. This is an **integration / adoption** phase: it introduces **no new
> visual primitives, tokens, colours, or artwork**. It wires an already-built render primitive
> (`BackgroundHost`) and asset resolver (`backgrounds.ts`) into the real navigation tree, adds one
> missing store setter, and adds one inline picker to an existing settings section. Every locked
> decision below is cited by its `D-NN` from `31.1-CONTEXT.md`; none is re-litigated here.

`styles.themeChipRow` in `SettingsScreen.tsx`).

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | Thumbnail inner gaps, selected-border inset |
| sm | 8px | Gap between thumbnails within a subgroup |
| md | 16px | Row padding, gap between subgroups, label-to-thumbnail gap |
| lg | 24px | Appearance-section vertical rhythm (matches existing rows) |

| Role | Token | Usage in this phase |

carries a declared `brightestPixel` bound in `backgrounds.ts`; the device-UAT matrix below is the
acceptance proof for the shipped assets.

## D-17 — Picker contract (inline grid in Settings → Appearance)

A new **inline thumbnail grid**, added to the existing Appearance section in `SettingsScreen.tsx`,
directly after the Accent swatch row, mirroring the accent-swatch-row idiom (inline, live preview,
immediate persist — the exact `setAccentForActivePackage(...) + void persist(...)` pattern at
`SettingsScreen.tsx:898-905`).

**Layout (binding):**
- Two labeled subgroups — **Galaxy** (its 4 assets) then **Standard** (its 4 assets) — followed by the
  shared **None (Solid)** option.
- **All 8 assets + None/Solid are ALWAYS visible regardless of the active package (D-02).** The picker
  must **not** filter by active package. `resolveBackground()` already renders any slot for any package,
  so every thumbnail is previewable.
- Ordering within each subgroup follows `BACKGROUND_ORDER` (minus the trailing `none`, which is rendered
  once as the shared option): Galaxy = Deep Space, Starfield, Nebula, Aurora; Standard = Dawn, Paper,
  Dusk, Mesh.
- Each thumbnail carries its **human-readable label** (table above) and an **accent-border selected-state
  cue** (`colors.accent`), consistent with the accent row. Non-selected = `colors.border`.

**Selected-state resolution (binding):**
- The "selected" thumbnail reflects the **active package's** stored slot, resolving `null` to that
  package's `PACKAGE_DEFAULT_SLOT` (Galaxy → `galaxy-deep-space`, Standard → `standard-dawn`). This
  mirrors the accent row's `activeAccent === null` → package-default selected cue.

**Write behaviour (binding, D-09 + D-17):**
- Selecting a thumbnail writes the slot to the **ACTIVE package's** remembered column via a **new**
  store setter + `persist()`:
  - Add `setBackgroundForActivePackage(slot: BackgroundSlotId | null)` to `theme-store.ts`, mirroring
    `setAccentForActivePackage` exactly (galaxy → `galaxyBackground`, standard → `standardBackground`).
  - On tap: `setBackgroundForActivePackage(slot)` (instant live preview via `ThemeProvider`) **and**
    `void persist(themePackage === "galaxy" ? { galaxyBackground: slot } : { standardBackground: slot })`.
- Consequence (intended, D-02/D-17): picking a `galaxy-*` thumbnail while **Standard** is active stores
  that id in `standard_background`. `assertBackgroundId` accepts it (validates the full id set, not a
  package-scoped subset) and `resolveBackground` renders it. This is the all-8 design, not a bug.
- **No AsyncStorage, no second preference source** (D-09). Persistence is the DAO write only.

**Accessibility:** each thumbnail is `accessibilityRole="button"`, `accessibilityLabel` = the label +
"background", `accessibilityState={{ selected }}`, tap target ≥ 44px.

**No cross-navigation (D-20):** the System picker lives ONLY here. Do **not** add any link, hint, or
"see also" between Profile's Background manager and this picker. The two systems stay fully independent.

## D-18 — Shell mount strategy (single root, Orrery excluded)

**One shell-level `BackgroundHost`** mounts behind the tab scenes (at/inside `RootNavigator.tsx`'s
`Tab.Navigator` scene area), NOT per-screen wrappers (rejects the copy-paste pattern D-10 warns against).

**Cooperating scene roots (binding, D-11/D-18):** every ordinary screen root that today paints an
opaque `colors.background` must be made to **cooperate** — its outermost container becomes transparent
so the fixed shell background shows through. This must **not** weaken the opaque semantic surfaces that
forms, sheets, dialogs, loading, and error states depend on: `GlassSurface` cards, input rows, modals,
bottom sheets, snackbars, and loading/error overlays keep their existing opaque/semi-opaque surface
tokens. The background shows through the *gaps between* surfaces, not through the surfaces themselves.

**Per-screen density (binding):** the single host's scrim density is driven by the **focused route**.
Recommended mechanism (planner's to wire): read the focused route name with
`getFocusedRouteNameFromRoute` — the same idiom `RootNavigator.tsx` already uses for tab-bar
visibility — and map it to a `SurfaceDensity` via the classification table below, passing that to the
shell `BackgroundHost`'s `density` prop. A bounded per-screen exception is allowed ONLY where the
single-root mount cannot serve a screen correctly (see exceptions).

**Orrery exclusion (binding, D-05):** the Orrery tab must show **zero** system-background bleed under
any camera/zoom/tilt state. The shell host must render solid/None behind the Orrery tab (detect the
focused tab), and the Orrery scene keeps its own opaque canvas. The Orrery follows shared theme tokens
but never renders the selected System image.

**Bounded per-screen exceptions (enumerated):**

1. **Profile (`ContactProfileScreen`)** — keeps its **own** `BackgroundHost` (already mounted:
   `density="presentation"`, `readability="profile"`, `appOwnedBackgroundUri={…}`). Because that host
   fills the Profile scene, it covers the shell host beneath — this is the mechanism that implements the
   Profile-photo-wins precedence (D-06/D-07). Do not remove or duplicate it. When no app-owned photo
   resolves, Profile's host reads the active package's stored System slot (fallback), satisfying D-06.
2. **Orrery (`OrreryScreen`)** — excluded as above (D-05).
3. **CropPhoto (`CropPhotoScreen`)** — the Skia crop viewport fills the screen with the user's photo;
   classify `dense`. It does not reveal art; no special mount, just an opaque/dense treatment.

`BackupStack`, `SettingsStack`) — verified on disk 2026-09-10. `presentation` = art prominent (light
scrim); `comfortable` = reading-dense non-input (mid scrim); `dense` = input/config/overlay (more-opaque

## Open assumptions for the planner

These are genuinely unresolved by `31.1-CONTEXT.md` and are surfaced rather than silently decided:

1. **Shell-host density wiring mechanism.** The classification table is authoritative; the *mechanism*
   (focused-route→density on the single host vs. a thin per-scene scrim wrapper) is delegated to the
   planner per D-18's "smallest maintainable transparent-scene approach." Recommendation: focused-route
   map via `getFocusedRouteNameFromRoute` (existing idiom). **Constraint:** whichever is chosen, opaque
   semantic surfaces (cards/sheets/dialogs/snackbars/loading/error) are never weakened (D-11).
2. **`DigestScreen` density = `comfortable`.** D-19's literal text groups reading-dense surfaces under
   "dense"; this contract places Digest at the `comfortable` middle tier as presentation-forward intent.
   If device-UAT row 3 shows any contrast miss, step it to `dense` (readability wins, D-04). Flagged so
   the planner can confirm or override.
3. **Human-readable labels** (Deep Space / Starfield / Nebula / Aurora / Dawn / Paper / Dusk / Mesh) are
   researcher-proposed display strings, not owner-locked. They map 1:1 to the locked slot ids and order;
   the owner may rename any label without touching `backgrounds.ts`.

None of the above reverses a locked decision (D-01–D-21 / HANDOFF §7 / ADR-087). If the planner finds a
choice that would weaken one, stop and escalate to the owner rather than resolving it here.
