## Concerns

- **HIGH — Follow System cannot currently satisfy the planned Pixel/release matrix.** The native Expo configuration explicitly locks the app to light appearance (app.json:8), and `expo-system-ui` is absent from dependencies (package.json:14). The installed Expo configuration code warns that `expo-system-ui` is required to enable `userInterfaceStyle` on Android (node_modules/@expo/prebuild-config/.../withAndroidUserInterfaceStyle.js:14). Meanwhile, Plan 04 requires live Follow-System testing but declares neither `app.json` nor package files. The executor cannot legitimately complete that UAT row without an undeclared native/config correction.

- **MEDIUM — Navigation/native chrome is not specified as a resolved-theme consumer.** Plan 01 asks for a singular theme object built from React Navigation's `DefaultTheme`/`DarkTheme`, while also saying all other colors must resolve through Orbit tokens (31.1-01-PLAN.md:125). The live resolved mode already exists in Orbit's provider (theme-provider.tsx:47), but `AppShell` currently reads only `colors`, and the status bar is permanently `light` (App.tsx:142, :422). On bright Standard backgrounds, this can produce mismatched navigation semantics and unreadable status-bar icons even if screen content passes contrast.

- **MEDIUM — Plan 04 discovers contrast failures but cannot repair them within its declared scope.** Its action says to "step that route one tier denser" and merely note a follow-up Plan 03 tweak (31.1-04-PLAN.md:149). The density map is owned by Plan 01's `focused-route-classification.ts`, but that file is absent from Plan 04's modified-file list (31.1-04-PLAN.md:93). Since Plan 03 is already complete by Wave 3, a failing UAT row leaves no executable repair-and-retest path while the plan still demands a fully passing matrix.

- **MEDIUM — The invalid-ID device test mutates the owner's durable database without a restoration protocol.** Migration 015 gives the background columns unconstrained `TEXT` storage (015-theme-settings.ts:43), and `getAppSettings` casts raw values without read validation (app-settings-dao.ts:553); that is why the direct tamper test can reach the render fallback. Plan 04 writes a bogus value and relaunches (31.1-04-PLAN.md:143) but never snapshots and restores the prior value. The bogus ID can therefore remain in the owner's device DB after UAT.

- **LOW — "Provably absent from the release APK" is stronger than the specified verification.** Plan 04 shows `<ThemePreviewScreen>` directly in the proposed stack registration (31.1-04-PLAN.md:105), which normally implies an import. Guarding the route and row with `__DEV__` proves unreachability, but a source grep does not prove the statically imported module or missing-file test string was removed from the release bundle. This is not a product-security defect if unreachable, but the acceptance claim is presently unproven.

## Suggestions

- Amend Plan 01 to include `app.json`, `package.json`, and the lockfile: install/configure `expo-system-ui`, change native appearance to `automatic`, and verify `useColorScheme()` changes on the standalone Android build.
- Define a token-backed `makeNavigationTheme(colors, mode)` rather than an ambiguous static object. It should set `dark` from the resolved mode, map navigation color fields to Orbit tokens, and localize only the transparent background literal.
- Make status-bar style react to the resolved mode and verify it over the brightest Standard asset in both modes.
- Add `focused-route-classification.ts` and its test to Plan 04 as an allowed remediation file, or specify that any contrast failure blocks completion and triggers a dedicated repair plan followed by the full affected UAT rerun.
- For row 14, record the original column value, stop the app, perform the WAL-aware mutation, verify fallback, restore the exact original value, relaunch, and re-read it before proceeding.
- Either change the harness criterion to "release-unreachable" or verify true bundle absence by inspecting the generated release bundle/APK rather than source grep alone.

## Risk Assessment

**HIGH until the native Follow-System configuration is incorporated.** The principal rendering, persistence, D-22/D-23, inventory, and decode-fallback designs are otherwise strong and execution-ready. Once the native appearance/status-bar contract and Plan 04 repair/cleanup paths are added, residual risk should fall to **MEDIUM**, driven mainly by Android native-stack transparency and the breadth of physical-device visual UAT.
