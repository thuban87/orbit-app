## Codex Review

**Reviewer:** independent cross-AI peer (Codex, gpt-5.6-sol, reasoning=medium), run directly via
`codex exec` with repo read access. Auth restored — the prior cycle's `token_revoked` did not recur.
**Method:** read all four plans + CONTEXT/UI-SPEC/RESEARCH/VALIDATION + HANDOFF, then verified
load-bearing claims against source (RootNavigator, the tab stacks, BackgroundHost, backgrounds.ts,
theme-store, app-settings-dao, the screen roots incl. MergeImpactSummary + SystemBuilder,
resolve-presentation, check-colors.sh, the desktop-build-pipeline runbook, ThemePreviewScreen).

### Summary

The architecture is largely sound: it reuses the existing local-only resolver and fixed background
host, preserves Profile precedence, sequences the shell tracer before broad adoption, and includes
physical-device and release gates. However, the plans are not ready to execute. Plan 01 directly
contradicts D-22 by suppressing the System background for the entire Orrery tab, Plan 03's screen
inventory contains demonstrably false claims, and its mechanical root-removal instructions do not
correctly distinguish ordinary content roots from loading/error surfaces. These defects would
prevent the phase from achieving "every ordinary page" behavior and would (as written) build the
Orrery behavior D-22 rejects.

### Strengths
- The proposed shell-level mount matches the primitive's composition model — `BackgroundHost`
  renders a fixed absolute image layer (`src/components/ui/BackgroundHost.tsx:139-168`) with content
  above it (`:169-171`); Plan 01 mounts one host outside the tab navigator (`31.1-01-PLAN.md:148-157`).
- The selection/render path is local-only — all eight slots are lazy bundled `require()` thunks
  (`src/theme/backgrounds.ts:58-102`); `backgroundHostSelection` accepts only `file://` app-owned
  URIs (`src/components/ui/background-host-model.ts:20-27`).
- Default/None/tampered behavior is centralized — `resolveBackground` (`backgrounds.ts:183-204`) +
  decode-failure latch (`BackgroundHost.tsx:104-125,143-167`).
- Plan 02 follows the established live-update + durable-write idiom (`SettingsScreen.tsx:893-942`,
  persist `:431-453`; validation `app-settings-dao.ts:807-822`; column routing `:438-469`).
- Profile precedence is supported by code (`resolve-presentation.ts:52-70`,
  `ContactProfileScreen.tsx:295-305`).
- Wave ordering is appropriate (`31.1-04-PLAN.md:3-10`) — contains the Android transparency risk
  before the broad sweep.
- The plans respect the color-token gate (`check-colors.sh:33-54`).

### Concerns
- **HIGH — Plan 01 does not reflect D-22 and (as written) would build the tab-based exclusion D-22
  rejects.** D-22 requires `slotId="none"` only when the deepest focused route is exactly `Orrery`,
  not when `OrreryTab` is active (`31.1-CONTEXT.md:153-162`). Plan 01 still specifies tab-based
  suppression in its truth, key link, task, and acceptance criterion (`31.1-01-PLAN.md:30`, `:49`,
  `:148-152`, `:175`). Observable via `OrreryStack.tsx:50-62` registering ordinary children
  (`ThingsToRemember`, `RecentlyDeleted`, `MemoryHistory`): as written they get solid/None via
  OrreryTab but the System background via another tab — exactly the inconsistency D-22 forbids. Not
  an open product question; execution must stop until corrected to
  `slotId={focusedRoute === "Orrery" ? "none" : undefined}`.
  *(Aggregator note: per CLAUDE.md this is a planner-level fix — it enforces the recorded D-22, it
  does not reverse a decision, so no new owner decision is required.)*
- **HIGH — Plan 03's inventory is false and omits a definitely-opaque production screen.** Plan 03
  claims `MergeImpactSummary` "roots on surfaces" and already cooperates (`31.1-03-PLAN.md:62`); in
  reality its full-page root paints `colors.background` (`src/components/MergeImpactSummary.tsx:21`).
  It is a live route in Dashboard/Orrery/Settings stacks (`DashboardStack.tsx:65-67`,
  `OrreryStack.tsx:60-62`, `SettingsStack.tsx:58-60`). Because the inventory grep is restricted to
  `src/screens`, this component escapes the sweep and stays an opaque wash.
- **HIGH — `SystemBuilderScreen` also does not "already cooperate," and D-22 makes it
  consequential.** Its absolute-fill `BuilderBackgroundCanvas` paints an opaque Skia `Fill` using
  `colors.background` (`src/screens/SystemBuilderScreen.tsx:198-219`), always mounted behind the
  builder UI (`:496-505`). Plan 03 excludes it on the same false "already cooperate" claim (`:62`).
  Once Plan 01 is route-gated, the shell renders the System asset on `SystemBuilder` but this opaque
  canvas conceals it — conflicting with D-22's "only actual Orrery visualization" rule and the UI
  classification of `SystemBuilderScreen` as an ordinary dense route (`31.1-UI-SPEC.md:275-282`).
  The specialized preview canvas may reasonably remain opaque, but the always-mounted base fill
  needs an explicit integration treatment. *(Aggregator note: Claude rates this LOW — see Divergent
  Views.)*
- **HIGH — Plan 03's one-line root-removal mechanics mishandle multi-layer/multi-state screens.**
  It repeatedly instructs removing only "the" outermost root fill while preserving nested fills
  (`31.1-03-PLAN.md:111-118`, `:168-175`). `ArchivedContactsScreen` has both an outer full-screen
  fill and a nested full-area `ScrollView` fill (`src/screens/ArchivedContactsScreen.tsx:181-189`) —
  removing only the outer leaves the art hidden. Conversely, several files have distinct
  loading/error and success roots: `EditContactScreen.tsx:547-570`, `ImportCompleteScreen.tsx:108-135`,
  `CaptureScreen.tsx:547-560/743-759`, `ReconcileDetailScreen.tsx:141-144`. Each render branch needs
  explicit classification rather than a per-file one-line rule.
- **MEDIUM — Plan 04's decode-failure UAT has no reachable harness.** The only UI passing
  `forceRenderError` is the dev-only `ThemePreviewScreen` (`src/components/ui/__dev__/ThemePreviewScreen.tsx:95-113`),
  which is not registered (`:19-21`; corroborated by `BackgroundHost.tsx:15,70`). No production route
  imports it and the shell host does not expose `forceRenderError`, yet Plan 04 requires testing it
  (`31.1-04-PLAN.md:111-113`, `:125-131`) while declaring only `31.1-UAT.md` modified. The UAT is not
  executable as specified without an unplanned source change or asset corruption.
- **MEDIUM — Plan 04's release-APK transport contradicts the runbook.** Plan 04 says transport +
  install on the Pixel "via rsync/scp" (`31.1-04-PLAN.md:181-184`, `:197-199`). The runbook records
  rsync is **absent** on droid and uses tar-over-ssh/scp for **source**, with install on the Pixel
  via `adb install -r` (`docs/runbooks/desktop-build-pipeline.md:23,48-49,130-139`). Followed
  literally, the plan provides no valid host→Android install mechanism.
- **LOW — The UI-SPEC retains stale tab-based wording** (`31.1-UI-SPEC.md:213-216`) while the
  authoritative D-22 requires the deepest route; since all four plans cite the UI-SPEC, leaving it
  raises the chance an executor "corrects" back toward the superseded behavior.

### Suggestions
- Rewrite every Plan 01 Orrery condition to gate on the focused leaf route
  (`slotId={focusedRoute === "Orrery" ? NONE_SLOT_ID : undefined}`); remove `tabName` from the
  focused-route store unless another consumer remains; add unit cases proving `Orrery → none` while
  `ThingsToRemember`/`RecentlyDeleted`/`MemoryHistory`/`SystemBuilder`/`SystemsManagement` do NOT
  suppress; update Plan 04 UAT row 6 to assert both sides.
- Amend Plan 03's `files_modified`/tasks/acceptance to include `src/components/MergeImpactSummary.tsx`,
  remove its full-page fill, and add it to the dense-flow device sample.
- Add an explicit `SystemBuilderScreen` task (make the always-mounted base canvas fill transparent
  while preserving the preview visualization), and verify System Builder via both OrreryStack and
  SettingsStack.
- Replace Plan 03's per-file grep sweep with a render-branch inventory (normal/loading/empty/error),
  requiring removal of both full-page fills in `ArchivedContactsScreen` while preserving intentional
  opaque loading/error surfaces; add a static audit that also scans outside `src/screens`.
- Make Plan 04's decode-failure test executable (temporary debug-only route/harness with cleanup and
  a declared modified-file set, or a debug-only injectable shell-host flag provably absent from
  release).
- Correct Plan 04 to follow the runbook (source→droid via tar-over-ssh/scp; APK→Linux via scp;
  Pixel receives it via `~/.local/bin/adb -s "$serial" install -r`).
- Synchronize the stale Orrery language in `31.1-UI-SPEC.md` and copied RESEARCH snippets after
  correcting the plans.

### Risk Assessment
**HIGH.** The underlying primitives and persistence design are mature, local-only, and well tested,
but the current plans contain phase-blocking correctness failures: a direct contradiction of D-22
and an incorrect production-screen inventory, plus a multi-root sweep that can leave full-page opaque
blockers behind or weaken loading/error surfaces the decisions require to remain opaque. After
correcting the route gate, inventory, branch-specific mechanics, and UAT harness, residual risk
should fall to MEDIUM, dominated by the already-recognized Android native-stack transparency behavior.
