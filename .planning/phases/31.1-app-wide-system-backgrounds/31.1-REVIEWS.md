## 4. Concerns

### HIGH — `FieldDefForm` remains an undeclared full-screen wash
`CustomFieldsScreen` has three render states: list, create form, edit form. The latter two return `FieldDefForm` directly (CustomFieldsScreen.tsx:314), whose root is an opaque full-screen `ScrollView` (FieldDefForm.tsx:187). Plan 03's frontmatter includes `CustomFieldsScreen.tsx` but not `FieldDefForm.tsx` (31.1-03-PLAN.md:25), and Task 1 incorrectly requires exactly one component wash (:144). Result: Custom Fields appears correct in its list state but becomes fully opaque in create/edit.

### MEDIUM — the decode harness proves a forced fallback, not runtime decode failure
The plan describes `forceRenderError` as exercising the same `onError` latch (04-PLAN.md:94). Source shows the forced flag bypasses image rendering, while only the actual image handler sets `renderFailed` (BackgroundHost.tsx:121,154). UAT row 15 therefore cannot substantiate its "runtime decode failure / latch reset" wording.

### MEDIUM — picker thumbnail failure handling is absent from Plan 02
The UI contract says a thumbnail decode failure silently uses the same solid fallback (UI-SPEC:326). Plan 02 instead mounts `resolveBackground(...).source()` directly in an `Image` with no `onError` state or fallback (02-PLAN.md:89). `resolveBackground` only resolves IDs; runtime failure handling lives in `resolveRenderableBackground` (backgrounds.ts:207).

### LOW — the manifest command does not match its "every occurrence" claim
Plan 03 promises every `colors.background` occurrence but searches only `backgroundColor: colors.background` plus one special System Builder grep (03-PLAN.md:125). It misses other forms such as the Crop Photo Skia fill (CropPhotoScreen.tsx:338) and the System Preview canvas fill (SystemPreviewCanvas.tsx:134). Its automated verification merely prints a count without asserting an expected result (:149).

### LOW — focused route is not initialized in `onReady`
Plan 01 writes the store only from `onStateChange` (03-PLAN.md... 01-PLAN.md:157). React Navigation deliberately suppresses `onStateChange` on first mount (BaseNavigationContainer.js:313). Cold launch happens to default correctly to Home/presentation, but the store does not actually hold the initial focused leaf until navigation changes.

## 5. Suggestions
1. Add `src/components/FieldDefForm.tsx` to Plan 03's `files_modified`, Task 3 files, manifest, verify command, and acceptance; remove its full-page `ScrollView` fill while preserving input/surface fills; update the cooperating count.
2. Change Task 1's inventory command to `rg -n "colors\.background" src/screens src/components`, classify every use by role, and make verification assert the expected wash/exception set rather than printing `wc -l`.
3. Make the dev harness provoke a real local `Image.onError` (e.g. a deliberately missing `file://` app-owned URI), then change selection and prove the latch resets.
4. Add release-artifact or release-UI verification demonstrating the dev route and entry are unavailable; source grep alone is insufficient.
5. Either implement thumbnail `onError` fallback in Plan 02 or narrow the UI-SPEC so it does not promise behavior the plan will not build.
6. Use one route-sync callback from both `NavigationContainer.onReady` and `onStateChange`.

## 6. Risk Assessment
**HIGH.** The D-22 and D-23 corrections are sound and the build transport is fixed, but Plan 03 still misses a production full-screen branch that defeats the app-wide result, and the decode-failure acceptance claims stronger evidence than its harness can produce. No owner decision needs reopening; these are plan-completeness and verification-mechanism defects.
