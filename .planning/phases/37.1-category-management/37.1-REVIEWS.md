# Cross-AI Plan Review — Phase 37.1

## Codex Review

### Summary

The nine-plan sequence is unusually thorough and largely achieves Phase 37.1’s goal: it centralizes category mutation, treats deletion as one rollback-safe transaction, covers every major user-facing selector, preserves stable ID/UID identity, and integrates backup non-resurrection semantics without a SQLite migration. However, one backup-version decision requires owner escalation if the plan intends to retain it, and the final writer/consumer audit is not yet scoped broadly enough to satisfy the repository’s full-subsystem review rule. Overall risk is **HIGH until the backup compatibility conflict is resolved**, then likely MEDIUM.

Graph evidence was unavailable to this reviewer: the required `npm run graph:ask -- governs …` invocations failed because `tsx` could not create its IPC socket (`EPERM`). No absence of governance was inferred.

### Strengths

- The plans correctly distinguish runtime deletion from schema migration. Migration 001 already provides durable category ID, UID, name, ordering, and timestamps (`src/db/migrations/001-initial.ts:41`); Plan 01 explicitly forbids migration edits or reseeding (`37.1-01-PLAN.md:62`).
- The deletion design respects the repository’s non-reentrant transaction model. The transaction implementation explicitly warns that nested writers deadlock (`src/db/transaction.ts:12`), while Plan 02 requires transaction-composable cores and one outer transaction (`37.1-02-PLAN.md:55`).
- All import-session statuses are covered. The database admits `pending`, `complete`, and `discarded` sessions (`src/db/migrations/012-import-sessions.ts:14`), and Plan 02 deliberately removes the status predicate and preserves unrelated fields. This closes a real FK hazard because `batch_category_id` has no delete action (`src/db/migrations/012-import-sessions.ts:20`).
- The identity split is sound: numeric IDs for local FKs, UIDs/ref tokens for portable and System identity, and names only for presentation or matching. Current System references already use `category:<uid>` (`src/db/app-settings-dao.ts:54`), and category rules resolve UIDs rather than names (`src/db/systems-dao.ts:800`).
- Cross-kind naming is handled symmetrically rather than only in the category screen. Current System validation already checks custom Systems, built-ins, and categories (`src/db/systems-dao.ts:225`); Plan 01 correctly requires one shared normalized visible-name key (`37.1-01-PLAN.md:75`).
- The plans preserve the owner’s runtime-rule-removal decision without fabricating a broken category rule. Plan 02 adds a separate typed validity result, while retaining `brokenRules` for genuinely malformed/historical references. This matches the dossier’s requirement to remove only the affected rule and retain the System (`docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:161`).
- Profile deletion semantics are correct. The existing assignment is keyed locally by category ID (`src/db/profile-presentation-dao.ts:306`), and the schema already supplies `ON DELETE CASCADE`; the plans nevertheless count and explicitly remove presentation for truthful preview while never transferring it.
- The shared selector policy is well bounded: canonical order, explicit Uncategorized policy, complete local filtering at 13+, and hidden-selection retention. This directly satisfies the approved UI contract (`37.1-UI-SPEC.md:110`).
- Backup application correctly identifies two current deficiencies: category tombstones are unmapped (`src/backup/restore-apply.ts:151`), and replace-all currently omits categories from its deletion order (`src/backup/restore-apply.ts:1245`). Plan 03 addresses both and tests zero-category restoration.
- UI publication is commit-truthful throughout: inputs remain open on failure, reorder restores the last committed sequence, deletion revalidates under lock, and success feedback happens only after commit. The manager also includes a non-gesture reorder path and a reusable themed anchored menu.

### Concerns

#### HIGH — Backup v5 compatibility conflicts with an accepted ADR

Plan 03 mandates emitting category tombstones while keeping `BACKUP_FORMAT_VERSION` at 5 (`37.1-03-PLAN.md:47`). The current v5 validator uses a closed tombstone vocabulary that rejects `category` (`src/backup/backup-schema.ts:243`), and the DAO likewise rejects that entity type (`src/db/tombstones-dao.ts:37`).

Consequently, a new Phase 37.1 backup labeled v5 will contain data that an older v5 implementation rejects. The parser only invokes forward migrations when the numeric format version is lower (`src/backup/backup-schema.ts:930`), so there is no compatibility mechanism between two different v5 dialects.

ADR-063 explicitly rejected adding a portable wire-shape change without a version bump (`docs/decisions/ADR-063-versioned-lifecycle-backup-and-dormant-cadence-restore.md:20`). The newer dossier says not to bump merely because Category Management exists, unless semantics are genuinely unrepresentable (`docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:258`); same-version readers demonstrably cannot represent the new closed-enum value.

The non-reversing resolution is to treat category deletion evidence as the dossier’s allowed genuinely unrepresentable persisted semantic, bump to v6, and add a v5→v6 migration. Retaining v5 would weaken ADR-063’s explicit compatibility rule and requires an owner-recorded supersession rather than an automatic plan edit.

#### MEDIUM — The final consumer audit’s mandatory reading set is incomplete

The dossier requires inventorying every execution-time category path, including merge/reconciliation, AI context, knowledge/search, profile reads, and bulk actions (`phase-37.1-category-management-dossier.md:272`). Plan 08 claims complete coverage but its `read_first` list omits several actual consumers and writers (`37.1-08-PLAN.md:47`), including:

- `src/screens/MergeConflictsScreen.tsx`, which reads category identity and labels through screen-local SQL (`MergeConflictsScreen.tsx:78`).
- `src/db/merge-dao.ts`, which writes the surviving contact’s `category_id`.
- `src/db/bulk-actions-dao.ts`, the Dashboard bulk category writer.
- `src/db/dashboard-read.ts`, `src/db/profile-read.ts`, `src/db/ai-context-read.ts`, `src/db/knowledge-search-read.ts`, and `src/db/first-class-knowledge-read.ts`, which consume category labels.
- `src/db/reconcile-apply.ts` and `src/stores/orrery-system-store.ts`, which can carry stale category state.

The broad prose instruction to include newly discovered consumers helps, but the execution plan should enumerate these known files now. Otherwise the promised complete audit depends on implementation-time initiative despite the repository rule requiring full-subsystem reading.

#### MEDIUM — Restore deletion is not explicitly tied to the canonical category fallout core

Plan 03 says restore should preserve the same parent-last fallout invariants and its key link points to `categories-dao.ts`, but that DAO is neither in Plan 03’s `read_first` list nor its modified files (`37.1-03-PLAN.md:72`). The current restore implementation performs generic UID deletes directly (`src/backup/restore-apply.ts:500`).

Without an explicit reusable non-mutexed category-fallout core, runtime deletion and restore deletion can drift on all-status import-session nulling, category rule suppression, `category:<uid>` preferences and overrides, active Orrery fallback, Dashboard filter cleanup, Profile presentation removal, and parent-last ordering. Plan 02 should export a narrow composable fallout core parameterized by interactive target versus merge-null target, or Plan 03 should deliberately specify a restore-specific sequence plus parity tests.

#### LOW — Unicode comparison behavior needs deterministic specification

Current System validation mixes SQLite `COLLATE NOCASE` with `toLocaleLowerCase()` (`src/db/systems-dao.ts:230`). Plan 01 correctly adds NFC normalization but does not specify deterministic locale behavior. Locale-sensitive lowercasing can produce different keys on devices with different locales, while SQLite `NOCASE` is not full Unicode case folding.

The shared helper and backup validator should use one explicitly deterministic comparison algorithm, with tests for composed/decomposed Unicode and locale-sensitive letters. This matters because restore validation must make the same decision as runtime writers.

#### LOW — The route becomes live before the complete manager exists

Plan 01 activates the production Settings route while initially building the Add tracer (`37.1-01-PLAN.md:62`); complete deletion UI does not land until Plan 04. The approved contract says the inert reservation should be replaced by a live Categories manager (`37.1-UI-SPEC.md:102`). This is acceptable if intermediate plan commits are explicitly treated as non-release checkpoints; otherwise route registration should land with the complete manager.

### Suggestions

1. Bump backup format to v6 and add a v5→v6 migration. Retain v5 only through an explicit owner-recorded supersession of ADR-063’s same-version compatibility posture.
2. Expand Plan 08’s mandatory source inventory to include all currently known category paths, especially Merge Conflicts, merge/bulk/reconcile writers, Dashboard/Profile/AI/search reads, and the Orrery store.
3. Have Plan 02 export a narrow non-mutexed fallout core with explicit interactive, backup-merge, and replace-all modes; Plan 03 should read and reuse it under restore’s outer transaction, or define restore-specific parity tests if reuse is unsafe.
4. Define the category/System name key precisely as trim → NFC → deterministic case normalization, and apply it consistently to category CRUD, System CRUD/duplication, incoming-manifest validation, and final survivor-union validation.
5. Either defer production route registration to Plan 04 or state that Plan 01’s incomplete manager commit is an internal tracer checkpoint and cannot be considered release-ready.

### Risk Assessment

**HIGH.** The runtime CRUD, deletion transaction, consumer integration, privacy posture, and test strategy are fundamentally strong. The rating is driven by the unresolved backup compatibility conflict. Once resolved, and once the audit inventory and restore-core reuse are tightened, the remaining implementation risk should fall to MEDIUM.

## Consensus Summary

Codex and Claude agree that the core plan set is strong: the transaction boundary, stable identity model, tombstone-backed deletion semantics, resolver validity split, and complete-category selection direction are well designed. Both independently identified that Plan 08’s supposedly complete audit omits known category consumers. Claude’s output carried the workflow’s no-source-citations marker, so its overall verdict is not counted at full consensus weight; its individual claims were checked against the plans before inclusion below.

The controlling concern is the backup version conflict. Plan 03 changes v5’s closed tombstone vocabulary while keeping the same format number, although ADR-063 rejects portable wire-shape changes without a forward version migration. The dossier already permits a bump when implementation discovers genuinely unrepresentable persisted semantics, so the plan-preserving path is v6 plus v5→v6 migration; retaining v5 is owner-only because it would supersede the ADR’s compatibility posture.

### Agreed Strengths

- One serialized, transaction-composable mutation boundary with parent-last category deletion and exactly one revision bump.
- Stable numeric IDs for local FKs and UIDs/ref tokens for portable/System identity; names remain presentation/matching data.
- All-status import-session handling, precise runtime rule removal, typed `needs-attention` validity, and commit-truthful UI publication.
- Complete, canonical category catalogs with explicit Uncategorized policy and shared search behavior at 13+.
- Exact taxonomy backup/restore intent, including zero categories and no seed reconciliation.

### Agreed Concerns

- **MEDIUM:** Plan 08’s mandatory inventory omits known category consumers/writers, including the AI and knowledge-search readers both reviewers called out. Expand its `read_first` and audit matrix to enumerate all currently known paths rather than relying only on “newly discovered consumers” prose.

### Divergent Views

- **HIGH (Codex, source-cited):** Plan 03’s same-version addition of a closed tombstone entity conflicts with ADR-063. This is the only current HIGH concern.
- **MEDIUM (Codex, source-cited):** Plan 03 names a link to `categories-dao.ts` but does not explicitly read, modify, or reuse its fallout core; define reuse or parity-tested duplication.
- **MEDIUM (Claude, verified from plans/UI-SPEC):** Plan 04’s used-delete reassignment control does not explicitly adopt Plan 05’s shared 13+ searchable `CategoryChoiceSheet`, leaving the large-catalog deletion target inaccessible by the phase’s own selection standard.
- **LOW (Codex, source-cited):** The shared normalized visible-name key does not specify locale-deterministic Unicode folding despite current mixed SQLite/JavaScript comparison behavior.
- **LOW (Claude, verified from plans):** Plan 06 says to use a v5 backup validator “extended in Plan 03” for a Dashboard closed token, but Plan 03 defines only category tombstone/manifest graph extensions. Assign the durable Dashboard-token validation contract explicitly to Plan 06 or add it to Plan 03.
- **Not retained:** Claude’s rollback-seam concern conflicts with the research’s explicit allowance for DAO-level injected-failure tests, and its Replace-All tombstone concern is already subsumed by the HIGH wire-version issue. Codex’s route-timing note is a release/checkpoint clarification, not an implementation blocker for an unshipped multi-plan phase.
