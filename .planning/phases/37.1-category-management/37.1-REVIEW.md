## Critical Issues

### CR-01: Deleting a category can erase every saved Dashboard filter when the stored JSON is malformed

**Classification:** BLOCKER  
**File:** `src/db/categories-dao.ts:240-248` (destructive write at `src/db/categories-dao.ts:407-425`)  
**Issue:** The deletion path uses a private permissive parser that converts invalid JSON, arrays, and non-object values to `{}`. It then unconditionally persists that replacement object. Consequently, deleting an otherwise unrelated category turns any malformed `dashboard_filters` value into `{}`, silently destroying all valid/unrelated saved filter families that might still be recoverable. This violates the transaction's stated “remove only the deleted numeric ID” behavior and the full-state preservation/atomic restore posture. The fingerprint also sees the coerced empty value, so confirmation cannot warn about the loss.

**Fix:** Fail the deletion transaction closed when the durable setting cannot be parsed by the canonical Dashboard parser; do not rewrite unrelated state. Parse JSON, pass it through `parseDashboardFilters()` from `dashboard-query-logic.ts`, and throw a typed integrity error when either step fails. Only clone and remove `String(category.id)` from a successfully validated filter object. Add a DAO test starting with malformed JSON and assert deletion rolls back every table and leaves `data_revision` unchanged.

## Warnings

### WR-01: The shared category sheet ignores the 13-item progressive-search threshold

**Classification:** WARNING  
**File:** `src/components/category/CategoryChoiceSheet.tsx:35-39` and `src/components/category/CategoryChoiceSheet.tsx:99-113`  
**Issue:** `buildCategoryChoices()` returns the canonical `searchable` decision, but the sheet discards it and always renders a search field and applies the query. This contradicts the implemented/docs contract that ordinary consumers retain their established picker through 12 real categories and expose progressive search only at 13+. It also means the shared component can never enforce the threshold even though the logic layer calculates it.

**Fix:** Return `searchable` from `categoryChoiceSheetModel`, render the `TextInput` only when true, and ignore/reset query when false. Add component/model boundary tests for 12 versus 13 eligible rows, including the optional Uncategorized row and excluded deletion target.

### WR-02: Focus refreshes create unhandled promise rejections on ordinary SQLite read failures

**Classification:** WARNING  
**Files:** `src/screens/CreateContactScreen.tsx:309-317`, `src/screens/EditContactScreen.tsx:618-635`, `src/screens/ImportReviewScreen.tsx:179-188`  
**Issue:** Each new focus refresh starts `listCategories(...).then(...)` without a rejection handler. A transient database/read failure therefore becomes an unhandled promise rejection instead of preserving the last committed catalog and reporting a controlled error. The Edit screen is especially inconsistent because its sibling photo refresh catches and logs failures while the category refresh does not.

**Fix:** Move each refresh into a guarded async callback with `try/catch`, preserve current rows/selection on failure, and log through the screen's existing `Logger` scope (plus the established non-blocking feedback where appropriate). Add a generation/unmount guard so an older focus request cannot overwrite a newer catalog.

### WR-03: Manager mutations report success and close destructive/editor UI even when committed readback fails

**Classification:** WARNING  
**File:** `src/screens/CategoryManagementScreen.tsx:266-283`, `src/screens/CategoryManagementScreen.tsx:321-325`, and `src/screens/CategoryManagementScreen.tsx:417-421`  
**Issue:** `load()` catches its own read error and resolves normally. Both editor submission and deletion therefore continue to publish a success Snackbar and close their UI after a committed write even when the required committed readback failed. The screen can display stale rows (including a just-deleted category), while simultaneously claiming success and setting `loadError`; because rows are already mounted, that mismatch can persist until another focus/retry. This breaks the phase's “success appears only after commit/readback” and truthful committed-state UI contract.

**Fix:** Have `load()` return a success result or throw after setting the load error. Mutation handlers should distinguish “write committed, refresh failed” from write failure: publish shell refresh, keep/recover a safe loading/error surface, and avoid claiming that the visible list was refreshed. Add component tests that make create/rename/delete commit successfully and then reject `listCategoriesForManagement()`.
