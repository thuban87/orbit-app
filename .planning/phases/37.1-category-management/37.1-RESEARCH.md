## User Constraints

The phase dossier is the authoritative owner context in place of a `CONTEXT.md`, and the approved UI-SPEC is the interaction contract. The following constraints are locked:

### Owner-ruling supersession — 2026-09-15

- Category deletion reassigns every referencing `import_sessions.batch_category_id` row — pending, complete, and discarded — to the same transaction-selected category or Uncategorized. Preview, fingerprint, mutation, rollback, backup merge, UI copy, tests, and docs use this all-status rule. It supersedes every pending-only research statement below.
- The owner approved a development-only category UAT database/fault harness with exact filename `orbit-category-uat.db`; compile-time `__DEV__` and memory-only activation; production activation that throws; and synthetic/private-free evidence. Ordinary bootstrap may open `orbit.db`, but no category-UAT read, write, close, or delete may target it. Cleanup may delete only the exact disposable filename. The implementation inventory/tests must cover `getExecutor()`, direct `getDb()` users, and cached executor references.

- Categories remain open-ended, single-assignment organizational rows. A contact stores one `category_id` or `NULL`; `NULL` is the permanent **Uncategorized** state, not a row. Zero real categories is valid. [VERIFIED: docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:31-45]
- The initial names are ordinary user-owned rows after creation. They may be renamed, reordered, or deleted; upgrades and restores must never reseed missing rows. [VERIFIED: docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:47-58]
- CRUD is centralized at `Settings → Contacts & Relationships → Relationship Structure → Categories` on the reserved `CategoryManagement` route. Other surfaces remain consumers, with no inline CRUD. [VERIFIED: docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:60-74]
- Names are trimmed, NFC-normalized, nonblank Unicode strings of at most 100 characters. Category duplicates and collisions with visible built-in/custom System names are rejected case-insensitively; capitalization-only rename is valid because the edited row is excluded. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:114-126]
- `display_order` is canonical. New rows append; reorder and delete normalize real categories to a contiguous sequence; Uncategorized is always outside that sequence. [VERIFIED: docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:115-128]
- Delete is immediately permanent after explicit preview/confirmation. There is no Undo, history, quarantine, recovery window, or `field_history` snapshot. The UI-SPEC explicitly supersedes the roadmap's older snapshot wording. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:10-16,146-161]
- A used category is reassigned to Uncategorized by default or one other existing category chosen for that transaction. The target is not remembered. [VERIFIED: docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:130-144]
- Deletion and every fallout write commit atomically or all roll back. The preview must be re-read before commit; any disappeared category/target or changed fallout cancels the mutation and refreshes the preview. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:146-160]
- Delete removes only matching category rules from custom Systems. Systems remain; they continue if meaningful rules or explicit include overrides remain, otherwise they surface canonical Needs Attention. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:175-180]
- Category Systems use stable category UID. Delete removes their prefs/overrides and repairs an active selection to All Contacts. Profile category presentation is deleted and is never transferred to the reassignment target. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:193-199]
- Backup format stays v5 unless implementation finds genuinely unrepresentable semantics. Merge honors newer category tombstones; replace-all reproduces the exact category set/order, including zero categories, without reseeding. [VERIFIED: docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:258-270; .planning/phases/37.1-category-management/37.1-UI-SPEC.md:193-199]
- Ordinary category selectors add local search at `CATEGORY_SEARCH_THRESHOLD = 12`: 0–12 real categories show the complete list directly; 13+ show that complete list with search. Hidden selections survive filtering. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:163-180]
- Orrery's selector becomes exactly three independently collapsible groups — **Built-in**, **Categories**, **Custom Systems** — without search, favorites, recents, truncation, or broader redesign. Group expansion is per-open session only. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:182-191]
- All data and search remain on device. No network, telemetry, analytics, or cloud lookup enters a category path. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:193-202]

## Summary

Phase 37.1 is a runtime mutability and referential-reconciliation phase, not a schema-design phase. The existing `categories` table already has stable integer identity, unique portable UID, name, order, and timestamps; `contacts.category_id` and `import_sessions.batch_category_id` are nullable foreign keys; the generic tombstone table can store a new category entity type without DDL. Current schema head is 29. Therefore the smallest safe implementation adds a canonical category DAO/service aggregate and TypeScript/backup-contract support for category tombstones, but **does not add migration 030**. A runtime delete of “Dog Park” is an application transaction. [VERIFIED: src/db/migrations/001-initial.ts:41-49,61-82; src/db/migrations/007-tombstones.ts:20-27; src/db/migrations/012-import-sessions.ts:13-28; src/db/database.ts:62-100] [VERIFIED: docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:146-159]

The hard part is the deletion aggregate. One locked transaction must revalidate the preview; reassign all contacts and every referencing pending, complete, or discarded import session to the same chosen target; remove matching category rules; classify affected custom Systems correctly; delete the generated category System's ref-keyed prefs/overrides; repair `orrery_last_system`; remove Profile presentation and Dashboard filter tokens; normalize order; write the category tombstone; delete the row; and bump `data_revision` once. Existing `inWriteTransaction` is non-reentrant, so the aggregate must call non-mutexed cores or direct bound statements and never call public transactional wrappers. [OWNER RULING: 2026-09-15; VERIFIED transaction pattern: src/db/transaction.ts:12-28,45-63]

Backup is an implementation blocker within the phase, not a format-bump reason. v5 already exports the needed identity graph, but category tombstones are rejected/ignored today and replace-all does not delete `categories` at reset. Merge deletion also cannot safely issue a raw category delete before repairing nullable/ref-token consumers. The restore pipeline must be made category-aware as one coherent change, with explicit zero-category, tombstone-wins, stale-rule, and rollback tests. [VERIFIED: src/backup/restore-apply.ts:118-175,500-534,1131-1275; src/backup/backup-schema.ts:243-260; .planning/phases/37.1-category-management/37.1-UI-SPEC.md:204-219]

**Primary recommendation:** Build one category domain aggregate first, then integrate the manager/consumers, then close backup reconciliation and end-to-end tests; do not split plans by screen and do not introduce a schema migration.

### Important contract supersession

`docs/systems/orrery-systems-backup-contract.md` currently says a category rule whose category UID is absent is preserved broken and that category deletion has the same outcome. The new owner-approved phase contract explicitly changes **runtime category deletion** to remove the affected rule. The plan must update this living system doc and its Changelog after implementation; it must not alter the immutable prior ADRs. [VERIFIED: docs/systems/orrery-systems-backup-contract.md:62-82; docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:161-176]

For merge restore, the new category tombstone must prevent an older backup rule from semantically resurrecting the deleted reference. The clean implementation is a category-aware repair pass: after category reconciliation identifies surviving UIDs, suppress/delete category rules whose UID lost to a category tombstone, while continuing to preserve unrelated genuinely missing historical rules under the older diagnostic contract. This distinction is necessary because `system_rules.value` is a string, not a declared parent FK. [RECOMMENDATION based on VERIFIED: src/backup/reconciliation.ts:106-139,255-290; docs/decisions/ADR-056-tombstone-backed-uid-reconciliation-for-portable-restores.md:12-36]

### Pattern 1: One outer transaction, composable cores

The project transaction primitive is non-reentrant. Public category operations may wrap `inWriteTransaction`; the category delete body must call `insertTombstoneCore(..., { bumpRevision: false })`, `updateAppSettingsCore`, and new/inline non-mutexed fallout cores, then call `bumpDataRevisionCore` once. Never call `updateAppSettings`, `setSessionBatchCategory`, `setSystemRules`, or another public writer from inside it. [VERIFIED: src/db/transaction.ts:12-28; src/db/tombstones-dao.ts:62-81; src/db/app-settings-dao.ts:1467-1526]

### Pattern 2: Preview fingerprint, then lock-time equality

Return a typed preview containing category ID/UID/name, target candidates, and counts for all fallout classes. Final delete accepts the preview fingerprint and target ID, enters the writer lock, rereads both rows and fallout, and compares the entire decision-relevant snapshot. Any difference returns a stale-preview outcome with refreshed data and makes no write. Do not trust counts or target existence captured by the open sheet. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:146-160]

### Pattern 3: Stable identity, live labels

Keep local relations by numeric `id`, portable/System relations by `uid`, and names as display/search text only. Rename updates the category row's normalized `name` and `modified_at`; it must not rewrite contacts, rules, refs, profile assignments, or backup identities. [VERIFIED: docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:91-113]

### Pattern 4: One shared catalog model with surface policy

Return real categories in `display_order, uid` order and layer policy flags for `includeUncategorized`, `allowMultiSelect`, and `realOnly`. Search is a presentation filter only. It never truncates the source or mutates selected IDs/UIDs. At 13+ rows show search; at 0–12 retain each established small-list control. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:163-180]

### Pattern 5: Commit-truthful UI publication

Maintain last committed manager order. Optimistic drag may display the dropped order while saving, but failure restores the committed order. Add/rename/delete overlays close and snackbars publish only after commit. After commit call the established shell refresh signal and explicitly rehydrate any durable preference stores whose in-memory state was changed directly by the aggregate. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:125-133,158-161; src/stores/shell-refresh-store.ts:14-30]

## Common Pitfalls

### Pitfall 1: Treating runtime delete as migration 030

**What goes wrong:** A forward migration bakes user-specific deletion behavior into launch, risks reseeding, or creates a one-way schema change with no need.
**Why:** ROADMAP's older wording conflates a destructive runtime operation with schema migration.
**Avoid:** No migration unless a genuinely missing schema capability is proven. Extend the TypeScript tombstone vocabulary; the table already stores arbitrary entity type text.
**Warning:** A plan edits a shipped migration, increments `TARGET_VERSION`, adds a category name index, or uses seed names to reconcile live rows. [VERIFIED: .planning/ROADMAP.md:972-978; docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:146-159]

### Pitfall 2: Adding a category `NOCASE` unique index

**What goes wrong:** A migration can fail on previously accepted restored/hand-authored data, still cannot enforce collisions with built-ins/custom Systems, and SQLite `NOCASE` does not implement the approved Unicode normalization contract.
**Avoid:** Serialize writers through the shared mutex and validate normalized keys against categories, built-in labels, and systems inside the transaction. Add backup parse/reconcile collision checks.
**Warning:** UI-only validation or SQL-only category uniqueness.

### Pitfall 3: Nested transactional writers

**What goes wrong:** The non-reentrant mutex deadlocks permanently.
**Avoid:** Extract cores and own one outer transaction.
**Warning:** A category DAO calls `setSessionBatchCategory`, `setSystemRules`, `updateAppSettings`, or `bulkSetCategory` inside `inWriteTransaction`. [VERIFIED: src/db/transaction.ts:12-28]

### Pitfall 4: Incomplete fallout preview

**What goes wrong:** “Unused” appears while ref-token state, import defaults, Dashboard filters, or Profile presentation will still be destroyed.
**Avoid:** Define one preview query/result type consumed by both UI and final lock-time reread. Lightweight delete requires every fallout count to be zero.
**Warning:** Preview counts only contacts.

### Pitfall 5: Deleting category before dependencies

**What goes wrong:** FK failure blocks delete, or non-FK TEXT/JSON refs dangle silently.
**Avoid:** Repair nullable FKs and text/JSON refs first; delete Profile assignment explicitly; delete category last after tombstone insertion, all inside one transaction.
**Warning:** Reliance on `ON DELETE CASCADE` beyond Profile presentation. [VERIFIED: src/db/migrations/001-initial.ts:61-82; src/db/migrations/012-import-sessions.ts:13-28; src/db/migrations/022-orrery-systems.ts:33-56]

### Pitfall 6: Fake Needs Attention through a stale rule

**What goes wrong:** Runtime deletion violates the locked rule-removal decision merely to reuse today's `brokenRules.length` UI.
**Avoid:** Extend canonical System validity so an empty definition without explicit includes is Needs Attention; do not preserve the deleted rule or invent a sentinel.
**Warning:** Tests assert the deleted UID remains in `system_rules`. [VERIFIED: docs/dossier/milestone-2/phase-37.1-category-management-dossier.md:161-176; src/screens/SystemsManagementScreen.tsx:330-364]

### Pitfall 7: Breaking valid manual-only Systems

**What goes wrong:** Every zero-rule System is marked invalid even when explicit include overrides still define membership.
**Avoid:** Validity checks meaningful rules **or explicit include overrides**. Exclude-only overrides do not form a positive membership definition. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:175-180; src/logic/system-rule-resolver.ts:196-265]

### Pitfall 8: Category tombstone without rule resurrection repair

**What goes wrong:** Merge correctly deletes a category, then an older backup's category rule survives as a broken reference and semantically resurrects deleted intent.
**Avoid:** Make reconciliation category-survivor/tombstone aware and distinguish category-deletion fallout from unrelated historical missing rules.
**Warning:** `categories` maps to a tombstone but `system_rules` are applied unchanged.

### Pitfall 9: Replace-all that is really merge-seeds

**What goes wrong:** Extra destination categories survive, and a zero-category backup restores nonzero taxonomy.
**Avoid:** Delete categories during ordered reset after dependent rows/contacts; then insert exactly incoming categories.
**Warning:** `categories` remains absent from `replaceAllReset` deletion list. [VERIFIED: src/backup/restore-apply.ts:1131-1275]

### Pitfall 10: Stale in-memory durable state

**What goes wrong:** SQLite is correct but Dashboard filters or Orrery preference stores still publish deleted IDs/ref until relaunch.
**Avoid:** Commit first, then refresh/rehydrate all listed consumers via existing focus/revision seams.
**Warning:** Only manager rows reload after deletion. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:193-200]

### Pitfall 11: Screen-local selector forks

**What goes wrong:** Some screens alphabetize, omit Uncategorized, truncate, or clear hidden selections.
**Avoid:** Shared pure catalog/search model, with small-control adapters and explicit real-only policy.
**Warning:** independent `listCategories().filter()` implementations proliferate.

### Pitfall 12: Privacy leakage in diagnostics

**What goes wrong:** Delete copy/logs reveal contact names, rules, profile data, or backup content.
**Avoid:** UI and structured diagnostics use aggregate counts and safe IDs/status only.
**Warning:** error strings interpolate private rows. [VERIFIED: .planning/phases/37.1-category-management/37.1-UI-SPEC.md:193-202]
