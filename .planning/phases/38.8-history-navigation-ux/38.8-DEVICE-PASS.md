## Release measurements

Physical phone, **RELEASE** build, `History Long` (912 interactions + 2 group-linked, 14 knowledge, 7 lifecycle).
Every run starts from a fresh Profile visit (Back to Home, reopen the Profile) and `dumpsys gfxinfo com.bwales.orbit reset`
immediately before the measured tap.

How the numbers were taken:
- **UI/RenderThread only** — `dumpsys gfxinfo … framestats`: time from the tap's input handling (`HandleInputStart` of the
  input frame) to the `FrameCompleted` of the last frame of the burst that draws the result, plus the slowest frame. These
  frames include the JS work only indirectly (the result frame cannot draw before the JS commit), so "input → result
  frame" is end-to-end latency as the user sees it; the JS thread itself is not profiled.
- **Screen recording** (`screenrecord`, variable frame rate, frame-stepped by script): used where the result is an animated
  scroll with a 5 s highlight fade (S4, S5) — framestats keeps only the last 120 frames, which the fade overruns. The tap
  instant is calibrated from S2/S3, where framestats and video agree: the tap is injected ≈1.01 s (±0.07 s) into each
  recording. `show_touches` does not mark adb-injected taps, so it could not be used (it was set and restored).
- "Janky" = gfxinfo's own janky-frame count for the scenario.

**Adequacy (plain statement):** the chunked plain-View stream is adequate on this phone for normal use. Opening History,
expanding a year and Show older all finish within about 0.1–0.4 s, and a heatmap jump into the oldest year lands in about
0.6 s. Each of these actions costs **one** visibly long UI frame (55–110 ms; up to ~0.2 s for the deepest Jump), a brief
hitch rather than sustained jank — scrolling itself stays at the panel rate (p99 16 ms while the highlight fades). The
slowest case, Jump to date into a month ~10 chunks deep in the oldest year, takes about **1 s** from tap to landing. That
is noticeable but not broken. No gap is raised; if the owner finds the deep Jump sluggish, the follow-up is a bounded read
or a virtualized stream (recorded as an option in the phase-end report, not a recommendation to act now).

## Release re-check of check 8 (collapsed-History reveal)

Because the DEBUG failure looked timing-dependent, the collapsed case was repeated on the RELEASE build (History Long,
History collapsed before each try): Last Interaction 1st try → title stopped at y=1991 (same failure); 2nd try → title at
y=374 (correct); View history 3 tries → y=374 each time. So on release it lands correctly most of the time and fails
intermittently (1 of 6 here); on DEBUG (slower load) it failed every time. The cause is the one seen in
`08c-collapsed-reveal.mp4`: the reveal scroll fires on the first layout of the expanded section, which can still be the short
"Loading history…" placeholder, so the page is too short and the scroll stops at its end; nothing re-scrolls after the load.
Check 8 stays **FAIL (intermittent on release)**. Not fixed here (no source change allowed). Evidence: `08f-release-collapsed-reveal.png`.
