# Potential Phase 38.8 — History Navigation UX Investigation

**Research/design workpaper · For owner + ChatGPT review · Recommendation unapproved**

## 1. Executive Summary

The strongest candidate is **a chronological activity stream inside the existing Profile History module, supported by a navigational heatmap and conventional jump-to-date**. Separate browsing actual records from selecting an analysis window. Retain cadence-relative insight without requiring another record-navigation paradigm.

This recommendation deliberately revisits accepted product decisions: the Rolodex and explicit summary-to-detail path were chosen, not accidental implementation. Approval would require named supersessions, particularly ADR-121 and part of ADR-123. No redesign, phase insertion or implementation is authorized by this workpaper.

The problem framing is substantially accurate, with important qualifications: heatmap period and Rolodex day are independent; Cycles has no previous/next paging in current code; knowledge history is narrower than a general knowledge activity log; Group Events appear through the person's child interaction, not an additional parent row. These distinctions matter to any replacement.

## 2. Why This Investigation Exists

The owner independently finds the Rolodex unintuitive. Phase 39's locked principle is that tutorials teach stable behavior rather than compensate for confusing UX. Discovery A27/A28 and fresh audit F24 identify several temporal mechanisms and explicit detail reveal. Teaching those mechanisms now risks teaching navigation that will shortly change.

Method: read repository orientation, HANDOFF, roadmap, current History/Profile dossiers and ADRs; inspect executable components, read models, temporal services, routes, preferences and relevant tests. Two read-only agents independently examined decision history and data/detail constraints; material claims were checked against the actual files. Graph discovery distinguished an **EXTRACTED** ADR-123 citation in HistorySection from **INFERRED** document key-file links; the documents/code, not graph absence, establish constraints.

This is code-grounded UX analysis with reference to the prior disposable Pixel walkthrough and its retained screenshots, not a new device session or measured novice study. No personal data, current Orrery UI, builds or device mutations were involved. Friction and alternative-model predictions below are reasoned assessments, not comparative user-test results.

## 3. Current History User Goals

| Goal | Current support | Implication for redesign |
|---|---|---|
| Remember what happened recently | Select date/range, reveal records, open interaction | Make actual records readily browsable. |
| Retrieve an older conversation or change | Wheels, date markers, heatmap paging | Support approximate time and exact date without traversing every empty day. |
| Recognize contact patterns | Interaction-count heatmap | Preserve a visual overview distinct from the mixed record stream. |
| Compare activity with intended cadence | Cycles and window-scoped Intensity | Keep understandable analysis, not a prerequisite for browsing. |
| Correct or backfill history | Canonical Detail/Edit/Delete and predated detailed Log | Keep existing domain ownership and explicit commit boundaries. |
| Understand relationship transitions/context | Lifecycle/current-state rows in date details; group context in interaction detail | Preserve distinct record families and permissions. |

The old dossier makes precise date browsing primary. For the proposed redesign, **activity browsing is the better-supported primary task**, because the useful object is a record and users need not know its date. Exact date is a retrieval aid. This is an unapproved product recommendation, not evidence of task-frequency research.

## 4. Current History UX / Interaction Model

### Navigation/browsing

History occupies the semantic `interaction-history` module in Profile, subject to layout visibility and collapse preferences. Last Interaction / View history reveal and expand it in place, without resetting selection; they are absent when the layout hides History. Profile's normal ScrollView hosts the module.

`HistorySection` starts at today and reads global lens/count preferences. Its heatmap and Intensity use a shared analysis span. **RolodexBrowser independently initializes its own selected date to today**; changing its wheels does not change that span, and selecting a heatmap date does not synchronize the wheels.

| Control | Executable behavior |
|---|---|
| Cycles | Default lens; 5/10/15/20 current-frequency spans, default 10, oldest first/newest bottom-right. Always ends at today. No paging controls. Unbound/no cadence shows an unavailable explanation rather than automatically switching to 7 Days. |
| 7 Days | Rolling seven local days ending at reference date; previous/next moves seven days, capped at today. |
| Month / Year | Calendar period grids; previous/next moves one month/year. Future cells and padding are noninteractive. |
| Lens change | Returns analysis reference to today; persists globally. Does not reset Rolodex's independent day. |
| Heatmap day/cycle tap | Opens an inline count-only context card. Positive count offers See details; zero count offers Log interaction. No record opens directly. |
| Rolodex | Three Month/Day/Year columns; pan settles a signed date step, or explicit steppers adjust it. Day carries month/year; shorter months clamp; future is capped; year floor is today minus 30 years. Visible neighboring rows themselves are not tap-to-select buttons. |
| Rolodex selected day | Drawer summarizes interaction/lifecycle counts. Populated day offers See details; marker-empty day offers Log interaction. No automatic detail reveal. |

### Visualization/summary

Heatmap saturation counts **all interaction rows only**, including one group-linked child per person; it does not include lifecycle or knowledge rows. Current cycle has structural emphasis. Month/day/cycle grids fit measured width. Year uses fixed 13dp cells, two whole weeks per vertical row.

Intensity is a neutral line plus progress bar, not a time-series graph. It uses the selected date window or full displayed cycle span, qualified interaction inputs and current cadence. It is unavailable for Unbound/no cadence. See §10 for exact semantics.

The canonical read loads all of this person's interactions and lifecycle events, plus retained current-state entries, without a record LIMIT. “No history yet” appears only when all three families are empty and offers detailed Log for today. Knowledge-only/lifecycle-only history instead renders the normal surfaces with zero interaction counts.

### Record detail/management

See details opens a shared `DateDetailSheet` for one day or a cycle range. It interleaves interactions, lifecycle events and current-state knowledge newest-first. Interaction row → canonical `InteractionDetail`; knowledge row → owning field's full history destination; lifecycle row remains read-only.

Standalone Edit opens `EditInteraction`; group-linked Edit asks participant versus Group Event scope. Delete confirms irreversible deletion of the displayed interaction, using the recency writer and refreshing consumers. Group parent management has separate routes. Historical Log uses `LogContact { contactId, prefillDate }`, never Quick Log.

## 6. Problems / Friction in the Current Model

| Grounded observation | Likely user consequence / interpretation |
|---|---|
| Analysis period, wheel day and open detail scope are separate states | A person can change “the date” without changing the chart, or page a chart while the drawer still shows today. There is no single visible browsing location. |
| Records appear only after summary selection and explicit reveal | Remembering an approximate conversation requires operating date controls before seeing useful content. |
| Wheel rows look selectable but only pan/steppers adjust them | Normal tapping a visible neighboring date is not the interaction offered by the code. The selection/scroll metaphor needs learning. |
| Markers only cover interactions/lifecycle; knowledge is loaded separately | Knowledge-only dates look empty in the drawer even though date detail could contain knowledge. A zero-interaction heatmap card also offers only Log, not a route to lifecycle/knowledge on that day. |
| Wheel years stop 30 years back; period paging has no equivalent lower bound | The two navigation paths have inconsistent retrieval reach. The arbitrary wheel floor is not a storage limit. |
| Cycles unavailable for untracked people; no cycle paging | A persisted default can initially show an unavailable visualization despite existing history. Older activity requires switching mechanisms. |
| Three-wheel assembly consumes substantial vertical space | Prior Pixel screenshot 65 shows the wheels/drawer occupying most of the visible Profile region below Intensity, before actual records appear. |

Two code/contract discrepancies deserve owner awareness within this investigation: the dossier §L rejects inventing a date for a multi-day period, but `HistorySection` prefills `card.end` / `sheet.end`; dossier §F discusses cycle/window exploration, but current Cycles remains anchored to today without navigation. These are bounded discovery findings, not fixes performed here.

## 7. Candidate Model: Heatmap + Timeline + Jump-to-Date

**Unapproved candidate structure:** retain the existing History slot; present a compact interaction-pattern overview, followed by actual chronological activity. Expose conventional jump-to-date as a secondary retrieval action. Keep optional analysis visibly distinct from browsing.

- Start with recent records, grouped by readable year/month/day headings; use reverse chronological order to match the existing detail list. Ordering is still an owner choice.
- Render days with records, not blank rows for every calendar date. Missing months need no huge spacer; headings and dates must make time gaps legible.
- Active heatmap date jumps to/highlights the corresponding day's records; a cycle cell locates or reveals its range. Do not silently filter away the rest of history unless filtering is separately agreed.
- A date with no interaction may still contain lifecycle/knowledge. Resolve actual records before declaring “No activity.” If truly empty, offer date-contextual detailed Log.
- A jump mechanism should support direct year/month selection, not require dozens of next/previous presses. For an empty exact date, show an explicit empty-date context and neighboring activity rather than fabricate a record or silently imply one exists.
- Collapsible older years or a compact year index could accelerate long histories. Keep jump targets discoverable inside collapsed/lazy-loaded groups. Sticky headers are optional, not necessary to establish the model.

This serves “When?” through the heatmap, “What?” through the stream and “I know roughly when” through Jump. It does not require the user to interpret cycle boundaries to find a note.

## 8. Alternative Models Considered

| Model | Serious advantage | Principal cost |
|---|---|---|
| Current wheels, with clearer labels/synchronized state | Lowest replacement cost; precise date selection; existing tests | Still hides records behind calendar selection and often traverses empty dates. Synchronizing two dates does not solve activity-first browsing. |
| Conventional calendar + selected-day agenda | Familiar date mapping; excellent exact-day logging and focused detail | Sparse years still need month paging/jump; dense days require another list; users must choose a date before discovering content. |
| Period-paged activity list + heatmap | Short bounded lists, existing shared window/Intensity reusable | Retrieval across empty periods and several years can remain slow; choosing period becomes a browsing prerequisite. |
| Continuous grouped stream + heatmap + Jump | Recent browsing and sparse-history retrieval expose actual content immediately; one record-navigation model | Requires virtualized grouped rendering, jump anchoring and analysis/browse-state separation. |

A standalone full-screen stream is a hosting variant, not another information model. It may simplify virtualization, but is **not the recommended default here** because it reverses the in-Profile/no-new-screen decision. A search-first archive is not necessary for the bounded redesign and would reopen explicitly deferred search/filtering scope.

## 9. Comparative Tradeoffs

| Dimension | Wheels | Calendar agenda | Period-paged list | Stream + overview + Jump |
|---|---|---|---|---|
| Discoverability / cognitive load | Three axes, markers, summary and reveal to learn | Familiar calendar, explicit day selection | Familiar records, but period gating | Ordinary scroll and rows; secondary overview/jump relationship needs clear feedback |
| Recent browsing | Fast if date known; content hidden | Current month clear; inspect days | Good within current period | Strong: latest actual content first |
| Old retrieval / several years | Year adjustment helps; 30-year cap | Needs direct year chooser | Needs jump to avoid repeated paging | Year index/jump needed; scrolling alone insufficient |
| Sparse history | Many selectable empty days | Empty months dominate | Empty pages interrupt | Only actual dates; gaps conveyed compactly |
| Dense history | One day/range at a time | Day agenda can grow | Bounded but arbitrary page seams | Good with virtualization and compact rows; not eager rendering |
| Cadence understanding | Existing separate grid | Overlay needs care | Analysis naturally shares period | Analysis/annotations complementary; not navigation rules |
| Mixed / group records | Existing detail taxonomy | Reuse same agenda taxonomy | Reuse same list taxonomy | Visible semantic rows; preserve one child, avoid parent duplication |
| Backfill / edit/delete | Existing paths, extra reveal | Natural selected-date Log | Period needs actual date | Explicit past Log or empty-date context; row opens canonical Detail |
| Small screen / accessibility | Large control stack, gesture alternate steppers | Dense calendar needs alternate list | Conventional rows, fewer simultaneous controls | Conventional rows, but heatmap cannot be sole navigation |
| Complexity / compatibility | Lowest if retaining behavior | Moderate UI replacement | Moderate; fewer jump/virtualization challenges | Highest presentation/state work; no domain schema inherently required |
| Residual onboarding | Likely still explains mechanics | Small hints may suffice | Period semantics may need hint | Aim for tiny contextual hint; cadence concept may still need explanation |

These are qualitative predictions to validate on representative sparse/dense histories and Android devices, not numerical scores or proven novice outcomes.

## 10. Cadence Cycles and Intensity

Current cycles are contiguous **current-cadence** spans ending at today, not persisted epochs, interaction-anchored periods or historically reconstructed frequency intervals. Changing cadence rebuckets history; tomorrow shifts boundaries. An annotation must label this interpretation rather than imply fixed historical chapters.

**Recommendation, unapproved:** retain cadence-relative analysis as optional summary/visualization. Do not use cycle separators as the mandatory stream structure; long cadences and sparse data make that structure awkward, and a shifting boundary should not destabilize record browsing. Optional range shading/annotations could work, but require a defined anchor and low visual clutter.

Cycles / 7 Days / Month / Year **need not all remain record-navigation modes**. A safe bounded candidate retains them initially as analysis choices with existing global preferences; decide separately whether four analysis lenses and count presets earn their space. Removing them now is not approved and would supersede ADR-120. Month/Year help pattern comparison; 7 Days may overlap Digest but remains a useful short window; Cycles supplies Orbit-specific context.

Intensity should remain tied to an **explicit labeled analysis window**, not silently to whichever rows happen to be on screen or loaded. Scrolling past years should not unexpectedly change the metric. Preserve its neutral tone, current-cadence guard and qualification rules: outbound/mutual effort; connected-only when Rarely Responds applies. Heatmap counts all interactions, so the two counts can differ.

Executable nuance: `intensityWindow` filters to the span, then `computeIntensity` uses `intendedPerPeriod = 1`; it does not scale expected effort by window-length/current-cadence. The UI passes real cadence separately to the caption. Do not describe the current multi-cycle result as a fully normalized expected-count ratio. Whether this wording/interpretation needs clarification is an owner question; changing the metric algorithm would expand beyond navigation scope.

## 11. Interaction / Knowledge / Group-Event Representation

Recommended stream reuses the **three existing families** with distinct semantic labels/icons, not a new general audit log:

- **Interactions:** communication channel, local time, useful metadata/note preview; tap opens canonical Detail.
- **Lifecycle:** archive/restore/snooze/unsnooze/bind/unbind; read-only.
- **Current-state knowledge:** retained registered Last Talked About / Current Location values, placed by `created_at`. Edits/promotions are not newly timestamped activity rows in this read. Tap currently opens the field's full MemoryHistory destination, not necessarily the exact historical item editor.

Ordinary Memory creation/edit/delete, Custom Field value history, Category and cadence changes are **not** included by this canonical read. Adding those is a separate event-taxonomy decision, not a necessary timeline feature. Prefer preserving current meaningful history rather than broadening into audit trails.

For Group Events, show one person's child interaction with group identity/link where helpful; do not add the parent as another event or count. Existing compact rows do not expose the joined group title until Detail; a restrained group label in stream rows is a candidate presentation improvement. Preserve shared Group Note versus participant Note, inherited fields and explicit edit scope. Event-level browsing/lifecycle remains in Events and Group Event Detail.

## 12. Historical Logging and Record Management

**Recommended retained behavior:** explicit **Log past interaction** or date-contextual Log opens the existing detailed form, preselecting the person and an exact day only when known. No immediate write, no historical Quick Log. Empty days should explain absence and offer Log on that date; populated days can also support adding a missing interaction. Multi-day context must not silently choose its end as the real event date.

Record tap opens canonical Interaction Detail. Standalone Edit uses the focused editor; group-linked Edit preserves participant/event scope. Delete remains explicit confirmed hard-delete of that displayed interaction; there is no new trash or undo policy. Do not invent a group-delete scope prompt: current child Delete is distinct from Group Event deletion/dissolution.

Retain the existing standalone Detail overflow action **Make this a group interaction**: title prompt → identity-preserving conversion → Group Event Detail. Navigation replacement must not silently remove that capability or redesign conversion ownership.

Reuse the recency writer and existing invalidation chain. After redating/deleting, refresh counts, record ordering and Profile/Digest state, and preserve a sensible browsing anchor even when the targeted day disappears. Errors must retain visible state and actionable retry rather than optimistically remove rows.

## 13. Accessibility / Small-Screen Considerations

Current wheel steppers provide non-gesture navigation, and reduced motion flattens depth. Those are useful guarantees, not evidence every screen-reader interaction is already clear: wheel rows lack direct press behavior; selected-axis semantics/focus need device evaluation. Dense Year cells remain 13dp despite capped hit slop, so the grid cannot be the only practical retrieval route.

Recommended stream offers readable date headers and semantic rows, complete year in accessible date labels, conventional focus order and explicit controls for jump/expand/log. Preserve non-color event distinctions and avoid color-only cycle annotations. Jumping should announce/highlight the destination without repeatedly stealing focus; collapsed years must expose their state and be operable without gestures.

Keep heatmap/analysis controls from occupying the whole viewport before records. Avoid horizontal scrolling, clipped large text, inaccessible sticky headers and gesture conflicts with Profile's outer scroll. Validate compact Android screens, maximum text, TalkBack, reduced motion and dense notes. Reusing current fit-width/Sheet primitives helps, but does not establish the new model's reachability automatically.

## 15. Phase 39 Onboarding Impact

**Owner-locked triage:** detailed teaching of current Rolodex/date navigation is deferred pending the redesign decision. Basic History in Prepare/Record remains locked. A tiny future contextual hint is open, not approved.

The recommended model aims to make ordinary scrolling, tapping records and date navigation sufficiently clear through product UI. Some explanation of cadence-relative analysis may remain useful; that does not justify a large History navigation walkthrough. Decide residual teaching after the redesigned UI exists and is tested, not by transferring all A27/A28 controls into tutorial steps.

## 16. Recommended Direction

**Unapproved recommendation:** activity-first chronological stream + retained interaction overview + conventional Jump, within the existing Profile History module. Keep analysis controls independent of stream navigation but maintain Heatmap/Intensity's explicit shared analysis span initially.

Retain record families, count-only visualization, current-cadence semantics, source-owned knowledge editing, canonical interaction/group routes, historical detailed logging and coherent refresh. Replace wheels/date-first browsing and mandatory summary-to-record indirection. Empty dates should be explicit contextual states, not blank timeline regions.

Do not automatically remove all four lenses, add all knowledge mutations, create a standalone screen, change Intensity math or invent historical cadence epochs. The recommendation is strongest for reducing browsing mechanics; its remaining risks are long-list integration, accessible jump behavior and making analysis distinct without hiding it.

**Assessment:** sufficiently coherent for a potential pre-Phase-39 phase if limited to Profile History navigation/presentation, its state/preference compatibility, accessible retrieval and reuse of existing routes. It touches one History/Profile subsystem, with shared-scroll and long-history verification as the principal feasibility questions. Bounded does not mean trivial or already estimated.
