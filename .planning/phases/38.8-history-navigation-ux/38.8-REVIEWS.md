## Consolidated findings

### HIGH

**C1-01 — HIGH — codex (HIGH) + claude (MEDIUM) — Plan 03 Task 1, reused by Plan 04 Tasks 1–3 (pending scroll)**
*Problem:* The plan does not guarantee that a jump scroll actually lands. That puts the core of D-19, D-20, D-17 and D-65 at risk.

*Evidence (verified):*
- Plan 03 Task 1 (`38.8-03-PLAN.md:172`) has a `useLayoutEffect` call `onRequestHistoryScroll(node)` as soon as the node is registered. A day View that `streamStateOnReveal` has just mounted registers through its callback ref during the same commit. So the measurement and `scrollTo` run before that node's `onLayout`, and possibly before the native ScrollView has its new content height.
- This contradicts the phase's own RESEARCH Pattern 3 "Timing" (`38.8-RESEARCH.md`, Pattern 3: "a reveal that expands a year or grows chunks must measure *after* the target lays out … Have the target DayGroup's `onLayout` call back").
- `module-host-model.ts:81-89` documents that the ScrollView clamps `scrollTo` to its current content height, which is why the existing reveal defers. A jump into a collapsed older year is exactly the case that grows content, so it can land short.
- The host's `measureLayout` failure callback is a no-op (`38.8-03-PLAN.md:169`), but HistorySection clears `pendingScroll` right after calling the host. A failed or clamped scroll is lost silently, and nothing retries.
- Plan 03's device smoke (Task 3) taps only a populated day and a cycle on `History Long`. It never jumps into a collapsed older year. The first test of that path is Plan 06's release measurement.

*Suggested PLAN.md fix (Plan 03 Task 1):*
- Specify a completion contract: when the reveal changed stream state (a year opened or chunks grew), the scroll fires from the target node's `onLayout` for the current `gen`, not from the layout effect. The layout-effect path is only for a target that was already rendered.
- `requestHistoryScroll` takes `gen` and ignores a stale callback.
- `pendingScroll` is cleared only once the scroll has been issued for the current generation. A measure failure is logged content-free and the pending target is kept for one `onNodeLayout` retry.
- Add a `module-host-model` or logic test for "stale gen ignored".
- Add a Plan 03 Task 3 device-smoke step: a Year-lens tap into the oldest collapsed populated year on `History Long` lands with the target day below the app bar.

### MEDIUM

**C1-02 — MEDIUM — codex + claude — Plan 04 Task 2 (`pickerInitialMonth`, D-50)**

D-50 says "or the current month if the user hasn't scrolled into it", and RESEARCH Pattern 5 says "if none … use the current month". **C1-03 — MEDIUM (codex rated HIGH; downgraded) — codex — Plan 04 Task 3 (D-31 place-keeping)**
*Problem:* The plan re-anchors only when the anchor day disappears. For every other case it relies, without saying so, on the Profile ScrollView keeping its numeric offset. RESEARCH Pattern 7 states that assumption; the plan does not.

That offset does not hold the visible content in place when records are inserted or grown above the viewport. Examples: redating the opened record to a newer date, or a Log from the + button while scrolled deep. The ScrollView (`ContactProfileScreen.tsx:561`) has no `maintainVisibleContentPosition`.

*Why it was downgraded:* The usual edit (time or note on the row in view) changes nothing above the viewport, and D-31 does not require pixel anchoring. The shift is one or a few rows, so the user does not lose their place.

*Fix:*
- Write the mechanism into Task 3's action: offset retention plus a vanished-day re-anchor.
- Also re-anchor when the opened record's day still exists but the record itself moved to a newer date. Scroll once to the record's new day, without a highlight.
- Add the device-smoke step "redate an older row to a newer month; the stream lands on its new day or stays on the old place" with the observed result recorded.
- Do not add `maintainVisibleContentPosition` to the shared Profile ScrollView without asking. That changes a screen outside this phase.

The repo precedent verifies before it reports `present`: `orrery-seed.ts:27-30` ("VERIFIED and reported `present` only if it matches the spec exactly; otherwise `partial`") and `:582-608`.

*Fix:* Add a `verifyHistoryFixture` (per-dataset family counts via `readContactHistory`, group-linked rows present on Long and Sparse, `archived_at` set on Archived). **C1-05 — MEDIUM — claude — Plan 01 + Plan 06 Task 1 (the seed goes stale; no re-anchor)**

## 3. Concerns

### HIGH — Plan 04, Task 3: day existence is insufficient to preserve position

The plan only restores an anchor when its day disappears: [Plan 04:206](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-04-PLAN.md:206).

However:

- Redating an interaction can remove substantial content above the visible position while leaving that day populated.
- Editing note length can change row height.
- Logging or knowledge updates can insert content above the viewport.
- An insertion can push a previously visible anchor beyond the year’s unchanged chunk limit.

Keeping the component mounted prevents state loss, but does not preserve the same content at the same screen position. The outer ScrollView currently tracks only the app-bar threshold; it supplies no content-anchor preservation mechanism: [ContactProfileScreen.tsx:199](/home/bwales/projects/orbit-app/src/screens/ContactProfileScreen.tsx:199), [ContactProfileScreen.tsx:571](/home/bwales/projects/orbit-app/src/screens/ContactProfileScreen.tsx:571).

This is incomplete enforcement of **D-31**, not a reason to weaken it.

### HIGH — Plan 03, Task 1; reused by Plan 04: pending jumps can be silently lost

The host’s measurement failure is a no-op, while HistorySection clears the pending request immediately after calling the host: [Plan 03:169](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-03-PLAN.md:169), [Plan 03:172](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-03-PLAN.md:172).

That leaves no retry when measurement fails. It also leaves no specified generation check inside the measurement callback, so an older measurement can scroll after a newer tap.

The existing reveal controller explicitly defers expansion scrolling because content-height clamping matters: [module-host-model.ts:81](/home/bwales/projects/orbit-app/src/profile/module-host-model.ts:81). The new path needs an equally explicit completion contract.

### MEDIUM — Plan 04, Task 3: stale anchors can override subsequent browsing

`anchorDayRef` is set by row opening or a jump, but is not updated or invalidated by manual scrolling: [Plan 04:206](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-04-PLAN.md:206).

A user can jump to day A, scroll elsewhere, and later receive a revision that removes A. The proposed effect then scrolls back near A. Scope restoration to the mutation-return session or capture the currently visible anchor before publication.

### MEDIUM — Plan 04, Task 2: picker viewport coordinates ignore the overlay app bar

The plan uses viewport bounds `0..windowHeight`: [Plan 04:174](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-04-PLAN.md:174). Consequently, a header hidden behind the bar can be treated as “currently in view.” Measurement callback arrival order also must not substitute for stream order. Both affect **D-50**.

## 3. Concerns

- `buildHistorySeedPlan(today)` puts records on the device's *seed-day* today and yesterday, and puts the empty year "three back".
- Plans 02–06 run on later days, with a phase code review in between. By Plan 06, nothing is labelled "Today" or "Yesterday", so check 1 (D-33) can't pass on seeded data.
- If the seed ran in late December, a later January pass also moves "current year" and "three back": the Quiet-year contact would then have records in the year that is now "last year".
- The uid-prefix idempotency check (`status: "present"`) makes reseeding impossible without deleting data, and the plans forbid clearing app data.

## Consolidated findings

### HIGH

**C2-01 — HIGH — codex — Plan 03 Task 1 (reused by Plan 04 Tasks 1 and 3): the scroll-generation watermark outlives the counter that feeds it**
*Problem:* `scrollWithinHistory(offsetY, gen)` keeps "the highest `gen` seen" inside the controller (`38.8-03-PLAN.md:170`). The generations themselves come from HistorySection.
- The controller is created once per ProfileModuleHost mount (`ProfileModuleHost.tsx:280-286`, `useRef` plus a lazy init).
- HistorySection unmounts whenever the History section collapses: `ProfileSection` renders `children` only when `state.expanded` (`ProfileModuleHost.tsx:122-124`).
- HistorySection also remounts on a contact change through the new C1-15 `key`.

After a few jumps the controller holds, say, gen 5. The user collapses and re-opens History, the new HistorySection's counter restarts at 1, and every jump returns `false` ("stale") and does not scroll until the counter passes 5. That breaks D-19/D-20/D-17/D-65 within one ordinary Profile visit. Verified.

*Suggested PLAN.md fix (Plan 03 Task 1, plus the Plan 03 interface and artifact rows):* make the authority and the token live equally long. Either:
- (a) Drop the watermark from the controller. `scrollWithinHistory(offsetY)` stays a plain additive scroll. `requestHistoryScroll(target, isCurrent, onResult)` calls `isCurrent()` in the `measureLayout` success callback, right before scrolling, and HistorySection's `isCurrent` compares the request's gen with its own current pending gen; or
- (b) Have the host mint the token: `scroller.beginHistoryRequest(): number` sets the current token at intent time, and `scrollWithinHistory(y, token)` scrolls only when `token === current`.

Either way, add a test in `module-host-model.test.ts` (b) or the HistorySection logic (a): "after requests with gens 1..5, a fresh mount's first request still scrolls". Option (a) is the smaller change. Plan 04's reuse text needs no change beyond the name.

**C2-02 — HIGH — claude — Plan 03 Task 1 (reused by Plan 04 Tasks 1 and 3): `awaitLayout` keyed on "stream state changed" never scrolls when the target is already rendered**
*Problem:* the plan sets `awaitLayout` = "whether the reveal changed stream state (a year opened or a count grew)", and when it is true "only `onNodeLayout` for that key issues it" (`38.8-03-PLAN.md:174`).

For a cycle span (D-20), `scrollDay` is the newest day with records. `streamStateOnReveal` grows chunks or opens an older year until the span's *oldest* record renders. If the newest day was already rendered, all the growth lands below it, so its frame does not change and React Native fires no `onLayout` for it. The scroll is never issued and `pendingScroll` stays set. The highlight and the announcement still fire, so TalkBack says "Showing …" and nothing moves.

This happens for any cycle that straddles the rendered chunk boundary, and for a span across New Year whose newest day is in the open, rendered year. The Plan 03 smoke ("tap a cycle cell") will usually pick a recent, fully rendered span, so it may not catch this. Verified against the plan's own rule. The existing reveal works only because the History header *does* change frame when it expands (`module-host-model.ts:81-89`).

*Suggested PLAN.md fix (Plan 03 Task 1):*
- Define `awaitLayout = !nodeRegistry.has(scrollKey)`, read when the tap is handled (before the reveal update), not "stream state changed". When the target is already registered, issue from the layout effect: content only grew below it, so clamping cannot get worse.
- Put the decision in a small pure helper with tests: "registered + grew → immediate", "unregistered → on layout".
- Change the must_have truth at `:43` to match.
- Plan 03 Task 3 device smoke: add a cycle tap on `History Long` whose span extends past the first rendered chunk of the current year.

Plan 04 Task 1 (month header) and Task 3 (redate or nearest day) inherit the rule through "Plan 03's completion contract". Change their parenthetical "(`awaitLayout` when the reveal changed stream state …)" to "(`awaitLayout` when the target node is not yet registered …)".

### MEDIUM

**C2-03 — MEDIUM — codex (C2-02) + claude (M-3) — Plan 03 Task 1: the pending scroll is not cancelled by newer intents, and its retry can fire much later**
*Problem:* 
- A pending request is replaced only by another reveal. An empty-target tap, a lens, preset or page change, a Jump, Show older or a year expand leaves an older `pendingScroll` alive.
- After `onResult(false)`, the request waits with `retried: true` for "the next `onNodeLayout` for that key" (`38.8-03-PLAN.md:174`). For a node that is already laid out, that event may arrive minutes later, for example when a Log inserts rows above it and moves it. The Profile would then jump on its own.
- Codex's interleaving case (A's measurement arriving after B is requested) depends on `measureLayout` being asynchronous, so it is unverified. The cancellation gap stands either way.

*Suggested PLAN.md fix (Plan 03 Task 1):*
- Every user stream intent clears `pendingScroll`: a heatmap tap of any result, a note close, a lens, preset or page change, Show older, a year expand. Plan 04 Task 1 adds Jump to this list.
- Bound the retry with one short top-of-file timeout (for example `HISTORY_SCROLL_RETRY_MS`), after which the request is dropped.
- When the C2-01 fix is in, staleness is checked right before scrolling, so a cancelled request can never scroll.
- Add a logic test: a newer intent drops an older retry.

**C2-04 — MEDIUM — codex (C2-04) + claude (M-4) — Plan 06 Task 1 check 6 contradicts Plan 04 Task 3 (the C1-03 rule)**
*Problem:* Plan 04 Task 3 (`38.8-04-PLAN.md:207`) says a record redated to a *newer* day scrolls once to its new day, and the nearest remaining day is used only when the anchored day vanished and the record did not move newer. Plan 06 check 6 (`38.8-06-PLAN.md:126`) says "redate a day's only record to another month and delete a day's only record → the stream lands on the nearest remaining day". A correct forward redate would be logged as a Plan 06 fail. Verified.

*Suggested PLAN.md fix (Plan 06 Task 1 check 6):* split it into three cases.
- Forward redate → the record's new day.
- Backward redate of a day's only record → the nearest remaining day.
- Delete a day's only record → the nearest remaining day.

Each case can be marked `done-earlier` from the Plan 04 smoke when that smoke recorded it.

## Concerns and specific suggestions

### C2-01 — HIGH — The scroll watermark outlives the counter that supplies it

**Evidence:** [03:170](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-03-PLAN.md:170) adds a highest-generation watermark to the host controller. That controller is retained in `ProfileModuleHost.tsx:280–286`. **Mechanism:** After several jumps, the controller may retain generation 5. Collapse/reopen History resets its local counter; its next jump supplies generation 1 and is rejected as stale. Ordinary section use can therefore disable jumps until the local counter catches up.

**Suggested correction:** Give request tokens and their authority the same lifetime. Allocate tokens in the retained host, or explicitly scope requests to a mounted History session and invalidate the old session. Preserve the contact key.

### C2-02 — MEDIUM — “Highest completed generation” does not identify the latest intent

**Evidence:** [03:171](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-03-PLAN.md:171) invokes `scrollWithinHistory` only from the asynchronous measurement callback.
