## Consolidated findings

### HIGH

**C1-01 — HIGH — codex (HIGH) + claude (MEDIUM) — Plan 03 Task 1, reused by Plan 04 Tasks 1–3 (pending scroll)**
*Problem:* The plan does not guarantee that a jump scroll actually lands. That puts the core of D-19, D-20, D-17 and D-65 at risk.

*Evidence (verified):*
- Plan 03 Task 1 (`38.8-03-PLAN.md:172`) has a `useLayoutEffect` call `onRequestHistoryScroll(node)` as soon as the node is registered. A day View that `streamStateOnReveal` has just mounted registers through its callback ref during the same commit. So the measurement and `scrollTo` run before that node's `onLayout`, and possibly before the native ScrollView has its new content height.
- This contradicts the phase's own RESEARCH Pattern 3 "Timing" (`38.8-RESEARCH.md`, Pattern 3: "a reveal that expands a year or grows chunks must measure *after* the target lays out … Have the target DayGroup's `onLayout` call back").
- `module-host-model.ts:81-89` documents that the ScrollView clamps `scrollTo` to its current content height, which is why the existing reveal defers. A jump into a collapsed older year is exactly the case that grows content, so it can land short.
- The host's `measureLayout` failure callback is a no-op (`38.8-03-PLAN.md:169`), but HistorySection clears `pendingScroll` right after calling the host. A failed or clamped scroll is lost silently, and nothing retries.
- Plan 03's device smoke (Task 3) taps only a populated day and a cycle on `History Long`. It never jumps into a collapsed older year. The first test of that path is Plan 06's release measurement.

*Suggested PLAN.md fix (Plan 03 Task 1):*
- Specify a completion contract: when the reveal changed stream state (a year opened or chunks grew), the scroll fires from the target node's `onLayout` for the current `gen`, not from the layout effect. The layout-effect path is only for a target that was already rendered.
- `requestHistoryScroll` takes `gen` and ignores a stale callback.
- `pendingScroll` is cleared only once the scroll has been issued for the current generation. A measure failure is logged content-free and the pending target is kept for one `onNodeLayout` retry.
- Add a `module-host-model` or logic test for "stale gen ignored".
- Add a Plan 03 Task 3 device-smoke step: a Year-lens tap into the oldest collapsed populated year on `History Long` lands with the target day below the app bar.

### MEDIUM

**C1-02 — MEDIUM — codex + claude — Plan 04 Task 2 (`pickerInitialMonth`, D-50)**
*Problem:* The plan's rule is "none above but one on screen → the first on screen" (`38.8-04-PLAN.md`, Task 2 behaviour). D-50 says "or the current month if the user hasn't scrolled into it", and RESEARCH Pattern 5 says "if none … use the current month". The plan rule opens on, for example, September when the stream top is merely visible and the current month is empty.

The plan also passes `viewportTop = 0`. The Profile has a 56 dp overlay app bar (`contact-profile-logic.ts:89`, `PROFILE_APP_BAR.height`; `ContactProfileScreen.tsx:650-655` lands targets below it), so a header hidden under the bar counts as "in view".

Pass `viewportTop` = the app-bar bottom (status inset + `PROFILE_APP_BAR.height`) instead of 0. Sort entries by stream order, not callback arrival. Add the test "first visible header ≠ current month, not scrolled in → current month".

**C1-03 — MEDIUM (codex rated HIGH; downgraded) — codex — Plan 04 Task 3 (D-31 place-keeping)**
*Problem:* The plan re-anchors only when the anchor day disappears. For every other case it relies, without saying so, on the Profile ScrollView keeping its numeric offset. RESEARCH Pattern 7 states that assumption; the plan does not.

That offset does not hold the visible content in place when records are inserted or grown above the viewport. Examples: redating the opened record to a newer date, or a Log from the + button while scrolled deep. The ScrollView (`ContactProfileScreen.tsx:561`) has no `maintainVisibleContentPosition`.

*Why it was downgraded:* The usual edit (time or note on the row in view) changes nothing above the viewport, and D-31 does not require pixel anchoring. The shift is one or a few rows, so the user does not lose their place.

*Fix:*
- Write the mechanism into Task 3's action: offset retention plus a vanished-day re-anchor.
- Also re-anchor when the opened record's day still exists but the record itself moved to a newer date. Scroll once to the record's new day, without a highlight.
- Add the device-smoke step "redate an older row to a newer month; the stream lands on its new day or stays on the old place" with the observed result recorded.
- Do not add `maintainVisibleContentPosition` to the shared Profile ScrollView without asking. That changes a screen outside this phase.

**C1-04 — MEDIUM — codex + claude — Plan 01 Tasks 1–2 (a partial seed reports `present`)**

But each contact commits in its own transaction, and `createGroupEvent` and `archiveContact` run after those commits (Task 2). A failure partway through, such as the blank-title or future-date guards at `group-events-dao.ts:325`, leaves partial data that every later run reports as `present`. Every smoke after that runs without group links or the archived contact, and nothing flags it.

The repo precedent verifies before it reports `present`: `orrery-seed.ts:27-30` ("VERIFIED and reported `present` only if it matches the spec exactly; otherwise `partial`") and `:582-608`.

*Fix:* Add a `verifyHistoryFixture` (per-dataset family counts via `readContactHistory`, group-linked rows present on Long and Sparse, `archived_at` set on Archived). Return `partial` with the problems, and still write nothing, when verification fails. Add a test that seeds, deletes one dataset's group link, re-runs, and expects `partial`.

**C1-05 — MEDIUM — claude — Plan 01 + Plan 06 Task 1 (the seed goes stale; no re-anchor)**

## 3. Concerns

### HIGH — Plan 04, Task 3: day existence is insufficient to preserve position

The plan only restores an anchor when its day disappears: [Plan 04:206](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-04-PLAN.md:206).

However:

- Redating an interaction can remove substantial content above the visible position while leaving that day populated.
- Editing note length can change row height.
- Logging or knowledge updates can insert content above the viewport.
- An insertion can push a previously visible anchor beyond the year’s unchanged chunk limit.

Keeping the component mounted prevents state loss, but does not preserve the same content at the same screen position. The outer ScrollView currently tracks only the app-bar threshold; it supplies no content-anchor preservation mechanism: [ContactProfileScreen.tsx:199](/home/bwales/projects/orbit-app/src/screens/ContactProfileScreen.tsx:199), [ContactProfileScreen.tsx:571](/home/bwales/projects/orbit-app/src/screens/ContactProfileScreen.tsx:571).

This is incomplete enforcement of **D-31**, not a reason to weaken it.

### HIGH — Plan 03, Task 1; reused by Plan 04: pending jumps can be silently lost

The host’s measurement failure is a no-op, while HistorySection clears the pending request immediately after calling the host: [Plan 03:169](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-03-PLAN.md:169), [Plan 03:172](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-03-PLAN.md:172).

That leaves no retry when measurement fails. It also leaves no specified generation check inside the measurement callback, so an older measurement can scroll after a newer tap.

The existing reveal controller explicitly defers expansion scrolling because content-height clamping matters: [module-host-model.ts:81](/home/bwales/projects/orbit-app/src/profile/module-host-model.ts:81). The new path needs an equally explicit completion contract.

### MEDIUM — Plan 04, Task 3: stale anchors can override subsequent browsing

`anchorDayRef` is set by row opening or a jump, but is not updated or invalidated by manual scrolling: [Plan 04:206](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-04-PLAN.md:206).

A user can jump to day A, scroll elsewhere, and later receive a revision that removes A. The proposed effect then scrolls back near A. Scope restoration to the mutation-return session or capture the currently visible anchor before publication.

### MEDIUM — Plan 04, Task 2: picker viewport coordinates ignore the overlay app bar

The plan uses viewport bounds `0..windowHeight`: [Plan 04:174](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-04-PLAN.md:174). Profile has a 56dp overlay bar, and its normal jump path compensates for that obstruction: [contact-profile-logic.ts:89](/home/bwales/projects/orbit-app/src/screens/contact-profile-logic.ts:89), [ContactProfileScreen.tsx:652](/home/bwales/projects/orbit-app/src/screens/ContactProfileScreen.tsx:652).

Consequently, a header hidden behind the bar can be treated as “currently in view.” Measurement callback arrival order also must not substitute for stream order. Both affect **D-50**.

The first matching UID causes an unconditional successful `present` result, but contacts commit separately and group/archive writes happen afterward: [Plan 01:113](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-01-PLAN.md:113), [Plan 01:148](/home/bwales/projects/orbit-app/.planning/phases/38.8-history-navigation-ux/38.8-01-PLAN.md:148).

## 2. Strengths

- **The canonical read really is enough.** `readContactHistory` returns all three record families with local `date`, `occurredAt`/`createdAt` and the group title/note join (`history-read.ts:144-151, :175-200, :258-289`). So "no new DAO / no schema" holds, and the Plan 02 prohibition on read changes is safe.
- **Ordering and keys.** `${family}-${id}` keys are correct. Knowledge rows come from the single `current_state_entries` table (`current-state-history-read.ts:30, 47, 75`), so ids can't collide across fields. Interaction ids and event ids are separate sequences, which is why the family prefix is needed.
- **The undated Log route is safe end to end.** `LogInteractionScreen.tsx:81-85` (`seedOccurredAt`) falls back to `now` when `prefillDate` is missing. Making `LogContactRoute.params.prefillDate` optional is therefore the whole D-28 fix.
- **The reduced-motion hold is handled correctly.** The installed `withDelay` signature is `(delayMs, animation, reduceMotion?)` (`delay.d.ts`), so `ReduceMotion.Never` as the third argument plus the inner timing's `reduceMotion` is valid. The extra `setTimeout(FADE + slack)` clear in HistorySection makes the highlight go away even if the animation misbehaves.
- **Every contract consumer is accounted for:**
  - `overlay-host-theme-contract.test.ts:24-30` slices from `export function X(` to `<Sheet` and forbids `useTheme()`. JumpToDateSheet's "useUnscopedTheme first statement" matches this.
  - `timestamp-consumer-contract.test.ts:30-33, :93` (minCalls 6, the DateDetailSheet row-label test) is moved in Plan 02 and removed in Plan 03.
  - The floor goes 21 → 20 (Plan 03) → 21 (Plan 04).
- **The D-27 write trap is spotted correctly.** `SegmentedControl.tsx:73` calls `onChange` even for the already-active segment. `lensTapIntent` returning `persist: null` for the fallback Month tap is the right guard.
- **`SegmentedControl` gets an opt-in density** instead of a new default, which protects Home, AI Personalization and Your Week (`SegmentedControl.tsx:114-133`).
- **The seed uses the real writers:**
  - `createContactFullCore` accepts `trackingEnabled` (`contacts-dao.ts:249-261`), so Unbound can be seeded.
  - `setCurrentStateValueCore` takes `now` as `created_at` (`current-state-history-dao.ts:66-82`).
  - `archiveContactCore` writes the archive lifecycle event itself (`contacts-dao.ts:916-931`).
  - `createGroupEvent` is a wrapped writer (`group-events-dao.ts:321`) and is correctly called outside the seed's transactions.

## 3. Concerns

**MEDIUM: the seed's dates go stale before the final device pass, and the seed can't be refreshed (Plan 01 Task 2/3; Plan 06 Task 1 checks 1 and 3).**
- `buildHistorySeedPlan(today)` puts records on the device's *seed-day* today and yesterday, and puts the empty year "three back".
- Plans 02–06 run on later days, with a phase code review in between. By Plan 06, nothing is labelled "Today" or "Yesterday", so check 1 (D-33) can't pass on seeded data.
- If the seed ran in late December, a later January pass also moves "current year" and "three back": the Quiet-year contact would then have records in the year that is now "last year".
- The uid-prefix idempotency check (`status: "present"`) makes reseeding impossible without deleting data, and the plans forbid clearing app data.
- `orrery-seed.ts:667-774` has a re-anchor action for exactly this case. History has none.

**MEDIUM: a half-finished seed reports `present` (Plan 01 Task 2).**
- Contacts are committed one transaction at a time. Group events and `archiveContact` run after those commits.
- If any later step fails (for example `createGroupEvent`'s blank-title or future-date guards, `group-events-dao.ts:325`), the next run sees the prefix and returns `present`.
- Every later smoke and the measurement then run on data with no group links or no archived contact, and nothing flags it.
- `orrery-seed.ts:27-30, :582-608` deliberately verifies before it says `present`. The History seed has no verify.

**MEDIUM: Plan 03 is the largest and riskiest plan (Plan 03, all tasks).** It contains:
- the scroll plumbing across three files;
- a new Reanimated component (the Hermes worklet hazard);
- cycle and cross-year reveal;
- the note reducer;
- the undated route;
- deleting two components;
- three contract-test migrations, plus Biome and `TimelineRow`;
- a device smoke.

Its estimate is 165k tokens at "low" confidence. This is the plan most likely to run out of executor context mid-retirement, which would leave a broken tsc gate (the orphaned-consumer memory). Splitting an agreed plan is an owner gate, so I'm flagging it rather than recommending a split. At minimum, the retirement step (Task 3) should be clearly resumable, and it should run its own `grep -rn "DateDetailSheet\|HeatmapContextCard" src biome.json` gate before `git rm`, not only after.

**MEDIUM: measuring before layout in `useLayoutEffect` is assumed, not proven (Plan 03 Task 1).**
- The plan calls `onRequestHistoryScroll(node)` from a `useLayoutEffect` as soon as the node is registered, and falls back to `onNodeLayout` only when the node is missing.
- For a node that *was just mounted* by `streamStateOnReveal` (an expanded older year), it relies on Fabric having committed layout before layout effects. That is true on the New Architecture.
- But `scrollTo` beyond the ScrollView's *current* content height is clamped (the same hazard `module-host-model.ts:81-89` documents for the reveal). If the content-size update lags, the jump into the oldest year lands short.
- Nothing retries once `measureLayout` succeeds with a clamped target.
- Plan 06's "heatmap jump into the oldest populated year" scenario covers this, but only on release.

**MEDIUM: D-50 behaviour differs from the decision in one case (Plan 04 Task 2).**
- `pickerInitialMonth` rule: "none above but one on screen → the first on screen".
- If the user hasn't scrolled into the stream, but the stream's first month header is visible and isn't the current month (for example, current month empty, so the first header is "September"), the picker opens on September.
- D-50 says "or the current month if the user hasn't scrolled into it".
- Headers that sit under the overlay app bar (`ContactProfileScreen.tsx:652-654`, `profileScrollTargetY`) count as on-screen when viewportTop is 0.
- Suggested rule: "a header at or above `appBarBottom` → the last such; else the current month".

**LOW–MEDIUM: Plan 05 paging drifts after a rollover.** While paged back, `advanceHistoryDay` keeps `refDate` (D-04). Today moves on, so the paged series is now offset by the rollover days from D-26's "current-cadence spans ending at today". `cyclesNextRef` clamps to `today`, so the series snaps back only on the last page. This tension sits inside D-04 vs D-26 themselves. A test should pin the chosen behaviour rather than leave it implicit.

**LOW: History state isn't keyed on `contactId`.** `ContactProfileScreen` re-keys its reads on a changed `route.params.contactId` (`ContactProfileScreen.tsx:215-258, :290`), but `ProfileModuleHost` and `HistorySection` are not keyed on it (`:647`). If a Profile route instance ever gets a new `contactId`, the new stream state would carry over the previous contact's open years and anchor. The existing `day` state already has this exposure, so the issue is pre-existing. Adding `key={snapshot.identity.id}` on `HistorySection` would make D-62 hold structurally.

**LOW: the relocated rows show raw stored direction values.**
- `DateDetailSheet.tsx:214-216` joins raw `r.direction` (`outbound`/`inbound`/`mutual`), and nothing maps them to labels (grep found no direction-label map).
- The accepted mockup shows "Outbound · Great".
- This is cosmetic and comes up at the D-63 sign-off. It's cheaper to decide before Plan 02 than to fix in a gap plan.

**LOW: a records-but-no-interactions year reads "2023 · 0 interactions" (Plan 02 Task 2).** This applies D-18 + D-35 literally, but it's owner-visible copy and may read like an empty year. It's worth one line in the Plan 06 report. Don't reinterpret D-35.

**LOW: comments left stale.**
- `ProfileModuleHost.tsx:441-444` (the `renderHistory` comment: "Heatmap + Intensity + Rolodex browser") is not in Plan 02's comment sweep. Plan 03 edits that file anyway.
- `DateDetailSheet.tsx:21-25` (the stale "dormant" comment) is copied into `HistoryStreamRows`. Plan 02 does fix this.

**LOW: the release-bundle grep runs against Hermes bytecode (Plan 06 Task 2).** `index.android.bundle` is HBC. Literal strings live in its string table, so `grep -a -c` works, but `0` is only meaningful if the same grep returns `>0` on a DEBUG bundle. Add that positive control.

**LOW: dataset size spec is loose.** Dense is specified as "more than 20" records, while Plan 02's test and Plan 06 check 2 assume exactly 25. Pin Dense to 25 in the spec.

## 4. Suggestions

1. **Plan 01:** add a dev-menu item, "History: re-anchor fixture to today", that shifts every seeded row by whole days through `editTouchpointFullCore` (the orrery re-anchor pattern). Alternatively, build each contact's dates from a stored anchor so they can be shifted. Plan 06 Task 1 should run it first.
2. **Plan 01:** add a `verifyHistoryFixture` (per-dataset family counts via `readContactHistory`, group-linked present, `archived_at` set). Report `partial` with the problems instead of `present` when it fails. Put the idempotency marker on the *last* write, for example the Archived contact's uid.
3. **Plan 03 Task 1:** after `scrollWithinHistory`, re-measure once on the next `onNodeLayout` (or `onContentSizeChange`) for the same generation, to undo a clamped landing. Add a node test in `module-host-model.test.ts` for a "second call wins" contract if one is introduced.
4. **Plan 03 Task 3:** put the consumer grep *before* `git rm`, and record its output in the SUMMARY (the orphaned-consumer memory).
5. **Plan 04 Task 2:** make `pickerInitialMonth` take the app-bar bottom as `viewportTop`, and use the current month whenever no header sits at or above it. Add a test case for "first visible header ≠ current month, not scrolled in".
6. **Plan 05 Task 1:** add one explicit test: paged back, rollover by 1 day, then prev/next refs. Document whether the page stays aligned to `refDate` or realigns.
7. **Plan 02:** decide the direction label casing (title-case through a small map in `HistoryStreamRows`) before the sign-off, or list it in the Plan 06 report as a known look item.
8. **Plan 06 Task 2:** add a debug-bundle positive control for the seed-label grep. Split "release build + measurements" from "docs + report" as two checkpoints inside the task, so running out of context doesn't lose the measurements.
9. Optionally, key `HistorySection` on `contactId` in Plan 02 (a one-line change in `ProfileModuleHost.tsx:446`).

## 5. Risk assessment: MEDIUM

The data layer isn't at risk. There are no writes, no schema change, and no backup change, and every new behaviour is a pure derivation over an unchanged, well-typed read. The contract-test and tsconfig/Biome archive steps are specified precisely enough to execute safely.

What remains is (a) mechanical: nested `measureLayout` scrolling inside the Profile ScrollView, and the Reanimated highlight on Hermes, which vitest can't see; and (b) verification: stale or half-finished seed data that can quietly weaken the Plan 06 device pass the owner's sign-off depends on. Both can be fixed by small additions to Plans 01, 03 and 04. None of them reverses a D-NN.
