## Critical Issues

### CR-01: Records added above the user drop the last rendered day, so the place is lost (D-31 / D-62)

**File:** `src/components/history/history-stream-logic.ts:337-376` (`requestedCount` / `visibleYear` / `streamStateOnShowOlder`), `src/components/history/HistorySection.tsx:914-942` (the anchor effect)

**Issue:**
- `StreamViewState.shown` stores a requested record count for each year. `visibleYear` re-slices `snapToDayEnd(records, requested)` against the new records on every re-read.
- Say the last rendered day starts at index `s`. After `m` records are added above it, that day stays visible only if `s + m <= requested - 1`.
- With typical sparse data (about one record per day), the last visible day starts exactly at `requested - 1`. One new record at the top therefore removes it. The "Show older" button jumps up to where the day was, and if the user was at the bottom the ScrollView clamps.

**Realistic triggers, all named in D-62 ("Returning from Detail/Edit/Log/MemoryHistory while the Profile is mounted keeps the place"):**
- **Log from the Profile + button.** A new record lands today, at the top of the current year.
- **Edit from MemoryHistory**, reached by tapping a knowledge row near the bottom of a chunk. It writes a new knowledge row at now, again at the top of the current year.
- **An InteractionDetail redate into the current year** from an older year.

**The anchor does not catch it.** The D-31 anchor effect decides "still in place" with `streamModel.dayIndex.has(anchor.day)` (line 926). It only checks that the day still exists, not that it is still rendered. A knowledge-row anchor (`recordKey: null`) whose day just fell off the rendered tail therefore issues no reveal and no scroll. The summaries' D-31 claim ("the Profile keeps its scroll position") holds only when nothing is added above the user.

**Fix:** Pin each year's boundary to a record, not a count. Either:
- **(a)** store the oldest rendered record key for each year in `shown`, and rebuild the count from it, or
- **(b)** on each new `history`, raise every open year's requested count by the number of records added newer than the previous boundary.

Also check the anchor against what is rendered, not just against `dayIndex`:

```ts
// history-stream-logic.ts
export interface StreamViewState {
  readonly openYears: ReadonlySet<number>;
  /** Year → key of the oldest record the user has made visible (null = initial chunk). */
  readonly through: ReadonlyMap<number, string>;
}
function requestedCount(state, entry): number {
  const key = state.through.get(entry.year);
  if (!key) return STREAM_INITIAL_VISIBLE;
  const i = entry.records.findIndex((r) => r.key === key);
  return i < 0 ? STREAM_INITIAL_VISIBLE : i + 1; // snapToDayEnd still applies
}

// HistorySection.tsx anchor effect: treat "present but not rendered" as needing a reveal
else if (!streamModel.dayIndex.has(anchor.day) || !isDayRendered(streamState, streamModel, anchor.day)) {
  target = streamModel.dayIndex.has(anchor.day) ? anchor.day : nearestRemainingDay(streamModel, anchor.day);
}
```

Add a logic test: one record per day, Show older once, add one record today, then assert that the previously last-visible day is still in `visibleYear(...)`.

## Warnings

### WR-01: Row accessible labels hide the record content from screen readers

**File:** `src/components/history/HistoryStreamRows.tsx:104, 152, 183`

**Issue:** Each row's `accessibilityLabel` overrides its children. A TalkBack user hears:
- **Interaction rows:** "Interaction, Call, 3:42 PM[, group event …]". The direction / No reply / quality meta and the two-line note (D-41) are never read.
- **Knowledge rows:** they drop the value.
- **Lifecycle rows:** they drop the detail.

The retired sheet did the same, but it was a secondary drill-down. The stream is now the main record surface (D-10). A screen-reader user would have to open every record in InteractionDetail to hear anything, so the visual and spoken versions no longer match (D-07 a11y intent).

**Fix:** Build each label from what the row shows. For example:

```ts
accessibilityLabel={[`Interaction, ${r.channel}, ${formatTimeMinuteOrFallback(r.occurredAt)}`, meta || null, groupTitle ? `group event ${groupTitle}` : null, r.note].filter(Boolean).join(". ")}
```

Do the same with `r.value` for knowledge rows and `r.detail` for lifecycle rows. Keep the `formatTimeMinuteOrFallback(` call in each label so the timestamp contract still holds.

### WR-02: Cycles paging makes dates without a year ambiguous, and heatmap cell labels still read "1 interactions"

**File:** `src/components/history/ActivityHeatmap.tsx:229-234, 327, 341-348`; `src/components/history/history-stream-logic.ts:986-988`

**Issue:**
- **Year ambiguity.** D-25 paging (new in this phase) makes pages from earlier years reachable. Three things carry no year:
  - the page title (`formatMonthDay`);
  - every cycle and day cell's accessible label ("Mar 1 – Mar 30, …");
  - the empty-span note ("Nothing logged Sep 1 – Sep 7").

  With 20 cycles of 30 days, one page covers more than a year, so these labels are ambiguous on screen and when spoken. Plan 05 surfaced the visible title as an owner question. The accessible labels and the span note have the same defect and were not mentioned.
- **Plural bug.** Cell labels still say `${count} interactions`, so "Mar 4, 1 interactions" is read aloud. This is the same plural bug the CONTEXT logged as Defect #1 for the retired card. This phase added `interactionCountLabel()` but did not use it here.

**Fix:**
- Use `interactionCountLabel(count)` in both cell labels. That part is a plain bug fix.
- Add the year to the accessible labels whenever the span is not wholly in the current year. Screen readers lose nothing by hearing the year.
- The wording of the visible title and the span note is the owner's call. Fold it into the pending Plan 05 "Cycles titles have no year" decision rather than deciding it here.

### WR-03: On a new-year rollover, the year the user was browsing collapses

**File:** `src/components/history/history-stream-logic.ts:239-245` (`isYearOpen`), `src/components/history/HistorySection.tsx:418-423, 626-630`

**Issue:**
- `isYearOpen` treats `model.currentYear` as always open, and `openYears` holds only older years the user expanded.
- When a Profile revision crosses Dec 31 → Jan 1 (for example, returning from Edit just after midnight), `advanceHistoryDay` moves `today` forward.
- `buildStreamModel` then treats the old current year as an older year that is not in `openYears`. It collapses to a single "2026 · N interactions" row, and the user's place inside it is gone.

This breaks D-31/D-62 "keeps the place while mounted". It is rare, but there is no recovery: the user has to re-expand the year and press Show older again.

**Fix:** When the model's `currentYear` advances while mounted, add the previous current year to `openYears`. Its `shown` entry is already keyed by year and carries over.

```ts
const prevYearRef = useRef<number | null>(null);
useEffect(() => {
  if (!streamModel) return;
  const prev = prevYearRef.current;
  prevYearRef.current = streamModel.currentYear;
  if (prev !== null && prev < streamModel.currentYear)
    setStreamState((s) => streamStateOnExpandYear(s, prev));
}, [streamModel]);
```

## Info

### IN-01: The one-shot anchor survives a Detail closed without changes

**File:** `src/components/history/HistorySection.tsx:901-904`
**Issue:** The anchor is set when InteractionDetail opens and is cleared only when the next new `history` uses it up. Suppose the user opens a row, closes it, and the anchored day later vanishes through another path, such as deleting a group event from the Events tab. On the next focus revision, the Profile then scrolls to the "nearest remaining day" with no action from the user.
**Fix:** Clear `anchorRef` in `onRequestClose` when no edit or delete followed (in `onDeleted` and `onEdit`, keep it).

### IN-02: Reduced motion reaches the highlight late, so it starts a timed fade first

**File:** `src/components/history/HistoryHighlight.tsx:55, 92-104`
**Issue:**
- `useReducedMotion()` starts at `false` and loads the real setting asynchronously in each new instance.
- On a reduced-motion device the highlight therefore starts a timed fade, then snaps `progress` back to 1 and holds.
- The flicker is a few frames at most, so it is not visible, but it is avoidable.

**Fix:** Read `useReducedMotionShared()` inside a single `withTiming`/`withDelay` choice. Alternatively, start in hold mode and switch to the fade only once reduced motion is confirmed off.

### IN-03: JumpToDateSheet shows the previous session's year for one frame on open

**File:** `src/components/history/JumpToDateSheet.tsx:55-59`
**Issue:** `year` is reset inside a `useEffect` after `visible` turns true. The first rendered frame of the opening sheet therefore shows the year (and dots) the user last stepped to.
**Fix:** Mount the sheet's content keyed by an open counter, or derive the year as `visible && !touched ? initialYear : year`.

### IN-04: Jump to date can wait up to 150 ms to measure headers for a case D-68 says cannot happen

**File:** `src/components/history/HistorySection.tsx:785-836`
**Issue:**
- `openJump` measures every registered month header with `measureInWindow`, and waits up to `PICKER_MEASURE_TIMEOUT_MS` before the sheet opens.
- D-68 records that the "month in view" branch cannot occur under D-32. The added latency, and the cost of measuring every month header, buy nothing in practice.

This is kept deliberately for D-50 fidelity, so it is not a defect. It is noted for the device pass: if the button feels sluggish on a long history, this is the cause.

### IN-05: An empty-month or empty-day result relies only on a live region for screen readers
