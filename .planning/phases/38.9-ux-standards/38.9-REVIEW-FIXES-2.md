## Warnings

### WR-01: The new exit hold drops taps with no visible state, and can last as long as the shared write mutex is busy

**File:** `src/components/group/GroupTitlePromptSheet.tsx:109-116`; `src/components/PostLogNoteEditor.tsx:400, 447-461`

**Issue:** While `savingRef` is set, **Cancel**, **Done**, **Create event**, the form's Cancel,
the scrim and system Back all do nothing silently. None of them looks disabled:
`confirmDisabled={!trimmed}` ignores the in-flight state, and the post-log buttons get no
`disabled` at all. The fix table itself notes that "a second Create event tap during the write is
dropped". Every one of these writes runs inside `inWriteTransaction` → `withMutex`. According to
`db/transaction.ts:66-70`, a backup export snapshot can hold that mutex "for the entire snapshot and
can delay every app write". So the hold is finite but has no upper bound. During it, the sheet looks
frozen: Cancel and Back do nothing, and nothing shows why. D-26 ("Disabled controls are dimmed")
expects a control that will not act to look disabled. The contact screens already pair their ref
with a `saving` state for exactly this reason.

**Fix:** Mirror the contact-screen idiom. Keep the ref as the guard, and add render state for the
look:
```tsx
// GroupTitlePromptSheet
const [busy, setBusy] = useState(false);
// in confirm(): savingRef.current = true; setBusy(true);
// release: savingRef.current = false; setBusy(false);
<ConfirmActions ... confirmDisabled={!trimmed || busy} cancelDisabled={busy} />
// PostLogNoteEditor: same `busy` state set/cleared beside savingRef in
// saveNote/createMemory/onEditMemory; pass disabled={busy} to Cancel, Done,
// Create Memory Instead and Save.
```
(If `ConfirmActions` has no `cancelDisabled`, add it there with the dimmed look.)

### WR-02: Create/Edit Contact still allow "Discard changes" during an in-flight save, which then commits and navigates anyway (pre-existing; not a regression)

**File:** `src/screens/CreateContactScreen.tsx:435-450, 500-517`; `src/screens/EditContactScreen.tsx:1189-1195, 1129-1130`; `src/navigation/discard-keep-guard.ts:166-200`

**Issue:** IN-04 made Save single-flight, but the screen's exits are not held during the save, so
the hold rule IN-01 just set for the sheets does not apply here. Sequence (Create): tap Save, which
enters `createContactFull`, then press Back. The `beforeRemove` listener sees
`hasUnsavedChanges` true and `bypassRef` false and shows "Discard changes?". The user taps **Discard
changes** and the route is removed. The write then commits, the contact exists even though the
user chose Discard, and the code runs `bypassRef.current = true` plus `navigation.replace(...)`, or
for `host === "settings"`, `navigation.goBack()` and
`openProfileInContactsTab(navigationRef.current, contactId)`. The last call goes through the
**root** ref, so it still pulls the user into the new Profile on the Contacts tab after they
discarded and left. Edit Contact does the same: its save commits, then
`navigation.navigate("Profile")` runs from a removed screen. No data is corrupted, but the user's
explicit choice is contradicted. The code predates this pass, but it is in the files reviewed and
in the same class as IN-01.

**Fix:** Hold removal while a save is in flight, the same way the sheets now do:
```ts
// useDiscardKeepGuard: accept an optional busyRef
navigation.addListener("beforeRemove", (event) => {
  if (bypassRef.current) return;
  if (busyRef?.current) { event.preventDefault(); return; } // save owns the exit
  ...
});
// Create/Edit: useDiscardKeepGuard({ ..., busyRef: savingRef })
// and ShellAppBar backDisabled={saving} for the look (as RestorePreview does).
```
This is a planner call: it enforces D-13/D-14 and reverses nothing.

### IN-01: Edit Memory's Delete / Restore / Allow AI are not held during an in-flight memory edit

**File:** `src/components/PostLogNoteEditor.tsx:271-315`; `src/components/MemoryEditor.tsx:613, 629, 643`

**Issue:** `onDeleteMemory`, `onRestoreMemory` and `onSetMemoryAllowAi` ignore `savingRef`. If
"Move to Recently Deleted" is tapped while an edit save is pending, both writes run, serialized by
the mutex (edit first). Then `onClose()` runs and the late `setCreatedMemory(outcome.row)` lands on
a closed sheet. Nothing is corrupted, because the reset effect clears state on the next open, but
this is the one set of controls in the sheet that the IN-01 rule does not cover.

**Fix:** `if (savingRef.current) return;` at the top of the three handlers.

### IN-02: HistorySection's conversion `.catch` swallows the reason and also catches success-branch throws

**File:** `src/components/history/HistorySection.tsx:1283-1291`

**Issue:** `.catch(() => setConversionError(...))` logs nothing. The DAO's specific rejections
("no longer standalone", "no interaction matched") are lost, and with them any field diagnosis.
Because the `.catch` comes after `.then`, a throw from `navigation.navigate` after a committed
create would also show "Couldn't create this event" for an event that exists. `setConverting(false)`
has already closed the sheet, so the stale error would only flash on the next open, which clears it
at `:1250`. This predates the pass. The pass made this chain the sheet's release signal, so it is
noted here.

**Fix:** `.then(onSuccess, (err) => { Logger.error(LOG_SCOPE, "convert to event failed", err); setConversionError(...); })`.

### IN-03: The new component test drives `useState` by call order; the contact contract test is source-text only

**File:** `src/components/PostLogNoteEditor.close.test.tsx:117-140`; `src/screens/contact-save-single-flight-contract.test.ts:44-61`

**Issue:** The close test assigns state by hook index ("text, error, createdMemory,
editingMemory, globalAi, memoryDraftDirty"). Adding or reordering one `useState` in
`PostLogNoteEditor` silently shifts every value, and the tests may still pass on the wrong state.
The contact test asserts substrings (`endInFlight(savingRef)` appears once). A refactor that keeps
the text but moves the call out of `finally` is caught only by the order check, if one exists. A
behaviour that is never executed is not proven.

**Fix:** Assert the hook count in the harness (`expect(state.index).toBe(6)` after render), so a
new hook fails loudly. Leave the contract test as it is, as a tripwire.

### IN-04: A failed memory edit in the post-log sheet is still silent (pre-existing)

**File:** `src/components/PostLogNoteEditor.tsx:248-251`

**Issue:** On `write-failed`, `onEditMemory` logs and returns `false`. `MemoryEditor.commit` then
keeps the form open, and the Edit Memory view shows no error. Save appears to do nothing. Not
introduced by this pass. Now that the form's Cancel prompts, the user's way out is clear, but the
failure is not.

**Fix:** Set an error string on `write-failed` and render it under the Edit Memory heading with
`colors.danger` (as the Add Note view does).
