## Warnings

### WR-01: The Add Note sheet's own exits still discard typed text; Edit Memory "Done" silently drops an edited memory

**File:** `src/components/PostLogNoteEditor.tsx:373` (also `:420`; `src/components/group/GroupTitlePromptSheet.tsx:88`)

**Issue:** CR-02 guarded only `Sheet.onRequestClose`. In the same sheet:
- **Edit Memory view.** The `MemoryEditor` opens with the form already open
  (`initiallyEditingId`), and a **Done** button (`onPress={onClose}`) sits right under the form's
  Save. A user edits the memory and taps Done. The sheet closes with no prompt and the edit is lost.
  `memoryDraftDirty` is already tracked (`:80, :364`) but Done ignores it. Back on the same view now
  asks first, so Back and Done behave differently.
- **Add Note "Cancel"** (`:420`) and **GroupTitlePromptSheet "Cancel"** (`:88`,
  `onCancel={onRequestClose}`) close at once over typed text. The fixer left these as direct closes
  on purpose. D-61's rule is "An editor's own Cancel button follows the same rule as Back (D-13/D-14):
  with typed changes it shows 'Discard changes?'". Its "Applies to" list does not name these two
  sheets, so Cancel is a judgment call. Done in the Edit Memory view is not: it is an exit that
  throws away a typed edit.
- The `MemoryEditor` here also gets no `onCancelRequest`, so the form's own Cancel discards the
  edit at once (`MemoryEditor.tsx:91-95`).

Enforcing D-13/D-14/D-61 here is a planner call. It does not reverse a decision.

**Fix:**
```tsx
// PostLogNoteEditor: one dirty-aware close for every exit
const requestSheetClose = () => { /* as now */ };
...
<MemoryEditor ... onCancelRequest={(close) =>
  memoryDraftDirty ? void confirmDiscard().then((d) => { if (d) close(); }) : close()} />
<Button role="tertiary" label="Done" onPress={requestSheetClose} />
...
<Button role="tertiary" label="Cancel" onPress={requestSheetClose} />
// GroupTitlePromptSheet
<ConfirmActions ... onCancel={requestSheetClose} />
```
Keep successful Save, Create Memory, and the post-edit close direct (D-61).

## Info

### IN-01: A Discard prompt can outlive its sheet when a save lands while it is open

**File:** `src/components/PostLogNoteEditor.tsx:118-174, 325-339`; `src/components/group/GroupTitlePromptSheet.tsx:40-50`

**Issue:** `requestSheetClose` does not check `savingRef`. The sequence: Save is tapped, Back is
pressed during the `readInteractionForEdit`/`editTouchpointFull` await, and "Discard changes?"
opens. The save then completes and calls `onClose()`, so the sheet disappears. The prompt stays on
screen over nothing, and "Discard changes" afterwards calls `onClose()` a second time. No data is
lost: the note is saved even though the user may then tap "Discard". But the prompt contradicts
what happened.

**Fix:** In `requestSheetClose`, `if (savingRef.current) return;` (hold Back while a write is in
flight), or skip the prompt when a save is pending.

### IN-02: Two D-22 "group" noun sites left outside the WR-03 pass

**File:** `src/components/group/GroupTitlePromptSheet.tsx:56`; `src/components/history/InteractionDetail.tsx:163`

**Issue:** Both read "Make this a group interaction". The same sheet then says "Give this event a
title" / "Create event". D-22 makes "Event(s)" the user-facing noun. "Group Log" and "Group Note"
are decided names; "group interaction" is not.

**Fix:** For example, "Make this an event" (plain-word copy under D-41, the planner's call). Add it
to `glossary-contract.test.ts`.

### IN-03: The standalone Off Limits editor's draft row is still unguarded (known, homed in 38.10)

**File:** `src/screens/OffLimitsEditorScreen.tsx:90`

**Issue:** This is the only `FuelEditor` consumer without `onDraftStateChange` or a guard. Back with
a typed, not-yet-added item loses it. The 38.9 workpaper (§4.B.1 `:179`, `:649`) already records
this as a gap for 38.10 (fuel retirement may delete the screen), so it is not a regression. CR-01's
new `FuelEditor` contract makes the fix a few lines if 38.10 keeps the screen.

**Fix:** None in 38.9. Carry the note to 38.10.

### IN-04: Create/Edit Contact save guard reads `saving` from a render closure; a duplicate-name false resets it mid-flight

**File:** `src/screens/CreateContactScreen.tsx:455-523`; `src/screens/EditContactScreen.tsx:987-1132`

**Issue:** `if (saving) return` is state, not a ref. If two Save presses reach `handleSave` before
a re-render, the second one now gets `false` from `confirmDuplicate` (WR-01 fix), returns, and its
`finally` runs `setSaving(false)` while the first dialog is still open. Save is then live again
during the first save's `createContactFull`. This is far less harmful than before the fix, when
both callers got `true` and could create two contacts. React's discrete-event flush makes it hard
to reach.

**Fix:** Use a `savingRef` single-flight (the `MemoryScreen` `beginInFlight` idiom) next to the
state.

### IN-05: `DEFAULT_BACKUP_HOST = "backup-tab"` has no host left after IN-01

**File:** `src/screens/backup-dualhome-logic.ts:12,19`; `BackupScreen.tsx:86`, `RestorePreviewScreen.tsx:100`, `RestoreResultScreen.tsx:20`

**Issue:** With `BackupStack.tsx` deleted, every mounted host passes `host="settings"`
(`SettingsStack.tsx:148-160`). The `"backup-tab"` default and its branches (title, root variant,
reset-to-Backup) are now dead paths. A new mount that forgets `host` would silently get the old
tab behaviour.

**Fix:** Make `host` required or default it to `"settings"`. Remove the `"backup-tab"` branches
when convenient.
