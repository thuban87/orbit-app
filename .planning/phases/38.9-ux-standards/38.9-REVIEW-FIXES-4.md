## Critical Issues

### CR-01: A parked widget/notification RESET comes back with no "Discard changes?", so typed work is silently lost

**File:** `src/navigation/discard-keep-guard.ts:261, 303`. Mechanism: `node_modules/@react-navigation/core/src/useOnPreventRemove.tsx:42-50, 56-59, 73`.

**Issue:** React Navigation 7 tags the action it passes to `beforeRemove` with a hidden
`VISITED_ROUTE_KEYS` set. It adds the guarded screen's key **before** emitting (`:73`). On any
later dispatch of that same object, it **skips** every key already in the set (`:56-59`). The
guard parks exactly that tagged object (`event.data.action`, `:261`) and re-dispatches it unchanged
(`:303`). So on the settle, this screen's `beforeRemove` never fires. The C6-H1 rule the fix claims
to restore ("prompts when typed work would be lost") is never applied, and the RESET removes the
screen with its typed contents and no prompt.

This is the same property that makes the guard's own Discard path (`:276`) work without
looping. The guard test that claims "dirty work prompts once" (`discard-keep-guard.test.ts:538-552`)
re-fires `beforeRemove` by hand (`:545`, "The navigator emits beforeRemove again"). The real
navigator does not, so the test passes on behaviour that does not exist on the device.

**Realistic repro (no race needed):** New contact → type a name that already exists plus any other
details → Save → the "Duplicate name" dialog opens (the claim covers it,
`CreateContactScreen.tsx:482`). The user taps a widget or a reach-out notification: the RESET is
held and parked, and the dialog is still showing. The user taps Cancel or Back on the dialog →
`return` → `finally` → `settleHold()` → the app jumps to the widget target, and the whole new-contact
form is gone with no prompt.

Before this pass, the widget tap was dropped and the form was kept. The same thing happens on:

- Edit Contact (duplicate dialog).
- CustomFields ("Change field type" / "Change dropdown options" cancel).
- Any covered save whose write fails: an UpdateContact row, AIPersonalization sections (also an
  unsaved Writing Style draft), EditInteraction, GroupLog, and the rest.

There is no loop and no double navigation. The re-dispatch fires once and is never re-parked.

**Fix:** re-dispatch a fresh action object, so the navigator emits `beforeRemove` to this screen
again and the normal rule runs with the settled form. The object spread in React Navigation copies
the symbol, so build the copy from the plain fields:
```ts
// discard-keep-guard.ts flush effect, in place of navigation.dispatch(parked)
const { type, payload, source, target } = parked as NavigationAction & {
  payload?: object;
  source?: string;
  target?: string;
};
navigation.dispatch({ type, payload, source, target } as NavigationAction);
```
The listener then either allows the action or shows one "Discard changes?". Its Discard dispatches
the newly tagged `event.data.action`, which proceeds without looping. Replace the hand-fired test
at `discard-keep-guard.test.ts:545` with one that asserts the dispatched action is not the parked
object, or that it carries no own symbol keys. Device check: duplicate-name dialog → widget tap →
Cancel must show "Discard changes?".
