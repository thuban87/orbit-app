## Critical Issues

### CR-01: The Off Limits draft on Add Contact and Edit Contact is unguarded; Back or folding the section throws away typed text

**File:** `src/components/FuelEditor.tsx:376-389`; `src/screens/CreateContactScreen.tsx:423-437, 870-895`; `src/screens/EditContactScreen.tsx:1174-1186, 1714-1730`

**Issue:**
- `FuelEditor`'s `DraftRow` keeps the new item's kind, text, label and url in private state.
  Nothing reaches the form until the user taps "Add".
- The Memory and Key People drafts were wired into the guard: `onDraftStateChange`, a
  `closeDraft` handle, `pickCreateSubEditor` and the D-68 fold `requestClose`.
- The Off Limits `FuelEditor` on both forms was not:
  - `hasUnsavedChanges` compares only `fuelDrafts` (Create) or the seeded off-limits rows (Edit),
    so an un-added draft never counts.
  - No sub-editor reports it.
  - The Off Limits section's `onExpandedChange` folds without asking.

Result: on Add Contact, a user opens Show More, starts an Off Limits item, types text and presses
Back (header, system or gesture). The form leaves at once with no prompt and the text is gone. The
same happens on Edit Contact, and when either form folds the Off Limits section. This is exactly
the E-01 / D-13 / D-14 / D-68 class this phase exists to close ("Back ... prompting only if typed
text would be lost"). The device check "Back with typed text on every newly guarded surface" would
not catch it unless the draft row is exercised.

**Fix:** Give `FuelEditor` the same contract as `MemoryEditor`/`RelationshipEditor`:
```tsx
// FuelEditor: lift the draft state, or report it
export type FuelEditorHandle = { closeDraft(): void };
onDraftStateChange?.({ open: draftOpen, dirty: text.trim() !== "" || label.trim() !== "" || url.trim() !== "" });
```
Then, in both screens:
- add `offLimits: offLimitsDraft` to `pickCreateSubEditor`, with the `close` dispatching to
  `fuelEditorRef.current?.closeDraft()`;
- route the offLimits section fold through
  `requestClose(() => { fuelEditorRef.current?.closeDraft(); setSectionExpanded("offLimits", false); }, offLimitsDraft.dirty)`;
- add a guard test that opens the draft, types, and presses Back.

### CR-02: The Add Note sheet throws away a typed note on Back or a scrim tap (D-14)

**File:** `src/components/PostLogNoteEditor.tsx:317-320` (consumers: `src/screens/HomeScreen.tsx:2280`, `src/components/UniversalFab.tsx:393`)

**Issue:**
- `<Sheet visible={target !== null} onRequestClose={onClose}>`: the system Back and the scrim
  both call `onClose` directly.
- The sheet holds the typed `text` (and, in its expanded branch, a `MemoryEditor` edit).
- D-14 is a decided rule: "Back first closes the innermost sheet ... prompting only if typed text
  would be lost". The Phase Boundary promises a guard on "every ... note-holding overlay".
- D-45 names this exact sheet as a person-scoped form, and it gained its person line in this
  phase, but not the guard.
- `PendingConfirmationsSheet` (J-07) shows the pattern was available: it uses
  `confirmDiscard()` in `requestSheetClose`.

`GroupTitlePromptSheet.tsx:37` (a typed group title, `onRequestClose` passed straight through) has
the same shape at lower stakes.

**Fix:**
```tsx
const requestClose = () => {
  if (text.trim() === "" && !memoryEditDirty) return onClose();
  void confirmDiscard().then((discard) => { if (discard) onClose(); });
};
<Sheet visible={target !== null} onRequestClose={requestClose} ...>
```
Keep a successful Save closing directly (D-61).

## Warnings

### WR-01: The confirm de-duplication shares one answer, so a double tap runs an irreversible action twice (focus item 1: real)

**File:** `src/stores/confirm-store.ts:18-25, 172-216`, and the call sites below

**Issue:** An identical `confirm()` returns the pending request's promise. Both callers get
`true` from one tap on Confirm. Any handler without its own synchronous in-flight guard therefore
runs twice. Before this phase, two native Alerts needed two separate confirmations. Now a single
tap does it. Sites verified on disk:
- **`MergeImpactSummary.tsx:73-102, 150-155`:** no guard at all. Two `mergeContactsWithPhotoOwnership`
  calls start. Both read the absorbed contact as live before the path lock, so the second stages
  photos and then fails inside `mergeContacts` ("absorbed contact is already tombstoned"). The
  "Merge contacts" button also stays live while the merge runs, so a later tap opens a fresh
  confirm. The DAO checks keep the data safe, but it is wasted work, plus a failure path running
  against freshly finalized photo files.
- **`ArchivedContactsScreen.tsx:133-185` (purge):** two taps run two `computeImpact` calls, which
  produce the same message, so one confirm resolves both into two `purgeContact` calls. The second
  throws "not archived — refusing to purge", which shows a false "Couldn't delete. Please try
  again." snackbar right after a successful permanent delete.
- **`BackupScreen.tsx:241-256`:** both callers resolve in the same microtask. `runExport`'s
  `if (exporting) return` reads a stale closure, so two exports and two share sheets run.
- **Others with the same shape:**
  - `CustomFieldsScreen.tsx:310-325` (permanent delete);
  - `SystemsManagementScreen.tsx:103-115, 471-490`;
  - `OffLimitsEditorScreen.tsx:68-80`;
  - `ProfileBackgroundManager.tsx:674-700`;
  - `SystemBuilderScreen.tsx:512-532`;
  - `ContactProfileScreen.tsx:751-790`, where Unbind and Reset are buttons in a sheet.

The guarded sites are fine: `RestorePreviewScreen` (single-flight), `use-import-leave-guard`
(`promptPendingRef`), and the Create/Edit duplicate-name prompt (`saving`).

**Fix:**
1. Fix it once, in the store. A duplicate `confirm()` shows no second dialog and resolves `false`
   for the second caller, which is what `confirmDiscard()` already does. Notices can keep sharing.
   ```ts
   export function confirm(request: ConfirmRequest): Promise<boolean> {
     if (findPending({ kind: "confirm", request })) return Promise.resolve(false);
     ...
   }
   ```
2. Also give `MergeImpactSummary` an in-flight ref and a disabled, dimmed "Merge contacts" button
   from the confirm until it settles.

### WR-02: Orbit switches flip to "Off" on every focus and during every save, because callers pass `disabled={busy}`

**File:** `src/screens/SettingsOrreryScreen.tsx:62-63, 139-148`; `src/components/orrery/OrreryViewOptions.tsx:86-87, 188-201`; `src/components/ui/orbit-switch-logic.ts:226-232`

**Issue:**
- `resolveSwitchVisual` draws any disabled switch as Off (D-26).
- Both Orrery screens compute `disabled = busy || !preferences.hydrated`, where
  `busy = hydration === "loading" || saving`.
- `hydrate()` runs on every focus. So the Relationship Satellites switch shows dimmed Off on each
  visit, and again during each save, then snaps back to On.
- In `OrreryViewOptions`, the text beside it says "On" while the switch is drawn Off.
- The RN Switch it replaced kept showing the stored value while disabled. OrbitSwitch has a
  separate `busy` prop "announced, never drawn" for exactly this case, but the callers also pass
  busy through `disabled`.

**Fix:** Pass `disabled={!preferences.hydrated}` and `busy={busy}`, and ignore presses while busy
inside `onValueChange` (or give OrbitSwitch a press-blocking `busy` that does not change the
drawing). Check the other `disabled=` callers the same way: `SettingsInteractionsScreen.tsx:217`,
`SettingsAIScreen.tsx:164`.

### WR-07: [OWNER] Header Back on Import complete and Check complete returns to a finished flow's setup screen (focus item 3)

**File:** `src/screens/ImportCompleteScreen.tsx:200`; `src/screens/ReconcileCompleteScreen.tsx:81`

**Fix:** Owner decision. Options:
(a) header Back = Done (`onBack={() => navigationRef.current?.reset(resetToDashboardRoot())}`, plus

(c) `backKind="cancel"` with Done semantics.
