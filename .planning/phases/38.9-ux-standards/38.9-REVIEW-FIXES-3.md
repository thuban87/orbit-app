## Summary

Every fix listed in `38.9-REVIEW-FIXES-2.md` is in the code on disk. I found **no path that
leaves an in-flight ref held for good.** I traced each claim:

- Every claim comes after validation, and nothing that can throw sits between the claim and the
  `try`. EditParticipant and EditGroupEvent build patches in that gap, but the builders are
  pure.
- Every release runs in `finally`.
- Every `confirm` the hold waits on can be dismissed (Back / scrim resolve false). Nothing outside
  tests clears the confirm queue without resolving it.
- UpdateContact's shared slot is released in the save closure's own `finally`, so an editor that
  unmounts mid-save still frees it. `onSaved` runs inside the `try`, so the slot is free before
  any other row can open.

No save's own navigation is held: every save sets `bypassRef` before `replace` / `goBack` /
`navigate`, the guard checks bypass first, and MemoryScreen's deferred `goBack` runs after the
release. In MemoryEditor, Allow AI uses `OrbitSwitch busy` and is never drawn disabled, so it is
never drawn Off while busy (C5-M2 / D-26 kept). No other caller of a changed component changes
look: every new prop defaults off.

Two WARNINGs remain:

1. The hold silently drops a widget- or notification-driven RESET. The hold lasts for the whole
   claim, including user-paced dialogs, and this goes against the 38.9-02 plan's C6-H1 truth.
2. List-level controls that swap or reset the draft being saved are still live while busy, so a
   failed save can lose the user's typed edit with no prompt.

## Warnings

### WR-01: The hold silently drops widget and notification RESETs, for as long as a user-paced dialog inside the claim stays open (code-level)

**File:** `src/navigation/discard-keep-guard.ts:93-94, 207`; `src/navigation/widget-linking.ts:330-341`; `src/screens/CreateContactScreen.tsx:482-497`; `src/screens/EditContactScreen.tsx:993-1008`; `src/screens/CustomFieldsScreen.tsx:210-245`

**Issue:** `decideGuardOnRemove` returns `"hold"` for **every** action type while busy. A
`navigationRef.current?.reset(...)` from `WidgetLinkingGate` (or the notification gate) therefore
gets `preventDefault` from the guarded screen's listener. The gate then calls
`setPending(null)` regardless (`widget-linking.ts:331, 341`), so the widget tap is consumed and
does nothing, with no feedback. That is a stated trade-off in REVIEW-FIXES-2, which assumed the
window is a short write. It is not: three claims deliberately cover an interactive dialog.

- Create and Edit Contact claim before `confirmDuplicate` ("Duplicate name").
- CustomFields claims before `confirmSummary` ("Change field type" / "Change dropdown options").

While either dialog is open, which can be for any length of time, every widget tap, reach-out
notification and post-merge-style RESET into the app is thrown away.

This also changes a recorded plan truth. `38.9-02-PLAN.md:53` (review C6-H1, under D-14) says: "any
other route removal (the post-merge reset, a widget-link reset, a tab re-tap pop) … proceeds at
once when nothing typed would be lost, otherwise shows one 'Discard changes?' whose Discard
completes that same navigation". The fix doc says "nothing reversed". That holds for
ADRs, HANDOFF and D-NNs: C6-H1 is a plan-review rule, not an owner D-NN, so this is **not an
ESCALATE** under CLAUDE.md. It is still a behaviour change against a recorded truth, and it should
be disclosed rather than called "nothing reversed".

**Fix (keeps the hold, loses nothing):** park a non-Back action and re-dispatch it when the save
settles, unless the save itself navigated:
```ts
// useDiscardKeepGuard
const parkedRef = useRef<NavigationAction | null>(null);
// in the listener, decision === "hold":
if (!BACK_ACTION_TYPES.has(event.data.action.type)) parkedRef.current = event.data.action;
return;
// returned alongside requestClose:
const settleHold = () => {
  const parked = parkedRef.current;
  parkedRef.current = null;
  if (parked && !bypassRef.current) navigation.dispatch(parked);
};
// each covered save: finally { endInFlight(savingRef); setSaving(false); settleHold(); }
```
The other option is to stop the claim from covering the dialog wait. That would bring back the
IN-04 double-submit window, so parking is the better fix.

### WR-02: List-level controls that swap or reset the draft being saved are still live while busy; on a failed save the typed edit is lost with no prompt (code-level)

**File:** `src/components/MemoryEditor.tsx:345-348, 421-425`; `src/components/RelationshipEditor.tsx:218-236`; `src/screens/AIPersonalizationScreen.tsx:700-717`

**Issue:** The pass holds each form's own Cancel / Save / Delete / Restore. It leaves alone the
list controls that **replace the open draft**:

- **MemoryEditor.** Every `MemoryCard` stays pressable (`onPress={() => openExisting(item)}`),
  including the single card above the Edit Memory form in `PostLogNoteEditor` and every card on
  MemoryScreen. Tapping during an edit save calls `setDraft(initialDraft(item))`. If the save then
  fails (`write-failed` → `return false`), the form stays open with the **stored** values, or with
  another memory's values. The user's typed edit is gone, and the error caption invites a "retry"
  that saves nothing. On success, `commit`'s `close()` closes the form the user just opened.
- **RelationshipEditor** (Update Contact → Key people, `busy={saving}`): **Edit** on another row
  swaps the draft in the same way. **Show on Profile** calls `onEdit`, which the shared slot drops
  silently (`beginInFlight` false → `return false`) while it is drawn enabled (D-26). **Delete**
  is already noted in REVIEW-FIXES-2.
- **AIPersonalization:** during a section save, **Rename / edit** on another section calls
  `setEditingUid(other)`. That unmounts the saving `SectionEditor` and loses its local
  title/body. On failure the error shows with the user's text gone. **Replace from file** and
  **Delete section** on the section being saved race the update (they are serialised by the mutex,
  but the order is not defined).

Without `busy`, a card tap over a dirty draft also resets it with no "Discard changes?" (a D-13
gap that predates this pass). The pass made `busy` the contract for "controls the save holds",
and these controls are outside it.

**Fix:** hold them while busy, as the pass did for Cancel:
```tsx
// MemoryEditor
<MemoryCard ... onPress={busy ? undefined : () => openExisting(item)} />
// RelationshipEditor: disabled={busy} on Edit, Delete, Show on Profile
// AIPersonalization: disabled={sectionFormBusy} on Rename / edit, Replace from file,
// Delete section (and on the overflow button that opens them)
```
(Separately, as a D-13 call for the planner: route a card tap over a dirty draft through
`onCancelRequest`-style dirty-aware switching.)

## Info

### IN-01: The held controls read render state, but the host drops on the ref; a tap in the same frame as Save is applied locally and never written (code-level)

**File:** `src/components/MemoryEditor.tsx:628-633, 651-655`; `src/components/PostLogNoteEditor.tsx:289-333`; `src/navigation/discard-keep-guard.ts:172-183`

**Issue:** `MemoryEditor` gates on the `busy` prop, which updates one render after the host claims
`savingRef`. In `PostLogNoteEditor` the host handlers return early on `savingRef.current`. If a tap
lands between the claim and the re-render:

- **Allow AI** flips `editing.allow_ai` locally, but `onSetMemoryAllowAi` drops the write. If
  the edit then fails, the open form shows an AI permission that was never stored. That can be
  "not allowed" over a stored On.
- **Delete** calls `close()` locally while the host drops the delete.

`useDiscardKeepGuard.requestClose` has the same gap, because it never reads `busyRef`. A Cancel
tapped in the same frame as Save prompts or closes during the save. The window is about one frame,
so this is low likelihood. The Allow AI case touches the consent display, so it is noted here.

**Fix:** have the host report whether it accepted the action: `onSetAllowAi` /
`onDelete` return `boolean`, and MemoryEditor applies the local flip or close only on `true`.
Add `if (busyRef?.current) return;` at the top of `requestClose`.

### IN-02: AIPersonalization reports a failed post-commit reload as a failed write (code-level; predates the pass, now inside the hold)

**File:** `src/screens/AIPersonalizationScreen.tsx:364-384, 419-437`

**Issue:** `addSection` and `saveEditedSection` `await load()` inside the write's `try`. `load`
has no catch of its own. If the reload fails after a committed create or update, the screen shows
"Couldn't add that section" or "Couldn't save that section" for a row that exists. The draft has
already been cleared, so the user retypes it and creates a duplicate. (CustomFields' `load` catches
on its own, so it is not affected.)

**Fix:** move `await load()` after the write's `try`, as MemoryScreen does (`restore` / `remove`),
with its own catch that shows the load error.

### IN-03: `docs/systems/ux-standards.md` is out of date with the follow-ups (documentation-level)

**File:** `docs/systems/ux-standards.md:139-142, 280-283`

**Issue:** The doc says the `busyRef` hold applies to "Create and Edit Contact". It now applies on

RelationshipEditor, FieldDefForm, section editors) and the shared AIPersonalization slot. The

**Fix:** update the bullet and add a Changelog row. Record the RESET behaviour, or its parking
fix, beside the C6-H1 rule.
