## Codex Review

## 1. Summary

**Changes are needed before execution.** The plans provide a coherent foundation-first sequence and preserve many important decisions, but several prescribed mechanisms leave gaps in unsaved-work protection and header coverage. The most consequential issues are nested editors that the proposed guard cannot observe, Cancel controls that bypass it, and asynchronous initialization that can incorrectly mark typed work as clean. This is a targeted source-verified review, not certification of every referenced file or all D-NN coverage. Repository HEAD was `d779d073`; no files were changed. The graph query failed because the sandbox denied its IPC socket.

## 2. Strengths

- **Separate overlay visibility from dismissal.** The existing shell explicitly calls `dismissTop()` on tab retap and hardware Back (`src/navigation/RootNavigator.tsx:110`, `:170`). Plan 01’s callback-free registry appropriately prevents that mechanism from gaining access to destructive dialogs.

- **Preserve dialog layout while changing presentation.** `src/components/ui/ConfirmDialog.tsx:134` delegates actions to `ConfirmActions`, whose measured row/stack layout begins at `:159`. Plan 01 retains this mechanism rather than replacing ADR-174’s behavior with a fixed layout.

- **Account for lazy tab initialization.** `src/navigation/tab-entry.ts:12–24` explains why `initial:false` is necessary, and `:63` supplies it. Plan 07 retains that entry helper and specifically addresses the separate mounted-Profile overwrite case.

- **Recognize backup refresh interference.** `src/screens/BackupSettingsScreen.tsx:96–100` currently reseeds both day fields and clears both errors after a read. Plan 03 correctly identifies that per-field saving must preserve the other draft.

## 3. Concerns

- **HIGH — Plans 02, 10: nested editor state is missing from the guard.**  
  **Evidence:** `src/screens/UpdateContactScreen.tsx:774–782` has a second editor level: choosing a generic custom field opens `CustomFieldFocusedEditor`, whose Cancel returns to the field chooser. `src/components/RelationshipEditor.tsx:52–59` separately owns its draft and picker state. Neither is observable through `session.activeRowKey` alone. Plan 02 also requires RelationshipEditor dirty reporting without listing that component among its modified files.  
  **Required edit:** In `38.9-02-PLAN.md`, Task 3, add explicit dirty/open/close reporting for both nested paths, include `RelationshipEditor.tsx` and its consumers in the ownership list, and specify innermost-first Back behavior. Add behavioral tests proving that Back closes the selected field editor before the outer chooser and protects a typed relationship draft.

- **HIGH — Plans 02, 10: visible Cancel controls bypass the new guard.**  
  **Evidence:** `src/components/MemoryEditor.tsx:246–249` clears the draft directly; its Cancel invokes `close` at `:502`. `src/components/FieldDefForm.tsx:396` invokes `props.onCancel`, wired directly to `setEditor(null)` at `src/screens/CustomFieldsScreen.tsx:334` and `:345`. Update Contact similarly closes its row directly at `src/screens/UpdateContactScreen.tsx:855`. These operations do not remove a route, so `beforeRemove` cannot protect them.  
  **Required edit:** In `38.9-02-PLAN.md`, Tasks 2–3, route user-requested editor cancellation through the same dirty-aware close function used by Back. Keep successful-save closure separate. Test dirty Cancel, clean Cancel, and successful save.

- **HIGH — Plan 02: Add Contact can capture user edits as its clean baseline.**  
  **Evidence:** The editable name exists before initialization completes (`src/screens/CreateContactScreen.tsx:193`, `:442`). Categories arrive asynchronously through `commitCategories` (`:282–289`), while other form data loads independently (`:291–314`). Capturing the *current form* when categories finish can include a name already typed by the user. The prescribed `baseline !== null` condition also leaves that early interval unguarded.  
  **Required edit:** In `38.9-02-PLAN.md`, Task 1, construct the baseline from seed values independently of the live draft. Apply asynchronous seed updates only to the relevant untouched field. Specify failure behavior and test typing before category resolution, failed initialization, and later catalog refresh.

- **MEDIUM — Plans 01, 02, 10, 17: native gesture protection is asserted without a supported mechanism.**  
  **Evidence:** The stacks use `createNativeStackNavigator` (`src/navigation/tabs/DashboardStack.tsx:1`, `:29`), while the existing guard only listens to `beforeRemove` (`src/navigation/discard-keep-guard.ts:22`). The installed navigator explicitly warns that this is not fully supported for native dismissal (`node_modules/@react-navigation/native-stack/src/utils/useDismissedRouteError.tsx:21–23`).  
  **Required edit:** In Plan 01 Task 2 and Plan 02 Task 1, specify how removal prevention integrates with native-stack, using its supported prevention mechanism where applicable. In Plan 17, distinguish Android system-navigation gestures from native stack swipe dismissal; mark unavailable paths as unavailable rather than claiming they passed. Pure decision-function tests do not establish native dismissal protection.

- **MEDIUM — Plans 02, 10: Custom Fields’ editor branch still lacks the shared header.**  
  **Evidence:** `src/screens/CustomFieldsScreen.tsx:324–346` returns `FieldDefForm` directly when editing. That component renders its own heading (`src/components/FieldDefForm.tsx:215–217`) and footer Cancel (`:396`). Replacing only the list branch’s Back does not put the house header on the editor branch. A source test finding one `ShellAppBar` in the file would miss this.  
  **Required edit:** In `38.9-10-PLAN.md`, Task 2, explicitly place the shared header above every Custom Fields render branch and connect its Back to the sub-editor guard. Add a render test with an editor open, not merely a file-level header assertion.

- **MEDIUM — Plan 03: Capture clears a typed new-contact name without checking dirty state. [POSSIBLE DECISION REVERSAL: D-14]**  
  **Evidence:** Capture owns `inlineName` (`src/screens/CaptureScreen.tsx:154–155`). Plan 03 Task 2 prescribes closing the inline surface and clearing that name whenever `inlineOpen` is true. D-14 requires prompting when closing an inner editor would lose typed text.  
  **Required edit:** In `38.9-03-PLAN.md`, Task 2, include the inline draft in the Back resolver and prompt before clearing a meaningful name. Test both untouched and typed inline forms. If unconditional discard is intended, it requires an explicit owner ruling.

- **MEDIUM — Plan 03: pending-note dirty tracking needs lifecycle and failure rules.**  
  **Evidence:** `AssistConfirmation` retains local note state (`src/components/AssistConfirmation.tsx:27–28`). Its parent’s action handlers can finish after a failed write while keeping the item pending (`src/components/PendingConfirmationsSheet.tsx:112–128`, `:142–149`). “Remove a uid when its item resolves” is ambiguous: the handler resolving is not proof that the item disappeared or the note was saved.  
  **Required edit:** In `38.9-03-PLAN.md`, Task 1, prune dirty IDs against actual queue membership, preserve dirty state after failed commits, and reset tracking when the sheet’s drafts are actually discarded. Test failure, external queue removal, close/reopen, and successful confirmation.

- **MEDIUM — Plans 01, 05, 06, 09–16: reading instructions contradict the repository review rule.**  
  **Evidence:** Plan 01 Task 3 says to read “only the import line and the Modal element”; Plan 06 Task 2 says to read listed lines. These are explicit alternatives to the full-file/subsystem reading required by `CLAUDE.md` under “Review the code, not the diff.” The missed nested state above demonstrates the practical consequence.  
  **Required edit:** Replace those narrow `read_first` instructions with full-file reading and named shared-state consumers. For label-only DAO edits, explicitly verify the owning query/transaction remains unchanged rather than relying solely on the supplied line reference.

- **MEDIUM — Plan 01: the new `dismissable` override can weaken declarative destructive confirms. [POSSIBLE DECISION REVERSAL: D-06 / ADR-086]**  
  **Evidence:** Today `src/components/ui/ConfirmDialog.tsx:94` unconditionally makes destructive dialogs non-dismissable. The proposed prop defaults to `!destructive` but does not expressly prohibit `destructive:true, dismissable:true`. The imperative store’s protection would not protect the nine declarative consumers.  
  **Required edit:** In `38.9-01-PLAN.md`, Task 2, define effective dismissal as false whenever destructive is true, regardless of the override. Add a component-level test for the conflicting-props case.

## 4. Suggestions

- Add rendered interaction tests for guard wiring, header presence in alternate branches, and dirty Cancel behavior. The proposed pure comparators and source scans cannot detect those failures.
- Give backup blur saves a per-field request/version rule so a completed refresh cannot overwrite newer typing in that same field (`src/screens/BackupSettingsScreen.tsx:91–105`).
- Before execution, reconcile the `110000–150000` token estimates with the actual executor context budget. File count alone does not justify splitting, but the plans currently provide no demonstrated basis for meeting the required ~50% budget. Any split of these already-seen plans requires owner approval.

## 5. Risk Assessment

**HIGH until the guard and render-branch gaps are corrected.** The architecture is broadly sound, but the plans currently promise stronger protection than their prescribed wiring delivers. Several failures would pass the planned helper/source-contract tests and surface only during the final device pass. Correcting these within the existing owning plans would substantially reduce risk without changing the phase’s product decisions.
