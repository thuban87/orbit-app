## Phase Goal

**As a** person tending my relationships, **I want to** correct and enrich a contact's details, **so that** the app reflects reality as it changes.

**This slice (Plan 05):** the edit data layer. TDD, headless. After this plan `updateContactFull` edits metadata atomically (recomputing recency only when the rarely-responds flag flips), and `getContactForEdit` assembles the form's initial values.

<objective>
Add the contact-metadata edit writer (every column except `last_contact`) with the mandatory `rarely_responds`→recompute path, plus the edit-form initial-values assembly. Both reuse the composed-core pattern and reads built in Plan 02.

Purpose: CRUD-03 requires editing every field; the subtle correctness rule is Pitfall 2 — flipping `rarely_responds` changes which interactions count toward recency, so a metadata-only UPDATE that skips the recompute silently corrupts status math. The metadata writer must NOT write `last_contact` itself (single-writer DATA-04); it routes the recompute through the single writer instead.
Output: `updateContactFull` in `contacts-dao.ts`, `getContactForEdit` in `contact-read.ts`, with tests.

**Owner ruling (2026-08-14, CONTEXT Area 3 — supersedes Plan 06's blanket "no last-spoke control"):** the edit form surfaces a last-spoke control for NEVER-CONTACTED contacts (`last_contact IS NULL`), and setting it must write a FIRST interaction through the single writer — the identical mechanism to create's tri-state. To keep that write on the single-writer path, `updateContactFull` (this plan) gains an optional `firstInteraction` that it writes via `insertInteractionCore` + `recomputeLastContactCore` ONLY when the stored `last_contact IS NULL`; for an already-contacted contact it rejects (timeline edits are Phase 6). Plan 06 wires the UI to it.

**Archived-read reconciliation (review divergence — settled here):** codex flagged (HIGH) that `getContactForEdit`/`getContactHeader` read `WHERE id = ?` without `archived_at IS NULL`, so an archived contact is loadable by id; the independent claude review verified this is CORRECT because profile/edit are reached FROM the Archived list (Plan 08) precisely to edit/restore an archived contact, and the only live `FROM contacts` list read (STATUS_SCAN, queries.ts:28) already filters `archived_at IS NULL`. RESOLUTION: do NOT add a blanket `archived_at IS NULL` predicate to the by-id seeks (it would break editing/restoring from the Archived list). Instead these by-id reads are documented as archived-reachable by design, and a must_have asserts no NEW live/list surface this phase reads contacts unfiltered. Recorded so the HIGH-vs-verified-correct divergence is settled, not left open.
</objective>
