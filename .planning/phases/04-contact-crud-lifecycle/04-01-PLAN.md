## Phase Goal

**As a** person tending my relationships, **I want to** add, edit, archive, and permanently delete the people I track — with their links, custom fields, and when we last spoke — **so that** my orbit only holds people I still care about and their details stay right.

> ROADMAP's `**Goal:**` line for Phase 4 is prose, not a user-story; this story is derived faithfully from that goal + the four success criteria (autonomous run — no owner prompt available). It invents no scope.

**This slice (Plan 01):** stand up the real navigation shell the whole phase's screens hang off, and place the two CRUD-05 "separate homes" (Settings → Custom Fields, Settings → Archived contacts). After this plan a user navigates Home ⇄ Settings ⇄ Custom Fields with a native header + back gesture, replacing the Phase-3 hand-rolled toggle.

<objective>
Introduce `@react-navigation/native` + native-stack (owner-locked in CONTEXT "Navigation shell"), migrate the existing `HomeScreen` `useState<Route>` toggle into the navigator, and relocate the Custom-Fields reachability route into a new Settings stack alongside an Archived-contacts entry. This fulfils the Phase-3 forward note ("Phase 4 introduces the real navigation shell") and reverses nothing — the dependency-free routing was an explicitly temporary Phase-1→3 state.

Purpose: every screen built in Plans 03–09 (Create, Profile, Edit, Archived) is a navigator route; without the shell there is nowhere for them to live. CRUD-05 also requires archived contacts to live in a "distinct, low-traffic" Settings home separate from never-contacted.
Output: a native-stack navigator, a Settings screen, a migrated Home shell, and the `danger` theme token — all colours through theme tokens.

**Review note (reviews-mode update):** three review findings land here — (1) the `danger` token (#E5484D) was relocated from Plan 09 to this wave-1 plan so validation/warning UI in Plans 03/04/06 can reference `colors.danger` per UI-SPEC:93; (2) native-stack headers are disabled (`headerShown: false`) so they never double up over each screen's own Back chrome (CustomFieldsScreen renders its own Back — codex duplicate-header flag); (3) acceptance wording says "system Back", not "back gesture", because predictive back is off in app.config.ts:26.

**Settings-rows reconciliation (codex "render three rows" finding — reconciled):** codex read UI-SPEC:192 as requiring three Settings rows (Custom Fields, Reachability, Archived). Verified against the code: `src/screens/` holds exactly two screens (`HomeScreen`, `CustomFieldsScreen`) and HomeScreen's single `useState<Route>` toggle has one destination — CustomFieldsScreen, whose own header comment labels it "REACHABILITY (Plan 08)". CONTEXT.md:96-98 names it "the Custom-Fields reachability route" (singular). UI-SPEC:192's "Custom Fields (from HomeScreen's dependency-free route)" and "the Reachability route (from the Phase-3 HomeScreen useState)" describe the SAME mechanism twice — there is no distinct Reachability screen on disk. Resolution: Settings hosts two real rows (Custom Fields, Archived); a phantom third row navigating nowhere is NOT created (it would be an UNREACHABLE dead route). Recorded so the divergence is settled, not silently dropped.
</objective>
