## Critical Issues

### B-CR-01: DECISION COLLISION, ADR-199. The bulk-frequency sheet's Continue is disabled instead of pressable, and the control test was inverted

**File:**
- `src/components/BulkFrequencySheet.tsx:70-80` (`disabled={!valid}`)
- `src/components/ui/field-error-logic.test.ts:103-121`
- `docs/decisions/ADR-199-…md:22`

**Decision:** ADR-199 (Validation, 38.9 D-19), still live; its partial supersessions ADR-212 and ADR-226 both state "the validation rules survive". It reads: "one primitive, `FieldError` under the field … plus `useFirstErrorReveal` … scrolls and focuses the first blocking problem on Save; **Save stays pressable**. Applied to … **the bulk-frequency sheet**."

**What dies:**
- "Save stays pressable" for the bulk-frequency sheet. Continue is now `disabled={!valid}` and its `onPress` early-returns.
- The `FieldError` primitive on that sheet. FrequencyPicker renders its own `Text`, not `FieldError`.
- The control test that enforced the rule by name. `field-error-logic.test.ts`'s "bulk-frequency sheet validation is inline (D-40, A-13)" block previously asserted `<FieldError … message={frequencyError}>` and `setFrequencyError(`. It now asserts `disabled={!valid}`.

**Sourcing:** The plan line that introduced it, 38.13-10-PLAN.md:42 ("blocks Continue while a custom entry is invalid … (D-39, D-18)"), cites D-39 and D-18. Neither says to block Continue. D-39 only says "uses FrequencyPicker instead of a raw days field", and D-14 carries ADR-199 forward as a standard this phase must use. The constraint therefore has no valid source, and the CONTEXT supersessions table does not list ADR-199.

**Failure scenario:**
1. A TalkBack user opens Change Contact Frequency, taps Custom… and types `0`.
2. The FrequencyPicker shows its caption, but focus stays on the input and Continue becomes a disabled button that announces only "Confirm frequency, disabled".
3. Nothing reveals or announces why. Under ADR-199, Continue would stay pressable, and pressing it would focus and announce the blocking error.

The old sheet did exactly that: `announceForAccessibility("Frequency must be a positive whole number")` plus a `FieldError`.

**Fix:** This needs the owner's ruling, not a silent fix, because it reverses a recorded rule. Proposed fix that preserves the rule:
- keep Continue pressable;
- on an invalid press, force and announce the picker's error through the existing opt-in props;
- restore the contract test to pin "pressable + revealed error".

```tsx
const [forceError, setForceError] = useState(false);
// reset forceError on the open edge alongside valid/intervalDays
<FrequencyPicker key={openCount} value={intervalDays} onChange={setIntervalDays}
  onValidityChange={setValid} errorForced={forceError} … />
<Button testID="bulk-frequency-continue" role="primary" label="Continue"
  accessibilityLabel="Confirm frequency"
  onPress={() => {
    if (!valid) {
      setForceError(true);
      AccessibilityInfo.announceForAccessibility(INVALID_INTERVAL_MESSAGE);
      return;
    }
    onContinue(intervalDays);
  }} />
```

If the owner prefers the disabled button, record it as a new D-NN that partially supersedes ADR-199 for this sheet, and add a row to CONTEXT's supersessions table.

### B-WR-02: D-78's fixed row thresholds do not make the categories fit, including the default 5-row list

**File:**
- `src/components/ui/option-sheet-logic.ts:24-35` (`OPTION_SHEET_COMPACT_MAX_ROWS = 5`, `OPTION_SHEET_DETAIL_MAX_ROWS = 10`)
- `src/components/ui/OptionSheet.tsx:177-195`

**Issue:** D-78: "a short category list opens at the compact bulk size; a long list opens straight away at a taller size **so the categories fit**." The thresholds are fixed row counts and are not derived from the window height.

Arithmetic at default text, from the code's own tokens:
- A row is `minHeight 44` (body lineHeight 24 + 2×SPACING.sm) plus `marginBottom 8`, so 52dp.
- Sheet chrome: handle 12+4+8 = 24, heading lineHeight 25, gap 12, body paddingBottom 24, plus the bottom safe-area inset (about 24 with gesture nav). That is about 109dp.
- Compact with 5 rows: 260 + 109 = about 369dp. The compact cap is 40% of the window: about 356dp on the Pixel 6 Pro (891dp window) and about 323dp on the Pixel 3a (807dp). The fifth row is clipped by 13dp on the 6 Pro and about 46dp on the 3a.
- 4 seeded categories plus Uncategorized is exactly 5 rows, so a fresh install's bulk Set Category sheet opens with its last row cut off.
- Detail with 10 rows: 520 + 109 = about 629dp, against a 60% cap of about 535dp (6 Pro) or 484dp (3a). Lists of 8–10 (3a) or 9–10 (6 Pro) open "taller" and still do not fit, which defeats D-78's stated purpose.

The list scrolls, so nothing is unreachable. The problem is that the promised "opens at a size that fits" does not happen.

**Fix:** Size from the measured window rather than a row count. For example:
- pass `useWindowDimensions().height` into a pure `optionSheetVariantFor(count, windowHeight)` that compares `count * ROW_PITCH + CHROME` against `0.40 * h` and `0.60 * h`;
- or lower the thresholds so they hold on the smallest supported window (compact ≤ 4, detail ≤ 7);
- keep D-78's "decided when it opens".

Verify on both test phones at default and large text in 38.13-11.

### B-WR-03: Horizon birthday avatars render at 50% opacity because the ring opacity is applied to the wrapper that contains the photo

**File:** `src/components/digest/HorizonSection.tsx:88-106` (also pre-existing at `:223-235` for Never Contacted rows)

**Issue:** `ringVisual(null)` returns `{ color: border, opacity: 0.5, width: 2 }` (`contact-card-ring.ts:58-60`). HorizonSection puts that `opacity` on the `View` that wraps `<Avatar>`, so the avatar is drawn at 50% as well. Every other ring consumer keeps the ring as a sibling View so only the ring fades: `ContactCard.tsx:128-139` and `GridCard.tsx:365-382`.

D-48 asked for birthday rows to show the avatar "like every other Digest row". Up Next and Overlooked rows have opacity 1, so their avatars are opaque.

**Failure scenario:** On the galaxy theme's glassy Digest, a birthday contact's photo is half-transparent, and the background art shows through the face. The birthday rows look disabled next to the opaque Up Next and Overlooked avatars just above.

**Fix:** Render the ring as an absolutely positioned sibling, as GridCard does:

```tsx
<View style={styles.avatarSlot}>
  <Avatar photo={birthday.contact.photo} name={birthday.name} contactId={birthday.id} size={40} />
  <View pointerEvents="none" style={[StyleSheet.absoluteFill, styles.ringOverlay,
    { borderColor: neutralRing.color, borderWidth: neutralRing.width, opacity: neutralRing.opacity }]} />
</View>
```

Apply the same fix in `CompactContactRow` for Never Contacted rows.

### B-WR-04: The bulk Set Category sheet changes size while it animates closed

**File:**
- `src/screens/HomeScreen.tsx:2742-2750` (`categories={categoryPicker?.categories ?? []}`)
- `src/components/category/CategoryChoiceSheet.tsx:121-124`

**Issue:** On pick or dismiss, HomeScreen nulls `categoryPicker` before the Sheet's close animation ends. `categories` becomes `[]`, so `model.rows` is just "Uncategorized", so `optionSheetVariantFor(1)` returns compact. A sheet that opened at detail (6–10 rows) or expanded (11+, the unsized block) flips to the compact sized block mid-fade, with one row.

Before this phase only the rows vanished during the fade; now the whole sheet visibly collapses. Elsewhere in the same file this exact class of glitch was fixed with `useRetainedWhileClosing` (snooze sheets, 38.11 review IN-06, `HomeScreen.tsx:795-799`).

**Failure scenario:** A user with 8 categories selects people, opens Set category (detail, about 60%) and picks one. As it fades, the sheet snaps down to a short compact sheet showing only "Uncategorized", highlighted because `selectedId={null}`.

**Fix:** Retain the picker's categories while closing:

```tsx
const categoryPickerShown = useRetainedWhileClosing(categoryPicker);
<CategoryChoiceSheet visible={categoryPicker !== null}
  categories={categoryPickerShown?.categories ?? []} … />
```

### B-WR-05: Returning from a D-46 Profile or event tap collapses the open day detail to a spinner and refills it

**File:**
- `src/components/digest/YourWeekSection.tsx:253-258`
- `src/components/digest/YourWeekSection.tsx:127-131`
- `src/components/digest/your-week-section-logic.ts:240-246`

**Issue:** D-46 makes "open day, tap a row, Profile, Back" the primary day-detail flow. On Back:
1. Digest's focus effect requests a refresh.
2. `onAccepted` bumps `refreshSignal`.
3. The effect retains the selected day and calls `loadDay`.
4. `startDayRead` ignores the previous state and returns `{status:"loading"}`.

The loaded rows are therefore replaced by a 36dp `ActivityIndicator` until the read settles. Your Week is the last section of the Digest ScrollView, so a user who scrolled down to the day detail has the content shrink by (rows − spinner) height. The ScrollView clamps the scroll offset, and when the rows return the user is no longer where they were.

This is the same "page jump" class D-49 fixed for the period switch, now on every round-trip D-46 introduced.

**Failure scenario:**
1. On a day with 6 interactions, the user scrolls to the bottom and taps the 5th row.
2. Profile opens; the user presses Back.
3. The detail flashes to a spinner, the page jumps up by about 300dp, then the rows reappear above the fold.

Needs a device look in 38.13-11 to confirm the magnitude.

**Fix:** Make a refresh-retained re-read keep the loaded rows visible: a refreshing state, or start the token without discarding rows.

```ts
export function startDayRead(state, date, token) {
  if (state.status === "loaded" && state.date === date)
    return { status: "loaded", date, rows: state.rows, token } as const; // settle/fail check token
  return { status: "loading", date, token };
}
```

Adjust `settleDayRead` / `failDayRead` to accept a token-bearing loaded state. A failed refresh should keep the rows, matching B-WR-06's posture for the week body.

### B-IN-05: The contact picker's resting height only ever grows, and the FAB's picker never unmounts

**File:** `src/components/ContactPicker.tsx:509-533`

**Issue:** `restingFrameHeight` is a ref that keeps the max height ever seen. UniversalFab's picker lives for the whole app session. If the window shrinks (the Razr's cover display vs the inner display, or split-screen), `resized = resting − frameHeight` is large even with no IME resize. The lift is then under-computed (often to 0) and the sheet sits behind the keyboard. The pattern is shared with `Sheet`, so it is not new in kind, but the FAB picker's lifetime makes it more likely here.

**Fix:** Reset `restingFrameHeight` when the modal opens (on the `visible` false-to-true edge), or when `useWindowDimensions().height` changes.
