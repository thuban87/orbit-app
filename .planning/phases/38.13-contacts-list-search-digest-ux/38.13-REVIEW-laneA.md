## Warnings

### A-WR-01: The fade start is applied after paint, so new rows can flash at full opacity, then blink out and fade in (List and Card)

**File:** `src/screens/HomeScreen.tsx:985-1022` (with `:1105-1107` and `src/screens/dashboard-refresh-scheduler.ts:214-215`)
**Issue:** D-44 moved the fade start from publish time to "after the rows commit". The publish sets `publishedFadeStart` and bumps `resultGeneration` in the same batch as `setRows`. The start value reaches `resultProgress` only inside a plain `useEffect`. A read publishes from a promise continuation, which is a default-lane update, so React flushes passive effects asynchronously after the commit. The new rows are mounted and can be painted at the previous opacity (1) before the effect runs `withSequence(withTiming(0, {duration: 0}), …)`. Reanimated then applies that start value on a later UI frame. Nothing in the code orders "start value applied" before "new rows painted".
**Failure scenario:** On the 1,000-contact set, tap Population → Favorites in List view (focused, app active, reduced motion off). The old list stays visible through the commit (the A-01 fix works). Then the Favorites rows appear at full opacity for at least a frame, drop to 0, and fade in over `MOTION.fast`. This flicker happens on every population, filter, sort and search change in both views. 38.13-08 SUMMARY deferred item 2 calls it "possible (RESEARCH A5)". It is structurally unprevented, so it should be treated as expected until a release build on the phone shows otherwise.
**Fix:** Apply the start before paint. The fade itself (0 → 1, same duration and easing) does not change, so this is not a D-55 fade change:
```tsx
// HomeScreen.tsx: same body, layout phase instead of passive phase
useLayoutEffect(() => {
  if (resultGeneration === 0) return;
  // ...unchanged generation / canAnimate logic...
}, [appActive, isFocused, publishedFadeStart, reducedMotion, resultGeneration, resultProgress]);
```
If the device pass still shows a frame of flash with the layout effect, raise it with the owner as the D-55 fade question SUMMARY 08 anticipated. Do not change the start value without asking.

### A-WR-02: Reset Contacts View is still reachable while selecting, so it changes which part of the frozen universe is visible while the hidden people stay selected

**File:** `src/screens/HomeScreen.tsx:2082-2101` (overflow built with no selection state), `:686-688` (`cardRows = rows ∩ frozenUniverse`), `:623-645` (`resetDashboard` clears the search too); `src/screens/dashboard-overflow-actions.ts:22-53`
**Issue:** D-76 hides the Population/Filters/Sort row and the search row while selecting, "Enforces ADR-102's frozen universe". The app bar's ⋯ still renders during selection with **Reset Contacts View** and **Select Contacts**. Reset rewrites populations, filters and sort, and it clears the session search with the search row hidden. The Card grid renders `rows.filter(frozenIds.has)`, so every selected person outside the new Active list disappears from the grid. They stay in `selectedIds` and `frozenUniverse`, the bar still counts them, and every bulk action still writes to them.
**Failure scenario:** On All Contacts, search "smith" in Card view; the results include two Unbound people (D-59). Long-press → Select, then Select All, so 6 are selected. Open ⋯ → Reset Contacts View. The search clears and the population returns to Active, so the Unbound and never-contacted Smiths vanish from the grid while the bar still reads "6 selected". More… → Move to Bin then bins 6 people, of whom only 3 are visible. Bulk Quick Log logs 6. "Deselect all" / "Select All" also act on people the user cannot see.
**Fix:** Close the remaining path to a query change during selection. This enforces D-76 and ADR-102 rather than reversing them, so it is a planner call:
```ts
// dashboard-overflow-actions.ts
interface BuildDashboardOverflowActionsInput { /* … */ selectionMode: boolean; }
// …omit (or disable) "Select Contacts" and "Reset Contacts View" when selectionMode
```
Pass `selectionMode` from HomeScreen. If keeping Reset reachable is preferred, Reset must run `exitBulkSelection()` first.

### A-IN-01: During a bar action's database read, taps on other bar buttons are dropped silently and show no busy state

**File:** `src/screens/HomeScreen.tsx:1514-1559`, `:1563-1611`, `:1617-1650`; `src/logic/dashboard-bulk-action-session.ts:49-63`
**Issue:** Favorite, Remove from Favorites and Snooze take a claim (`tryAcquire`) and then await `readSelectionLifecycle` / `readCurrentlySnoozedIds` before they `consume`. While that claim is held but not consumed, `bulkActionPending` stays false (correct for D-41), so every bar button looks enabled. Any tap on another button calls `tryAcquire`, gets `null` and returns with no feedback.
**Failure scenario:** Tap Favorite and then Quick Log at once. The Quick Log tap is lost and nothing tells the user. The window is one SQLite read, so this is rare, but it is the same lost-tap class D-27 removed from the control row.
**Fix:** While a claim is held but not consumed, either set `aria-busy`/disabled on the bar (with a `heldPending` flag that does not show "Working…"), or queue the second tap.

### A-IN-02: A failed combined Populations+Filters write can be rolled back for only one of the two axes

**File:** `src/stores/dashboard-query-store.ts:155-168`
**Issue:** Rollback is per axis. When a `setPopulationsAndFilters` write fails while a newer filters-only write is pending, populations are restored and filters are not. The final state keeps the newer filters with the old population, a pair the user never chose. The store still matches the database.
**Failure scenario:** Tap "N Never Contacted →" on "Everyone's tucked away", then a Filters chip, before the first write lands. If the first write fails, the user sees the old population with the new chip and the "Couldn't show Never Contacted" snackbar. Local SQLite writes rarely fail, so this is low-likelihood.
**Fix:** For a multi-axis write, restore all of its axes when any one is still at this `seq`, or document that a combined drill write is best-effort per axis.

### A-IN-03: The D-50 focus guard reads a ref that updates only on render

**File:** `src/components/control-surface/DashboardControlRow.tsx:96-101`, `src/components/control-surface/panel-open-guard.ts:9-13`
**Issue:** `isFocusedRef.current` is written during render from `useIsFocused()`. If the `measureInWindow` callback arrives after the blur event but before the re-render triggered by that blur, the guard still sees `true` and opens the panel on the hidden screen. That is the exact D-50 case, though it needs a navigation inside about one frame of a trigger tap.
**Fix:** Read live navigation state in the callback: `const navigation = useNavigation(); const stillFocused = useCallback(() => navigation.isFocused(), [navigation]);`.

### A-IN-04: D-75 also amends ADR-102's "frequency-only Sensitive Operations", but the supersessions table does not record it (KB extraction)

**File:** `src/components/BulkActionSurface.tsx:166-183`; `38.13-CONTEXT.md` `<supersessions>`

The owner decided this, so it is not a collision. The supersessions table, though, lists only D-72's two ADR-102 parts (bottom bar; replacing the control area).
**Fix:** At KB extraction, add the ADR-102 partial for D-75: the Careful group is Change Contact Frequency plus Move to Bin; Archive is no longer a routine bar action.

### A-IN-05: HomeScreen's read body has an unreachable search branch, and its header comment is stale

**File:** `src/screens/HomeScreen.tsx:1133-1154` (also `:3-4`, `:21`, import `:129`)
**Issue:** Inside the `!isSearch` arm, `term !== "" ? listDashboardSearch(…) : listDashboardPopulation(…)` always takes `listDashboardPopulation`, because `isSearch === (term !== "")`. The branch was already there at `232ef7f9`, but this phase rewrote the read body around it. The file header still says Home renders `listDashboardSearch` "when a term is present"; the read actually uses `composeDashboardSearch`.
**Fix:** Collapse the branch to `listDashboardPopulation(exec, query, now)`, drop the `listDashboardSearch` import, and correct the header comment.

### A-IN-06: A logic module imports from the components layer

**File:** `src/logic/dashboard-empty-copy.ts:13-16`
**Issue:** `src/logic/` is meant to be React-free and framework-free. `dashboard-empty-copy.ts` imports `AXIS_DEFAULT_LABELS` and `POPULATION_LABELS` from `@/components/control-surface/control-labels`, which inverts the layering. It works today because `control-labels.ts` has no React import, but the next React-bearing import there would pull UI into node-tested logic.
