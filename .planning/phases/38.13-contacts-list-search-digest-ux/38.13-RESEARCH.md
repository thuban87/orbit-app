## Summary

The List-view problem has a concrete, code-level mechanism that the measurements can confirm or reject quickly. Every List row mounts a `ReanimatedSwipeable` (RNGH 2.32.0), which allocates 9 shared values, 3 animated refs, 3 animated styles and **two `GestureDetector`s**. Orbit adds one more shared value, one `useAnimatedReaction` (with its own shared value), and in see-through themes one more animated style. In Reanimated 4.5.1, every mapper start (`startMapper`) and every shared-value unmount (`cancelAnimation`) is a `scheduleOnUI` job from the JS thread. That matches the debug OOM stack (`worklets::AsyncQueueUI::push ← scheduleOnUI on mqt_v_js`). Separately, `GestureDetector` calls native `updateGestureHandler` for each detector on **every re-render** (`useEffect(..., [props])`). With an inline `renderItem` and no `React.memo`, every HomeScreen render re-renders every mounted row, so one Population tap means two native calls per mounted row. Card view shares the same unmemoised fan-out but has no gestures, and it measured 0.20 s against List's 1.98 s. That points at the per-row gesture machinery multiplied by the re-render, not at fan-out alone. [VERIFIED: node_modules source read this session; INFERRED for the causal link]

The rest of the phase is mostly small, well-located changes. Three seams need care. (1) **D-59** has one seam, `searchScope()` in `dashboard-read.ts`, which has exactly one consumer (HomeScreen via `composeDashboardSearch`). But it opens Unbound rows to row actions whose DAOs do **not** guard Unbound (favourite and snooze writers guard only the Bin). It also lets the shared needs-attention filter admit Unbound people. (2) **D-61** can be made exact by deriving Overlooked from the Up Next candidate read, which already uses the drill's predicate. (3) **D-72** puts a bar above the tab bar, where the root snackbar (Undo for bulk results) currently sits. The snackbar layout must learn about the bar, or bulk Undo pills will cover it.

**Primary recommendation:** Plan the phase as about 8 plans in this order: (1) device measurement + owner checkpoint; (2) List-row host rebuild (memoised, extracted rows, windowing, D-25/D-26/D-44 fade); (3) control surface + query store (D-23/D-58/D-27/D-35/D-36/D-50); (4) HomeScreen session + empty states (D-24/D-29/D-31/D-28/D-30/D-65/D-32/D-33/D-52); (5) search (D-59/D-60/D-37/D-51/D-53/D-44 search state); (6) selection bar (D-69/D-72/D-74/D-75/D-76/D-40/D-41 + snackbar/FAB); (7) bulk sheets + ContactPicker (D-39/D-71/D-70/D-43); (8) Digest (D-61/D-63/D-45–D-49), then the final device plan. No migration. No new packages.

### Pattern 5: D-44 — fade applied at commit, not at publish

That shared-value write reaches the UI thread **before** React commits the heavy List tree. ## Common Pitfalls

### Pitfall 1: Unbound people reaching writers that never expected them (D-59)
**What goes wrong:** a star tap or bulk Favorite/Snooze writes a rank or snooze to an Unbound person. The DAOs allow it (Bin guard only).
**How to avoid:** ADR-233 rules on the row and card menu; exclude Unbound from the selection universe; the needs-attention predicate gets the cadence precondition.
**Warning signs:** a favourite count that differs between Contacts and the widget; an Unbound person shown as snoozed.

### Pitfall 2: Search-scope parameter misalignment
**What goes wrong:** the D-59 branch is extended to a population with params (birthdays), and the `?` params shift by N.
**How to avoid:** limit the exception to exactly `["all-contacts"]`, and add a test asserting `composition.where.params.length === 0` for it.

### Pitfall 3: Snackbar covering the new bottom bar
**What goes wrong:** "Logged 3 interactions · Undo" sits on top of the Quick Log/Snooze buttons. Taps go to the wrong control, or the 6 s Undo is unreachable.
**How to avoid:** a shell obstacle for the bar, fed into `snackbarLayout`; check on device.

### Pitfall 4: Removing `?? 1` breaks name-only rows (D-44)
**What goes wrong:** `searchResult === null` is **also** the legitimate "name-only match" case (`HomeScreen.tsx:2024-2028` passes `?? null`; `composeDashboardSearch` returns `match: null` for name-LIKE-only rows, `dashboard-search-read.ts:55-59`). Today those render "1 match".
**How to avoid:** track the term the published results belong to (add it to the read outcome). Show a searching state only when `publishedTerm !== currentTerm`. Give name-only rows a plain label (D-37), e.g. "Name".

### Pitfall 5: D-37 snippet equals the name — now confirmed
The corpus name entry is `{ source: "name", part: "identity", label: "Name", text: contact.name }` (`src/db/knowledge-search-read.ts:370`). A name hit's snippet is therefore the contact's name, which the row already shows on line 1. Skip the snippet when it equals the name, and use the descriptor's `fieldLabel` ("Name", "Phone", "Email", "Category") in place of "Identity" (`list-row-content.ts:51`). This resolves the CONTEXT's "LIKELY". [VERIFIED]

### Pitfall 6: Optimistic state vs out-of-band writers (D-27)
Category deletion writes `dashboard_filters` directly (`categories-dao.ts:428-432`). An in-flight optimistic filter write queued earlier could re-persist a deleted category id. The existing focus reconcile (`DashboardControlRow.tsx:73-104`) repairs it on next focus. Keep that reconcile running through the same queue.

### Pitfall 7: Moving swipe code breaks the D-48 source contract
`list-row-swipe-backing.test.ts:155-170` slices `HomeScreen.tsx` by function anchors. Moving the row host to a new file fails that test even with the invariant intact. Update its anchors in the same plan (see the orphaned-test memory note: grep all consumers, including tests, before reshaping).

### Pitfall 8: Perf evidence on the wrong thread or build
`gfxinfo`/`anr_check.py` see only the UI/RenderThread. Tap latency lives on `mqt_v_js` (D-13; workpaper M6). Debug timings are screening only. Release is not `run-as`-debuggable (runbook §3.1), so seed data on debug and measure on release.

### Pitfall 9: Measurement manifest leaking into a real build
A hand-edited `profileable` in the normal droid tree survives a later "tar overwrite + assemble" (runbook §3.8). Use a separate droid directory (Pattern 2).

### Pitfall 10: Overlooked double dedupe
`dedupOverlooked` runs both in `DigestLoadedBody` (`DigestScreen.tsx:307`) and inside `HorizonSection` (`:51`). It is idempotent today. If Overlooked becomes `candidates.slice(3)`, keep exactly one source of truth to avoid confusion.
