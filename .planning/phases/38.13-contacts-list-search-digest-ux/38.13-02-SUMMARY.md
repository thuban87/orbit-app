# Phase 38.13 Plan 02: Contacts control row (Population, Filters, Sort) Summary

**The Population panel gets an Active Contacts row that is selected by default, and All Contacts and Active Contacts are now exclusive. Population, Filter and Sort taps are no longer dropped: the store shows each choice at once and saves the writes one after another, in order. When a save fails, that choice goes back to the last value that was really saved. The Sort chip now reads "Default (X)", the Filters chip reads "None" when nothing is set, and a panel can no longer open after the screen has lost focus.**

## Accomplishments

- **D-23 / D-58:** `nextPopulations(current, tapped)` is a pure function that owns the exclusivity rules. `"active"` exists only as a panel key: the function never returns it, and `parseDashboardPopulations` still rejects it. The stored format is unchanged, so there is no migration and no backup or validator change. A stored mix such as `["all-contacts","favourites"]` is cleaned up on the next tap. `samePopulations` turns a re-tap of the selected row into a no-op (no write, no generation bump, no reload; review R1-16).
- **D-27:** `setPopulations`, `setFilters`, `setPopulationsAndFilters`, `setSort` and `resetDashboardView` now all use one `queueWrite` shape:
  - The store `set()`s the new value at once and bumps `generation + 1`.
  - The `updateAppSettings` call joins a module-level promise chain, so writes land in strict issue order.
  - The returned promise settles when that write does. The Digest drill and Home's Reset still await it.
  - Each axis tracks its last committed value and the sequence number of its latest issued write.
  - When a write fails, an axis is restored to its committed value only if no newer write for that axis is still pending, and then the error is rethrown.
  - `pendingAxes` counts the writes still pending on each axis.
- **Hydrate (review R2-05):** hydrate counts each axis's successful writes when its read begins. When the read resolves, every axis with no successful write since then takes the snapshot as its committed value, even when the publish is dropped. A failing first tap therefore restores a value that is really stored.
- **DashboardControlRow:**
  - The four `if (pending) return` guards and the `disabled={pending}` props are gone.
  - The "Couldn't save …" text still shows when a write is rejected.
  - A write still pending after `PENDING_INDICATOR_DELAY_MS` (250, at the top of the file) shows a small `ActivityIndicator` in the `accentText` colour. It sits absolutely positioned inside its trigger and sets `accessibilityState.busy`.
  - The focus-time category reconcile still calls `setFilters`, which now goes through the queue (Pitfall 6).
- **D-35 / D-36 / D-50:**
  - `defaultSortLabel(populations)` labels the Sort panel's Default option and the Sort chip.
  - `AXIS_DEFAULT_LABELS.filters` is now `"None"`.
  - `openIfStillFocused(stillFocused, open)` wraps all three `measureInWindow` callbacks. It reads an `isFocusedRef` fed by `useIsFocused()`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Hydrate publish is decided per axis, not by the all-or-nothing generation guard**
- **Found during:** Task 2
- **Issue:** The old guard dropped the whole snapshot whenever any write bumped `generation`. Two things went wrong with that:
  - A Sort tap during launch hydration left Population and Filters at their initial defaults, even though their stored values differed.
  - A write issued *before* hydrate began and still pending when it resolved could be overwritten by a snapshot older than the optimistic value.
- **Fix:** Hydrate now publishes an axis only when that axis has no write pending and no successful write since the read began. The generation guard still decides `viewMode`, which keeps its old behaviour. Every planned hydrate behaviour still holds, and the existing late-hydrate test stays green.
- **Files modified:** src/stores/dashboard-query-store.ts
- **Verification:** dashboard-query-store.test.ts, 19/19
- **Commit:** c77f6e89

**2. [Process] Tracer feedback gate run in its autonomous form**
- **Found during:** after Task 1
- **Issue:** `workflow.auto_advance` is false, so the executor protocol's interactive form would stop after the tracer for a human check.
- **Fix:** I ran the gate in its autonomous form instead: I re-ran the tracer's `<verify>` on the committed state, it passed, and I went on to the expansion tasks. My reasons: the plan is `autonomous: true` and has no device work, and owner memories "execution autonomy, only serious stops" and "lean execution" (no per-plan device checks) apply.

**Total deviations:** 1 auto-fixed bug, 1 process adaptation. **Impact:** the hydrate change only narrows when a stale snapshot can overwrite state. It does not reverse any recorded decision.

## Deferred / out of scope (for the orchestrator to bring to the owner)

1. **The committed filters value can go stale after a category deletion.** `categories-dao.ts:428-432` writes `dashboard_filters` without going through the store, so `committed.filters` can still hold the deleted category id. If a later filter write fails with nothing newer pending, the store restores that id until the next focus reconcile removes it. That reconcile runs through the same queue. This is low impact and self-heals on focus. Recommendation: accept, or have the category-delete path call a store refresh in a later plan.
2. **A superseded failure still shows the error text.** When write B fails while a newer write C is pending, "Couldn't save …" appears even if C then succeeds. The text clears on the next tap, which matches the old behaviour. Recommendation: accept; the device pass can judge it.
3. **The `disabled` props are now unused.** The `disabled?` prop on PopulationPanelContent, FilterPanelContent and SortPanelContent has no caller passing it any more. I left it in place: it is harmless and outside this plan's file list for FilterPanelContent. This is a cleanup nit.
4. **Device check for the spinner (plan 11).** The spinner is absolutely positioned at top-right inside each trigger. On a narrow trigger it may overlap the end of a truncated summary while a slow write is pending. This needs a look in the phase's device pass (38.13-11).
