## Warnings

### A-WR-01: The fade start is applied after paint, so new rows can flash at full opacity, then blink out and fade in (List and Card)

**File:** `src/screens/HomeScreen.tsx:985-1022` (with `:1105-1107` and `src/screens/dashboard-refresh-scheduler.ts:214-215`)
**Issue:** D-44 moved the fade start from publish time to "after the rows commit". The publish sets `publishedFadeStart` and bumps `resultGeneration` in the same batch as `setRows`. The start value reaches `resultProgress` only inside a plain `useEffect`. A read publishes from a promise continuation, which is a default-lane update, so React flushes passive effects asynchronously after the commit. The new rows are mounted and can be painted at the previous opacity (1) before the effect runs `withSequence(withTiming(0, {duration: 0}), …)`. Reanimated then applies that start value on a later UI frame. Nothing in the code orders "start value applied" before "new rows painted".
**Failure scenario:** On the 1,000-contact set, tap Population → Favorites in List view (focused, app active, reduced motion off). The old list stays visible through the commit (the A-01 fix works). Then the Favorites rows appear at full opacity for at least a frame, drop to 0, and fade in over `MOTION.fast`. This flicker happens on every population, filter, sort and search change in both views. 38.13-08 SUMMARY deferred item 2 calls it "possible (RESEARCH A5)". It is structurally unprevented, so it should be treated as expected until a release build on the phone shows otherwise.
**Fix:** Apply the start before paint. The fade itself (0 → 1, same duration and easing) does not change, so this is not a D-55 fade change:
```tsx
// HomeScreen.tsx: same body, layout phase instead of passive phase
useLayoutEffect(() => {
  if (resultGeneration === 0) return;
  // ...unchanged generation / canAnimate logic...
}, [appActive, isFocused, publishedFadeStart, reducedMotion, resultGeneration, resultProgress]);
```
If the device pass still shows a frame of flash with the layout effect, raise it with the owner as the D-55 fade question SUMMARY 08 anticipated. Do not change the start value without asking.

**File:** `src/screens/HomeScreen.tsx:2082-2101` (overflow built with no selection state), `:686-688` (`cardRows = rows ∩ frozenUniverse`), `:623-645` (`resetDashboard` clears the search too); `src/screens/dashboard-overflow-actions.ts:22-53`

### B-CR-01: DECISION COLLISION, ADR-199. The bulk-frequency sheet's Continue is disabled instead of pressable, and the control test was inverted

**File:**

**Decision:** ADR-199 (Validation, 38.9 D-19), still live; its partial supersessions ADR-212 and ADR-226 both state "the validation rules survive". It reads: "one primitive, `FieldError` under the field … plus `useFirstErrorReveal` … scrolls and focuses the first blocking problem on Save; **Save stays pressable**. 2. The FrequencyPicker shows its caption, but focus stays on the input and Continue becomes a disabled button that announces only "Confirm frequency, disabled".
3. Nothing reveals or announces why. Under ADR-199, Continue would stay pressable, and pressing it would focus and announce the blocking error.

- on an invalid press, force and announce the picker's error through the existing opt-in props;

### B-WR-02: D-78's fixed row thresholds do not make the categories fit, including the default 5-row list

**File:**
- `src/components/ui/option-sheet-logic.ts:24-35` (`OPTION_SHEET_COMPACT_MAX_ROWS = 5`, `OPTION_SHEET_DETAIL_MAX_ROWS = 10`)
- `src/components/ui/OptionSheet.tsx:177-195`

**Issue:** D-78: "a short category list opens at the compact bulk size; a long list opens straight away at a taller size **so the categories fit**." The thresholds are fixed row counts and are not derived from the window height.

Arithmetic at default text, from the code's own tokens:
- A row is `minHeight 44` (body lineHeight 24 + 2×SPACING.sm) plus `marginBottom 8`, so 52dp.
- Sheet chrome: handle 12+4+8 = 24, heading lineHeight 25, gap 12, body paddingBottom 24, plus the bottom safe-area inset (about 24 with gesture nav). That is about 109dp.
- Compact with 5 rows: 260 + 109 = about 369dp. The compact cap is 40% of the window: about 356dp on the Pixel 6 Pro (891dp window) and about 323dp on the Pixel 3a (807dp). The fifth row is clipped by 13dp on the 6 Pro and about 46dp on the 3a.
- 4 seeded categories plus Uncategorized is exactly 5 rows, so a fresh install's bulk Set Category sheet opens with its last row cut off.
- Detail with 10 rows: 520 + 109 = about 629dp, against a 60% cap of about 535dp (6 Pro) or 484dp (3a). Lists of 8–10 (3a) or 9–10 (6 Pro) open "taller" and still do not fit, which defeats D-78's stated purpose.

The list scrolls, so nothing is unreachable. The problem is that the promised "opens at a size that fits" does not happen.

**Fix:** Size from the measured window rather than a row count. For example:
- pass `useWindowDimensions().height` into a pure `optionSheetVariantFor(count, windowHeight)` that compares `count * ROW_PITCH + CHROME` against `0.40 * h` and `0.60 * h`;
- or lower the thresholds so they hold on the smallest supported window (compact ≤ 4, detail ≤ 7);
- keep D-78's "decided when it opens".

Verify on both test phones at default and large text in 38.13-11.

2. `onAccepted` bumps `refreshSignal`.
3. The effect retains the selected day and calls `loadDay`.
4. `startDayRead` ignores the previous state and returns `{status:"loading"}`.

The loaded rows are therefore replaced by a 36dp `ActivityIndicator` until the read settles. Your Week is the last section of the Digest ScrollView, so a user who scrolled down to the day detail has the content shrink by (rows − spinner) height. The ScrollView clamps the scroll offset, and when the rows return the user is no longer where they were.

This is the same "page jump" class D-49 fixed for the period switch, now on every round-trip D-46 introduced.

**Failure scenario:**
1. On a day with 6 interactions, the user scrolls to the bottom and taps the 5th row.
2. Profile opens; the user presses Back.
3. The detail flashes to a spinner, the page jumps up by about 300dp, then the rows reappear above the fold.

Needs a device look in 38.13-11 to confirm the magnitude.

**Fix:** Make a refresh-retained re-read keep the loaded rows visible: a refreshing state, or start the token without discarding rows.

```ts
export function startDayRead(state, date, token) {
  if (state.status === "loaded" && state.date === date)
    return { status: "loaded", date, rows: state.rows, token } as const; // settle/fail check token
  return { status: "loading", date, token };
}
```

Adjust `settleDayRead` / `failDayRead` to accept a token-bearing loaded state. A failed refresh should keep the rows, matching B-WR-06's posture for the week body.
