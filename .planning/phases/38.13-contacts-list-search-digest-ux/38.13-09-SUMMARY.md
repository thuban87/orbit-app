# Phase 38.13 Plan 09: Card-view selection bar (M3b), More… sheet, applicability and Unbound skip, Working… after confirm, Undo above the bar Summary

**Card-view selection now uses the owner's M3b bar at the bottom of Contacts, directly above the tab bar: [✕] "N selected" … Select All, then Quick Log, Snooze, Favorite and More…. The More… sheet holds Log Interaction, Remove from Favorites and Set Category, then a separate "Careful actions" group (Change Contact Frequency, Move to Bin). While selecting, the Population/Filters/Sort row, the search row and the + are hidden. Select All toggles to "Deselect all", and each action is enabled only when it applies. Unbound people can be selected, but Favorite, Remove from Favorites and Snooze skip them, based on a database read at action time. "Working…" appears only after an action is confirmed and writing. An Undo pill moves up once to sit above the bar and never drops back.**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `bulkWriteIds` also drops existing favourites from Favorite and non-favourites from Remove from Favorites**
- **Found during:** Task 2
- **Issue:** The plan's rule was "returns only ids whose entry is present and Bound" for all three restricted actions. `setFavouriteRankCore` (`src/db/favourites-dao.ts:43-49`) sets `favourite_rank = MAX + 1` unconditionally. Under that rule, bulk Favorite on a selection that includes an existing favourite would move that favourite to the end of the owner's Favorites order. The outcome would also say "Added N" for people who were already favourites. Remove from Favorites would likewise count non-favourites as "Removed".
- **Fix:** add-favorites writes Bound non-favourites. remove-favorites writes Bound favourites, which matches D-75's "removes every selected favourite". snooze writes Bound people. Ids missing from the map are never written, and every other action passes its ids through unchanged. This is consistent with the plan's applicability rules: Favorite is enabled only when a Bound non-favourite is selected, and Remove only when a Bound favourite is.
- **Files modified:** src/logic/dashboard-selection-applicability.ts (+ test)
- **Commit:** 4508664f

**2. [Process] Tracer feedback gate run in its autonomous form**
- `workflow.auto_advance` is false, but the plan is `autonomous: true` with no device work. The orchestrator also directed that the tracer gate run with no human stop. I re-ran Task 1's verify on the committed state and it passed.

**Total deviations:** 1 auto-fixed (Rule 1) and 1 process note. **Impact:** the favourite counts are exact, and the Favorites order no longer reshuffles on bulk add. No recorded decision was changed.

## Behaviour change worth knowing

- **Bulk snooze sheet (D-77, ADR-233):** the sheet now opens only over the selected people the database classifies as Bound. Its title count, its writes and its Unsnooze row all use those ids. A snoozed Unbound person who is selected can therefore no longer be unsnoozed from the bulk sheet. Before this plan, 38.11 review IN-01 counted them. This plan's text ("filter before setSnoozePicker, so the shared sheet, its write and its count see only Bound ids") and ADR-233 ("no Snooze for Unbound people") decide this case. The `readCurrentlySnoozedIds` comment now says so (`2068119f`). The reader itself is unchanged.
- **The bar during a waiting sheet or dialog:** buttons are no longer greyed while a confirm dialog or sheet waits, because pending is now reported only on consume. A tap there is still a no-op, because the held claim blocks `tryAcquire`. Sheets and dialogs are modal overlays anyway.

- **Grid bottom clearance under the bar:** I kept today's `bottomClearance` for the Card grid, as the plan says (Claude's discretion per CONTEXT). The 38.13-11 device pass should confirm that the last card row can scroll fully above the bar.

If the bar ever moves off the tab bar (for example, an in-flow banner below it), the lift would need `windowHeight - rect.y` instead. This plan does not need that.
