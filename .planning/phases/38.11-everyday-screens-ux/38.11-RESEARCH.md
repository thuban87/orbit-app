## Summary

The dossier is accurate for the eight items. Reading the code turned up six things the planner needs that the dossier does not say:

1. **D-66 breaks a Profile route if done naively.** The Profile opens the `Memory` route for the "add memory" heading actions (`ContactProfileScreen.tsx:357-358`). But `Memory` is registered in every stack only because it is in `FAB_ROUTES`; it is **not** in `PROFILE_REACHABLE_ROUTES` (`shell-contract.ts:66-84`). If you take `Memory` out of `FAB_ROUTES` and its registrations, the Profile's add-memory buttons silently do nothing in release (RG-021). Move `"Memory"` into `PROFILE_REACHABLE_ROUTES` and keep all five registrations.
2. **D-48 Birthday and Social battery are not written by create today.** `createContactFullCore` INSERTs only `uid, name, category_id, interval_days, tracking_enabled, rarely_responds, created_at, modified_at` (`contacts-dao.ts:290-305`). The header comment says birthday and social battery are "INTENTIONALLY create-excluded" (`:39-41`). D-48 needs two new optional input fields and two new INSERT columns, plus a post-create `reconcileSchedule` so a new birthday gets its notification before the next launch.
3. **D-77 has two working precedents for "stage, commit, then promote"**: import (`import-staging/`) and reconciliation (`reconcile-staging/`). Both use a durable document-dir staging namespace, an allowlist regex, list/delete helpers and a launch orphan sweep. Copy that shape for a create namespace. The pipeline cannot store a contact photo before the contact exists, because the canonical path is derived from the contact id: `avatars/contact-<id>.jpg`.
4. **D-62 / D-41 / D-45 each trip a pinned count in a contract test.** The placeholder floor is exactly met: 62 sites against `toBeGreaterThanOrEqual(62)`, and `UpdateContactScreen.tsx` holds one. `no-native-alert-contract.test.ts` pins "exactly one `Alert.alert` in HomeScreen: the snooze". Each plan has to update the pin it breaks.
5. **D-26:** React Navigation 7's `navigate` no longer goes back to a screen already in the stack (CITED), which explains defect #2. `popTo("Profile")` without `getId` matches the **nearest Profile of any contact** (VERIFIED in the router source). The safe rule is `goBack` when the previous route is this contact's Profile or Compose, else `replace("Profile", {contactId})`.
6. **D-69 count:** I found 22 user-facing string sites in the same 11 files the dossier lists. The dossier said 15 strings. The difference is multi-line JSX text and composed copy (see §7 for what was counted).

**Primary recommendation:** For each data change, keep to the existing composition contract (one `inWriteTransaction`, `*Core` writers only, exactly one `data_revision` bump). For each retirement, grep every consumer **including tests and pinned counts** in the plan that removes the symbol.

### Risks
- **R1.** Calling `applyLinkDiff` or `addLink` from inside `createContactFullCore` nests the non-reentrant mutex: "nesting it is a PERMANENT hang" (`contacts-dao.ts:9-11`). Only a `*Core` link writer may be composed.
- **R2.** A second `bumpDataRevisionCore` from the link path would double-bump. `applyLinkDiff` bumps itself (`contact-links-dao.ts:299-301`), so it cannot be reused as-is.
- **R3.** `CropPhotoScreen` and `PhotoSourcePicker` both hard-require a persisted contact (`"contact photo target missing"`). Adding a fourth `PhotoTargetDescriptor` kind changes `relPathForTarget` and every exhaustive switch over `target.kind` (CropPhotoScreen, PhotoSourcePicker, restore paths). Grep `target.kind` before you choose.
- **R4.** If the held image lives only in the evictable cache (the picker or manipulator output), it can vanish while a long form is open, and D-77's "photo wasn't added" path fires for no visible reason. That is LIKELY on a low-storage device.
- **R5.** App kill between pick and Save leaves the held file behind. That needs a launch backstop, as import and reconcile have.
- **R6.** A birthday entered on Add will not get its notification scheduled until the next launch sweep (`registerNotificationScheduleSweep`, `notification-schedule.ts:614-619`) unless create calls `reconcileSchedule`. LIKELY user-visible for a birthday today or tomorrow.
- **R7.** `persistOwnedMaster` overwrites `avatars/contact-<id>.jpg`. If a purged contact's id were ever reused, a stale file at that path is simply replaced. That is harmless and matches import. (LIKELY. Whether `contacts.id` is AUTOINCREMENT was not checked.)

### Recommendation (composition) [this research only, within D-48/D-77 and Claude's Discretion]

**Links: inside the create transaction.**
- In `contact-links-dao.ts`, export a non-mutexed `addLinksCore(exec, { contactId, links: Array<{uid,url,label}>, now })` that loops the existing `addLinkCore` and does **not** bump. (Or export `addLinkCore` itself.)
- `CreateContactFullInput` gains `links?: CreateLinkInput[]`. `createContactFullCore` calls `addLinksCore` after the contact INSERT and before the single bump (`:419`). One transaction, one bump. A link failure rolls back the whole create, which is the ADR-016 contract.
- Move `buildLinksForDiff` (`EditContactScreen.tsx:277-286`: trim, empty label → null, drop blank URLs) into a shared logic module, so Add and Edit shape link drafts identically. Add uses it with no `id`s.
- Edit's two-transaction save is **not** in scope (D-48 is about the create write). Leave `edit-contact-save-coordinator.ts` alone.

**Birthday / Social battery: inside the create INSERT.**
- `CreateContactFullInput` gains `birthday?: string | null` and `socialBattery?: string | null`. The INSERT gains the `birthday, social_battery` columns (`?`-bound, default null).
- The form converts with the existing `buildBirthdayForStorage` (`edit-contact-logic.ts:316-325`) so storage is identical: `MM-DD` when the year is unknown, `YYYY-MM-DD` otherwise.
- After create, when a birthday was set, call `reconcileSchedule(exec)` (fire-and-forget with a Logger catch, as Edit does) and `notifyWidgetDataChanged()`.

**Photo: held in a durable create-staging namespace, promoted after commit.**
1. Add a `create-staging/` namespace that mirrors `reconcile-staging/`:
   - `SAFE_CREATE_STAGING_RELATIVE` plus `assertSafeCreateStagingRelative` in `photo-relative-path.ts`
   - `createStagingRelPath(token)`, `stageCreatePhoto`, `listCreateStagingPhotos`, `deleteCreateStaging`, `resolveCreateStagingUri` in `photo-storage.ts`
   - token from `newUid()`, sanitised to `[A-Za-z0-9_-]`
2. Crop in "hold" mode. Give `CropPhotoScreen` a route param for a held crop (a request id plus a staging token) instead of a new `PhotoTargetDescriptor` kind, which avoids R3's switch ripple. On Use photo, `encodeMaster(sourceUri, cropRect)` → `stageCreatePhoto(encodedUri, stagingRel)` → `discardDerivative(encodedUri)` → `publishCropResult(requestId, true)` → `goBack()`. No canonical write and no DB write.
3. Add Contact holds `heldPhoto: { stagingRel } | null` in screen state (not in the dirty-compared seed). It previews via `resolveCreateStagingUri`. The Identity photo control needs a create-mode affordance (Add / Change / Remove of the held file). Remove deletes the staging file.
4. On Save, after `createContactFull` resolves, promote with a helper modelled on `persistImportedPhotoPostCommit`: `persistOwnedMaster(exec, stagedUri, contactPhotoRelPath(contactId), { authorize: uid === input.uid })` → `setContactPhotoForUid(exec, contactId, input.uid, relative, now)` → `notifyWidgetDataChanged()` → `deleteCreateStaging(stagingRel)`. Wrap all of it in a try/catch. On failure, log, keep the contact, show the D-77 "photo wasn't added" snackbar, and still navigate to the Profile. The staging file is deleted in `finally`.
5. **Discard, Back or unmount without save:** delete the held staging file in the screen's unmount cleanup (the pattern at `EditContactScreen.tsx:731-767`), and in the discard-guard's Discard branch.
6. **App kill:** add a launch orphan sweep that deletes **every** `create-staging/` file not owned by an active staging session. No DB row ever references `create-staging/`, so nothing there survives a kill legitimately. Register it the way the import and reconcile sweeps are registered (`launch-sweep.ts` / App.tsx one-shot guard; LIKELY location, verify when planning). `staging-sessions.ts` (`beginStagingSession`/`endStagingSession`, `:6-17`) already exists for "don't sweep a live staged photo".
   - Its `matches()` (`:25-34`) only knows the `_restore_pending` paths. Extend it for `create-staging/`, or have the sweep skip while a create form is mounted.

A lighter alternative (no new namespace) holds the encoded master in the cache dir and cleans it with `discardDerivative`. It is weaker on R4 and R5. Choose it only if the planner judges the extra staging plumbing too large. Either way is within D-77; the durable namespace matches the two existing precedents.

## 8. D-26 — Edit save navigation; D-41 `useBottomClearance`

### D-26 current state (VERIFIED)
- Edit save ends with `bypassRef.current = true; navigation.navigate("Profile", { contactId });` (`EditContactScreen.tsx:1167-1168`).
- React Navigation is `@react-navigation/native` 7.3.18 / native-stack 7.18.8 (VERIFIED in `node_modules`). In v7, `navigate` "will stay on the current screen if the screen is already focused. Otherwise, it pushes a new screen", and `popTo(name)` goes back to it if present (CITED: reactnavigation.org/docs/upgrading-from-6.x). This is defect #2.
- **`popTo` without `getId` matches the nearest earlier route with that name, regardless of params** (VERIFIED `node_modules/@react-navigation/routers/lib/module/StackRouter.js:375-399`). If not found, it pops the current route and pushes the target.

**Stack shapes into Edit** (VERIFIED by grep of `navigate("Edit"` / `"Edit"` destinations):

| Entry | Code | Stack at save | Desired return |
|---|---|---|---|
| Profile ⋯ Edit (today; D-63 moves it to a Hero button) | `ContactProfileScreen.tsx:872` | `[…, Profile(c), Edit(c)]` | back to Profile(c) |
| Profile custom-fields heading / custom-field knowledge change / value history | `contact-profile-logic.ts:76-77, 118-119, 215-216` → `ContactProfileScreen.tsx:369-370`; `:816-818` | `[…, Profile(c), Edit(c)]` | back to Profile(c) |
| Compose "Add a phone number or email" | `ComposeScreen.tsx:1734` | `[…, Profile(c), Compose(c), Edit(c)]` | back to Compose(c). Compose re-reads on every focus (`ComposeScreen.tsx:614-…`), so the new number shows. |
| Contacts swipe Edit | `HomeScreen.tsx:666` → `navigateDashboardContactAction` → `navigateIntoTab(…, "DashboardTab", "Edit", {contactId})` (`:222-230`) | `[Home, Edit(c)]` | the Profile (D-26 "else pop to Profile") |

**Recommended rule** [this research only, implementing D-26 + D-13]: a pure helper, e.g. `resolveEditSaveExit(state, contactId)` in `edit-contact-logic.ts`, unit-tested:
- previous route is `Profile` **or** `Compose` with `params.contactId === contactId` → `goBack()`
- otherwise → `replace("Profile", { contactId })`

Use **`replace`, not `popTo`**, for the fallback. `popTo` could return to a **different** contact's Profile lower in the stack (router source above). `replace` removes the finished Edit so Back doesn't replay it (D-13).

D-26's second half ("Bin from a Profile never lands on a stale Edit form") follows: once Edit is never left under a Profile, `archive()`'s `navigation.goBack()` (`ContactProfileScreen.tsx:571-583`) lands on whatever preceded the Profile. A test can pin that the Profile→Edit→save shape leaves no `Edit` route.

### D-41 current state (VERIFIED `src/navigation/use-bottom-clearance.ts:20-24`)
```ts
export function useBottomClearance(extraForFab = true): number {
  const tabBarHeight = useMeasuredTabBarHeight();
  return tabBarHeight + (extraForFab ? FAB_SIZE + FAB_EDGE_GAP : 0);
}
```
The FAB sits at `bottom = tabBarHeight + FAB_EDGE_GAP` with height `FAB_SIZE` (`UniversalFab.tsx:192, 504-506`). Scroll padding therefore ends **exactly at the FAB's top edge**: "zero margin" (defect #8 confirmed).
- **Consumers:** 30 production files (grep, excluding the definition). None passes `false`.
- **Tests that import the constants:** `fab-clearance-contract.test.ts` (structural: every FAB-bearing screen applies it; no numeric pin found), `section-add-fab-*.test.ts`, `snackbar-host.test.ts`, plus render tests that mock it.

**Recommendation** [this research only; CONTEXT leaves the choice to Claude]:
- Add a top-of-file tunable `FAB_CLEARANCE_MARGIN` (e.g. `SPACING.base`, 16; CLAUDE.md "tunable constants at the top") inside `useBottomClearance`. One edit fixes the Profile and AI Data Permissions and keeps all 30 screens consistent.
- Cost: every FAB-bearing screen gains that much extra scroll at the end. Harmless.
- Check `snackbar-host.test.ts` and `section-add-fab-logic` (which computes its own `+ FAB_SIZE + FAB_EDGE_GAP`, `section-add-fab-logic.ts:175-183`) for any assertion that equates the two clearances.

## Common Pitfalls

1. **Nested write mutex.** Any `inWriteTransaction` wrapper called inside `createContactFullCore` hangs forever (contacts-dao.ts:9-11). Watch for it as a code-review grep for `applyLinkDiff(`/`addLink(` inside contacts-dao.
2. **Double `data_revision` bump.** Create must bump exactly once (contacts-dao.ts:413-419). Pin it in a test (an existing pattern in contacts-dao.test.ts).
3. **Memory route silently unregistered** (§2 R1). Release `navigate` to an unregistered route is a no-op. A debug build may only warn.
4. **Placeholder floor and native-Alert pin** fail the full suite after a correct change (§2, §6).
5. **Exhaustive `Record<ProfileOverviewModuleId, …>`** in `RelationshipOverview.tsx`. tsc catches it, which is good, but only if the post-merge gate runs `tsc --noEmit` (memory "tsc in post-merge gate").
6. **Editor vs Profile order mismatch** for Birthday if the editor's `completeBucket` (append) and the Profile's completion (by position) disagree (§4).
7. **`popTo` picks the wrong contact's Profile** (§8). Use `replace`.
8. **Year-unknown 2000 leak** reappears in any new birthday control that copies Edit's switch (§4).
9. **Hermes `crypto`.** Staging tokens via `newUid()` only.
10. **Worklet forward-reference** (memory note) if any new gesture code is added to the background page: define helpers above callers.
