# Phase 38.11 Plan 09: Duplicate-name Open existing Summary

**Add Contact's duplicate-name warning is now a three-way themed dialog (Open existing / Save anyway / Cancel) built on a new `choose()` in the confirm store. Open existing jumps to the first matching live person, after the save's single-flight release and behind the "Discard changes?" prompt. Duplicates still only warn.**

## Accomplishments
- `findDuplicateNameIds` (live, `COLLATE NOCASE`, `?`-bound, `ORDER BY name COLLATE NOCASE, id`). `isDuplicateName` now delegates to it, so Edit Contact's boolean check behaves exactly as before.
- `choose(request)`: a third entry kind in the one imperative dialog family (ADR-198). It resolves `"confirm" | "secondary" | "cancel"`, joins the same FIFO, and Back/scrim resolves `"cancel"` when the dialog is dismissable. An identical pending request resolves `"cancel"` at once. `confirm()` and `notice()` are unchanged.
- `ConfirmDialog` / `ConfirmActions` gained `secondaryLabel` + `onSecondary`. All three buttons share the existing measure-then-row-or-stack layout (`confirmActionsFit` now takes an optional `secondary` width).
- Add Contact: on save, a duplicate name opens the three-way dialog. Save anyway saves. Cancel writes nothing. Open existing records the first id and skips the save. The jump runs after the `finally` through `openExistingContact`: if the form is dirty it asks "Discard changes?" first, and Keep editing stays on the form. Otherwise it sets the bypass, then on Contacts-style hosts does `replace("Profile")`, and on the Settings host does `goBack()` + `openProfileInContactsTab`.
- Single-flight contract: each screen now has its own duplicate-prompt marker (Create `choose(`, Edit `confirmDuplicate(`), and the test checks the marker is present. A new case pins `openExistingContact(` after the `finally`'s release.

## Decisions Made
- Dialog copy as the plan set it: title "Duplicate name", message "You already have a contact named {name}.", buttons Open existing / Save anyway / Cancel. The copy is built by `duplicateNamePrompt` in the logic module so it can be tested.
- `duplicateNameOutcome("secondary", [])` returns cancel. This is defensive only, because the prompt never opens with no ids.
- If navigation fails during Open existing, the bypass is reset and the error is logged. The user stays on the form and no snackbar is shown. Only a bug can reach this state.

## Owner calls made by the executor
These are small visual or behaviour choices the plan did not settle. They are listed so the orchestrator can surface them; none reverses a recorded decision.
1. **Button order and emphasis in the three-way dialog.** The plan made Save anyway the "confirm" and Open existing the "secondary" button. I placed them Cancel, Open existing, Save anyway, left to right, with Save anyway as the Primary (filled) button, matching the existing Cancel-then-confirm order. Stacked, they keep that order. D-73 lists them "Open existing · Save anyway · Cancel", so if the owner wants Open existing emphasised or ordered first, that is a one-line change.
2. **A typed-but-unadded draft in an in-section editor counts as unsaved work for Open existing.** The plan said to use the guard's `hasUnsavedChanges`. I also counted an open sub-editor holding typed text, because the guard itself prompts for that on a non-Back exit like `replace`. In practice the form is always dirty here, since Save needs a typed name.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Extended the layout helper outside the listed files**
- **Found during:** Task 1
- **Issue:** The plan says the third button stacks "via the existing layout helper", but `confirmActionsFit` (`src/components/ui/confirm-dialog-layout.ts`) only took two widths. That file and its test file were not in `files_modified`.
- **Fix:** Added an optional `secondary` width (two-way behaviour unchanged) and one test in `confirm-dialog-contract.test.ts`.
- **Files modified:** src/components/ui/confirm-dialog-layout.ts, src/components/ui/confirm-dialog-contract.test.ts
- **Verification:** confirm-dialog-contract suite green, including the existing two-width cases
- **Committed in:** c0864dcd

**2. [Rule 2 - Missing critical] Open existing counts an open, typed sub-editor draft as unsaved work**
- **Found during:** Task 1
- **Issue:** Passing only `hasUnsavedChanges` would let Open existing set the bypass and drop an unadded draft without asking. The guard would have prompted for the same `replace`.
- **Fix:** `dirty: hasUnsavedWork || (pickedDraft.open && pickedDraft.dirty)`
- **Files modified:** src/screens/CreateContactScreen.tsx
- **Committed in:** c0864dcd

**3. [Rule 2 - Missing critical] try/catch around the Open existing jump**
- **Issue:** The jump runs after the save's catch. A throw would leave the bypass set and the promise unhandled.
- **Fix:** On error, reset the bypass and log it, mirroring the save's catch.
- **Committed in:** c0864dcd

**Small additions (not deviations in substance):** a `chooseCurrent` store action (DialogHost resolves each choice through it, and `resolveCurrent` maps true/false on a choice head), and the `duplicateNamePrompt` builder. To keep the open path from returning out of the `try` (which would skip the post-`finally` code), the save body after the duplicate check is now nested in an `else` branch. Its logic is unchanged.
