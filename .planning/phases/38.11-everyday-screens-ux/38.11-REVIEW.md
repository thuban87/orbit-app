## Summary

All 86 files in scope were read in full, along with the code that shares their data. I also read the 13 SUMMARY files and checked their claims against the code. `npx tsc --noEmit` passes.

I found no Critical issues. These areas held up when traced against the hot-spot list:
- **Create transaction.** Birthday, social battery and links are written inside the one `inWriteTransaction`. A link failure rolls the whole create back, and there is exactly one `data_revision` bump.
- **Held photo.** The form's staging session protects the held file from the foreground sweep. Save clears `heldPhotoRef` before the promote. The unmount cleanup reads the ref, not stale state. The promote runs while `busyRef` still holds every exit.
- **Open existing.** The jump runs only after the `finally` releases the save lock, and it waits behind the "Discard changes?" prompt.
- **Move to Bin.** The success snackbar can only follow a write that resolved, so an error never shows success.
- **Edit save exit.** It returns to the screen it came from or replaces Edit, and never stacks a second Profile.
- **Snooze sheet.** Bulk Retry takes a fresh claim. Undo restores the effective previous state.
- **Platform rules.** No worklet calls a worklet defined later in the file. The only `crypto` use goes through the guarded `newUid()`. There is no `toISOString` date slicing, no hardcoded colour, and no new network call.

The open issues are side-effect gaps and edge cases:
- Move to Bin from the Profile skips the widget refresh and the reminder reconcile.
- The new layout Reset deletes its row with no tombstone, so a merge restore brings the old layout back.
- The "Never Contacted" wording is wrong for Rarely Responds contacts.
- Add Contact silently drops a link that has a label but no URL.
- A "this plan only" constraint, the birthday picker cap, has spread into a later plan.

No ADR, HANDOFF or CONTEXT control was removed or weakened outside an owner ruling. The removed bulk Unsnooze button, the ⋯ Reset, Edit, Save-as-template and instant Unsnooze entries, the Archive Undo, Unbind's red styling and the Appearance background picker each trace to an owner ruling: D-82, D-65, D-63, D-64, D-71, D-68 or D-84.

## Warnings

### WR-01: Profile "Move to Bin" leaves the widget and scheduled reminders showing the binned person

**File:** `src/screens/ContactProfileScreen.tsx:629-647`, `src/screens/contact-profile-logic.ts:712-749`
**Issue:** After `archiveContact` resolves, `runMoveToBin` closes the overlay, goes back and shows the snackbar. It never calls `notifyWidgetDataChanged()` or `reconcileSchedule()`.
- Other Profile writes in this phase do both: `saveBirthday` (`ContactProfileScreen.tsx:686-704`) and snooze/unsnooze (`:669`, `:682`).
- Bulk Move to Bin at least runs `commitBulkOutcome`, which refreshes the widget (`HomeScreen.tsx:1134-1150`).
- The schedule's population is `archived_at IS NULL` (`src/db/notification-read.ts:108`). Without a reconcile, birthday and decay notifications already scheduled for the person keep firing until the next foreground sweep.

**Failure scenario:** The user moves Alex to the Bin two days before Alex's birthday, then leaves the app. The OS still fires "Alex's birthday", and the home-screen widget keeps listing Alex until something else triggers a refresh.

This was already true of the old `archive()`, but this phase rewrote that path and it is a hot spot. The bulk path also lacks a reconcile.

**Fix:** Add the side effects to the screen's `archive` dependency, so a failed write still never reports success:
```ts
archive: async () => {
  await archiveContact(getExecutor(), contactId, localDateTime());
  notifyWidgetDataChanged();
  void reconcileSchedule(getExecutor()).catch((cause) =>
    Logger.error(LOG_SCOPE, "failed to reconcile after Move to Bin", cause),
  );
},
```
Also add a `reconcileSchedule` to `performBulkArchive`'s `.then`.

**Outcome:** Fixed in `c822672a`. `runMoveToBin` gained an `afterArchive` hook that runs only after the archive write resolves; the Profile passes `notifyWidgetDataChanged()` plus a logged `reconcileSchedule`. A throw from the hook is logged and does not undo the move. `performBulkArchive` now reconciles the schedule after commit (its widget refresh was already in `commitBulkOutcome`). Tests: `contact-profile-logic.test.ts` (order, no side effects on failure or cancel, throw tolerated).

### WR-02: Layout "Reset to default" deletes the presentation row with no tombstone, so a merge restore resurrects the old layout

**File:** `src/db/profile-presentation-dao.ts:477-505` (and the same pattern at `:507-520`)
**Issue:** When the person has no background, `resetContactLayoutPresentation` runs `DELETE FROM profile_contact_presentation` and writes no tombstone. This came from 38.11-05 deviation #1; the plan had specified an all-null upsert.
- `profile_contact_presentation` is an LWW entity (`src/backup/reconciliation.ts:184-187`).
- `reconcileEntity` turns an incoming row with no local row and no tombstone into an `insert` (`reconciliation.ts:541-600`).
- The background half of the same reset (`assignContactBackgroundTemplate(null)`, `background-manager-model.ts:220`) upserts instead, so it wins LWW correctly. The two halves of D-65 behave differently under restore.

**Failure scenario:** The user resets Ann's layout and open/closed sections (deleted row). Later they run a merge restore of a backup taken before the reset. The old freeform layout and collapse map are inserted back, silently reversing the Reset.

**Fix:** Pick one:
- Keep the planned upsert (`layoutTemplateUid: null, freeformLayoutJson: null, clearCollapse: true`), which has a newer `modified_at` and wins LWW. Make share-Undo's ownership check treat an all-default row as non-blocking (`capture-dao.ts:609`).
- Write a `profile_contact_presentation` tombstone keyed by the contact uid in the same transaction as the DELETE.

**Outcome:** Fixed in `0ada86e2` (with IN-02). The tombstone route was not available: `TombstoneEntityType` has no presentation type and `restore-apply.ts` maps `profile_contact_presentation` to no tombstone entity; adding one would change the backup format. So both `resetContactLayoutPresentation` and the unused `resetProfilePresentation` now upsert an all-default row stamped `now`, which wins LWW. Share Undo's ownership rule for `profile_contact_presentation` became `blocks-unless-default`: an all-default row (no layout, no freeform layout, no background, collapse `{}`) does not block, and any other row still does. No migration. Tests: a merge restore of an older backup no longer brings the reset layout back (`restore-apply.test.ts`); DAO row and `modified_at` (`profile-presentation-dao.test.ts`); share Undo blocks on an override row but not on an all-default row (`capture-dao.test.ts`).

### WR-03: Rarely Responds contacts with logged interactions are told "Orbit Status starts after your first logged interaction"

**Outcome:** Fixed in `99f70e63`, following owner ruling D-87. A Bound Rarely Responds contact with no connected interaction reads "Orbit Status starts after your first interaction that connects." Everyone else keeps "…after your first logged interaction." Both cases are tested in `profile-metrics.test.ts`.

### WR-04: Add Contact silently drops a link that has a label but no URL, yet treats it as unsaved work

**Fix:** Pick one:

- Count only URL text in the signature, and accept the silent drop.

**Outcome:** Fixed in `ff114870`, following owner ruling D-88. `LinksEditor`, which Add and Edit both mount, shows the warn-only caption "Add a link or this row won't be saved." under a row that has a label but no URL. It uses the same danger-caption style as the contact-method warning. Save is never blocked and `buildLinksForDiff` still drops the row. Tests: `links-editor-logic.test.ts` and `links-editor-render.test.tsx`.

### IN-03: Hold-mode crop result is dropped if the picker refocuses before the result is published

**File:** `src/components/PhotoSourcePicker.tsx:194-212`, `src/screens/CreateContactScreen.tsx:866-870`, `src/screens/CropPhotoScreen.tsx:363-368`
**Issue:** Two fragile points:
- The focus effect clears `pendingHoldRef` before checking that `consumeCropResult` returned anything.
- CropPhoto does not block Back while `busy`.

So if the user taps "Use photo" and then presses Back while the encode and stage are still running, the Add form refocuses, the pending path is cleared, and the late `publishCropResult` is never consumed. The staged file stays an orphan until the form unmounts and the next foreground sweep runs. The user did press Back, so no data the user expects is lost.

Separately, `hold={{…}}` is a new object on every CreateContactScreen render, so `useFocusEffect` tears down and re-runs on every keystroke.
**Fix:** Clear `pendingHoldRef` only once a result was consumed, or the crop was explicitly cancelled. Memoise the `hold` object with `useMemo` over `[photoSessionToken, heldPhoto, updateHeldPhoto]`.

**Outcome:** Fixed in `0c0652b6`. The picker keeps `pendingHoldRef` until a result for that path is consumed. A focus that finds no result yet leaves the path pending, so a late crop is consumed on the next focus. Add Contact memoises `hold`. CropPhoto still does not block Back while busy: blocking Back could leave the user stuck if the encode hangs, and the picker fix already prevents the lost result. Test: `photo-source-picker-render.test.tsx`.
