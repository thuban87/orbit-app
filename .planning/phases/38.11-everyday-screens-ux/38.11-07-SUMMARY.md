# Phase 38.11 Plan 07: Add Contact Photo (held until Save) Summary

**Add Contact offers Photo beside Name: the crop is held in a guarded `create-staging/` file (one per pick), promoted after the create commits through the 38.6 owned persist onto `avatars/contact-<id>.jpg`, and deleted on Remove, re-pick, discard/unmount or by a session-aware launch/foreground sweep after an app kill (D-77).**

## Accomplishments
- New durable `create-staging/` namespace with its own allowlist regex and assert. Tokens are checked against `[A-Za-z0-9_-]` before any path is built (T-38.11-16).
- CropPhoto hold mode (route params `{ rawUri; hold: { stagingRel } }` in all five param lists): encode, stage, discard the derivative, publish, go back. No canonical lock, no DB write, no fourth target kind (the union still has exactly contact, profile and customField).
- PhotoSourcePicker hold mode gives Add the same Add / Change / Remove and paste-URL surface as Edit. The held preview is an `expo-image` `Image` fed by `resolveCreateStagingUri`; it never goes through `Avatar` or the "Photo unavailable" check.
- `promoteCreatePhoto` runs after `createContactFull`. It never throws, and on `{ ok: false }` Add Contact shows "Contact saved, but the photo wasn't added. Add it from Edit Contact." and still opens the new Profile (both host branches).
- Cleanup: the form holds a staging session while mounted. Unmount deletes an unpromoted held file, reading it through `heldPhotoRef`. A held photo alone makes Back ask first. `registerCreateStagingSweep` runs once from App.tsx and deletes every create-staging file that no live form owns.
- `docs/systems/photos.md` now has a "Holding a photo on Add Contact" subsection, two Key-files rows, an extended gotcha 9 and a 38.11 Changelog row.

## Decisions Made
See the frontmatter `key-decisions`. The plan already set the namespace, the hold-mode shape and the failure copy. Executor-level choices:
- **Stricter create-staging regex.** It accepts `.jpg` only, plus the `create-` prefix, because the plan's behaviour line says to reject "other extension".
- **Hyphen-free tokens.** This makes the session-prefix match exact.
- **The picker deletes the replaced held file.** It does this on focus consume, as the plan says.
- **Ref and state change together.** One setter, `updateHeldPhoto`, sets both, so no render-to-effect window exists between them.

## Owner calls made by the executor
None of these reverses a recorded decision. They are listed so the orchestrator can surface them if it wants to:
1. **Photo position.** Photo sits at the top of Identity, directly above Name. This matches Edit Contact's Identity. The planning ledger said "Identity, beside Name"; I read "beside" as the adjacent field, not side by side on one row.
2. **Remove confirm on a held photo.** It reuses today's copy, "This deletes the photo from this device and can't be undone." The plan said "same confirm as today". For a photo that was never saved this wording is still true, just slightly formal.
3. **Held preview load failure.** If the held preview file fails to load, the picker shows a blank surface-coloured circle, not "Photo unavailable". The plan says to skip that check for held files, and a load failure here can only come from a bug.
