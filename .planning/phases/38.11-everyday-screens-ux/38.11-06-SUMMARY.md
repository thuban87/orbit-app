**A new Settings → Profile Backgrounds page for the global background, Category backgrounds and the saved backgrounds (Delete, Choose photo). It is built on a shared library hook and a shared crop-and-name flow extracted from the 1219-line background sheet. Appearance's "Default profile background" row now opens it.**

## Accomplishments
- `ProfileBackgroundsScreen` (route `ProfileBackgrounds`, title "Profile Backgrounds"). It has three sections. Global background shows the current name or "None", with a Clear button. Category backgrounds lists each Category that has its own background and offers Clear through `CategoryChoiceSheet`. Saved backgrounds has Choose photo and one card per template: thumbnail, name, "Set as global default", "Use for a category", and Delete in the card's ⋯ menu. Each write gets a confirming snackbar (38.9 feedback rule). The scroll content ends with `useBottomClearance()`.
- Choose photo (D-79) runs the shared flow inside `<Sheet variant="expanded">` (review V-05), then offers Set as global default, Use for a category, or Not now. The sheet's scrim and system Back use the same guarded exit as the chevron. The page also guards route removal with `useDiscardKeepGuard` while a crop or name is pending.
- `useProfileBackgroundLibrary` holds the load, the delete (themed destructive confirm, transactional delete, derivative cleanup per ADR-112) and the global and Category assignment writes (the Category's layout uid is kept). The Profile sheet uses it with unchanged behaviour.
- `ProfileBackgroundCreateFlow`: a state hook owns the draft, the pending file, tokens, crop shared values and gestures; a view renders the crop and name steps. The `clampSelection` worklet is defined above the pinch gesture that calls it. The crop header Back is now `<Button role="iconOnly" icon="back" accessibilityLabel="Back">` (D-43).
- D-84: Appearance's existing row navigates to the page. Its label and value are unchanged, and the helper now reads "Global, category and saved backgrounds". The shared picker is narrowed to `"layout" | null`, and its background branch is removed (`onSelectGlobalTemplate` became `onSelectGlobalLayout`).
- The route is registered in all five hosts: SettingsStack plus `SETTINGS_REGISTERED_ROUTES`, literal `<Stack.Screen>` in Dashboard and Orrery, and the `DIGEST_STACK_ROUTES` / `EVENTS_STACK_ROUTES` arrays plus both `*_ROUTE_COMPONENTS` maps. It is also in `PROFILE_REACHABLE_ROUTES` and in all five param lists.
- A new generic test checks every `PROFILE_REACHABLE_ROUTES` entry against Dashboard and Orrery (T-13). Together with the existing Digest/Events and Settings checks, all five hosts are now covered for every Profile-reachable route.

## Decisions Made
- **The flow is a hook plus a view.** A self-contained component holding the state would sit inside the sheet's Modal, which unmounts its children when hidden. The Profile sheet would then lose an unsaved crop whenever it hides, and its reopen check (`shouldResetBackgroundManagerViewOnOpen(managerState)`) would have nothing to read. The hook stays in the host, so behaviour is unchanged.
- **Delete sits behind the ⋯ menu on the page's cards.** Source: docs/systems/ux-standards.md "Destructive actions" rule 4 (38.9 D-30). The Profile sheet keeps its inline Delete for now; 38.11-11 removes it (D-58.3).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Create-flow API shape**
- **Found during:** Task 2
- **Issue:** The plan describes "a component that takes a picked source and reports onSaved(templateUid) or onCancel()". State held inside the component would be lost when the sheet's Modal hides, which would change the Profile sheet's behaviour. It would also leave the manager's reopen check with nothing to read.
- **Fix:** `useProfileBackgroundCreateFlow({ defaultName, onSaved(uid, name) })` holds the state in the host; `<ProfileBackgroundCreateFlow flow onCancel standalone? />` renders it. `chooseImage()` returns `"picked" | "cancelled" | "failed"`, so the page can show an error snackbar. The manager ignores the result and still shows the error line as before.

## Deferred / out-of-scope items
- **A route-guard Discard leaves its pending crop for the launch sweep.** Suppose the page is removed by something other than Back (for example a widget or notification link) while a crop or name is pending, and the user picks Discard. The page then leaves without deleting the pending file at once. The existing ADR-112 launch reconciliation sweep removes it. The Profile sheet has always behaved the same way. *Recommendation:* leave it. The path is rare, the file is app-owned and cleaned at the next launch, and an unmount-time delete would race with an in-flight save.
