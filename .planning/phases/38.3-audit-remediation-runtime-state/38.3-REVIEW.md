## Warnings

### WR-01: Home runs shell/foreground reads while the app is backgrounded. D-23 says it must not.

**File:** `src/screens/HomeScreen.tsx:888` (scheduler `isVisible`); related `src/services/notifications/notification-actions.ts:171,182`
**Issue:** D-23 says: "A refresh requested while Home is hidden (shell bump, foreground) is deferred until Home focus, **not run in the background**." `isVisible` checks only navigation focus (`isFocusedRef.current`). `useIsFocused()` stays `true` while the app sits in the background with Home as the focused screen. `appActiveRef` is already maintained at `:719-720`, but the scheduler ignores it.

This path is reachable. The notification action handler now calls `bumpShellRefresh()` (`notification-actions.ts:171,182`). A Mark/Snooze action delivered to a live-but-backgrounded process (`opensAppToForeground:false`) runs the full 9-query Home bundle in the background. On resume the post-sweep foreground tick reads again anyway, so the background read is pure waste and contradicts the recorded call.
**Fix:** Gate visibility on both conditions. The resume read is already covered by the foreground tick.
```ts
isVisible: () => isFocusedRef.current && appActiveRef.current,
```
Add a scheduler unit case: a "shell" request with `isVisible() === false` returns `null` and issues no read. The existing case covers only blur.

### WR-02: Resume freshness waits for the whole sweep, and a hung hook stops it permanently

**File:** `src/services/launch-sweep.ts:304-353`, `App.tsx:336-339`
**Issue:** `publishForegroundRefresh` fires only in the owning run's `finally`, after every hook, including the backup hook's SAF write/encrypt (`backup-sweep.ts`) and notification reconcile. Home and Profile no longer have their own AppState resume read (the old Home listener was deleted), and Digest relies on the same tick.

If any hook awaits a promise that never settles (SAF provider, SecureStore, `requestWidgetUpdate`):
- the foreground tick never publishes, so every resume after that point leaves Home, Profile and Digest stale until a focus change;
- `running` stays `true`, so every later sweep coalesces into `pendingRerun` and never runs.

RESEARCH A3 flagged the latency risk. The UAT-026c measurement (~0.3 s pass) ran without a due automatic backup, so the worst case was never measured. No bound exists.
**Fix:** Give sweep hooks a bounded per-hook timeout. Log it and mark the hook's id unavailable, as the catch path already does. Alternatively, publish the foreground tick once the purge/expiry producers finish, before backup. That still meets D-14's intent ("reads the sweep's writes (purges, expiry)"). Choosing the ordering point is a D-14 interpretation, so confirm it with the owner if you move the tick.

**File:** `src/screens/EditGroupEventScreen.tsx:174-196, 198-217`; `src/screens/GroupEventDetailScreen.tsx:118-142`; `src/components/group/RemoveParticipantSheet.tsx:33,38`

### WR-04: EditGroupEventScreen keeps an old failure message after later actions succeed

**File:** `src/screens/EditGroupEventScreen.tsx:72, 191-195, 211-216, 324-328`
**Issue:** `error` is cleared only by `saveEvent` (`:122`). The following sequence leaves the red "Couldn't update the group event. Your changes weren't saved." caption on screen next to a list that shows the new participant:
1. a remove fails;
2. a participant add or participant edit then succeeds.

D-04 requires pending, failed and successful outcomes to stay distinguishable. A stale failure beside fresh success violates that.

### WR-05: The Home favourite toggle writes rows outside the single publication seam

**File:** `src/screens/HomeScreen.tsx:1338-1377`
**Issue:** The RG-022 design says `publishDashboardRead` is "the ONLY place a read's result reaches Home's state" and that "no individual setter can publish stale data on its own". `toggleFavourite` breaks this: it calls `setRows(applyCommittedMembership(...))` directly and issues no read. Two consequences:
- **Stale read reverts the star.** A read that is in flight and still current, but snapshotted before the favourite write, resolves afterwards. It publishes the old `favourite_rank` over the patched row, and `favouriteStore.resolve(..., "success")` has already dropped the overlay. The star flips back until the next focus.
- **Counts and filtering go stale.** `populationCounts.favourites`, and Favourites-population membership or sort order, are never re-read. Un-favouriting inside the Favourites population leaves the row listed.
**Fix:** After the write commits, request a read through the scheduler. That begins a new token, supersedes the in-flight read, and republishes counts. For example, add a `"favourite"` source (non-deferrable) to `DashboardRefreshSource` and call `reload("favourite")` in the `.then`. Keep `applyCommittedMembership` only as the optimistic bridge.

### WR-06: Favourite toggles and Group Event writes never notify the widget

**File:** `src/screens/ContactProfileScreen.tsx:272-283`, `src/screens/HomeScreen.tsx:1344-1356`, `src/screens/GroupEventDetailScreen.tsx:101-163`, `src/screens/EditGroupEventScreen.tsx:139-146, 157-217`
**Issue:** `widget-refresh.ts`'s contract lists "favourite toggle/reorder" as a required `notifyWidgetDataChanged()` publisher. Neither the Profile nor the Home favourite toggle calls it, so the OrbitFavourites widget stays stale until the next foreground launch sweep.

Likewise, participant add/remove/delete/dissolve and a parent `occurredAt` change (which moves every participant's `last_contact`) publish nothing. **Fix:** After each committed write, call `notifyWidgetDataChanged()`, plus `bumpShellRefresh()` for the recency-changing Group Event writes. This covers the two favourite toggles, `addParticipants`, `deleteGroupChild`, `detachParticipant`, `dissolveGroupEvent`, `deleteGroupEventAndInteractions` and `updateGroupEvent`. Put the calls outside the write's catch, so a publication failure can never be reported as a write failure (D-04).

### WR-07: The SettingsTab FAB allowlist sends an archived contact into the Contacts tab

### WR-08: History's re-read on every revision can undo a lens or preset change

**File:** `src/components/history/HistorySection.tsx:199-213, 234-251`
**Issue:** `load()` now runs on every Profile publication (focus, shell tick, foreground tick, collapse commits), not just on focus. Each run calls `setLens(settings.historyLens)` / `setCycleCount(...)`. This can override the user's choice in two ways:
- **Race.** `onLensChange` sets the lens and fires `void updateAppSettings(...)`. A read that began before the settings write commits (for example, one triggered by a concurrent shell tick) republishes the old lens and silently reverts the user's choice.
- **Failed write.** `void updateAppSettings` has no `.catch`, so a failed write is an unhandled rejection (this pre-dates the phase). The next revision re-read then silently reverts the lens.
**Fix:** Stop re-publishing lens/preset from revision-driven re-reads once they are hydrated: apply `settings.historyLens` only on the first successful load, or track a local "user-set" flag. Add `.catch` handlers that log the failure and revert the local state explicitly.

## Critical Issues

### CR-01: Post-Log "Create Memory Instead" reports "Couldn't save" after the Memory committed, which invites a duplicate (D-04)

**File:** `src/components/PostLogNoteEditor.tsx:178-201` (also `:210-224`)

**Issue:** `createMemory` awaits `addMemory(...)`, which commits, then bumps the shell. It then awaits `reReadCreatedMemory(id, contactId)` (a `listMemoriesForContact` read) inside the **same** `try`.

If that read throws, the catch at `:199-201` sets `SAVE_FAILED_MESSAGE` ("Couldn't save. Please try again."). The typed text stays in the editor and the "Create Memory Instead" action stays live. A second tap runs `addMemory` again, which creates a **duplicate Memory**.

This is the exact class D-04 forbids ("a committed write must never replay because a later read or presentation step failed"). The phase edited this function and its new comment (`:186-187`) explicitly anticipates the failed re-read, yet the failure is still routed to the write's error copy. The WR-02 note at `:189-191` ("creation is TERMINAL") is contradicted by the throwing branch.

`onEditMemory` (`:210-224`) has the same shape: `editMemory` commits, a throwing re-read returns `false`, and the editor treats the committed edit as a failed save. That one is idempotent, so its impact is lower.

**Fix:** move the post-commit re-read out of the write's catch and make it terminal:
```ts
let id: number;
try {
  id = await addMemory(getExecutor(), { contactId, type: result.type, value: result.value, createdAt: now, now });
} catch (err) {
  Logger.error(LOG_SCOPE, "failed to create memory", err);
  setError(SAVE_FAILED_MESSAGE);
  return; // finally releases savingRef
}
bumpShellRefresh();
let row: MemoryRow | null = null;
try {
  row = await reReadCreatedMemory(id, contactId);
} catch (err) {
  Logger.error(LOG_SCOPE, "memory re-read failed after commit", err); // content-free
}
const next = resolvePostCreateMemoryTarget(row); // null -> "close" (already terminal)
if (next.target === "close") { onClose(); return; }
setCreatedMemory(next.row);
```
Apply the same split in `onEditMemory`: return `true` once `editMemory` resolved, whether or not the re-read succeeds.

### CR-02: The D-20 hold release is inert on the primary bulk-import path, and Back from "Import stopped" lands on a dead Setup screen

**Files:**
- `src/screens/ImportProgressScreen.tsx:31,106`
- `src/screens/use-open-import-session.ts:13`
- `src/screens/BulkImportSetupScreen.tsx:49,58,97-124`
- `src/services/import/import-flow-guard.ts:32-49`
- `src/services/import/contact-import-resume-sweep.ts:200`

**Issue:** D-20 requires "Release the open-import-session hold on fatal exit, so the resume sweep can offer the session again". Plan 11 lists this as a must-have. The code breaks it in two ways.

1. **Refcounted hold never reaches zero.**
   - The normal entry is `BulkImportSetup.startBatch` → `navigation.navigate("ImportProgress", …)` (`BulkImportSetupScreen.tsx:116`). That is a native-stack **push**, so BulkImportSetup stays mounted underneath.
   - BulkImportSetup holds its own mark via `useOpenImportSession(route.params.sessionId)` (`:49`).
   - `markImportSessionOpen` is refcounted (`import-flow-guard.ts:32-45`). When ImportProgress flips `active` to false on the stopped phase, the count only drops from 2 to 1.
   - `isImportSessionOpen(sessionId)` therefore stays `true`, and the resume sweep's `if (!isImportSessionOpen(...))` (`contact-import-resume-sweep.ts:200`) never offers the session.
   - The release only works when ImportProgress was entered from the resume prompt, which is the rare path.
2. **Back leads to a disabled screen.**
   - `startBatch` calls `setSaving(true)` (`:100`) and never resets it on the success path; the navigate happens inside `try` with no `finally`.
   - When the user leaves "Import stopped" through the new "Back" button (`ImportProgressScreen.tsx:106`, the session-unreadable branch) or hardware Back, they land on BulkImportSetup with `disabled={saving || count === 0}` (`:318`) permanently true.
   - The screen has no recovery affordance, and it still holds the session so no resume prompt appears either.

`use-open-import-session.test.ts` tests only the effect body in isolation, so neither failure is covered.

**Fix:** decide which screen owns the hold for the import run. Two options:
- **(a) Replace, don't push:** `navigation.replace("ImportProgress", …)` from BulkImportSetup. Setup unmounts, its mark is released, and ImportProgress's release on fatal stop reaches zero.
- **(b) Keep the push:** have BulkImportSetup release its mark while it is not focused (e.g. `useOpenImportSession(sessionId, isFocused)`). Then reset `saving` in a `finally` or on focus:
```ts
useFocusEffect(useCallback(() => { setSaving(false); void load(); }, [load]));
```
Add a mounted-stack test: Setup → Progress → fatal → assert `isImportSessionOpen(id) === false`.

### WR-01: With the hold released, the resume prompt cannot restart a stopped ImportProgress (same-route NAVIGATE is a no-op)

**Files:**
- `src/components/ResumeImportPrompt.tsx:45-48`
- `src/screens/ImportProgressScreen.tsx:33-68`
- `node_modules/@react-navigation/routers/lib/module/StackRouter.js:213-218`

**Issue:** This is the path where D-20's release *does* work: ImportProgress was entered from the resume prompt, so no Setup screen is beneath it. The sequence is:
1. The import fatally stops; the user leaves the app on "Import stopped" and comes back.
2. The sweep now offers the session.
3. "Resume" (bulk, pending > 0, nonPending > 0) calls `navigateIntoTab(nav, "SettingsTab", "ImportProgress", { sessionId, batchCategoryId: null })`.

In React Navigation 7, a NAVIGATE whose name equals the **current** route reuses that route (`StackRouter.js:217-218`) and only replaces its params. ImportProgress's run effect depends on `[navigation, route.params.sessionId]`, and both are unchanged. The effect does not re-run, and `state` stays `{ phase: "stopped" }`. The user taps Resume and nothing happens. This is the exact recovery path D-20 created.

**Fix:** give the stopped screen its own explicit "Try again" action, which is user-initiated and so allowed by D-20 ("nothing re-runs *automatically*"). Alternatively, make the resume entry distinct, for example:
- `navigation.push`, or
- a `getId` on the ImportProgress screen, or
- a `runKey` param included in the effect deps.

### WR-02: DuplicateReview link choice has no in-flight latch; a double tap reports a committed link as failed, or drops a queued row

**File:** `src/screens/DuplicateReviewScreen.tsx:225-254` (modal choice `Pressable` at `:343-346` has no `disabled`)

**Issue:** Two taps on a choice run `chooseLink` twice. Both capture the same `linking` row and the same `next`. The first `linkExistingContactToRow` commits, and `onWritten` advances the modal to `next`. The second call then does one of two things:
- It hits the active `UNIQUE (provider, external_contact_id)` index (`migrations/011-contact-lifecycle-schema.ts:180`) and throws. `onWriteError` then shows "Couldn't link this contact — Please choose again." over the *next* row's modal, for a link that committed. The user may pick a contact for the wrong row.
- Or, if it resolves, `setLinkQueue((q) => q.slice(1))` runs twice and silently drops a queued row.

This is the same D-04 class the phase set out to close in this function.

**Fix:** add a synchronous `useRef<InFlightRef>` latch (`beginInFlight`/`endInFlight` from `@/utils/single-flight`) around `chooseLink` and `resolveAction`. Disable the choice buttons while a link is in flight.

### WR-03: The ImportComplete Retry (now shown for pending rows too, D-26) has no synchronous latch; a concurrent double run can mark an imported row "failed"

**Files:**
- `src/screens/ImportCompleteScreen.tsx:111-135,279-284`
- `src/services/import/import-driver.ts:139-193`
- `src/db/imported-contact-dao.ts:125-201`

**Issue:** Retry is guarded only by `disabled={retrying}`, which is async React state. Two taps in one tick start two `runImportBatch` runs over the same `pending` snapshot, and `importContactRecord` has no in-transaction row-status recheck. The second insert for the same row violates the active external-link UNIQUE index. The driver's catch then runs `markRowStatus(exec, row.id, "failed", …)` (`import-driver.ts:184-190`), overwriting the row the first run just marked `imported`, while `contact_id` stays set. The summary then shows a phantom failure and re-offers Retry.

D-26 widened the exposure by showing Retry whenever pending rows exist (`import-complete-logic.ts:27-31`).

**Fix:**
```ts
const retryLatch = useRef<InFlightRef>({ current: false });
const retry = useCallback(async () => {
  if (!beginInFlight(retryLatch.current)) return;
  setRetrying(true);
  try { … } finally { setRetrying(false); endInFlight(retryLatch.current); }
}, …);
```
Apply the same to `skipPhotos`. Consider also a `WHERE row_status IN ('pending','failed') AND contact_id IS NULL` guard inside the import transaction.

### WR-04: ImportComplete shows a failed Retry, or a failed post-Retry re-read, as "Couldn't load the import summary. Please go back" with no read-only Retry

**File:** `src/screens/ImportCompleteScreen.tsx:53-92,111-135,171-181`

**Issue:** `retry()` runs `runImportBatch`, the photo retries, `finalizeSessionIfTerminal` and then `load()` in one `try`. Any failure there sets `error = true`, and the whole summary is replaced by "Couldn't load the import summary. Please go back and try again."

- **Retry write failure:** this is not a summary-load failure. It hides the committed counts that were just on screen.
- **Post-commit re-read failure:** there is no read-only Retry, so the only way out is Back. After the D-20 "View import summary" `replace()`, Back lands on the disabled BulkImportSetup from CR-02.

This is the one import screen the phase touched that was not moved to `ReadPhase` + `runGatedRead`. Its publications are also not authority-gated: the retry path's `load()` publishes unconditionally.

**Fix:** convert the summary read to `ReadPhase` + `createLatestRequestAuthority` + `runGatedRead` (never rejects), as in ReconcileComplete. Render `error` with a read-only Retry. Keep a Retry *write* failure as an inline notice above the still-loaded summary, and run the re-read outside the write's catch (`commitThenRefresh` in `backup-settings-logic.ts` is the existing helper).

### WR-05: `runAssistAction` reports "done" for a write that was a silent no-op; Compose then exits as "logged" with no interaction row

**Files:**
- `src/services/assist-commit.ts:145-167`
- `src/db/interaction-assist-dao.ts:87,97`
- `src/screens/ComposeScreen.tsx:1123-1130`

**Issue:** `markAssistLogged` returns normally when the assist is no longer `pending`, both at the pre-read (`:87`) and at the in-transaction recheck (`:97`). The runner cannot tell that apart from a commit, so it returns `"done"`, publishes, and Compose calls `performExit("logged")`. That clears the session and returns toward origin, even though nothing was written. Reachable cases:
- the user dismissed the same assist from the banner ("Don't log") and then taps Compose's "Yes, log interaction";
- opt-out expired every pending assist (`app-settings-dao.ts:1457-1462`);
- the six-pending cap expired it (`interaction-assist-dao.ts:52-63`);
- the launch sweep expired it.

D-04 requires that pending, failed, empty and successful outcomes stay distinguishable. A double confirm of an already-*logged* assist is correctly harmless, but a confirm of a *dismissed* or *expired* one is falsely presented as logged.

**Fix:** have `markAssistLogged` / `markAssistDismissed` return an outcome (`"logged" | "already-resolved"`), or throw a typed `AssistNotPendingError`. Map a non-logged terminal state to its own copy (e.g. "This reach-out was already closed"). Do not call `performExit("logged")` unless a row was actually written. Leave the ADR-071 guard, `handoff_at` stamping and the recheck unchanged.

### WR-06: A Your Week refresh failure wipes the loaded body and shows whole-Digest copy with no Retry

**File:** `src/components/digest/YourWeekSection.tsx:106-109,190-198,290-297`

**Issue:** Your Week re-reads settings and the period on every accepted Digest focus, shell tick and foreground tick. Any failure of those reads sets `error = true`, and the render at `:290` then hides the heatmap and the day detail even when `loaded` holds good data.

The replacement copy is "Couldn't load your Digest / Try opening it again in a moment". That copy is wrong for a single section while Up Next and Horizon are visible, and it has no Retry.

Plan 14's review cycle 1 kept DigestScreen's loaded body on a refresh failure precisely so that Your Week's view survives (`DigestScreen.tsx:127-129`, `digest-refresh.ts:393-409`). Your Week then discards its own loaded view on the next transient failure. The selected day survives in controller state but is not shown.

**Fix:** mirror `digestLoadStateOnFail`:
- when `loaded !== null`, keep rendering the heatmap and detail, and show a compact "Couldn't refresh Your Week" notice with a Retry that bumps a local re-read;
- use the full error branch only when nothing has loaded;
- use section-specific copy.
