# Phase 38.3 plan review

## Summary

The 16 plans cover the phase’s main workflows and preserve the recorded navigation, privacy, and data decisions. The strongest parts are the shared refresh signals, explicit read states, and the separation of committed writes from later readback. **Overall risk: HIGH** until the issues below are resolved. Several proposed tests exercise pure helpers but would not catch failures in the mounted screen or in the write → publication sequence.

## Strengths

- **Plans 01, 08, 12, 14, and 15** establish a consistent latest-request rule. That addresses a real gap in Home’s independently guarded reads at [HomeScreen.tsx](/home/bwales/projects/orbit-app/src/screens/HomeScreen.tsx:705) and Your Week’s date-only guard at [YourWeekSection.tsx](/home/bwales/projects/orbit-app/src/components/digest/YourWeekSection.tsx:171).
- **Plans 03 and 06** preserve explicit participant follow state and separate a committed add from its refresh. The current combined catch at [EditGroupEventScreen.tsx](/home/bwales/projects/orbit-app/src/screens/EditGroupEventScreen.tsx:149) demonstrates why both fixes are needed.
- **Plans 09, 10, and 13** respect semantic tab roots, Settings-host route limits, and the existing in-Profile History decision.
- **Plan 16** requires evidence for mounted flows and keeps blocked device checks open instead of treating unit tests as device proof.

## Concerns

- **HIGH · Plan 05 · MECHANICAL:** The proposed `runAssistAction` catches a failed *write*, then awaits `publish()` outside that catch. The publisher description explicitly contains queue-refresh failure, but widget notification or shell publication can also throw. If either does, a committed confirmation rejects, potentially leaving Compose on its confirmation screen and inviting another tap. The current entries combine these operations at [AssistBanner.tsx](/home/bwales/projects/orbit-app/src/components/AssistBanner.tsx:42) and [ComposeScreen.tsx](/home/bwales/projects/orbit-app/src/screens/ComposeScreen.tsx:1066). **Fix:** make the entire post-commit publisher non-throwing, catch each publication independently, and test a throw from each dependency—not only `refreshQueue`.

- **HIGH · Plan 11 · MECHANICAL:** The proposed DuplicateReview change separates the final `refresh()` from a committed link, but `chooseLink` currently catches `linkExistingContactToRow` and `finalizeSessionIfTerminal` together at [DuplicateReviewScreen.tsx](/home/bwales/projects/orbit-app/src/screens/DuplicateReviewScreen.tsx:196). A successful link followed by failed finalization still shows “Couldn't link this contact” and invites another choice. The bulk path likewise performs writes before `finalizeAndRefresh()` at [DuplicateReviewScreen.tsx](/home/bwales/projects/orbit-app/src/screens/DuplicateReviewScreen.tsx:150). **Fix:** mark each resolve as committed immediately after its write; handle finalization and readback as separate recovery steps. Test write success followed by finalization failure for both link and bulk resolve.

- **HIGH · Plan 14 · STRUCTURAL:** Digest renders `DigestLoadedBody` only in its loaded phase and removes it in error at [DigestScreen.tsx](/home/bwales/projects/orbit-app/src/screens/DigestScreen.tsx:183). Plan 14 retains that phase behavior while putting Your Week’s period and selected day in component state. A transient outer Digest read failure therefore unmounts Your Week and loses that selection, contrary to D-15’s preservation rule. **Fix:** retain the last loaded body during a refresh failure and show an error alongside it, or hoist Your Week’s transient state above the phase switch. Test success → failed refresh → successful retry with an in-window selected day.

- **MEDIUM · Plan 04 · MECHANICAL:** Cold-response clearing is described as unconditional, but the current call follows `await applyBodyNav(data)` within one async block at [notification-gate.tsx](/home/bwales/projects/orbit-app/src/navigation/notification-gate.tsx:226). A lookup or navigation rejection skips `clearLastNotificationResponseAsync()`. The proposed chronology guard does not address that path. **Fix:** put clearing in `finally`, with its own logged failure, and test a rejected cold lookup as well as a stale dropped result.

- **MEDIUM · Plan 07 · MECHANICAL:** BackupSettings’ current `reload()` starts an async IIFE and returns a cancellation function at [BackupSettingsScreen.tsx](/home/bwales/projects/orbit-app/src/screens/BackupSettingsScreen.tsx:67). Existing write handlers use `await reload()` at [BackupSettingsScreen.tsx](/home/bwales/projects/orbit-app/src/screens/BackupSettingsScreen.tsx:127), which does **not** await the read. The plan changes read phases but does not explicitly require changing this return contract. **Fix:** make post-write reload return a real promise, with separate focus cleanup, and test commit → delayed/failed reread → error presentation.

- **MEDIUM · Plan 08 · STRUCTURAL:** The proposed History error handling displays an error only “when no history has loaded yet.” History currently keeps its previous `history` value at [HistorySection.tsx](/home/bwales/projects/orbit-app/src/components/history/HistorySection.tsx:156) and renders it whenever non-null at [HistorySection.tsx](/home/bwales/projects/orbit-app/src/components/history/HistorySection.tsx:291). After a successful Profile snapshot refresh, a failed History reread would leave current metrics beside stale History with no visible failure. **Fix:** give History an explicit refresh-error state even when old data is retained, and label that data as stale with Retry. Test successful initial read → new parent revision → failed History read.

- **MEDIUM · Plan 12 · STRUCTURAL:** Scheduler tests prove token ordering, while the proposed source scan checks only `reload` dependencies. Neither proves that every Home publication uses the token. The current read publishes rows, line-3, search matches, counts, errors, animation generation, and loading flags in separate statements at [HomeScreen.tsx](/home/bwales/projects/orbit-app/src/screens/HomeScreen.tsx:785). **Fix:** extract one testable read-result publication boundary, or add a mounted test that resolves two real read bundles out of order and checks *all* displayed projections, including error and refreshing state.

- **MEDIUM · Plan 16 · STRUCTURAL:** The RG-020 device row says a `uiautomator dump` after dismissal proves controls are clickable. The dump exposes accessibility properties and bounds; it does not prove that `pointerEvents` and gesture handling recovered. The failure originates in the panel store and Home wrappers at [DashboardOverlayHost.tsx](/home/bwales/projects/orbit-app/src/components/control-surface/DashboardOverlayHost.tsx:32) and [HomeScreen.tsx](/home/bwales/projects/orbit-app/src/screens/HomeScreen.tsx:1651). **Fix:** tap the app bar, search toggle, and a row after each dismissal, and record the resulting UI change alongside the dump.

## Suggestions

- **Plans 02, 03, 06, 09, 10, 13, and 15:** keep the planned helper tests, but add one integration assertion per critical path that observes the screen or DAO outcome. Source-string checks are useful regression tripwires, not behavioral proof.
- **Plans 01, 04, 05, 07, 08, 11, 12, and 14:** add a compact failure matrix to their acceptance criteria: write/read success, read rejection, stale completion, unmount, and retry where applicable.
- **Plan 13:** test the selector runner through the component’s pending state. The current reducer settles `pending` only on `success`, `failure`, or `dismiss` at [relationship-sheet-model.ts](/home/bwales/projects/orbit-app/src/profile/relationship-sheet-model.ts:149); a pure runner test alone may miss a stale `isPending` callback held in a ref.

The findings above are implementation corrections within the recorded decisions. I found no basis here to recommend reversing an owner decision.

## Claude Review

# Review: Phase 38.3 Plans (01–16)

## Summary

This is an unusually well-grounded plan set. I spot-checked roughly a dozen of the plans' most load-bearing factual claims directly against the files on disk — `DashboardOverlayHost.tsx`'s close-before-read bug (RG-020), `launch-sweep.ts`'s `finally`/coalescing structure, `EditGroupEventScreen.load()`'s reseed of `baselineRef`/`draft`, `AssistBanner.confirm/dismiss`'s missing try/catch and shell bump, `notification-gate.tsx`'s always-true default `isCurrent` on the cold path, `SettingsStack.tsx`'s absence of `RecentlyDeleted`/`Compose`, `relationship-sheet-model.ts`'s `profileHeroActionState` (no archive/host awareness) and `relationshipExplanation`'s unconditional `routes: ["history"]`, `ContactProfileScreen.tsx`'s hard-coded `navigate("ThingsToRemember", …)` for both History actions, `log-guards.ts`'s exact future-date error text, and `YourWeekSection.tsx`'s `onSelectDay`/`onPeriodChange` empty-then-load pattern with its date-only staleness guard — every one matched the plan's description exactly, including line ranges. That is a materially higher hit rate than typical for audit-remediation plans of this scope, and it means the diagnoses (not just the fixes) can be trusted. The plan set's structure — one shared primitive plan (01) feeding two dependency waves of producer/consumer fixes, then a dedicated device-UAT closure plan (16) — is sound, and the wave/file-ownership graph is almost entirely conflict-free (I checked every pair of same-wave plans for shared `files_modified` and found none, other than the deliberately staggered cross-wave touches on `HomeScreen.tsx`, `ContactProfileScreen.tsx`, `ComposeScreen.tsx`, `ImportCompleteScreen.tsx` and `relationship-sheet-model.ts`, all of which are correctly wired through `depends_on`). The main residual risks are the classic ones for a phase this size: a few plans build a fresh read-authority abstraction inline rather than reusing Plan 01's `createLatestRequestAuthority` where it would clearly apply (duplication, not a defect), a couple of "closes the loop" claims depend on data-flow assumptions I could not fully trace end-to-end (Plan 08's revision-driven History refresh; Plan 13's reveal-through-persisted-collapse mechanism), and Plan 16's device-UAT gate is the single point of failure for the phase's actual correctness claim, since vitest here is explicitly render-free.

## Strengths

- **Root-cause claims are verified, not asserted.** Plan 02's RG-020 diagnosis (`DashboardOverlayHost.tsx:32-35`: `close()` nulls `request` *then* reads `request?.onDismiss()`, so the callback is always called on a null object) is exactly what's on disk. The capture-before-clear fix in `dismissDashboardPanel()` is the correct minimal fix and doesn't touch `AnchoredPanel`'s scrim/Back wiring.
- **D-04 ("never replay a committed write") is operationalized consistently**, not just asserted per-plan: Plan 05's `runAssistAction`/`publishAssistCommit` never lets a post-commit publish failure flip to an error state; Plan 06's `runParticipantAdd` awaits only the write, never the refresh, for the same reason; Plan 07/11's tri-state read helpers keep write failures and read failures in separate branches. This is the one property that's easy to get wrong across five different screens and it's handled with one repeated shape.
- **Owner decisions are correctly scoped and not silently reinterpreted.** D-07 (ContactPicker fallback kept), D-08 (RN-013 reopened with specific required behaviors), D-25/D-27 (Settings-hosted Message disabled, but native SMS untouched) are each implemented as literally described, and Plan 10's Task 1 test explicitly asserts Compose/ComposeResearch stay *unregistered* under Settings — a real regression guard against the tempting-but-forbidden fix.
- **Wave/dependency graph is file-disjoint within waves.** Wave 2 (05/06/07/08) shares zero files. Wave 3 (09/10) shares zero files. Wave 4 (11/12/13/14) shares zero files. Sequenced cross-wave edits to shared files (`HomeScreen.tsx`: 02→09→12; `ContactProfileScreen.tsx`: 08→10→13; `ComposeScreen.tsx`: 05→09; `relationship-sheet-model.ts`: 10→13) are all backed by explicit `depends_on` entries.
- **Test-orphan hazard is explicitly tracked.** Several plans (06, 09, 13, 14) call out by name the existing tests that assert the *old*, soon-to-be-wrong contract (`contact-picker-multiselect.test.ts:131-145`, `profile-module-host-render.test.tsx` props objects, `DigestScreen.test.tsx`/`YourWeekSection.test.tsx` mocks) and schedule their rewrite in the same plan that breaks them, rather than leaving them to bit-rot.

## Concerns

- **HIGH (Plan 08, STRUCTURAL)** — History's refresh is now entirely downstream of the Profile snapshot's *success*. `contact-profile-logic.ts`'s `createProfileSnapshotLoader` only calls `publish(value, revision)` — which bumps `historyRevision` — on a successful current read; `fail()` does not bump it. If the Profile snapshot read fails transiently while History was previously loaded fine (e.g., a momentary SQLite busy error on shell-tick refresh), History silently stops refreshing on every subsequent trigger until a Profile snapshot read finally succeeds again — there is no independent "History needs a refresh" signal once decoupled from its own `useFocusEffect`. The plan removes `HistorySection`'s focus effect entirely (verified: `src/components/history/HistorySection.tsx:164-179` currently owns its own `readContactHistory` call independent of the parent). This is a real regression risk versus the current design where History refreshes on its own focus regardless of Profile snapshot health. **Fix:** either bump `historyRevision` on both success and failure paths (treat it as "a read attempt happened," not "a read succeeded"), or keep a lightweight independent focus-triggered fallback specifically for History.
- **HIGH (Plan 14, MECHANICAL)** — The claim that Digest "never presents an older result over a newer one" for Your Week's *period* read is only partially covered. `resolveYourWeekRefreshPeriod` + Task 2's "request-scoped `createLatestRequestAuthority()` token" is per-invocation of the signal effect, but the period-read call and the generation-based `reconcileYourWeekRead` mechanism (existing code, confirmed at `YourWeekSection.tsx:140-166`) are two different staleness mechanisms running side by side after this plan (one keyed on `generation`, one on the new authority token). The plan doesn't specify how these interact when both a manual period toggle (which bumps `generation` via `selectYourWeekPeriod`/`beginYourWeekPeriodWrite`) and a `refreshSignal`-driven re-read race concurrently — e.g., user taps "Calendar Week" the instant a shell-tick refresh fires. This is exactly the kind of "two coordinators for one value" bug class RG-022's D-23 was written to eliminate elsewhere in the phase, reintroduced here in miniature. **Fix:** make the request-scoped authority the *sole* staleness gate for the period read, and have generation checks defer to it, or document explicitly why both must coexist.
- **MEDIUM (Plan 13, OWNER-DECISION-adjacent)** — D-10 says the reveal must not reset History's period/selection, and the plan implements the expand step via "the SAME persisted `toggle` a header tap uses" (planner call A1, explicitly flagged as not reversing a recorded decision). But `toggle({ id: "interaction-history", expanded: defaultExpanded })` persists a layout override — meaning a Status-sheet "View history" tap on a contact whose owner had deliberately collapsed History now durably re-expands it for future visits, not just for this viewing. That's a real, user-visible side effect of an action the owner described only as "scroll to and expand" (D-10), and it is different from an ephemeral expand-for-this-view. The plan does flag this for owner attention in the SUMMARY per its own text, but the fix ships regardless of that flag being read — worth confirming this is genuinely what the owner wants before this plan executes, since D-11's "no layout mutation" sibling rule makes the asymmetry (omit-when-hidden vs. persist-when-shown) a little uncomfortable.
- **MEDIUM (Plan 12, MECHANICAL)** — The "reload dependencies exclude animation/lifecycle state" guard test is implemented by textually locating `const reload = useCallback(` in `HomeScreen.tsx` and bracket-counting to the dependency array. This is a reasonable pragmatic test given no component renderer is available, but it is fragile to reformatting (e.g., Biome reflowing the callback signature across more lines, or a second `useCallback(` appearing earlier in the file that the scan latches onto first) and gives a false sense of "tested" for a property that's really about runtime behavior, not source shape. Since this guards a PERF-002 regression specifically called out as previously reintroduced, a companion behavioral test (assert `HomeScreen`'s `reload` callback identity is stable across `reducedMotion`/`appActive` prop changes, via a minimal test harness) would be more durable — though I recognize the constraints explicitly rule out a renderer here.
- **MEDIUM (Plan 09, MECHANICAL)** — The repository-wide guard test in Task 3 (regex scan for `.navigate(` + tab-name literal or `intent.tab`) is a good mechanical backstop, but as written it only catches the exact literal-tab-name shape. A `.push(...)`/`.replace(...)` call with a nested `screen` payload targeting a different tab's navigator (obtained via a differently-named ref, e.g. `parentNav`, not matched by the `.navigate(` regex family described) would slip through undetected. Given this guard is meant to be the durable backstop against the whole RN-002 bug class reappearing in future phases, it's worth widening the regex to also match `.replace(`/`.push(` with the same tab-name/`.screen` shape, or documenting explicitly that it's `.navigate(`-only by design.
- **LOW (Plan 05, MECHANICAL)** — `runAssistAction`'s behavior list requires "queue refresh rejects ⇒ onError not called," which is correct for D-04, but there's no test case (in the `<behavior>` list at least) for "the *write* succeeds, `notifyWidget`/`bumpShell` are synchronous no-throw calls, but something in the write's own commit path throws asynchronously after `write()` already resolved" — i.e., a race where the DAO's in-transaction pending recheck (ADR-071, `interaction-assist-dao.ts:97`) determines the assist was already resolved by a concurrent path between when `write()` resolves and `publish()` runs. This is likely a non-issue in a single-threaded JS runtime with `markAssistLogged` fully transactional, but it's worth a one-line confirmation in the plan that "write() resolving means the transaction is durably committed" rather than leaving it implicit.
- **LOW (cross-plan, STRUCTURAL)** — Several plans build their own tiny `createLatestRequestAuthority()`-*shaped* mechanism instead of reusing Plan 01's utility directly where a generic gate would suffice (e.g., Plan 14's `createDigestRefreshController<T>` in `digest-refresh.ts` reimplements the same publish/fail/isVisible-gated pattern as Plan 12's `createDashboardRefreshScheduler`, and both wrap `createLatestRequestAuthority` rather than sharing a single generic `createGatedRefreshController` between Home and Digest). This is explicitly by design per D-03 ("no new state library" ≠ "no shared controller shape"), and each screen's controller does have legitimately different hidden/visible semantics, so this is a mild missed-reuse opportunity rather than a defect — flagging as a suggestion, not a blocker.

## Suggestions

- In Plan 08, add an explicit `must_haves.truths` line (or a Task 1 test case) for "a failed Profile snapshot read still bumps `historyRevision` (or otherwise signals History to retry independently), so History does not go permanently stale behind a persistently-failing snapshot read."
- In Plan 14, add one sentence in the objective or Task 2 action clarifying the interaction between the existing `generation`-based reconciliation (`reconcileYourWeekRead`) and the new request-scoped authority, so the executor doesn't have to infer it.
- In Plan 13, have the executor confirm with the owner (or record as an explicit open question in the SUMMARY, as intended) whether persisting the expand-via-`toggle` is acceptable, versus an ephemeral scroll-and-visually-expand-without-persisting approach, given D-11's parallel "no layout mutation" rule for the omitted case.
- In Plan 09's guard test, widen the pattern to also flag `.replace(`/`.push(` calls with the same nested-screen shape, or add a one-line comment stating the guard is intentionally `.navigate(`-scoped.
- Plan 16's Task 2/3 device rows are the only mechanism that actually proves mounted-lifecycle correctness for roughly a dozen fixes across the whole phase (vitest is render-free by explicit project convention). Given how much rides on this single plan, consider whether splitting the D-05 TalkBack gate (which can legitimately block on device/owner availability) from the rest of Task 2's rows would reduce the risk of the entire phase stalling behind one investigation gate — though I recognize this is presumably intentional given the joint-run note with 38.4.

## Risk Assessment

**LOW-MEDIUM.** The plan set's diagnoses are unusually well-verified against the actual codebase (every claim I checked was accurate down to the line), the D-04/D-09/D-25/D-27 owner constraints are correctly enforced with regression-guarding tests rather than just prose, and the wave/dependency graph avoids same-wave file collisions almost perfectly. The residual risk is concentrated in a small number of places where a single upstream signal (Plan 08's snapshot-success-gated revision; Plan 14's dual staleness mechanisms) has been made the sole trigger for a downstream refresh without an explicit failure-mode discussion, plus the standard risk that this phase's actual correctness proof lives almost entirely in Plan 16's on-device UAT rather than in the (necessarily render-free) automated suite. None of these are severe enough to block execution, but Plan 08's History-refresh coupling in particular is worth a one-line fix before that plan runs, since it's the kind of regression that would only surface intermittently in the field.
