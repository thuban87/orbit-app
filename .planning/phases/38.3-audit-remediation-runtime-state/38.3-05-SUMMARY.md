# Phase 38.3 Plan 05: Shared Assist Publication & Failure Contract Summary

**All three assist confirmation entries (banner, pending sheet, Compose) now share one module, `src/services/assist-commit.ts`:**
- **Latched write.** A synchronous latch lets each confirm or dismiss write run once, even on a double tap.
- **Publication after commit.** After the write commits, one publisher notifies the widget, bumps the shell tick and refreshes the queue. The publisher never rejects.
- **Truthful failure Alerts.** A failed write shows an Alert. A clock rollback raises the typed `FutureOccurredAtError`, which gets its own copy.
- **Ordered queue refresh.** An older queue refresh can no longer overwrite a newer one.
- **Post-Log refresh.** The Post-Log editor publishes the shell tick after each committed write.

## Accomplishments
- **`assist-commit.ts` (DI, node-tested).** It imports only `log-guards` and `single-flight`. Its exports:
  - `runAssistAction` claims the latch synchronously. It returns `"busy"` without writing if the latch is held, `"failed"` after `onError(kind, error)`, and `"done"` once the write commits, however publication went (D-04). It releases the latch in `finally`.
  - `publishAssistCommit` wraps each of its three steps (widget notify, shell tick, queue refresh) in its own `try/catch`. A failure is logged content-free and the remaining steps still run.
  - `publishAssistDismissal` refreshes the queue only.
  - `classifyAssistFailure` and `ASSIST_FAILURE_COPY` supply content-free copy. The clock-rollback title is "Check your device clock".
- **`FutureOccurredAtError`.** Only the `occurredAt > now` branch throws it, with a byte-identical message. The two malformed-value branches still throw a plain `Error`. The guard logic, the handoff-time `occurred_at` and the DAO's in-transaction pending recheck are unchanged; `interaction-assist-dao.ts` has no diff (ADR-071).
- **AssistBanner.** It declares a ref latch and a `pending` state above the early return, runs confirm and dismiss through the runner, and passes `pending` to `AssistConfirmation`.
- **PendingConfirmationsSheet.** Latches are per assist uid, and a set of pending uids drives the UI. The sheet uses the same runner, publishers and Alert copy as the banner.
- **AssistConfirmation.** A new optional `pending` prop disables Yes, No answer and Don't log, setting both `disabled` and `accessibilityState.disabled`. The handlers are now awaited inside `try/catch` and a rejection is logged; the bare `void` calls are gone. The styling and note toggle are unchanged.
- **Compose `onConfirmYes`.**
  - A ref latch now guards the write alongside the existing `logging` UI state.
  - It publishes through `publishAssistCommit` before `performExit("logged")`.
  - A future-date failure shows the typed clock-rollback copy; any other failure keeps Compose's existing generic copy.
  - No other Compose code path was touched.
- **assist-store.** A module-level `createLatestRequestAuthority()` gates `refresh`:
  - The token is taken first, then `applyUatFault("assist-queue-refresh")` runs (inert outside `__DEV__`), then the read.
  - The store publishes only if the token is still current. A read failure still rejects to its own caller.
  - `subscribeAppState` attaches a `.catch` that logs the failure.
- **PostLogNoteEditor.** `bumpShellRefresh()` is called exactly once after each committed write:
  - the note save;
  - Memory create (before the re-read);
  - Memory edit;
  - the resolved branch of Memory delete, restore and Allow-AI.

  It is never called on the no-op or missing branches, or in `catch`.

## Decisions Made
- **`onError(kind, error)`.** The plan specified `onError(kind)`. Adding the raw error as a second argument keeps Compose's existing error log and lets the banner and sheet log a failed write content-free. It is additive.
- **Publish guard in `runAssistAction`.** The runner also wraps `publish` (with an optional `logFailure`). A publish that breaks its never-reject contract still cannot report a committed write as failed.
- **Sheet latches are never deleted.** They stay in the map for the sheet's lifetime, which is bounded by the five-pending cap. Deleting them after each run would have been safe only by a microtask-ordering argument.
- **Token before the fault wait.** The queue refresh takes its token before the dev fault wait, so a delayed older refresh is always superseded.
