# Phase 38.3 Plan 04: Cold/Warm Notification Ingress Chronology Summary

**A warm notification body tap now marks a per-mount chronology controller, so a slower cold-launch lookup that resolves afterwards is dropped (debug log only, no payload data) instead of resetting the navigator. The cold launch response is now cleared in a `finally`, so it is cleared even when the read or the navigation fails.**

## Accomplishments

- `createNotificationIngressChronology()` is exported with closure methods: `markWarmBodyAccepted`, `coldIsCurrent` and `teardown`. `coldIsCurrent` is true only while no warm body tap has been accepted and the gate is still mounted.
- `NotificationResponseGate` holds the controller in a ref. It is created in a mount effect declared before the warm-listener and cold-start effects, and the effect's cleanup calls `teardown()`. The cold predicate reads the ref when the event fires (`chronologyRef.current?.coldIsCurrent() ?? false`).
- Warm routing (`handleWarmNotificationResponse`) marks the chronology only in the `DEFAULT_ACTION_IDENTIFIER` branch, and does so before `setPendingBodyData`. Mark and Snooze still go through `runActionTap`, which calls `handleNotificationAction`. Any other action ids are ignored.
- The cold routine (`handleColdStartResponse`) passes a logging `isCurrent` into the unchanged `applyBodyNav(data, isCurrent, lookup)`. The first time `isCurrent` returns false it logs `Logger.debug("notif-gate", "stale cold notification navigation dropped")`, once. `clearLastNotificationResponseAsync()` now sits in a `finally`, and the outer `.catch` in the effect still logs routing errors.
- The warm flush request-id gate, readiness gating, the `coldStartHandled` once-latch and `applyBodyNav`'s default `isCurrent` are unchanged.
- 18 new ordering, logging and replay-guard tests were added. The 7 existing tests still pass (25 total).
- `docs/systems/notifications.md` now has the chronology rule under "Opening a notification" and a 38.3 Changelog row that cites RG-042.

## Deviations from Plan

**1. [Rule 3 - Blocking] Extracted the cold and warm routines as exported functions**
- **Found during:** Task 1
- **Issue:** The vitest env is node-only and render-free (vitest.config.ts), so the component's effects cannot be driven directly. The rejected-lookup and clear-still-runs test, and the check that action taps never mark acceptance, need callable routines.
- **Fix:** `handleColdStartResponse(coldIsCurrent, lookup?)` and `handleWarmNotificationResponse(response, chronology, park)` were extracted. The component calls them with no change in behavior.
- **Files modified:** src/navigation/notification-gate.tsx
- **Commit:** 29179ec

**2. [Rule 1 - Robustness] Changed the clear error handler to try/catch inside `finally`**
- **Found during:** Task 1
- **Issue:** The plan sketched `await clearLastNotificationResponseAsync().catch(...)`. That form would not contain a synchronous throw, or a clear that returns nothing.
- **Fix:** Used `try { await clearLastNotificationResponseAsync(); } catch (err) { Logger.error(LOG_SOURCE, "clear last notification response failed", err); }`, keeping the same log message.
- **Commit:** 29179ec

**3. [Doc] Reworded the header comment**
- **Issue:** The acceptance criterion requires `grep -c "clearLastNotificationResponseAsync()"` to return 1. The existing header comment also contained the call with parentheses.
- **Fix:** Rewrote the replay-guard paragraph to name the function without parentheses and to describe the `finally`.

**Total deviations:** 3, all minor. **Impact:** None on scope. Action semantics are unchanged, and nothing from widget or native-intent handling was merged into the gate.
