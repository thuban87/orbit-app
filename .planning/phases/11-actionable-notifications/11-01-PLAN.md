## Phase Goal (MVP user story)

**As a** person maintaining relationships in Orbit, **I want to** get a calm morning notification when I'm overdue with someone (or it's their birthday) that I can act on in one tap — mark contacted, snooze, or open the compose screen — **so that** I actually reach out before the connection decays, without the app nagging me.

**MVP sequencing exception (owner-authorized, grounded in the codebase):** this phase's true end-to-end behaviours (a notification firing, a killed-app headless action write) are OS-runtime and cannot be exercised by the JS test harness — they are Pixel-UAT only (see 11-VALIDATION.md Manual-Only). So, exactly as Phase 9 (expo-sms) and Phase 10 (expo-share-intent) did, the mandatory native/data foundation lands first (Wave 1) and the vertical feature slices (scheduling, headless actions, settings UI, birthday) build on it. Each post-foundation plan still delivers an observable capability.

<objective>
Land the native enablement and the shared contracts every later plan imports: install `expo-notifications`, register its config plugin, provide a node-safe test double so the Wave-0 unit suites can assert call shapes, and create the single `notification-ids` constants module (stable identifiers, channel/category/action ids, generic body copy, and the `NotificationData` payload type).

Purpose: unblock every downstream notification plan and guarantee identifiers/copy/channel ids have ONE source of truth (no drift between the scheduler that writes them and the handler that reads them).
Output: `expo-notifications` installed + plugin registered; `__mocks__/expo-notifications.ts`; `src/services/notifications/notification-ids.ts` (+ test).
</objective>
