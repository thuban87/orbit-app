## ADR-075 compliance (favourites) — enforced + flagged (reviews cycle 2026-09-02)

ADR-075 (Accepted, owner-ratified 2026-09-01) makes favourites BINARY membership with NO user-facing order anywhere, and retires the Manage-favourites reorder screen + its Dashboard and Settings entries "with nothing put in their place." Its own named risk: any read that ORDERs by `favourite_rank` silently keeps the retired rank deciding user-visible order. **Verified on disk this cycle:** ADR-075 is NOT yet implemented in code — `dashboard-read.ts:245/:333`, `sun-picker-read.ts:45`, and `capture-read.ts:65-66` still ORDER BY `favourite_rank ASC`; `ManageFavouritesScreen.tsx` + `favourites-reorder-logic.ts` + the `favourites-dao` rank-rewrite writes still exist; favourite membership is stored as `favourite_rank IS NOT NULL` (there is no boolean `is_favourite` column).

**ENFORCED in this phase** (planner call — enforcing a recorded decision, per CLAUDE.md "enforcing a recorded decision is a planner call"):
- **Plan 06 `picker-read.ts` (a NEW read path)** MUST NOT ORDER BY `favourite_rank ASC` — that is exactly the ADR-075 risk reintroduced in a new path. It orders by favourite MEMBERSHIP band (`(favourite_rank IS NULL)` → 0 for a favourite, 1 for the rest) → Default ordering (`last_contact DESC` interaction recency) → `name COLLATE NOCASE`. Rank never decides user-visible order.
- **Plan 04** removes the two user-facing entries ADR-075 names verbatim: the Dashboard favourites-filter "Manage" entry (`HomeScreen.tsx:319`, inside the `filter === "favourites"` block) and the Settings "Manage favourites" row (`SettingsScreen.tsx:2008`).

**FLAGGED for the owner** (dropping the ManageFavourites ROUTE would DELETE a shipped recorded behavior and force a product decision ADR-075 did not make — per CLAUDE.md "reversing a recorded decision is the owner's" and the review's own escape clause, STOP and flag, do not silently choose):
- The `ManageFavourites` route stays REGISTERED in DashboardStack this phase. The shipped favourites home-screen widget's empty-state "Choose favourites" tile deep-links `orbit://favourites` → a RESET onto `[Home, ManageFavourites]` (`widget-render.tsx:549`; `widget-linking.ts:132-137`, WDG-02/03, node-tested; passed through `widget-quick-action-guard.ts:33`). Retiring the route requires re-targeting that live deep-link — where "Choose favourites" now lands, given the reorder screen is gone, is a product/behavior decision the owner owns, and it lives in the widget subsystem (outside this nav phase's scope). Removing the route without that decision would crash the widget tap (route-not-found).
- The FULL ADR-075 retirement — delete `ManageFavouritesScreen.tsx` + `favourites-reorder-logic.ts`; retire the `favourites-dao` rank-rewrite; re-point `dashboard-read.ts` (favourites branch :245 + `listFavouritesForReorder` :333), `widget-data.ts`, `sun-picker-read.ts:45`, `capture-read.ts:65-66`, and `merge-candidate-read.ts:29` (all verified `favourite_rank ASC` on disk this cycle) from `favourite_rank ASC` to Default ordering; and decide the `orbit://favourites` widget tap target — is a dedicated cross-subsystem effort (dashboard/widget/orrery data layer), NOT this nav phase. **Recommend the owner schedule it as its own phase/task.**

Net: this phase ships NO new favourite-rank ordering and removes both named user-facing entries; the residual (route registration + widget deep-link + the pre-existing rank reads in dashboard/widget/orrery/capture) is flagged for the owner, never silently reversed.

## Typing strategy (planner discretion — minimizes consumer churn while staying correct)

`types.ts` gains four per-tab param lists + `TabParamList` (via `NavigatorScreenParams`) + per-tab `CompositeScreenProps` helpers (e.g. `DashboardScreenProps`/`OrreryScreenProps` = `CompositeScreenProps<NativeStackScreenProps<ThatStackParamList,T>, BottomTabScreenProps<TabParamList>>` so a screen registered in a tab stack can also type a cross-tab `navigate("<OtherTab>",{screen,params})`). **`RootStackParamList` is retained as a back-compat combined alias** (the four per-tab lists merged) so the existing `RootStackScreenProps<T>` / `NativeStackNavigationProp<RootStackParamList>` consumers keep compiling for INTRA-stack navigation — they are NOT force-migrated. Each per-tab stack is `createNativeStackNavigator<ThatTabStackParamList>()` and registers only its subset (react-navigation permits registering fewer screens than the list declares).

**Container-level type safety (closes the tsc-blindness meta finding, HIGH #4):** `navigationRef` (linking.ts) is retyped from the merged alias to `NavigationContainerRef<TabParamList>`. The merged alias let ANY container-level `navigate`/`replace`/`reset` route name type-check regardless of owning stack — that is exactly what hid the birthday `navigate("Profile")`, the ShareIntent `navigate("Backup")`, and the merge `replace("Profile")` runtime crashes from `tsc`. With the ref TabParamList-typed, every container-level navigate/reset MUST use the nested `{screen,params}` form and a stray cross-stack route name fails `tsc`. All navigationRef consumers Plan 01 owns (notification-gate, widget-linking, linking.ts N1/N2, reset-intents) are reshaped to the nested form in the SAME task so `tsc` stays green at the end of Plan 01; the component-`navigation`-prop cross-tab sites (Resume prompts, ImportComplete, ContactProfile, MergeImpactSummary) are reshaped by Plan 03 (wave 2) using the composite helpers / navigationRef + reset-intents. Note: dual/tri-registered screens still resolve their intra-family navigates via each stack's identical family subset; the ref retype specifically hardens the CONTAINER-level class where the crashes lived.

**Compile-safety contingency (reviews cycle-4 actionable — codex rates HIGH "will not compile as written", cursor rates LOW "compiles, stays tsc-blind"; two of three lanes judge it compiles, so this is recorded as an EXPLICIT contingency, not a confirmed blocker).** The strategy above registers screens whose components are typed `RootStackScreenProps<T>` / `NativeStackNavigationProp<RootStackParamList>` into narrower per-tab `createNativeStackNavigator<ThatTabStackParamList>()` navigators. React-navigation's `<Stack.Screen component={…}>` type-checks the component's props against the owning stack's param list, so a `RootStackScreenProps`-typed screen registered in a narrower stack MAY fail `tsc` (the exact codex concern). **If `npx tsc --noEmit` fails on any such registration, the in-scope remedy is NOT an out-of-scope migration and NOT relaxing the acceptance criterion — the affected consumer screens ENTER Plan 01's scope and are retyped to their owning stack's composite/tab props** (e.g. `EditContactScreen` → `DashboardScreenProps<"Edit">`/`OrreryScreenProps<"Edit">` via the CompositeScreenProps helpers; `CropPhotoScreen` → the composite props for its three registrations Dashboard/Orrery/Settings; likewise `RestoreResultScreen`, `RestorePreviewScreen`, and any other screen `tsc` flags). Likely-affected set (the multi-registered / cross-tab-typed screens): the Profile contact-detail family (Profile, Edit, Compose, **CropPhoto** — now tri-registered), the merge cluster, ArchivedContactsScreen, RestorePreview/RestoreResult. The executor adds any screen `tsc` actually flags to Plan 01's file set, migrates its props to the composite helper, and RECORDS the final affected-screen list in 22-01-SUMMARY.md. `tsc`-green is Plan 01's acceptance bar; reaching it via composite-prop migration of the screens Plan 01 already registers is IN scope (it is the same registration work), not a scope escape. Because Plan 01 is wave 1 and these screens are also touched by later waves (e.g. EditContactScreen by Plan 03 wave 2), the wave order guarantees Plan 01's prop migration lands first with no parallel conflict.
