### A-WR-01: Replace-all permanently deletes the phone's Bin, but neither the people counts nor the confirm say so

**File:** `src/backup/restore-apply.ts:948-974` (`peopleCounts`). Consumers: `src/screens/backup-restore-logic.ts:325, 346, 417`.
**Issue:** `replaceAllReset` (`restore-apply.ts:1902-1933`) deletes every `contacts` row, including people in the phone's Bin. `peopleCounts` reads only `archived_at IS NULL` rows (`liveBefore`), so `removed` counts only live people the backup lacks. The Replace confirm says "This replaces the N contacts on this phone…", where N excludes the Bin. The result line then says "Contacts removed: X", which also excludes the Bin.
**Concrete failure:** The phone has 3 people in the Bin and the backup does not carry them. The user confirms Replace and sees "Contacts removed: 0", but those 3 people are permanently deleted. When no backup folder is set (`configured` is false at `:2111-2130`), no safety backup is taken, so the deletion cannot be undone.
D-59 asks for "a correct deletions line for Replace", and the Bin "never empties itself" (D-10 / 38.11 D-70). The only-live definition of `removed` is the planner's reading, not an owner ruling: the comment at `:91-98` cites only D-59 and D-140.
**Fix:** Count Bin people separately, from the same before-write read, and show the line only when N > 0, like D-140.
```ts
const binBefore = await exec.getAllAsync<{ uid: string }>(
  "SELECT uid FROM contacts WHERE archived_at IS NOT NULL",
);
// …
removedFromBin: replacing
  ? binBefore.filter((row) => !backupUids.has(row.uid)).length
  : 0,
```
Mention the Bin in the Replace confirm when the phone's Bin is not empty. The copy is the owner's at the device check.

### A-WR-02: Backup files are identified by the last segment of their URI, which cannot work on Google Drive (pre-existing; affects D-116, D-136, D-62)

**File:** `src/services/backup/backup-service.ts:396-398` (`ownedName`), `:449-457`, `:780-813`; `src/services/backup/saf-storage.ts:59-63` (`ownedAutomaticUris`, used by `BackupScreen.tsx:191`).
**Issue:** Every ownership, prune, collision and "kept backups" check uses `decodeURIComponent(uri).split("/").pop()` as the file name. This holds for `com.android.externalstorage.documents`, whose document ids are paths. Drive's DocumentsProvider uses opaque ids (`acc=1;doc=encoded=…`), which is why D-143 needs a native display-name lookup just to show the folder name. On Drive, then:
- `isOwnedAutomaticBackupName` never matches, so automatic backups are **never pruned**.
- A passphrase change (`createAutomaticBackupReencryptionService`) finds no sources. It returns `{status:"changed", reencryptedCount:0}` and makes the new passphrase active while every existing backup stays under the old one. A user who changes a compromised passphrase is told it worked.
- The D-62 hero "kept backups" count reads 0.
- New in 38.12: the D-136 collision suffix relies on the same listing. Old names had millisecond precision and never collided; the new minute-precision names can. For example, "Back up now" and the launch sweep in the same minute both write `orbit-auto-…-0930.json`.

The owner's backups go to Drive (D-143, "all my backups go to drive").
**Fix:** List children as `{ uri, name }` pairs, taking the name from `DocumentsContract.Document.COLUMN_DISPLAY_NAME` (or `DocumentFile.getName()`), ideally in the same native module that 38.12-26 extends for D-143. Make `ownedName` read that name, not the URI. Before changing anything, confirm on device with a Drive folder: `readDirectoryAsync` output, then whether the hero count and pruning work. This is a correctness fix, not a decision reversal.

### A-WR-03: Undo of a Bin Restore re-dates the Bin entry, so the original "moved to the Bin" date is lost

**File:** `src/db/contacts-dao.ts:1039-1072` (`archiveContactCore`), called from `src/screens/ArchivedContactsScreen.tsx:290-296` (`undoRestore`).
**Issue:** `restoreContact` nulls `archived_at`. Undo then calls `archiveContact(exec, id, localDateTime())`, which writes a new `archived_at = now`. The date the person first went to the Bin is permanently overwritten. That is the date D-40 shows on the Bin row, and the list sorts by it (`listArchived ORDER BY archived_at DESC`), so the person also jumps to the top of the Bin. This Undo does not return the data to its earlier state.
**Fix:** Before the restore, capture the row's `archived_at`, and have Undo write that value back through a core that takes it as a parameter, keeping the `archived_at IS NULL` precondition and the event:
```ts
export async function archiveContactCore(exec, id, now, archivedAt = now) {
  const result = await exec.runAsync(
    "UPDATE contacts SET archived_at = ?, modified_at = ? WHERE id = ? AND archived_at IS NULL",
    [archivedAt, now, id],
  );
  // …
}
```

### B-CR-01: Missing-source Unlink / Link to a different phone contact act on the wrong link

**File:** `src/screens/ReconcileDetailScreen.tsx:278-296` (unlink), `:297-344` (relink); `src/db/reconcile-relink-dao.ts` (`relinkExternalSource`, `unlinkExternalSource`)

**Issue:** Both actions take `const staleLink = scan?.links[0]`. That is the first active link by id, not a missing one. The screen already holds `scan.missingLinkIds`, which 38.12 added, but neither action uses it. Failure cases:
- A contact has link L1, which still reads, and link L2, which is gone from the phone. The card is a missing-source card. "Unlink from phone contact" retires L1, the healthy link, and leaves L2 active and missing, so the card comes back on the next check. "Link to a different phone contact" also retires L1 and attaches the newly picked contact in its place.
- With D-45's "kept as is" memory, a contact can hold an older kept-missing link L1 and a newly missing link L2. Both actions again act on L1.

Both DAO writes are committed and correct for the id they are given, so the wrong link is permanently deactivated. This code predates 38.12, but the phase built the multi-link missing-source handling (kept links stay active), which makes this state more common.

**Fix:**
```ts
// ReconcileDetailScreen.tsx
const staleLinkId = scan?.missingLinkIds[0];
if (staleLinkId == null) return;
await unlinkExternalSource(getExecutor(), { staleLinkId, now: localDateTime() });
// relink: relinkExternalSource(..., { staleLinkId, ... })
```
When there are several missing links, either act on each one or show which phone contact each action refers to. Add a two-link test where `links[0]` reads and `links[1]` is missing.

**Fix:** fixed in f76a4a8a (Unlink retires every missing link; relink replaces the first missing link; two-link tests)

### B-CR-02: D-45 memory on contacts with several links: reviews are written to some links but read last-link-wins, so the same difference is asked again forever

**File:** `src/db/reconcile-memory-read.ts:100-119` (`Object.assign({}, ...perLink)`); `src/logic/reconcile-selection.ts:49-57` (`reviewedLinkIds`); `src/db/reconcile-apply.ts:151-171`; `src/screens/ReconcileDetailScreen.tsx:376-380` (`recordReviewedPhoto`)

**Issue:** `loadReviewMemory` merges each link's snapshots with `Object.assign`, so the highest link id wins for every family. A `null` value also overrides. A review is written only to `reviewedLinkIds(diff, field)`, meaning the links that contributed an option for that field. Diff-wide `diff.sourceLinkIds` is used only when the field has no options. Any link that has memory for a family but no current option for it keeps its stale value, and that stale value wins the merge on every later scan.

Concrete path, reachable through D-99 (Merge from a Profile):
1. Contact A is linked to L1 with phone photo fp1. Import recorded `photo = fp1` (D-132).
2. Contact B is linked to L2. B's phone contact has no photo, but B has an Orbit photo. "Keep Orbit" on removed-from-source wrote `L2.photo = ""`.
3. Merge B into A. The survivor now has L1 and L2.
4. The next check sees sources L1 = fp1 and L2 = none, so the comparable is `fp1`. The merged memory is `""` because L2 wins. The result is a conflict card.
5. The user picks Keep Orbit. Memory `fp1` is written to L1 only, because only L1 has the option. The merged memory is still `""` from L2, so the card returns on every check.

Birthday and name behave the same way, for example when a phone contact's birthday is later removed on one link. This defeats D-45 ("Reviewed, unchanged differences never come back"), the phase's headline defect fix.

**Fix:** Write review memory to every link that was read for the card, not only the option links:
```ts
function reviewedLinkIds(diff: ReconcileDiffResult): number[] {
  return [...(diff.sourceLinkIds ?? [])];
}
```
Do the same for `pendingPhoto.sourceLinkIds` in `recordReviewedPhoto`. Alternatively, have `loadReviewMemory` ignore memory on links that currently provide no option for that family. Add a test: two links with divergent memory, review once, rescan, expect no field.

### B-WR-04: D-144: unticking a pre-ticked number makes a number the person never tapped primary

**File:** `src/screens/ReconcileDetailScreen.tsx:599-614`; `src/logic/reconcile-selection.ts:138-143`; `src/db/reconcile-apply.ts:325-329`

**Issue:** Any tap on a phones/emails row adds the family to `tappedFamilies`, and that includes unticking. `electPrimary` then promotes `sourceMethods[0]`, the first remaining pick in display order, which is sorted by canonical value.

Example: Orbit's primary is Mobile P0, and the phone offers A and B, both pre-ticked. The person unticks B because they don't want it. A becomes primary even though they never tapped A. D-144 says "only an explicit user tap changes Orbit's primary".

A related trap: because the defaults are pre-ticked, tapping the number you want unticks it. There is then no way to add both A and B with B as primary. The 38.12-20 SUMMARY records "tick, untick or Orbit" as counting as a tap, but D-144 is about choosing a value.

**Fix:** Track the tapped option ids, not just the family. Elect only an option the person explicitly ticked: the last or first one they ticked, never an untapped default. If the only taps were unticks, keep Orbit's primary. This enforces D-144 and reverses nothing. The display-order rule comes from planner convergence c3 D-1, not from the owner.

**Fix:** fixed in 30a1a8ae (D-148: only the person's own latest tick elects; unticks never; untick+re-tick picks which added number is main; "Becomes the main number" marker and a hint line)

### B-WR-05: Check linked contacts can delete and tombstone existing Orbit methods ("nothing is deleted" is not guaranteed)

**File:** `src/db/reconcile-apply.ts:296-336`; `src/logic/reconcile-diff.ts:451-464` (`buildDesiredMethodList`); `src/db/contact-methods-dao.ts:133-143, 199-223`

**Issue:** `current` is built from `buildDesiredMethodList(seeded, additions, effectivePhoneRegion)`, which keeps only the first method per type and canonical value. `applyContactMethodDiffCore` likewise drops colliding drafts and then deletes and tombstones every seeded row missing from `current`.

Two stored methods can be distinct under the region they were written with but collide under today's region (`override ?? device`, D-45). One example is a national number stored while no region was known plus the same number in E.164, after the user sets a region override. Two unparseable methods with the same trimmed raw value also collide. In either case, applying any phone or email addition silently deletes one of the seeded rows. ## Warnings

### D-WR-01: Custom field text with `$` corrupts the prompt Orbit sends (String.replace patterns)

**File:** `src/ai/prompt-template.ts:544` (`const prompt = scaffold.replace(FIELD_MARKER, fieldsBlock);`)

**Issue:** `fieldsBlock` holds user-entered custom-field labels and values. `sanitizeValue` neutralizes only `=`. With a string as the replacement, `String.prototype.replace` interprets the special patterns `$$`, `$&`, `` $` `` and `$'`. I ran a throwaway vitest probe (since deleted; the tree is clean) with a shared field `Budget = "costs $$5 and $' end"`:
- The line sent was `"- Budget: costs $5 and "`. The user's `$$` became `$`.
- `$'` spliced the whole remainder of the prompt into the field: the `===== END DATA: CONTACT CONTEXT =====` fence, the memory, style and personalization blocks, then the real remainder again.
- `` $` `` would splice in the whole instruction and contact header the same way.

The preview is byte-identical, because it is the same string. D-27 "preview = payload" therefore still holds, but what both show and send is not the user's data. It also breaks the DATA-fence structure that the T-14-09 injection defence relies on. No new data leaves the device: the spliced text is already in the payload. This bug predates the phase, but it sits on the one egress builder this lane covers.

**Fix:** use a replacer function, which does no pattern expansion:
```ts
const prompt = scaffold.replace(FIELD_MARKER, () => fieldsBlock);
```
Also add a `prompt-template.test.ts` case with `$$`, `$&` and `$'` in a field label and value.

### D-WR-02: Review matches bulk bar sits under the system navigation bar (no bottom inset)

### D-WR-03: Folder-name fallback shows a Google Drive document id as the folder's "real name" and stores it

**File:**
- `src/screens/backup-settings-logic.ts:582-598` (`backupFolderDisplayName`)
- Persisted through `src/services/backup/backup-now.ts:213` (`backupFolderName: deps.folderName(directoryUri)`)
- Shown in `BackupScreen.tsx` (hero `keptBackupsLine`) and `BackupSettingsScreen.tsx:443-445`

**Issue:** the derivation assumes `<volume>:<path>` tree ids. A Google Drive SAF tree id decodes to the form `acc=1;doc=encoded=AbCd…` with no colon. The function then returns that whole opaque string as the "last segment", so the hero reads "3 backups kept in acc=1;doc=encoded=…". The owner's own setup hits this ("all my backups go to drive", D-143). D-143's native lookup (38.12-26, not yet executed) falls back to this function whenever the lookup fails, so the fallback has to be safe on its own. The value is also written to `backup_folder_name` whenever a folder is chosen.

**Fix:** derive a name only when the decoded id has the device-storage `volume:path` shape and a non-empty path segment. Otherwise return `BACKUP_FOLDER_FALLBACK_NAME`. For example:
```ts
if (colon === -1) return BACKUP_FOLDER_FALLBACK_NAME; // provider-opaque id (Drive etc.)
```
Add a test with a Drive tree URI. This belongs in the not-yet-executed 38.12-26, which already owns D-143.
