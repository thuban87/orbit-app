# Cross-AI Plan Review — Phase 18.2

## Consensus Summary

Two source-grounded reviewers (Codex, Cursor) independently assessed the ten-plan Phase 18.2
set against the live v10 codebase. Both verified the plans are well decomposed
(schema → transactional write DAO → Bound-aware SQL read owners → nullable-cadence consumers →
headless notification/widget effects → forms/profile UI → backup v3 → verification + device UAT),
correctly grounded in the actual on-disk baseline (`TARGET_VERSION = 10`, migrations through
`010`, methods already normalized, cadence consumers currently assuming non-null `interval_days`),
and that all four settled owner decisions are placed in the right plans. The reviewers diverged on
one material point — Codex found a HIGH implementation gap in Plan 06 Task 4 (notification
body-tap fail-closed) that Cursor did not; the aggregator verified it against source and confirms
Codex is correct. The remaining agreed issues are specification seams, not architectural mistakes.

Overall phase risk: **MEDIUM–HIGH** until the Plan 06 Task 4 notification-gate ownership gap is
closed; the other plans are well scoped.

### Agreed Strengths
- Migration 011 (Plan 01) correctly treats the change as a full contacts parent-table rebuild
  (v9's `interval_days` is `NOT NULL`, `009-contact-method-normalization.ts:16-35`), expands the
  FK-child inventory beyond `EXPECTED_CONTACT_CHILDREN` to include `contact_methods` and
  `external_contact_links`, adds integer-typed cadence CHECK plus the one-way trigger, and proves
  preservation via `PRAGMA table_info`/`sqlite_master` comparison (both reviewers).
- Read-owner centralization (Plan 03): lifecycle eligibility is gated at SQL read owners rather
  than screen filters; nullable-cadence arithmetic hazards (`status.ts:59` `PROGRESS_SQL`,
  `STATUS_SCAN` in `queries.ts:26-29`) are correctly identified (both).
- Explicit-AI nullable-cadence bug is precisely located: `ai-context-read.ts` currently
  fabricates `intervalDays: 1` when impact is null (`ai-context-read.ts:228-238`); Plan 04's
  tagged unavailable-intensity result prevents null arithmetic and PII egress (both).
- Ring-seq Guard 2/Guard 3 parity (Plan 05) and widget stale-Compose fail-closed (Plan 06 Task 3)
  are real seams correctly targeted (`ring-seq-dao.ts:77-95`, `widget-linking.ts`) (both).
- Backup v3 (Plan 09) correctly targets the real gaps: v2 wire version (`backup/types.ts:14`),
  export omitting `trackingEnabled` (`export-manifest.ts:48`), and the unconditional restore
  cadence upsert (`restore-apply.ts:148`); the pre-transaction COALESCE merge planner implements
  settled decision #3 (both).
- Plan 10's consumer ledger as a committed CI test (not Markdown-only) is the right backstop for
  the "grep misses import-reached fragments" gap (both).

### Agreed Concerns
- **Plan 08 Edit-vs-Profile lifecycle effects (MEDIUM, both).** Task 1's acceptance requires an
  Edit save that flips `tracking_enabled` to fire the same reconcile-schedule + widget-refresh
  effects as the profile Bind/Unbind seam, but Task 1's `<action>` does not require routing
  `EditContactScreen`'s existing ad-hoc `reconcileSchedule`/`notifyWidgetDataChanged`
  (`EditContactScreen.tsx:369-389`) through the `bindWithLifecycleEffects`/
  `unbindWithLifecycleEffects` owners. Risk: two divergent lifecycle-effect implementations.
- **Plan 06 frontmatter `tasks: 3` (LOW, both).** The metadata declares three tasks but the body
  contains four (Tasks 1–4). Documentation inconsistency.

### Divergent Views
- **Plan 06 Task 4 notification body-tap fail-closed.** Codex rated this **HIGH** — the live-Bound
  guard cannot be delivered within Task 4's declared files. Cursor rated Task 4 "correctly planned"
  and did not flag the file-ownership gap. **Aggregator verification against source confirms
  Codex.** `resolveNotificationNav()` is pure and synchronous with no DB access
  (`notification-nav.ts:67-107`); the body-tap intent is applied by `applyBodyNav` in
  `notification-gate.tsx:82-96` (fed by the warm-tap park `setPendingBodyData(data)` at :133 /
  flush at :143, and cold-start at :169). A live-Bound lookup is an async DB read
  (`contact-read.ts` exposes only async lookups), so implementing the guard forces a change to
  `notification-gate.tsx` — which is absent from Plan 06's `files_modified` (line 7) and Task 4's
  `<files>` (line 92) and verification set (line 100). The `notification-actions.ts` half
  (ACTION_MARK) is feasible in-file because `handleNotificationAction` already `await`s
  `openAndMigrate()`; only the nav/body-tap half is unowned.
- **Plan 09 restore-staging ordering.** Codex raised a MEDIUM that lifecycle merge planning might
  run after `stageCandidates`, leaving staged photo artifacts on a conflicted restore.
  **Aggregator verification does not sustain this:** in `restore-apply.ts`, `reconcileEntity`/plan
  building and the `incompatible-destination` early return already precede `stageCandidates`, and
  Plan 09 Task 2 explicitly computes the retained cadence "before the upsert" (line 75). The merge
  planning is correctly sequenced before staging. Not actionable.
- **Plan 04 shared unavailable-intensity type.** Both reviewers suggested pinning the
  `{ available: false }` contract in one shared exported module. Plan 04 Task 1 already directs
  pinning the exact contract in `src/services/impact.ts` so the profile view-model (18.2-08) and
  `ai-context-read` (Task 2) consume the same shape (line 52). Largely addressed; optional
  refinement only.

The phase is well decomposed around schema → write/read owners → proactive consumers → UI/backup → end-to-end validation. ## 18.2-01 — Lifecycle schema migration

**Summary:** Strong migration plan. It accurately treats v11 as a parent-table rebuild, which is necessary because v9’s `contacts.interval_days` is `NOT NULL` ([009-contact-method-normalization.ts:16-35](src/db/migrations/009-contact-method-normalization.ts:16)).

**Strengths**

- Correctly expands migration 009’s child inventory, which currently includes six direct contact FK children ([009-contact-method-normalization.ts:7-14](src/db/migrations/009-contact-method-normalization.ts:7)).
- The proposed preservation proofs go materially beyond the existing `PRAGMA foreign_key_check` safeguard ([009-contact-method-normalization.ts:252-255](src/db/migrations/009-contact-method-normalization.ts:252)).

**Concerns**

- **MEDIUM:** The plan says it will preserve “indexes and triggers” for every rebuilt child, but the current migration 009 only explicitly recreates `idx_interactions_recency` after rebuilding children ([009-contact-method-normalization.ts:213-223](src/db/migrations/009-contact-method-normalization.ts:213)). - **LOW:** [reserved-columns.ts:37-38](src/db/reserved-columns.ts:37) still lists retired `phone`/`email`, despite v9 having removed them from `contacts` ([009-contact-method-normalization.ts:16-35](src/db/migrations/009-contact-method-normalization.ts:16)). The plan correctly fixes this, but its “source of truth” commentary will also need revision.

**Suggestions**

- Require migration code to snapshot `sqlite_master` rows for child indexes/triggers before the rebuild and compare them after, rather than maintaining a second hand-written expected list.

**Risk:** **MEDIUM** — parent rebuilds are inherently delicate, but the planned direct-child and metadata tests are proportionate.
