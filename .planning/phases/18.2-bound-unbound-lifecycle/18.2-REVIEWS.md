# Cross-AI Plan Review — Phase 18.2

## Consensus Summary

Both reviewers (Codex, source-grounded at `gpt-5.6-terra`; Cursor, source-grounded, model unrecorded) independently verified the plans against the on-disk repo and reached the same top-line verdict: the ten-plan wave decomposition is **architecturally sound** — lifecycle is correctly treated as a SQL-predicate concern gated at read owners rather than screen-level filtering, matching the existing never-contacted gating pattern — but the phase is **not executable as written** because of a small cluster of Wave-1/Wave-2 defects with irreversible-data risk. The overall risk rating from both reviewers is **HIGH until those are re-cut**, dropping to MEDIUM afterward.

### Agreed Strengths

- Bound/Unbound eligibility placed in SQL read owners (dashboard, orrery, notifications, digest, status), not UI filters — matches current independent-predicate architecture (`dashboard-read.ts`, `orrery-read.ts`, `decay-suppression.ts`).
- The nullable-cadence NULL-division hazard is correctly identified: `PROGRESS_SQL` divides by `interval_days` (`status.ts:59`) and `STATUS_SCAN`/`DECAY_ELIGIBLE_WHERE` have no Bound guard today; centralizing `tracking_enabled=1` at the owners is the right fix.
- The contacts-rebuild follows the proven migration 009 rename-rebuild-copy template (`009-contact-method-normalization.ts`) rather than inventing a new approach.
- Ring-sequence Guard 2/3 Bound predicate (`ring-seq-dao.ts:77-95`) is an easy-to-miss correctness fix that both reviewers flagged as necessary.
- Post-commit side-effect isolation in 18.2-06 (`unbindWithLifecycleEffects`) correctly avoids rolling back a committed lifecycle transition when notification/widget refresh fails.
- Backup parse-time pre-validation before the restore transaction is the right safety posture.

### Agreed Concerns (highest priority — raised by both)

- **HIGH — Migration 010 / user_version 10 collision.** Every plan still names the lifecycle migration `010-contact-lifecycle-schema.ts` at `v9→v10`, but 18.1 already shipped `010-contact-method-label.ts` at version 10 (`database.ts:33-45`, `010-contact-method-label.ts:14`). The runner selects migrations strictly above `PRAGMA user_version` (`runner.ts:43`), so a second v10 silently never runs. Must move to `011` / user_version 11 across all plan bodies, `TARGET_VERSION`, fixtures, and UAT text. *(This is the known pending re-cut recorded in 18.2-CONTEXT.md — both reviewers independently confirmed it against source.)*
- **HIGH — Contacts-rebuild child-FK inventory is incomplete.** Migration 009's `EXPECTED_CONTACT_CHILDREN` (`009-contact-method-normalization.ts:7-14`) covers six tables but not the post-009 children `contact_methods`, `external_contact_links`, `contact_method_provenance` (`009-...:225-249`). A contacts rebuild must retarget/defer FK for all of them; `foreign_key_check` alone does not prove indexes, triggers, or FK actions survived. Plan 01 must enumerate the full v11 child set (port/expand `assertExpectedChildren`).
- **HIGH — Aggregate create/edit DAO lifecycle ownership is unassigned.** `createContactFull`/`updateContactFull` require a positive `intervalDays` before opening a transaction and write no lifecycle field (`contacts-dao.ts:119-127,320-323,141`). Plan 08 requires Unbound create/edit with NULL cadence but no task's `<files>` block owns `contacts-dao.ts` or a DAO test, even though it appears in plan metadata. Codex rates this MEDIUM, Cursor rates it HIGH; recorded here at the higher severity.

### Divergent Views

- **Backup wire-format version (Plan 09).** Codex rates this **HIGH**: adding lifecycle fields changes the portable JSON shape, and `types.ts:13` explicitly instructs bumping `BACKUP_FORMAT_VERSION` (already `2`) whenever the shape changes, so lifecycle needs a **v3 format with a v2→v3 forward migration**. Cursor rates the same plan **acceptable**, viewing the additive v2 extension as "consistent with 18.1-04 layering." This is a direct product/compat-contract disagreement and should be resolved deliberately — it touches the forward-only backup compatibility boundary. Cursor does independently ask for a negative parse test (`trackingEnabled:1, intervalDays:null → BackupSchemaError`), which partially overlaps Codex's concern.
- **Plan 08 `depends_on: [18.2-04]`.** Cursor rates the missing dependency **HIGH** (profile intensity/gravity rendering needs Plan 04's nullable `ImpactInputs`); Codex rates the same gap **MEDIUM**, noting wave ordering already mitigates it in practice. Recorded at the higher severity.

- Add Plan 04 as a direct dependency of Plan 08.
