## 18.2-08 — Create/edit/profile lifecycle UI

### Strengths

- Correctly recognizes the aggregate writer as the core seam: it currently performs contact metadata, values, methods, and revision behavior inside one write transaction ([contacts-dao.ts](/home/bwales/projects/orbit-app/src/db/contacts-dao.ts:138)).

### Concerns

- **HIGH — The edit-save side-effect seam is not implementable from the produced APIs without either a duplicate transition or a new, unspecified API.** Plan 06 defines `bindWithLifecycleEffects`/`unbindWithLifecycleEffects` as wrappers around the lifecycle DAO. Plan 08 simultaneously requires `updateContactFull` to write the lifecycle transition as part of its one aggregate transaction. Calling a wrapper after that aggregate save would execute a second lifecycle DAO transition, causing an additional `modified_at`/revision write and potentially duplicate side effects. The current aggregate flow already owns its transaction and metadata update ([contacts-dao.ts](/home/bwales/projects/orbit-app/src/db/contacts-dao.ts:337)), while notification action flows show why duplicate writers are treated carefully ([notification-actions.ts](/home/bwales/projects/orbit-app/src/services/notifications/notification-actions.ts:99)).

### Suggestions

- Amend Plan 06 to export a DAO-free post-commit function, e.g. `applyLifecycleTransitionEffects(contactId, direction, deps)`, used by both lifecycle DAO wrappers and aggregate edit saves.
- Amend Plan 08 to require:
  1. aggregate save commits the lifecycle state once;
  2. it reports whether the lifecycle changed;
  3. the screen/service calls the DAO-free effects function exactly once after commit.
- Add a regression test proving an edit-triggered lifecycle transition increments `data_revision` exactly once while schedule reconciliation and widget refresh each run once.

### Risk assessment

**High** until the seam is specified — this is a cross-plan transaction/side-effect ownership conflict in a core lifecycle path.
