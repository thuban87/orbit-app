# Cross-AI Plan Review — Phase 18.2

## Consensus Summary

Both source-grounded reviewers (Codex, Cursor) agree the cycle-2 re-cut is convergence-ready in
its core: **all three LOCKED owner decisions are correctly implemented** (v3 backup format with a
v2→v3 forward migration in Plan 09; widget fail-closed scope with live-Unbound Profile-open in
Plan 06; restore merge-conflict `interval_days = COALESCE(incoming, local)` with modified-at
winner's `tracking_enabled` in Plan 09), and every cycle-1/2 HIGH finding is incorporated in plan
text (v11/migration-011 renumber, the corrected direct-vs-transitive FK child inventory, Bind/Unbind
symmetry, the aggregate-DAO lifecycle ownership, the consumer ledger, and the nullable-cadence TS
sweep). Consumer-ownership in Plans 03/05/08/10 lines up with the files that today carry no
`tracking_enabled` predicate.

The reviewers **converge on one remaining substantive gap**: Plan 09's declared file ownership does
not include the code that actually assembles the backup *export*. `src/backup/export-manifest.ts:48`
selects `c.interval_days AS intervalDays` but not `tracking_enabled`, and no plan in the phase lists
`export-manifest.ts` in `files_modified` (verified: grep across all ten PLAN.md files returns
nothing). Plan 09 Task 1's action text says "extend backup-schema/**export**/restore," but its
`files_modified` is only `[types.ts, backup-schema.ts, backup-schema.test.ts, restore-apply.ts,
restore-apply.test.ts]`. As written, a v3 export would emit contacts with no `trackingEnabled`,
silently dropping Bound/Unbound state and breaking the CDN-04 lossless round-trip that this phase's
success criterion 3 requires. Codex rates this **HIGH** (a production data-loss path, not a test
gap); Cursor rates the same defect **MEDIUM** (an executor might infer it from the action text). The
portable-settings *snapshot* half is owned by Plan 07 (`app-settings-dao.ts`, wave 4), but Plan 09's
backup round-trip runs in wave 3 — an ordering ambiguity both reviewers flag.

### Agreed Strengths
- The three locked owner decisions are wired into the correct plans and match live code seams
  (Codex, Cursor — both cite `widget-linking.ts:110`, `restore-apply.ts:148`, `types.ts:13/14`).
- Lifecycle filtering is placed at the SQL query owners, not screen filters, matching the real
  unfiltered consumers on disk (`dashboard-read.ts:142`, `ring-seq-dao.ts:78`, `orrery-read.ts:93`,
  `decay-suppression.ts:58`, `contact-status-read.ts:70`).
- Migration 011 correctly rebuilds `contacts`, enumerates the eight direct FK children, and leaves
  the transitive `contact_method_provenance` FK undisturbed (corrects the cycle-2 conflation).
- Bind/Unbind symmetry (`bindWithLifecycleEffects` + `unbindWithLifecycleEffects`) and the
  aggregate-DAO lifecycle ownership in Plan 08 close the cycle-2 asymmetry HIGH.

### Agreed Concerns
- **Plan 09 under-declares the export/settings touch points** (Codex HIGH / Cursor MEDIUM). The
  contact export SELECT in `export-manifest.ts:48` must gain `tracking_enabled AS trackingEnabled`
  (nullable `intervalDays` is already selected), and `export-manifest.ts` (+ its test) must be added
  to Plan 09's `files_modified` and verification — otherwise v3 export is not lossless.
- **Plan 09 (wave 3) vs Plan 07 (wave 4) settings ordering** (Cursor MEDIUM). The lifecycle
  portable-settings snapshot fields land in Plan 07's `app-settings-dao.ts`; a real DB
  export→parse→restore settings round-trip cannot pass in wave 3. Plan 09 should cross-reference /
  `depends_on` Plan 07 for the settings-snapshot portion, or sequence that round-trip test after 07.

### Divergent Views
- **Severity of the Plan 09 export-ownership gap.** Codex: HIGH — a concrete production path where v3
  backups omit `tracking_enabled` and the Unbound settings, a direct lossless-backup failure. Cursor:
  MEDIUM — the action text says "extend…export," so a careful executor could catch it, but
  `files_modified` (the executor's contract) is wrong. Adjudication: treated as **HIGH** here on the
  owner's risk-posture rule (do not down-scope a silent-data-loss path that fails a locked success
  criterion); the fix is small and mechanical regardless of label.

## Codex Review

## Summary

The re-cut is strong and covers the lifecycle state across the real query/write owners. The locked widget and restore decisions are implemented correctly in the plan. One **HIGH** issue remains: Plan 09 does not include the actual export/settings owners needed to make the v3 backup shape lossless.

## Strengths

- **Plan 01** correctly recognizes that v11 must rebuild `contacts` and preserve all direct FK children. The current v9 migration’s child inventory has six tables ([009-contact-method-normalization.ts](/home/bwales/projects/orbit-app/src/db/migrations/009-contact-method-normalization.ts:7)), while `contact_methods` and `external_contact_links` are additional direct children ([same file](/home/bwales/projects/orbit-app/src/db/migrations/009-contact-method-normalization.ts:226)). The plan explicitly expands this inventory and leaves the transitive provenance FK alone, matching the actual graph ([same file](/home/bwales/projects/orbit-app/src/db/migrations/009-contact-method-normalization.ts:244)).

- **Plans 03 and 05** put lifecycle filtering at SQL owners, not screen filters. This is necessary because the current dashboard, Orrery, favourites, status, digest, and ring-sequence reads all currently assume positive cadence and include all non-archived contacts; e.g. Orrery’s population is currently only `archived_at IS NULL AND last_contact IS NOT NULL` ([orrery-read.ts](/home/bwales/projects/orbit-app/src/db/orrery-read.ts:93)) and ring reorder repeats that predicate in both count and update guards ([ring-seq-dao.ts](/home/bwales/projects/orbit-app/src/db/ring-seq-dao.ts:77)).

- **Plan 04** correctly separates gravity from intensity. `ImpactInputs.intervalDays` is currently non-null ([impact-read.ts](/home/bwales/projects/orbit-app/src/db/impact-read.ts:23)) and AI always computes intensity from it ([ai-context-read.ts](/home/bwales/projects/orbit-app/src/db/ai-context-read.ts:224)); the proposed nullable/Bond-gated contract closes a real null-arithmetic risk.

- **Plan 06 implements the locked widget decision correctly.** Current widget navigation parses and dispatches Profile/Compose solely from the URI ([widget-linking.ts](/home/bwales/projects/orbit-app/src/navigation/widget-linking.ts:110)), so the planned post-parse live-state guard is the correct seam. It explicitly permits live-Unbound Profile navigation while failing closed for Compose/active actions.

- **Plan 08 correctly addresses the aggregate-write seam.** Existing aggregate writes require a positive cadence before opening a transaction ([contacts-dao.ts](/home/bwales/projects/orbit-app/src/db/contacts-dao.ts:119)) and unconditionally write `interval_days` on edit ([contacts-dao.ts](/home/bwales/projects/orbit-app/src/db/contacts-dao.ts:283)). The plan’s explicit Bound→Unbound dormant-cadence preservation test is needed and well targeted.

- **Plan 09 implements the locked restore-conflict rule in its intended location.** It identifies that the current restore upsert writes `interval_days` unconditionally ([restore-apply.ts](/home/bwales/projects/orbit-app/src/backup/restore-apply.ts:148)) and requires a pre-transaction planner to retain local assigned cadence while applying the winning lifecycle flag.

## Concerns

- **HIGH — Plan 09 cannot currently deliver lossless v3 export because it omits the actual export and portable-settings owners.** Its `files_modified` excludes `src/backup/export-manifest.ts`, `src/backup/export-manifest.test.ts`, and `src/db/app-settings-dao.ts`. But contact export is assembled by a SQL projection in [export-manifest.ts](/home/bwales/projects/orbit-app/src/backup/export-manifest.ts:48), which currently selects `intervalDays` but not `tracking_enabled`; without changing it, a v3 export silently drops lifecycle state. Likewise, the portable settings projection currently has no lifecycle settings ([app-settings-dao.ts](/home/bwales/projects/orbit-app/src/db/app-settings-dao.ts:128)) and its SQL does not select them ([app-settings-dao.ts](/home/bwales/projects/orbit-app/src/db/app-settings-dao.ts:377)). Plan 07 is later and does not declare backup/export tests. This violates CDN-04’s lossless round-trip goal despite a correct v2→v3 parser migration.

- **MEDIUM — Plan 09’s targeted verification does not run the export-owner suite.** Its named verification only runs schema/restore tests, while the actual export seam has its own test file ([export-manifest.test.ts](/home/bwales/projects/orbit-app/src/backup/export-manifest.test.ts:28)). A restore fixture can mask the fact that production export never emitted `trackingEnabled`.

- **LOW — Plan 10’s ledger should include the direct status fragment consumers as explicit inventory entries, not only broad `interval_days` matches.** `DECAY_ELIGIBLE_WHERE` embeds `PROGRESS_SQL` ([decay-suppression.ts](/home/bwales/projects/orbit-app/src/services/notifications/decay-suppression.ts:58)); so do `readOverlooked` ([digest-read.ts](/home/bwales/projects/orbit-app/src/db/digest-read.ts:109)) and direct status reads ([contact-status-read.ts](/home/bwales/projects/orbit-app/src/db/contact-status-read.ts:57)). The plan’s stated syntax inventory likely covers this, but naming these fragment consumers prevents an overly narrow ripgrep gate.

## Suggestions

- Amend **Plan 09** to own or explicitly depend on the required export/settings changes:
  - add `tracking_enabled AS trackingEnabled` to the contact export projection;
  - extend `PortableSettingsSnapshot`, `getPortableSettingsSnapshot`, portable-key validation, and restore patch mapping with `includeUnboundNeverContacted` and `birthdayUnboundEnabled`;
  - add `export-manifest.ts` and its test to the plan’s files and verification;
  - add a real DB export → parse → restore test for both Unbound lifecycle cells and both lifecycle settings.

- In **Plan 10**, enumerate `status.ts` fragment consumers by owner in the CI ledger, including notification suppression, digest overlooked, profile status, dashboard, and Orrery.

## Risk Assessment

**HIGH** until Plan 09 is amended. The lifecycle schema, consumers, widget behavior, and locked merge rule are well covered, but the current plan file boundary leaves a concrete production path where v3 backups omit `tracking_enabled` and the Unbound settings. That is a direct lossless-backup failure, not merely a test gap.
