# Cross-AI Plan Review — Phase 18.2

Both reviewers had full repo access and cited concrete `file:line` evidence throughout;
their findings were re-verified against the on-disk source before this summary was written.
Three product/risk decisions were declared settled and out of scope (backup v3 + v2→v3
migration; widget fail-closed scope; restore merge dormant-cadence rule) — reviewers assessed
only that the plans implement them correctly, and both found them faithfully implemented.

## Consensus Summary

The ten-plan wave structure is architecturally sound and unusually well grounded in the actual
v10 codebase: it correctly targets the real migration runner, query owners, backup format, and
the phase's dependency ordering (schema → transactional writes → SQL-owner read gating →
nullable-cadence consumers → headless effects → UI/settings → backup v3 → validation + device
UAT). Both reviewers independently reach a MEDIUM-to-MEDIUM-HIGH verdict and converge on one
material gap that blocks the stated phase goal, plus a cluster of smaller specification gaps.

The single agreed, verified gap that warrants a plan change is **notification ingress**: the
phase goal is explicitly "across every proactive surface — dashboard, Orrery, Never Contacted,
notifications, widgets, favourites, AI," and the widget surface is guarded to fail closed on
active-cadence actions, but **no plan owns `notification-nav.ts` or `notification-actions.ts`**.
A decay notification delivered while a contact is Bound survives an Unbind (reconciliation
cancels only the *scheduled* request, not an already-delivered one), and its tap/quick-actions
remain unguarded: `notification-nav.ts:90-97` routes a decay tap to Compose unconditionally, and
`notification-actions.ts` `ACTION_MARK` writes a touchpoint via `recordTouchpoint` with no
lifecycle check. This is the same active-cadence-action class the widget guard deliberately
closes — an asymmetry that Plan 10's own UAT codifies (it tests "stale widget quick actions fail
closed" but not stale notification taps). Cursor rated this HIGH; source verification confirms an
unguarded active-cadence write path on a surface the phase goal names explicitly.

The remaining concerns are specification/coverage gaps rather than design errors: an
integer-storage hole in the v11 cadence CHECK, an underspecified birthday-notification settings
read, an Edit-initiated lifecycle-effects seam that is not explicitly tested, an "intensity
unavailable" contract that is not pinned, and a portable-settings round-trip that Plan 09 depends
on but Plan 07 does not assert.

### Agreed Strengths
- **Forward-only migration discipline (Plan 01).** Both reviewers confirm the app is at v10
  (`src/db/database.ts:45`) and that adding migration 011 (rather than editing 009/010) with a
  full-transaction rebuild is correct; the expanded FK-child inventory beyond
  `EXPECTED_CONTACT_CHILDREN` to include `contact_methods` and `external_contact_links`
  (`009-contact-method-normalization.ts:7-14` vs `:225-248`) is warranted.
- **Bound filtering at SQL owners, not UI (Plans 03–07).** Dashboard, Orrery, notifications, and
  widgets each have dedicated query owners (`src/db/dashboard-read.ts:215-250`,
  `src/db/orrery-read.ts:87-99`, `src/services/notifications/decay-suppression.ts:58-62`); pushing
  the `tracking_enabled = 1` predicate to the owners avoids headless/UI disagreement.
- **Nullable-cadence hazard correctly isolated (Plans 04, 05, 10).** Both confirm `PROGRESS_SQL`
  divides by bare `interval_days` (`src/db/status.ts:59`) and that the ring-seq reorder guards
  (`src/db/ring-seq-dao.ts:77-95`) need the same Bound predicate on both count and update legs.
- **v3 backup direction is correct (Plan 09).** Current format is v2 (`src/backup/types.ts:14`),
  parsing chains explicit forward migrations (`src/backup/backup-schema.ts:274-285`), and export
  currently omits lifecycle state (`src/backup/export-manifest.ts:48`) — the v2→v3 migration and
  pre-transaction merge planner are correctly targeted.
- **Enforceable consumer ledger (Plan 10).** A CI-enforced `lifecycle-consumer-ledger.test.ts`
  over a Markdown table, plus a nullable-cadence TypeScript-contract sweep that explicitly names
  `ImpactInputs.intervalDays` and `ContactEditRow.interval_days`, closes the "grep misses the
  fragment reached via import" hole (verified present at 18.2-10-PLAN.md:61).

### Agreed Concerns
- **Notification ingress unowned (HIGH).** Raised most sharply by Cursor and verified: no plan
  guards delivered-notification taps or headless mark/snooze actions for a now-Unbound contact.
  See Current HIGH below.
- **Birthday-notification settings read is underspecified (MEDIUM).** Both flag that Plan 06 says
  to "thread" `birthday_unbound_enabled` to eligibility (18.2-06-PLAN.md:53) but does not name the
  authoritative read seam; `getAppSettings` has no lifecycle fields in its projection today
  (`src/db/app-settings-dao.ts:287-343`).

### Divergent Views
- **v11 cadence CHECK integer enforcement.** Codex rates the missing `typeof(...)='integer'`
  guard HIGH ("release-blocking"); Cursor does not raise it. On verification the practical risk is
  lower than HIGH: the constraint text is `CHECK (interval_days IS NULL OR interval_days > 0)`
  (18.2-01-PLAN.md:83), and every app write path goes through the DAO integer guard
  (`src/db/contacts-dao.ts:319-325`) — the pre-v11 `INTEGER NOT NULL` column relied on the same
  DAO for integer-ness, so v11 does not *regress* the invariant. It is a worthwhile
  defense-in-depth strengthening (free to add now, permanent once shipped), classified below as an
  actionable non-HIGH rather than a blocker.
- **`readOverlooked` Bound predicate.** Cursor rates this HIGH as a risk that it "must not be
  dropped during execution." On verification it is **already owned**: Plan 03 Task 2 explicitly
  says "Add the Bound predicate to digest-read's active-orbit/overlooked projections"
  (18.2-03-PLAN.md:69), with `digest-read.ts`/`.test.ts` in `files_modified`. It is a genuine
  correctness risk in the *current* code (`src/db/digest-read.ts:110-123` has no lifecycle filter)
  but the plan already covers it, so it warrants execution vigilance, not a plan change.

## Codex Review

# Review: Phase 18.2 Bound/Unbound Lifecycle

## Summary

The plans are unusually well grounded in the existing codebase: they correctly target the actual v10 baseline, query owners, migration runner, and backup flow. They cover the settled v3 backup format, widget guard boundary, and dormant-cadence restore rule. Two material gaps remain: v11's proposed SQL constraint does not enforce the repository's integer-day cadence invariant, and lifecycle changes made through Edit lack an explicit lifecycle-effects integration/test path equivalent to Profile Bind/Unbind.

## Strengths

- **Plan 01 correctly follows the forward-only migration architecture.** The real app registers migrations centrally and is currently at v10 (`src/db/database.ts:45-58`); the runner wraps each migration and `PRAGMA user_version` update in one transaction (`src/db/migrations/runner.ts:47-66`). Adding 011 rather than changing 009/010 is correct.

- **Plan 01 correctly recognizes that `contacts` rebuilds must preserve dependent tables, not merely pass `foreign_key_check`.** Migration 009 already rebuilds `contacts` and six direct FK children (`src/db/migrations/009-contact-method-normalization.ts:7-14`, `209-223`), while `contact_methods` and `external_contact_links` are additional direct children created later in the same migration (`225-248`). The plan's broader inventory and per-child proof are warranted.

- **Plans 03–07 put Bound filtering at SQL owners rather than UI filters.** Current dashboard branches are independent predicates (`src/db/dashboard-read.ts:215-250`), Orrery has its own population owner (`src/db/orrery-read.ts:87-99`), notifications compose a dedicated eligibility fragment (`src/services/notifications/decay-suppression.ts:58-62`), and widgets derive from favourite reads. The planned owner-level changes avoid headless/UI disagreement.

- **Plan 03 preserves the intended search distinction.** Existing dashboard search intentionally relaxes to archived-only (`src/db/dashboard-read.ts:215-225`), and the UI contract explicitly permits neutral Unbound search results while normal dashboard population remains Bound-only. This is the correct place to carry `trackingEnabled` and null active-card chrome.

- **Plans 04 and 10 correctly identify nullable-cadence hazards.** `PROGRESS_SQL` divides directly by `interval_days` (`src/db/status.ts:59`), and the current status reader only protects never-contacted contacts (`src/db/contact-status-read.ts:70-87`). The planned Bound-aware impact/AI contracts and consumer ledger directly address a real propagation risk.

- **Plan 05 correctly protects the Orrery reorder seam.** Both the current count guard and scoped update use the orbiting predicate (`src/db/ring-seq-dao.ts:77-95`), so adding the same Bound condition to both is necessary; changing only the read would make a contacted Unbound row cause reorder failures.

- **Plan 09 correctly uses a new v2→v3 wire migration.** The current format is v2 (`src/backup/types.ts:14`) and parsing already chains explicit forward migrations (`src/backup/backup-schema.ts:274-285`). Export currently includes `intervalDays` but omits lifecycle state (`src/backup/export-manifest.ts:48`), so adding `trackingEnabled` to both export and validation is necessary.

## Concerns

- **HIGH — Plan 01's proposed v11 cadence CHECK permits fractional SQLite values, contradicting the established integer-day contract.** The plan specifies `CHECK (interval_days IS NULL OR interval_days > 0)`. SQLite `INTEGER` affinity does not itself guarantee an integer storage class, while the application DAO rejects non-integers before every create/edit (`src/db/contacts-dao.ts:119-126`, `319-325`) and backup parsing does the same (`src/backup/backup-schema.ts:164-166`). Direct SQL could therefore insert or update a Bound row to `1.5`, permanently weakening the schema invariant that the plan says it is making durable. *(Planner note: verified — the CHECK text is at 18.2-01-PLAN.md:83. Severity re-assessed to actionable-non-HIGH: no app write path reaches raw SQL, and the pre-v11 `INTEGER NOT NULL` column relied on the same DAO guard, so this is a defense-in-depth strengthening, not a regression.)*

- **MEDIUM — Plan 08 allows Edit to perform Bound↔Unbound transitions but does not explicitly route that path through, or test it against, the lifecycle-effects service.** Existing Edit commits `updateContactFull` and separately fires schedule reconciliation/widget refresh (`src/screens/EditContactScreen.tsx:352-389`). Plan 08 adds lifecycle state to that aggregate update, while its explicit `bindWithLifecycleEffects` / `unbindWithLifecycleEffects` integration is limited to Profile actions. This creates two lifecycle-transition implementations with different error/sequencing coverage and risks later drift.

- **MEDIUM — Plan 06's notification birthday policy needs an explicit atomic settings/read contract.** The current birthday candidate read returns all non-archived birthday contacts without consulting settings (`src/db/notification-read.ts:89-97`), and `getAppSettings` currently has no lifecycle fields in its typed projection (`src/db/app-settings-dao.ts:287-343`). Plan 06 says to "thread" the setting, but does not state whether the candidate query joins/subqueries `app_settings`, whether the scheduler reads it once per reconciliation, or how missing `id=1` fails. Plan 07 defines this discipline for Never Contacted, but not Plan 06's birthday path.

- **LOW — Plan 03 redundantly says it will add method projections to `contact-read`, although normalized method groups already exist.** `ContactForEdit` already returns grouped methods (`src/db/contact-read.ts:144-153`, `195-203`). The lifecycle addition should be narrowly specified as adding `tracking_enabled`/nullable cadence to the relevant header/edit contracts, to avoid unnecessary reshaping of the Phase 18.1 method read.

## Suggestions

1. **Plan 01:** change the new cadence CHECK to enforce SQLite integer storage as well as positivity, e.g. conceptually:

   ```sql
   CHECK (
     interval_days IS NULL OR
     (typeof(interval_days) = 'integer' AND interval_days > 0)
   )
   ```

   Add direct-SQL tests for fractional values on both Bound and Unbound rows, plus rollback preservation.

2. **Plan 08:** require Create/Edit lifecycle transitions to use a single lifecycle-transition orchestration seam, or explicitly test Edit's existing post-commit reconciliation/widget path for Bound→Unbound and Unbound→Bound. Assert DAO success precedes effects and that effect failure cannot roll back or repeat the durable save.

3. **Plan 06:** specify one authoritative birthday-notification eligibility read that incorporates `birthday_unbound_enabled` from the singleton settings row, with a test for missing/corrupt `app_settings.id=1` matching `getAppSettings`' loud-failure behavior (`src/db/app-settings-dao.ts:303-305`).

4. **Plan 03:** narrow Task 1 wording from "extend ... with method projections" to "preserve existing method projections and add lifecycle fields," with a regression assertion that no scalar `phone`/`email` read is reintroduced.

## Per-plan assessment

| Plan | Assessment |
|---|---|
| 01 | Strong migration/preservation design, but should strengthen the fractional-cadence SQL CHECK. |
| 02 | Correctly separates named Bind/Unbind operations from cadence nullability and updates Capture's Bound create contract. |
| 03 | Correct query-owner placement; dashboard search/neutral rendering distinction is aligned with the UI contract. |
| 04 | Correctly isolates nullable-cadence impact and explicit-AI behavior after query owners stabilize. |
| 05 | Correctly handles active Orrery/picker exclusion and the ring-sequence guard parity. |
| 06 | Strong post-commit effects and widget guard plan; birthday eligibility needs a more concrete settings-read contract. |
| 07 | Comprehensive UI/settings implementation, including the shared Never Contacted list/count policy and neutral Unbound presentation. |
| 08 | Covers the form/profile lifecycle UX, but needs Edit-transition effects ownership/testing. |
| 09 | Correct v3 wire-format direction and settled merge conflict behavior; validation-before-transaction is well targeted. |
| 10 | Appropriate final consumer ledger, full regression gate, and device upgrade/UAT checkpoint. |

## Risk Assessment

**Overall: Medium.** The phase design is coherent and has unusually strong migration, query-owner, backup, and UAT coverage. The v11 fractional-cadence constraint is worth strengthening while the migration is being written (permanent once shipped); the Edit lifecycle-effects seam is a meaningful cross-surface consistency risk but is straightforward to close before execution.
