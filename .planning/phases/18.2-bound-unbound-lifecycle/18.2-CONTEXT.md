# Phase 18.2 — Bound/Unbound Lifecycle: Context

Phase 18.2 is the **cross-cutting lifecycle half** of the original Phase 18: establish the
independent Bound/Unbound contact lifecycle across every proactive surface — dashboard, Orrery,
Never Contacted, notifications, widgets, favourites, and AI — without losing relationship history,
on top of Phase 18.1's normalized method model. It ships the **v11 pure-shape migration**.

**Depends on Phase 18.1** being executed and verified on-device first: 18.2's proactive surfaces and
Compose read the normalized **primary actionable method** that 18.1 creates, and v10 is a shape
change on the v9 table.

## Authoritative product source

`docs/dossier/18-contact-data-normalization.md` — **read in full.** The clusters that govern 18.2:
- **G** — Bound/Unbound lifecycle (existing contacts migrate Bound; unbinding preserves history).
- **H** — gravity independent of Bound state; intensity cadence-dependent.
- **I** — cadence nullability lifecycle (`interval_days = NULL` means never-assigned only; Bound
  requires positive cadence; once assigned, never cleared).
- **J** — Never Contacted (Unbound excluded by default; optional global include).
- **K** — favourites (Unbound not presented as favourite).
- **L** — notifications and birthdays (independent of `reminders_off`; birthday-for-Unbound global toggle).
- **M** — dedicated Unbound screen; dashboard/Orrery stay Bound-only.
- **N** — AI (explicit person-level allowed for Unbound; proactive cadence-driven excludes Unbound).
- **S** — widget / quick actions fail gracefully for now-Unbound targets.
- **R (lifecycle half only)** — backup carries Bound/Unbound state and dormant cadence.

Clusters **A–F, O, P, Q and the method half of R** govern **Phase 18.1** (the normalized model this
phase builds on) — read them to understand the substrate.

# Cross-AI convergence — cycle 1 owner decisions (2026-08-28)

These were surfaced during the cross-AI review (codex + cursor) and decided by the owner; they are **locked** for 18.2 execution and were baked into the plans this cycle:

- **[LOCKED] Backup format bumps to v3 (Plan 09).** Adding lifecycle fields (`tracking_enabled` + nullable cadence) changes the portable JSON wire shape, so per the `types.ts:13` bump-on-shape-change contract it ships as `BACKUP_FORMAT_VERSION = 3` with a new **v2→v3** forward migration (existing contacts default to Bound with their existing positive cadence). It is **not** an additive v2 extension. Rationale: 18.1's method normalization already bumped v1→v2 under the same rule; lifecycle is the next shape change.
- **[LOCKED] Widget fail-closed scope (Plan 06 Task 3).** A widget tap on a now-Unbound target **fails closed only for active-cadence actions** (Compose / quick-action); a plain **Profile-open still navigates** to the live Unbound contact, which remains a complete, viewable relationship record (dossier Cluster M). "Fail gracefully" (Cluster S) means degrade the action, not dead-end a valid record. Only genuinely missing/archived targets resolve to no navigation.
- **[LOCKED] Restore merge-conflict rule — retain dormant cadence (Plan 09, cycle 2).** When a modified-at-winning backup contact is Unbound with NULL cadence but the local row has a positive cadence, restore **never nulls the assigned cadence**: it applies the winner's `tracking_enabled` but keeps the local positive cadence dormant (`interval_days = COALESCE(incoming, local)`). This honors the recorded cadence-once-assigned-never-cleared invariant (Cluster I) and never trips the v11 one-way trigger. Chosen over skipping/rejecting the conflicting contact.
- **[LOCKED] Notification ingress fails closed (Plan 06 Task 4 / Plan 10, cycle 4).** The widget fail-closed principle extends to the delivered-notification surface: a stale decay notification whose contact is now Unbound does **not** route to Compose on tap (fails closed); a birthday notification still opens Profile; `ACTION_MARK` still records the real touchpoint (Unbound preserves history) but does not re-arm cadence; snooze is a no-op for a now-Unbound contact. Chosen over permitting delivered-notification interactions as unrestricted explicit actions. Distinct surface from the widget decision — notification-nav.ts / notification-actions.ts were previously unowned.
