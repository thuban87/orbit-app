### Agreed Concerns (2+ reviewers — highest priority)

- **MEDIUM — The Off Limits section exposes all fuel kinds, not only `off_limits` (data-loss risk).** `listFuelForEditor` deliberately returns EVERY fuel kind (`fuel-read.ts:19-24`, `:45-65`), and `FuelEditor` defaults new rows to `"topic"` and presents all five kinds in its picker (`FuelEditor.tsx:72-81`). 34-08 states "filtered to kind off_limits" only in read_first/action prose (`34-08:123/129`); there is no enforced must_have/prohibition constraining the seed AND the editor to `off_limits`, and no test asserting a contact's `recent`/`topic`/`fact`/`gift` rows survive an Off Limits edit. Because the `{add,edit,delete}` diff computes any seeded row absent from the draft as a DELETE, an unfiltered seed would let the first Save destroy the other kinds; an unconstrained editor would also let a user create/edit ordinary fuel from the "Off Limits" section. This is the shared-table data-loss class CLAUDE.md warns about, and fuel is the one table where the section owns a single kind of a multi-kind table. **Fix:** add a data-loss prohibition + acceptance test to 34-05 and 34-08 — the `offLimits` seed baseline must be kind-scoped to `off_limits` on BOTH diff sides (a kind-filtered read or an off-limits adapter that forces `kind:"off_limits"` for adds/edits), and a round-trip test must prove an Off Limits edit leaves non-off_limits fuel untouched. (codex MEDIUM #3, claude MEDIUM, orchestrator-verified)

### Codex Review

## Summary

The plans are materially stronger after cycle 4, especially around current-state routing, explicit diff ownership, and aggregate revision ownership. Four unresolved implementation-contract gaps remain.

## Strengths

- The planned single aggregate `data_revision` owner correctly addresses the present conditional-bump bug in create/update and the method-diff self-bump: `src/db/contacts-dao.ts:231-244`, `src/db/contacts-dao.ts:504-516`, `src/db/contact-methods-dao.ts:277-278`; plans `34-03-PLAN.md:177-192` and `34-05-PLAN.md:27-29`.
- The current-state design is source-correct: `setCurrentStateValueCore` only updates history/current-state rows and does not write interactions or `last_contact` (`src/db/current-state-history-dao.ts:55-84`). The plan's changed-only comparison preserves that model (`34-05-PLAN.md:135-142`).
- The edit screen needs separate knowledge reads because `getContactForEdit` returns contact metadata, custom values, links, and methods only (`src/db/contact-read.ts:153-213`). The explicit seed/reseed direction is therefore sound (`34-08-PLAN.md:123-129`), apart from the Fuel issue below.

## Concerns

- **MEDIUM — Create enrichment normalization is incomplete for relationship and fuel records.** The plan says the core injects only `contactId` and memory timestamps (`34-03-PLAN.md:184-185`, `34-03-PLAN.md:192`), but relationships also require `createdAt` and `now` (`src/db/relationships-dao.ts:8-18`). Fuel requires caller-minted `uid`, `createdAt`, `source`, and `now`, in addition to `contactId` (`src/db/fuel-dao.ts:54-71`). As written, semantic-only relationship/fuel drafts cannot be safely passed to their core writers.
- **MEDIUM — Off-Limits deletion would still double-bump `data_revision`.** The plan makes `updateContactFull` the sole revision bumper and applies off-limits deletions through `deleteFuelCore` (`34-05-PLAN.md:27-29`, `34-05-PLAN.md:135-142`). But `deleteFuelCore` inserts a tombstone without disabling its default revision bump (`src/db/fuel-dao.ts:227-249`), and `insertTombstoneCore` defaults `bumpRevision` to `true` (`src/db/tombstones-dao.ts:62-81`). An aggregate edit deleting Off Limits would bump once in the tombstone path and again at aggregate completion.
- **MEDIUM — The proposed Off Limits section exposes all fuel kinds, not only `off_limits`.** The plan describes `listFuelForEditor` as filtered to Off Limits (`34-08-PLAN.md:123`, `34-08-PLAN.md:129`), but the query deliberately returns every fuel kind (`src/db/fuel-read.ts:19-24`, `src/db/fuel-read.ts:45-65`). Further, `FuelEditor` defaults new rows to `"topic"` and presents all kinds in its picker (`src/components/FuelEditor.tsx:71-81`, `src/components/FuelEditor.tsx:430-536`). Without a fixed-kind adapter/filter, the Off Limits section can show and mutate ordinary fuel records and create non-Off-Limits rows.
- **LOW — The MemoryEditor composition does not specify required AI-gate props.** `MemoryEditor` requires both `onSetAllowAi` and `globalAiEnabled` (`src/components/MemoryEditor.tsx:60-70`), and its existing caller derives availability from app settings before passing both (`src/screens/ThingsToRememberScreen.tsx:171-184`, `src/screens/ThingsToRememberScreen.tsx:613-621`). The planned new MemoryEditor composition does not state equivalent wiring (`34-07-PLAN.md:158`; `34-08-PLAN.md:129`). This is likely caught at compile time, but needs explicit plan coverage to preserve the edit-only AI control.

## Suggestions

- Define distinct create-only draft types and normalize all required core fields: timestamps for relationships; `uid`, timestamps, and explicit `"user"` source for fuel.
- Add a revision-suppression option to the aggregate fuel-delete path while retaining tombstone creation; test a delete-only Off Limits update advances the revision exactly once.
- Add an Off-Limits-only FuelEditor adapter: filter seed rows, force `kind: "off_limits"` for additions/edits, and test that ordinary fuel is neither displayed nor mutated.
- Specify the settings-derived `globalAiEnabled` and deferred `onSetAllowAi` wiring for every new MemoryEditor host.

## Risk Assessment

**MEDIUM.** The remaining issues are localized and testable, but affect atomic aggregate updates, backup-freshness revision correctness, and the privacy-sensitive Off Limits domain.
