Review finding (ACTIONABLE, cycle-2): `SqlExecutor` exposes the identical write-capable surface (`runAsync`/`execAsync`) inside an `inReadSnapshot` body as inside `inWriteTransaction`, so "no writes inside it" is currently a doc-comment, not a type guarantee — a future accidental write inside a snapshot would silently commit under a misleading API name. Make this structural at low cost: export `type ReadOnlyExecutor = Pick<SqlExecutor, "getFirstAsync" | "getAllAsync">` from `transaction.ts` (or `types.ts`) and type `inReadSnapshot`'s `body` parameter as `(ro: ReadOnlyExecutor) => Promise<T>`, passing the same underlying `exec` object narrowed to that type — not the full `SqlExecutor`. Update export-manifest.ts's read sequence to consume the passed-in `ro` parameter (not the outer closed-over `exec`), so a call to `ro.runAsync(...)` is a compile error. Review finding (ACTIONABLE, cycle-2): because `inReadSnapshot` and `inWriteTransaction` share one non-reentrant mutex, an in-progress export (or 17-06's automatic-backup sweep) holds that mutex — and therefore blocks every other app write, including a headless notification-tap or widget write — for as long as it takes to read every exportable table and base64-encode every referenced photo.
