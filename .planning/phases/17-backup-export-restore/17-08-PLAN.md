  <action>Implement restore-apply using only non-mutexed DAO cores under one inWriteTransaction; do not call createContactFull because it owns its own write transaction. Before writes, validate that every serialized contact/definition pair is present exactly once and that each value, including value=null, has valid UID parents. Review findings (HIGH, source-verified — both close real gaps, not stylistic notes):

(1) Photo durability. `persistMaster` (src/services/photos/photo-storage.ts) performs real filesystem I/O and can throw; committing DB rows before photo bytes are proven writable can leave a committed contact/value row pointing at a photo that was never created. Close this with a two-phase protocol: BEFORE opening the outer transaction, decode every referenced photo's base64 bytes (contact avatars, profile, custom photo-field values) and write each to a fresh OS temp/cache file, keyed by its backup-stable UID reference (contact uid, or contact-uid+col_name for a custom photo field) — NOT yet to any canonical `avatars/` name, since new Merge-created contacts have no local id until after commit. If any temp write fails (disk full, unexpected decode failure), abort the whole restore before the transaction opens — local data and every existing canonical photo file remain untouched, honoring D-05/D-15's "local data unchanged on failure" literally, not just for SQL rows. Only once every photo stages successfully does the outer inWriteTransaction open, build UID-to-local-ID maps in parent-first order, execute Merge actions or validated Replace-all replacement, seed/apply normalized value pairs, and commit. AFTER commit, for each staged temp file, resolve its now-known local contact id / col_name and call the existing, unmodified `persistMaster(tempFileUri, canonicalRelativeName)` to finalize it into place — this reuses persistMaster's own crash-safe `.tmp`/`.bak` swap, so an app-kill mid-finalize is already reconciled by the existing `reconcilePhotoWrites` launch sweep with no new code. If `persistMaster` itself still throws for one photo (a narrow residual risk now that bytes are already proven decodable and writable), catch it per-photo — do not abort or roll back the other photos or the committed restore — log the technical cause privately (Logger, no content) and add that photo to a `photosNeedingAttention` count in the typed apply result so the UI can tell the user plainly (e.g., "N photo(s) could not be restored — reopen the affected contact to re-add its photo") rather than silently logging it. Delete each staged temp file (best-effort) once finalized or once reported as failed.

(2) Schedule rebuild is a separate, independently-failable post-commit step from photo finalization; do not couple their error handling. If notification/digest schedule reconciliation throws after commit, catch it, log privately, and set a `schedulesNeedResync: true` flag on the typed apply result (surfaced as "reminders will resync automatically" — non-blocking, never "restore failed"). This is honest, not aspirational: `reconcileSchedule` (`src/services/notifications/notification-schedule.ts`, registered via 11-10) and `reconcileDigestSchedule` (`src/services/notifications/digest-schedule.ts`, registered via 15-03) are BOTH already-registered launch-sweep hooks that fully re-read current DB state and reconcile OS schedules on every subsequent real foreground launch — no new marker/table is needed for this case; add a regression that, after simulating a rebuild-call failure, invokes those existing reconcile functions and asserts the mismatch clears.

(3) sunContactUid vs. tombstones. Resolve sunContactUid from the completed contact UID map immediately before the settings-apply call, but validate it against the reconciliation module's reference-to-tombstoned-parent fallback (17-04) rather than a bare map lookup: if the named contact UID lost to a winning tombstone in this same restore pass, resolve to null/self regardless of whether the incoming or the locally-retained settings row is the one being written — a locally-retained row can dangle too if this restore is what tombstones its sun contact. Apply the one validated app-settings singleton through Plan 17-12's updateAppSettingsCore: in Merge compare modifiedAt through the reusable D-02/D-03 policy and retain a newer local row (after the sunContactUid re-validation above); in Replace-all write the incoming allowlisted non-secret row. Never write the serialized source integer id and never invoke SecureStore.

Query/assert the final pair count and uniqueness against the full contact × definition matrix before commit. Never assign contacts.last_contact from payload, and invoke recomputeLastContactCore after interaction mutation. Before Replace-all, call the existing verified automatic snapshot path when configured, otherwise return the required no-destination disclosure state. Do not import field_history or serialized schedule/path state.</action>
