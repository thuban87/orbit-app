Review finding (HIGH, Pass-3 audit B-21, source-verified): setting a new secret and setting the SQLite `encryption_enabled` flag are two independent systems with no shared transaction; a failure between them leaves a contradictory state, and inferring "disabled" from a missing cached secret alone reproduces B-16's fail-open bug at the enable/disable boundary. Do not prune either a verified new copy or its still-needed old copy prematurely at any boundary.

Review finding (MEDIUM, existing text extended above): SAF provides no general atomic-replace guarantee, so re-encryption of an accessible automatic file must follow an explicit crash-recovery protocol, not an in-place overwrite — for each accessible automatic file: (1) write a new, distinctly-named encrypted snapshot with the new passphrase; (2) re-read and decrypt-verify that new file; (3) only after verification succeeds, delete the superseded old-passphrase file; a crash/failure at any point before step 3 leaves the previously verified (old-passphrase) file fully intact and re-encryption resumable/retryable on the remaining files, never partially replacing a file in place.
