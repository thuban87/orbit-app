## Critical Issues

### CR-01: The full-width root snackbar covers the + dial's "Add Contact" row, so a tap there can fire the snackbar's Undo

**Files:**
- `src/components/snackbar-host.ts:106-112` (D-143 geometry)
- `src/components/Snackbar.tsx:85-113` (the overlay is `box-none`, but the pill itself takes touches; it is hidden only from accessibility while the dial is open)
- `src/components/UniversalFab.tsx:118-126, 149-157, 192` (dial rows)
- `App.tsx:448-449` (`<Snackbar />` renders after `<UniversalFab />`, so it is on top)

**Issue:** With the universal + on screen, the pill now sits from `tabBarHeight + 80` (FAB row bottom 16, plus FAB 56, plus gap 8) upwards, full width.
- The dial's first row, "Add Contact" (`UNIVERSAL_FAB_ACTIONS[0]`), sits at `bottom: tabBarHeight + 16`, translated up by 68 and 44 tall. That puts it at `tabBarHeight + 84` to `+128`.
- That band lies entirely inside a one-line pill (minimum height 48, so `+80` to `+128` and taller when the label wraps). A two-line pill also clips the "Quick Log" row (`+128` to `+172`).
- The Snackbar overlay is a later sibling of UniversalFab at the App root, so the pill wins hit-testing over the dial rows.

So for the 6 seconds a snackbar is up, opening the + and tapping "Add Contact" either does nothing, or fires the pill's action. The dial rows are right-aligned (`right: 20`), and that is exactly where the pill's Undo (and Quick Log's "Add Note") sit.

**Concrete path:**
1. Quick Log from the dial. The snackbar shows Undo + Add Note.
2. Open the + again and tap "Add Contact".
3. The tap hits Undo, and `deleteTouchpoint` hard-deletes the interaction just logged.

Every delete snackbar has the same exposure: its Undo restores the deleted entry.

Before 9306c912 the root pill sat at a fixed 112 dp, below the first dial row, and D-132's width clamp kept it off the + lane. D-143 removed both. The owner's re-check confirmed only that the + and Undo are tappable. D-132 says "The FAB under/near a toast stays tappable", and the dial rows are part of that FAB.

**Fix (keeps D-143's geometry):** make the root snackbar touch-transparent while the dial is open. It is already hidden from accessibility then, via `fabDialBackgroundA11y`.
```tsx
// Snackbar.tsx, the overlay View
pointerEvents={fabDialOpen ? "none" : "box-none"}
```
Whether the pill should also be hidden or dismissed while the dial is open, so it does not visually cover "Add Contact", is a look decision. **Owner's call.** Add a render test: with the dial open and a snackbar showing, the overlay's `pointerEvents` is `"none"`.

## Warnings

### WR-01: History page: an open edit form disappears when a reload drops its row, and the page stays held

**File:** `src/screens/MemoryHistoryScreen.tsx:662, 679-725, 793-823`

**Issue:**
- `renderRow` renders the edit form only in place of a row that is still in `groups`.
- Unlike `cardEditSlots` (the section and Key People editors) and `OffLimitsEditorScreen.tsx:509-513`, the history page has no fallback for an edited row that a reload removed. Plan 20's SUMMARY states that fallback as an invariant: "a typed draft never disappears".

**When it happens:** if the row goes while its form is open, `form` stays `{ mode: "edit" }`. This is reachable:
- the page is a tab page with the + visible, so + → Update Contact → delete or move that entry → Back triggers the focus reload;
- the same history page can be open in another tab's stack;
- a restore or a merge.

**Result:**
- The draft is gone from the screen.
- `controlsHeld` keeps every row and the top Add disabled.
- The section FAB stays suppressed.
- If it was the last entry, the empty state shows above a disabled Add.
- Back then "closes" an invisible form, and asks Discard/Keep if it was dirty.

**Fix:** render the form after the groups when its row is gone, matching Off Limits. Also keep it reachable when the list becomes empty:
```tsx
{form?.mode === "edit" &&
 !(phase.phase === "loaded" && phase.data.some((r) => r.id === form.row.id))
  ? <HistoryEntryForm key={`edit-form-${formKey}`} /* same props as renderRow's edit form */ />
  : null}
```
The cleaner alternative is to close the form (with a notice) when its row is gone. Either way, add a test that drops the edited row on reload.

### WR-02: The section-FAB morph can start animating while its screen is blurred or the app is in the background (pause convention)

**File:** `src/components/SectionAddFab.tsx:142-150, 171-199, 208-216`

**Issue:** the pause effect cancels and snaps the morph only on the transition to blurred or backgrounded. After that, `applyTarget` can still start a `withTiming`:
- The keyboard listeners are global (`Keyboard.addListener`).
- So a section editor left mounted under another screen (for example after `openLinked` → EditInteraction, which has text inputs) flips `keyboardUp` when that screen's keyboard opens or closes.
- That re-evaluates suppression and starts a `MORPH_DURATION_MS` timing on the hidden screen.
- A save from that screen that changes `formOpen` or `loaded` does the same.

CLAUDE.md: "All animation pauses on `useIsFocused === false` and on `AppState` background". The cost is small, but the convention is broken.

**Fix:** mirror a paused flag into a shared value and use duration 0 while it is set. Better still, ignore keyboard events while unfocused.
```ts
const paused = useSharedValue(false);
useEffect(() => { paused.value = !(isFocused && appActive); }, [isFocused, appActive, paused]);
// in applyTarget:
progress.value = withTiming(next, {
  duration: reducedMotion.value || paused.value ? 0 : MORPH_DURATION_MS,
});
```

### IN-02: Key People keeps `initialEditId` after its first load

**File:** `src/screens/KeyPeopleEditorScreen.tsx:186-190`

`SectionEditorScreen.tsx:214-217` clears `initialEditId` on later loads. Key People does not.

If a re-read fails, the phase goes to `error` and `RelationshipEditor` unmounts. Retry then remounts it with the original `editId`, which reopens that row's form unasked.

**Fix:** call `setInitialEditId(undefined)` on later loads, as SectionEditor does.

### IN-03: A comment in the backup service contradicts the code

**File:** `src/services/backup/backup-service.ts:67-73, 108-110`

The doc comment says `sourceFormatVersion` is "only called after the parse has validated the whole file". In the code it runs on the line *before* `parseBackupManifest(raw)`.

The behaviour is correct, because a bad file throws before the preview is built. Only the comment is wrong.

**Fix:** reword it ("its value is used only when the parse below succeeds"), or move the call below the parse.

### IN-04: The root pill jumps between two positions while a snackbar is up on a section page

**File:** `src/components/snackbar-host.ts:99-112`

On a focused section editor, the pill switches between two geometries as the section FAB shows and hides:
- the FAB row baseline when the FAB is present;
- the fixed 112 dp when it is not.

This happens with scrolling (the morph's hysteresis), and when a form opens or closes. So the Undo button moves under the user's finger while they scroll.

This is a look question for the owner. One option is to latch the geometry for a message's lifetime.

### IN-05: D-148's "newest entries" is implemented as meaningful-date-first order

**File:** `src/db/profile-knowledge-read.ts:315-324`

The section body uses the shared read's order without its pin key: dated entries first by `meaningful_date` DESC, then `created_at`. As a result, a Gift Idea with an old or future meaningful date outranks one added today with no date.

The code comment records this reading, and the owner's fix-check passed. Listed only so the owner can confirm that "newest" was meant this way.
