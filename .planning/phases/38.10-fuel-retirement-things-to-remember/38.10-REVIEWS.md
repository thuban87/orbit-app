# Cross-AI plan review: Phase 38.10 (Fuel Retirement, Things to Remember & Sharing)

**Verdict:** the plans are sound and nothing needs a restructure. One cross-plan contract gap is serious enough to fix before execution (C-01). A few smaller gaps would otherwise surface during execution or at the device pass.

## 1. Summary

The schema block (W1 migration → W2 knowledge DAOs → W3 current state and the move DAO → W4 retarget) is the right answer to "tsc can't see SQL." Within it:

- Migration 033 is designed to be total: it never throws on odd data, keeps fuel uids, and is proved equal to the v7 converter by a test.
- The linked-note model (a copy of the text, `ON DELETE SET NULL`, sync in TypeScript through `editTouchpointFullCore`) makes "deleting the interaction leaves a standalone entry" true by construction.
- The lock markers (`group_note_copy`, `note_ai_locked`) are enforced by the schema, so AI access can only narrow.

The main weakness is D-66 keyboard centring. Plan 09's hook only works if the host screen wires each text field to it. The plans wire it on only two screens, and the editors that hold most of those fields are not allowed to add the plumbing. Smaller issues:

- a restore unique-index collision;
- Current Location becoming movable although D-84 doesn't include it;
- snackbar wording that breaks 38.9's feedback rules;
- one contradiction in the backup-schema instructions.

## 2. Strengths

- **The one-way door is handled with care.**
  - `App.tsx:381-397` shows the app stays bricked forever if a migration throws, and plan 01 accordingly only throws when a copy proof fails.
  - It deletes each source row only after a per-row re-read, the same pattern as `017-knowledge-egress-datamove.ts:113-135`.
  - Its foreign-key check is scoped to the three tables it touches, unlike the unscoped check in `011-contact-lifecycle-schema.ts:246-250`.
- **The schema facts check out.** `ALTER TABLE … ADD COLUMN … REFERENCES … ON DELETE SET NULL` matches the existing precedent in `026-group-events-schema.ts:31-32`. The new settings defaults follow the pattern in `029-ai-configuration.ts:43-50`.
- **The one-directional link CHECK is a sharp catch.** A both-or-neither CHECK would make every interaction delete fail once FK SET NULL fires.
- **AI gating fails closed in SQL.** Today the interaction-note gate is a JS check (`ai-context-read.ts:191`, `row.allow_ai === 1 && row.note?.trim()`). Plan 06 moves it into the query as a column projection, so the structured rows are still sent. Compose Research already marks current-state items `aiEligible: false` (`compose-research-read.ts:174`), so Last Talked About stays out of AI.
- **Every interactions `allow_ai` writer is covered** by the D-103 clamp: `recency-dao.ts:351` (plan 03), `ai-permissions-dao.ts:362,367` (plan 10), and the restore upsert at `restore-apply.ts:889` (plan 04).
- **The D-100 ownership guard is built from the live schema.** It derives the list from `pragma_foreign_key_list` plus an explicit list for columns without a foreign key, and a test enforces it. I confirmed the creation artefacts it allows: `createContactFullCore` seeds global custom-field values with `null` (`contacts-dao.ts:283-296`), and `upsertValueCore` writes no history (`field-values-dao.ts:104-120`).
- **The revision-bump rule matches the code.** Purge does N+1 default-bumping tombstone writes today (`purge-dao.ts:472-482`). `createContactFullCore` bumps exactly once at its end, which plan 08 relies on (no second bump).
- **The resume-prompt gate is placed correctly.** `ShareIntentProvider` wraps `AppShell` (`App.tsx:490`), the early returns are at `:382` and `:400`, and plan 08 puts the hooks before them. CaptureScreen already calls `resetShareIntent` on finish and cancel (`CaptureScreen.tsx:182, 306`), so suppression clears.

## 3. Concerns

### C-01 — HIGH — Plans 09, 13, 14, 15, 17 (and 19): D-66 centring can't be wired for most fields

**What D-66 requires.** The field "rises above the keyboard and sits centered" on Add/Edit Contact **and in the new per-section editors (D-75)**.

**How plan 09 builds it.** `useKeyboardCentering` returns `{ onFieldFocus(fieldRef), bottomSpacer }`. The host screen has to call `onFieldFocus` from each field's focus event and render the spacer.

**Where it breaks.**
- On Add/Edit Contact, the Memories, Gift Ideas and Thought of Them fields live inside `MemoryEditor` (`MemoryEditor.tsx:476,492,509,526`). Key People's fields live inside `RelationshipEditor` (`:271,286,317`). Neither component's props offer a focus callback (`MemoryEditor.tsx:71-110`).
- Plan 14 is told: "Do not edit RelationshipEditor.tsx or MemoryEditor.tsx here." Plan 13's MemoryEditor rework adds no such prop either.
- So on the forms, only the Off Limits, Last Talked About and Current Location rows that plan 14 writes inline can be centred.
- No plan wires the hook at all in `SectionEditorScreen` (13), `OffLimitsEditorScreen` / `OffLimitsForm` (15), `MemoryHistoryScreen` (17) or `MemoryAddScreen` (17). Those plans only say "uses EntryTextField".
- Plan 19 tests centring on the contact forms only.

**Result:** the owner's D-66 look checkpoint will fail late, and fixing it means reopening plans in four waves.

**Fix.** In plan 09, provide the hook through a React context: a `KeyboardCenteringProvider` that `EntryTextField` reads on focus. Hosts then only wrap their scroll view, and nested editors need no new props. Alternatively, add an `onEntryFieldFocus` pass-through prop to MemoryEditor (13) and RelationshipEditor (15). Either way:
- add the wiring to plans 13, 15 and 17;
- extend plan 19 Task 2's centring check to the section editors, the Off Limits editor, the history page and the + → Memory Add form.

### C-02 — MEDIUM — Plan 04: restore can collide with a local link on a different uid

The memories upsert is `ON CONFLICT(uid)` only (`restore-apply.ts:972`). Plan 01 adds a partial unique index on `(interaction_id, link_source)` for each table.

**Failure case:** a local memory with uid a is linked to interaction I (`note`). A Merge restore brings in a memory with uid b linked to the same interaction. The insert hits the unique index and the whole restore rolls back. This happens when both devices restored from a common backup and then each used "Also save to" on the same interaction.

Plan 04's `normalizePlan` collapse is described over the incoming rows, "across memories and current_state_entries". It doesn't say:
- that rows staying from the local database take part;
- which row wins;
- that the losing row is unlinked (`interaction_id → NULL`, keeping its text) rather than dropped.

The cross-table case (local Last Talked About entry vs incoming memory on the same interaction) breaks no schema rule. It silently breaks D-95 instead.

**Fix.** Specify that the collapse covers local rows that stay, that the newer `modified_at` keeps the link, that the loser becomes a standalone entry, and add a test for each of the same-table and cross-table cases.

### C-03 — MEDIUM — Plans 03 and 17: Current Location entries become movable, outside D-84

D-84 lists exactly Memories, Thought of Them, Gift Ideas, Last Talked About and Off Limits. But:
- Plan 17 puts "Move goes through `MoveEntrySheet`" on the history page, which serves both Last Talked About and Current Location.
- Plan 03's `KnowledgeEntryRef` is keyed by table, so a `current_location` row in `current_state_entries` is accepted as a source and would land as a memory.
- Plan 13's `moveTargetsFor(section)` has no Current Location section.

This adds behaviour without an owner decision.

**Fix.** Have plan 03 reject `field_key = 'current_location'` sources with a typed error and a test, and hide Move on the Current Location history page. If Current Location should be movable, ask the owner.

### C-04 — MEDIUM — Plans 11, 13, 15, 17: snackbar wording breaks 38.9's feedback rules (carried by D-19)

`docs/systems/ux-standards.md:71-73` (38.9 D-39): "Tapping Undo shows its own confirming snackbar." `:75-78` (D-46): "verb first, then whom … The Undo confirmation names what was undone."

The plans propose:
- "`<Section> entry deleted for <name>`" (plan 13);
- "Off Limits item deleted for `<name>`" (plan 15);
- "Entry deleted for `<name>`" (plan 17).

None of these is verb first, and no plan wires the confirming snackbar after Undo. That includes plan 11's share Undo, which only shows the D-110 message when the contact is kept.

**Fix.** Use verb-first copy, e.g. "Deleted Gift Idea for Ann" and "Moved to Off Limits for Ann". Add the post-Undo confirmation (e.g. "Gift Idea restored") on every Undo path. Add these strings to plan 19's wording review (see C-11).

### C-05 — MEDIUM (owner question) — Plans 10 and 12: Group Note copies make a Group Note impossible to clear

Research Q4 (block a linked note from being cleared to blank) was a planner call. Plan 10 applies it to Group Notes: `propagateGroupNoteCore` throws `LinkedNoteBlankError` "if the note becomes blank while copies exist."

With D-96 there is one copy per participant, spread across N Profiles. To clear an event's Group Note, the user would first have to find and delete N section entries. For a participant's own note, blocking is cheap (one entry). For Group Notes it is a trap.

**Owner question:** when a Group Note is cleared while copies exist, should the copies become standalone (still locked AI-off under D-102), or should clearing stay blocked? I recommend unlinking. It loses no data and matches D-37, which already makes the entry standalone when the interaction is deleted.

### C-06 — MEDIUM — Plan 03: the D-85 drop list can still lose data silently

`fieldsDroppedByMove` lists "note / meaningful date / pinned / link" for memory → Off Limits.

- Memories also carry `outdated` and `hidden` (`016-contact-knowledge.ts`; `MemoryRow`, `memories-read.ts:6-25`). Neither survives a move into Off Limits or Last Talked About, and neither is listed. D-85 says "Nothing is lost silently."
- "link" is ambiguous. The same bullet says the url is kept, so it presumably means the interaction link. Name it explicitly ("linked note").

**Fix.** Add `outdated` and `hidden` to the drop list, give "linked note" its own entry, and add a behaviour test for each.

### C-07 — LOW — Plans 03 and 04: the shared order constant has no table prefix

`CURRENT_STATE_ORDER_SQL = "entry_date DESC, COALESCE(entry_time, substr(created_at,12,8)) DESC, id DESC"` names its columns without a table prefix. Plan 04 orders the export by it, but the export query joins `contacts c` (`export-manifest.ts:185`), which also has `id` and `created_at`. SQLite will reject the query as an ambiguous column name.

Tests will catch this, but the cleaner fix is a builder, `currentStateOrderSql(alias)`.

### C-08 — LOW — Plan 04: contradictory backup-schema instructions

Plan 04 says to "reject `fuel[]` as an unknown array" and also requires zero "fuel" in `backup-schema.ts`. The validator has no generic unknown-key check; it only lists required arrays (`backup-schema.ts:439-455`). Rejecting `fuel[]` therefore means naming it, and a generic unknown-key rejection could break the optional arrays (e.g. value history, `:459`).

**Fix.** Pick one: drop the rejection (`fuel[]` is just ignored), or put the check in the allowlisted `v7-legacy-conversion.ts`.

### C-09 — LOW — Plan 15: a stated outcome has no task behind it

Plan 15's must-haves say "Both editors use … the D-66 field." The Key People editor only hosts `RelationshipEditor` unchanged, and Task 2 converts none of its fields. Either convert the note field (and fold it into C-01), or narrow the claim.

### C-10 — LOW — Plans 15, 16, 17: link display (D-24) not explicit for every section with links

D-24 "applies to every section that stores links." After this phase, Last Talked About entries store a url (D-46 shares) and so does Off Limits. Plan 16 only spells out link detail for memory items, and plans 15 and 17 don't mention a URL with an Open action. Say it explicitly for Last Talked About (Profile and history page) and for Off Limits (Profile and editor).

### C-11 — LOW — Plans 12, 13, 16, 19: plan 19's wording review misses proposed copy

Plan 12 says its History tag suffix "joins the plan-19 wording review," but plan 19 Task 3 lists only the lock reason, the "kept" snackbar and the linked-row label. These are also missing:
- plan 16's "N items" count;
- the move and delete snackbars (plans 13, 15, 17);
- the "Moved to …" snackbar.

Wording is the owner's call, so plan 19 should present one combined list.

### C-12 — LOW — Plan 02: Undo's "link taken" check covers one table only

Plan 02's Undo checks whether the `(interaction_id, link_source)` link is taken before `linked-entry-dao` exists, so it checks only the row's own table. D-95 also holds across tables. Plan 10 should update the Undo cores to use its cross-table check.

### C-13 — LOW — Plan 06: a linked note can reach the AI twice

A linked memory whose interaction is among the 3 most recent goes into the prompt twice: once as a memory and once as the interaction note. Research suggested removing the duplicate; plan 06 doesn't. This isn't a leak, but it wastes tokens and gives the text extra weight.

### C-14 — LOW — Plan 04: Merge keeps the lower `allow_ai` (a visible behaviour change)

`MIN(local, incoming)` on Merge is consistent with D-13. Still, turning AI on for an item on one device will now never carry over by Merge. This changes the current code's last-writer-wins behaviour (`restore-apply.ts:889, 972`), so record it in the summary and in the knowledge base.

### C-15 — LOW — Plan 17: nothing sets the `origin` parameter

The snackbar's Open Profile action is suppressed only when `origin === "profile"`. But `resolveFabTarget` passes `{ contactId }` with no `origin` (`universal-fab-logic.ts:206-215`). So + → Memory started from a Profile offers to open the Profile the user is already on. This is harmless; either set `origin` in the FAB intent or drop the condition.

### C-16 — LOW — Plans 09, 11, 13, 17, 18: count and anchor bookkeeping

The RG-029 inventory steps (a sha commit followed by a separate commit to record it) and the transitional placeholder floor add churn to plans whose job is elsewhere. Given the owner's pruning todo, keep these edits minimal and don't expand them.

## Concerns

### HIGH

- **C-01 — Restore can link one person’s entry to another person’s interaction. Plans 04, 06.**  
  Entities reconcile independently, and interaction upserts can change their owning contact. A valid local graph and valid incoming graph can therefore produce an Alice-owned retained memory pointing to a Bob-owned winning interaction. Plan 04 resolves the link by existence and copies its text; Plan 06’s proposed predicate checks permission but not matching ownership. I reproduced those reconciliation winners. This risks incorrect Profile content and AI disclosure under the wrong contact.  
  **Fix:** validate links against final surviving owners, including retained rows; detach mismatches without losing text, and add matching-owner checks to AI SQL. [reconciliation.ts:574](/home/bwales/projects/orbit-app/src/backup/reconciliation.ts:574), [restore-apply.ts:889](/home/bwales/projects/orbit-app/src/backup/restore-apply.ts:889), [Plan 04:170](</home/bwales/projects/orbit-app/.planning/phases/38.10-fuel-retirement-things-to-remember/38.10-04-PLAN.md:170>)

- **C-02 — Sticky locks and consent reductions do not cover retained reconciliation rows. Plan 04.**  
  The proposed `MIN`/`MAX` rules live in upserts, but `writes()` excludes `retain`, and restore can return before the post-pass. An older incoming locked/off row therefore cannot narrow a newer local unlocked/on row as the plan promises. Link-collapse also needs to preserve permission and lock evidence across different-UID contenders before deleting losers.  
  **Fix:** merge these safety fields during reconciliation/normalization, promote changed retained rows to updates, and account for them before the no-op return. Test older incoming locks and conflicting linked-entry identities. [restore-apply.ts:425](/home/bwales/projects/orbit-app/src/backup/restore-apply.ts:425), [restore-apply.ts:1941](/home/bwales/projects/orbit-app/src/backup/restore-apply.ts:1941), [Plan 04:175](</home/bwales/projects/orbit-app/.planning/phases/38.10-fuel-retirement-things-to-remember/38.10-04-PLAN.md:175>)

- **C-03 — Share Undo does not prove the contact was created by that share. Plans 08, 11; interface in 05.**  
  The proposed API accepts arbitrary numeric contact/row references. An older pristine active contact can satisfy the ownership guard, so an empty or unrelated row list could authorize its permanent deletion. That exceeds D-106’s narrow exception. Additionally, `modified_at = created_at` does not prove unchanged metadata: timestamps have whole-second precision.  
  **Fix:** issue and validate a creation receipt containing stable contact/share identities and initial metadata before deleting anything. Reject unrelated, stale, empty, or replayed receipts; compare actual metadata rather than timestamps alone. [purge-dao.ts:363](/home/bwales/projects/orbit-app/src/db/purge-dao.ts:363), [database.ts:115](/home/bwales/projects/orbit-app/src/db/database.ts:115), [Plan 11:104](</home/bwales/projects/orbit-app/.planning/phases/38.10-fuel-retirement-things-to-remember/38.10-11-PLAN.md:104>)

- **C-04 — Changing a new memory’s type can carry the wrong AI default. Plans 02, 13, 14, 17.**  
  Plan 13 supplies one scalar `defaultAllowAi`; the generic Add form retains a selectable type. The current picker changes only `type`. With Memories default ON and Gift Ideas default OFF, choosing Gift Ideas can retain ON, which Plan 02 then treats as an explicit override. This contradicts the selected type’s creation default.  
  **Fix:** resolve defaults by the selected type and distinguish an untouched seeded default from an explicit switch choice. Preserve explicit choices and existing-item permissions. [MemoryEditor.tsx:471](/home/bwales/projects/orbit-app/src/components/MemoryEditor.tsx:471), [Plan 13:153](</home/bwales/projects/orbit-app/.planning/phases/38.10-fuel-retirement-things-to-remember/38.10-13-PLAN.md:153>)

- **C-05 — The shared entry field would erase spaces while typing. Plan 09.**  
  `normalizeEntryText` is specified to trim for saving, then applied on every `onChangeText`. Entering `"hello "` becomes `"hello"`; the next word joins onto it. Existing text widgets preserve the entered string.  
  **Fix:** normalize newlines during typing while preserving spaces; trim only at submission. Verify sequential multiword typing and pasted newlines. [TextAreaFieldWidget.tsx:22](/home/bwales/projects/orbit-app/src/components/field-widgets/TextAreaFieldWidget.tsx:22), [Plan 09:173](</home/bwales/projects/orbit-app/.planning/phases/38.10-fuel-retirement-things-to-remember/38.10-09-PLAN.md:173>), [Plan 09:194](</home/bwales/projects/orbit-app/.planning/phases/38.10-fuel-retirement-things-to-remember/38.10-09-PLAN.md:194>)

### MEDIUM

- **C-06 — Undo can reconnect a snapshot to a reused interaction ID. Plans 02, 03.**  
  The planned parent check is `SELECT 1 ... WHERE id = ?`. Interactions use reusable `INTEGER PRIMARY KEY` IDs. After deletion and reinsertion, that check can find a different interaction, including another contact’s. I reproduced this with the proposed schema. Separate per-table unique indexes also cannot enforce D-95 across both entry tables.  
  **Fix:** snapshot parent UID and ownership, resolve that identity on Undo, and check link occupancy across both tables. Fall back to standalone when identity or occupancy differs. [011-contact-lifecycle-schema.ts:98](/home/bwales/projects/orbit-app/src/db/migrations/011-contact-lifecycle-schema.ts:98), [Plan 02:245](</home/bwales/projects/orbit-app/.planning/phases/38.10-fuel-retirement-things-to-remember/38.10-02-PLAN.md:245>)

- **C-07 — Undo’s timestamp may tie its deletion tombstone. Plans 02, 03.**  
  Writing `modified_at = now` does not guarantee a newer stamp when deletion and Undo occur within one second. Reconciliation deliberately lets deletion win equality; an incoming deletion snapshot can consequently delete the restored row again.  
  **Fix:** retain deletion evidence in the snapshot and ensure Undo’s modification stamp is strictly newer. Preserve the existing deletion-wins tie policy. [database.ts:115](/home/bwales/projects/orbit-app/src/db/database.ts:115), [reconciliation.ts:310](/home/bwales/projects/orbit-app/src/backup/reconciliation.ts:310), [Plan 02:246](</home/bwales/projects/orbit-app/.planning/phases/38.10-fuel-retirement-things-to-remember/38.10-02-PLAN.md:246>)

- **C-08 — Random collision remapping breaks repeatable v7 conversion. Plans 01, 04.**  
  UID uniqueness is per table, so a legacy row can validly collide with a destination UID. Migration and each backup parse then mint different random replacement UIDs. Repeated Merge restores can create duplicates; unmapped triple tombstones can target the unrelated original UID. Comparing collision rows only by content masks this identity problem.  
  **Fix:** use a consistent source-identity collision mapping across both conversion paths, including tombstones, and require collision equivalence by UID. [016-contact-knowledge.ts:13](/home/bwales/projects/orbit-app/src/db/migrations/016-contact-knowledge.ts:13), [Plan 01:202](</home/bwales/projects/orbit-app/.planning/phases/38.10-fuel-retirement-things-to-remember/38.10-01-PLAN.md:202>), [Plan 04:246](</home/bwales/projects/orbit-app/.planning/phases/38.10-fuel-retirement-things-to-remember/38.10-04-PLAN.md:246>)

- **C-09 — Restore can leave Group Note entries linked to a missing event. Plans 04, 10.**  
  Deleting a Group Event nulls the interaction’s `group_event_id`, while the interaction survives. Restore uses raw deletes, bypassing Plan 10’s explicit unlink helper. The entry’s interaction link therefore remains, but its proposed route requires the missing Group Event.  
  **Fix:** restore’s post-pass should unlink Group Note copies without a surviving event, preserving their text and permanent AI-off marker. [026-group-events-schema.ts:32](/home/bwales/projects/orbit-app/src/db/migrations/026-group-events-schema.ts:32), [restore-apply.ts:614](/home/bwales/projects/orbit-app/src/backup/restore-apply.ts:614), [Plan 10:124](</home/bwales/projects/orbit-app/.planning/phases/38.10-fuel-retirement-things-to-remember/38.10-10-PLAN.md:124>)

- **C-10 — Share-card actions lack asynchronous ownership and editing-aware timeout rules. Plan 11.**  
  A cross-table move replaces row references. A subsequent chip, note, AI, or Undo action can capture the old references before the result is adopted; the write mutex cannot repair stale arguments. The reducer also lacks pending/failure transitions. Touch-only timer pausing can close the activity while the user types on the keyboard, whereas current behavior holds the timer throughout note editing.
