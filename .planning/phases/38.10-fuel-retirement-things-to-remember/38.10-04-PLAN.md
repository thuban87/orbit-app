In a group of two or more, the winner is `normalizedWinner(actions)` (newer `modified_at`, then uid); every loser is **detached** as above. Never set a loser's `kind` to `"delete"`: the contact-method collapse at ~:458-470 deletes losers, and copying it here would hard-delete user text (D-37, D-69). Only rows with a non-null `interactionUid` are keyed (the index is partial on `interaction_id IS NOT NULL`); a null `interactionUid` with a leftover `linkSource` such as `'note'` is never collapsed (checker cycle 2 W-10).
    The pass runs before the post-pass below, so a detached row never receives a copied note. After it, every surviving linked row's source note is non-blank, so the post-pass's "when non-blank" guards are a backstop only. It never touches an interaction's `noteAiLocked` or any row's `groupNoteCopy`, so lock evidence survives the collapse (F-D2).
- **Link-slot release before child upserts (convergence c2 G-D3, Codex C-02).** Plan 01's partial UNIQUE indexes `idx_memories_interaction_link` and `idx_current_state_interaction_link` are immediate, and the child loop writes memories and current-state actions sorted by uid only (`restore-apply.ts:818-834`). Example: local linked memory `z-local` loses the D-95 collapse to newer incoming `a-incoming` on the same `(interaction, 'note')`; `a-incoming` is upserted first while the stored `z-local` row still holds the slot, the insert fails UNIQUE and the restore rolls back. A two-row swap (A: I1→I2, B: I2→I1) fails the same way. So, inside the restore transaction, after the delete pass (~:2040) and before `upsertChildren` (~:2046), run for each of `memories` and `current_state_entries`: `UPDATE <table> SET interaction_id = NULL, link_source = NULL WHERE uid IN (…) AND interaction_id IS NOT NULL` over the uids of that table's `update` actions (including rows promoted from `retain` by the passes above), chunked under SQLite's bound-variable limit (this plan only). That covers every row whose link changes: detached losers and owner/blank detaches are promoted to `update`, and a moved or swapped link arrives as an `update`. Releasing an `update` whose link does not change is harmless, because its upsert writes the final link straight back; so the upserts' `ON CONFLICT DO UPDATE` must set `interaction_id` and `link_source` from the incoming row. `retain` rows are not touched: after the link pass, a retained row that still holds a link is the only holder of its slot. The release changes no CHECK outcome (`interaction_id IS NULL` satisfies the link CHECK; the D-102 CHECK does not read the link). Deletes already ran, so a deleted row's slot is free. Replace-all mode runs the same step (harmless on an emptied table).
- Upserts:
  - memories and interactions use `allow_ai = MIN(allow_ai, excluded.allow_ai)` on conflict. This enforces D-13 "restore never re-opens permission" and fixes the stale ~:877-881 comment; it is a behaviour change, so say so in the SUMMARY.
  - the lock markers are sticky: `group_note_copy = MAX(group_note_copy, excluded.group_note_copy)` and `note_ai_locked = MAX(note_ai_locked, excluded.note_ai_locked)`, and the same statement writes `allow_ai = 0` whenever the resulting marker is 1, so the migration 033 CHECKs can never abort a restore (D-102, D-103). In the `ON CONFLICT DO UPDATE`, compute `allow_ai` from the **merged** marker, not from the column: `allow_ai = CASE WHEN MAX(group_note_copy, excluded.group_note_copy) = 1 THEN 0 ELSE MIN(allow_ai, excluded.allow_ai) END` (and the same with `note_ai_locked` on interactions). Inside one UPDATE SET every right-hand side reads the pre-update row, so a `CASE WHEN group_note_copy = 1` would see the old 0 and leave allow_ai 1 next to a new marker of 1, which fails the CHECK (checker cycle 3 I-6). On insert, a row with a marker of 1 is written with allow_ai 0.
