## Pattern Assignments

### Migration 033 (`src/db/migrations/033-*.ts`)
- **Head check:** `ls src/db/migrations` ends at `032-import-batch-cadence.ts`. `database.ts:70` reads `TARGET_VERSION = IMPORT_BATCH_CADENCE_SCHEMA_VERSION` (32). Re-verify at plan time (memory note migration-005-006-renumber, ROADMAP migration rule 2).
- **Versioned export + registration:** copy the shape of `029-ai-configuration.ts:15-17` (`export const X_SCHEMA_VERSION = 29; export const migration029: Migration = {...}`). Then repoint `database.ts:70` and append to `MIGRATIONS` (`database.ts:73-106`).
- **Integrity error class:** `017-knowledge-egress-datamove.ts:11-33` (`MIGRATION017_INTEGRITY_CODE`, `Migration017IntegrityError`, `isMigration017IntegrityError`). Clone it as 033. Throw only when the proof fails. The data mapping itself never throws (RESEARCH 1.5; CLAUDE.md, "anything a migration gets wrong is permanent").
- **Copy → re-read → delete with changes check:** `017:131-133`:
  ```ts
  const result = await exec.runAsync("DELETE FROM fuel WHERE id = ?", [row.fuelId]);
  if (result.changes !== 1) {
  ```
  `apply(exec, deps)` signature at `017:155`. Difference from 017: keep the fuel `uid`/`created_at`/`modified_at`. Do not mint them the way 017 does with `deps.newUid()` (RESEARCH 1.4 recommendation).
- **Table rebuild (current_state_entries):** `011-contact-lifecycle-schema.ts:200-212` uses the rename-old pattern. RESEARCH 1.3 recommends the SQLite-documented create-new → copy → drop → rename order instead. Either way, recreate indexes explicitly.
- **FK check at end:** `009-contact-method-normalization.ts:254` (`PRAGMA foreign_key_check`). FKs are ON inside the migration (`database.ts:177`; RESEARCH 1.1).
- **ADD COLUMN with REFERENCES:** precedent is `026-group-events-schema.ts` (`group_event_id`) (RESEARCH 1.3 step 3).
- **Tombstone + delete for the D-88 purge:** mirror `memories-dao.ts:283-310` in SQL (insert tombstone with the row's `deleted_at`, then delete).

## Shared Patterns
- **Transaction composition:** `*Core(exec, …)` functions never open transactions. Mutexed wrappers own one transaction and bump `data_revision` (`memories-dao.ts:88-90`, `:312`). This applies to every new DAO write, including the multi-table move/link compositions (D-84, D-93, D-96).
- **Scoped mutation:** `WHERE id = ? AND contact_id = ?` + `assertOneChange` (`memories-dao.ts:75-86, 141-156`).
- **Tombstone on delete:** `insertTombstoneCore` (`memories-dao.ts:296-304`). The tombstone entity union must drop `fuel` and add `off_limits` (RESEARCH 1.3 step 8, 2.2).
- **Feedback:** `showSnackbar` with `action` (`stores/snackbar-store.ts:5, 50`).
- **38.9 UX standards** (D-19): `useDiscardKeepGuard`, `useContactHeader`, `FieldError`, `EmptyState`, `useFirstErrorReveal`.
