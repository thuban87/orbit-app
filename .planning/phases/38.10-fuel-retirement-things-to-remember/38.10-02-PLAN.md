<objective>
Build the post-033 knowledge DAOs:
- a dedicated Off Limits DAO and read;
- per-type AI defaults, with the share force-off;
- delete with Undo for memories, key people and Off Limits;
- the two new AI-default settings, plumbed end to end;
- fuel-dao and fuel-read turned into an Off Limits-only shim, so the UI hosts owned by later plans (Create and Edit Contact, the Off Limits editor, Update Contact) keep working until those plans rewrite them.

Purpose: this is schema block W2 (ordering decision in 38.10-01 / PLAN-MAP §1).

**Revision-bump rule (PLAN-MAP §5 "Revision bumps", a planner engineering call; checker cycle 5 B-2).** One user-level write advances `data_revision` by exactly 1. Sources: D-28 requires every share write to bump; "exactly 1" matches the existing pins `contacts-dao.test.ts:1205` and `:1427` ("EXACTLY once", "no double-bump"). Every delete core that writes a tombstone takes `{ bumpRevision?: boolean }` (default `true`) and forwards it to `insertTombstoneCore(…, { bumpRevision })`, the way `insertTombstoneCore` itself does (`tombstones-dao.ts:65-83`). The core's own default keeps a standalone call bumping once; an aggregate that bumps once itself (Edit Contact's `updateContactFull`, purge, the share wrappers, the move DAO) passes `bumpRevision: false`. The mutexed wrappers in this plan call the core with its default and do **not** add a second `bumpDataRevisionCore`, so each wrapper still bumps exactly once. Undo cores remove a tombstone rather than writing one, so they never bump; their wrappers bump once.

Gate rule (this plan only, from RESEARCH Pitfall 1): `npx tsc --noEmit` and the tests this plan touches must be green. Other suites stay red until W4.

Commit in place. Never run `git worktree`, never push (CLAUDE.md).

**`off-limits-dao.ts`**

Cores never open a transaction (the `memories-dao.ts:88-90` rule). They are:
- `addOffLimitsCore(exec, { uid, contactId, label, text, url, now, createdAt?, groupNoteCopy?, fromShare? })` returns the new id. It rejects a new row whose label, text and url are all blank (DAO validation, not a CHECK). The optional origin markers default to 0 and `createdAt` to `now`; plan 03's move DAO passes them so a moved entry keeps its markers and its creation time (D-102, D-108).
- `editOffLimitsCore(exec, { id, contactId, label?, text?, url?, now })` is a partial patch with `WHERE id = ? AND contact_id = ?` and assertOneChange.
- `deleteOffLimitsCore(exec, { id, contactId, now, bumpRevision? })` returns an `OffLimitsSnapshot`. It runs `insertTombstoneCore('off_limits', uid, now, { bumpRevision })`, then the DELETE scoped by id and contact, with assertOneChange.
- `undoDeleteOffLimitsCore(exec, snapshot, now)` re-inserts with the same uid and `modified_at = now`, then calls `deleteTombstoneCore`. It reuses the snapshot id only when `SELECT 1 FROM off_limits WHERE id = ?` is empty; otherwise it inserts without an id and returns the new one (checker W6). The snapshot carries every column, including `group_note_copy` (D-102) and `from_share` (D-108).

Mutexed wrappers `addOffLimits`, `editOffLimits`, `deleteOffLimits` and `undoDeleteOffLimits` each own one transaction and exactly one revision bump: `addOffLimits`, `editOffLimits` and `undoDeleteOffLimits` call `bumpDataRevisionCore`; `deleteOffLimits` relies on `deleteOffLimitsCore`'s default `bumpRevision: true` and adds no second bump (revision-bump rule above).
