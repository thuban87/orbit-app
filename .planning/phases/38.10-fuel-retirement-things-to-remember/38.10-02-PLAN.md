**`off-limits-dao.ts`**

Cores never open a transaction (the `memories-dao.ts:88-90` rule). They are:
- `addOffLimitsCore(exec, { uid, contactId, label, text, url, now })` returns the new id. It rejects a new row whose label, text and url are all blank (DAO validation, not a CHECK).
- `editOffLimitsCore(exec, { id, contactId, label?, text?, url?, now })` is a partial patch with `WHERE id = ? AND contact_id = ?` and assertOneChange.
- `deleteOffLimitsCore(exec, { id, contactId, now, bumpRevision? })` returns an `OffLimitsSnapshot`. It runs `insertTombstoneCore('off_limits', uid, now, { bumpRevision })`, then the DELETE scoped by id and contact, with assertOneChange.
- `undoDeleteOffLimitsCore(exec, snapshot, now)` re-inserts with the same uid and `modified_at = now`, then calls `deleteTombstoneCore`. It reuses the snapshot id only when `SELECT 1 FROM off_limits WHERE id = ?` is empty; otherwise it inserts without an id and returns the new one (checker W6). The snapshot carries every column, including `group_note_copy` (D-102).

Mutexed wrappers `addOffLimits`, `editOffLimits`, `deleteOffLimits` and `undoDeleteOffLimits` each own one transaction and one `bumpDataRevisionCore`.
