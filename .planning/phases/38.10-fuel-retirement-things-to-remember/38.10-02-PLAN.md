**Revision-bump rule (PLAN-MAP §5 "Revision bumps", a planner engineering call; checker cycle 5 B-2).** One user-level write advances `data_revision` by exactly 1. **`undo-restore.ts` (new leaf module, convergence c1 F-D3/F-D4; this plan only for the module shape).** It imports no DAO (only executor types and the date helpers), so plan 03's and plan 10's DAOs can import it without a cycle (plan 10's import-graph rule). It exports:
- **Snapshot stamp name (convergence c2 G-D1, Claude C-01).** Every delete snapshot in this phase (Off Limits and memories and key people here, current state in plan 03) stores its tombstone stamp as `tombstoned_at`, never `deleted_at`: `memories.deleted_at` and `relationships.deleted_at` are live columns (migration 016:27, :43) that every reader filters on (`memories-read.ts:31`, `:38`; `relationships-read.ts:27`), so a snapshot field of that name would be re-inserted as "still deleted" and the restored row would stay invisible. The snapshot types carry no `deleted_at` field at all.
- `undoModifiedAt(now, tombstonedAt)`: returns the later of `now` and `tombstonedAt` + 1 second, built with `parseLocalMs` (`src/utils/dates.ts`) and `localDateTime` (`database.ts:115-121`), never `toISOString` (CLAUDE.md). Every Undo core in this phase (Off Limits, memories, key people here; current state in plan 03) writes `modified_at = undoModifiedAt(now, snapshot.tombstoned_at)`, so the restored row is strictly newer than its tombstone (`compareRowAndTombstone`, `reconciliation.ts:310-315`: equal seconds favour the tombstone) (F-D4, Codex C-07).
- `deleteStampAt(now, rowModifiedAt)` (convergence c9, Codex C-01 / Cursor CU-01): returns the later of `now` and the row's `modified_at` (compared with `parseLocalMs`, returned in the same local-datetime string form). Every hard-delete core in this phase (Off Limits, memories, key people here; current state and the move's source tombstone in plan 03) passes it as the `deletedAt` to `insertTombstoneCore` and stores it as `snapshot.tombstoned_at`. Reason: Undo writes `modified_at = undoModifiedAt(now, tombstoned_at)`, up to 1 s ahead of the clock, so a second delete in the same second stamped with raw `now` would write a tombstone older than the row it removes, and a backup carrying the restored row would beat it under `compareRowAndTombstone`'s strict `>` (`reconciliation.ts:310-315`). With this stamp an equal stamp is still a tie and deletion still wins it; F-D4 and the cycle-2 rules are unchanged. Each core already reads the row before its DELETE (the snapshot), so `modified_at` costs no extra query.
- `resolveUndoLinkCore(exec, { interactionUid, linkSource, contactId })` (used by Task 3 and plan 03): returns `UndoLink | null`, where `UndoLink = { interactionId, text, occurredAt, allowAi }` is the source **as it is now** (convergence c2 G-D2, Codex C-04). It is `null` unless all of these hold:
  - `SELECT id, contact_id, note, occurred_at, allow_ai, group_event_id FROM interactions WHERE uid = ?` finds a row whose `contact_id` equals the entry's `contactId` (F-D3);
  - neither `memories` nor `current_state_entries` holds a row with that `(interaction_id, link_source)` (`SELECT 1 FROM memories WHERE interaction_id = ? AND link_source = ? UNION ALL SELECT 1 FROM current_state_entries WHERE interaction_id = ? AND link_source = ?`) (F-D3; D-95);
  - `linkSource = 'note'`: the interaction's `note` is non-blank after trim. A linked participant note can never be blank (plan 10's Q4 rule, `LinkedNoteBlankError`); while the entry was deleted nothing blocked clearing it, so relinking would create a blank linked note. Then `text` = `interactions.note`, `occurredAt` = `interactions.occurred_at`, `allowAi` = `interactions.allow_ai` (already 0 when `note_ai_locked = 1`, migration 033's CHECK; D-49 one switch, D-103);
  - `linkSource = 'group_note'`: the interaction's `group_event_id` is non-null, `SELECT group_note, occurred_at FROM group_events WHERE id = ?` finds the event, and its `group_note` is non-blank after trim. A dissolved event (`detachParticipant`, `group-events-dao.ts:664-680`, leaves the interaction alive with `group_event_id` NULL) or a cleared Group Note means the copy stays standalone (D-113, D-102).   It reads `interactions` and `group_events` (migrations 011 and 026) and both entry tables (plan 01), so it needs nothing from plan 10. It never writes the interaction or the event.
