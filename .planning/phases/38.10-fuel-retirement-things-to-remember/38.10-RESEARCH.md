# Phase 38.10: Fuel Retirement, Things to Remember & Sharing - Research

**Researched:** 2026-10-12 (HEAD `d16779f1`)
**Domain:** On-device SQLite schema/data migration, backup wire format, linked-record data model, RN TextInput/keyboard behaviour
**Confidence:** HIGH for the data layer (every claim read on disk this session); MEDIUM for the keyboard approach (official docs plus RN source, but it needs a device check)

## Summary

The phase is dominated by one coupled data-layer change. Migration **033** (head is 032 on disk) creates the Off Limits table, reshapes `current_state_entries`, adds interaction links, moves every fuel row, purges soft-deleted rows, rewrites `custom` memories and `fuel` tombstones, then drops `fuel`. All of this runs inside the runner's single per-step transaction with `foreign_keys = ON`. The biggest planning hazard is not the migration itself. It is that **dropping `fuel` and removing `is_current` break every SQL-string consumer at runtime, and `tsc` cannot see SQL**. In this repo that is 11 source files and about 10 test files for `fuel`, and 10 source files and 14 test files for `is_current`. Vitest catches the breakage, because about 81 non-migration tests and several migration tests run the chain to `TARGET_VERSION`. So the plan that lands the migration must also carry, or deliberately shim, every one of those consumers, including backup export and restore. Without a deliberate interim shim, the migration, the DAO/read retarget and backup v8 are one inseparable seam.

A failing migration is permanent for that user. `App.tsx:381-397` shows "Couldn't start Orbit" forever when `openAndMigrate` rejects. So migration 033 needs a **total mapping**: it must never throw on legitimate-but-odd data (blank text, url-only rows, odd `created_at` strings, uid collisions). It throws only when a copy/re-read proof fails, which can only mean a bug. Copied rows should **keep their fuel `uid` and timestamps**, so that the SQLite migration and the v7→v8 backup converter produce the same rows. A Merge restore of a pre-upgrade backup then reconciles instead of duplicating.

For linked notes (D-37/D-38/D-42/D-49), I recommend a **linked copy with interaction-owned text**. Each linked entry keeps its own text, date and AI flag, plus a nullable `interaction_id` FK `ON DELETE SET NULL`. This makes "deleting the interaction leaves a standalone entry" structural on all seven interaction-deletion paths. Sync happens in TypeScript at three choke points (`editTouchpointFullCore`, the entry editors, the AI-permission writers). AI reads fail closed on both rows. For D-66 there is no keyboard library, and none is needed. Use `TextInput multiline` + `submitBehavior="submit"` + `returnKeyType="done"`, plus a small hook built on the repo's own precedents (`Sheet` keyboard listener, `useFirstErrorReveal`'s `measureLayout`→`scrollTo`) with a pure, unit-tested centering function. KeyboardAvoidingView is not used.

**Primary recommendation:** Plan the migration, data-layer retarget and backup v8 as one coupled area. Build the migration as a total, uid-preserving copy-then-prove-then-drop with a migration-vs-converter equivalence test. Store linked notes as linked copies with FK `SET NULL`, TS-side sync and fail-closed AI SQL.

### 1.3 Recommended migration shape (Claude's discretion; recommendation, not a decision)

All inside migration 033's `apply`, in this order. The runner owns the transaction.

1. **Create `off_limits`** (recommended columns): `id INTEGER PRIMARY KEY, uid TEXT NOT NULL UNIQUE, contact_id INTEGER NOT NULL REFERENCES contacts(id) ON DELETE CASCADE, label TEXT, text TEXT, url TEXT, created_at TEXT NOT NULL, modified_at TEXT NOT NULL`, plus an index on `(contact_id, created_at)`. **No `allow_ai` column** (D-09, D-36). Keep `label` and `url` so off_limits rows copy losslessly and D-84 moves don't drop fields. **Do not put a content CHECK on it**: legacy rows may be label-only or url-only, and a CHECK that rejects one bricks the migration. Validate new writes in the DAO.
2. **Rebuild `current_state_entries`** with the SQLite-documented order. Create `current_state_entries_new`, `INSERT … SELECT`, `DROP TABLE current_state_entries`, `ALTER TABLE current_state_entries_new RENAME TO current_state_entries`, recreate indexes [CITED: sqlite.org/lang_altertable.html, "Caution … constructs the revised table definition using a new temporary name, then renames"]. Migration 011 used rename-old-first, which was safe there only because it re-created every child. Here the table is a leaf, so either order works, but use the documented one. Recommended columns: existing columns minus `is_current`, plus `entry_date TEXT NOT NULL` (`YYYY-MM-DD`), `entry_time TEXT` (`HH:MM:SS`, NULL for direct entries, D-48), `url TEXT` (D-46 "its link kept"), `interaction_id INTEGER REFERENCES interactions(id) ON DELETE SET NULL` (D-37). Optionally add a `GLOB` shape CHECK on `entry_date`; this is only safe because step 2's SELECT always computes a valid date (see 1.5). Indexes: `(contact_id, field_key, entry_date, …)` for date order (D-51), and a partial unique index on `(interaction_id) WHERE interaction_id IS NOT NULL` if one link per interaction per table is chosen (open question Q2). **Drop `idx_current_state_current`.** It is recreated nowhere, because D-45 makes "Most Recent" the latest date.
   - Existing rows: `entry_date = substr(created_at,1,10)` when it is a valid date, else fall back (1.5). `entry_time = NULL`; existing entries are direct entries (D-48). Then the order is by date, and within a day by creation time (D-51).
   - Behaviour change to note: a row previously "promoted" to current (`promoteToCurrentValueCore`, `current-state-history-dao.ts:105-127`) stops being Most Recent if it is older. This is D-45's intent; D-60 rules out legacy repair.
   - **Why rebuild rather than keep `is_current` as a dead column:** the partial unique index must go regardless (`DROP INDEX`). Keeping a dead `NOT NULL` column invites readers to keep using it, and the v8 wire shape drops it. DROP COLUMN `is_current` is possible on 3.50.3 once the partial index is dropped [CITED: sqlite.org "column is named in the WHERE clause of a partial index"]. But a rebuild is needed anyway to add `entry_date NOT NULL` without a sentinel default. **Cost:** 14 test files insert `is_current` (list in Validation Architecture).
3. **`ALTER TABLE memories ADD COLUMN interaction_id INTEGER REFERENCES interactions(id) ON DELETE SET NULL`** — allowed because the default is NULL [CITED: sqlite.org "If foreign key constraints are enabled and a column with a REFERENCES clause is added, the column must have a default value of NULL"]. Precedent: `026-group-events-schema.ts` adds `group_event_id … REFERENCES group_events(id) ON DELETE SET NULL` the same way [VERIFIED: Read]. A partial unique index on it is optional (Q2).
4. **Add two `app_settings` columns** for D-61, following 029's shape: `ADD COLUMN ai_default_<gift> INTEGER NOT NULL DEFAULT 0 CHECK(… IN (0,1))` (`029-ai-configuration.ts:43-50` pattern) [VERIFIED: Read]. ROADMAP rule 4 says "All new durable preferences live in `app_settings` columns". Default 0 (fail closed) [ASSUMED — the owner did not say whether the new defaults inherit `ai_default_memory_allow`; DEFAULT 0 narrows].
5. **D-86:** `UPDATE memories SET type='general', modified_at=? WHERE type='custom'`. `custom_label` is untouched, so the label is kept.
6. **Copy fuel → homes (D-56), per row, proof before delete** (017 pattern, `017:58-119`):
   - `off_limits` → `off_limits` (label/text/url as-is).
   - `gift` → `memories` type *gift registry key*; `topic` (any source) → type *thought-of-them key*; `fact` → `general`. `value`/`custom_label`/`url` are mapped as in 1.5; `provenance = 'share'` when `source='share'`, else `'user'`; `allow_ai = 0`.
   - `recent` → `current_state_entries` with `field_key='last_talked_about'`, `entry_date` = date part of `created_at`, `entry_time = NULL`, `url` = fuel url, and value as in 1.5.
   - `source='ai'` rows may exist again even though 017 removed them, because restore writes v≤7 fuel with any `source` (`restore-apply.ts:924-935`) [VERIFIED: Read]. Map by **kind** only.
   - **Unknown kind** (no CHECK exists) → `general` memory, never a throw [recommendation].
   - Proof: re-read each destination by uid, compare every mapped field and `allow_ai = 0` (memories), then `DELETE FROM fuel WHERE id = ?` asserting `changes === 1`, then assert `COUNT(*) FROM fuel = 0`.
7. **D-88 purge:** for every `memories` and `relationships` row with `deleted_at IS NOT NULL`, insert a tombstone (`memory`/`relationship`, `deleted_at` = the row's `deleted_at`) and then delete it. This mirrors `purgeMemoryPermanentlyCore` (`memories-dao.ts:283-310`) [VERIFIED: Read], and the tombstone keeps Merge restore from resurrecting the row.
8. **Rewrite local `fuel` tombstones** (D-54). Without this, `listTombstones` throws on export once `"fuel"` leaves the union. A tombstone carries only a uid, not a kind. Recommendation: replace each `('fuel', uid, t)` with `('memory', uid, t)`, `('off_limits', uid, t)` and `('current_state_entry', uid, t)` (`ON CONFLICT … keep max`), then delete the `fuel` rows. With uids preserved (1.4), a tombstone matches whichever home the row would have gone to; the other two are inert [ASSUMED interpretation of D-54/D-55's "disposition consistent with v8"; see Q3].
9. **`DROP TABLE fuel`** last. With FKs ON, DROP performs an implicit `DELETE FROM`. `fuel` has no children, so nothing cascades [CITED: sqlite.org lang_droptable behaviour; leaf verified by grep].
10. **`PRAGMA foreign_key_check`** must return zero rows (runbook step 5 pattern; `011:204-208`).

### 1.4 Preserve uids and timestamps (strong recommendation)

017 minted new uids (`deps.newUid()`, `017:89`) and stamped `modified_at = deps.now` [VERIFIED: Read]. **For 033, keep `uid`, `created_at` and `modified_at` from the fuel row.** Reasons:
- A v7 backup restored in Merge mode after upgrade is converted with the same mapping (Item 2). Matching uids reconcile via LWW instead of creating duplicates.
- Fuel tombstones (step 8) only mean something if uids carry over.
- It enables a deterministic **migration ≡ converter** test (Validation Architecture).
- Collision: memories/off_limits/current_state uids are UNIQUE per table. Fuel uids are random UUIDs (`newUid`), so a collision means corrupt data. **Do not throw.** Mint a new uid for that row and keep going [recommendation], and test this path.

## Item 3 — Linked-note data model (D-37, D-38, D-42, D-49)

### 3.1 The requirement, restated from the decisions

- One text in two places; editing either side updates both (D-37).
- History shows one row tagged with the section; tapping the entry opens the interaction (D-37).
- Deleting the interaction leaves a standalone entry; deleting the entry leaves the interaction and its note (D-37, D-69).
- A linked LTA entry takes the interaction's date and time (D-41, D-48).
- One Allow AI switch covers every place the text appears; off blocks every route; LTA itself is never sent to AI (D-49).
- Targets: LTA, Gift Ideas, Thought of Them, Memories (D-38).

### 3.2 Options evaluated against the code

**A. Shared text, read-through.** The entry stores no text; it holds `interaction_id`, and readers `COALESCE` the interaction's note.
- Deleting the interaction must first *materialize* the text into the entry. There are **seven** deletion routes: `deleteInteractionCore` (`recency-dao.ts:377-410`, used by HomeScreen and UniversalFab Undo, InteractionDetail, `group-events-dao.ts:648, 751`, `bulk-actions-dao.ts:85`), purge (`purge-dao.ts:96`), and restore tombstone/replace-all raw deletes (`restore-apply.ts`). Any route that misses the hook plus FK `SET NULL` leaves an **entry with no text**, which is silent data loss.
- Every reader of `memories.value` / `current_state_entries.value` would need the JOIN: search corpus, dashboard line 3, Compose Research, AI read, export, Profile read and history.
- **Rejected:** too many hooks, and the failure mode is data loss.

**B. Linked copy, interaction-owned text (RECOMMENDED).**
- Both rows keep their own columns. The entry has `interaction_id … ON DELETE SET NULL` (1.3 steps 2-3).
- **Deletion is structural:** SQLite nulls the link on every deletion route, so the entry keeps its own text and date and becomes standalone with no hook. Deleting the entry touches nothing on the interaction.
- Sync at TypeScript choke points:
  1. **`editTouchpointFullCore`** (`recency-dao.ts:331-371`) is the only exported interaction edit path. It is used by EditInteractionScreen `:136`, PostLogNoteEditor `:157`, and every group-event participant edit (`group-events-dao.ts:406…565`). Inside the same transaction, propagate `note` → linked entries' text, `occurred_at` → linked LTA `entry_date`/`entry_time`, and `allow_ai` → linked memories. One choke point covers about 8 call paths. It also keeps ADR-010's single recency writer: "maintains `contacts.last_contact` through one serialized recency DAO. Each interaction create, edit, or delete recomputes it" [VERIFIED: Read ADR-010].
  2. **Entry edits** of a linked memory or LTA entry: read the interaction, then call `editTouchpointFullCore` with the new note, plus update the entry, in one `inWriteTransaction`. Do not add a second interaction-note writer; the comment at `recency-dao.ts:306` says it is "the ONLY exported edit path".
  3. **Create:** `recordTouchpoint` (`:268-293`) has no exported core. Add a composed DAO that inserts the interaction, inserts the linked entry and recomputes recency in one transaction. This is needed for Log Interaction "Also save to" (D-40). For the Add Note sheet (D-42), compose `editTouchpointFullCore` + insert entry.
  4. **AI flag writers:** `setMemoryAllowAiCore` (`memories-dao.ts:141-157`) and `ai-permissions-dao.ts` `setSelectedPermissions` (`:345-380`) must also set the partner row's flag.
- **AI read, fail-closed on both sides** (D-49, D-31):
  - Memory branch: today `MEMORY_AI_ELIGIBILITY = "allow_ai = 1 AND deleted_at IS NULL"` (`memories-read.ts:31`) [VERIFIED: Read]. Extend it in SQL: `… AND (interaction_id IS NULL OR EXISTS (SELECT 1 FROM interactions i WHERE i.id = memories.interaction_id AND i.allow_ai = 1))`.
  - Interaction-note branch: today it is gated in **JS** (`row.allow_ai === 1 && row.note?.trim()`, `ai-context-read.ts:191`) [VERIFIED: Read]. Move it to SQL and add `AND NOT EXISTS (SELECT 1 FROM memories m WHERE m.interaction_id = interactions.id AND m.allow_ai = 0)`.
  - Result: if a sync is ever missed, the text is withheld, never leaked. Optionally de-duplicate (a linked memory whose interaction is in the 3 newest notes is sent once) [recommendation].
  - LTA has no `allow_ai` and is never read by `ai-context-read.ts` (no `current_state` read there) [VERIFIED: Read]. This stays true.
- **History:** `readKnowledgeChanges` (`history-read.ts:260-292`) must skip entries with `interaction_id`, so there is no duplicate row. The interaction record gets a `linkedSections` tag list, and should use `entry_date` instead of `created_at`.
- **Profile:** the LTA projection carries `interactionId` for tap-through. History page and See all: same.
- **Merge restore divergence:** handled by the 2.5 post-write pass.
- **Cost:** about 6 writer touch points (`recordTouchpoint` composition, `editTouchpointFullCore`, the entry-edit composition, `setMemoryAllowAiCore`, `setSelectedPermissions`, the restore post-pass), 2 AI SQL predicates, the `history-read` change, and 2 FK columns. Text is stored twice. The AI Permissions review list shows the pair twice (memory item and interaction-note item); recommend listing linked memories once, under the interaction.

**C. SQLite triggers** (`AFTER UPDATE OF note ON interactions` → update entries). This covers restore and raw writes structurally, but CLAUDE.md says "There is no RPC equivalent. Logic that would live in a Postgres function lives in TypeScript." The only existing trigger is a guard (`RAISE`, `011:181-186`), not logic. **Not recommended**; it is a fallback only if the owner prefers schema enforcement.

### 3.3 Edge cases the planner must decide (open questions Q2, Q4, Q5)

- One linked entry per interaction, or several sections at once? D-38's "can also be saved to" is ambiguous.
- Clearing a linked interaction's note to blank. Entry text cannot be blank (`assertMeaningfulValue`, `current-state-history-dao.ts:40-44`). Recommend blocking it with a `FieldError` while linked, or unlinking.
- Moving a linked entry into Off Limits (D-84). The same text stays in the interaction's note with its own `allow_ai`. **Recommend that the move sets the interaction's `allow_ai = 0` in the same transaction (narrowing only)**, or blocks the move for linked entries. This is security posture, so it goes to the owner.

So **multiline + `submitBehavior="submit"` gives the IME action key (Done/Send per `returnKeyType`), and Enter fires `onSubmitEditing` without a newline.** This was read on main, not the 0.86.2 tag [ASSUMED same in 0.86.2; device-verify].
- `returnKeyType` cross-platform values include `done` and `send` [CITED: textinput docs]. The 0.85/0.86 docs also list `enterKeyHint` [CITED: websearch summary of the 0.85/0.86 docs].
- `numberOfLines` is the max lines, and Android has a separate `rows` [CITED: textinput docs]. "Grow to about 3 lines, then scroll": use an auto-growing multiline input capped by `maxHeight` (≈ 3 × lineHeight + vertical padding from theme tokens) with internal scroll [ASSUMED standard RN behaviour; device-verify cursor-in-view].
- Keyboard events: "Only `keyboardDidShow` and `keyboardDidHide` events are available on Android. The events will not be fired when using Android 10 or below if your activity has `android:windowSoftInputMode` set to `adjustResize` or `adjustNothing`." [CITED: reactnative.dev/docs/keyboard]. The test phones run Android > 10 [ASSUMED, check the runbook]. Read `Keyboard.metrics()` on focus too, in case the keyboard is already up.

### 4.3 Recommended approach (Claude's discretion)

1. **`EntryTextField`** (shared component; D-66 "built as one shared field"):
   - `multiline`, `submitBehavior="submit"`, `returnKeyType="done"` (or `"send"` per surface), `onSubmitEditing={save}`.
   - Auto-grow capped at about 3 lines via `maxHeight`; theme-token typography and colours only.
   - Optional newline strip in `onChangeText` for pasted text [recommendation; D-66 says Enter adds no newline, paste is unspecified].
   - The visible Save button stays (D-66), disabled while blank and guarded against double taps (D-89).
2. **`useKeyboardCentering({ scrollRef, contentRef })`**, reusing `useFirstErrorReveal`'s refs:
   - On focus, and on `keyboardDidShow`: get the keyboard top from `event.endCoordinates` (`screenY`, or window height minus `height`).
   - Get the field's content-y and height via `measureLayout(contentRef)`, and the ScrollView's window frame via `measureInWindow` (reliable under edge-to-edge since 0.86).
   - **Pure helper `centeredScrollY({fieldY, fieldH, viewportTop, viewportBottom, keyboardTop, scrollY, contentH})`** → target scrollY so the field's centre sits at the centre of `[viewportTop, min(viewportBottom, keyboardTop)]`, clamped. Unit-test it like `sheetKeyboardLayout`.
   - **Add a bottom spacer equal to the keyboard overlap while the keyboard is up.** If the window is not resized (edge-to-edge), the ScrollView extends behind the keyboard and the last fields cannot scroll far enough to centre. The overlap must be computed the robust way `sheet-contract` does: keyboard height minus whatever the frame already shrank.
   - Call `scrollTo({ y, animated: true })` once. This is native-driven, not per-frame React state (CLAUDE.md animation rule).
3. **Do not use KeyboardAvoidingView** for these forms. The memory note `adb-tap-false-negatives` records: "KeyboardAvoidingView does NOT lift absolute-positioned elements … multiline surfaces need a keyboard-height offset" (fact/practice note, not an owner rule). The forms are ScrollViews, and the hook above is the offset.

### Anti-Patterns to Avoid
- **Throwing on odd legacy data in 033.** This locks the user out permanently (1.5).
- **Equal counts as proof.** Use a per-row uid mapping and re-read every destination (runbook Pitfall 7).
- **Importing the shared kind→home map into the migration.** Freeze the literals and test-pin them (runbook Pitfall 9).
- **A second interaction-note writer.** Compose `editTouchpointFullCore` instead (ADR-010; `recency-dao.ts:306`).
- **Gating AI in JS only.** D-13 says it fails closed in SQL. The interaction-note branch is JS-gated today (`ai-context-read.ts:191`).
- **KeyboardAvoidingView around absolute bottom surfaces** (memory note; Item 4).

## Common Pitfalls

### Pitfall 1: The migration plan is wider than it looks
**What goes wrong:** the plan lists DAO files but not the SQL-string consumers and tests. Vitest then goes red across about 24 files.
**Why:** tsc cannot see SQL, and about 81 tests migrate to `TARGET_VERSION`.
**How to avoid:** put every file in the 1.6 lists plus the test lists in the migration plan's `files_modified`, or shim deliberately (memory note `orphaned-test-consumer-build-breaker`).
**Warning signs:** `no such table: fuel`, `no such column: is_current`.

### Pitfall 2: Source-reading contract tests break with ENOENT, not tsc
**What goes wrong:** these tests `readFileSync` retired files and fail when the file is deleted: `control-a11y-contract.test.ts:141` (FuelEditor), `save-hold-busy-ref-contract.test.ts:125,195,215,332` (MemoryScreen), `ai-enablement.test.ts:38-41` (MemoryScreen, ThingsToRememberScreen, PostLogNoteEditor), `editor-cancel-contract.test.ts:42-43` (MemoryScreen, MemoryEditor), `display-date-contract.test.ts:149-150, 237, 279` (ThingsToRememberScreen, MemoryEditor), `services/reach-out/handoff.test.ts:212` (OffLimitsEditorScreen), `post-log-edit-memory-scroll-contract.test.ts:19` (PostLogNoteEditor memory edit) [VERIFIED: grep].
**How to avoid:** move each assertion to the replacement file in the same plan that deletes the original.

### Pitfall 3: `016-contact-knowledge.test.ts` migrates to TARGET_VERSION
See 1.7. Pin it to 16.

### Pitfall 4: Dashboard line 3 starts showing shares
`dashboard-knowledge-read.ts:67-99` reads **all** memory types except `'birthday'`. New Gift Ideas and Thought of Them rows, including shares, appear on Dashboard list cards automatically. That is a new glanceable surface (Q6).

### Pitfall 5: Share AI default
`addMemoryCore` seeds `allow_ai` from the `"memory"` default except for `provenance === 'import'` (`memories-dao.ts:103-108`). Shares must be forced to 0 (D-57). Typed Gift Ideas and Thought of Them use their **own** defaults (D-61). Recommendation: `provenance === 'share'` → 0, structural like ADR-091, plus a per-type default resolver. Keep `AiPermissionCategory` (`"memory" | "interaction-note" | "custom-field"`, `ai-permissions-dao.ts:15-18`) for the review list rather than widening the closed union.

### Pitfall 6: Off Limits through linked notes or moves
See 3.3. Moving a linked entry into Off Limits leaves the text in an AI-eligible interaction note unless the move narrows it.
