## Critical Issues

### CR-01: Migration 033 and the v7 converter silently drop the label of a "Recent" item that has both a label and text (one-way data loss)

**Files:**
- `src/db/migrations/033-knowledge-homes.ts:558` (`const value = firstNonBlankFrozen(row.text, row.label, row.url);` — the insert at :564-580 has no label column)
- `src/db/legacy-fuel-mapping.ts:336` (the same rule, used by the v7 → v8 converter at `src/backup/v7-legacy-conversion.ts:376-390`)

**Issue:**
- `current_state_entries` has no label column. For a legacy `recent` row with both a non-blank `text` and a non-blank `label`, the mapping keeps `text` as `value` and discards `label`.
- The legacy FuelEditor let the user type a label for any kind (`git show 681add50:src/components/FuelEditor.tsx:373-377, 506-546`), so such rows can exist.
- After `DROP TABLE fuel` (step 9) the label cannot be recovered on that device. CLAUDE.md: "Anything a migration gets wrong is permanent for that user."
- The app itself treats this as data loss elsewhere. The move DAO lists exactly this drop ("label") in the D-85 confirm (`knowledge-move-dao.ts:308-311`), and D-85 says "Nothing is lost silently".
- RESEARCH §1.5 covered only blank text. It never addressed the "label and text both present" case, and no D-NN decision accepts this loss.
- The v7 converter has the same rule, so a restored v7 backup loses these labels too.

**Severity basis:** silent, irreversible loss of user-entered content in a one-way migration.

**Fix (owner call):** this changes the D-56 output shape, so it needs the owner's agreement before 033 runs on any device. One lossless option is to fold the label into the value when both are present. It must be changed identically in the frozen copy and in `legacy-fuel-mapping.ts`, with `legacy-fuel-mapping.test.ts` and the equivalence test updated:
```ts
// 033 step 7 (frozen) and mapLegacyFuelRow (shared), recent -> current_state
const value =
  !blank(row.label) && !blank(row.text)
    ? `${row.label}: ${row.text}`
    : firstNonBlankFrozen(row.text, row.label, row.url);
```
The other option is to route a `recent` row that carries both fields to a Memory instead (Memories keep `custom_label`). Either way, add a 033 test row `{kind:'recent', label:'Work', text:'new job'}` that asserts no text is lost.

## Warnings

### WR-01: The shared entry field turns all existing line breaks into spaces on the first keystroke, and the flattened text propagates to the linked interaction note

**Files:**
- `src/components/ui/EntryTextField.tsx:86` (`onChangeText={(text) => onChangeText(sanitizeEntryInput(text))}`)
- `src/components/ui/entry-text-logic.ts:13-16`
- Consumers:
  - `src/components/MemoryEditor.tsx:756-762`;
  - `src/screens/MemoryHistoryScreen.tsx:188-196`;
  - `src/components/OffLimitsForm.tsx:150`;
  - `src/components/RelationshipEditor.tsx:426`;
  - `src/screens/EditContactScreen.tsx:1617, 1691`;
  - `src/screens/CreateContactScreen.tsx:877, 947`.
- Propagation:
  - `src/db/memories-dao.ts:421-432` (memory edit → `editInteractionNoteCore`);
  - `src/db/current-state-history-dao.ts:326-337` (Last Talked About edit → `editInteractionNoteCore`).

**Issue:**
- `sanitizeEntryInput` replaces every newline in the whole string, not just a newly typed or pasted one. Opening a stored multi-line value and changing one character rewrites all of its paragraph breaks as spaces.
- Stored multi-line values are routine:
  - imported Contacts notes are written verbatim as `memories.value` (`src/db/imported-contact-dao.ts:166-175`, `src/services/import/source-consolidation.ts:236-243`) and are editable in the Imported section editor and on Edit Contact (D-116);
  - interaction notes are entered in a multiline `TextInput` (`TouchpointRefineForm`).
- For a `note`-linked entry (D-37), fixing a typo in its Last Talked About or memory copy also rewrites the interaction note through `editTouchpointFullCore`. The History note loses its formatting with no warning.
- D-66/D-114 decided that *pasted or typed* line breaks become spaces. Neither decision covers rewriting line breaks that are already stored, and on another record.

**Fix:** sanitize only what the user inserted, not text that is already stored. For example, in `EntryTextField`, pass through any change whose newline count is not greater than that of `value`, and flatten only a newly inserted break:
```ts
const count = (s: string) => (s.match(/\r\n|\r|\n/g) ?? []).length;
onChangeText={(text) =>
  onChangeText(count(text) > count(value) ? sanitizeEntryInput(text) : text)}
```
Alternatively, keep `sanitizeEntryInput` for new entries only and use a plain multiline field when editing a stored value that already contains a line break. Also, `normalizeEntryText` at save must not re-flatten stored breaks; check the save paths in `MemoryHistoryScreen` and `OffLimitsForm`.
