## Strengths

- **[38.4-01]** The index migration is additive and registered through the existing ordered `MIGRATIONS` list. The plan calls for tests from both v1 and v30.
- **[38.4-02, 11, 15]** Conditional performance and accessibility changes have evidence gates. The native expo-modules-core remedy remains an owner decision under D-25.

- **[38.4-10, 12, 16]** The wave ordering accounts for files edited by earlier plans.

## Concerns

- **HIGH [38.4-01] — “Results identical” is broader than the range predicate can guarantee.** The current reads accept rows through `date(occurred_at)` ([your-week-read.ts](/home/bwales/projects/orbit-app/src/db/your-week-read.ts:38)). Restore writes backup `occurredAt` strings directly into both tables ([restore-apply.ts](/home/bwales/projects/orbit-app/src/backup/restore-apply.ts:654), [restore-apply.ts](/home/bwales/projects/orbit-app/src/backup/restore-apply.ts:823)). A timezone-suffixed value can satisfy the existing `date()` predicate yet fail the proposed lexical range before the residual is evaluated. The plan acknowledges this edge, but its parity must-have and threat disposition still describe exact preservation. **DECISION-COLLISION: D-18 / ADR-148** if execution treats dropping a previously counted restored row as an accepted fix without an owner ruling on that behavior.

- **HIGH [38.4-14] — Import Complete focus is not read-only as planned.** The proposed focus callback calls `load()`, whose `readImportCompleteSummary()` first calls `finalizeSessionIfTerminal()` ([ImportCompleteScreen.tsx](/home/bwales/projects/orbit-app/src/screens/ImportCompleteScreen.tsx:50)). The plan’s “focus path calls only the read” assertion and proposed source-scan test would miss that transitive write. Trace the finalizer’s effects and decide how a focus refresh can meet D-10’s no-write requirement.

- **MEDIUM [38.4-04, 17] — Opening the model picker can refresh the catalog.** Its existing load path calls `refreshOpenRouterCatalogIfStale({ fetchImpl: fetch, … })` automatically ([AIModelPickerScreen.tsx](/home/bwales/projects/orbit-app/src/screens/AIModelPickerScreen.tsx:97)). Plan 17 says “no catalog refresh” during verification, yet its saved-model check opens this screen. Specify a network-free verification path or explicitly account for the automatic request. Model choice also calls `activateAiConnection()` ([AIModelPickerScreen.tsx](/home/bwales/projects/orbit-app/src/screens/AIModelPickerScreen.tsx:141)); restoring only the remembered model may leave the active connection changed.

- **MEDIUM [38.4-14] — The favourite test should exercise completion ordering at the screen seam.** The current success callback applies an optimistic `setRows` outside the scheduler ([HomeScreen.tsx](/home/bwales/projects/orbit-app/src/screens/HomeScreen.tsx:1349)). A pure scheduler test can prove token invalidation, but cannot prove two rapid write completions publish the final committed membership in Home. Add a screen-level ordering test or device procedure that controls both write and read completion order.

- **LOW [38.4-02] — Resource tests need the actual publication path.** `mergeResources` retains departed keys, while `publish` currently merges even for a settled update ([use-orrery-switch-runtime.ts](/home/bwales/projects/orbit-app/src/components/orrery/use-orrery-switch-runtime.ts:170), [use-orrery-switch-runtime.ts](/home/bwales/projects/orbit-app/src/components/orrery/use-orrery-switch-runtime.ts:254)). Pure helper cardinality tests are useful, but at least one hook-level test should verify `finish`, generation-checked prune, and a following non-switch publication together.

## Suggestions

1. **[38.4-01]** Resolve the restored-timestamp parity decision before changing predicates. Make the test and documentation state the chosen behavior consistently; do not claim exact parity if the accepted input set is narrower.
2. **[38.4-14]** Separate terminal-session finalization from summary retrieval, or revise the focus-path contract after tracing the finalizer and obtaining any decision needed to allow its write.
3. **[38.4-04, 17]** Disable or stub the automatic catalog refresh in the device verification route, and record the active connection as well as the remembered model before and after testing.
4. **[38.4-02, 14]** Add tests at the runtime publication seams alongside the proposed pure-helper tests.

## Risk assessment

The remaining concerns are bounded verification gaps. That gate will very likely fail on first run, and an executor under pressure to satisfy a red gate is exactly the failure mode CLAUDE.md's decision-collision guidance warns about (a "bug fix" to a failing check quietly narrowing scope beyond `SYSTEM_ALERT_WINDOW`).

## Strengths

- **Exceptional grounding.** Nearly every plan cites file:line evidence that I verified matches the code on disk exactly, including subtle bugs (e.g., `use-orrery-switch-runtime.ts:264` merges old resources whenever `current.length` is truthy, regardless of `isSwitch` — Plan 02's fix is not cosmetic, it's a real bug fix I confirmed by reading the function).
- **Boundary math is actually correct.** Plan 01's `occurred_at >= date(?) AND occurred_at < date(?, '+1 day')` range predicate relies on SQLite's lexicographic TEXT comparison behaving correctly against `'YYYY-MM-DD HH:MM:SS'` stored values vs `'YYYY-MM-DD'` bound literals at both boundaries (a day-after row at exactly `00:00:00` is correctly excluded because a string that is a strict prefix of another sorts before it). This is non-obvious and the plan gets it right, then requires exactly the boundary tests needed to prove it.
- **Clean wave partitioning.** I did a file-collision sweep across all Wave-1 plans (01–08, 10, 11) and found no two plans in the same wave touching the same file; doc files that multiple plans want to append to (`digest.md`, `interaction-history.md`, `dashboard.md`, `app-shell.md`, `profile.md`) are consistently pushed to a later wave by the plan that would otherwise collide.

- **No decision reversals found.** Every touch of an owner-reserved surface (Standard-Light glass opacity, protected Galaxy Dark hues, artwork, permissions) defers to the existing ruling or escalates properly.

## Concerns

- **HIGH [38.4-13]** — Task 1's automated verify gate hardcodes the expected post-fix permission set as exactly `{CAMERA, INTERNET, READ_CONTACTS, READ_EXTERNAL_STORAGE, RECEIVE_BOOT_COMPLETED, RECORD_AUDIO, VIBRATE, WRITE_EXTERNAL_STORAGE}` (8 entries). `app.config.ts:137` registers the `expo-notifications` plugin, whose Android config plugin adds `android.permission.POST_NOTIFICATIONS` (Android 13+ notification permission) at prebuild — I found no `blockedPermissions`/removal for it anywhere in `app.config.ts` or `plugins/`. The resolved manifest almost certainly contains more than 8 permissions, so this gate will likely fail as written. Given the task's acceptance criteria treat gate-pass as proof of correctness, an executor hitting the failure has to choose between (a) correctly recognizing the allowlist is stale and updating it, or (b) mistakenly treating the extra permission as evidence something needs to be trimmed — which would violate D-09's "No other permission changes." The plan should either derive the expected set from a live `introspect` run at plan-check time (the way D-06 requires for migration heads) or explicitly enumerate and justify every permission expo-notifications/other plugins are known to add.
- **MEDIUM [38.4-03]** — The D-24 "STOP HALTS THIS PLAN" rule lives inside a `type="auto" tdd="true"` task (Task 2), not a `type="checkpoint:decision"` task the way Plan 15's D-25 gate does it. If the execution harness's checkpoint/pause behavior is keyed off the task `type` attribute (as Plan 15 implies), an "auto" task that internally decides to stop via prose instruction ("Return `## CHECKPOINT REACHED`") may not reliably halt wave progression or block dependent plans the way a formally typed checkpoint does. Given `autonomous: false` is set at the plan level, this is probably caught at the plan boundary — but the inconsistency between the two STOP mechanisms in the same phase (Plan 03 prose-based vs. Plan 15 typed) is worth reconciling before execution.
- **MEDIUM [38.4-11]** — The plan is `autonomous: true` but its tasks require extensive live `adb`/`emu-connect` driving of the owner's physical Pixel (tapping the FAB open/closed, capturing `uiautomator dump`s, changing `font_scale`/`wm density`, and — in Task 3 — using a synthetic ZZ-UAT contact in Recently Deleted for a real permanent-delete flow). CLAUDE.md's device runbook explicitly frames `adb`/`emu-connect` invocations as needing the owner present ("outside YOLO mode these commands prompt for approval — that is expected at the human checkpoint"), and this project's own memory log (`adb-tap-false-negatives`, `logbox-toast-blocks-tab-taps`) documents repeated device-driving mishaps. Marking a plan with this much unsupervised device interaction `autonomous: true` is inconsistent with that established caution, even though the individual commands will still hit the permission prompt.
- **MEDIUM [38.4-17]** — Same device-autonomy concern at larger scale: the plan drives font_scale/density changes, a real notification/AI-master toggle sequence, and — critically — a `assembleRelease` build that gets installed and then must be reinstalled with debug afterward. A partial failure mid-sequence (e.g., after the release install but before the debug reinstall, if the session terminates) would leave the owner's Pixel on the non-debuggable release build, silently breaking any of the owner's own subsequent on-device debugging until noticed. The plan's own acceptance criteria do check for this ("debug APK is reinstalled afterwards"), but there's no explicit recovery instruction if a mid-sequence device/tool failure interrupts the process before that final step.
- **LOW [38.4-16]** — Task 2's `accent-text-glass-contract.test.ts` is scoped to whatever the inventory in `38.4-RG029-INVENTORY.md` records as "misroles on glass" — but that inventory is produced by Plan 03 (wave 1) while Plan 16 executes in wave 4, after Plans 04–14 have all landed and potentially moved or deleted the exact line anchors the inventory recorded. The plan does anticipate this ("if a row's site no longer exists... mark it obsolete") but the `files_modified` list for Plan 16 is described as a "planning-time superset," meaning the actual touched-file set is determined at execution time from a document written three waves earlier — a real, if bounded, staleness risk that the plan handles reasonably but doesn't eliminate.
- **LOW [38.4-01]** — The accepted timezone-suffix edge case (a value like `2026-09-26T23:18:00+02:00` written only via a hand-crafted/restored backup) is explicitly documented as unrepaired, consistent with 38.2 D-23 ("no legacy-data repair"). This is a deliberate, disclosed tradeoff rather than an oversight, but worth flagging as an actual (if narrow) behavior change risk for anyone restoring a foreign-format backup after this phase ships — the *range* predicate could now silently exclude a row from Your Week that the old `date()`-only predicate would have included, in that one accepted case.
- **LOW [38.4-09]** — `MIN_CELL`/`MAX_CELL` values are "planner discretion... within the rulings" (D-13), and the plan's own 320dp fit test is described as deriving its expected value from "the number... document it in the test" rather than a value fixed at plan time. This is fine methodologically, but there's no cross-check in the plan against the *other* narrow-device fixture already recorded in 38.3-UAT.md (Moto Razr / `wm density 720`/`660`) to make sure the chosen `MIN_CELL` doesn't regress the owner's own prior "no overflow, just empty space" observation into actual overflow at the extreme end of the density sweep.

## Suggestions

- For 38.4-13 Task 1, replace the hardcoded 8-permission list in the verify command with either (a) a snapshot taken from `npx expo config --type introspect` on the pre-change tree, diffed against the post-change tree with an explicit assertion that the only removed entry is `SYSTEM_ALERT_WINDOW` and no entries were added/removed otherwise, or (b) an explicit, justified list that includes every permission a registered plugin is known to add (notably `POST_NOTIFICATIONS`), verified once at plan-check time the same way D-06 requires for the migration head.
- Convert 38.4-03 Task 2's D-24 STOP rule into a proper `type="checkpoint:decision"` task (mirroring 38.4-15 Task 3) rather than a prose convention inside an `auto` task, so the halt behavior is enforced by the harness rather than by the executor's compliance with a paragraph.
- For 38.4-11 and 38.4-17, consider explicitly gating the device-driving tasks behind a human-present precondition in the plan text (not just relying on tool-level permission prompts), given this project's own memory log documents repeated adb-driving false negatives and the release/debug-reinstall sequencing risk in 17 has a real (if narrow) failure window.
- 38.4-16: add a cheap pre-check at the start of Task 2 that re-greps the inventory's recorded anchors against the current file contents before editing, and fails loudly (rather than silently treating a moved line as "obsolete") if the anchor text is present but at a different, unexpected location — reducing the chance of misclassifying a still-live site as removed.

The one concrete defect (38.4-13's stale permission allowlist) is real and could cause an executor to chase a false gate failure in a security-relevant area (Android permissions), but it's a narrow, single-task issue with an easy fix, not a structural flaw in the phase.
