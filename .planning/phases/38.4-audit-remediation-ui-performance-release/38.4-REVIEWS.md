## Claude Review

## 1. Cycle-2 fix verification

**RESOLVED**, with evidence.

The cycle-2 finding (raw-luminance extrema instead of per-regime composite extrema) is fixed soundly in `aebbbba`. I verified the underlying math against the actual implementations on disk, not just the plan prose:

- `src/theme/tokens/surface.ts:356-364` (`alphaComposite`) blends **per-channel, independently**, on raw 0–255 sRGB bytes: `C_c = α·T_c + (1-α)·P_c`. For fixed `(tint, α)` this is monotonic non-decreasing in each background channel `P_c`.
- `src/theme/contrast.ts:31-54` (`relativeLuminance`) is a positively-weighted sum (0.2126/0.7152/0.0722) of a per-channel monotonic-increasing gamma function. Composed with the linear blend above, luminance of a composite is monotonic non-decreasing in each raw background channel.
- Consequence: for a **fixed regime** (tint/opacity), a synthesized pixel formed by taking the channel-wise **minimum** across several candidate pixels produces a composite luminance ≤ the composite luminance of *every* one of those candidates under that same regime — even if the synthesized pixel isn't a real pixel. The plan's "channel-wise MIN of the raw-darkest pixel and every regime's composite-argmin pixel" is therefore a mathematically valid (conservative) bound simultaneously across every regime that contributed a candidate. The symmetric MAX argument holds for the brightest bound. This is exactly the claim the plan makes and it checks out.
- The card/chrome regimes actually exercised by `surface.test.ts` today (`:188-208`, `:301-315`) are fully determined by `(package, mode, treatment)` via `palette[SURFACE[pkg].tintTokenKey]` (= `palette.surface`, unaffected by accent — confirmed against `accents.ts:131-141`) and `cardTintOpacity`/`chromeScrimOpacity`. That's a closed, enumerable 8-tuple regime table, so a Python port of it is feasible and the proposed `surface.test.ts` sync-guard (parsing the script's regime table and diffing against the TS-computed tuples) has something concrete to check against.
- Internal consistency: Task 2's `STATUS_FGS`/`rogue`/`accentText`/`danger` upgrade reuses the *same* 8 regime tuples (only the tested foreground changes with accent, never the tint), so Task 1's proof helper and Task 2's STATUS_FGS upgrade share one bound-computation path — no divergent contract between the two tasks.
- `backgrounds.ts` today declares only `brightestPixel` (no `darkestPixel` yet, confirmed at `:39-102`), consistent with Plan 03 Task 1 being the one to add it.

Two non-blocking residual concerns from the corrected proof (reported below, not blocking the RESOLVED verdict).

## 4. Concerns

**MEDIUM — `38.4-03`, Task 1: the cross-language regime-table sync guard is underspecified and could silently stop catching drift.**
`src/theme/tokens/surface.test.ts` (post-Plan-03) is asked to "read the script's regime table text and assert every `(tint, opacity)` pair the card and chrome suites composite appears in it." This means a TypeScript test regex/string-parses a **Python source file** to extract hex/opacity literals and diff them against values computed from `cardTintOpacity`/`chromeScrimOpacity`/`palette.surface`. The plan gives no normalization rule (hex case, `0.5` vs `0.50` vs `0.5000000001` from float formatting, trailing whitespace). A formatting-only edit to the Python script (e.g. re-running Black, or the script emitting `0.5` where the TS side computes `0.5000000000000001` due to floating-point `cardMatchesMode` branching) could make the guard spuriously fail, or — worse — a parsing bug could make it silently match nothing and pass vacuously, defeating exactly the T-38.4-03-02 anti-drift mitigation the plan cites. **Fix:** have the Python script emit its regime table as JSON (or the TS test import a small JSON/TS-literal artifact the script also writes), rather than regex-parsing Python source text; compare numeric values with `Number()` parsing + a small epsilon, not string equality.

**LOW — `38.4-03`, Task 1: the script composites every asset against all 8 regimes regardless of the asset's own package, which is more conservative than what `surface.test.ts` actually exercises for that asset.**
`surface.test.ts`'s card/chrome suites fix `pkg = slot.package` per asset and only vary `mode` (`:190`, `:303`) — so a `standard-*` asset is only ever tested against the two Standard-package tint regimes (both modes × 2 treatments = 4 regimes), never the Galaxy tint. The plan's script action says "for EVERY tint regime (a tunable table... each `(package, mode, treatment...)`" — read literally, this composites every asset (including Galaxy assets) against Standard's tint regimes and vice versa, which no test ever needs. This doesn't break correctness (a MIN/MAX bound that folds in extra, irrelevant regimes is still a valid — just needlessly tighter — bound), but it can make declared `darkestPixel`/`brightestPixel` bounds artificially more extreme than necessary, which feeds directly into Task 2's D-24 "lightness alone cannot pass" STOP threshold — i.e. it could trigger an unnecessary owner escalation that a package-scoped regime set would have avoided. **Fix:** scope each slot's regime iteration to `slot.package` only (4 regimes per asset, not 8), matching what `surface.test.ts` actually tests.
