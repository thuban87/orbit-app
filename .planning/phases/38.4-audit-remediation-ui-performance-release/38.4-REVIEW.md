## Warnings

### WR-01: Bulk setup overwrites an unsaved Bound/frequency choice on every focus and on the mount race

**File:** `src/screens/BulkImportSetupScreen.tsx:92-125` (reached through lane files `import-session-read.ts:81-94` and `bulk-import-setup-logic.ts:47-54`)

**Issue:** `load()` runs twice on mount, from the `useEffect` at :113 and the `useFocusEffect` at :120. It runs again on every later focus. Each run unconditionally does `setTrackingEnabled(saved.trackingEnabled)` / `setIntervalDays(saved.intervalDays)` (:104-105) from the persisted session. The session holds the user's choice only after Import or Combine, via `setSessionBatchDefaults` (:148, :212).

Two concrete scenarios:

- **(a) Mount race.** The screen opens and renders the `useState(false)` default. The user taps Bound, then Weekly, before the two mount reads resolve. The late `load()` resets the radio to the session's Unbound. With `edited` already true, the user can tap Import without noticing, and the whole batch is created Unbound.
- **(b) Focus return.** The user picks Bound + Weekly, then a notification tap or a widget deep link routes into another tab (`NotificationResponseGate`, `WidgetLinkingGate`). On Back to this screen, `useFocusEffect` reloads and silently restores Unbound, and also the persisted category (the category reset predates 38.4, but the lifecycle reset is new).

In both cases the user's explicit choice is dropped without notice. That choice decides whether reminders are created for every imported contact.

**Fix:** Restore from the session only until the user has edited, and stop the stale mount read from clobbering a newer choice:
```tsx
const editedRef = useRef(false);
// in every onPress/onChange: editedRef.current = true; setEdited(true);
const load = useCallback(async () => {
  ...
  setCount(counts.pending);
  if (!editedRef.current) {
    setCategoryId(session.batchCategoryId);
    const saved = initialBulkLifecycle(session);
    setTrackingEnabled(saved.trackingEnabled);
    setIntervalDays(saved.intervalDays);
  }
  setCategories(nextCategories);
}, [route.params.sessionId]);
```
Alternatively, keep the focus reload for `count` and categories only, and hydrate lifecycle and category once.

### WR-02: A batch can end with mixed lifecycles; the "one lifecycle for the whole batch" invariant is not enforced after a Combine or a partial pass

**File:** `src/screens/BulkImportSetupScreen.tsx:193-247, 295-341` and `src/db/import-session-dao.ts:501-528`

**Issue:** D-57 and the screen's own comment (:287, "one lifecycle for the whole batch") make the durable session the single source of the batch lifecycle. But `setSessionBatchDefaults` overwrites the session lifecycle at any time, and the setup screen keeps the Bound/Unbound radio and the frequency picker editable after rows have been resolved.

Two concrete scenarios:

- **After a Combine.** Setup is Bound + Weekly → Import → the consolidation prompt → Combine. `setSessionBatchDefaults` writes Bound, and `combineCluster` creates the merged contact **Bound, Weekly**. The user stays on setup (`sessionComplete` is false), switches to Unbound and taps Import. `startBatch` overwrites the session to Unbound, and the remaining rows are created **Unbound**.
- **After a stop.** The same happens after an "Import stopped" → Back to setup, where some rows are already imported under the first choice.

The session then records Unbound for a batch that already contains Bound contacts, so the completion report and resume can no longer say what was applied. The user gets reminders for some imported contacts and not for others, with no signal.

**Fix:** Freeze the lifecycle once any row in the session is resolved. In setup, disable the radio and the frequency picker, and show the saved choice read-only, when `counts.imported + counts.linked + counts.skipped + counts.failed + counts.needs_review > 0`. As a data-layer backstop, make `setSessionBatchDefaults` refuse a lifecycle change when any `import_session_rows.contact_id IS NOT NULL` exists for the session:
```ts
const resolved = await exec.getFirstAsync<{ n: number }>(
  "SELECT COUNT(*) AS n FROM import_session_rows WHERE session_id = ? AND contact_id IS NOT NULL",
  [sessionId]);
const current = await exec.getFirstAsync<{ t: number; d: number | null }>(
  "SELECT batch_tracking_enabled AS t, batch_interval_days AS d FROM import_sessions WHERE id = ?",
  [sessionId]);
if ((resolved?.n ?? 0) > 0 &&
    (current?.t !== (defaults.lifecycle.trackingEnabled ? 1 : 0) ||
     current?.d !== defaults.lifecycle.intervalDays)) {
  throw new InvalidImportLifecycleError("batch lifecycle is locked once contacts exist");
}
```
If the owner prefers mixed batches, record that and drop the "whole batch" wording instead. This is a product call.

### IN-01: Your Week range pre-filter silently drops offset-bearing timestamps; "keeps results exact" overstates the equivalence

**File:** `src/db/your-week-read.ts:5-12, 49-50, 87-88, 124-125`

**Issue:** The new conjunct `occurred_at >= date(?) AND occurred_at < date(?, '+1 day')` is a string-prefix window. `date(occurred_at)` normalizes values that carry a timezone offset to UTC.

I verified this with `node:sqlite`. The value `2026-09-27T23:30:00-05:00` was counted on 2026-09-28 by the old predicate. It is now counted on neither day: the range admits it only for 09-27, and the residual rejects it there.

Every live writer enforces strict `YYYY-MM-DD HH:MM:SS` (`log-guards.ts:31`), so today this is reachable only through a restored backup, because `backup-schema.ts` does not validate `occurredAt`.

**Fix:** Soften the header claim to "exact for the strict local wall-clock format every writer enforces". Optionally, validate `occurredAt` / `group_events.occurred_at` shape in the backup schema so the invariant the index relies on holds for restored data too.

### IN-02: `sessionBatchLifecycle` fails open to Unbound on an inconsistent session

**File:** `src/db/import-session-read.ts:81-94`

**Issue:** A session with `batch_tracking_enabled = 1` and a NULL or invalid cadence is silently read as Unbound. Every writer asserts today, so this is unreachable now. But if a future writer regressed, a user's Bound batch would import Unbound with no error, while `importContactRecord` would have rejected it loudly.

**Fix:** Throw `InvalidImportLifecycleError` when `batchTrackingEnabled` is true without a positive integer cadence, instead of returning `UNBOUND_IMPORT`. The driver's per-row catch then marks the rows failed rather than silently importing them Unbound.

### IN-03: `setSessionBatchCategory` is now dead and bypasses the one-write rule

### IN-04: Bound-effects plumbing is duplicated and inconsistent (awaited vs fire-and-forget)

**File:** `src/services/import/import-lifecycle-effects.ts:37-60`, `import-driver.ts:74-87, 241-243`, `import-acquire.ts:200-211`, `source-consolidation.ts:328-343`, `DuplicateReviewScreen.tsx:255-261`

**Fix:** Export one `runBoundImportEffectsSafely(exec, effects?)` helper, or reuse the lifecycle-effects module. Pick one policy for all four paths. Fire-and-forget matches the "never delays or fails the import" intent.

### IN-05: Unbound imports never reconcile the schedule, though Unbound birthdays can be reminder candidates

**File:** `src/services/import/import-lifecycle-effects.ts:10-11`, `import-driver.ts:241`, `source-consolidation.ts:328`, `import-acquire.ts:200`

**Issue:** The effects are gated on `lifecycle.trackingEnabled`. `listBirthdayNotificationCandidates` (`notification-read.ts:104-112`) also includes Unbound contacts when `birthday_unbound_enabled = 1`. An Unbound bulk import of contacts with birthdays is not scheduled until the next launch or foreground sweep. The gap predates 38.4 (no effects ran before), but the new module now encodes it as intended ("An Unbound import runs no effects, as before").

**Fix:** Run the reconcile whenever the pass created any contact with a birthday, or simply whenever it created any contact. The reconcile is idempotent and coalesced.

### IN-06: The Bound blurb over-promises for never-contacted imports

**File:** `src/screens/bulk-import-setup-logic.ts:25-26` (consumed by the D-57 flow)

**Issue:** "Bound adds every imported contact to your reminders at this frequency." Imported contacts have `last_contact` NULL, and `notification-schedule.ts:210-211` returns no decay reminder for them until a first touchpoint. The file's own comment says so. The copy therefore implies reminders that will not fire.

### IN-07: Whole-navigator a11y hiding now hangs on a transient entry that has no unmount cleanup

**File:** `src/navigation/RootNavigator.tsx:138-150` (with `UniversalFab.tsx:211-235`)

**Issue:** `TabNavigatorContainer` hides the entire tab navigator from TalkBack and Switch Access whenever `shellTransientStore` contains `fab-speed-dial`. `UniversalFab` removes that entry only in `closeDial`. Nothing closes it on unmount.

In production `UniversalFab` unmounts only with the whole tree, and `ready` never flips back in `App.tsx`, so this is not reachable today. But any future remount while the dial is open, such as a keyed remount after restore, would leave the entire app invisible to screen readers.

**Fix:** In `UniversalFab`, add `useEffect(() => () => shellTransientStore.getState().closeTransient(FAB_DIAL_TRANSIENT_ID), [])`.

**Scenario (bulk, 150 contacts):**

```tsx
// Unbound hides the picker: reset validity when switching to Unbound
onPress={() => { setEdited(true); setTrackingEnabled(bound); if (!bound) setIntervalValid(true); }}

// use `blocked` for disabled/colours, and early-return in onImport/startBatch/onCombine
```

### WR-01: A failed write on AI Data Permissions hides every count and empty-state line until the user leaves the screen

**File:** `src/screens/AIPermissionsScreen.tsx:153` (with `:108`, `:123`, `:179`, `:203`, `:225`)
**Issue:** One `error` state serves both the read and every write. The summary treats any non-null `error` as a failed read: `loadFailed: !loaded || error !== null` (line 153). Three write paths set `error`:
- a failed default toggle (`toggleDefault`, line 179)
- a failed impact review (`requestEnable`, line 203)
- a failed bulk apply (`applyPending`, line 225)

Only a successful `load()` clears it (line 123). None of those failure paths reloads, and there is no focus reload. So after one failed write, `buildPermissionSummaryCopy` returns all nulls, even though `items` still holds a clean read.

*Scenario:* the user flips "Allow AI for new Memories" and the write fails. The access line ("AI can currently access information from N contacts · M items"), the D-44 list line, and any "No information matches these filters." / "AI can't access any…" copy all disappear. The contact groups stay. The numbers D-44 requires to reconcile are gone until the user navigates away and back.
**Fix:** Split read failure from action failure, and derive counts only from the read:
```tsx
const [readError, setReadError] = useState<string | null>(null);
const [actionError, setActionError] = useState<string | null>(null);
// load(): setReadError(null) on success, setReadError(...) on failure
// toggleDefault / requestEnable / applyPending: setActionError(...)
loadFailed: !loaded || readError !== null,
// render {readError ?? actionError}
```

### WR-02: The AI Data Permissions "Enabled" caption uses the accent fill as text inside the glass card (about 2.2:1 on Standard Light / Dusk)

**File:** `src/screens/AIPermissionsScreen.tsx:405-411`
**Issue:** `color: item.enabled ? colors.accent : scoped.textSecondary`. `accent` is the fill role (ADR-084), not a text role. It is also read from the root palette, outside the `GlassSurface` scope, so the D-24/D-26 Standard-Light glass `accentText` variant cannot reach it.

With the Standard default slate-indigo fill `#4453B0` over Dusk's darkest composite `#94939A`, the contrast is about 2.2:1. That fails both AA 4.5 and AA_LARGE 3.0. Plan 20 recorded this exact site ("Plan 20 out-of-scope findings", `deferred-items.md`) and assigned it to Plan 21, which edited this file. It was not fixed. The glass-scope contract misses it because `accent` is not a glass-overridden token.

*Scenario:* in Standard Light on the Dusk or Mesh background, the "Enabled" label on each expanded item is hard to read against the card. That label is the one that tells the user AI can read this item.
**Fix:** use the scoped text role that is already in hand:
```tsx
style={{ color: item.enabled ? scoped.accentText : scoped.textSecondary }}
```
Add an `accent`-as-text guard to the Plan 16 Table C source contract so the next such site is caught.

### WR-03: The D-44 per-contact "AI can access N" count and each item's Enabled/Disabled state are not announced by TalkBack

**File:** `src/screens/AIPermissionsScreen.tsx:362-380`, `:385-419`
**Issue:**
- **Contact header.** The header `Pressable` sets `accessibilityLabel={`${expanded ? "Hide" : "Review"} ${group.contactName}`}`. On Android an explicit label replaces the aggregated child text, so `permissionGroupCaption` ("3 items · AI can access 1 · Review"), the D-44 reconciliation number, is never spoken.
- **Item row.** Each item `Pressable` sets `accessibilityLabel={`${item.label}: ${item.value}`}`, which hides the "Enabled"/"Disabled" caption. A screen-reader user can check an item but cannot hear whether AI can currently access it.

This screen exists to make AI access legible (RG-008, D-44). Its key facts are visual-only.

*Scenario:* a TalkBack user hears "Review Allison Phoenix, button, collapsed", then "Birthday: 3 May, checkbox, not checked". They are never told that only 1 of her 3 items is AI-accessible, or which one.
**Fix:**
```tsx
accessibilityLabel={`${expanded ? "Hide" : "Review"} ${group.contactName}, ${permissionGroupCaption(group, expanded)}`}
// item row:
accessibilityLabel={`${item.label}: ${item.value}, ${item.enabled ? "AI can access" : "AI can't access"}`}
```
Pin both labels with a test. Consider a caption variant without the trailing "Review/Hide" affordance, so it is not announced twice.

### WR-04: A selection survives filter, search and collapse, so the bulk consent change and the "N selected" count can refer to rows that are not on screen

**File:** `src/screens/AIPermissionsScreen.tsx:157-160`, `:431-449`, `:231-234`
**Issue:**
- `refs` is computed from the unfiltered `items` against `selected`.
- `selected` is never pruned when the type chip, the search, the "Enabled only" switch or the expanded contact changes.
- The bulk bar ("N selected", Disable/Enable selected) stays visible.
- The disable confirmation ("Remove AI access from the selected information?") names nothing.

This contradicts D-44's rule that every number on the screen reconciles with the list. Bulk enable/disable changes AI consent on items the user can no longer see.

*Scenario:* the user selects two of Abbe Vallen's memories, then searches "Allison" and selects one of hers. The bar says "3 selected" while only one checked row is visible, and "Enable access" makes all three available to AI.
**Fix:** either (a) clear `selected` when the filter, query or expanded contact changes, or (b) intersect it with the visible items:
```ts
const visibleKeys = new Set(filtered.map((i) => i.itemKey));
const refs = useMemo(
  () => selectedPermissionRefs(filtered.filter((i) => visibleKeys.has(i.itemKey)), selected),
  [filtered, selected],
);
```
With (b), the bar should show "N selected (M hidden by filters)". Option (a) is simpler and matches the screen's reconcile-everything rule.
