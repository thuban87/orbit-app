# Phase 38.4 Plan 03: Standard-Light Glass Contrast Proof and Foreground Scope Summary

**The contrast proof now composites over both declared extrema of every background asset and rejects mid-tone foregrounds. Its bounds are checked against the decoded art by a Pillow script. On Standard-Light glass and chrome a surface-scoped palette applies: secondary text resolves to primary, and status, rogue, danger and every accent's link text resolve to darker lightness-only variants. Opaque overlays reset to the root palette, and inputs get their own `textPlaceholder` token (RG-029, `ui-accessibility/AUD-UIA-001`; D-12, D-24, D-26, D-27).**

## Accomplishments

- **Both-extrema proof (Task 1, prior executor).**
  - Every background slot now declares a `darkestPixel`.
  - `scripts/measure-background-extrema.py --check` validates each declared bound against the per-regime COMPOSITE extrema of the decoded `.webp`. `--self-test` covers the fixture where raw-luminance order and composite order differ.
  - `surface.test.ts` asserts the floor at both extrema. It also requires the foreground luminance to lie strictly outside the composite interval, and it uses the same effective palette the app renders.
- **Glass foreground scope (Task 1).**
  - `resolveGlassForegroundPalette` is active only in Standard Light over an asset background.
  - `GlassSurface` cards, `ChromeScrim` and the `ShellAppBar` (title, Back, trailing content, overflow trigger) render inside `GlassForegroundScope`. There `textSecondary` resolves to `textPrimary`.
- **Status, rogue and danger variants (Task 2, prior executor).** Committed in `STANDARD_LIGHT_GLASS_VARIANTS` from the 97-hit inventory, all lightness-only.
- **accentText, all eight accents (Task 2, this continuation, owner ruling D-26).**
  - `STANDARD_LIGHT_GLASS_ACCENT_TEXT` is keyed by the resolved accent id.
  - Each value was re-confirmed against the proof. Dusk worst case is now 4.60–4.66 (was 1.98–2.58); Mesh is 5.80–5.87.
  - Exclusion E-2 is retired. The proof asserts `accentText` for every curated accent plus the default, in every package and mode, over both card and chrome.
  - The hue-preservation test also covers the accent variants. Aurora-teal and emerald have a 10% L floor, as owner-accepted under D-26.
- **Scope boundaries and `textPlaceholder` (Task 3).**
  - `ThemePalette.textPlaceholder` equals `textSecondary` in all four palettes. The preset changes are additions only, and the glass resolver never overrides the token.
  - The pure helpers `glassScopedTheme` and `unscopedTheme` back `GlassForegroundScope`, `UnscopedTheme` and the new `useUnscopedTheme()`.
  - `overlay-base` wraps overlay content in `UnscopedTheme`. `ConfirmDialog` and the `OverflowMenu` sheet read the root palette.
- **Runbook.** The maintenance runbook now covers `darkestPixel` and the `--check`, the interval proof, the scope and its reset points, `textPlaceholder`, and the rule that a new foreground on glass is proven or excluded in writing. It has a new Changelog section.

## Deviations from Plan

### Auto-fixed Issues

**1. [Owner-approved] The OverflowMenu sheet resets the glass scope inside `OverflowMenu.tsx`**
- **Found during:** Task 3
- **Issue:** `ShellAppBar` renders `OverflowMenu` inside `GlassForegroundScope`, and the menu's opaque `surfaceElevated` sheet is a raw RN `Modal`, not built on overlay-base. It would inherit the glass palette. `ShellAppBar` cannot reset only the sheet, because the trigger and the sheet live in one component.
- **Fix:** The trigger keeps the scoped palette. The sheet reads `useUnscopedTheme()` and is wrapped in `UnscopedTheme`. The owner approved this as within plan intent (owner response item 4).
- **Files modified:** `src/components/OverflowMenu.tsx`
- **Commit:** `e502ed2`

**2. [Rule 1 - Bug] ConfirmDialog body text read the scoped palette above its own overlay boundary**
- **Found during:** Task 3
- **Issue:** `ConfirmDialog` reads `colors.textSecondary` in its own render, above `BaseOverlay`. Wrapping overlay-base content in `UnscopedTheme` therefore would not reset the dialog's body text when the dialog is mounted inside a glass scope. The plan's truth "opaque sheets/dialogs are unchanged" would not hold.
- **Fix:** `ConfirmDialog` reads `useUnscopedTheme()`. `Sheet` and `Modal` read only `surface`/`border`, which the scope never changes, so they need no change.
- **Files modified:** `src/components/ui/ConfirmDialog.tsx`
- **Commit:** `e502ed2`

**3. [Rule 3 - Blocking] A strict `@/theme` test mock lacked the new export**
- **Found during:** Task 3 full-suite gate
- **Issue:** `orrery-controls-render.test.tsx` renders the real Sheet/Modal via overlay-base with a `vi.mock("@/theme")` that exports only `useTheme`. 7 tests failed with "No UnscopedTheme export".
- **Fix:** Added an `UnscopedTheme` pass-through to that mock. Galaxy has no glass override, so behaviour is identical.
- **Files modified:** `src/components/orrery/orrery-controls-render.test.tsx`
- **Commit:** `e502ed2`

**4. [Owner-bucket, HELD, no change made] Galaxy Light coral accentText, exclusion E-7**
- **Found during:** Task 2 continuation, when D-26 put `accentText` under the proof in every package and mode
- **Issue:** Coral's shared light link tone `#B03A26` measures **4.48:1** against the Galaxy Light presentation-density card: opaque 0.88 `#FBFCFE` over the darkest Galaxy pixel gives `#DDDEE0`, and the floor is 4.5. Comfortable (5.01), dense (5.49) and chrome (5.49) pass, and the other seven accents pass (4.79–5.82). This regime is outside Standard Light, so under the plan's STOP rule it is the owner's call. Every fix touches the owner's bucket: retune coral's shared `accents.ts` light tone by about 1% L, which also moves Standard Light links; widen the glass scope beyond D-12/D-24; or accept an exception.
- **Action:** Nothing was retuned. I added a narrowly scoped `held-for-owner` exclusion (galaxy / light / coral / card only). New tests require every held exclusion to be fully scoped and to be marked HELD in the inventory. The item is recorded in STATE Blockers/Concerns as non-blocking, in deferred-items.md, and in the windows ledger as a deviation.
- **Commit:** `7cbc61f`

**5. [Guard change, for transparency] The exclusion guard test distinguishes accepted and held exclusions**
- The prior guard ("the only non-Standard-Light exclusion is E-1") became "the only ACCEPTED non-Standard-Light exclusion is E-1", plus a new test covering held exclusions. Without this change E-7 could not be recorded. The narrowing is visible rather than silent, and it disappears when the owner rules on E-7.
