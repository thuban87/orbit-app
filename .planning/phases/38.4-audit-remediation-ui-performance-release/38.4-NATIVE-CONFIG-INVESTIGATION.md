## D-50 native theme

### Does `userInterfaceStyle` change anything on Android here?

**No.** It corrects the D-42 C rationale.

- `expo-system-ui` is not installed (`ls node_modules | grep expo-system-ui` is empty). Without it, prebuild falls back
  to `@expo/prebuild-config/build/plugins/unversioned/expo-system-ui/withAndroidUserInterfaceStyle.js:12-21`, which
  reads the key and **only** adds the warning "Install expo-system-ui in your project to enable this feature." It
  writes no resource.
- The clean prebuild confirms it: no `expo_system_ui_user_interface_style` string exists anywhere under `res\`, and the
  prebuild printed that exact warning.
- No other installed Android config plugin reads the key (a grep of `node_modules/**/*.js` for `userInterfaceStyle`
  outside iOS/web code finds only that fallback, RN's iOS-only Alert/ActionSheet specs and react-navigation's iOS
  header config).
- The DayNight AppTheme parent comes from the Expo template itself. It is present with `userInterfaceStyle: "light"`,
  so the key does not set the Android theme parent.

**Consequence for `app.json`:** the key stays unchanged (D-43 keeps D-42 C as shipped). D-42 C's stated reason ("it sets
the native Android theme parent") was wrong. The key is inert on Android and harmless to leave. It only has an effect
on iOS, which is not a target.

### Which theme do RN `Alert` and the datetimepicker dialogs use?

- **RN `Alert`** (`DialogModule` → `AlertFragment`). `onCreateDialog` calls `createDialog(requireActivity(), …)`.
  `isAppCompatTheme(activityContext)` (`AlertFragment.kt:84`) is true for an AppCompat theme, so it builds
  `androidx.appcompat.app.AlertDialog.Builder(activityContext)` (`AlertFragment.kt:142`). The dialog theme is the
  activity theme's `alertDialogTheme`. Under `Theme.AppCompat.DayNight` that attribute resolves from `values` or
  `values-night` according to the **activity's current night configuration**.
- **Date picker** (`RNDatePickerDialogFragment.getDialog`). Orbit never passes `display="spinner"` (grep of the five
  `DateTimePicker` call sites), so the default path is `new RNDismissableDatePickerDialog(activityContext, listener, …)`
  (`RNDatePickerDialogFragment.java:87`) → `DatePickerDialog(context, …)` with theme 0
  (`RNDismissableDatePickerDialog.java:42`). The platform resolves `android:datePickerDialogTheme` from the activity
  theme, which also follows the activity's night configuration. The spinner styles the library ships are DayNight too
  (`res/values/styles.xml`: `SpinnerDatePickerDialogBase parent="Theme.AppCompat.DayNight.Dialog"`).
- **Time picker** (`RNTimePickerDialogFragment.java:85-86`) follows the same default path with `activityContext`.

All three therefore take their light or dark look from the **activity's night configuration**. Today that is the
device's, because nothing overrides it. That is why the dialogs render light while Orbit is dark on a light device.

### Will `AppCompatDelegate.setDefaultNightMode` restyle them without recreating the activity?

**Yes.**

- RN 0.86 `Appearance.setColorScheme` (`Libraries/Utilities/Appearance.js:96-110`) calls
  `NativeAppearance.setColorScheme`. `AppearanceModule.kt:85-94` maps `"dark"` → `MODE_NIGHT_YES`, `"light"` →
  `MODE_NIGHT_NO` and `"unspecified"` → `MODE_NIGHT_FOLLOW_SYSTEM`, on the UI thread.
- MainActivity is a `ReactActivity` (an `AppCompatActivity`) and declares `uiMode` in `configChanges`.
- AppCompat's `AppCompatDelegateImpl.updateAppConfiguration` (bytecode of the AppCompat 1.7.1 AAR in the local gradle
  cache, via `javap -c`) takes the no-recreate branch when the activity handles `uiMode`. It skips
  `ActivityCompat.recreate` and calls `updateResourcesConfiguration`, which does `Resources.updateConfiguration` →
  `ResourcesFlusher.flush` → theme re-apply → `updateActivityConfiguration` → `Activity.onConfigurationChanged`. The
  version catalog pins AppCompat 1.7.0; both versions have the same branch.
- `ReactActivity.onConfigurationChanged` → `ReactDelegate.onConfigurationChanged` (`ReactDelegate.kt:237-246`) →
  `ReactHostImpl.onConfigurationChanged` → `AppearanceModule.onConfigurationChanged`, which emits `appearanceChanged`
  to JS if the scheme changed.
- The React tree is not recreated and state is kept. Dialogs built after the change read the updated activity
  resources and theme.
- An `Alert` or picker that is already open when the mode changes keeps its old look until it is reopened. This is
  not reachable in practice: the mode is changed on the Appearance screen, where no native dialog is open.

**The feedback-loop hazard, confirmed in source.**
- Once overridden, `useColorScheme()` reports the override. `AppearanceModule.getColorScheme()` reads
  `UiModeUtils.isDarkMode(activity)` (`UiModeUtils.kt:23-25`), which reflects the forced night mode.
- `Appearance.setColorScheme` also sets the JS cache directly (`Appearance.js:101-108`).
- So Orbit's own "System" mode must map to `"unspecified"` (FOLLOW_SYSTEM) and **never** to the resolved value.
  Otherwise a forced "dark" would feed back into `resolveMode("system", …)` and freeze System on the last forced value.
- With "system" → `"unspecified"`, the device scheme is reported again. For one JS tick, the JS cache
  (`Appearance.js:105-106`) may hold the pre-switch value, because `getColorScheme()` runs before the UI thread applies
  FOLLOW_SYSTEM. The `uiMode` configuration change then emits `appearanceChanged` with the real device scheme, and
  `useColorScheme()` re-renders `ThemeProvider` with it. This is a self-correcting one-frame lag, not a freeze.
- `setDefaultNightMode` with an unchanged value is a no-op in AppCompat, so re-applying the same mode (for example
  "system" at boot) does nothing.

### Verdict

**A: RN core `Appearance.setColorScheme` is sufficient.**
- The AppTheme parent is already DayNight (template, not `userInterfaceStyle`), and MainActivity handles `uiMode`, so
  no activity recreation and no parent-theme plugin are needed.
- No native package is needed (`expo-system-ui` is not required and is not added).
- The fix is JS-only. It drives the night mode from the active package's mode *setting*, with "system" →
  `"unspecified"`.

## D-48 storage audit

**Framing fact.** READ_EXTERNAL_STORAGE and WRITE_EXTERNAL_STORAGE are *dangerous* (runtime) permissions. With minSdk
24, a declaration alone never grants them. They are granted only by a runtime `requestPermissions` call, or by the user
turning on "Files and media" by hand in Android's App info. With `maxSdkVersion="32"` they do not exist on Android 13+.

**Who requests them at runtime.** A grep of `node_modules/**` and `modules/**` Kotlin/Java for `EXTERNAL_STORAGE`,
`getExternalStorageDirectory`, `getExternalStoragePublicDirectory` and `READ_MEDIA_` finds three hits:
- `expo-image-picker`'s `ImagePickerModule.kt:258-266` (`getMediaLibraryPermissions`, used only by
  `requestMediaLibraryPermissionsAsync` / `getMediaLibraryPermissionsAsync`, `:48-58`) and `:275-301` (the
  `launchCameraAsync` path). Orbit calls neither function and never calls `launchCameraAsync`.
- `expo-share-intent`'s `getAbsolutePath` (`ExpoShareIntentModule.kt:226-274`). This is unreachable: the committed
  patch returns early for anything but `text/plain` and handles text only (`:114-117`, `:128-141`).
- `expo-clipboard`'s `ClipboardFileProvider.kt:216`, which serves image-clipboard files only. Orbit calls only
  `Clipboard.setStringAsync` (`ComposeScreen.tsx:1044,1064`).

App JS has no `requestMediaLibraryPermissionsAsync`, no `MediaLibrary`, and no storage `PermissionsAndroid` call. The
only `PermissionsAndroid` use is READ_CONTACTS (`use-read-contacts-permission.ts:72-108`). **Nothing in Orbit ever
requests either storage permission**, so on a normal install they are never granted.

### Residual risk

A backup restore or backup share whose source is a **raw `file://` path** from a sender or file-manager app that
targets Android 6 or older (API < 24) needs READ_EXTERNAL_STORAGE to be *granted*.

- Orbit never requests the permission. **Today** that read therefore fails too, unless the user has turned on "Files
  and media" for Orbit by hand in Android's App info. Orbit never asks them to.
- On Android 10–12 (targetSdk 36, no `requestLegacyExternalStorage`), scoped storage stops a manual grant from exposing
  another app's non-media `.json` file by path anyway. The combination matters only on **Android 7–9** (API 24–28).
- Removing the pair changes behaviour for exactly one user: on Android 7–9, who has manually granted "Files and media"
  to Orbit, and who restores from an old (pre-Android-7-targeting) file manager that hands over a raw path. After
  removal, that restore fails, and the in-app "Choose backup file" through the system picker still works.

The declaration does not mitigate this for anyone else. The backup ingress has no `content://`-only scheme guard that
would make the permission irrelevant.

### Verdict

**KEEP.** Nine of the eleven rows are an unconditional "no" with source evidence. The two backup-ingress rows are "no" for every URI a modern
sender can produce, but not an unconditional "no": the legacy `file://` path depends on this permission when the user
has granted it by hand. That is real, if vanishingly narrow, and not mitigated in code. Under D-48 ("only if proven
100% unused … if any doubt remains, do not remove them") and this plan's residual-risk rule, the pair stays. The
evidence goes to the owner (Task 3).
