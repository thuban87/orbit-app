Gap closure G2 (owner ruling D-33): the Contacts (Home) screen freeze.

**Owner report (2026-09-26):** choosing a population, a filter or a sort-order action from the controls at the top of the Contacts screen makes the app unresponsive. Tabs cannot be switched and a force-restart is needed. The setting change **is** persisted. The owner reproduced it on the Pixel 3a by changing population. The report also carries a Plan 11 observation, **E**: twice, a warm `orbit://contact/<id>` deep link or a Quick Log snackbar left the Profile ScrollView ignoring swipes until a cold start. It may be the same class of defect, or an adb-injection artifact (`deferred-items.md` Plan 11). Neither was tracked anywhere before. Requirement `GAP-G2`.

**Investigation-first.** No fix is chosen before the freeze is reproduced and classified on hardware. Verified on disk at planning, as a starting map only; the root cause is not assumed:
- `DashboardControlRow.tsx`:
  - The three controls open a request in `dashboardPanelStore` (`open`/`openFilters`/`openSort` ~:172-238). The toggles write through `useDashboardQueryStore.getState().setPopulations/setFilters/setSort(getExecutor(), …)` (~:98-170) behind `pending` guards captured in `useCallback` closures.
  - Three `useEffect`s re-`open()` the active request with fresh content whenever store state changes (~:240-292).
  - The row's wrapper has `zIndex: 20, elevation: 20` (~:442), while the panel root has `zIndex: 10, elevation: 10` (`AnchoredPanel.tsx` ~:150).
- `AnchoredPanel.tsx` registers a `"dashboard-panel"` shell transient on `visible` (~:84-97), steals accessibility focus, and animates with Reanimated.
- `DashboardOverlayHost` renders inside `HomeScreen` (~:1944).
- HomeScreen:
  - It derives inertness from `dashboardPanelStore(selectPanelOpen)` (~:529, ~:1714-1717, ~:1775-1780; 38.3 RG-020, `0d012d2`).
  - It subscribes to the query store with `useShallow` (~:419-426). The comment there records a previous "Maximum update depth exceeded" loop.
  - Its reads go through the 38.3 refresh scheduler (`973f6c6`, `4618dc9`, `6e820ae`), which Plan 14 extends with a `"favourite"` source.
- `RootNavigator.handleActiveTabPress` dismisses the top shell transient instead of acting when the ACTIVE tab is pressed (~:95-120).
- Known false freezes on this hardware, which the investigation must rule out rather than report as the bug:
  - The debug-build LogBox toast, which overlays the tab bar and eats tab taps (memory `logbox-toast-blocks-tab-taps`).
  - adb taps missing small Pressables (memory `adb-tap-false-negatives`).
  - A full-screen overlay that is transparent but still touchable. That one is a real app bug.

**Folded in 2026-09-27: E1 (owner ruling D-51, `OA-E1`), a light investigation.** Contacts said "5 contacts" while the "All Contacts" population showed 25+ in Card view, and List view showed only 5 rows. On disk at planning:
- The header renders `counts.live` from `countLiveContacts` (`src/db/dashboard-read.ts` ~:612): bound, non-archived **contacted** contacts (HIGH-2). It is not the population's row count. That is the documented Phase 26 behaviour (`26-UAT.md` "Product observation": "count header stays total-live").
- List (`FlatList data={rows}`) and Card (`CardGrid rows={cardRows}`, where `cardRows = rows` outside selection mode) render the same `rows` from one read.
- So a count below the population size is by design. A List/Card difference for the same population is a real bug, plausibly the G2 class: the population change persisted, but the list was not re-read.

**Changed 2026-09-27: E1 count semantics (owner ruling D-55).** The header now shows what is actually on screen: the number of contacts the active view displays for the active population, filters and search. This supersedes the Phase 26 total-live rule (`26-UAT.md` "Product observation"; no ADR records it) and D-51's "record, don't change". Task 3 implements it test-first, before Task 4 re-verifies on the device. Verified on disk at planning:
- The header is `listHeader` in `HomeScreen.tsx` (~:1605-1618): `counts.live > 0` shows a `ChromeScrim`-backed `dashboard-header-count` Text reading `` `${counts.live} contact${…}` ``.
- The same `listHeader` element is passed to both views: the List's `FlatList` (`ListHeaderComponent`, `data={error || showInitialSkeleton ? [] : rows}`, ~:1863-1899) and `CardGrid` (`listHeader`, `rows={cardRows}`, where `cardRows` is `rows` filtered to the frozen universe in selection mode, ~:490-492, ~:1923-1944). So one helper covers both views.
- `counts.live` also feeds `selectDashboardEmptyState` (~:1590): the empty-state logic keeps reading it.

It runs beside Plans 15 and 18 with disjoint files (see the frontmatter note). Plan 16 (wave 5) depends on this plan, because it also edits HomeScreen, DashboardControlRow, FilterPanelContent and Snackbar. Plan 17 re-runs the device rows.
