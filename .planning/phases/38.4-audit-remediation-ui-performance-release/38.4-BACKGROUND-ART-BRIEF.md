# 38.4 Background art brief: regenerate the backgrounds so bare text passes contrast

**For:** the owner, to hand to Codex (the image model that made the current art).
**Written:** 2026-09-26, against `main` at `738ae12`. Read-only on source code.
**Supporting files:** `38.4-art-brief/` (next to this file). It has per-image heat maps, band example sheets, CSV grids and `check_art.py`, the self-check script.

Every number carries a label:

- **MEASURED**: decoded from the shipped `.webp` bytes, or read from code on disk.
- **COMPUTED**: derived by formula from measured inputs (the WCAG contrast maths).
- **ESTIMATED**: read from layout styles or inferred, not measured on a device.

---

## One-page summary (read this first)

**The goal.** Text that sits straight on the background, with no card and no scrim behind it, has to be readable (WCAG AA: 4.5:1 for text and links, 3:1 for status glyphs). The owner wants this fixed in the art itself. The plan: squeeze each image's range of light and dark into a band where every text colour passes, and keep the look.

**What the numbers say.**

1. **Squeezing the range works, but only one mode per image.** The band that works is very different in light mode and dark mode:

   | Where the art is used | Art must stay in this band (before the app's light veil) | Grey swatch at the edge | Current art in that mode |
   |---|---|---|---|
   | **Galaxy, Dark mode** | L\* ≤ 8 (≤ 18.5 if red error text is exempt, like the existing E-1 exemption) | `#181818` (`#2D2D2D`) | Passes, except red `danger` text on the brightest wisps (0–1.1% of pixels) |
   | **Galaxy, Light mode** | L\* ≥ 87 | `#DADADA` | Fails on 100% of pixels (the art is near-black) |
   | **Standard, Dark mode** | L\* ≤ 22 | `#343434` | Fails on 86–100% of pixels |
   | **Standard, Light mode** | L\* ≥ 87 | `#D9D9D9` | Fails on 94–100% of pixels, **including Dawn and Paper** |

   L\* is perceived lightness: 0 is black and 100 is white. All COMPUTED from the palette tokens and veil, at the lightest-veil (worst) screen density.

2. **One image cannot serve both modes.** Light mode needs art at L\* 87 or above; dark mode needs L\* 22 or below. Those two ranges do not overlap. Even if every bare text used only the strongest colour (`textPrimary`), light mode would need L\* ≥ 53–55 and dark mode L\* ≤ 45–47. They still do not overlap. **This is the main finding.** Today every image is used in both modes, so every image fails in one of them.

3. **What that means in practice.** Each image needs to be painted for one mode:
   - Galaxy art: a dark, near-black space field with only faint, low-contrast colour. That is essentially what ships today. Only the brightest aurora/nebula wisps need to come down (or be exempt from red error text).
   - Standard art: a **pale** field. The whole image sits between about L\* 89 and 97 (cream, pale lilac, pale blue). That is much lighter than Dusk and Mesh today, and somewhat lighter than Dawn and Paper. The sheet `38.4-art-brief/band-examples-standard.png` shows each Standard image remapped into that band, so the owner can judge the look.

4. **Cards and the app bar stay safe.** Any art that meets the bare-text band above also keeps every existing card and app-bar contrast proof passing. Those proofs are looser (COMPUTED, §D).

**Owner decisions this raises** (none of them are Codex's call):

- **OD-1: What happens in the mismatched modes (Galaxy in Light, Standard in Dark)?** The options:
  - (a) ship a light **and** a dark version of each image. This needs a code change: today one asset per slot serves both modes.
  - (b) land the parked theme merge (Galaxy becomes Dark and Standard becomes Light), so each image only ever serves its own mode.
  - (c) keep a scrim only in those two combinations.
  - (d) accept failing bare text there.
  Option (c) is what D-35 already decided for Standard Dark.
- **OD-2: This strategy replaces recorded decisions.** "No scrims, fix the art" reverses **D-29** (scrim the failing bare text on Standard-Light Dusk/Mesh) and **D-35** (scrim it in Standard Dark on all four backgrounds). Both are still planned as Plan 16 Task 3, which has not been executed. The owner should restate or cancel that task before Plan 16 runs.
- **OD-3: D-29 assumed Dawn and Paper pass. They do not.** Bare `textSecondary` measures 2.95:1 on Dawn and 2.60:1 on Paper. `danger` measures 3.03 / 2.67, and the coral link 2.78 / 2.45 (MEASURED composite, COMPUTED ratio). Plan 03 only tabulated Dusk and Mesh, so this did not show up.
- **OD-4: Red error text in Galaxy Dark.** `danger` `#E5484D` is owner-protected (ADR-084, exclusion E-1 for cards). On bare art it forces Galaxy art down to L\* ≤ 8. If E-1 is extended to bare text, the ceiling is L\* 18.5 and today's Galaxy art already passes everything else.
- **OD-5: Two Galaxy images will be replaced anyway** (the owner's plan). The Galaxy band above applies to any new Galaxy art unchanged.

- **OD-6: Accent colour used as text on bare art.** 14 bare text sites (plus 9 spinners) draw with the accent **fill** colour instead of the link colour (`accentText`). ADR-084 calls this a misrole, and Plan 16 already plans the swap. If the swap does not land before the new art, the bands tighten to L\* ≥ 94 (light) and ≤ 15 (dark), which is nearly white and nearly black. The brief assumes the swap lands.

**How much bare text there is.** There are 294 bare text sites across 50 screens (100 hand-verified, 194 found by a script but not hand-read), plus 24 components that are bare only on some screens. Most of it is grey secondary captions (142) and primary text (105). It spans nearly the full width (x = 16 … W−16 dp) and mostly scrolls, so it can land anywhere over the fixed art. **Placing the lighter or darker areas away from text (the secondary lever) helps very little. Equalizing the whole image has to do the work.**

### A.3 How the image maps onto a phone (MEASURED: `BackgroundHost.tsx`; COMPUTED crop)

- `<Image resizeMode="cover">` is sized to `useWindowDimensions()`, absolutely filled and **fixed**: content scrolls over it and the art never moves. The host wraps the whole shell, including the status-bar area. `cover` scales the image to fill the window and centres it, so on phones the full **height** shows and the **sides** are cropped.

| Screen (dp) | Scale | Visible part of the 941×1672 image |
|---|---|---|
| Pixel 3a, 392×805 | 0.481 | x 63–878 (815 px wide), full height |
| Pixel 6 Pro, 411×890 | 0.532 | x 84–857 (773 px), full height |
| 20:9, 360×800 | 0.478 | x 94–847 (753 px), full height |
| 21:9, 384×896 | 0.536 | x 112–829 (717 px), full height |
| Foldable inner, about 673×841 | 0.715 | full width, y 248–1424 (top and bottom cropped) |

To convert on a Pixel 6 Pro: dp = (image_x − 84) × 0.532 and dp_y = image_y × 0.532. **Because devices crop different parts, the band must hold over the whole canvas.** Put visual interest in the central 717 px so it survives every crop.

## C. Text inventory: what sits bare on the art

**Method.** A TypeScript-AST walk (scratch script, not committed) visited every non-test `.tsx` under `src/screens` and `src/components`, excluding Orrery canvas components and `__dev__`. It looked at every AppText, RN `Text`, `Icon`, `TextInput`, `ActivityIndicator`, `Ionicons`, and every fill-less `Button` (the `tertiary` role, which draws `accentText`, and `iconOnly`, which draws `textPrimary`). From each one it walked up to the nearest backing, using Plan 03's classes (§0 of `38.4-RG029-INVENTORY.md`):

- glass: `GlassSurface`, `ChromeScrim`, `ShellAppBar`
- opaque: `surface`/`surfaceElevated`/`background` fills, `Sheet`/`Modal`/`ConfirmDialog`

Where a component had no backing of its own, the walk crossed component boundaries to **every render site**, up to the stack route. ## D. Cards and the app bar: how far the art may move without breaking them

Cards (`GlassSurface`), the app bar (`ShellAppBar`) and `ChromeScrim` tint over the art too. Their text is proven in `src/theme/tokens/surface.test.ts` against each asset's declared `darkestPixel` / `brightestPixel`, using the regimes in `scripts/background-extrema-regimes.json`. In Standard Light the glass palette from `glass-foregrounds.ts` applies (secondary text becomes primary, and there are darker status, danger and link variants).

| Regime (MEASURED tint and opacity) | Text it carries | Art range that keeps every proof passing (COMPUTED, grey-equivalent) | Binding colour |
|---|---|---|---|
| Galaxy Dark card and chrome, `#141828` @ 0.05 | root light palette, all 8 accents; `danger` exempt (E-1) | art **L\* ≤ 18.9** (`#2E2E2E`, Y ≤ 0.027) | `textSecondary` `#8B93B0` |
| Galaxy Light card @ 0.88, chrome @ 0.97, `#FBFCFE` | root light palette | any art | — |
| Standard Dark card @ 0.97, chrome @ 1.0, `#191C22` | root dark palette | any art | — |
| Standard Light card and chrome, `#FFFFFF` @ 0.5 | glass variants | art **L\* ≥ 14.2** (`#242424`, Y ≥ 0.018) | `danger` `#590E11` and the link variants (tuned to Dusk's darkest pixel `#292634`) |

**Result:** every bare-text band in §E sits inside these card ranges. Galaxy Dark bare ≤ 8 (or 18.5) is within card ≤ 18.9. Standard Light bare ≥ 87 is within card ≥ 14.2. So **art that meets its bare band cannot break a card proof**. The checker in §H verifies both, pixel by pixel.

One caveat: if new art ever serves a mode other than its package's matched mode (for example, a pale Galaxy image for Light mode under OD-1(a)), the card treatment for that combination is the opaque band. That passes over any art.

## E. Target luminance bands (the core deliverable)

### E.1 How the band is computed: a worked example (Standard Light, `textSecondary`)

1. The text colour is `textSecondary` `#565D6B`. Its relative luminance is Y_t = 0.1087 (COMPUTED from `theme-presets.ts`).
2. WCAG contrast is (Y_light + 0.05) / (Y_dark + 0.05). Normal text needs ≥ 4.5. The background is lighter here, so Y_bg ≥ 4.5 × (0.1087 + 0.05) − 0.05 = **0.6642**.
3. The background under bare text is the veil composited over the art, per channel in sRGB (as `alphaComposite` does). The veil is white `#FFFFFF` at 0.05 on presentation routes. For a grey art value g (0–255): c = 0.05 × 255 + 0.95 × g = 12.75 + 0.95g.
4. Y_bg = 0.6642 corresponds to an sRGB channel value of 1.055 × 0.6642^(1/2.4) − 0.055 = 0.8346, which is **213** of 255. So 12.75 + 0.95g ≥ 213, which gives g ≥ 210.8. Round up to **g = 211, `#D3D3D3`**.
5. As art: Y = 0.651, which is **L\* = 84.6**. Any art pixel at or above that lightness passes for `textSecondary`.
6. Repeat for every colour that can sit bare in that mode, including all eight user-selectable link accents. The band is the tightest result. In Standard Light that is the coral link `#AC3925`, at **L\* ≥ 86.7 (`#D9D9D9`)**.

For coloured pixels the grey equivalent is a guide. `check_art.py` does the exact per-pixel composite.

## G. Secondary guidance: where bare text lives (placement)

All ESTIMATED, from the AST layout reading in §C:

| Question | Answer |
|---|---|
| Horizontal | **Every** bare site is inset at least 16 dp. 234 of 318 span exactly **x = 16 … W−16**, the full content width; the rest are inset 20–44 dp. So on a 411 dp phone, bare text covers x ≈ 16–395 dp, which is 92% of the width. |
| Alignment | 63% left-aligned, 20% left-aligned in a row (Back button + title headers), 17% centred (loading, error and empty states; Capture grid labels). The left half carries the most text. |
| Vertical | 62% in **scrolling** content, which can land anywhere on screen because the art is fixed. 18% in top headers (about 26 fixed at y ≈ 0–70 dp below the status bar). 11% in a static body. 9% in centred states (around mid-screen). <1% fixed at the bottom. |

**Conclusion: placement helps very little.**

- Bare text effectively covers the whole width, and scrolling content can put it at any height.
- The only zones with less text are the outer 16 dp gutters (which the phone crop already partly hides) and the bottom ~90 dp above the tab bar.
- So **equalizing the luminance range (§E) has to carry the fix on its own.**

If any accent lighting remains, the least risky places, in order, are:

1. the outer 16 dp edges and the corners;
2. the bottom 10% of the image;
3. the **right** third rather than the left, because left-aligned text and headers weigh on the left.

Even there, the pixel must stay inside the band. H1 checks the whole canvas.
