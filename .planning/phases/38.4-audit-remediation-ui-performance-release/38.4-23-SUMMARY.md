# Phase 38.4 Plan 23: FAB Clearance and Permanent FAB Border Summary

**The FAB never hides a screen's last item: every FAB-bearing scroll screen now ends with the shared `useBottomClearance()` padding, enforced by a contract that derives the screen set from the tab-stack registrations; and the FAB carries a permanent 2dp `onAccent` ring on every screen (D-52 / OA-E3, D-56 / OA-C2, superseding D-45).**

## What was built

### Task 1 (tracer): route-derived clearance contract + AI Data Permissions (D-52)

`src/navigation/fab-clearance-contract.test.ts` builds the FAB-bearing screen table from source:
- tab stacks = the `@/navigation/tabs/*` modules `RootNavigator.tsx` imports (Dashboard, Digest, Events, Orrery, Settings; the orphan `BackupStack.tsx` is correctly excluded);
- routes from `<Stack.Screen name component>` and the `DIGEST_/EVENTS_ROUTE_COMPONENTS` maps;
- local route wrappers (`AIPermissionsRoute`, `BackupSettingsHostRoute`, `SettingsProfileHostRoute`, …) resolved to the screen they render;

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] Custom fields' create/edit form scrolled its Save/Cancel row under the FAB**
- **Found during:** Task 3 (CustomFieldsScreen)
- **Issue:** `CustomFieldsScreen` returns `<FieldDefForm>` in place of its list while a field is being created or edited. `CustomFields` is not a focused route, so the FAB shows, and the form's own ScrollView (Save/Cancel at the end) had no clearance. A file-level scan of the screen could not see it. This is the D-52 truth ("every scrolling screen that shows the FAB") on the same route.
- **Fix:** `FieldDefForm` takes a required `bottomClearance: number` prop (the CardGrid pattern) and pads its ScrollView; CustomFieldsScreen passes its clearance in both modes. The contract gained a "delegated scroll components" check (CardGrid ← HomeScreen, FieldDefForm ← CustomFieldsScreen: required prop, reaches `contentContainerStyle`, host passes it).
- **Files modified:** src/components/FieldDefForm.tsx, src/screens/CustomFieldsScreen.tsx, src/navigation/fab-clearance-contract.test.ts
- **Commit:** 38d7148

**2. [Rule 1 - Bug] Type of the border colour key**
- **Found during:** Task 2 GREEN
- **Issue:** Annotating `FAB_BORDER_COLOR_KEY: keyof ThemePalette` makes `colors[KEY]` include the palette's `readonly string[]` members, and tsc rejects it as a `borderColor`.
- **Fix:** `"onAccent" satisfies keyof ThemePalette` keeps the literal key type while still proving it is a palette key.
- **Commit:** 738e49b

**3. [Contract reading] Allowlist semantics**
- The plan's "stale entry = no longer a FAB-bearing scroll screen" would make the OrreryScreen entry (no scroll container) stale on day one. Implemented instead: every FAB-bearing screen must be cleared or allowlisted; a screen with no scroll container of its own must be allowlisted too (catches delegated scroll); an entry is stale if it is no longer FAB-bearing or now applies the clearance.

No ADR or HANDOFF decision reversed; no schema change; no package installs.
