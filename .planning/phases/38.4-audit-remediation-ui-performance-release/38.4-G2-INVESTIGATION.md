### The real freeze — reproduced (release-relevant)

- Found while probing the FAB: after the universal FAB speed dial is opened **once** and closed (by scrim tap, by Back, or by choosing an action such as Quick Log), the whole app except the FAB stops responding to touch, permanently, until a cold start.
- Deterministic repro from a clean cold start (fab1, 06:05): Contacts responds (`POP-OK`) → FAB `touchscreen tap` → dial rows present → scrim tap → rows gone → Population trigger: nothing (`POP-DEAD`) → Events tab: nothing → `touchscreen swipe` on the list: no scroll. Repeated three times across sessions (z-series 05:48, r-series 05:56, fab1 06:05).
- Classification in the wedged state:
  - JS thread idle (`mqt_v_js` 0.0 %; 0.01–0.03 s CPU per tap), so not a JS loop.
  - `dumpsys window`: `mCurrentFocus` = Orbit `MainActivity`; no extra Modal/dialog window; input dispatcher `PendingEvent: <none>`, `InboundQueue: <empty>` (input-stuck.txt).
  - uiautomator dump completes and shows the normal Contacts tree, no "Open debugger" toast, no dashboard panel.
  - The FAB still works (opens the dial), and the dial scrim still closes it — everything drawn BELOW the FAB overlay is dead, including native ScrollView scrolling (so touches never reach the navigator's native views).
- Discriminating probes (temporary `console.log`s via Fast Refresh, removed afterwards; no commit):
  - `UniversalFab` render: `{"open":false,"ref":false,"pe":"none"}` — JS state is correctly closed; the scrim's `onPress` never fired on the dead taps, so the scrim is not the interceptor.
  - `onStartShouldSetResponderCapture` / `onTouchStart` on the tab navigator container (`TabNavigatorContainer`): **never fires** on a dead tap — JS never receives a touch whose target is inside the navigator.
  - `onTouchStart` on the FAB overlay `View`: every dead tap reports `target 200`.
  - `dumpsys activity top`: tag `#c8` (= 200) is the dial container `View` (`UniversalFab.tsx` `pointerEvents="box-none"`, `style={styles.dial}` = full-screen absoluteFill) — the full-screen view holding the six action rows.
  - Native hierarchy with the dial OPEN (act-top-open.txt): `#c8` is **absent** — the dial container is flattened away and its rows are hoisted into the overlay. With the dial CLOSED again (act-top-closed.txt): `#c8` is back as a **new native object** (`97d64b` vs the earlier `9819d1`).

3. `HomeScreen` `query` (`useShallow`, ~:420) changes → `reload` identity changes (~:905) → `useFocusEffect` re-issues `reload("focus")` → scheduler `request` → `readRef.current` (Promise.all read + counts, ~:743-882) → `publishDashboardRead` (single `isCurrent` gate) → one batched render.
4. `DashboardControlRow` content-refresh effects (~:242-290) re-`open()` the active request with fresh content (bounded: `populations`/`pending` changes only) → `DashboardOverlayHost` re-renders → `AnchoredPanel` (its transient/focus effect depends on `visible` only, WR-01).
5. Home inertness from `selectPanelOpen` (~:530; both wrappers `pointerEvents={panelOpen ? "none" : "auto"}`) — restored on every dismissal path tested (scrim, Back, trigger re-tap).
- Measured: every hop completes; the JS thread returns to idle within ~2 s; the tab bar and list respond afterwards. The controls path does not stop making progress.

Freeze path (where progress stops):
1. FAB `onPress` → `openDial()` (`UniversalFab.tsx` ~:222) → `setOpen(true)`. The dial container's props flip: `importantForAccessibility` `"no-hide-descendants"` → `"auto"`, `accessibilityElementsHidden` `true` → `false` (~:420-421).
2. Fabric view flattening (`ViewShadowNode::initialize`, `node_modules/react-native/ReactCommon/react/renderer/components/view/ViewShadowNode.cpp`): `pointerEvents: BoxNone` does **not** make a node form a view, and `accessibilityViewIsModal` does not keep it one on Android (observed). While closed the container forms a view only because of the hidden-a11y props; when open it has no view-forming prop → **flattened** (native view deleted, rows hoisted).
3. `closeDial()` → `setOpen(false)` → the a11y props flip back → the node forms a view again → Android re-creates the native `ReactViewGroup` for tag 200. The re-created view does **not** get `pointerEvents="box-none"` applied (that prop never changed on the JS side, so it is not in the update the Android mounting layer applies; a new/recycled `ReactViewGroup` defaults to `PointerEvents.AUTO`, `ReactViewGroup.kt:181`/`:675`).
4. **Here progress stops:** a full-screen, childless-at-the-touch-point `ReactViewGroup` with `pointerEvents` AUTO sits above the tab navigator. `TouchTargetHelper` returns it as the target for every touch outside the FAB; it has no JS handler, so every tap is swallowed and native scrolling never starts. Only the FAB (drawn after it) responds.

## Root cause

**One mechanism:** the universal FAB's full-screen dial container (`src/components/UniversalFab.tsx:417-424`, `pointerEvents="box-none"`, `style={styles.dial}` = absoluteFill) is flattened by Fabric while the dial is open and re-created by Android when it closes, and the re-created native view comes back with the default `pointerEvents` **auto** instead of `box-none`. From the first dial close onward it swallows every touch below the FAB — all five tabs, the Contacts controls, the list, Profile scrolling — until the app is cold-started. JS stays idle and correct (`open=false`), which is why it looks like a hard freeze.

- **Release-relevant.** It is a Fabric/Android view-flattening mechanism, not a debug-only overlay. It exists on the owner's report date: the container's props are unchanged since Phase 22 (`6a96a03`), and nothing on the control path touches the FAB.
- **Isolated from the false freezes:** the LogBox toast was dismissed and absent from every wedged dump; `mCurrentFocus` was Orbit; dead controls were retried with both input sources at their centres; and the wedge does not follow control use alone (15+ clean cycles). It follows one dial open→close, deterministically.
- **Relation to the owner's report:** the owner's symptoms (tabs dead, the control change already persisted, no recovery without a force-restart) are exactly this wedge. The controls path itself does not wedge on this build. The most likely owner sequence is a FAB dial use (for example the Plan 11 FAB/Quick Log owner rows, or any capture) around the control change. Plan 17's finger row checks this order explicitly. The debug LogBox toast independently blocks tab taps from launch until dismissed, which can compound the impression.
- **Same class elsewhere (grep of every `pointerEvents="box-none"` View whose other props toggle):** `Snackbar.tsx:25-29` (absoluteFill overlay, box-none, `fabDialBackgroundA11y(fabDialOpen)` spread) flattens/re-forms with the dial while a snackbar is up. A first formation was checked on the device and kept box-none (dial rows stayed tappable over a live snackbar, s1–s3.xml), but a re-formation within one snackbar's lifetime has the same exposure. `AssistBanner.tsx:135-139` has `elevation: 32` (always forms a view) and is not exposed. `OrreryViewOptions`/`OrrerySystemSelector` change `pointerEvents` together with the a11y props, so the re-formed view always receives an explicit value and is not exposed.
- **E looks like the same class:** after FAB → Quick Log on Brian Ploof's Profile, the snackbar showed and the Profile no longer scrolled, both during and after the snackbar, and the Events tab was dead (k8–k13). Choosing any dial action closes the dial, which re-creates the container. (Recorded in full under Task 4.)
- **Fix direction (no recorded decision touched):** keep the dial container a permanent native view (`collapsable={false}`) so it is never flattened and never re-created, and apply the same to the `Snackbar` overlay root. ADR-095/ADR-092 are not involved; ADR-082 (FAB actions) and ADR-146 (tab shell) are unaffected; D-31's accessibility props stay exactly as they are.
