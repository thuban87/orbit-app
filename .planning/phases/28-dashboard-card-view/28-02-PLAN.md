<objective>
Build the data layer for Card View bulk management: extract the missing non-mutexed *Core primitives and compose them into atomic bulk composers, one inWriteTransaction per bulk operation. This is the phase's highest-risk work — in this repo the expensive bugs live in the data layer; the risk is entirely about WHERE the transaction boundary sits and WHICH writers get composed.

Per RESEARCH's on-disk-verified Data-Layer Composition Map: only recency (insertInteractionCore/recomputeLastContactCore) and events (recordEventCore) expose non-mutexed cores today. Archive, favourites, and snooze expose only mutexed top-level writers; category/frequency have no single-column setter at all. Because the write mutex is non-reentrant, a bulk op cannot loop the mutexed writers inside one transaction — so we extract cores (the established bulk-review-dao core/wrapper idiom) and compose them.

Purpose: correct-by-construction bulk writes that honour the single recency writer (ADR-010/024/071) and the immutable lifecycle-event trail (ADR-025).
Output: src/db/bulk-actions-dao.ts (+ test) and the extracted cores in contacts-dao / favourites-dao / snooze-dao.
</objective>
