<objective>
Add the two remaining capture surfaces that reuse the same pipeline: the pasted-URL path and the user's own (self record) photo.

Phase Goal (user story): **As a** user, **I want to** paste an image URL or set my own photo **so that** I can add a picture even when it isn't in my gallery, and personalise my own record — all landing as the same local master.

`url-image.ts` re-ports ONLY the plugin `ImageScraper`'s download + content-type→extension logic (as `fetch`/`downloadFileAsync`, dropping the wikilink/vault/conflict logic — no vault on mobile). It is a one-time WRITE path: it downloads once to cache, then feeds the identical crop → manipulate → persist pipeline. Reads are never network (local-first §3 intact). Security is the load-bearing part: only `https` URLs are accepted (reusing the Phase-4 positive-allowlist posture) — `http://`, `file://`, `intent://`, `javascript://` and non-image content are rejected with the SPEC error copy, closing the SSRF/cleartext surface. The self-record photo adds a "Your photo" entry in Settings that drives the same `PhotoSourcePicker`/crop flow against the `profile` target. Setting AND removing the self photo both route through Plan 05's fully target-kind-aware picker — the `profile` Remove branch (clearProfilePhoto + delete) already exists there, so Settings does not need (and must not add) its own Remove logic.

Purpose: PHOTO-02 (URL download-once) + the self-record half of PHOTO-01.
Output: `url-image.ts` (+ test), the URL submit wired into `PhotoSourcePicker`, and the Settings self-photo entry.
</objective>

| T-05-03 | Denial of service | malicious/huge remote image, decode bomb | medium | mitigate | download to evictable cache (not document) and validate content-type before use; the 512px re-encode bounds output; decode failure → SPEC copy, no crash |
