<objective>
Build the single storage chokepoint and the atomic photo write DAOs — the shared data/file foundation every photo slice depends on.

Phase Goal (user story): **As a** user, **I want to** set a contact's (or my own) photo and have it survive reboots and restores **so that** my avatars never silently vanish and never break on a new device.

`photo-storage.ts` is the ONLY place the relative↔`file://` mapping and the `contactId`-derivable filename scheme are observable (so a future `expo-file-system` signature drift is a one-file change). The DAO writers are dedicated atomic single-column updates because `updateContactMetadataCore` deliberately excludes `photo` (05-RESEARCH Pitfall 6) — the photo write is decoupled from the metadata form so the inline old-file delete can pair with the DB update. A net-new `profile-dao.ts` gives the single-row self record its own writers (none existed).

Purpose: PHOTO-03 (one 512px master under the document dir, relative path resolved at read) and the write half of PHOTO-05 (clear + delete).
Output: `photo-storage.ts` (+ test), `contacts-dao.ts` additions, net-new `profile-dao.ts` (+ `photo-dao.test.ts`).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → filesystem | a relative filename becomes a real path under the document dir |
| caller → SQLite | a photo path string is written to a TEXT column |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-02 | Tampering | photo-storage filename scheme | medium | mitigate | filenames derived from integer `contactId` + the whitelist-constructed `col_name` only — no raw user text, no `../`; the path helpers themselves enforce this (positive-int `contactId` + `isSafeColName(colName)` throw at the boundary, not only at UI call sites); writes confined to `Paths.document/avatars` |
| T-05-03 | Elevation of privilege | contacts-dao/profile-dao SQL | low | mitigate | every value `?`-bound; no identifier interpolated; `changes===1` guard prevents silent no-op writes |
| T-05-05 | Denial of service | cache eviction / absolute-path storage | medium | mitigate | persistMaster copies out of evictable cache into the document dir and returns the RELATIVE path; absolute/cache URIs are never stored (Pitfalls 1 & 3) |
| T-05-10 | Denial of service | irreversible master loss on failed replace | medium | mitigate | persistMaster copies to a temp file FIRST and only renames over the destination once the copy succeeds, with compensation — a failed copy/move can never destroy the prior master (no backup exists); node failure-path test proves the dest is untouched on a copy throw |
</threat_model>
