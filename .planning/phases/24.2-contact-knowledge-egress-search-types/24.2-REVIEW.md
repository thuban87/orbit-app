## Warnings

### WR-01: New `custom_field_defs` fields (`scope`, `history_retained`, `field_group`) are not validated at the parse boundary, and the scope-completeness check trusts the raw value

**File:** `src/backup/backup-schema.ts` (def handling around L289-291; no per-field validation exists) and `src/backup/restore-apply.ts:161-164` (`assertCompleteIncomingPairs`)

**Issue:** `validate()` runs `uidSet` on `customFieldDefs` but performs no field-level validation of `scope`, `history_retained`, or `field_group` (grep for these keys in backup-schema.ts returns nothing). The new scope-aware `assertCompleteIncomingPairs` branches on `def.scope !== "global"` to skip the full contact×def pair-completeness check. Because `scope` is never validated, a corrupt or hand-edited backup can:
- set `scope` to any non-`"global"` string (including `"Global"`, `"global "`, or a typo) and **silently bypass** the completeness guard, so a manifest that omits legitimately-required global pairs is accepted; and
- carry a non-null, non-string `scope` (number/object). Restore binds `r.scope ?? "global"` (restore-apply.ts L173), which only guards `null`/`undefined`; a number is coerced to TEXT by SQLite affinity, while an object throws at bind time and rolls the whole restore back with an opaque error rather than a clean `BackupSchemaError`.

This mirrors the pre-existing loose validation of other def fields (`type`, `col_name` are also unvalidated), so it is not a regression — but the new scope-branching is the first logic that makes a bad `scope` change a control-flow outcome rather than inert data, which is why it is worth hardening now rather than deferring to Plan 05.

**Fix:** Validate the new def fields in `validate()` alongside the existing checks, e.g. reject a def whose `scope` is present and not one of the known values, and whose `history_retained`/`field_group` are the wrong type:
```ts
for (const def of arrays.customFieldDefs) {
  if (def.scope !== undefined && def.scope !== null &&
      def.scope !== "global" && def.scope !== "contact")
    fail("customFieldDefs has an invalid scope");
  if (!isNullableBinaryFlag(def.history_retained ?? def.historyRetained))
    fail("customFieldDefs has an invalid history_retained flag");
  // field_group: string | null | undefined
}
```
(If Plan 05 owns the canonical scope vocabulary, gate on a shared constant rather than inlining `"contact"`.) This keeps the completeness bypass reachable only for genuinely contact-scoped defs and turns a malformed-file restore failure into a clean, content-free parse error.

## Info

### IN-01: `customFieldValueHistory` rows are validated for parentage only, not for `createdAt`/`value`/`modifiedAt` shape

**File:** `src/backup/backup-schema.ts:419-425` and `:577-582`

**Issue:** History rows are checked with `uidSet` (uid present/unique) and for known `contactUid`/`fieldDefUid`, but there is no check that `createdAt` is a string or that `value` is `string | null`. A legitimate export always supplies these (export-manifest.ts L61), so the round-trip is unaffected. But a malformed backup with a history row missing `createdAt` parses successfully and then fails at INSERT against the `created_at TEXT NOT NULL` column (restore-apply.ts L194), rolling the entire restore back with an opaque error instead of a clean `BackupSchemaError`. Separately, an omitted `modifiedAt` makes the reconcile row's `modified_at` `undefined`; impact is effectively nil because `insert-if-missing` retains the local row regardless of the tie-break. This matches the existing minimal validation of `events`/`interactions` (which also only check `contactUid`), so it is a parity note, not a new defect.

**Fix:** For parity with the stricter entities, add `if (typeof history.createdAt !== "string") fail("customFieldValueHistory has an invalid row")` (and a `value` type guard) inside the existing history loop.

### IN-02: `custom_field_value_history` tombstone type is newly accepted — confirm the purge/def-delete producers stay aligned (they do today)

**File:** `src/backup/backup-schema.ts:181` (`TOMBSTONE_ENTITY_TYPES`) and `src/backup/restore-apply.ts:51` (`tombstoneEntity`)

**Issue (informational):** Adding `"custom_field_value_history"` to the accepted tombstone types is required and correct — `field-ddl.ts:164-170` (def delete) and `purge-dao.ts:86` (contact purge, landed in 24.2-05) already emit these tombstones, so before this plan a backup taken from a DB that had purged such rows would have failed validation with `"tombstones has an invalid row"`. This plan closes that gap. I verified the type string matches across `tombstones-dao.ts` (`TombstoneEntityType`), both producers, the schema allow-list, and the restore `tombstoneEntity` map. No action needed; flagged so any future producer of a new tombstone entity type remembers this four-point alignment (producer → `tombstones-dao` union → backup `TOMBSTONE_ENTITY_TYPES` → restore `tombstoneEntity`).
