# Cross-AI Plan Review — Phase 24.2

Both reviewers had full repo access and grounded their findings in real `file:line`
evidence (verified: both open the actual migration head, DAOs, backup modules, and the
native picker module rather than reviewing plan text in isolation).

## Consensus Summary

Both reviewers agree the **seven-plan split and the schema → consumers → backup ordering
are sound**, and that the plans are unusually disciplined about naming real invariants
(no FTS5 / ADR-031, ADR-001 uniqueness untouched, per-item default-OFF egress, Off Limits
kept structurally separate) and enforcing them with grep/verification gates rather than
prose promises. Where they diverge is on residual risk: **Codex (gpt-5.6-terra) rates the
cluster HIGH** because several plans reference integration files that do not exist or omit
the writers/inventories that actually own the tables they touch; **Claude (sonnet) rates it
MEDIUM**, judging the same migration-numbering and privacy-boundary work correctly grounded
and concentrating residual risk in Plan 01's fuel-row disposition plus a few test-coverage
edge cases. Both reviewers independently flag the **Plan 01 destructive fuel data-move** as
the single item to fix before execution begins.

### Agreed Strengths

- **Migration numbering is correct and version-bump discipline is honored.** Both verify
  migration head is 016 on disk (`src/db/database.ts:51` `TARGET_VERSION=16`), so Plan 01's
  017 and Plan 05's 018 are head+1/+2, and Plan 07 correctly declines to re-bump
  `BACKUP_FORMAT_VERSION` (already 4 at `src/backup/types.ts:14`), surfacing the stale
  "Phase 36 owns v4" milestone note as an owner flag rather than silently resolving it.
- **ADR-001 uniqueness genuinely untouched** — Plan 05 adds `custom_field_value_history` as
  a new table with its own `uid UNIQUE` and leaves `UNIQUE(contact_id, field_def_id)` on
  `custom_field_values` intact (both cite `field-values-dao.ts:74` `ON CONFLICT(contact_id, field_def_id)`).
- **ADR-031 (no FTS5) enforced with a grep gate**, and the two-stage corpus + TypeScript
  typo-scorer design matches the decided edit-distance thresholds.
- **Off Limits kept structurally separate from AI permission**; both confirm
  `RANKED_FUEL_EXCLUSIONS` is real at `fuel-read.ts:133-135` and that Plan 03 correctly
  builds a *separate* memory-eligibility fragment rather than merging the two controls.
- **Plan 05 enumerates the two real seeding writers** — `contacts-dao.ts:196-207` and
  `field-ddl.ts:79-91` — matching the "enumerate every writer" requirement.

### Agreed Concerns

- **HIGH — Plan 01's destructive fuel data-move is underspecified and risks silent data
  loss or double-surfacing (KNOW-16).** Both reviewers land here from different angles.
  Codex: the "no AI-fuel producer shipped" premise is **false** — `confirmFuelCore` promotes
  `source='ai'` → `manual` at `fuel-dao.ts:199` and `FuelEditor.tsx:39` presents an
  AI-confirmation UI, so deleting all `source='ai'` rows destroys user-visible review work
  and needs an owner-authorized disposition, not a test precondition. Claude: the
  share-capture (`kind='topic', source='share'`) migration presents deletion-vs-preserve as
  an open choice in prose, yet the "no double-surfacing" outcome only holds if source rows
  are deleted after a verified copy — and Task 2's acceptance criteria never assert the fuel
  rows are gone. Both want the disposition stated affirmatively and asserted in
  `017-*.test.ts`; Codex additionally wants a per-row mapping/provenance integrity proof
  (count-equality can't detect a duplicated row masking a dropped one).
- **MEDIUM — Custom-field value-history append semantics on first-write / no-op are
  undefined (Plan 05).** Both note `upsertValueCore` uses one `INSERT ... ON CONFLICT DO
  UPDATE` path for both first-set and update, so the plan must define whether a from-NULL
  first write appends a (NULL) history row and whether an unchanged write appends nothing —
  and test the from-NULL case, which is the common first write.

### Divergent Views

- **Overall risk: Codex HIGH vs Claude MEDIUM.** The gap is almost entirely the set of
  "missing integration file" findings Codex rates HIGH that Claude did not surface: Plan 03's
  missing parent controller for `MemoryEditor` persistence and absent durable global-AI gate;
  Plan 05's value-history lifecycle across `merge-dao.ts`/purge/restore and the promotion
  atomic-core deadlock risk; Plan 06's nonexistent `OrbitContactPicker.types.ts` and the
  unwired note→importer pipeline (`picked-contact-map.ts:75` excludes notes); and Plan 07's
  omission of `reconciliation.ts`, the replace-all restore inventory, and a tombstone
  deletion writer. These are concrete, file:line-grounded, and mostly about `files_modified`
  lists that omit the real owners of the tables/contracts each plan touches — they warrant
  treatment as actionable gaps even though Claude's headline risk is lower.
- **Legacy Fuel in the new search corpus (Plan 02).** Codex flags (MEDIUM) that KNOW-10's
  named sources are contact name / Memories / relationships / eligible custom fields and that
  folding legacy Fuel in broadens the surface and may preserve legacy behavior unintentionally
  (`dashboard-read.ts:212` already searches Fuel separately); Claude does not raise this.

## Codex Review

# Plan Review: Phase 24.2

## Overall assessment

The seven-plan split and schema → consumers → backup ordering are sensible, and the plans identify important invariants such as no FTS5, per-item default-off egress, and preserving ADR-001’s normalized-value uniqueness. However, several plans currently cannot achieve their stated outcomes because they omit required integration files or assume APIs/settings that do not exist. The most serious gaps are the destructive migration’s false producer precondition, the native-note import’s missing JS/import pipeline wiring, and backup’s missing reconciliation integration.

Overall risk: **HIGH** until the high-severity gaps below are planned.

## Plan 01 — Migration, egress tracer, ADR-081

### Summary

Good vertical-slice intent, but the destructive migration gate is based on an incorrect factual assumption: this repository has a shipped AI-fuel producer/confirmation path. The proposed migration also needs more explicit data integrity and egress-boundary coverage.

### Strengths

- Correctly begins from the actual migration head: `TARGET_VERSION = 16` and `migration016` is last in the registration list at [src/db/database.ts:51](/home/bwales/projects/orbit-app/src/db/database.ts:51) and [src/db/database.ts:70](/home/bwales/projects/orbit-app/src/db/database.ts:70).

- Correctly treats the existing Memories table as additive. Its current schema contains no `allow_ai` column at [src/db/migrations/016-contact-knowledge.ts:10](/home/bwales/projects/orbit-app/src/db/migrations/016-contact-knowledge.ts:10).

- Correctly targets the sole AI context projection. `readPromptContext` is explicitly documented as the only contact-derived outbound projection at [src/db/ai-context-read.ts:2](/home/bwales/projects/orbit-app/src/db/ai-context-read.ts:2).

- Correctly keeps Fuel exclusions structural. `RANKED_FUEL_EXCLUSIONS` excludes both Off Limits and `source='ai'` directly in SQL at [src/db/fuel-read.ts:133](/home/bwales/projects/orbit-app/src/db/fuel-read.ts:133).

### Concerns

- **HIGH — The checkpoint’s “no producer shipped” premise is false.** The existing code documents that Phase 14 writes AI-proposed fuel, and `confirmFuelCore` promotes it from `source='ai'` to `manual` at [src/db/fuel-dao.ts:199](/home/bwales/projects/orbit-app/src/db/fuel-dao.ts:199). FuelEditor likewise presents an AI-confirmation UI at [src/components/FuelEditor.tsx:39](/home/bwales/projects/orbit-app/src/components/FuelEditor.tsx:39). The plan must not characterize all `source='ai'` rows as orphaned, unshipped proposals.

- **HIGH — Deleting every `source='ai'` fuel row needs an owner-confirmed data-loss disposition, not a test precondition.** Existing unconfirmed suggestions are user-visible review work, not necessarily garbage. The ADR may authorize retirement, but the plan should explicitly state whether they are deleted, migrated into a non-egress Memory, retained until dismissed, or exported in a pre-migration safety record.

- **MEDIUM — The data-move needs a per-row mapping integrity proof, not only count equality.** Equal counts do not detect a duplicated source row combined with a missing different row. Migration 006 uses integrity checks around its normalized move; Plan 01 should compare a source identifier/mapping set or preserve source provenance sufficient to verify every eligible source row was copied exactly once.

- **MEDIUM — Adding `sharedMemories` changes the closed PromptContext contract beyond the listed files.** Consumers and prompt formatting likely construct or serialize `PromptContext`; the plan only lists [src/ai/prompt-types.ts](/home/bwales/projects/orbit-app/src/ai/prompt-types.ts) and `ai-context-read.ts`. Existing consumers already create contexts with `sharedFields`, e.g. [src/logic/ai-suggestion-compose-integration.test.ts:68](/home/bwales/projects/orbit-app/src/logic/ai-suggestion-compose-integration.test.ts:68). Compilation may identify these, but the plan should inventory and test all prompt builders/formatters so opted-in memories actually appear in the inspected outbound payload.

- **LOW — The search tracer’s SQL `LIKE` requirement is unclear.** The stated corpus read is per-contact and the scorer does matching in TypeScript. It should avoid introducing a redundant SQL search filter that could make typo matches impossible before the TypeScript scorer runs.

### Suggestions

- Replace the producer checkpoint with: “inventory existing `source='ai'` rows and obtain explicit authorization for their selected disposition.” Include an upgrade test with both unconfirmed and confirmed AI-originated Fuel.

- Require a deterministic source-to-memory verification strategy, preferably a migrated-row mapping/provenance value or a per-source-row copy assertion before deleting originals.

- Inventory every `PromptContext` producer and formatter, then add an end-to-end test that an opted-in Memory is present in the exact resolved prompt/payload, not only `readPromptContext()`.

### Risk assessment

**HIGH.** The intended migration deletes established user-visible data under an invalid “no producer” premise.

## Plan 02 — Full search corpus and typo scorer

### Summary

The two-stage design is aligned with ADR-031, but the corpus plan currently over-specifies Fuel handling while omitting clear custom-field eligibility semantics and an actual interface for Phase 25.

### Strengths

- The scorer’s threshold cases directly cover the decided limits and avoid a dependency. This fits the existing pure-module convention; for example, the existing parser module is explicitly node-pure at [src/db/field-parsers.ts:25](/home/bwales/projects/orbit-app/src/db/field-parsers.ts:25).

- The plan correctly avoids FTS5 and SQL ranking.

- It correctly reuses the project’s safe custom-value read approach: `getValuesForContact` uses definition IDs as bound values rather than interpolating `col_name` at [src/db/field-values-dao.ts:20](/home/bwales/projects/orbit-app/src/db/field-values-dao.ts:20).

- It correctly preserves the structural Fuel exclusions rather than reimplementing them.

### Concerns

- **MEDIUM — “Eligible custom-field content” is not defined.** Existing custom field AI eligibility is `share_with_ai`, but searchability is a separate product concern. `getValuesForContact` returns exactly the caller-provided definition IDs at [src/db/field-values-dao.ts:27](/home/bwales/projects/orbit-app/src/db/field-values-dao.ts:27); the plan must specify whether search includes all live definitions, only non-quarantined definitions, only nonblank values, and whether hidden or contact-scoped definitions participate.

- **MEDIUM — Fuel should not be in this new knowledge corpus unless the requirement intentionally includes it.** The stated KNOW-10 sources are contact name, Memories, relationships, and eligible custom fields. Adding Fuel creates a broader glanceable-search surface and potentially preserves legacy behavior unintentionally. Existing dashboard search already handles Fuel separately at [src/db/dashboard-read.ts:212](/home/bwales/projects/orbit-app/src/db/dashboard-read.ts:212). Decide explicitly whether Phase 25 combines legacy Fuel search with this corpus.

- **MEDIUM — “Expose searchability metadata” has no concrete public API or test contract.** A `{ contactId, corpusText }` result alone does not expose field-level metadata. Phase 25 needs a named export and stable result shape, such as source kind/field keys, to consume without parsing concatenated text.

- **LOW — Tokenization needs Unicode and punctuation behavior defined.** Whitespace-only splitting will make `"O'Connor"`, email addresses, phone numbers, and punctuation-heavy URLs inconsistent. This matters especially once URL/email/phone fields are introduced in Plan 04.

### Suggestions

- Define a searchable-definition predicate in one named function, including quarantined, blank, scope, and visibility behavior.

- Keep legacy Fuel search outside this module unless requirements explicitly include it; if retained, document the merge behavior for Phase 25.

- Export a structured corpus entry type with source metadata that is safe to expose and excludes internal IDs.

- Add punctuation/Unicode/diacritic cases and a bounded maximum corpus/query size to protect UI responsiveness.

### Risk assessment

**MEDIUM.** The architecture is sound, but eligibility and the Phase-25 contract are too underspecified.

## Plan 05 — Scope, promotion, and value history

### Summary

This is the strongest data-model plan, especially its refusal to weaken ADR-001. The biggest missing concern is delete/merge/restore lifecycle handling for the new history table and tombstone model.

### Strengths

- It preserves the key normalized uniqueness invariant. The current upsert depends on `ON CONFLICT(contact_id, field_def_id)` at [src/db/field-values-dao.ts:74](/home/bwales/projects/orbit-app/src/db/field-values-dao.ts:74).

- It correctly identifies both existing seeding writers: field creation fans out to all contacts at [src/db/field-ddl.ts:79](/home/bwales/projects/orbit-app/src/db/field-ddl.ts:79), and contact creation seeds every definition at [src/db/contacts-dao.ts:198](/home/bwales/projects/orbit-app/src/db/contacts-dao.ts:198).

- The plan’s same-transaction history append respects the repository’s non-reentrant transaction constraint at [src/db/transaction.ts:49](/home/bwales/projects/orbit-app/src/db/transaction.ts:49).

### Concerns

- **HIGH — The value-history table needs lifecycle ownership beyond the listed writer path.** Current contact merge reparents a fixed table list at [src/db/merge-dao.ts:180](/home/bwales/projects/orbit-app/src/db/merge-dao.ts:180); the new table is absent. Likewise, hard-delete/purge and replace-all restore table inventories must be updated. Otherwise histories can be deleted unexpectedly by cascade, stranded, or omitted during merge/replace flows.

- **HIGH — “Promotion seeds remaining contacts” needs an atomic core, but the plan places it ambiguously in `field-defs-dao.ts`.** Existing field definition writes are standalone mutexed wrappers, while pair seeding uses `upsertValueCore`. A promotion operation must own one transaction, update scope, query all missing contacts, seed them, and bump revision. Calling a public field-DDL function from the DAO would risk the documented nested-mutex deadlock.

- **MEDIUM — Scope ownership is not represented in schema.** A `scope='contact'` row alone does not record which contact owns the definition. The plan relies on existing value rows to infer it, which becomes ambiguous after promotion, restore, deletion, or a malformed/missing seed. Consider a nullable `owner_contact_id` / `contact_id` foreign key or explicitly document the invariant and enforce exactly one seeded target before promotion.

- **MEDIUM — The history append needs no-op semantics.** The plan says “when value changes,” but `upsertValueCore` does not currently read prior values. It must avoid appending history when prior and incoming raw values are identical, and decide whether changing non-null → null and null → non-null should create history entries.

### Suggestions

- Add affected lifecycle files to the plan: at minimum `merge-dao.ts`, `purge-dao.ts`, and Plan 07’s replace-all table list; add tests for merge and purge behavior.

- Define a single `promoteContactFieldToGlobal` transaction-body operation with explicit scope/ownership validation and missing-pair insertion.

- Add schema-level ownership or enforce a strict application-level owner invariant with tests.

- Add tests for unchanged writes, clearing values, first assignment, rollback, and promotion after a target contact is deleted.

### Risk assessment

**HIGH.** The primary feature is sound, but unplanned lifecycle paths can corrupt or lose new durable history.

**MEDIUM — Plan 05's value-history append (Task 3) doesn't specify what happens on `INSERT` (first-time value creation) vs. `UPDATE`.** The action says "when a `history_retained` def's value changes, compose `appendValueHistoryCore`... appending the PRIOR value before overwriting." `upsertValueCore` (verified `field-values-dao.ts:64-79`) uses `INSERT ...
