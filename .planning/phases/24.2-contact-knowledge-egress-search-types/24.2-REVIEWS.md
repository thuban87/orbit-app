## Summary

The seven-plan sequence is substantially improved and source-grounded. It correctly stages migrations before consumers and backup work, preserves ADR-001/ADR-031 constraints, and explicitly addresses both prior HIGH findings. The remaining material risks are an incomplete retirement of the legacy AI-fuel path, a tracer-scoring contradiction, and a missing explicit dependency for Plan 07.

## Strengths

- HIGH-1 is properly repaired in Plan 05: the plan targets the real edit route, `updateContactFull` → `upsertValueCore`, rather than the standalone wrapper. On disk, `updateContactFull` owns the transaction and directly calls `upsertValueCore` at `contacts-dao.ts:375` and `contacts-dao.ts:412`, while the wrapper is separate at `field-values-dao.ts:45`. The plan's prior-value read-before-upsert and real-path test are the right mechanism.
- HIGH-2 is comprehensively covered in Plan 05. The current purge design has both an exhaustive `PURGE_CHILDREN` map at `purge-dao.ts:80` and a separate explicit deletion array at `purge-dao.ts:318`, while tombstone types are a closed union plus runtime switch at `tombstones-dao.ts:8` and `tombstones-dao.ts:35`. The plan explicitly updates all three and adds merge reparenting beside the existing bespoke `field_history` update at `merge-dao.ts:180`.
- The migration ordering is accurate: the repository is at `TARGET_VERSION = 16` with migration 016 registered at `database.ts:51` and `database.ts:70`. Plan 01's seeded-at-16 fixture resolves the earlier invalid fixture-order concern.
- Plan 01's copy-verify-delete migration design is appropriately defensive for local-only data. It uses the existing `memories` schema, whose fields support the proposed carry-over at `016-contact-knowledge.ts:10`.
- The Plan 02 tokenizer correction is well specified: one exported tokenizer for queries and corpus text, bounded input, punctuation behavior, and explicit typo-distance boundaries. This prevents mismatched query/corpus tokenization.
- Plan 03 correctly follows parent-owned persistence. `MemoryEditor` currently has no DAO dependency, while the screen owns the editor render sites; the planned callback approach is aligned with that architecture. The gate source also exists as specified: `getAppSettings` is the durable reader at `app-settings-dao.ts:381`.
- Plan 04 correctly retains Photo. The current field model has seven types including Photo, so adding URL, Email, and Phone to make ten is the safe additive interpretation.
- Plan 06 traces every real import hop. `PickedContact` is indeed defined in `modules/orbit-contact-picker/index.ts:14`, notes are deliberately currently excluded in `picked-contact-map.ts:75`, and `importRowAsNew` passes the mapped record into the transactional import writer at `import-driver.ts:68` and `imported-contact-dao.ts:122`.
- Plan 07 correctly identifies the format-4 compatibility problem. `BACKUP_FORMAT_VERSION` is already 4 at `types.ts:14`, and backup validation currently requires every listed array at `backup-schema.ts:259`. Normalizing a missing new top-level array is necessary.

## Concerns

- **MEDIUM — ADR-030 is not actually retired from the application code.** Plan 01 removes existing `source='ai'` rows and writes ADR-081, but it does not modify `fuel-dao.ts`, `FuelEditor.tsx`, or `ContactProfileScreen.tsx`. The legacy confirmation API remains active at `fuel-dao.ts:199`, UI behavior remains documented in `FuelEditor.tsx:45`, and the Profile still imports and invokes `confirmFuel`. Even if no present producer inserts AI fuel, the retired model remains supported and can be accidentally revived.
- **MEDIUM — Plan 01's scorer scope is internally contradictory.** Task 3 says the tracer scorer is prefix/substring-only and that full edit distance belongs to Plan 02, but its acceptance requires a one-edit typo match. Decide whether Plan 01 includes the bounded edit-distance primitive or removes that acceptance criterion. The architecture should not have a test requirement without an implementation commitment.
- **MEDIUM — Plan 07's declared dependencies omit Plan 06, despite testing its output.** Plan 07's round-trip test explicitly seeds an `imported` Memory type, but `depends_on` lists only Plans 01 and 05. `MemoryTypeKey` currently permits only `general | custom` at `memory-registry.ts:14`. The wave barrier may hide this in normal execution, but the plan is not independently runnable as declared.
- **LOW — "Global AI enabled" is approximated as provider configured.** Plan 03 uses `ai_provider !== 'none'` as gate one. That is defensible before Phase 36, but it is not equivalent to the future global AI master toggle. Document this as an interim availability gate and make Phase 36 responsible for replacing or composing it with the actual master-enabled state.
- **LOW — The migration's AI-off off-limits conversion preserves egress safety but loses user-visible semantics.** The plan discloses this safety-net case, which is good. Still, if unexpected `source='ai' AND kind='off_limits'` rows exist, converting them to a general memory loses the "avoid topic" meaning even though `allow_ai=0` prevents AI egress. Consider retaining a migration audit marker or surfacing a post-migration review count.

## Suggestions

- Add a Plan 01 task to remove or hard-disable the legacy `source='ai'` production model: `confirmFuelCore`, AI-unconfirmed UI, relevant profile handlers, and obsolete tests. Keep historical migration handling, but prevent new legacy-path use.
- Resolve the Plan 01/02 typo-scoring split explicitly: either implement a small tested bounded-edit matcher in Plan 01, or defer all typo assertions to Plan 02.
- Add `24.2-06` to Plan 07's `depends_on`, since its test fixture and backup validation rely on the new `imported` registry key.
- In Plan 03, name `aiProvider !== 'none'` "AI configured/available" rather than the durable global master gate, then specify Phase 36's replacement seam.

## Risk Assessment

**Overall: MEDIUM.** The destructive migrations and value-history lifecycle are thoughtfully guarded, and the cycle-2 HIGH fixes are genuinely wired into the plans against the real code seams. The primary unresolved risk is that ADR-030 retirement currently removes rows without removing the still-present legacy behavior, which could leave two competing AI-knowledge models in the codebase.

- **LOW — Plan 05 purge availability guard is a two-edit subtlety stated only directionally.** For the tombstone loop (`purge-dao.ts:291`) and delete loop (`:318`) to skip `custom_field_value_history` on a pre-018 fixture, the executor must add the table to **both** the `KNOWLEDGE_CHILD_TABLES` map (`:96-100`) **and** the `sqlite_master … IN (…)` list inside `availableKnowledgeChildren` (`:107-111`). - **LOW (latent / Phase-31 handoff) — Plan 05's scoped-write guard can throw on legitimate non-owner edits once scoped defs exist.** `assertContactScopedWriteAllowedCore` throws when a `scope='contact'` def has a pair on another contact and none on the edited contact — including for a **null/empty** write. If `EditContactScreen` submits an empty value for a rendered contact-scoped def on a non-owner, `updateContactFull` would throw and roll back the whole edit. This is **not reachable in 24.2** (no in-phase UI creates `scope='contact'` defs — Plan 04's picker adds none; all migration-018 defs default `scope='global'`, which passes the guard), so it is not a blocker. Flag for the Phase-31 handoff: the edit-form scope filter must land in the same phase that exposes scoped-def creation, and Phase 31 must ensure the form never submits a non-owner's contact-scoped def.
- **LOW (documentation only) — Plan 03 calls `getAppSettings` "the ONLY reader."** `ai_provider` is also read by `getPortableSettingsSnapshot` (`app-settings-dao.ts:468`) and a targeted read in `updateAppSettingsCore` (`:855`). `getAppSettings` is only the sole reader of the full `AppSettings` shape.
