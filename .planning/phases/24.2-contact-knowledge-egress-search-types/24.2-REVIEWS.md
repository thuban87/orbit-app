## Summary

The seven-plan structure is strong: migrations are ordered, egress is SQL-gated, search remains no-FTS TypeScript scoring, and Plan 05 now explicitly covers value-history deletion through merge, purge, and definition drop. ## Strengths

- Plan 01 correctly builds on the actual migration head: `TARGET_VERSION = 16` and `migration016` is last in the authoritative list at `src/db/database.ts:51`. The runner wraps each migration step and `user_version` bump in one rollback-safe transaction at `src/db/migrations/runner.ts:56`.
- The proposed `allow_ai` addition belongs in the correct existing model. `memories` has no such column today (`src/db/migrations/016-contact-knowledge.ts:10`), while the outbound AI read is already clearly established as the sole egress boundary at `src/db/ai-context-read.ts:1`. Plan 01/03's SQL predicate and default-OFF test are the right defense-in-depth design.
- Plan 02 correctly avoids SQL term filtering. `getValuesForContact` binds definition IDs rather than interpolating field identifiers (`src/db/field-values-dao.ts:20`), and `sortExpr()` is the existing safe raw-TEXT ordering seam (`src/db/field-sort.ts:29`).
- Plan 05's corrected definition-drop treatment is genuinely wired into the plan and internally consistent. The current `dropFieldValues` is a private non-mutexed core (`src/db/field-ddl.ts:104`) invoked under caller-owned transactions; it presently deletes the definition at `field-ddl.ts:154` without value-history handling. The revised plan specifically inserts select → explicit delete → tombstone work before that deletion, and requires a field-drop test. Correct location; avoids nested mutex acquisition.
- The revised Plan 05 correctly identifies all three lifecycle seams that currently lack value-history handling: merge only reparents existing fixed tables plus `field_history` (`merge-dao.ts:180`); purge's exhaustive registry and explicit delete list omit value history (`purge-dao.ts:80`, `purge-dao.ts:318`); and the tombstone union is closed (`tombstones-dao.ts:8`). The planned changes and tests address each.
- Plan 07 correctly recognizes backup restore's multiple exhaustive integration points across `entities`, `tableOf`, `tombstoneEntity`, row selection, child inserts, and replace-all deletion (`restore-apply.ts:49`, `:170`, `:245`). Its plan calls out all of them.

## Concerns

- **HIGH — Plan 06 drops `note` before its proposed import-driver path can read it.** `acceptPickedContacts` explicitly serializes only `displayName`, `methods`, and `birthday` into `sourcePayload` at `src/services/import/import-acquire.ts:89`. `importRowAsNew` reconstructs the picker object solely from that JSON at `src/services/import/import-driver.ts:54`. Adding `note` to `PickedContact` does not make it serialize automatically. Plan 06 does not modify `import-acquire.ts`, so all session-based new-contact imports will silently lose the note. Add `import-acquire.ts` to Plan 06's files/tasks/tests; serialize `note: contact.note`. Also audit `commitSingleImport`, which directly invokes `importContactRecord` without a note argument at `import-acquire.ts:120`.

- **MEDIUM — Plan 05's contact-scoped-definition ownership is not durable.** The plan treats the sole `custom_field_values` pair as the owner marker. But the pair is `ON DELETE CASCADE` from its contact (`src/db/migrations/006-normalize-custom-field-values.ts:41`). After permanently purging the owning contact, the definition remains with no owner; `defsForEditForm` currently returns every live definition for every contact (`field-values-dao.ts:117`). The "initial owner if no pair exists" guard could then permit a different contact to claim it. Add a durable ownership rule before landing contact-scoped creation: preferably nullable `owner_contact_id` on `custom_field_defs` for `scope='contact'`, with restore/merge/purge semantics; alternatively explicitly tombstone/delete a contact-scoped definition when its owner is purged. Add tests for owner purge, merge, and restore.

- **LOW — Plan 03's first gate is only an interim proxy.** `aiProvider !== 'none'` shows configured-provider state (`app-settings-dao.ts:436`) but is not the future global AI master toggle. The plan acknowledges this; preserve the single computed seam and require Phase 36 to replace it.

## Suggestions

- Fix Plan 06 before execution by adding note serialization and direct single-import propagation, with one test for each route: picker → session payload → bulk/new import; picker → session → review/single import; existing-contact linking remains intentionally no-note.
- Resolve scoped-definition ownership in Plan 05 rather than relying on a value row as identity. Include ownership in backup/restore if adding a column.
- Keep the revised Plan 05 field-drop assertion exactly as written: create history, delete the definition through a public route, assert both explicit deletion and one tombstone per history UID.

## Risk Assessment

**HIGH until Plan 06 is corrected.** The phase's imported-Contacts-note requirement can appear implemented at the native and DAO layers while silently failing in the normal session-based import flow. Once that is fixed, the remaining principal risk is the contact-scoped-definition ownership lifecycle in Plan 05.
