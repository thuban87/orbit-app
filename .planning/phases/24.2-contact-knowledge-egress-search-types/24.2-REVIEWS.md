# Cross-AI Plan Review — Phase 24.2 (Convergence Cycle 2)

Two independent reviewers (Codex `gpt-5.6-terra`, and a read-only Claude subagent) reviewed the cycle-2 revision (commit `2d2a461`) against the source tree. The revision is, overall, an honest and substantially correct response to cycle-1: migration 017 is genuinely reworked to non-destructive copy-then-remove with per-row proof-of-copy, the "no `source='ai'` producer" premise is TRUE on disk, the backup reconciliation path is real with accurate line references, and the picker/import wiring is correctly traced end-to-end. **Six of the seven claimed cycle-2 changes verify cleanly. The phase's risk is concentrated almost entirely in Plan 05**, which carries two verified HIGH defects (a silent false-green on the value-history append, and an under-scoped purge/tombstone coupling). The other six plans are ready or need only minor plan-wording corrections.

## Consensus Summary

Both reviewers agree the architecture, egress/privacy posture, and migration transactionality are strong. Both independently flagged the Plan 05 purge/tombstone-registry coupling (Codex rated it HIGH, Claude MEDIUM). The Claude lane additionally found — and the orchestrator verified — a **new** HIGH that Codex missed: the value-history append is wired to a dead code path. Codex additionally raised the Plan 04 field-type-count contradiction and the Plan 01 migration-test seeding sequence (both verified real; adjudicated to actionable non-HIGH). Neither reviewer found a local-first / network-egress violation, a reversal of a `[DECIDED]`/ADR item, or a widening of what the AI feature transmits. The single new egress surface (`PromptContext.sharedMemories`) carries only already-opted-in memories through the existing sole egress read.

## Orchestrator-Verified Findings (adjudicated severities)

### HIGH-1 — Plan 05: value-history append is wired to a dead code path (false-green). [VERIFIED, UNRESOLVED]

**Evidence (orchestrator re-verified on disk):**
- `upsertValue` (wrapper, `field-values-dao.ts:45`) has **zero production callers** — `grep "upsertValue\b"` outside `*.test.ts` returns only the definition and two doc-comments (`contacts-dao.ts:9`, `field-defs-dao.ts:12`).
- The real custom-field edit writer is `updateContactFull` (`contacts-dao.ts:342`, "the metadata-edit writer"), called in production by `EditContactScreen.tsx:420`. Its body loops `upsertValueCore` at `contacts-dao.ts:414` — the **core**.
- Plan 05 Task 3 explicitly instructs: "Wire the append into the value-write WRAPPER `upsertValue` … NOT into `upsertValueCore`."
- Therefore: value-history unit tests (which call `upsertValue` directly) pass, while every real user edit through the Edit-Contact form appends nothing. The automated gate cannot catch this. This is a silent production no-op on the headline KNOW-13 value-history feature.

**Fix (requires re-planning Plan 05 Task 3, not a spot-fix):** attach the append to the real edit writer — inside `updateContactFull`'s `upsertValueCore` loop (`contacts-dao.ts:414`): read the def's `history_retained` and the current stored value per pair BEFORE the upsert, and append when `history_retained=1 && prior non-null && prior != incoming` (and on clear-to-NULL). Add a device UAT that edits a `history_retained` field and asserts a history row appears.

### HIGH-2 — Plan 05: purge/tombstone coupling is under-scoped and omits a required file. [VERIFIED, UNRESOLVED]

**Evidence (orchestrator re-verified on disk):**
- `TombstoneEntityType` (`tombstones-dao.ts:8-21`) is a closed union with no `custom_field_value_history`; `assertTombstoneEntityType` (`:35-54`) is a runtime `switch` that throws on unknown types.
- `PURGE_CHILDREN` (`purge-dao.ts:80`) is an exhaustive `Record<TombstoneEntityType, PurgeChildSpec | null>` — adding a `custom_field_value_history` entry will not compile until the union gains the member. Plan 05 mis-names this map `PURGE_ENTITIES`.
- The tombstone write loop (`purge-dao.ts:291-311`) passes the key to `insertTombstoneCore` as a `TombstoneEntityType` — a runtime reject without the union member.
- The explicit per-row DELETE fan-out is a **separate, non-exhaustive** hard-coded `as const` array at `purge-dao.ts:318` ("Not relying on FK CASCADE — auditable"). Omitting `custom_field_value_history` there **compiles** but silently leaves history rows to FK CASCADE — the silent-miss component.
- `src/db/tombstones-dao.ts` is NOT in Plan 05's `files_modified`.

**Fix:** add `src/db/tombstones-dao.ts` (+ its test) to Plan 05 `files_modified`; extend `TombstoneEntityType` and `assertTombstoneEntityType`; correct `PURGE_ENTITIES`→`PURGE_CHILDREN`; add the entity to both the `PURGE_CHILDREN` map AND the `purge-dao.ts:318` delete array. Coordinate with Plan 07 (which owns the separate `TOMBSTONE_ENTITY_TYPES` set in `backup-schema.ts:170`) so both registries are updated.
