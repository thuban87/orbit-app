## Concerns

**1. MEDIUM — Intensity is not gated by interaction history the way the reference implementation it claims to mirror is, producing a display-state divergence for a Bound, never-contacted contact.**

`24.1-04-PLAN.md:161,166` specifies `getFirstClassDerived`:
> "gravity = computeContactGravity(inputs, now) when the contact has interaction history else null (mirroring ContactProfileScreen's hasHistory gate), intensity = computeContactIntensity(inputs, now) (a tagged { available: false } for an Unbound contact)"

Gravity is gated on `hasHistory`; intensity is only gated on Unbound (`trackingEnabled`/`intervalDays`), with no `hasHistory` condition at all.

Compare the actual reference this plan cites as authoritative, `src/screens/ContactProfileScreen.tsx:282-291`:
```
const hasHistory = impactInputs !== null && impactInputs.interactions.length > 0;
setGravity(hasHistory ? computeContactGravity(impactInputs, now) : null);
...
const derivedIntensity = hasHistory ? computeContactIntensity(impactInputs, now) : null;
```
Here **both** gravity and intensity are gated on `hasHistory` — for a contact with zero interactions ever, intensity is forced to `null` without even calling `computeContactIntensity`.

Mechanism of the divergence, verified against the pure math:
- `src/services/impact.ts:134-147` (`computeContactIntensity`) returns `{available:false}` only for `trackingEnabled !== 1 || intervalDays === null`. For a Bound contact (tracking on, `intervalDays` set) with **zero** interactions, it proceeds to `computeIntensity(inputs.interactions, ...)` with an empty array.
- `src/services/intensity-logic.ts:97-` (`computeIntensity`) does not special-case an empty array — it returns a real `IntensityResult` (`currentCount: 0`, `trailingAvgGapDays: null`, no throw).
- So for a Bound, never-contacted contact: `getFirstClassDerived` per the plan text returns `gravity: null` (correctly hidden) but `intensity: { currentCount: 0, intendedPerPeriod: ..., multiple: 0, ... }` — a real, "available" result.
- `24.1-06-PLAN.md:135,149` renders intensity whenever `intensity.available !== false` — since `IntensityResult` has no `available` key, `undefined !== false` is `true`, so this row **would render** ("0× this period vs N intended") for a contact that has never had a single interaction, while the gravity row on the same screen is correctly suppressed.

This is an internal inconsistency on the new surface itself (gravity hidden, intensity shown, for the identical no-history input) and a behavioral divergence from `ContactProfileScreen`, which the plan explicitly claims to match "exactly" (`ai-context-read.ts:224-261`/`ContactProfileScreen.tsx:278-296` citations at `24.1-04-PLAN.md:150-151`).

The gap is not caught by the plan's own acceptance criteria: `24.1-04-PLAN.md:184` lists the `getFirstClassDerived` test matrix as "history → gravity+intensity, Unbound → intensity unavailable, **no-history → gravity null**, missing id → null" — the no-history case only asserts `gravity` is null; it says nothing about what `intensity` should be in that same case, so an executor implementing exactly what's specified will ship the divergence without a failing test to catch it.

**Suggested fix:** gate `intensity` on the same `hasHistory` check as `gravity` in `getFirstClassDerived` (`intensity = hasHistory ? computeContactIntensity(inputs, now) : { available: false }` or equivalent null), and add a test case for "Bound contact, zero interactions" asserting intensity is unavailable/absent — matching `ContactProfileScreen`'s actual behavior.
