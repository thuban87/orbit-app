## Concerns

- **MEDIUM (new) — No DB-level self-link constraint on a frozen, irreversible table.** `relationships.linked_contact_id` self-link prevention relies entirely on application code: `assertNotSelfLink` in `addRelationshipCore`/`editRelationshipCore` (Plan 03 Task 1), and the merge-time SET-NULL guard (N6). There is no `CHECK (linked_contact_id IS NULL OR linked_contact_id != contact_id)` in the migration 016 schema text (confirmed no such CHECK is specified anywhere in Plan 01 Task 1's action). This codebase already uses CHECK constraints elsewhere (`CREATE_PROFILE` in `src/db/migrations/001-initial.ts:52`: `id INTEGER PRIMARY KEY CHECK (id = 1)`), so the idiom is proven and cheap. Given the plan itself repeatedly calls migration 016 "a frozen contract" that cannot be altered after shipping, and rates the self-link threat T-24.1-14 as HIGH, a DB-level backstop would protect against any *future* writer (24.2+) that reparents, restores, or bulk-imports relationship rows without going through the guarded cores or being aware of the merge precedent. This is not a currently-exploitable gap — my trace of every current/planned writer (add/edit/merge/purge/restore/expire) found no path around the existing guards — but it is a one-way missed opportunity for defense-in-depth on a table this plan treats as sensitive enough to warrant a dedicated post-merge invariant test.

- **LOW (new) — post-merge relationships invariant asserted once, not per test case.** Plan 03 Task 3 adds "a general post-merge invariant assertion after the merge cases" — phrasing suggests one assertion appended after the last test case rather than an `afterEach`-style check run after every merge-producing test. A future edit to an earlier test case that introduces a self-link would not be caught unless it also happens to run before wherever the single invariant assertion sits. Recommend the invariant run after every test that calls `mergeContacts` with relationship fixtures present, not just once.

- **LOW — reaffirm, not new: staged-upgrade test cost.** The N8 fix parameterizes over all 16 prior versions (0..15) in `016-contact-knowledge.test.ts`. This is a full DB creation + full migration replay per iteration; correctly justified by the plan as cheap given migration 016's irreversibility, but worth the executor keeping an eye on CI time if this pattern is later copied uncritically into faster-moving future migrations that don't carry the same irreversibility stakes.

No other new HIGH/MEDIUM findings surfaced. I did not find any plan content that reverses ADR-001, ADR-028, or ADR-031, and D-03/D-05/D-11's constraints (additive-only migration, application-owned registry, provisional-name-as-`human_needed`) are all reflected in executable acceptance criteria, not just prose.

## Suggestions

- Add `CHECK (linked_contact_id IS NULL OR linked_contact_id != contact_id)` to the `relationships` table DDL in migration 016 as defense-in-depth alongside the existing application guards (see Concerns, MEDIUM). Low cost since the table is being authored now, not retrofitted.
- Convert the single post-merge relationships invariant into a shared helper called at the end of every `mergeContacts`-exercising test case in `merge-dao.test.ts`, not just the named self-link cases.
- Since `current_state_entries`'s single-current invariant is *already* enforced by the partial unique index (`idx_current_state_current`) at the DB level — unlike the relationships self-link case — no equivalent suggestion is needed there; that design is already more robust than the relationships side, which is exactly why the CHECK-constraint suggestion above targets `relationships` specifically.
