## Codex Review

## Summary

The plan has a strong schema-first decomposition and correctly verifies migration 016 is currently head+1: [`src/db/database.ts:50`](/home/bwales/projects/orbit-app/src/db/database.ts:50) is `TARGET_VERSION = 15`, with migrations 001–015 registered at [`src/db/database.ts:53`](/home/bwales/projects/orbit-app/src/db/database.ts:53). Its DAO transaction and launch-sweep approach follows real established patterns. However, there are several blocking implementation-contract gaps: routes are assigned to the wrong navigator, the custom-field read call is incomplete, registry/current-state metadata is underspecified, and the trash-sweep test clock is not actually injectable.

## Strengths

- **Plan 01:** Correctly preserves the forward-only migration model. The runner wraps each migration and `user_version` update in an atomic transaction ([`runner.ts:56-66`](/home/bwales/projects/orbit-app/src/db/migrations/runner.ts:56)), so an additive migration with independently executed DDL statements is appropriate.

- **Plans 01–04:** The intended core/wrapper DAO pattern is exactly right. The shared transaction primitive is explicitly non-reentrant ([`transaction.ts:12-23`](/home/bwales/projects/orbit-app/src/db/transaction.ts:12)), and the existing fuel DAO demonstrates both-key patch scoping and `assertOneChange` ([`fuel-dao.ts:170-196`](/home/bwales/projects/orbit-app/src/db/fuel-dao.ts:170)).

- **Plans 02–05:** Soft-delete followed by a guarded permanent-delete operation is a good safety boundary. It matches the repository’s structural archive-before-purge precedent, where the DAO—not merely the UI—enforces the precondition ([`purge-dao.ts:10-23`](/home/bwales/projects/orbit-app/src/db/purge-dao.ts:10)).

- **Plan 05:** Using a launch hook rather than a timer is correct. The established field sweep uses a candidate scan followed by an authoritative write-side recheck, avoids nested transactions, and uses a strict `<` expiry boundary ([`field-sweep.ts:93-119`](/home/bwales/projects/orbit-app/src/services/field-sweep.ts:93)). Registration after migration readiness also follows the app’s lifecycle pattern ([`App.tsx:196-210`](/home/bwales/projects/orbit-app/App.tsx:196)).

- **Plans 03–04:** Using FK cascade for owned records and `ON DELETE SET NULL` for an optional linked contact is a sensible relationship model. Foreign keys are enabled before migrations on the actual Expo connection ([`database.ts:137-145`](/home/bwales/projects/orbit-app/src/db/database.ts:137)).

- **Plans 06–07:** The parent-owned persistence posture is consistent with the existing `FuelEditor`, which intentionally imports no DAO and delegates writes/reloads to its parent ([`FuelEditor.tsx:2-23`](/home/bwales/projects/orbit-app/src/components/FuelEditor.tsx:2)).

## Concerns

- **HIGH — Plans 01, 06, 07: navigation changes target the wrong file.** `RootNavigator` only declares the four bottom tabs ([`RootNavigator.tsx:149-208`](/home/bwales/projects/orbit-app/src/navigation/RootNavigator.tsx:149)); it does not register Dashboard stack routes. Dashboard screens are registered in [`DashboardStack.tsx:28-60`](/home/bwales/projects/orbit-app/src/navigation/tabs/DashboardStack.tsx:28). Adding `ThingsToRemember`, `RecentlyDeleted`, and `MemoryHistory` types but registering screens in `RootNavigator.tsx` will not make them navigable.

  This is worse for Profile reachability: `ContactProfileScreen` is also mounted under Orrery ([`OrreryStack.tsx:14-25`](/home/bwales/projects/orbit-app/src/navigation/tabs/OrreryStack.tsx:14)). A route added only to `DashboardStackParamList` is unavailable from an Orrery-origin profile. The plans must decide whether these screens belong in both stacks or whether profile navigation explicitly targets the Dashboard tab.

- **HIGH — Plan 06: the described custom-field read cannot compile or meet the requirement.** `getValuesForContact` requires `(exec, contactId, defs)` ([`field-values-dao.ts:20-38`](/home/bwales/projects/orbit-app/src/db/field-values-dao.ts:20)), but Plan 06 only describes calling it as a fourth source without loading field definitions. It also needs `listDefs()` and likely `visibleDefsForProfile()` to identify labels, types, order, and which values should render ([`field-values-dao.ts:121-134`](/home/bwales/projects/orbit-app/src/db/field-values-dao.ts:121)). As written, it cannot display custom fields coherently.

- **HIGH — Plans 01 and 04: the registry contract does not define the history field keys it later requires.** Plan 01 specifies only `general | custom` Memory keys, while Plan 04 requires `last_talked_about` and `current_location` to be registry-defined history-aware keys. The plans neither define a distinct current-state registry nor extend the stated registry type to model these fields. This will either create hardcoded screen strings—the explicit anti-goal—or leave `field_key` validation impossible.

- **HIGH — Plan 01: the “migration from arbitrary prior version” test method is unsafe if it literally forces `PRAGMA user_version`.** The runner uses `user_version` solely to select migrations ([`runner.ts:38-45`](/home/bwales/projects/orbit-app/src/db/migrations/runner.ts:38)). Setting a fresh/full-schema test database to version 1, 8, or 15 does not create a genuine database at that schema version. Test each upgrade by first migrating a clean DB to that actual prior target, then running the new target; otherwise the test can falsely pass with tables that would not exist on a real old install.

- **MEDIUM — Plans 01–02: application-owned types are only a TypeScript convention unless writers validate them.** The existing fixed fuel kind model relies on a TypeScript union while the SQLite column has no constraint ([`fuel-dao.ts:37-52`](/home/bwales/projects/orbit-app/src/db/fuel-dao.ts:37)). The new plans call the registry an enforcement boundary but do not explicitly require `addMemory` and `editMemory` to reject unregistered runtime `type` values, or to require `custom_label` for `custom`. Without validation, a future caller or restored/corrupt row can create a type that the registry cannot render or resolve visibility for.

- **MEDIUM — Plan 05: its injectable `now` cannot drive the proposed expiry test.** The reference sweep’s injectable `now()` is used only for write timestamps ([`field-sweep.ts:83-102`](/home/bwales/projects/orbit-app/src/services/field-sweep.ts:83)); its candidate predicate still uses SQLite’s real `datetime('now', 'localtime', ?)`. Plan 05 proposes the same SQL while claiming deterministic “exactly N days” test coverage through an injectable clock. That injection would not affect the query. Inject the cutoff timestamp/clock into both scan and authoritative purge guard, or use a test clock supported by the SQL abstraction.

- **MEDIUM — Plan 05: the stated device-clock guarantee is not achievable with the proposed storage/query model.** Comparing local text timestamps against SQLite’s device-local `datetime('now','localtime', ...)` means a forward clock jump can expire a row early. A backwards jump delays deletion, but cannot establish “true elapsed time.” Either drop that guarantee or introduce a reliable monotonic/server time source—which is incompatible with this local-first scope.

- **MEDIUM — Plans 06–07: the unified surface does not actually enumerate first-class fields.** The plan composes current-state entries, relationships, memories, and custom fields, but “first-class fields” are broader than the two new history fields. Existing profile data is loaded through separate profile/contact reads, e.g. profile fields and custom definitions are loaded independently in [`ContactProfileScreen.tsx:236-260`](/home/bwales/projects/orbit-app/src/screens/ContactProfileScreen.tsx:236). Define exactly which stable contact properties are part of Things to Remember and add a read projection for them; otherwise KNOW-01 is only partially achieved.

- **MEDIUM — Plans 03 and 07: relationship soft-delete is not actually restorable through the described UI.** Plan 03 promises relationship restore, but Plan 07’s `RelationshipEditor` receives only add/edit/delete callbacks. The only Recently Deleted screen lists memories. Either add relationship restore to an appropriate recovery surface or avoid claiming that relationship deletion is a user-restorable feature in this phase.

- **LOW — Plans 06–07: “Off Limits Memory” behavior is internally inconsistent with this phase boundary.** The Plan 01 registry starts with `general` and `custom`; Plan 06 nevertheless asks MemoryCard to render Off Limits markers. Existing Off Limits is a `fuel.kind` state ([`fuel-dao.ts:38-43`](/home/bwales/projects/orbit-app/src/db/fuel-dao.ts:38)), and 24.1 explicitly defers AI/Off Limits model work to 24.2. Remove this affordance from 24.1 or define an owner-approved memory representation and consumer path.

- **LOW — Plan 05: memory permanent deletion bypasses tombstones.** Existing hard deletes write tombstones before removal ([`fuel-dao.ts:227-249`](/home/bwales/projects/orbit-app/src/db/fuel-dao.ts:227)). Deferral may be intentional because backup/sync wire shape is 24.2/36 scope, but the plan should explicitly record whether permanent memory deletion needs a future reconciliation tombstone and how old pre-24.2 purges are treated.

## Suggestions

- Amend Plans 01, 06, and 07 to modify `src/navigation/tabs/DashboardStack.tsx`, and add equivalent routes to `OrreryStack` if the shared Profile must navigate locally from either origin.

- Add a small, explicit `CURRENT_STATE_FIELD_REGISTRY` or a unified knowledge registry with entries for `last_talked_about` and `current_location`. Make Plan 04 validate against it and Plan 06 derive labels/group ordering from it.

- Revise Plan 06’s load contract to fetch definitions via `listDefs`, values via `getValuesForContact(exec, contactId, defs)`, and select visible definitions with the existing pure selector.

- Require runtime registry validation at every Memory write boundary, including custom-label validation for the custom kind and a defined fallback/error strategy for unknown persisted types.

- Change migration tests to build real intermediate schemas through the migration runner rather than spoofing `user_version`.

- Make trash expiry testable with an injected cutoff that is used by both candidate scan and guarded purge. Clarify that device-clock changes can delay or accelerate expiry under local wall-clock semantics.

- Add a phase-level integration test/UAT checklist for:
  - Dashboard-origin and Orrery-origin Profile routes;
  - relationship FK `SET NULL` after contact purge;
  - current-state promotion rollback when target is from another contact/field;
  - a custom field with no value, a visible value, and a quarantined definition;
  - Trash restore racing sweep purge.

## Risk Assessment

**HIGH.** The foundational database and transaction approach is sound, but navigation registration and the custom-field read contract are presently implementation blockers, while the registry/current-state mismatch leaves a core data-model invariant undefined. Resolve those before executing migration 016; migration shape is irreversible once released.

# Cross-AI Plan Review — Phase 24.1 (Contact Knowledge Foundation: Model, Storage & UI)

## 1. Summary

This is an unusually well-specified plan cluster: it correctly re-derives the migration head (`TARGET_VERSION=15` → new migration `016`, cross-verified in RESEARCH.md, PATTERNS.md, and the plan frontmatter itself, all citing `src/db/database.ts:50,53`), consistently follows the repo's core/wrapper mutex pattern (`src/db/fuel-dao.ts:131-152` / `:255-264`), and correctly keeps the ADR-001/028/031 ESCALATE trip-wires out of scope rather than "fixing" them. The wave structure (tracer → parallel DAO layers → Trash/UI → drill-in surfaces) is a sound dependency spine. The main risks are: (a) one direct contradiction between the approved UI-SPEC and Plan 06's execution (the `sparkle` icon registry entry), (b) a soft-delete/permanent-delete design that never mints a tombstone, which is fine in isolation but creates a latent restore-resurrection gap for 24.2/36 to inherit silently, and (c) a few under-specified edge cases in the current-state-history promote/demote transaction and the visibility three-state column that are low risk given the mitigations already described but deserve an explicit test call-out.

## 2. Strengths

- **Migration-numbering discipline is real, not cargo-culted.** Every plan frontmatter and the checkpoint task in Plan 00 require re-verifying `TARGET_VERSION`/`ls src/db/migrations/` at execution time rather than trusting the number written in the docs — correctly following D-03 and Pitfall 1 in RESEARCH.md.
- **Core/wrapper mutex discipline is applied uniformly.** Every DAO plan (00, 02, 03, 04) explicitly requires cores to assume BEGIN is open and wrappers to own exactly one `inWriteTransaction`, matching the verified `fuel-dao.ts:131-152`/`:255-264` pattern, and each plan's acceptance criteria include a grep guard against nested `inWriteTransaction` calls (e.g. Plan 04 Task 2: `grep -c inWriteTransaction src/services/memory-trash-sweep.ts` must be 0).
- **TOCTOU-safe sweep design directly mirrors the one verified working analog.** Plan 04's trash sweep (bare candidate scan → per-item direct call to the mutex-owning guarded writer → its own try/catch, no re-wrap) is a faithful copy of `src/services/field-sweep.ts:83-133`, which is the one sweep in the codebase already proven correct under this exact TOCTOU constraint (HIGH-1 lesson cited in the file's own header comment).
- **The two-stage soft-delete → guarded-permanent-delete pattern is correctly modeled on the existing `purge-dao.ts` "archived-only-before-purge" precedent** (Plan 04 Task 1), and the acceptance criteria enforce it via SQL grep (`deleted_at IS NOT NULL` must appear in the purge statement).
- **The ADR-028 boundary is treated as a genuine escalation, not a planning detail.** Plan 00's `checkpoint:decision` task requires explicit owner sign-off before the migration is authored, correctly matching D-05's "stop and ask" framing rather than silently building toward a user-writable type set.
- **Registry-driven visibility resolution avoids hardcoded defaults.** Plan 02 Task 3's `resolveVisibility` test explicitly asserts the function "follows a registry-default change" rather than a fixed default — this is a good test design choice that would actually catch a hardcoded fallback.

## 3. Concerns

- **[MEDIUM] UI-SPEC/plan contradiction on the `sparkle` icon registry entry — `24.1-UI-SPEC.md:31-34` vs `gsd-review-plan-05.md` (Plan 06).** The *approved* UI-SPEC (status: approved, checker sign-off 6/6 PASS) states under "New registry entry this phase **MUST** add": *"`sparkle` — … It is **absent** from `icon-registry.ts` today … Add it to the central registry as one more `{ outline, filled }` pair."* Plan 06 (24.1-06), however, explicitly does the opposite: its `flagged_assumptions` say "the sparkle glyph… [is] Phase 24.2," Task 1's `read_first` says "do NOT add a sparkle entry — AI marker is Phase 24.2," and its acceptance criteria grep for `sparkle` and require it to return *nothing*. Whichever is correct (I believe the plan's framing is the right one, since 24.1-CONTEXT.md D-08/D-09 explicitly forbid building AI egress in 24.1), **this is an unresolved conflict between a signed-off design contract and the executable plan**, not a planning nuance — it should be flagged back to the UI-SPEC as a correction, not silently overridden by the plan without a recorded note. As written, a naive executor who trusts the UI-SPEC over the plan (or a reviewer diffing the two) will see a direct contradiction.
- **[MEDIUM] No tombstone on soft-delete or on the eventual permanent purge — cross-phase resurrection risk not flagged for 24.2/36.** `deleteFuelCore` (`src/db/fuel-dao.ts:228-250`) inserts a tombstone via `insertTombstoneCore` before every hard DELETE, specifically for "UID reconciliation for portable restores" (ADR-056, per RESEARCH.md's "Don't Hand-Roll" table). Plans 02 and 04 explicitly and correctly *avoid* tombstoning memories (deferring backup/tombstone wiring to 24.2/36, matching the CONTEXT boundary), but **neither plan records this as a flagged assumption for the next phase to act on**. Since `purgeMemoryPermanently` is a genuine hard DELETE (Plan 04, Task 1) with no tombstone, once 24.2/36 wires memories into backup/restore-merge, a permanently-purged memory that predates a stale backup could be silently resurrected on restore with no tombstone to suppress it. This should at minimum be a `flagged_assumptions` entry in Plan 04 or 05's summary, the way Plan 00 flags the fuel↔memory coexistence assumption.
- **[LOW] `hidden` column has no CHECK / no documented invalid-value handling — Plan 00 Task 1.** The three-state `hidden` column (`NULL`/`0`/`1`) is specified with no `CHECK (hidden IN (0,1))` constraint, consistent with the codebase's existing no-CHECK convention (`fuel.kind` also has no CHECK per ADR-028's own text: "The column has no CHECK — the union is the enforcement boundary"). This is *consistent* with project norms, not a deviation, but it does mean `resolveVisibility(type, hidden)` (Plan 02 Task 3) needs to defensively handle an out-of-range integer (e.g. `2`) if a future writer ever gets it wrong — the plan's behavior spec only enumerates `1`/`0`/`null`, not "anything else." Low severity given the closed writer set, but worth a one-line test.
- **[LOW] `promoteToCurrentValueCore`'s demote step is unconditional on whether the target is already current — Plan 03 Task 2.** The demote statement (`UPDATE ... WHERE contact_id=? AND field_key=? AND is_current=1`) runs before the promote regardless of whether the target row is already the current one. If a caller calls "Make current" on the row that is already current, the demote step first flips it to 0, then the promote step flips the *same row* back to 1 via `id=?` — net effect is correct (still current, `modified_at` bumped twice via two statements in the same core), but the plan doesn't call out this no-op-safe-but-slightly-odd double-write as a tested case. Given the "must never destroy the prior value" requirement is the load-bearing invariant here, an explicit test for "promote the already-current entry" would remove any doubt.
- **[LOW] Plan 06's `~3-then-View-all cap`/grouping composition (Task 2) reads from four sources without a documented combined-read performance budget.** `getValuesForContact`, `listMemoriesForContact`, `listRelationshipsForContact`, and `getCurrentStateValue` (called once per history-aware field key) are all separate round-trips composed in one `useFocusEffect`. For a single contact this is bounded and cheap (SQLite is local, per CLAUDE.md), so this is not a correctness risk, but the plan doesn't specify batching `getCurrentStateValue` for multiple field keys (e.g. Last Talked About + Current Location) — likely 2 sequential awaits rather than one batched query. Not worth blocking on, but worth a one-line efficiency note for the executor.

## 4. Suggestions

- Have Plan 06 (or a small addendum) explicitly record the `sparkle`-deferral-to-24.2 decision as a correction against `24.1-UI-SPEC.md`, so the design-contract history isn't silently contradicted by the executable plan.
- Add a `flagged_assumptions` line to Plan 04's frontmatter (mirroring Plan 00's existing pattern) noting that permanent memory deletion mints no tombstone in 24.1, and that 24.2/36's backup/restore-merge wiring must account for this before it can safely serialize memories.
- Add one test case to Plan 03 Task 2 covering "promote the already-current entry to current" to close the demote/promote no-op ambiguity.
- Consider batching the current-state-history reads in Plan 06 Task 2 into a single query keyed by an `IN (?, ?)` over `field_key` rather than one call per history-aware field, since the set of history-aware field keys is registry-known ahead of time.

## 5. Risk Assessment

**LOW-MEDIUM.** The schema is additive-only and forward-only as required, the mutex/DAO patterns are faithfully copied from proven analogs, the ESCALATE trip-wires (ADR-001/028/031) are correctly treated as owner gates rather than resolved in-plan, and the wave/dependency ordering is internally consistent. The one MEDIUM finding that should block a clean sign-off is the UI-SPEC/Plan-06 contradiction on the `sparkle` icon — it's a small scope question with an easy resolution, but as written it's a genuine discrepancy between an "approved" contract and the plan meant to implement it, and it should be reconciled explicitly rather than left for the executor to guess which document wins.
