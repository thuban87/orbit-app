## Concerns

- **MEDIUM — Hidden live items become unreachable, so "presentation-only" is not practically reversible.** Plan 06 loads Memories through the profile-visible selector and filters relationships with `resolveRelationshipVisibility` (24.1-06-PLAN.md:132). Plan 02 defines that selector as excluding hidden rows (24.1-02-PLAN.md:147, :151); the only editor wiring is in that same TTR surface (24.1-07-PLAN.md:144). Thus, after Hide from Profile, there is no planned route to reveal or unhide a live Memory/relationship. That conflicts with the dossier's "presentation-only, not a privacy rule" decision (dossier §G).
- **MEDIUM — `MemoryHistoryScreen` is not instructed to remove the current row from the backlist.** Plan 04 defines `getCurrentStateHistory` as returning *all* entries, including current (24.1-04-PLAN.md:149, :158). Plan 07 then says to render the current row on top "then the ordered backlist" (24.1-07-PLAN.md:117). Without an explicit `is_current === 0` filter, the current row is duplicated and the required "No earlier entries" state for a current-only field cannot occur (24.1-07-PLAN.md:32).
- **LOW — `editHistoryEntry` accepts `fieldKey` but the planned UPDATE does not scope by it.** Plan 04's proposed edit SQL scopes only `id` and `contact_id` (24.1-04-PLAN.md:124). A stale/misrouted Last-Talked-About screen can therefore mutate a Current Location row for the same contact, despite the caller-supplied field-key contract. This is unlike the project's usual two-key write posture, e.g. editFuelCore (fuel-dao.ts:190).

## Suggestions

- Add a management-only "Hidden from Profile" section or an include-hidden TTR view. Keep hidden items out of the Profile composition, but make each live hidden item visible there with an Unhide action. Add hide → reopen → unhide UAT for both tables.
- In `MemoryHistoryScreen`, derive `priorEntries = history.filter((row) => row.is_current === 0)`; render only those beneath the current card. Add a current-only UAT/test asserting one visible current row and "No earlier entries."
- Change `editHistoryEntry` to `WHERE id = ? AND contact_id = ? AND field_key = ?`, bind `fieldKey`, and test that a same-contact/different-field entry causes rollback.
