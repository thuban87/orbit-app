## Codex Review

## Summary

The plan set is strong and substantially addresses the prior review cycles. It matches the repository’s real architecture: forward-only migrations, node-SQLite test harness, non-reentrant write mutex, dual Dashboard/Orrery profile stacks, and launch-sweep conventions. I found three new actionable gaps—one around data-revision bumps in the new expiry path, one merge integrity edge case, and one migration-test coverage mismatch.

## Strengths

- Migration sequencing is grounded in the live code: `TARGET_VERSION` is 15 and migrations end at 015 in [database.ts](/home/bwales/projects/orbit-app/src/db/database.ts:50), so 016 is correct at plan time.

- The staged-upgrade test approach is sound. The runner selects pending migrations strictly from the real `PRAGMA user_version` ([runner.ts](/home/bwales/projects/orbit-app/src/db/migrations/runner.ts:38)), so the plan correctly rejects spoofing a user-version onto a fully migrated schema.

- The N1 expiry fix correctly follows the established safe pattern. `expireFieldIfStale` reacquires the write transaction, rechecks the complete stale predicate, and calls a non-mutexed core ([field-ddl.ts](/home/bwales/projects/orbit-app/src/db/field-ddl.ts:232)). The plan mirrors that instead of nesting a transaction, which would deadlock under the deliberately non-reentrant mutex ([transaction.ts](/home/bwales/projects/orbit-app/src/db/transaction.ts:49).

- Dual-stack route registration is necessary and correctly planned: `ContactProfileScreen` is mounted in both [DashboardStack.tsx](/home/bwales/projects/orbit-app/src/navigation/tabs/DashboardStack.tsx:43) and [OrreryStack.tsx](/home/bwales/projects/orbit-app/src/navigation/tabs/OrreryStack.tsx:18).

- The relationship merge/purge work appropriately closes a real lifecycle hole. Current `mergeContacts` reparents only a fixed list before deleting the absorbed contact ([merge-dao.ts](/home/bwales/projects/orbit-app/src/db/merge-dao.ts:153)); unlisted new FK children would otherwise cascade-delete. Likewise, purge intentionally uses explicit fan-out ([purge-dao.ts](/home/bwales/projects/orbit-app/src/db/purge-dao.ts:244)).

- The phase scope is cleanly protected: requirements 01–09 belong to 24.1, with search, AI egress, import, custom-field expansion, backup, and share-capture migration explicitly assigned to 24.2 in [REQUIREMENTS.md](/home/bwales/projects/orbit-app/.planning/REQUIREMENTS.md:53).

## Concerns

- **MEDIUM — expiry writers may fail to bump the data revision.**  
  Plans 03 and 05 specify that `expireRelationshipIfStale` / `expireMemoryIfStale` open a transaction and call the non-mutexed permanent-purge core. But neither task explicitly requires `bumpDataRevisionCore` after a successful expiry. Existing standalone writers do this inside their transaction—for example, [addFuel](/home/bwales/projects/orbit-app/src/db/fuel-dao.ts:255) calls `bumpDataRevisionCore` after its core write. Without it, sweep-driven permanent deletes can leave backup/dirty-state consumers unaware of a durable change.

  Add `bumpDataRevisionCore(exec)` only after a successful stale deletion in both expiry functions, and test revision unchanged for a skipped candidate and incremented for a deleted one.

- **MEDIUM — merge logic misses one self-link case created by reparenting.**  
  Plan 03 nulls links where `linked_contact_id = absorbedId` before reparenting. That protects a survivor-owned relationship pointing at the absorbed contact. But an absorbed-owned relationship pointing to the survivor (`contact_id = absorbedId`, `linked_contact_id = survivorId`) becomes a self-link after `contact_id` is reparented to the survivor. Current production merge code has no knowledge-table handling yet, and its generic reparent simply updates `contact_id` ([merge-dao.ts](/home/bwales/projects/orbit-app/src/db/merge-dao.ts:88)).

  Before reparenting, also clear rows matching `contact_id = absorbedId AND linked_contact_id = survivorId`, and add a regression test. This preserves the plan’s stated “never self-link” invariant even for rows inserted outside the normal DAO path.

- **LOW — Plan 01 overclaims “any prior version” while testing only 1, 8, and 15.**  
  The planned tests meaningfully exercise early, middle, and immediate-predecessor upgrades, but they do not prove the stated “any prior user_version v1..v15” truth. The existing full-chain test only covers v0 to target ([full-chain.test.ts](/home/bwales/projects/orbit-app/src/db/migrations/full-chain.test.ts:16)).

  Either parameterize staged-upgrade tests across versions 0–15, or narrow the must-have statement to representative prior-version coverage. Since this is an irreversible migration, exhaustive inexpensive coverage is preferable.

- **LOW — relationship deletion copy is misleading.**  
  Plan 07 says relationship soft-delete should show “Moved to Recently Deleted,” while its own scope says relationships are Undo-only and excluded from that surface. This can direct users toward a recovery location where the item will not appear.

  Use relationship-specific copy such as “Relationship removed” with Undo.

- **LOW — no read indexes are specified for the new main query paths.**  
  The planned live/trash/history reads filter by `contact_id`, `deleted_at`, and `field_key`; only the partial “current” uniqueness index is planned. The existing schema adds a dedicated contact/date index for recency reads ([001-initial.ts](/home/bwales/projects/orbit-app/src/db/migrations/001-initial.ts:112)). The new tables will be small initially, but Profile and Trash are recurring reads.

  Evaluate `EXPLAIN QUERY PLAN` with realistic fixtures and, if needed, add additive indexes such as `(contact_id, deleted_at, id)` for Memories/Relationships and `(contact_id, field_key, created_at DESC)` for state history.

## Suggestions

1. Amend Plans 03 and 05 to require data-revision bumps in successful expiry transactions and add direct tests.
2. Extend Plan 03’s merge SQL and tests for absorbed-owned rows linked to the survivor.
3. Make the migration staged-upgrade matrix exhaustive, or make its guarantee accurately representative.
4. Correct relationship Undo snackbar copy.
5. Add a small query-plan/index validation to the migration/read-layer work.

## Risk Assessment

**MEDIUM.** The plans are unusually well specified, dependency-aware, and aligned with the codebase. The remaining risks are concentrated in irreversible or background-like mutation paths: revision signaling during launch-sweep deletes, merge-created relationship self-links, and proving migration safety across all upgrade states. Addressing the first two before execution should reduce implementation risk to low-to-medium.

# Cross-AI Plan Review — Cycle 3 (Convergence Check)

## Summary

The 24.1 plan set is unusually mature after two review cycles — the N1 TOCTOU fix (mutex-owning `expireMemoryIfStale`/`expireRelationshipIfStale` that re-verify the full past-window predicate under the write lock before calling the non-mutexed purge core) is implemented consistently across Plans 03 and 05 and matches the cited `field-ddl.ts:232-252` precedent's shape as described. Most cycle-1/cycle-2 findings are genuinely incorporated with grep-checkable acceptance criteria. However, tracing Plan 03 Task 3's merge-dao self-link handling against its own stated invariant turned up a concrete, previously-unflagged data-integrity bug in the merge self-link avoidance logic — it only guards one of the two directions a self-link can be created during a contact merge.

## Strengths

- The N1 fix is structurally sound: `expireMemoryIfStale`/`expireRelationshipIfStale` open exactly one `inWriteTransaction`, re-check `deleted_at IS NOT NULL AND deleted_at < datetime('now','localtime', ?)` under the lock, and only then call the non-mutexed `purge*PermanentlyCore` — this correctly closes the restore-then-redelete race the cycle-2 review flagged, and the sweep (Plan 05 Task 2) calls these instead of the existence-only user-facing purge writers (`grep -c "purgeMemoryPermanently\|purgeRelationshipPermanently" src/services/memory-trash-sweep.ts` gated to 0 is a good regression guard).
- `24.1-01-PLAN.md` Task 1's staged-upgrade test requirement (runMigrations to N=1,8,15 then to 16, with a grep forbidding spoofed `user_version` writes) correctly avoids the M4 pitfall of faking an old-schema DB via `PRAGMA user_version` alone.
- The core/wrapper mutex discipline is applied uniformly and every new writer's acceptance criteria include a grep for "cores contain no `inWriteTransaction`" — consistent with `fuel-dao.ts:131-152/255-264` and the documented non-reentrancy hazard.
- Provenance (N2) and the empty-state gate exclusion (N5) are both incorporated with matching truths, actions, and greppable acceptance criteria in Plans 06.

## Concerns

**HIGH — `merge-dao.ts` self-link avoidance (Plan 03, Task 3) only guards one direction, leaving the other to silently create a self-link.**
`24.1-03-PLAN.md` Task 3's action specifies, verbatim:
```
UPDATE relationships SET linked_contact_id = NULL, modified_at = ?
 WHERE linked_contact_id = ? AND contact_id IN (?, ?)
 -- bound [now, absorbed.id, survivor.id, absorbed.id]
```
This only nulls rows where **`linked_contact_id = absorbed.id`** — i.e., a relationship (owned by either the survivor or the absorbed contact) that *points at* the absorbed contact. It does not touch the symmetric case: a relationship **owned by the absorbed contact** whose `linked_contact_id` already equals the **survivor**'s id (`contact_id = absorbed.id AND linked_contact_id = survivor.id`). That row is *not* selected by the SET-NULL step (its `linked_contact_id` is `survivor.id`, not `absorbed.id`), so it survives untouched into the generic reparent loop, where `reparent()` (per the file's own `UPDATE table SET contact_id = ? … WHERE contact_id = ?` shape, cited at `merge-dao.ts:88`) rewrites its `contact_id` from `absorbed.id` to `survivor.id` — producing a row with `contact_id = survivor.id` and `linked_contact_id = survivor.id`: a self-link, written by raw migration/merge SQL that never passes through `assertNotSelfLink` (that guard only fires inside `addRelationshipCore`/`editRelationshipCore`, per Plan 03 Task 1's own description).
- **Failure scenario:** Contact A has a relationship record "Sister — linked to Contact B" (`contact_id=A, linked_contact_id=B`). B is merged into A (A survives). The SET-NULL step only looks for rows with `linked_contact_id = absorbed.id`; here `absorbed = B`, and the row's `linked_contact_id = B`... wait — re-check: if B is absorbed and A is survivor, this row (owned by A=survivor, linking to B=absorbed) **is** caught by the SET-NULL clause (`contact_id IN (survivor, absorbed)` and `linked_contact_id = absorbed`). The gap is the reverse: a relationship **owned by B** (`contact_id=B`) whose `linked_contact_id = A` (the survivor) — e.g., B has "Sister — linked to A" before the merge. This row's `linked_contact_id` is `A.id` = `survivor.id`, not `absorbed.id`, so the SET-NULL predicate does not match it. The reparent loop then flips its `contact_id` from `B` to `A`, producing `contact_id=A, linked_contact_id=A` — a self-link.
- **Why it matters:** Task 3's own must-have truth says "a relationship OWNED by the survivor whose link pointed at the absorbed contact is not turned into a self-link — it is SET NULL explicitly (assertNotSelfLink invariant, review L3) and this case is tested" — but the mirror direction (owned by the *absorbed* contact, linking to the *survivor*) is neither implemented nor listed among the Task 3 test cases ("reparent, re-point, self-link-avoidance, single-current-collision, and purge fan-out cases" — no case named for absorbed-owns/survivor-target). This is exactly the kind of case a real user hits: two people who already know each other and each recorded the other as a Key People relationship before one contact gets merged into the other.
- **Suggested fix:** extend the SET-NULL predicate (or add a second statement) to also cover `contact_id = ? AND linked_contact_id = ?` bound `[absorbed.id, survivor.id]` — i.e., null out (or otherwise handle) any relationship *owned by the absorbed contact* whose link already targets the survivor, before the reparent loop runs.

**MEDIUM — Plan 03 Task 3's acceptance criteria don't actually gate on the missing case, so this would ship unnoticed.**
None of the Task 3 acceptance-criteria greps (`assertNotSelfLink`, the reparent-list grep, the `UPDATE relationships SET linked_contact_id` grep for statement location) would catch the omission, since the existing SET-NULL statement genuinely exists above the `DELETE FROM contacts` line — it's just under-scoped. A reviewer or CI running only the specified greps would see all criteria pass while the row-level bug ships. Recommend adding an explicit merge-dao.test.ts case (owner is B pre-merge, `contact_id=B, linked_contact_id=A`, A survives) and asserting `linked_contact_id !== id` post-merge for every relationships row.

**LOW — the `RELATIONSHIPS_GROUP.visibilityDefault` type in Plan 01 Task 2 duplicates the shape of `MemoryTypeMeta.visibilityDefault` without sharing a named type**, per the action text (`RELATIONSHIPS_GROUP: { displayName: string; visibilityDefault: 'show' | 'hide'; presentationOrder: number }` declared inline rather than via a shared interface). Not a correctness bug, but a minor missed reuse opportunity Plan 01 itself could tighten (a `VisibilityDefault` type alias) — low priority, doesn't block anything.

## Suggestions

1. In Plan 03 Task 3, replace the single directional SET-NULL statement with one that also matches `contact_id = absorbed.id AND linked_contact_id = survivor.id` (or generalize to: null any relationship row, on either contact, where after the pending reparent it would have `contact_id == linked_contact_id`). Add the missing test case named above.
2. Add a general post-merge invariant assertion to the merge-dao test suite: after any merge, `SELECT COUNT(*) FROM relationships WHERE contact_id = linked_contact_id` is always 0 — this is a stronger, harder-to-miss regression guard than enumerating specific directional cases.

## Risk Assessment

**MEDIUM.** The rest of the plan set (migration shape, mutex discipline, TOCTOU fix, soft-delete/visibility/provenance rendering) is solid and the cycle-1/cycle-2 dispositions check out against the cited source files. But the merge self-link gap is a genuine, silent data-integrity defect that would violate the plan's own stated invariant (and the DAO-level `assertNotSelfLink` guarantee) via a code path that bypasses that guard entirely — it should be fixed before Plan 03 executes, since migration 016 and the relationships table are frozen contracts other phases build on.
