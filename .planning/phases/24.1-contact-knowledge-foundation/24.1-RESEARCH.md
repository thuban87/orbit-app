## Summary

Phase 24 defines Orbit's durable contact-knowledge model and is verified (this session) to be **almost entirely unbuilt** — the dossier's D-04 claim holds against the code on disk. What exists today is: a fixed-5-kind `fuel` table (conversational notes, hard-DELETE, `source` as a bare string), a normalized `custom_field_values` model (ADR-001 / migration 006) with 7 field types and a destructive-only `field_history` table, and a name-plus-eligible-`fuel.text` LIKE search inside `dashboard-read.ts`. There is **no** Memory-type registry, **no** relationships table, **no** current-state history (Last Talked About / Location), **no** soft-delete or Recently Deleted, **no** per-item AI permission, and **no** note import. This phase builds all of that.

**Migration state verified on disk:** `TARGET_VERSION = 15` (`src/db/database.ts:50`), migration files run `001`–`015`, and `MIGRATIONS` registers `migration001`…`migration015`. **The first new migration this phase writes is `016`.** (The STATE.md note saying "001–011, TARGET_VERSION 11 as of P19" is stale — head has drifted since; always re-verify at plan time, D-03.) `BACKUP_FORMAT_VERSION = 3` (`src/backup/types.ts:14`); Phase 36 bumps it to 4 — **do not bump it here** (D-03).

**Primary recommendation:** Treat this as a **schema-first, multi-plan cluster** with a strict wave order: (1) the migration(s) creating the new tables/columns and the in-code Memory-type registry; (2) DAOs + the unified semantic read layer (Memory items, relationships, current-state history, per-item AI permission, soft-delete); (3) the migration data-moves (share-capture carry-over, ADR-030 retirement); (4) the search-corpus exposure + TS typo scoring; (5) custom-field extensions (3 new types, value-history table, scope column) — enumerating and updating every seeding writer; (6) the "Things to Remember" / Recently Deleted UI. **This phase is very likely too large for one plan cluster — see `## Phase-Split Assessment`.** Several ESCALATE trip-wires (D-05/06/07) and a terminology flag (D-11) are owner calls; surface them, do not resolve them.

### Pattern 1: Core/Wrapper split with the non-reentrant mutex
**What:** Every mutating DAO exposes a non-mutexed `…Core(exec, …)` (assumes BEGIN is open) and a standalone wrapper that owns exactly one `inWriteTransaction`. Multi-row fan-outs compose the Cores inside ONE outer transaction — never nest the mutex.
**When:** All new writers (memories, relationships, history, AI-permission, soft-delete/restore).
**Example:** `src/db/fuel-dao.ts:131` (`addFuelCore`) + `:255` (`addFuel`); fan-out in `src/db/capture-dao.ts:43` (`captureMultiAttach`).

### Pattern 2: Single read choke point with in-SQL exclusions
**What:** One read module per domain; the structural access-control predicates (off_limits exclusion, AI-eligibility) live IN the SQL, exported as reusable fragments, never as a UI `.filter()`.
**When:** The Memory/search read layer; the AI-egress read.
**Example:** `src/db/fuel-read.ts:133` (`RANKED_FUEL_EXCLUSIONS` — `kind != 'off_limits' AND source != 'ai' AND …`), reused by `dashboard-read.ts` with a parity test guarding against drift.

### Pattern 3: Additive value-history table (NOT relaxing ADR-001)
**What:** History-retained custom fields and current-state fields get a **new** table holding one durable row per historical value (with `uid`, `contact_id`, `field_def_id`/field key, `value` TEXT, `created_at`). The current value stays the single `custom_field_values` pair row (KNOW-04/12). `sortExpr()` still routes ordering over the current value column.
**When:** KNOW-03/04/12.
**Example seam:** `sortExpr()` at `src/db/field-sort.ts:29` is latent (no runtime consumer yet) and expects a `values_table.value` join constrained by `field_def_id` — a first consumer may appear this phase; keep raw-TEXT ordering, CAST only for number/toggle.

### Pattern 4: Launch-sweep hook for time-based cleanup
**What:** Register an idempotent async hook on `registerSweepHook`; it runs once per real `background→active` (and cold start). No background timer, no trigger.
**Example:** `src/services/field-sweep.ts:87`, `src/services/backup-sweep.ts:25`, `src/services/photos/photo-reconcile-sweep.ts:30` all follow this exact shape. Trash expiry + history retention register here (D-11).

### Anti-Patterns to Avoid
- **Flattening all knowledge into one generic text table** — dossier explicitly warns against it; keep first-class fields, custom fields, relationships, and Memories distinct behind the unified surface.
- **Inferring AI eligibility from type or storage location** — permission is explicit state, default OFF (dossier "Notes for Roadmapper", ADR-050/078).
- **A UI-side privacy filter for Off Limits** — reverses ADR-036; exclusion must be in SQL (D-09).
- **Interpolating a custom-field identifier into ORDER BY / comparison** — always route through `sortExpr()` (D-06).
- **Editing a shipped migration (001–015)** — forward-only, irreversible in production; add 016+.
- **Bumping `BACKUP_FORMAT_VERSION` here** — it stays 3; Phase 36 owns the bump (D-03).
- **A background timer for Trash/history expiry** — nothing watches a timestamp; use the launch sweep (D-11).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Serialized writes | Ad-hoc `BEGIN`/`COMMIT` | `inWriteTransaction` + core/wrapper split (`transaction.ts`) | Mutex is non-reentrant; nesting deadlocks (HIGH-1 lessons across Phases 3/8/13). |
| Merge identity | Auto-increment only | `newUid()` + `uid TEXT UNIQUE` per table | Portable restore/merge (ADR-056); backup keys on uid. |
| Local timestamps | `new Date().toISOString().split('T')[0]` | `localDateTime()` / `formatLocalDate()` | UTC evening off-by-one; already fixed once (CLAUDE.md). |
| Time-based cleanup | `setInterval` / background task | `registerSweepHook` launch sweep | SQLite has no scheduler; triggers fire only on data events (D-11). |
| Custom-field type validation | Pairwise converters | One parser per `FieldType` (`field-parsers.ts`) | ADR-014: exactly N parsers, never N² converters; `Record<FieldType,…>` makes it exhaustive at `tsc` (D-12). |
| Custom-field ordering | Inline `ORDER BY <col>` | `sortExpr()` (`field-sort.ts`) | Raw TEXT makes numeric ordering observable; the helper CASTs safely (D-06). |
| Cross-contact search index | FTS5 / new index | LIKE eligibility filter + TS edit-distance scoring | ADR-031 rejected FTS5; reversing → ESCALATE (D-07). |
| Value timeline | `field_history` reuse | New additive value-history table | `field_history` is destructive-only, unread, 30-day-pruned, backup-excluded (R-08, D-06). |

**Key insight:** Nearly every "how do I do X safely in this DB layer" question already has a canonical, tested answer in an existing DAO. Read the neighbor before writing new SQL (CLAUDE.md "Review the code, not the diff").

## Common Pitfalls

### Pitfall 1: Assuming a migration number
**What goes wrong:** Writing `migration016` when head has drifted, or hardcoding a number from these notes.
**Why:** Every schema phase bumps head; STATE.md's "001–011" note is already stale (now 001–015).
**How to avoid:** At plan time, re-read `src/db/database.ts` `TARGET_VERSION` and `ls src/db/migrations/`. Verified today: head is **15**, first new is **016**.
**Warning signs:** A migration whose `version` collides with an existing file → runner applies wrong order.

### Pitfall 2: Nesting the non-reentrant mutex
**What goes wrong:** Calling a wrapper (`addFuel`) inside another `inWriteTransaction` → deadlock.
**How to avoid:** Compose `…Core` functions inside one outer transaction (see `capture-dao.ts`). Every prior phase (3/8/13) hit and documented this.

### Pitfall 3: Reversing an ADR while "fixing a bug"
**What goes wrong:** Relaxing `UNIQUE(contact_id, field_def_id)` to store history, adding FTS5 for "better" search, or letting users create system types — each silently reverses ADR-001/031/028.
**How to avoid:** These are ESCALATE trip-wires (D-05/06/07). Stop and ask the owner; name which decision dies. A reviewer flagging a control removal by name is an escalation trigger, not a finding to close (CLAUDE.md).

### Pitfall 4: Treating "Memory" / default-type name as final
**What goes wrong:** Hardcoding the user-facing "Memory" label per screen; naming the default built-in type before the owner reconciles it.
**How to avoid:** Surface label as a single-source copy constant (24-UI-SPEC). The **schema/model is buildable with "Memory" as the provisional label** — but the *default/general built-in type name* is unresolved and blocks Rapid-Capture-phase copy, surfacing as `human_needed` at verify time (D-11).

### Pitfall 5: Off Limits treated as a privacy/AI-permission control
**What goes wrong:** Merging Off Limits into the new per-item AI permission, or hiding it.
**How to avoid:** Off Limits is a *state* ("avoid this topic"), stays **visible by default**, stays a **separate control** from AI permission, and its SQL-level exclusion stands unless a superseding ADR exists (D-08/09; check `docs/decisions/` for ADR-050/078/036).

### Pitfall 6: Forgetting the backup entity declaration
**What goes wrong:** New entities (memories, relationships, history, AI-permission, soft-deleted rows) not declared for Phase 36's format-4 serialization → they silently miss backup.
**How to avoid:** Declare the full new entity list in this phase's plan (KNOW-15/16, R-09). Add new tombstone entity types to `TOMBSTONE_ENTITY_TYPES` (`backup-schema.ts`). Do NOT bump `BACKUP_FORMAT_VERSION` (stays 3).

### Applicable ASVS Categories
| ASVS Category | Applies | Standard Control |
|---------------|---------|------------------|
| V5 Input Validation | yes | Read-time parsers (`field-parsers.ts`) flag, never coerce; TEXT storage forever. |

| V6 Cryptography | no (new) | Backup encryption unchanged (existing `src/backup/encryption.ts`); not touched here. |

### Known Threat Patterns for {expo-sqlite / local-first / AI egress}
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| SQL injection via custom-field identifiers in ORDER BY | Tampering | `sortExpr()` only; never interpolate identifiers; `?`-bind all values (T-03-04). |
| Private/off-limits content reaching a glanceable/AI surface | Information Disclosure | In-SQL exclusion fragment reused with a parity test (`RANKED_FUEL_EXCLUSIONS` model); explicit AI-permission predicate. |
| AI-permission inferred from type → accidental egress | Information Disclosure / Elevation | Permission is explicit state, default OFF, two gates; changing a type default affects NEW items only (dossier §M). |
| Irreversible migration corrupts unreachable devices | Denial of Service (data) | Forward-only, no assumed start state, atomic per-step transaction, proof-of-copy pattern (migration 006 model); never edit shipped migrations. |
| Soft-deleted/history rows leaking or lost on backup | Information Disclosure / data loss | Declare all new entities (incl. soft-deleted) for Phase 36 format-4; add tombstone entity types; keep `field_history` backup-excluded. |
