## Critical Issues

### CR-01: A revived knowledge UID cannot be permanently deleted again

**Classification:** BLOCKER

**File:** `src/db/tombstones-dao.ts:65-69`, `src/backup/restore-apply.ts:247`, `src/backup/restore-apply.ts:279`, `src/db/memories-dao.ts:268-272`, `src/db/relationships-dao.ts:179-183`

**Issue:** Merge reconciliation permits a live incoming row whose `modifiedAt` is newer than an existing tombstone to survive, but `importTombstones` deliberately retains that older tombstone. When the resurrected Memory or relationship is later soft-deleted and purged, the DAO calls `insertTombstoneCore`, whose plain `INSERT` violates `UNIQUE(entity_type, entity_uid)`. The surrounding write transaction rolls back, so the user cannot permanently delete that row. The same raw insert is used by contact-purge fan-out, so an archived contact containing a revived UID can also make the whole purge fail.

**Fix:** Make `insertTombstoneCore` use the same conflict-safe, maximum-timestamp upsert as `importTombstones` (or remove a superseded tombstone when a newer live row wins). Add a regression that merges a newer same-UID Memory/relationship over an old tombstone, then soft-deletes and permanently purges it successfully; cover contact-purge fan-out too.

### CR-02: Restore accepts contact-knowledge rows that violate application-owned registries

**Classification:** BLOCKER

**File:** `src/backup/backup-schema.ts:394-421`, `src/backup/restore-apply.ts:185-187`

**Issue:** The backup parser only checks that `memories[].type` and `currentStateEntries[].fieldKey` are strings. It accepts an arbitrary Memory type, an arbitrary current-state field, a `custom` Memory without its required label, or a wholly blank Memory, then `upsertChildren` writes those values directly rather than using the validated DAO boundary. This violates the phase's application-owned Memory/current-state registries and leaves malformed, uneditable rows in the database after importing a malformed or future backup.

**Fix:** Validate backup knowledge rows against `isMemoryTypeKey` and `isCurrentStateFieldKey`; enforce the same `custom` label and nonblank effective-content rules as `addMemoryCore`, plus the closed provenance/flag contracts. Reject the manifest before `applyRestore` opens its transaction, with parser tests for each invalid case.
