## Warnings

### WR-01: Fresh Memories still replace inherited visibility with an explicit override

**Classification:** WARNING

**File:** `src/components/MemoryEditor.tsx:160-171`, `src/components/MemoryEditor.tsx:188-191`, `src/screens/ThingsToRememberScreen.tsx:273-281`

**Issue:** The latest fix preserves `hidden: null` only when an existing `MemoryRow` has `hidden IS NULL`. For a new item, optional chaining produces `undefined`, which fails the `=== null` check and initializes the draft to `false`. The create path spreads that value into `addMemory`, which persists `hidden = 0`. New Memories therefore stop inheriting their type's visibility default before the user selects an override, contradicting the nullable three-state contract and making future registry-default changes ineffective for every newly created item.

**Fix:** Initialize both an absent item and an inherited item to `null`, and add a create-path regression.

```ts
hidden:
  item?.hidden === 1 ? true : item?.hidden === 0 ? false : null,
```

### WR-02: Relationship DAO accepts invalid visibility values that make backups unexportable

**Classification:** WARNING

**File:** `src/db/relationships-dao.ts:8-29`, `src/db/relationships-dao.ts:68-84`, `src/db/relationships-dao.ts:121-124`, `src/backup/backup-schema.ts:449-450`

**Issue:** `NewRelationshipInput.hidden` and `EditRelationshipInput.hidden` are unrestricted `number | null`, and both writers bind the value directly. A caller can persist `hidden: 2` (or any other number). Rendering silently treats it as the group default, while the export parser correctly rejects it as a non-binary flag; the user can then no longer produce a backup from that database.

**Fix:** Narrow the public input to `0 | 1 | null` (or normalize a boolean), validate it at both writer boundaries, and add regressions that reject `2` without changing a row.

### WR-03: Restore parser leaves relationship optional fields unvalidated

**Classification:** WARNING

**File:** `src/backup/backup-schema.ts:440-450`, `src/backup/restore-apply.ts:186`

**Issue:** Relationship validation checks the required fields and flags, but never validates optional `relationType`, `note`, or `deletedAt`. A malformed backup can therefore pass a number or another non-string for these fields to raw restore SQL. SQLite can coerce scalar values into the TEXT columns (or an unsupported binding can fail the whole restore), bypassing the otherwise strict portable-schema contract and leaving data that was not represented by the manifest types.

**Fix:** Before restore planning, require each optional field to be `null`/`undefined` or a string, matching the Memory validation immediately above; add parser cases for invalid `relationType`, `note`, and `deletedAt`.
