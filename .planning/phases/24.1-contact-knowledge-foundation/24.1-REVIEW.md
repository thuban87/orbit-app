# Phase 24.1: Code Review Report

**Reviewed:** 2026-09-04T07:27:25Z
**Depth:** deep
**Files Reviewed:** 38
**Status:** issues_found

## Summary

The migration and most DAO transaction boundaries are sound, but the phase ships a new durable data domain that is omitted from every backup and restore, exposes arbitrary URI schemes through a new card action, and fails to mark automatic-backup state dirty after permanent deletes. The focused test suite and TypeScript check pass, but neither exercises these cross-module failure paths.

## Narrative Findings (AI reviewer)

## Critical Issues

### CR-01: Contact Knowledge is silently excluded from every backup and restore

**Classification:** BLOCKER

**File:** `src/db/memories-dao.ts:257`, `src/db/relationships-dao.ts:177`, `src/db/current-state-history-dao.ts:87`, `src/backup/export-manifest.ts:45-80`, `src/backup/types.ts:48-66`, `src/backup/restore-apply.ts:49-54`

**Issue:** All three new writers mark the database dirty, causing the app to create a backup, but the manifest has no `memories`, `relationships`, or `currentStateEntries` fields and `readManifest` never queries their tables. The parser and restore entity list also cannot carry or apply them. A manual or automatic backup taken after a user adds this data reports success but omits it; restoring that backup silently loses the entire Phase 24.1 knowledge domain.

**Fix:** Version the portable backup format and add validated, UID-based manifest records for all three tables. Export rows joined to their contact UIDs (and linked-contact UID for relationships), restore them after contacts, and add round-trip tests covering live, deleted, linked, and current/history rows. Do not ship the tables before the backup format supports them.

### CR-02: Memory links bypass the repository’s required http/https allowlist

**Classification:** BLOCKER

**File:** `src/components/MemoryCard.tsx:21-23`

**Issue:** The card passes the stored URL directly to `Linking.openURL`. This contradicts the project’s established positive allowlist in `LinksEditor`/`FuelEditor`, which intentionally prevents `file:`, `intent:`, `javascript:`, and other custom schemes from reaching the OS. Memory values can be imported or otherwise persisted outside the editor, so a crafted record can trigger an arbitrary registered URI handler when the user taps “Open link.”

**Fix:** Reuse `normaliseLinkUrl` from `LinksEditor` (or extract it into a shared URL-safety utility) before opening the URL, and add a component/logic test for hostile schemes:

```ts
void Linking.openURL(normaliseLinkUrl(url)).catch(() => {});
```

### CR-03: Permanent memory and relationship removal does not trigger a backup

**Classification:** BLOCKER

**File:** `src/db/memories-dao.ts:301-334`, `src/db/relationships-dao.ts:212-244`

**Issue:** Public add/edit/soft-delete/restore wrappers advance `data_revision`, but user-confirmed permanent purge and launch-sweep expiry only call their core DELETEs. The automatic-backup policy explicitly skips a run when `data_revision === last_backup_data_revision`. Consequently, if a soft-deleted item has already been backed up, a later permanent purge/expiry is never snapshotted and a restore can resurrect data the user permanently deleted.

**Fix:** Advance the revision exactly once inside each successful public purge/sweep transaction (not in the core, so composed operations remain controllable), and test that both manual permanent purge and stale-expiry increment it.

## Warnings

### WR-01: The DAO persists wholly blank Memory rows despite the phase contract

**Classification:** WARNING

**File:** `src/db/memories-dao.ts:97-123`, `src/db/memories-dao.test.ts:68-90`

**Issue:** `addMemoryCore` normalizes a blank value and label to `NULL` then inserts the row. This violates the phase’s explicit commit-boundary rule that a draft with blank/whitespace value and no custom label is not persisted. Such a direct DAO call produces an effectively empty, glanceable card; the current test codifies the faulty behavior rather than guarding it.

**Fix:** Normalize value and label first, then reject when both are null. Keep the existing custom-label rule and replace the normalization-only test with an assertion that no row is written.

### WR-02: Showing hidden rows destroys the promised deterministic ordering

**Classification:** WARNING

**File:** `src/screens/ThingsToRememberScreen.tsx:232-249`

**Issue:** DAO reads are correctly ordered (pinned, date, creation, id), but this screen partitions them into visible and hidden arrays and, when the toggle is on, concatenates all visible rows before every hidden row. A hidden pinned/new row is therefore displayed after a visible unpinned/older row. Relationships have the same defect. This makes the include-hidden surface disagree with the ordering contract and changes a row’s place solely because of a presentation flag.

**Fix:** Preserve the original ordered DAO array in state and filter it only for the hidden-off view, or merge the partitions with the original comparator. Add a UI/logic test with interleaved hidden and pinned rows.
