<objective>
Build the per-contact custom-value data access (read/UPSERT) and the pure visibility selectors that
decide where each field appears (FLD-07). Tables already exist (FLD-01) — this wires the value
operations.

Purpose: A field's data is one column per field on `contact_custom_values` (one row per contact). This
plan owns reading a contact's values with a dynamic (whitelist-built) SELECT, UPSERTing a single value,
and the three placement rules from §14.7: profile = value-present OR always_show; create form =
show_on_new only; edit form = every non-quarantined field. The host forms/profile are Phase 4's shell —
this plan delivers the selectors those screens call.

Output: `src/db/field-values-dao.ts` (getValuesForContact, upsertValue, visibleDefsForProfile,
defsForCreateForm, defsForEditForm), node:sqlite-proven.

Independence: this plan does NOT depend on Plan 03's DDL — its test fixture adds a value column with a
direct `ALTER TABLE contact_custom_values ADD COLUMN` so it can run in parallel. It DOES depend on
Plan 01's `isSafeColName` to guard identifier interpolation.
</objective>
