<objective>
Build the field-DEFINITION editor (§14.10 item 1 — the largest net-new UI) and make it reachable: a
Settings → Custom Fields screen that lists fields, creates/edits/reorders them, runs the dynamic
delete/quarantine action, and drives a type change through the pre-flight summary. This is the surface
the owner reviews at the --to 3 gate.

Purpose: This screen composes the whole data layer into the user-facing capability of FLD-02/03/04/05
and the FLD-07 curation flags. It edits field DEFINITIONS (label, type, dropdown options, show_on_new,
always_show), not per-contact values — the value widgets (Plan 06) render a live preview so the owner
can see each type at the gate.

Output: `src/components/FieldDefForm.tsx` (create/edit a definition), `src/screens/CustomFieldsScreen.tsx`
(list, reorder, dynamic delete/quarantine, launch the editor, type-change summary), and a HomeScreen
route to reach it.

Scope fence: NO contact CRUD/profile shell (Phase 4), NO navigation-library dependency (reachability is
a local screen-state toggle), NO share_with_ai toggle (Phase 14). Verification is tsc + biome +
check:colors here and the owner's visual review at the --to 3 gate (no RN-component test harness exists).
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | col_name from a user label | high | mitigate | The screen calls makeColName (Plan 01) and the tested DAOs; it never interpolates a label into SQL itself. |
| T-03-02 | Denial (data loss) | delete of a populated field | high | mitigate | The dynamic action forces Quarantine (reversible 30d) for a populated field; immediate Delete is offered only when isFieldEmpty is true. |
| T-03-07 | Information disclosure | hardcoded colour | low | mitigate | check:colors runs on every new UI file; error emphasis composed from tokens. |
