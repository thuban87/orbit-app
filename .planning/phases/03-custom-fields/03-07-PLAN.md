<objective>
Build the launch-time quarantine-expiry + history-retention sweep (FLD-05) and wire it into the app.
This is the DATA-06 registry's intended first consumer: nothing watches a timestamp, so quarantine
expiry runs as a sweep at real foreground launch.

Purpose: A field quarantined past the fixed 30-day window is permanently dropped (its data snapshotted
to field_history first); field_history itself is pruned on the same 30-day schedule. The sweep loop calls
Plan 03's PUBLIC `dropField` DIRECTLY — `dropField` already owns its mutex + transaction, so each stale
def is dropped in its own serialized transaction "for free," and per-def failure isolation comes from a
per-iteration try/catch. Critically, the loop must NOT wrap `dropField` in a second
`withMutex`/`inWriteTransaction`: `withMutex` is non-reentrant (mutex.ts:32-36), so an inner acquisition
queues behind the outer's settlement while the outer awaits the inner — a permanent hang that leaves
`running=true` and disables the launch-sweep registry for EVERY later phase's hook (archived purge,
schedule reconcile, backup rotation). This is the phase's one clear must-fix defect (review HIGH-1).

Output: `src/services/field-sweep.ts` (`QUARANTINE_WINDOW_DAYS` constant + `registerFieldSweep(getExec)`),
node:sqlite + injected-clock test, and the App.tsx / database.ts wiring that registers it after
migration.
</objective>
