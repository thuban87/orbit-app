<objective>
Build the type-change layer (FLD-04): a read-only pre-flight that partitions a field's stored values
into convert-vs-flag using the target parser, and an apply step that is ONE `UPDATE custom_field_defs
SET type` plus a same-transaction `field_history` audit snapshot — with `contact_custom_values` never
touched.

Purpose: This is the phase's most-misread requirement. §14.2 + CLAUDE.md make it non-negotiable that a
type change has "blast radius zero" — it must NOT touch `contact_custom_values` at all. So "auto-convert
clean values" means: clean values are already VALID under the new type and render/sort correctly at read
time (via the widget + sortExpr); unconvertible values render a tap-to-fix error state on the profile.
Nothing is coerced or cleared. §14.6's "snapshot in the same transaction" is satisfied by writing a
field_history audit row for the pre-change state, still leaving stored bytes byte-identical. (This is
the CONTEXT-recorded reconciliation of the two spec clauses — enforcing the dominant invariant, not
reversing a decision. Surfaced for the owner's --to 3 review.)

Output: `src/db/field-type-change.ts` (preflightTypeChange, applyTypeChange), node:sqlite-proven,
including the load-bearing "values unchanged" invariant assertion.
</objective>
