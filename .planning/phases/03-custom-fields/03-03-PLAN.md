<objective>
Build the transactional DDL layer (FLD-02/03/05) and the field-definition metadata DAO. This is the
correctness core of the phase: creating, dropping, renaming, reordering, and quarantining a custom
field, each atomic and each serialized with the recency writers through the shared mutex.

Purpose: `contact_custom_values` is a real column per field. Creating one is `INSERT def + ALTER TABLE
ADD COLUMN` in one transaction; deleting a populated one is irreversible, so it is snapshot-to-history
then `DELETE def + DROP COLUMN` in one transaction, gated behind quarantine. These are the operations
whose atomicity the whole subsystem's data-safety depends on.

Output: `src/db/field-ddl.ts` (createField, dropField, deleteOrQuarantineField) and
`src/db/field-defs-dao.ts` (renameField, reorderFields, changeFieldOptions, quarantineField,
restoreField, listDefs, isFieldEmpty), both node:sqlite-proven.

Reuse-not-rebuild: copy the `inWriteTransaction` helper VERBATIM from recency-dao.ts (withMutex +
hand-rolled BEGIN/COMMIT/ROLLBACK preserving the original error). NEVER use expo
`withTransactionAsync` (Phase-2 pitfalls P3/P4). Take `exec: SqlExecutor` as the first argument so
every op stays node-testable.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user field def → DDL/SQL | Label, options, and the generated col_name cross into DDL (`ADD/DROP COLUMN`) and def-table writes. |
| quarantine expiry → irreversible DROP | A populated field's data is destroyed by DROP COLUMN; recovery exists only via the field_history snapshot. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | createField / dropField / isFieldEmpty col_name interpolation | high | mitigate | Only a whitelist-constructed col_name is interpolated (double-quoted), re-checked with isSafeColName before every ALTER; all other values `?`-bound. |
| T-03-02 | Denial (data loss) | dropField ordering | high | mitigate | Snapshot to field_history BEFORE DROP COLUMN in the same txn; immediate delete never offered for a populated field (quarantine first). |
| T-03-03 | Integrity | orphan def/column | medium | mitigate | createField's INSERT+ADD and dropField's DELETE+DROP are each one atomic transaction (both or neither); rollback test proves it. |
| T-03-05 | Denial (data loss) | index/UNIQUE on value column | medium | mitigate | Value columns declared TEXT with no index/UNIQUE; a populated-field DROP-succeeds test would fail if one existed. |

No package installs (phase adds zero dependencies) — no supply-chain checkpoint applies.
</threat_model>
