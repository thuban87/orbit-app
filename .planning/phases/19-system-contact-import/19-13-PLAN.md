<objective>
Close GAP B (IMP-02, failed verifier truth 2): the editable birthday field in the single-import
review accepts arbitrary text, and `importContactRecord` writes any non-null `params.birthday`
straight into `UPDATE contacts SET birthday = ?` with no validation — bypassing the shared
`isValidStoredBirthday` gate the picker mapper already uses. A malformed birthday can be reported
as a successful import.

Two layers, one shared gate:
1. **Persistent boundary (primary fix):** validate the birthday at the DAO write in
   `importContactRecord` using the SAME `isValidStoredBirthday` gate; reject invalid non-null
   values with a typed error rather than persisting or silently clearing them.
2. **Review surface:** validate/normalize the review-screen birthday input through one shared
   normalizer, show an inline error, and block Import while the input is non-empty and invalid.

Purpose: A "safe import" must never persist a malformed stored birthday. This restores the single
persistent validation boundary for `contacts.birthday` on the import path.
Output: A validated DAO boundary, a shared edited-birthday normalizer, a review error state, and
node tests covering malformed-rejected and valid-year-unknown-accepted at both surfaces.

**Same-table-writer note (verified on disk):** the runtime writers of `contacts.birthday` are
`imported-contact-dao.ts` (import — the unvalidated one, this fix), `source-consolidation.ts`
`combineCluster` (already validates via `isValidStoredBirthday` at line 191 — leave it, it is the
consistency template), and `contacts-dao.ts` `updateContact` (the Phase-4 edit path, fed by a
constrained date PICKER via `buildBirthdayForStorage`, so it cannot emit arbitrary text — out of
scope, do not touch). The import review is the only free-TEXT birthday source, which is why the DAO
gate is the import path's safety net.
</objective>
