# Forensic Report: Phase 30 System-switch animation downgrade

**Investigated:** 2026-09-09
**Scope:** Decision record -> Phase 30 specifications -> plan revisions -> execution -> code review -> verification/UAT
**Mode:** Read-only investigation. No application source, configuration, or existing planning artifact was changed.

## Verdict

The owner-approved animation did not disappear from the original planning record. It survived verbatim into the Phase 30 UI contract. It was weakened during cross-AI plan review cycle 2, when the existing Phase 29 fade/shrink/grow continuity transition was incorrectly classified as already providing Phase 30's "shedding/capture" animation. The resulting replan removed the explicit entering/leaving choreography and instructed execution to modulate the existing transition instead.

The executor then implemented the weakened plan faithfully but minimally: a 260 ms existing fade/grow transition, a small reversible per-body rotation capped at 0.22 radians, and a slight progress-curve adjustment. No entering contact streams inward and no leaving contact peels or scatters away. The implementation therefore cannot produce the decided choreography.

A separate integration defect initially prevented even that weak transition from appearing: the System store cleared the outgoing scene during loading, unmounting `OrreryWorld`, the sole transition owner. Commit `942c1bb` fixed that lifecycle defect. Once fixed, the owner could see the weak implementation that had been hidden underneath.

## Ground truth: the behavior was not ambiguous

- `docs/dossier/milestone-2/phase-09-orrery-systems-dossier.md:462-483` marks the visual model `[DECIDED]`: rotational impulse; nonmembers shed/peel away; retained contacts persist; new contacts stream/capture inward; geometry settles; intensity follows membership delta. Only exact spin count, velocity curves, particles/light streaks, timings, and easing are implementation/device-tuning.
- The same dossier explicitly separates the phases: Phase 29 may use a simpler functional transition; Phase 30 owns polished spin/shedding/capture.
- `.planning/phases/29-orrery-camera-scale-exploration/29-UI-SPEC.md:117` defines the Phase 29 transition as restrained fade/shrink/settle and explicitly says not to introduce the later spectacle.
- `.planning/phases/30-orrery-systems/30-UI-SPEC.md:234-235` preserves the decided behavior: narrowing sheds nonmembers, expanding streams new members inward, retained members provide continuity, and Reduced Motion alone gets the simple crossfade/reposition.
- `.planning/REQUIREMENTS.md:140,161` independently preserves the boundary: ORRC-11 is restrained continuity; ORRS-13 is spin + shedding/capture.

Conclusion: describing this as ambiguity was incorrect. The visual behavior was explicit; only tuning was open.

## Where it went off the rails

### 1. Initial Plan 30-10 was under-specified, but had not yet erased the contract

Commit `e3de53e` created Plan 30-10. It repeated "spin + shedding/capture" but did not decompose the visible choreography into concrete entering, leaving, and retained-body trajectories. Its automated coverage was pure membership-delta/focus math plus grep/color gates; visual correctness was deferred to Pixel UAT.

This was the first process weakness: the plan named the outcome without making the distinct motion phases executable or testable.

### 2. Cycle 1 corrected the weakness

The first plan review correctly flagged that the declared file set could not render per-body shedding/capture. Replan commit `a6f4d02` added `OrreryWorld` and an explicit transition contract:

- entering and leaving member ID sets;
- leaving contacts fade/scatter out;
- entering contacts stream inward;
- retained contacts maintain continuity;
- membership delta scales the drama.

At this revision, the plan was materially aligned with the owner's decision.

### 3. Cycle 2 made the semantic substitution

Cycle 2 asserted in `.planning/phases/30-orrery-systems/30-REVIEWS.md:499` that `orrery-frame.ts` "already sheds/captures on generation change." At line 522 it directed the replan to drop the entering/leaving contract and pass only switch intensity plus a spin term. The detailed finding at line 789 equated these existing behaviors with shed/capture:

- leaving: opacity -> 0 and radius -> 75% at the same interpolated position;
- entering: opacity 0 -> 1 and radius 75% -> 100% at its final destination position.

That equivalence was false against both the code and the decision record. Phase 29's code comment says new entries begin at their resolved position; it contains no inward stream, outward peel, scatter trajectory, staged rotational impulse, or capture path. Phase 29's UI spec explicitly labels it non-spectacle continuity.

The review was trying to avoid a technically risky duplicate animation pipeline. Avoiding duplication was reasonable; declaring the old transition semantically complete was not. The correct response was to extend the existing transition data model with real entering/leaving trajectories, not remove those trajectories from the plan.

Replan commit `008fc2e` incorporated the mistaken finding. Final Plan 30-10 explicitly says:

- the existing pipeline "already derives shed/capture";
- do not add entering/leaving ID-set choreography;
- add only intensity modulation and a per-body spin;
- preserve existing opacity/radius ownership.

This is the first artifact where the approved behavior was concretely weakened into the shortcut that shipped.

### 4. Later review cycles ratified the mistake instead of rechecking the canonical contract

Cycle 3 states that the replan "fully landed" and that Plan 30-10 correctly modulates the existing shed/capture pipeline. Subsequent cycles worked on focus/Home framing, selection ownership, reload gating, and persistence races. None revisited whether Phase 29 fade/grow actually satisfied Phase 30's visible choreography.

The plan kept the words "spin," "shed," and "capture," so requirement traceability looked intact while their meaning had changed underneath. This is semantic token compliance: the labels survived, the decided behavior did not.

### 5. Execution implemented the weakened plan

Commit `b74c230` made only 62 lines of animation-related changes. The resulting code:

- keeps `WORLD_SETTLE_MS = 260`;
- starts entering bodies at their final x/y, 75% radius, opacity 0;
- leaves departing bodies at their current x/y while shrinking to 75% and fading out;
- rotates contacts by at most `0.22` radians (~12.6 degrees), alternated by contact ID, then reverses to rest;
- changes sampled progress by at most `0.075 * intensity`.

There is no spin-up/cruise/slowdown choreography, no orbital peel-off path, no offscreen or outward shedding, no inward capture path, and no staging between retained/leaving/entering groups. The owner's report that bodies appear in two or three steps is consistent with this implementation: the only meaningful membership animation is a short opacity/radius interpolation at final coordinates while the scene/Home camera changes.

The executor summary nevertheless marked `requirements-completed: [ORRS-12, ORRS-13]` and described the result as a "membership-delta-scaled Skia spin/shed/capture transition," while also acknowledging that physical Pixel judgment remained required. That completion claim was stronger than the evidence.

## Why the gates did not stop it

### Plan verification checked wiring and vocabulary, not choreography

Final Task 3's automated gate was `npm run check:colors`. Its acceptance checks grepped for `beginWorldTransition`, `sampleWorldTransition`, `switchIntensity`, and `spin`, and explicitly checked that no entering/leaving prop existed. Those gates prove architectural wiring and enforce the downgraded design; they do not prove the approved animation.

### Unit tests proved only small mathematical properties

- `orrery-frame.test.ts` proves zero intensity is unchanged, midpoint coordinates differ, and the spin returns to rest at progress 0 and 1. It does not assert direction, travel distance, stages, duration, velocity profile, inward capture, outward shedding, or visible delta scaling.
- `orrery-frame-mapper.test.ts` proves the compiled Reanimated closure runs and republishes. It does not evaluate appearance.
- `orrery-switch-animation.test.ts` proves membership-delta arithmetic and a bounded scalar intensity. It does not prove how that scalar affects bodies.

### Code review audited robustness, not conformance to the visual contract

The post-execution deep review listed the relevant plan, renderer, frame logic, store, and screen, but its final report found only an unrelated delete/Undo recovery issue. It did not compare body trajectories to the dossier/UI-SPEC or flag that entering bodies began at their destination and leaving bodies never peeled away.

### Formal verification did not falsely pass the visual behavior

`30-VERIFICATION.md:68,99,143` correctly left the switch presentation behavior unverified/NEEDS HUMAN. It proved only that delta data reached the rendered-motion path. This gate was honest, but too late to prevent the executor summary from claiming ORRS-13 complete.

### UAT exposed rather than approved the failure

`30-UAT.md:39-42` left the switch test pending, explicitly reserving comparative membership-delta motion feel for owner review. The owner's testing then identified the mismatch. The UAT process did not approve the shortcut; it was the first gate capable of seeing it.

## The separate blocker that hid the downgrade

The Phase 29 System store, introduced in commit `1d4bbe0`, set `snapshot` to `null` during a different-System load. `OrreryScreen` conditionally renders `OrreryWorld` from that snapshot, so a real switch unmounted the only object holding the outgoing world and transition shared values. The destination mounted already settled.

Plan review noticed that the null loading state complicated membership-delta calculation, but prescribed stashing source IDs only. It did not reason through component ownership and keep the outgoing renderer mounted. Plan 30 execution therefore composed an animation signal over an incompatible lifecycle.

The later debug investigation and commit `942c1bb` preserved the outgoing snapshot during loading and added a regression test. That fixed the blocker, not the choreography. The current weak animation becoming visible after that fix is expected.

## Root causes

1. **Primary — semantic decision loss in cycle-2 plan review.** A reviewer/orchestrator treated Phase 29 fade/shrink/grow as equivalent to the explicitly later, polished shedding/capture behavior and revised the plan accordingly.
2. **Primary — visual behavior was not decomposed into enforceable motion contracts.** The plan lacked explicit phase/state/trajectory requirements after cycle 2, allowing a tiny reversible rotation plus opacity/radius interpolation to satisfy its text.
3. **Contributing — token-based traceability.** "Spin/shed/capture" remained in headings, must-haves, summaries, and requirement mappings, concealing that their operational meaning had changed.
4. **Contributing — manual-only visual acceptance at the end.** No executable trajectory assertions, deterministic animation snapshots, or mandatory pre-completion Pixel evidence guarded ORRS-13.
5. **Contributing — subsystem lifecycle coverage gap.** Store tests, renderer tests, and transition tests were separate; none asserted that a real System selection preserved one `OrreryWorld` instance across loading into the next generation.
6. **Contributing — completion was claimed before human judgment.** The executor marked ORRS-13 complete while its own coverage metadata said physical Pixel judgment was still required.

## Responsibility chain

- **Owner record:** correct and explicit.
- **UI specification:** correct and explicit.
- **Initial plan:** too vague to guarantee the behavior.
- **Cycle-1 review/replan:** corrected the renderer scope and added real entering/leaving choreography.
- **Cycle-2 review/orchestrator:** introduced the decisive downgrade by falsely equating Phase 29 continuity with Phase 30 shed/capture.
- **Cycle-2 replan and later review cycles:** encoded and ratified that downgrade.
- **Executor:** implemented the downgraded contract and overstated it as ORRS-13 complete.
- **Code review:** missed the contract mismatch.
- **Formal verifier/UAT:** did not pass the visual behavior; both left it for human review, where the failure was found.

## Process remedies

1. Treat `[DECIDED]` visual verbs as behavioral invariants. A reviewer may change architecture but must preserve observable motions; any weakening must stop for owner approval.
2. Require every polished animation plan to specify a state/phase model: source state, rotational acceleration, departing trajectories, retained-body continuity, entering trajectories, settling/deceleration, interruption behavior, and Reduced Motion replacement.
3. Ban semantic satisfaction by naming: a plan/review cannot call an existing primitive "shed/capture" without mapping each decided observable to code behavior.
4. Do not mark a human-judgment requirement complete until the required physical-device test passes. Use `implemented_needs_human`, not `requirements-completed`.
5. Add deterministic tests for trajectory properties even when fluidity remains manual: entering bodies begin outside/inward of final orbit and move inward; leaving bodies move outward/peel while fading; retained bodies remain continuous; intensity changes displacement/duration/velocity, not only a scalar in wiring.
6. Add an integration contract covering selection-store loading publication through persistent `OrreryWorld` ownership. The new store regression guards the specific lifecycle blocker, but a renderer-level ownership test would protect the whole seam.

## Confidence

**High.** The downgrade is visible in committed plan history, the review directive, the final plan's prohibitions, the executor commit, and the current motion equations. No inference about hidden agent intent is required.
