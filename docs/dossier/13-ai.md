# Dossier 13 — `ai` — AI message suggestions

**Status:** complete · Interrogated 2026-08-14 · 9 questions over 4 rounds · No `[OPEN]` items remain

## Scope

The optional AI feature: a user picks a contact (or opens the compose screen) and Orbit
sends structured context about that contact to a **user-configured** provider, returning a
short check-in message. This is the app's **sole network egress** (HANDOFF §3). The plugin's
`AiService.ts` (540 lines, 5 providers) ports nearly as-is — `requestUrl` → `fetch` — but its
prompt system extracted arbitrary markdown sections from note bodies (`{{Heading}}`), which no
longer exist, so the prompt context is rebuilt from structured data (fuel, log aggregates,
fields). This domain decides: providers on mobile, credential storage & security posture, the
prompt context and template, where "AI Suggest" is invoked and what a suggestion does, and the
BYO-key ↔ monetisation tie-in (HANDOFF open question #1).

**Much of the AI privacy boundary is already decided upstream and is NOT reopened here** — see
"Inherited (already-decided) constraints" under Findings.

## Decisions

### Cluster A — Invocation & result surface

**[DECIDED] "AI Suggest" is invokable from BOTH the in-app compose screen (primary) and the
contact profile.** The compose screen is the reminder→send collapse (a decay notification or
the widget's Message action opens it with fuel visible); the profile hosts browse-initiated
drafting. One generation path, two entry points.
Rationale: the compose screen is where a suggestion turns into a sent message with fuel still
in view — the friction collapse HANDOFF §6 exists for. But suggestions are also wanted when
just browsing a contact (the plugin's Hub model), so the profile keeps an entry point.
*Consequence:* a profile-invoked suggestion routes into the compose screen (the editable-draft
surface); it does not need a second result UI. **[REJECTED] Compose-only** (can't suggest
while browsing); **[REJECTED] Profile-only** (loses the reminder→send collapse the mobile
compose screen was built to deliver).

**[DECIDED] A returned suggestion becomes an EDITABLE DRAFT on the compose screen; the user
edits it and taps Send, which hands off to the SMS composer. Copy-to-clipboard is the reliable
fallback.** Not the plugin's decoupled Copy/Regenerate/Dismiss card.
Rationale: mobile-native and collapses to send. **Recorded platform caveat, load-bearing:**
03-fuel F8 — an Android SMS app is only required to *open* on a `SENDTO` intent, not to honour
a prefilled body, so the draft handed to the SMS composer may silently arrive empty. Copy is
therefore not decoration; it is the only guaranteed handoff and must always be present.
**[REJECTED] Standalone card / manual paste** (plugin parity — loses the send integration);
**[REJECTED] Generate 2–3 variants** (more API calls per use; not chosen for v1, addable later
since it needs no schema).

### Cluster B — Prompt context & template

**[DECIDED] §14 custom fields reach the prompt only when the user opts a field in, via a new
per-field "shareable with AI" flag.** Default off. Un-flagged fields never leave the device.
Rationale: the owner chose the middle ground over blanket inclusion (too broad) and blanket
exclusion. It respects 01-data's reasoning for rejecting category-as-a-custom-field (the prompt
should not silently depend on any field the user can quarantine/delete) while still letting
genuinely useful facts (Pets, Kids, Job) inform a suggestion when the user says so.
*Mechanics recorded:* flagged fields are exposed to the global template as placeholders **bound
to `col_name`** (survives §14 rename) and **displayed by label** (F-AI-4). Quarantining or
dropping a flagged field degrades gracefully through 03-fuel Cluster E's existing rule — the
template editor flags placeholders that matched nothing, and an unmatched placeholder resolves
to `None available` (can only ever send *less*), so **no new §14 quarantine-time surface is
strictly required** (note it anyway to the fields/crud phases).
**[REJECTED] All custom fields reachable** (widens egress to arbitrary fields; needs a
quarantine warning surface); **[REJECTED] No custom fields at all** (loses genuinely useful
context the owner wanted available under his control).

**[DECIDED] One global, user-editable prompt template.** Plugin parity, with the default
rewritten from the structured context (the shipped default references dead sections). The
raw-template power-user surface ("make it sound like you") is preserved.
Rationale: templating was already decided to survive (03-fuel Cluster E); the owner kept it as
a single global template rather than fragmenting it. The default must enumerate the new
structured placeholders (fuel by kind, aggregates, gravity tier, intensity, quality) — its
exact wording is a design/taste item for the phase.
**[REJECTED] Per-category templates** (more surface; the prompt can already vary tone by
category in prose); **[REJECTED] Toggles-only** (loses the raw voice-matching the plugin's
users relied on).

### Cluster C — Providers, endpoints & the LAN boundary

**[DECIDED] All three cloud providers ship in v1: OpenAI, Anthropic, Google Gemini.** Ollama
was already cut (03-fuel). Platform-verified 2026-08-14: all three endpoints and request/
response shapes are current; OpenAI Chat Completions is not deprecated (Responses API only
*recommended* for new projects); Anthropic `anthropic-version: 2023-06-01` is still current.
**Only one dead model ID:** Anthropic `claude-sonnet-4-20250514` — retired; swap for
`claude-sonnet-4-5-20250929` or `claude-sonnet-5`. The other five hardcoded IDs and all three
endpoints/headers still work as written.

**[DECIDED] The Custom OpenAI-compatible endpoint is kept, but HTTPS-only.** OpenRouter and a
TLS self-host remain possible.
Rationale, and this is a deliberate boundary: allowing a plain-`http://` LAN endpoint would
**(1) reopen the zero-egress LAN path the owner explicitly [REJECTED] for Ollama** (03-fuel
Cluster E) and **(2)** force app-wide `usesCleartextTraffic: true` (`expo-build-properties`),
weakening the entire app's network posture — an arbitrary user-typed IP can't be pre-listed in
a per-domain `network_security_config.xml`. HTTPS-only avoids both. **The OpenAI-compatible
`{model, messages, temperature}` → `choices[0].message.content` contract is still the de-facto
2026 interop standard** (verified), so the feature stays valid.
**[REJECTED] Drop Custom entirely** (loses OpenRouter / self-host); **[REJECTED — flagged,
risk-posture reversal] Allow http:// LAN Custom** (reopens declined LAN egress + global
cleartext weakening).

**[DECIDED] Models are chosen by dynamic fetch from each provider's list-models endpoint.**
All three expose one (`GET /v1/models` for OpenAI & Anthropic; `GET /v1beta/models?key=` for
Gemini).
*Mechanics recorded:* **Gemini's list returns embeddings/image models too — filter on
`supportedGenerationMethods` containing `generateContent`** (verifier). The AI settings screen
is not a read path, so a network call there does not violate HANDOFF §3's offline rule — **but
the fetch must fall back gracefully** (offline / bad key) to a **free-text model-ID entry** so
a user is never blocked. The **HTTPS Custom endpoint keeps the plugin's single free-text
model-name field** (no guaranteed list endpoint). Dynamic fetch structurally prevents the
stale-hardcoded-list bug that killed the Sonnet 4 option.
**[REJECTED] Curated hardcoded list** (rots — the exact bug just found); **[REJECTED]
free-text-only** (user must know the current ID).

### Cluster D — Credentials, security & monetisation

**[DECIDED] API keys are excluded from the JSON backup/export. The user re-enters each provider
key once on a new device.**
Rationale: the export is meant to be safe to store in cloud/email/share; live credentials in
that file would defeat that. Keys are cheap to re-enter. Reinforced by platform fact — a
Keystore-backed key is deleted on uninstall and cannot ride an Android auto-backup regardless,
so "include" would mean the app *deliberately* copying the secret into the export payload, which
is the exact risk being avoided. Domain 15's export-encryption decision does not change this;
excluding is safer either way.
**[REJECTED] Include keys in export** (device-migration convenience at the cost of credentials
in a user-held, possibly-unencrypted file).

**[DECIDED — HANDOFF open Q1, AI half] AI is free and BYO-key in v1; monetisation is deferred.**
No entitlement check and no IAP plumbing around the AI feature in v1. Because the user pays the
provider directly, there is no server cost forcing a subscription, so nothing about the AI
architecture depends on the monetisation model. HANDOFF Q1 stays open and can be decided later
with **no AI rework**.
**[REJECTED for v1] AI as the paid tier** — a one-time purchase gating AI would add IAP + an
entitlement check now, scope the owner chose not to take on in v1. Still available later since
BYO-key means the gate would be a simple entitlement wrapper, not a re-architecture.

## Cross-domain constraints exported

- **[ai → fields / crud]** `custom_field_defs` gains a **`share_with_ai`** flag (default
  **false**). The field editor (06-crud / 02-fields surfaces) needs a per-field toggle. The AI
  prompt binds flagged fields to **`col_name`** (rename-safe) and displays them by **label**.
  This is a column on the *defs* table (one row per field), **not** `contact_custom_values`, so
  CLAUDE.md's index/DROP-COLUMN rules are untouched. Add it in migration 1 or a later defs
  migration — no data-integrity reason it must be migration 1.
- **[ai → backup (15)]** **API keys are NEVER exported** (stored in `expo-secure-store`,
  re-entered per provider on a new device). The **exportable** AI settings are the non-secret
  ones — provider, model, prompt template, HTTPS custom-endpoint URL, and the `share_with_ai`
  field flags — which live in the SQLite settings, not the Keystore.
- **[ai → compose screen (unowned) / notify (11) / widget (12)]** The compose screen must host
  an **"AI Suggest"** affordance that produces an **editable draft**; **Copy is the guaranteed
  handoff** (SMS prefill via `sms_body` is unreliable — 03-fuel F8). AI is a **second consumer**
  of the still-unowned compose screen (11-notify and 12-widget already deep-link to it). The
  **contact profile** (also unowned) is the second AI-Suggest entry point.
- **[ai → data]** AI introduces **no new per-contact columns**. It reads recency from the newest
  interaction row via the single query 04-log already mandated, and flagged custom-field values
  by `col_name`. AI *writes* only through already-decided paths: `source='ai'` fuel proposals
  (03-fuel, excluded from prompts until confirmed) and — if ever adopted — `source='ai'`
  interaction rows (04-log; see deferred).
- **[ai → data / crud]** The **HTTPS-only** rule for the Custom endpoint is a security-posture
  boundary: it must be validated at entry (reject `http://`), and the app must **not** enable
  `usesCleartextTraffic`. This keeps the declined LAN zero-egress path closed (03-fuel Cluster E)
  and preserves the whole app's network posture.
- **[ai → planning]** Port hazards to carry into the phase: **`fetch` does not reject on 4xx/5xx**
  (every `generate()` path needs an explicit `response.ok` throw, or a bad key becomes a generic
  parse error); **AbortController** for a Cancel button is usable but **unverified on-device**
  for `expo/fetch` (RN-core has open defects) — spike it; **no built-in fetch timeout** (manual
  `AbortController` + `setTimeout`, not `AbortSignal.timeout()`); **redact the assembled-prompt
  debug log** (`AiService.ts:139` writes fuel-bearing prompts to logcat).

## Decisions made without you

Orchestrator's picks on items with no articulable divergence. **Read each as the decision AS
ADOPTED.** Veto any cheaply at review.

1. **API keys are stored in `expo-secure-store` WITHOUT `requireAuthentication`.** Secure-store
   is the only Expo-endorsed mechanism (plaintext-in-SQLite is discouraged); `requireAuthentication`
   is omitted because a fingerprint change would then silently invalidate a stored key — wrong
   trade for a low-friction API key.
2. **AI defaults to disabled (provider = `none`), opt-in.** Ports the plugin's default. The
   first-enable one-time notice and the per-provider first-send prompt preview (03-fuel Cluster E)
   both stand.
3. **All contacts are eligible for AI Suggest**, including never-contacted and rogue; thin
   context is handled by the prompt, not by gating the button.
4. **Flagged custom fields are exposed to the template as placeholders** (bound to `col_name`,
   shown by label), resolving through 03-fuel Cluster E's existing resolver and its
   unmatched-placeholder warning — so quarantining/dropping a flagged field degrades gracefully
   with no new §14 surface.
5. **Non-secret AI settings are exportable; only keys are excluded** (the split that makes the
   backup safe to share).

### Inherited (already-decided) constraints — binding, NOT reopened here

From **03-fuel** (Cluster E and exports):
- **No local/Ollama provider on mobile → no zero-egress mode.** LAN Ollama was **[REJECTED]**
  (owner call). Every AI use ships fuel to a third party.
- Free-text prompt placeholders survive, resolved against **fuel kind names and per-item
  labels**; the template editor flags placeholders that matched nothing.
- The assembled prompt is **shown before the first send to a given provider**; a settings
  **inspector always shows exactly what a request contains**; after the first send, direct.
- `off_limits` fuel is **never transmitted** and absent from the placeholder resolver's search
  space. Fuel **age** must reach the prompt.
- AI may **propose fuel items** (`source='ai'`, rendered unconfirmed, **excluded from prompts
  until confirmed**). Article summarisation at capture is **[REJECTED for now]** (would widen
  egress to third-party article bodies).

From **04-log** (Cluster D and exports):
- Interaction history reaches the prompt as **AGGREGATES ONLY** — counts, cadence, quality
  summary, `gravity` tier name, `intensity`. **No interaction note text is ever transmitted**
  (an interaction row has no `off_limits` analogue).
- The channel fact comes from the **newest interaction row via a single query**, handling
  `unspecified` explicitly and tiebreaking `occurred_at DESC, id DESC` (fixes 01-data's F5).
- `interactions.source` includes an `ai` value (for if an AI-drafted send ever writes a row).

### Port hazards (verified in prior workpapers, carried forward)
- `fetch` resolves on 4xx/5xx; `requestUrl` did not — the ported `generate()` paths must add
  explicit `response.ok` handling or "invalid key" becomes a generic parse error.
- `fetch` brings `AbortController` → a real Cancel button, which the plugin lacked.
- The plugin's hardcoded model lists are ~a year stale (`AiService.ts:233-237,289-292,345-348`)
  and several IDs are likely dead — platform-verified this run (see workpapers).
- `AiService.ts:139` writes the fully-assembled prompt (fuel included) to the debug logger —
  on Android that lands in logcat/Metro. Redact or drop on port (on-device disclosure).
